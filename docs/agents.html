Technical Documentation

The AONIK Agent Platform

AONIK is an AI-native financial platform. Its agents are how users accomplish work in natural language — they read state, reason, and propose actions across billing, the ledger, payments, and personal finance. This document explains how agents are built, what they can do, where their prompts live, and — above all — the security boundary that guarantees an agent can propose a money movement but can never execute one without a validated human decision.

01Foundations

What agents are, and why they matter#

An AONIK agent is a large-language-model reasoner wired to a curated set of server-side tools (functions over the domain) and a system prompt that defines its role and constraints. Agents are the primary interface through which a user — an operator in the Admin UI, or a customer talking to Simi in Payabo — gets work done: "issue the invoice for order 1042", "why did my grocery spend jump last month", "schedule a reminder for my rent".

Agents matter because AONIK is not a chatbot bolted onto a ledger; the agent layer is a first-class part of the platform. It is the place where unstructured human intent is turned into structured, audited, policy-checked financial operations. That makes the agent layer a security surface as much as a product surface — which is why most of this document is about the controls around what an agent is allowed to do.

The five non-negotiable principles

Every design decision in the agent layer flows from these platform rules:

⚖️

Agents propose; systems execute

An agent never bypasses human-in-the-loop for a mutation. Sensitive actions are marshalled into durable proposals and executed by the platform, not the model.

📒

The ledger is financial truth

Double-entry, immutable. Agents read and propose; they do not write the ledger directly. An order is the canonical record of a requested service, never collapsed into a payment.

🧾

Every AI action is auditable

Each model call is recorded as an AiRun; every classified mutation persists a durable approval record. Nothing the agent does is off-the-books.

🎚️

Risk tier determines autonomy

A reversible note can run inline; an everyday domain write needs a confirm; moving money always becomes a proposal. The tool's risk tier — not the prompt — decides.

The organising idea

“Agents propose; systems execute” is enforced structurally, in server code, not by asking the model nicely in a prompt. Even a jailbroken or buggy model cannot move money in-band: the code path that would call a payment service simply does not exist inside the agent's tool invocation for a high-risk action. The rest of this document shows how.

02Foundations

Architecture at a glance#

Runtime foundation

Agents are built on the Microsoft Agent Framework (MAF) (Microsoft.Agents.AI) layered over Microsoft.Extensions.AI. The concrete agent type is ChatClientAgent — an AIAgent that wraps an IChatClient, a set of AITool / AIFunction tools, and its instructions. MAF runs the tool-call loop internally; AONIK contributes the tools, the prompts, the governance, and the security gate.

Accuracy note

Semantic Kernel appears in the platform's tech-stack table, but the live agent path uses MAF + Microsoft.Extensions.AI exclusively. There is no Semantic Kernel in the request hot path. (See ADR-004.)

Where agent code lives

The agent layer is deliberately spread across modules so that domain modules own their agents without depending on the agent runtime. The contract lives in SharedKernel; modules contribute descriptors; the Agents module orchestrates; the Ai module governs models, prompts and audit.

03Foundations

The agents themselves — what they can do#

A domain agent is defined by an IDomainAgentDescriptor: a name, a description, its instructions, the tools it builds, and an AgentType (SubAgent — invoked as a tool — or Orchestrator — routes user turns). Descriptors are registered as singletons by their owning module and discovered by the runtime through IEnumerable<IDomainAgentDescriptor> injection. These are the agents that ship today:

AgentTypeWhat it doesTool families
finance-agent SubAgent B2B billing, ledger and payments. Create / issue / cancel / query invoices; create ledgers & accounts; manage payment-intent lifecycle. Invoice · Ledger · Payment
financial-life-graph-agent SubAgent Read-only traversal and retrieval over the Financial Life Graph — holistic views, relationship and impact queries. FLG schema · traversal · retrieval
personal-finance-agent “Simi” Orchestrator The user-facing Payabo companion: accounts, transactions, bills, budgets, goals, insights, orders, linked accounts. Requires a User Brief. PersonalFinance · AccountLinking · Memory
pf-insights SubAgent “Why / what / rank” spending analysis with exact arithmetic. Structured-output, CodeAct-capable. Invoked by Simi via pf_run_insights. Insights slice

pf-classify SubAgent Walks the categorisation review queue at scale; proposes corrections and rules. Structured-output. Invoked via pf_run_classify_review. Classify slice
platform-agent SubAgent Read-only identity & governance: tenants, users, roles, permissions, compliance documents. Tenant · User · Compliance
Spec 025 — CodeAct sub-agents

The pf-insights, pf-forecast and pf-classify agents are the “split” of the old monolithic personal-finance reasoner. Each returns schema-bound JSON and can use a CodeAct execution slice to do exact numeric work in code rather than free-form arithmetic in the prompt — the right design for money math.

Agent-as-tool routing

In the orchestrator pattern, each domain agent is built, instrumented with an OpenTelemetry invoke_agent span, and exposed to the top-level agent as a callable function. The orchestrator's LLM reads its routing instructions and decides which specialist to call; results are synthesised back into one answer. Cross-cutting tools the user always needs — long-term memory, document search (RAG-by-default), and reminders — are attached directly to the orchestrator rather than buried in a sub-agent. The memory and retrieval machinery is detailed in §11.

04Foundations

Anatomy of a run#

The production entry point is the AG-UI streaming endpoint POST /ai/agui, an SSE stream that emits message, tool-call and voice events as the model produces them. The endpoint itself is deliberately thin; it composes a set of small services.

Run lifecycle · POST /ai/agui
1
Voice-mode pre-flight
Validate before any SSE byte is written, so a bad request fails cleanly.
2
Resolve thread & agent
Ensure/created the chat thread; resolve the target agent by AgentId (or fall back to the orchestrator). Stamp OpenTelemetry session/user baggage for trace grouping.
3
Assemble messages
Reconstruct history, convert messages, and — for agents that require it — prepend the User Brief system message as ground-truth context.
4
Build run options
Combine client tool declarations with the per-agent model override into ChatClientAgentRunOptions.
5
Stream the model run
AIAgent.RunStreamingAsync(...) drives the model. MAF runs the tool-call loop internally; the pipeline translates each chunk — text, tool call, tool result, reasoning, usage — into AG-UI SSE events.
✓
Finish & persist
Emit RUN_FINISHED with metrics, then on a detached scope persist the assistant turn, generate a thread title, and write the AiRun audit row (tokens, latency, use-case).

Conversation state is tracked by MAF AgentSessions keyed by thread; the agents themselves are stateless and cached after first build. When a gated tool is encountered during step 5, the stream surfaces an approval card instead of a result — that mechanism is the subject of §7.

05Behaviour

Prompts & instructions — where they live#

An agent's behaviour is shaped by instructions assembled from up to four layers at run time. Knowing where each lives is the key to changing behaviour safely.

1 · Code default
Each descriptor ships a default Instructions string in source — the canonical persona and constraints. Example below.
2 · DB override
An Agent config row (InstructionsText) can override the code default per-tenant or globally. A non-empty value replaces the code instructions. Resolution is tenant → global → code default.
3 · User Brief
For agents with RequiresUserBrief (today, Simi), a per-request system message carrying the user's current financial context is projected and prepended — “treat as ground truth for this session”.
4 · Tenant skills
Opted-in agents attach an AIContextProvider that injects tenant-uploaded Agent Skills (SKILL.md) via progressive disclosure. See §8.

A real domain-agent prompt

Instructions are written as structured, tagged prompts. This is the Finance agent's default, in FinanceAgentRegistration.cs — note the explicit constraints around destructive actions and never exposing internal errors:

You are the AONIK Finance Agent, a sub-agent responsible for B2B
financial operations within the AONIK platform.
</role>

<constraints>

  payment, mark paid), confirm the action with the user first by
  describing what will happen.

The orchestrator's routing prompt

The master orchestrator's instructions live as a constant in MasterOrchestratorService. They enumerate the domain agents, define routing rules, conversational pacing for voice, and the human-in-the-loop convention. Note that the prompt-level confirmAction guidance is now a presentation affordance — the real enforcement is the server gate (§7).

Ancillary prompts

Smaller LLM tasks that support agents — thread-title generation, conversation summaries, memory extraction, prompt-improvement, playground review — are not hard-coded. They live as seeded, tenant-overridable AiTask rows in the Ai module and are resolved per use-case (model + system prompt + user template) by IAiTaskProfileResolver, which resolves the tenant-specific override first, then the global AiTask row.

Configuring an agent without a deploy

Operators tune agents through the config endpoints — overrides are stored in the DB and resolved at the next build (cached ~60s):

  • PUT /ai/agents/configurations/{name} — set a tenant override: instructions, enabled-tools whitelist, model, risk tier, active flag.
  • POST …/reset-prompt and …/reset-toolset — revert to the descriptor defaults.
  • POST /ai/agents/improve-prompt — AI-assisted prompt refinement.
06Behaviour

Model governance#

No agent hard-codes a model. A model is resolved per use-case key ("orchestrator", "title-generation", a specific agent name) through IAiModelResolver, which consults an AiRoutePolicy table. Policies can be global or tenant-specific; a tenant policy wins over the global default, and the result is cached. This lets a deployment shift a use-case onto a cheaper or more capable model centrally.

ConcernMechanism
Which model for a use-caseAiRoutePolicy (UseCase → model, tenant-overridable) via IAiModelResolver. Managed at /ai/route-policies.
Model & provider catalogAiProvider / AiModel entities (context window, cost & latency profiles). Managed at /ai/providers, /ai/models, /ai/model-catalog.
Honouring a per-agent override inside the orchestratorModelPinningChatClient — see below.
Cost accountingAiCostCatalog per-token pricing; computed cost stamped on each AiRun and emitted as a meter.

Why ModelPinningChatClient exists

In the agent-as-tool pattern, when the orchestrator's LLM dispatches into a sub-agent, MAF invokes that sub-agent internally — there is no opportunity to pass run-time model options. Without intervention the sub-agent would silently inherit the orchestrator's model and the admin's per-agent override would be lost. ModelPinningChatClient is a thin DelegatingChatClient that forces the configured ModelId on every call; the sub-agent's chat client is wrapped with it at build time when an override exists. (On the single-agent path the model is instead stamped onto the run options directly.)

07Security · the centerpiece

The security model: agents propose, systems execute#

This is the most important part of the agent layer. Two specs combine into a single classification model selected by risk tier: in-band approval gating (Spec 023 / Spec 032) and durable proposal execution (Spec 030). The boundary is enforced in server code and fails closed.

The gate

Every agent assembles its tools through one seam: IToolApprovalGate.GateAll(...), called at agent-build time. The gate consults each module's IToolApprovalManifest to classify a tool, then:

  • Read-only (classified, or unclassified and not mutating-looking) → passes through unchanged.
  • Classified mutating → wrapped in ApprovalGatedAIFunction, an enforcing decorator that cannot execute ungated.
  • Unclassified but mutating-looking → throws ToolNotClassifiedException at build time. The agent will not start.
src/Aonik.SharedKernel/Agents/Approval/ToolApprovalGate.csfail-closed
public AITool Gate(AITool tool, IServiceProvider? serviceProvider = null)
{
    var classification = Classify(tool.Name);

    if (classification is null)
    {
        // No module claims this tool. Fail closed for anything that
        // looks like a mutation; let read-looking tools through.
        if (MutatingToolNameHeuristic.LooksMutating(tool.Name))
            throw new ToolNotClassifiedException(tool.Name);
        return tool;
    }

    if (classification.IsReadOnly) return tool;

    return new ApprovalGatedAIFunction(
        function, classification.Options!, _auditSink, serviceProvider);
}

“Mutating-looking” is a name heuristic (_create_, _capture_, _pay_, _transfer_, _refund_, _update_, _delete_, …). It is deliberately not the runtime authority — the manifest is. The heuristic only powers the fail-closed default and a lint test that asserts no mutation-verb tool is ever classified read-only.

The four classifications

Read-onlyNo state change

Queries: get_ / list_ / search_ / graph_. Not a tier — omitted from manifests entirely.

Runtime: executes directly, no ceremony.
LowReversible personal write

No financial or cross-party impact. e.g. user_memory_save, pf_reject_commitment.

Runtime: persists an audit record (best-effort) and runs in-band. Never blocks.
MediumEveryday domain write

Real, reversible state; no money movement. e.g. finance_create_invoice, finance_issue_invoice, all pf_create_*.

Runtime: refuses, persists a Pending request; runs in-band once after a validated human confirm.
HighMoney / ledger / partner

Moves money, posts to the ledger, or calls a partner. e.g. finance_capture_payment, finance_mark_invoice_paid.

Runtime: never runs in-band. Marshalled into a durable Proposal and executed by the dispatcher after approval.
The one-line routing rule (Spec 032 §4.1)

If a tool can move money, post to the ledger, or call a partner — it is High and must become a Proposal. Everything else that writes state is Medium, unless it is a trivial reversible personal-state write, which is Low. Anything not classified is treated as a mutation and the build fails. Tier is a floor, not a ceiling: a module may classify up (the shipped Finance manifest classifies finance_create_payment_intent as High).

Classification is a plain, ordinal name → tier dictionary per module:

src/Aonik.Finance/Agents/FinanceToolApprovalManifest.csclassification
// High — money movement / ledger posting / partner calls
["finance_capture_payment"]   = High("Finance.CapturePayment", ...),
["finance_mark_invoice_paid"] = High("Finance.MarkInvoicePaid", ...),

// Medium — everyday domain writes (no money movement)
["finance_create_invoice"]     = Medium("Create a draft invoice"),
["finance_issue_invoice"]      = Medium("Issue an invoice"),
["finance_create_ledger"]      = Medium("Create a ledger"),

The Medium flow — confirm, then run once

A Medium tool requires an in-session confirmation. The crucial property is that the approval is bound to the exact arguments the human saw, is single-use, and time-boxed.

Medium tier · multi-turn handshake
1
Model calls the tool → refused
The gate persists a Pending ToolApprovalRequest (tenant, user, tool, args-hash, 15-min expiry) and returns a requires-approval result instead of running.
2
Client renders an approval card
The stream emits a tool.approval.required event carrying the durable request id.
3
Human decides
POST /ai/tool-approvals/{id}/decide → DecideAsync validates identity, tenant, expiry (before status), single-use status, and that the decider is the requester. On approve it records the decision — it does not run the tool.
✓
Agent re-invokes → consumed
On the agent's resubmit, the gate finds the matching Approved row by args-hash, stamps ConsumedAt (single-use), and runs the inner tool exactly once.

The binding is a stable SHA-256 over canonicalised arguments — keys sorted, values serialised to JSON — so re-ordering can't change the hash, and changing an argument produces a different hash, no match, and a fresh Pending request. A decision can never authorise a call with different arguments:

…/Abstractions/Agents/ToolApprovalContracts.cs — ToolArgumentsHashreplay guard
public static string Compute(IDictionary<string, object?>? arguments)
{
    var ordered = new SortedDictionary<string, object?>(StringComparer.Ordinal);
    if (arguments is not null)
        foreach (var kvp in arguments) ordered[kvp.Key] = kvp.Value;

    var json  = JsonSerializer.Serialize(ordered);
    var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(json));
    return Convert.ToHexString(bytes);
}

The High flow — proposal & dispatcher

A High tool's inner function is never reachable from the agent. The gate serialises the model's arguments into a durable Proposal (status Proposed) plus a linked approval request, and returns a queued result. Execution happens only later, through the dispatcher:

model calls High toolfinance_capture_payment → durable ProposalProposed → human approvespolicy-checked → ProposalDispatcherkeyed by type → IProposalHandlerthe only money path

Approval (whether from the in-session card or the proposals queue) runs the same IProposalApprovalPolicy check and the same ProposalApprovalService.ApproveAsync — there is no fast lane. The proposal moves Proposed → Approved (the human decision persists independently of execution), then the dispatcher resolves a DI-keyed IProposalHandler by the proposal's type and calls the domain service. Handlers are idempotent (get-before-act; “already done” is success). Money safety is explicit in the status model:

StatusMeaning
ProposedMarshalled, awaiting a human. (Non-High failures revert here so “Approve again” is the retry.)
ApprovedA human authorised it — recorded before execution is attempted.
AppliedThe system executed it successfully (terminal).
FailedHigh-tier execution failed or was uncertain — terminal. A capture is never retried in place; recovery is a brand-new proposal, so funds can't double-move.
RejectedDeclined by a human (terminal). A rejected in-session High call also dismisses the proposal so it can't linger in the queue.

Surfacing approvals through the stream

When a gated tool returns its structured result rather than running, the pipeline emits a machine-parseable CUSTOM event (tool.approval.required for Medium, tool.approval.queued for High) carrying the durable id(s) the client needs to route a decision. Because a gated tool may run inside a sub-agent (whose result never reaches the top-level stream), the decorator also records each approval into a request-scoped notifier that the pipeline drains at end-of-run — so an approval card is never silently dropped on the orchestrator surface.

Security properties, summarised

Structural human-in-the-loop

Enforcement lives inside the tool's invocation, not in a prompt. A jailbroken or buggy host loop still cannot run a Medium/High mutation in-band.

Fail-closed everywhere

Unclassified mutation → build fails. Missing approval service, missing tenant, or High without a proposal type → refuse. The safe path is the only path.

Replay & single-use

Decisions are bound to an args-hash and consumed once (ConsumedAt). A decision can't be reused or repointed at new arguments.

Time-boxed

Pending approvals expire after 15 minutes; expiry is checked before status, so a stale approval is never consumable.

Tenant isolation

Requests and proposals are read through a fail-closed tenant query filter; a cross-tenant id simply returns “not found”. Write paths re-check tenant.

One decision authority

DecideAsync is transport-neutral — AG-UI, voice, and the playground all route through it. No transport decides whether a mutation runs.

Tenant-managed agent extensibility#

Spec 033 lets a tenant extend their agents with their own capabilities — without ever being able to add an ungated mutation. The governing idea: a tenant can add capability, but only a PlatformAdmin can approve anything that runs code, moves money, or opens a new network destination. Tenant-contributed tools flow through the same approval gate as built-ins.

The same gate, defaulting to High

A tenant tool is registered into a request-scoped classification store before it reaches the gate, and its risk is mapped fail-safe: a tenant cannot self-lower risk. Every tenant tool defaults to High in the database; only a PlatformAdmin review can set it to Medium or mark it read-only. Anything mutating-looking that somehow reached the gate unclassified still throws at build. So the worst a tenant can do unilaterally is add a tool that becomes a proposal — never one that runs money in-band.

Tenant isolation

All three entities are ITenantScoped and read through the fail-closed EF query filter (a missing tenant context exposes only global rows, never another tenant's). Runtime caches — MCP connections, materialised skills, the classification store — are keyed by tenant or scoped per-request, so there is no cross-tenant bleed. Names are unique per tenant, not globally.

Implementation caveats (this slice)

Skill script sandboxing is partial. The per-skill ScriptsEnabled and deployment-wide AllowSkillScripts flags are persisted and audited but not yet wired to a constrained script runner; today's enforced containment is the framework's always-on script-approval hook plus the rule that script-bearing skills never auto-approve.

Egress is a positive allow-list, not an IP/metadata denylist. SSRF containment rests on the curated host allow-list + HTTPS-only + final-URL re-check; there is no explicit private-IP / cloud-metadata (169.254.169.254) / DNS-rebinding check. Allow-list governance is an open decision in the spec.

A note on AgentRun

An AgentRun entity exists (goal, plan, steps, linked AI-run ids) and is surfaced read-only in the Admin UI, but it is currently populated only by the demo seeder — the live per-call audit trail is AiRun, not AgentRun.

Telemetry & the kill-switch

TelemetryChatClient is the single source the observability dashboard queries: per call it emits a structured log, a family of meters (latency, TTFT, tokens, estimated cost), and a Langfuse-style generation span. With sensitive-data capture enabled it serialises the full request/response — including agent tool schemas — into traces. A per-tenant kill-switch (TenantAgentSettings) is enforced in AiRunWriter.StartRunAsync: when engaged it throws before any model resolution or DB write, halting all AI for that tenant immediately.

Long-term memory

A memory is a UserMemoryEntry — a namespaced dot-key (finance.preferred_currency, identity.household_size, communication.reminder_time) with a JSON value, an EntryType (Identity, Preference, Correction, Fact), a Confidence, and a Source (UserStated / AiInferred). Entries are never deleted: an update supersedes the prior entry through a SupersededById chain, so the whole history stays auditable. Inferred entries decay in confidence over time (floored, then filtered); user-stated facts never decay.

Two backends sit behind one IUserMemoryService, chosen globally by the Ai.UserMemory.Backend setting:

SQL Server default

Durable relational store with the full supersede + decay model. Semantic search is a no-op stub — recall returns nothing, and the agent leans on the User Brief instead.

Qdrant semantic

Every entry is embedded and stored as a Qdrant point; CRUD, supersession and semantic recall all happen in vector payloads. This is what makes user_memory_recall meaningful.

The two memory tools an agent sees

user_memory_save
Low Persists a fact the user stated or a correction. The userId comes from authenticated context, never the model. No approval gate — the AG-UI stream is its audit trail. The orchestrator prompt explicitly forbids wrapping it in a confirm or delegating it to a sub-agent.
user_memory_recall
Read-only Semantic lookup the agent calls mid-conversation when the User Brief isn't enough. Guarded by a hard 2-second timeout that fails open to “empty”, so a slow or unreachable Qdrant can never stall chat.

Both tools live on SharedKernel and self-disable if their providers aren't registered, so any agent can attach them. Today the master orchestrator and Simi both do.

Where Qdrant fits

Qdrant is AONIK's vector database, reached through QdrantVectorStore over a hand-rolled REST client (QdrantHttpClient — no vendor SDK; cosine distance). It is the backend for both user memory and document RAG, with collections named from Qdrant:CollectionPrefix (e.g. aonik-dev-user-memory, aonik-dev-documents). Two properties matter for safety:

  • Fail-closed tenant isolation. Every upsert injects tenant_id and every search merges a tenant_id filter; both throw if there is no tenant context, so vectors can never cross tenants.
  • Dimension-validated & resilient. Embeddings whose length ≠ the configured VectorDimensions (1536) are rejected; a startup initializer pre-creates the memory collection and its payload indexes. A Qdrant outage reports Degraded (drops the pod from readiness) rather than crashing the process.

Embeddings come from an IEmbeddingGenerator selected — like the chat model — by Ai.Provider: OpenAI (text-embedding-3-small) in production, or a deterministic stub (hash-seeded vectors) otherwise. The stub is internally consistent but not semantically meaningful.

The default deployment has no real semantic recall

Out of the box, Ai.UserMemory.Backend = SqlServer (whose semantic search is a stub) and Ai.Provider = Stub (hash-based embeddings). Meaningful user_memory_recall and document RAG require both Ai.Provider = OpenAI and the Qdrant memory backend. The User Brief path still works on SQL because it's a relational query, not a vector search.

Document RAG (Spec 035)

The user-facing RAG tool is documents_search, backed by ScopedDocumentVectorIndex. Its retrieval scope is derived entirely from authenticated context — tenant plus the caller's owner-party id — never from a model argument, so an agent cannot widen its own reach. On top of tenant isolation it enforces document classification and purpose: Restricted content is never embedded and Sensitive content is metadata-only, so raw sensitive text never reaches the embedding service. The tool is attached directly to the orchestrator (“RAG-by-default”).

Memory vs the User Brief

These are complementary. The User Brief is a proactive, per-session digest (cash position, flows, top categories, risks) projected fresh at session start and injected into the prompt of agents that require it (Simi). It includes the highest-value current memory entries — read with their own 2-second timeout. Long-term memory is the reactive, durable layer the agent reads on demand (user_memory_recall) and writes back to (user_memory_save, plus a background extraction pass — see §12).

Background workers for agents & memory#

A dedicated Worker host (src/Aonik.Worker) runs the platform's background work. It is the only host that runs the Quartz scheduler and the only one that drains the transactional outbox — so every integration-event handler (including document ingestion into Qdrant) and every scheduled job executes there. The Aspire AppHost starts it and waits for Qdrant to be ready.

Two background-work mechanisms exist (Spec 014): cron-scheduled jobs, and an on-demand “enqueue a job now” abstraction (IBackgroundJobManager). This section is scoped to the jobs that build or feed the agent and memory layers; the platform runs other background jobs (transaction sync, AI cost alarms, and so on) that are out of scope here. The relevant ones:

JobCadenceWhat it doesLLM?
StaleSessionDetectorJob5 minThe conversation-memory engine. For idle chat threads it writes a summary and extracts learnable facts into long-term memory (Qdrant) — see below.yes
CustomerInsightSnapshotJob15 minBuilds a deterministic per-user spending snapshot (no LLM). Spec 015no
CustomerInsightAiSummaryJob30 minInterprets each snapshot into a structured narrative that the pf-insights agent (and Simi) consume. Writes an explicit AiRun. Spec 015yes
WorkItemDispatchJob60 sFires due work items — reminders and scheduled agent actions; high-risk ones land as Proposals, never executed inline. Spec 034indirect

The conversation → memory pipeline

This is how memory accumulates without the user explicitly telling the agent to “remember” things. StaleSessionDetectorJob hands stale threads (idle ≥ 15 min) to ConversationSummaryGenerator, which makes two LLM calls per thread: one writes a ConversationSummary (use_case = conversation-summary), the second extracts durable user facts (use_case = conversation-memory-extraction) and saves each through the same IUserMemorySaveProvider the live user_memory_save tool uses — i.e. into Qdrant. Spend guards keep it safe: a per-thread attempt cap (×3) and a hard ceiling of 20 memories per session (each memory costs an embedding).

Biggest gotcha: this job no-ops by default

StaleSessionDetectorJob only processes threads whose agent is on an allow-list that ships empty (Quartz:ScheduledJobs:StaleSessionDetector:AgentNames). Until an operator populates it, the job runs every 5 minutes but produces no summaries and no memories — automatic conversation memory simply will not appear.

Other agent-relevant facts

  • Document → Qdrant is event-driven, not cron. On upload, an outbox event drives DocumentIngestionHandler → DocumentIndexer (chunk → embed → upsert), all inside the Worker, under the originating tenant. The backfill job above only mops up stragglers.
  • Every job that calls the LLM produces an AiRun via the same AuditMiddleware as interactive chat — so background AI is auditable too.
  • Jobs run with no HTTP context, so each sets tenancy explicitly: either a system “see-all” context (a null tenant sentinel that opens the query filter) or a per-item tenant set inside the loop.
  • Transaction auto-categorization is not a background job — it runs inline in user/agent request flows (rules first, AI fallback), despite the “background classification” framing in Spec 028.

Workflows — graph orchestration#

Beyond conversational agents, the module hosts a workflow subsystem: a persisted, tenant-scoped, editor-authored directed graph of typed step nodes (a visual automation playbook). At run time the saved graph is translated into a MAF Workflow and executed node-by-node, where an agent node invokes a domain agent via IDomainAgentResolver.

Node kindBehaviourStatus
triggerVirtual entry; the first downstream node becomes the start.live
agentResolves and runs a named domain agent with the composed task + upstream output.live
notify / emitPublish a notification / generic event to the event bus.live
endTerminates and records terminal output.live
tool · decision · loop · human · waitSave fine and render on the canvas, but throw NotSupportedException if executed.deferred
Current execution scope

Edges are presently added unconditionally — conditional branching (decision yes/no, loop body/done) is stored and seeded but not yet honoured by the runtime. In practice only linear trigger → agent/notify/emit → end chains execute end-to-end today. Seven richly modelled demo workflows ship (Match & apply, Dunning cadence, KYC re-check, Month-end close, …) and render fully in the editor.
