AONIK · Phase 1 Implementation Plan

Protect financial truth: reconnect the money paths to the ledger.

Phase 1 of the backend review is eight findings that share one theme — places where money can change state without the ledger ever recording it, or where it can be recorded twice. This plan sequences all eight into buildable work. Four of them form a single cluster around the ledger and must land in order; the other four are independent and can run in parallel. It is grounded in a fresh read of current source: every "current state" below cites file:line and was re-verified, not recalled. This is a plan, not a change — no source under src/ was modified to produce it.

01What Phase 1 protects

Eight findings, one invariant.

The architecture's first non-negotiable rule is that the double-entry ledger is the source of financial truth. Phase 1 is every place that rule is currently sidestepped or unguarded. Two are Critical (a status can flip without a ledger post; nothing structurally blocks a double-post), five are High, one is Medium — but they cluster tightly enough to plan and ship as one body of work.

The cluster — must land in order. These four share the ledger and a transaction boundary:

  • H3 — the journal balance check nets debits against credits across currencies, so a multi-currency entry can falsely "balance." Fix it before anything new posts through that path.
  • C1 — every post is hard-coded to SourceType "Manual" / SourceId Guid.Empty, and there is no uniqueness guard, so the same event can be journalled twice. Give posts a real identity and a structural no-double-post guarantee.
  • H6 — a payment can never reach Authorized, so capture is unreachable dead code. Add the authorize step (two-step auth→capture, as decided) so there is a capture to hook into.
  • C2 — capture and invoice mark-paid flip a status column and never touch the ledger. Route both through it. This is the payoff, and it depends on the other three.

The independents — parallelizable. No ordering constraint against the cluster or each other:

  • H5 — order idempotency key is stored trimmed but looked up untrimmed, with no DB uniqueness and no race handling.
  • H8 — the outbox has no row-claim, so a second worker instance double-dispatches every due message.
  • H9 — the recurring sync job scopes itself to Guid.Empty and silently processes zero rows.
  • M9 — user-initiated transactions aren't wrapped in the retrying execution strategy, so the first transient retry throws.

H3

The journal balance check nets debits against credits across currencies

HighCorrectnessno migrationno deps

Current state — verified

Evidence src/Aonik.Finance/Services/Ledger/LedgerService.cs:246–256 — the guard sums every Debit line and every Credit line with no regard for currency, then asserts the two totals are equal: totalDebit != totalCredit. A 100 USD debit against a 100 EUR credit passes, because 100 == 100. Meanwhile the same file already assumes the opposite: the metric at :295–298 documents that "journal entries are constrained to a single currency," and the balance read path groups by currency (:204). Only the write guard forgets currency.

The change — recommended

Enforce the invariant the rest of the file already relies on: reject any entry whose lines span more than one currency, after which the existing debit == credit check is correct for that single currency. One guard, added right after line normalization (the normalizedLines projection ends at :244):

if (normalizedLines.Select(l => l.Currency).Distinct().Count() > 1) throw new InvalidOperationException("A journal entry must use a single currency.");

This also makes the "currency is taken from the first line" assumption at :298 actually true, instead of merely hoped-for.

The change — alternative (defer unless needed)

If multi-currency journal entries are a genuine domain requirement, instead group lines by currency and assert sum(debit) == sum(credit) and both > 0 within each currency group, and record the metric per group rather than off the first line. This is more general but larger, and it contradicts the codebase's current stated single-currency intent — so it should only be taken when a real multi-currency posting exists. Recommendation: ship the single-currency guard now.

Files · migration · tests

  • Files: LedgerService.cs only. Migration: none.
  • Tests (InMemory): a single-currency balanced entry still posts; a two-currency entry whose totals net to equal is now rejected; (if the alternative is taken) a per-currency-balanced multi-currency entry posts.
  • Watch out: this tightens accepted input — grep callers for any entry that today relies on cross-currency aggregate balancing before shipping. PartnerPrefundSeedHelper posts single-currency, so it is unaffected.
Impact Medium–HighEffort LowOrder 1st in cluster
C1

Posts have no real identity and no uniqueness guard against double-posting

CriticalCorrectnessmigrationenables C2

Current state — verified

Evidence src/Aonik.Finance/Services/Ledger/LedgerService.cs:275–276 — every entry built by AddJournalEntryAsync hard-codes SourceType = "Manual" and SourceId = Guid.Empty. The service-layer request it consumes carries no source identity at all: Contracts/Models/Ledger/LedgerModels.cs:18–22 is just (LedgerId, Reference, Description, Lines). And Persistence/Configurations/JournalEntryConfiguration.cs:36 indexes SourceId non-unique with no composite on (TenantId, SourceType, SourceId). Nothing — not the DTO, not the database — stops the same economic event being journalled twice. The one idempotent-post pattern that exists, PartnerPrefundSeedHelper.cs:126–222, works around this by hand with an AnyAsync(SourceType && SourceId) pre-check.

The change — three parts

  1. Give posts an identity. Add optional SourceType / SourceId to the service-layer AddJournalEntryRequest (LedgerModels.cs), defaulting to "Manual" / Guid.Empty so the manual API path is unchanged, and persist the supplied values instead of the hard-coded constants at :275–276.
  2. Idempotent post. When a real source is supplied (not Manual/Empty), pre-check JournalEntries.AnyAsync(e => e.SourceType == src.Type && e.SourceId == src.Id) — generalizing the PartnerPrefundSeedHelper pattern — and return the existing entry rather than posting a second.
  3. Structural guarantee. A tool-generated filtered unique index on (TenantId, SourceType, SourceId), filtered WHERE [SourceType] <> 'Manual'. Configure with .HasFilter(...) in JournalEntryConfiguration.

Why the filter is load-bearing

Every legacy and future manual entry shares the pair ("Manual", Guid.Empty). An unfiltered unique index would fail to create against existing data and would block all future manual entries. The WHERE [SourceType] <> 'Manual' predicate exempts them while making every real source event post exactly once. Before applying, query for any existing duplicate non-Manual (SourceType, SourceId) pairs and resolve them, or index creation fails.

Files · migration · tests

  • Files: LedgerModels.cs (DTO), LedgerService.cs (persist + pre-check), JournalEntryConfiguration.cs (filtered unique index). The DbSet already lives on AonikDbContext.
  • Migration: JournalEntryIdempotencyIndex — tool-generated via AonikDbContext, one index, never hand-authored.
  • Tests: app-level idempotency (same source twice → one entry, second call returns the existing one) is InMemory-testable. The DB-level race (two concurrent posts → one wins, the other throws DbUpdateException) needs a relational test — InMemory ignores filtered and unique indexes.
Impact HighEffort Low–MediumOrder 2nd in cluster
H6

Captured is unreachable — the payment lifecycle has no authorize step

HighCorrectnessdecision: two-step auth→captureunblocks C2

Current state — verified

Evidence PaymentStatus is Pending / Authorized / Captured / Failed / Cancelled. src/Aonik.Finance/Services/Payments/PaymentService.cs:42–50 — CreatePaymentIntentAsync creates a Pending payment and fills PayerPartyId = Guid.Empty and PaymentMethodType = "Card" as placeholders. :74–102 — CapturePaymentAsync requires status Authorized before moving to Captured — but no method anywhere sets Authorized. There is no AuthorizePaymentAsync. So a payment can never leave Pending, and capture is dead code.

The change — two-step auth then capture (locked decision)

  1. Add the authorize step. AuthorizePaymentAsync(Guid paymentId, …) on IPaymentService / PaymentService: Pending → Authorized, guarded (must currently be Pending; record who and when). Capture then works unchanged — Authorized → Captured — and becomes the hook C2 posts from.
  2. Stop fabricating payer and method. Add real PayerPartyId (Guid) and PaymentMethodType (string) to CreatePaymentIntentRequest and validate them non-empty, instead of defaulting to Guid.Empty / "Card".
  3. Endpoint. Add an authorize endpoint (FastEndpoints) mirroring the capture endpoint, using Send.OkAsync() conventions.

Files · migration · tests

  • Files: PaymentService.cs, IPaymentService, Contracts/Models/Payments/CreatePaymentIntentRequest.cs, new AuthorizePaymentEndpoint. Migration: none — Payment already has the columns and status is an enum.
  • Tests (InMemory): full lifecycle Pending→Authorized→Captured; capture-before-authorize rejected; double-authorize rejected; create-intent rejects an empty PayerPartyId.
  • Watch out: adding required fields to CreatePaymentIntentRequest is a breaking DTO change — grep every caller and test that constructs it.

C2

Capture and invoice mark-paid flip a status and never touch the ledger

CriticalCorrectnessdecision: minimal chart-of-accountsseed changeneeds H3 · C1 · H6

Current state — verified

Evidence PaymentService.cs injects FinanceDbContext, ITenantProvider, IPermissionService, ICurrentUserProvider, FinanceMetrics — no ILedgerService; CapturePaymentAsync flips Status to Captured and saves, nothing posts. BillingService.cs:163–177 — MarkInvoiceAsPaidAsync checks Status == "Issued" then sets "Paid" and saves, also with no ILedgerService. Both are exactly the economic events double-entry exists to record. ILedgerService is already registered at FinanceModule.cs:57. The seeded chart (FinanceTenantProvisioningContributor.cs:149–226) is Cash 1000, Accounts Receivable 1100, Accounts Payable 2000, Retained Earnings 3000, Operating Revenue 4000, Operating Expenses 5000 — there is no clearing account, and provisioning validates only that some accounts exist (:142–146).

The change — four parts

  1. Account resolution. Add a small ChartOfAccountsResolver that maps a role (Cash, Receivable, Clearing) to a LedgerAccountId by Code, generalizing PartnerPrefundSeedHelper.ResolveCashLedgerAccountIdAsync (Code == "1000", fallback by Name). It must throw loudly when a role can't be resolved — never silently post to a wrong account.
  2. Add the missing Clearing account. Extend CreateDefaultChartOfAccounts with e.g. 2100 "Payments Clearing" (Liability). This is a data/seed change, not a schema migration. New tenants get it automatically; existing tenants need a backfill — extend the provisioning repair path (the :142–146 check) to ensure the Clearing account specifically exists, so it self-heals on next provision/validate.
  3. Post inside the status transition. Inject ILedgerService into both services and post in the same transaction as the status flip:
    // capture: money received, not yet applied Dr Cash 1000 / Cr Payments Clearing 2100 amount = payment.Amount, currency = payment.Currency SourceType = "PaymentCapture", SourceId = payment.Id // invoice paid: collect the receivable Dr Cash 1000 / Cr Accounts Receivable 1100 amount = invoice.Total, currency = invoice.Currency SourceType = "InvoicePaid", SourceId = invoice.Id
    Both are single-currency and balanced (so they pass H3) and idempotent via C1's source keys.
  4. Atomicity under retry. The caller and LedgerService share the scoped FinanceDbContext, so wrap "flip status + post journal" in one transaction. Because FinanceDbContext uses EnableRetryOnFailure, that transaction must run through CreateExecutionStrategy().ExecuteAsync(…) — the same wrapper M9 introduces. Re-read the payment / invoice inside the delegate so a retry is safe.

One open question — for the finance owner

Can capture and mark-paid both fire for the same money?

If a captured payment settles an invoice, posting both Dr Cash / Cr Clearing (capture) and Dr Cash / Cr Receivable (mark-paid) would double-count Cash. The clean pairing is: capture → Dr Cash / Cr Clearing, then mark-paid → Dr Clearing / Cr Receivable — net effect Dr Cash / Cr Receivable, no double count. If mark-paid is standalone (no capture step), use Dr Cash / Cr Receivable directly.

The mechanism is identical either way; only the credit account on mark-paid differs. The defaults above are my recommendation — this is the single point that is accounting policy, not code, and worth a sign-off before C2 ships.

Files · migration · tests

  • Files: PaymentService.cs, BillingService.cs, FinanceModule.cs (inject ILedgerService into both; register the resolver), new ChartOfAccountsResolver.cs, FinanceTenantProvisioningContributor.cs (Clearing seed + repair).
  • Migration: none — it rides on C1's index. The Clearing account is a seed, not a schema migration.
  • Tests: capture posts a balanced Dr Cash / Cr Clearing entry; mark-paid posts Dr Cash / Cr Receivable; re-capture / re-mark is idempotent (no second entry); the resolver throws when Clearing is absent. App-level postings are InMemory-testable; the idempotency race is relational.

H5

Order idempotency key: trim asymmetry, no DB uniqueness, no race handling

HighCorrectnessmigration

Current state — verified

Evidence src/Aonik.Finance/Services/Orders/OrderService.cs:189–201 — CreateBillPaymentOrderAsync looks up an existing order with the raw, untrimmed request.IdempotencyKey, but stores it .Trim()-ed at :215. A key submitted with surrounding whitespace is stored trimmed, so the next lookup with the same untrimmed value misses it and a duplicate order is created. There is no try/catch around SaveChanges (:248). Persistence/Configurations/OrderConfiguration.cs:82 indexes IdempotencyKey non-unique and single-column; only OrderNumber is unique. IdempotencyKey is nullable string? (max 200).

The change — three parts

  1. Trim once. Normalize the key at the top of the method and use the trimmed value for both the lookup and the store — symmetry.
  2. DB uniqueness. A tool-generated filtered unique index on (TenantId, OrderType, IdempotencyKey) filtered WHERE [IdempotencyKey] IS NOT NULL, so orders without a key stay unconstrained.
  3. Race handling. Wrap SaveChanges in try/catch DbUpdateException; on a unique violation, re-fetch the existing order by the same (tenant, type, key) and return it — a concurrent duplicate becomes an idempotent success, not a 500.

Files · migration · tests

  • Files: OrderService.cs, OrderConfiguration.cs. Migration: OrderIdempotencyUniqueIndex — tool-generated.
  • Tests: same key with and without whitespace → one order (the trim fix is InMemory-testable); concurrent duplicate → one wins, the other returns the existing order (relational only — InMemory ignores the unique filter).
Impact Medium–HighEffort LowIndependent
H8

The outbox has no row-claim — a second instance double-dispatches every message

HighScalabilityCorrectnessmigration

Current state — verified

Evidence src/Aonik.Infrastructure/Messaging/Outbox/OutboxProcessor.cs:69–76 — ReadDueMessageIdsAsync selects due ids; :84–108 — ProcessMessageAsync re-reads but takes no lock, dispatches, then sets ProcessedAt and saves. The class doc (:18–20) admits the double-dispatch risk. SharedKernel/Events/Outbox/OutboxMessage.cs has no claim/lease column. Today one OutboxBackgroundService runs in the Worker (src/Aonik.Worker/Program.cs:31, 10 s poll, batch 50), so it's latent — but a second instance double-dispatches every due message. Provider is SQL Server (Infrastructure/DependencyInjection.cs:161–165).

The change — claim before dispatch

  1. Lease columns. Add ClaimedAt, ClaimExpiresAt (DateTimeOffset?) and ClaimedBy (string?) to OutboxMessage; update OutboxMessageConfiguration's dispatch index to include the claim predicate. Tool-generated migration.
  2. Atomic claim. Replace read-then-process with a single SQL Server UPDATE … OUTPUT under WITH (READPAST, UPDLOCK, ROWLOCK) that stamps the claim on up to N due rows and returns their ids — peers skip claimed rows via READPAST, so each message is claimed by exactly one worker. Process only what you claimed; on success set ProcessedAt; on failure set Error/NextAttemptAt and clear the claim.
  3. Crash recovery. Reclaim rows whose ClaimExpiresAt has passed. Guard the raw SQL behind the relational provider.

Illustrative claim — confirm the mapped table and column names against the generated migration:

UPDATE TOP (@batch) m WITH (READPAST, UPDLOCK, ROWLOCK) SET m.ClaimedBy = @worker, m.ClaimedAt = SYSUTCDATETIME(), m.ClaimExpiresAt = DATEADD(SECOND, @lease, SYSUTCDATETIME()) OUTPUT inserted.EventId FROM <outbox-table> m WHERE m.ProcessedAt IS NULL AND m.DeadLetteredAt IS NULL AND (m.NextAttemptAt IS NULL OR m.NextAttemptAt <= SYSUTCDATETIME()) AND (m.ClaimExpiresAt IS NULL OR m.ClaimExpiresAt <= SYSUTCDATETIME());

Files · migration · tests

  • Files: OutboxMessage.cs, OutboxMessageConfiguration.cs, OutboxProcessor.cs. Migration: OutboxMessageLease — three columns plus the claim-supporting index.
  • Tests: integration only — the claim is SQL-Server semantics (READPAST/UPDLOCK) the InMemory provider cannot model. Use LocalDB / Testcontainers and assert two concurrent processors never dispatch the same message, and that an expired lease is reclaimed.
  • Good news: the relational harness already exists — tests/Aonik.Finance.IntegrationTests runs against a Testcontainers SQL Server fixture (SqlServerContainerFixture), and LedgerInvariantSqlServerTests already exercises ledger invariants there. H8's claim test and C1/H5's race tests extend that suite rather than needing new infrastructure.

H9

The recurring sync job scopes itself to Guid.Empty and sees no rows

HighCorrectnessno migration

M9

User-initiated transactions aren't wrapped in the retrying execution strategy

MediumCorrectnessshares wrapper with C2

Current state — verified

Evidence src/Aonik.PersonalFinance/Services/PersonalFinance/HouseholdService.cs:236–240 (and AddMemberAsync near :310) and FinancialLifeGraphWriteService.cs:65–69 open BeginTransactionAsync(IsolationLevel.Serializable) guarded by useTransaction = IsRelational(). PersonalFinanceModule.cs:56 registers the context with EnableRetryOnFailure. A retrying execution strategy throws on a user-initiated BeginTransaction unless the whole unit is wrapped in CreateExecutionStrategy().ExecuteAsync(…) — and there is no such wrap anywhere today. The first transient retry on these paths throws "…does not support user-initiated transactions."

The change — wrap the unit

Wrap each begin→work→commit block in the execution strategy, keeping the useTransaction = IsRelational() branch so the InMemory path stays transaction-less:

var strategy = _dbContext.Database.CreateExecutionStrategy(); await strategy.ExecuteAsync(async () => { await using var tx = useTransaction ? await _dbContext.Database.BeginTransactionAsync(IsolationLevel.Serializable, ct) : null; // re-read entities here — the delegate may run more than once // … work … if (tx is not null) await tx.CommitAsync(ct); });

The delegate must be re-runnable: re-read entities inside it and don't depend on state mutated before the boundary, because the strategy may invoke it more than once.

Files · migration · tests

  • Files: HouseholdService.cs, FinancialLifeGraphWriteService.cs. Migration: none. C2's new transaction uses this same wrapper — do M9 first, or factor a shared helper.
  • Tests: behavior unchanged on InMemory (transaction skipped); the retry-safety itself is only observable on SQL Server — note it rather than over-asserting in a unit test.
Impact MediumEffort LowIndependent · do before C2

06Testing strategy

What the InMemory provider can prove — and what it can't.

The pure-logic fixes are unit-testable with the existing InMemory + TestTenantProvider patterns. The database-level guarantees are not: the InMemory provider does not enforce unique or filtered indexes and cannot execute raw SQL. Anything whose correctness lives in the database needs a relational test (SQL Server LocalDB or Testcontainers).

InMemory-testable (existing patterns)

  • H3 rejects a cross-currency / multi-currency entry
  • C1 app-level idempotency — second post returns the existing entry
  • H6 lifecycle transitions and guard rejections
  • C2 postings land on the right accounts/amounts/source keys; resolver throws when Clearing is absent
  • H5 trim symmetry — same key, with/without whitespace, → one order
  • H9 enumerates all tenants, scopes per connection
  • M9 behavior unchanged (transaction skipped on InMemory)

Relational / integration only

  • C1 unique-index race — concurrent posts, one wins
  • H5 unique-index race — concurrent duplicate returns existing
  • H8 the READPAST/UPDLOCK claim + expired-lease reclaim
  • C2 the posting idempotency race
  • M9 the actual retry semantics under EnableRetryOnFailure

The relational harness already exists: tests/Aonik.Finance.IntegrationTests runs against a Testcontainers SQL Server fixture (SqlServerContainerFixture / SqlServerCollection), and LedgerInvariantSqlServerTests already locks ledger invariants there. The right-hand column extends that suite — there's no new harness to stand up, which lowers the cost of the race and claim tests considerably.
