1. Executive summary

Arke Studio is a free, MIT-licensed, local-first desktop application for authoring fictional worlds and producing media from them. Its own specification is categorical: "the filesystem as the only durable truth. No cloud backend on the hot path, no database of record, no git," and "any account, subscription, billing or cloud backend" is listed out of scope for v1. Arke Kids is a separate, child-facing product in the same family, already removed from the Studio repository.

A commercial tier is now under consideration alongside — explicitly not instead of — the free product. This brief exists because that decision has a much smaller blast radius than it appears to, and the reason is worth stating plainly:

The finding

AONIK already holds almost everything a commercial Arke needs, and it holds it generically. Authentication across three operator-choice IdPs, tenancy, parties, subscriptions with plan versions and renewal, three kinds of meter, orders, invoices, a double-entry ledger, groups with roles and invitations, and scoped revocable sharing are all built, merged and product-neutral. Of the twenty Arke Studio capability specifications, eleven need nothing from AONIK at all — they are the product, and the platform must never learn them.

What is genuinely missing is two things and a decision: a versioned tree of files the platform can own (Spec 089), an entitlement a laptop can verify with no network (Spec 090), and a ruling on whether cloud dispatch spends AONIK credits or the user's own provider key — which is a business decision wearing an architecture costume.

The three sentences that follow from that:

  1. The free product does not change. Sync is opt-in, the folder stays the interchange format, and nothing in Arke's local domain layer gains a dependency on AONIK. If that stops being true, the commercial tier has eaten the product it was meant to sit beside.
  2. The platform owns containers, identity and money. The product owns meaning. AONIK stores a world; it must never know what a canon entry is. §4 makes this testable rather than aspirational.
  3. Arke Kids is the reason any of this is platform work. One consumer is a feature; two is a capability. Both products have worlds, families, subscriptions and sharing — and it is the second consumer that justifies putting them in the platform rather than the product.

2. The two products

2.1 Arke Studio — what it is today

A Windows desktop application (Electron shell, local coordinator, an embedded coding-harness adapter). A world is a folder of readable files on the user's own disk. The authored record — canon entries, character and location sheets, productions, scenes, shots — lives in those files and nowhere else. A derived index makes them queryable. Nothing enters the authored record without a human accepting it: proposals are ripple-checked against canon and either accepted, rebased or rejected. Media generation is dispatched to providers with the user's own keys, through a durable local job queue, and the spend is recorded in a local append-only ledger.

The twenty capability specifications group into four bands:

BandSpecsWhat it is
Substrate 001, 002, 003, 016 Shell, contracts, coordinator; the world on disk; the derived index; first run, packaging, updates.
Authoring 004, 005, 006, 007, 015, 017 The accept gate; the harness adapter; canon; sheets; import and fact extraction; art direction.
Media 008, 009, 010, 011, 012, 013, 019, 020 Providers and the ledger; the job queue; reference kits; voice; productions; takes and exports; long-form video; local generation.
Oversight 014, 018 Activity, the needs-you queue and spend; voice mode.

Arke's own architecture note warns that conflating the authoring path and the media path is the main risk it exists to prevent. That warning matters here, because a cloud tier adds a third axis — local versus remote — crossing both. §7.5 is where that lands.

2.2 Arke Kids — what it is

A separate, child-facing product sharing the same substrate: worlds, characters, generated stories and video. The commercial shape is already sketched in Spec 087 as the worked example that proved the entitlement model: a Peek tier free forever, then three paid tiers at £9.99 / £19.99 / £39.99, gated on stories per month, videos per month, child profiles and HD output.

Structurally it differs from Studio in four ways that all land on the platform:

DifferenceConsequence for AONIK
The subscriber is a parent; the users are children. The owner of a workspace may be a party who cannot authenticate. This is exactly why ADR-015 keyed membership on PartyId rather than UserId.
A family is the unit, not an individual. A family is a Group whose kind is family — already supported, already merged, and the exact case that broke when the platform's noun was Household.
It is cloud-first, not local-first. Kids inverts Studio's assumption. It needs the same Workspace, but as the primary store rather than a mirror.
Children are a protected class in law. Guardian relationships, verifiable parental consent, and content safety are not features — they are conditions of shipping. §12.
Why the second product is the load-bearing one Every extraction in this programme passed the same test: one consumer is a feature, two is a capability. Groups went to the platform because Payabo households and Arke Kids families are the same shape. Workspaces go to the platform because Studio worlds and Kids worlds are the same shape. If Arke Kids were cancelled tomorrow, a fair reviewer would ask whether Aonik.Workspaces should still exist — and the honest answer is that it would be a closer call.

3. The commercial model

The tier structure has to answer one question before any of it is buildable: what is a paying customer actually buying? There are three candidate answers and they have different architectures.

What is soldWhat it requiresAssessment
A. Storage and continuity — worlds in the cloud, on every machine, backed up, shareable. Workspaces, sync, quota meters, sharing. Spec 089 + 090. Buildable now. No custody change, no metering of third-party spend, no new liability. This is the tier to ship first.
B. Features — long-form video, HD voice, richer reference binding, collaboration. Flag meters. Already exist in Spec 087; need 090 to be checkable offline. Buildable now, and it composes with A at no extra cost. The caution is that the client is open source, so a flag gates the honest, not the determined — §7.2.
C. Compute — we run the generation, the customer buys credits instead of holding provider keys. Server-side dispatch, key custody, counter meters transactional with execution, and a ruling on which ledger is true. Not buildable yet, and it is the one that changes AONIK's liability profile. Four of the five hard seams in §7 exist only because of C.
Recommendation

Ship A+B. Defer C until A+B has customers.

A+B needs two specifications, both now written, and no change to AONIK's risk posture. C needs provider-key custody, a reconciliation rule between two ledgers, a server-side execution subsystem, and an answer to what happens when a provider bills us for work a customer disputes. That is not a phase-two of the same project; it is a different business — reselling compute — and it deserves to be entered deliberately with revenue already on the board, not as a consequence of shipping sync.

4. The governing rule: one seam

Everything below is downstream of a single boundary. State it once, and most of the mapping decisions answer themselves.

The seam

AONIK owns the container, the identity, and the money. Arke owns the meaning.

The platform stores a workspace, its revisions, its files and their bytes; it knows who owns it, who it is shared with, how large it is and whether the subscription covering it is current. It never opens the files. What a canon entry is, what a ripple check does, what a model sheet compiles to, how a shot becomes a take — all of that is product, operating on contents the platform is structurally incapable of interpreting.

4.1 Why this is testable rather than aspirational

The same rule already survived one full implementation cycle. In Spec 086, a share grant carries TermsJson — an opaque blob the platform persists and never reads. The consuming product parses it; the platform cannot, because it has no type for it. That is the test: 

If Aonik.Workspaces ever gains a type called CanonEntry, Sheet, Shot or Take,
the seam has failed and the module has become a second copy of the product.

It is enforceable in review, in a single grep, and it has one clean precedent. The equivalent for the other direction is just as important: 

If Arke's local domain layer ever gains a reference to Aonik, the free product
has become a client of a paid backend, which is the thing this design exists
to prevent.

4.2 The vocabulary rule that comes with it

Platform code says Workspace. "World" is Arke's word and stays in Arke's UI. Platform code says Group with Kind = "family". "Family" is Kids' word. ADR-013 made this a rule; Spec 086 paid for breaking it. When the platform's noun was Household, the personal-finance lifecycle contributor treated an Arke Kids family as a household, wrote it into PersonalProfile.HouseholdId, and then refused the user's second family with "User already belongs to a household." Three review rounds to fully close. The vocabulary invited the defect; the defect was not a coding slip.

5. How to read the map

Every Arke capability falls into exactly one of four classes. The classification is the useful part — a mapping that says "related to" for everything says nothing.

REUSE AONIK already provides it. Arke consumes it; nothing new is built.
MIRROR Both sides have their own implementation of the same idea. They must be reconciled, and the reconciliation rule must be written before either changes.
PRODUCT Stays in Arke permanently. The platform must never learn it. Listing these is as important as listing the others.
GAP Neither side has an answer. Named, sized, and given a proposed spec number in §11.

Status chips: built merged to master · draft specified, not implemented · none no specification exists.

7. The five hard seams

Everything in §6 marked MIRROR or GAP reduces to five decisions. Four of the five exist only because of commercial model C.

7.1 The world ↔ workspace seam

The question. A world is a folder. A cloud tier needs it to exist somewhere other than one person's disk. Where does it live, and which copy is true?

The answer (ADR-016, Spec 089):

Workspace
container, owner, head
→
WorkspaceRevision
= a manifest
→
WorkspaceFile
path → hash
→

IFileStore already returns a SHA-256 on upload, so content addressing costs nothing new. Sync reduces to "which of these hashes do you not have?" — and takes of one shot dedupe hard, which is the case that matters for size.

Why it must be platform, not product. This is the argument that actually settles it, and it is a sharing argument rather than a storage one. Spec 086 §6 makes a share grant name a ResourceKind plus ids, and requires the owning module to answer "does this owner own these ids?" through an IShareResourceResolver. That question is asked on the hot path of an authorisation check. If worlds live in the product, the platform must call the product over HTTP to answer it — inverting the dependency, for a product designed to work offline. With workspace registered as a share resource kind, the resolver is a query against the platform's own table.

Which copy is true. The local tree is authoritative on the machine that holds it; the cloud head is authoritative between machines. A remote revision that does not descend from the local head is not merged and not silently overwritten — it arrives as a proposal and goes through Arke's existing accept gate. No merge algorithm, no conflict markers, no new vocabulary. The product already has a word for "a change not yet accepted".

Status: specified, not built — Spec 089 (five phases) and Spec 091 (five phases). The module does not yet exist.

7.2 The entitlement seam

The question. IEntitlementReader is a live database read. Arke Studio runs on a laptop with no network. How does a paid feature check itself?

The answer (Spec 090): a compact Ed25519-signed token carrying flags and ceilings only, with a short expiry and a long grace. Seven days fresh, thirty days grace, then paid features stop — and nothing else does.

The distinction the whole design turns on A flag ("may use long-form video") and a ceiling ("at most 25 workspaces") stay true until the subscription changes, so they travel safely in a signed artefact. A counter ("1,200 credits remaining") changes every time it is used — and an offline client holding one can spend the same credits on two machines, or restore yesterday's file and spend them again. That is not a bug to fix with better client code; it is what an offline balance is. Counters are therefore never issued offline, and anything that spends credits requires the network — which is already true, because it calls a provider.

What it does not defend, said out loud. The client is MIT-licensed and open. Anyone determined can delete the check and compile their own build. The goal is not "unbreakable" — it is that the honest path is effortless and the casual dishonest path is pointless. A spec that pretends otherwise leads to expensive obfuscation work that buys nothing.

The rule that decides the product's character. Lapsing removes paid features. It never removes the user's work, and it never removes the free product. A lapsed customer returns to Arke Studio-as-it-exists-today — free, MIT, every world still on disk, every file still readable.

Status: specified, not built — Spec 090, four phases.

7.3 Ledger authority — two ledgers, one word

The question. Arke keeps an append-only spend ledger with provider-reported actuals. AONIK's non-negotiable rule 1 is that the ledger is the source of financial truth, double-entry and immutable. Both are called "the ledger". Which one is?

The answer, proposed: they are ledgers of different things, and the confusion is entirely in the noun.

Arke's spend ledgerAONIK's ledger
RecordsWhat a dispatch cost, as the provider reported itWhat money moved between whom
Currency of recordThe user's own provider spendAONIK-denominated value
PartyThe user and their provider — AONIK is not a partyAONIK and its customer
NatureObservation, like a personal-finance bill recordTruth, double-entry, immutable

Under models A and B this resolves cleanly: Arke's ledger observes the user's own spending on their own keys, exactly as Aonik.PersonalFinance observes "this user pays £9.99 a month to Netflix" without that being an AONIK financial event. Under model C it does not resolve at all: if a customer buys credits and we dispatch on their behalf, a single generation is simultaneously a counter-meter commit, an AONIK ledger posting, and a cost we incur from the provider — and the three must reconcile.

Status: no specification. Proposed Spec 094. This must be written before any line of model C is built, not after — an unreconciled second ledger is the kind of defect discovered by an auditor rather than a test.

7.4 Provider-key custody

The question. Locally, a user's FAL or ElevenLabs key sits in an app-owned encrypted file under the OS key store — their machine, their key, their liability. In the cloud, someone has to hold it.

Three options, honestly assessed:

OptionWhat it meansAssessment
1. Never hold keys Cloud sync only; all dispatch stays local on the user's machine and their key. recommended for v1 Zero custody change. Model A+B is entirely achievable this way. The customer buys storage, continuity and features — not compute.
2. Hold the customer's key They paste their FAL key into our cloud; we dispatch on their behalf against their account. worst of both Full custody liability, a breach exposes customer credentials at other vendors, and we still cannot meter it as revenue because the spend is theirs. Rejected.
3. Our key, their credits We hold provider relationships; customers buy AONIK credits; we dispatch and bear the provider cost. model C Coherent, and the only version where compute is genuinely a product. But it makes AONIK a compute reseller with margin risk, provider concentration risk, and abuse exposure. Enter deliberately.

Status: no specification. Proposed Spec 093, needed only if model C is chosen. Option 1 needs no spec, which is the strongest argument for it.

7.5 Server-side dispatch, and the third axis

The question. Arke's job queue is local and calls providers directly. Does anything execute server-side?

Arke's own architecture note warns that conflating the authoring path and the media path is the main risk its design exists to prevent. Adding local-versus-remote gives four combinations where the product currently reasons about two:

LocalRemote
Authoring v1 The product as it exists. Harness, accept gate, ripple check. out of v1 Would mean running the harness, the keys, the staging directory, the accept gate and the ripple check server-side — the whole product rebuilt, for a feature nobody asked for.
Media v1 Local queue, user's own keys, unmetered by us. model C Where credits are actually consumed. A new subsystem, transactional with metering. Not a port of the local queue — a laptop that sleeps and a server with a transactional database have incompatible failure models.

Ruling for v1: sync a tree; do not author on the server. That single sentence keeps the cloud tier at "storage and continuity" and prevents the quiet expansion where remote authoring appears one endpoint at a time.

Status: no specification. Proposed Spec 092, model C only. The v1 ruling is recorded in Spec 091 §4.

8.2 A worked example: ShareResourceKind

Worth spelling out, because it is the mechanism that makes "two products, one sharing implementation" true rather than merely claimed.

In Spec 086, a share grant does not name a table. It names a kind plus a set of ids: 

ShareGrant
  ResourceKind = "workspace"          // what sort of thing
  ResourceIds  = [ <guid>, <guid> ]   // which ones
  AccessLevel  = Read | Write | Owner // closed enum — the platform DOES read this,
                                      //   and enforces it at its own endpoints
  TermsJson    = { … }                // opaque — the platform never reads it

Note on AccessLevel: an earlier revision of this brief and of Spec 089 put read-versus-write inside TermsJson, on the reasoning that a role is product vocabulary. That was wrong in a way worth recording: the commit endpoint belongs to the platform, so a read-only recipient could simply call it directly and the product-side check would be decoration. Authorisation for the platform's own endpoints is the platform's job; product semantics — what "co-author" means, whether comments are allowed — remain opaque in TermsJson. The seam moved to the right place rather than moving.

First, a correction — an earlier revision of this example could not pass its own validation

It assigned the world's OwnerPartyId to the child, then had the parent create the grant. Step 2 below asks whether the granting party owns the workspace, and the answer would have been no. The guardian relationship that would let a parent act for a child is listed three rows above as GAP — so the example depended on the very thing it acknowledged was missing.

v1 resolution: the subscribing parent's party owns the workspace; the child is a member of the family group with access to it. This is honest about who is accountable — the parent holds the subscription, consents on the child's behalf, and can be contacted — and it needs nothing that does not exist. Moving ownership to the child is a Spec 095 follow-up, and the field is party-keyed precisely so that move is a data change rather than a schema one.

Concretely, for Kids: a parent shares a story world from their family with a grandparent.

  1. Kids calls the platform: grant workspace, ids [world-id], access Read, expires in 30 days, terms {"canComment":true,"canDownload":false}.
  2. The platform asks Aonik.Workspaces: does this party own world-id? A query against its own table — no HTTP, no cross-module reference, no product callback. It resolves because the parent is the owner.
  3. The platform issues a single-use invite, sends it, renders an anonymous preview, records the accept, and enforces expiry and revocation.
  4. The grandparent's Read access is enforced by the platform, at the endpoint — they cannot commit even by calling the sync API directly (Spec 089 §10.1).
  5. Kids parses TermsJson and decides what "can comment" means. The platform never opens it.

The grandparent needs no account until they accept; revocation is immediate; the invite cannot be replayed. None of that is written twice. Studio's "share a world with a collaborator" is the same four steps with a different TermsJson.

12. Risks that are not engineering risks

These would not surface from a code review, and each can stop a launch on its own.

R1 — Children are a protected class

Arke Kids processes children's data and generates content for them. That engages the UK Age Appropriate Design Code, GDPR Article 8 parental consent, and COPPA if the product reaches the US. Verifiable parental consent is a higher bar than a consent record — a checkbox is not it. AONIK has PartyConsent as an entity and no mechanism behind it.

Implication: Spec 095 is not a nice-to-have that follows launch; it is a precondition of it, and it needs a legal read before an engineering one — which is why its first phase is counsel with no code. It also found that PartyConsent is a table nothing writes to, so the platform has no consent mechanism at all.

R2 — Generative content for children A model that produces a story or a video for an eight-year-old can produce something distressing, and neither product has a moderation layer. The reputational asymmetry is total: one bad output reaches a parent, and no amount of "the model did it" survives that conversation. Now specified as Spec 096, which had been the largest unaddressed item in this brief. Its central finding: the strongest lever is structural — narrowing what can be generated beats filtering what was — and free-text prompting by the youngest children is the riskiest feature in the product.
R3 — Open source and paid tiers Arke Studio is MIT. A community fork that strips the licence check is legal, and a hostile framing ("they went commercial") is a real risk to the goodwill the free product earns. Mitigation is positioning, not cryptography: sell what a fork cannot provide — hosted storage, sync between machines, sharing with people who have no install. Selling a feature flag invites the fork; selling infrastructure does not.
R4 — Storage economics A world with video takes is plausibly gigabytes, and content addressing does not help with the takes — it dedupes byte-identical blobs, and independently generated takes share no bytes (§6.3/013). Model the media path as undeduplicated: a flat monthly price against unbounded storage is a business model with a hole in it, and the hole is larger than an earlier revision of this brief implied. Set the byte ceiling before the first customer, not after. Quotas retrofitted onto users who already uploaded 200GB are a support problem, not an engineering one — which is ADR-016's stated reason for putting workspaces in the platform where meters can see them.
R5 — The product-versus-platform pull Every cloud feature will present an argument for moving one more piece of Arke into AONIK. Each argument will be locally reasonable. The end state is that the free local-first product becomes a thin client for a paid backend — at which point the thing with the users has been dismantled to serve the thing with the revenue. §14 exists because this risk is gradual and therefore hard to see in any single pull request.

The shortest path to revenue Steps 1–5. Two specifications already written, one integration step that is small because the platform work is done, and one obligation spec. That is a commercial Arke Studio selling storage, continuity and sharing — with no change to AONIK's liability profile, no key custody, no second ledger, and a free product that still works exactly as it does today with the network unplugged.

14. Drift rules

Five statements. Each one is checkable in review, and each has already been paid for somewhere.

  1. No Arke noun in platform code. Not World, not Canon, not Sheet, not Take. The platform says Workspace with Kind = "world". ADR-013; the bill was paid in Spec 086's Household defect.
  2. The platform never opens a workspace file. Same rule as TermsJson. If Aonik.Workspaces gains a type that describes file contents, the seam has failed.
  3. Arke's local domain layer never references Aonik. Sync is an additive client at the edge. The free product must build and run with no knowledge that a platform exists.
  4. No counter meter is ever issued offline. Spec 090 §10, enforced by a test over the projection rather than by reviewer memory.
  5. Lapsing never removes the user's work. Paid features stop; worlds, files and the free product do not. Sync pauses; it does not delete.
If only one of these survives Rule 3. Rules 1, 2, 4 and 5 protect the architecture and the customer. Rule 3 protects the reason anyone chose Arke Studio in the first place — and it is the one that erodes silently, one reasonable pull request at a time.
