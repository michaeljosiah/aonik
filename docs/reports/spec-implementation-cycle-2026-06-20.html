3. Completed work

Spec 007 — Cards vault complete · PR #159

A token-only customer card vault: six /payments/methods endpoints (setup-intent, list, get, save, delete, active) over a new PaymentMethod store. AONIK persists only a gateway vault token plus masked display metadata (brand, last-four, expiry) — never a PAN, CVV, or PCI-scoped data. Owner + tenant scoping is server-resolved (never from request input); the Last4 column is deliberately nvarchar(4). The setup-intent extends IPaymentProviderGateway (Stripe-sim impl); the "active" list aligns with registered-gateway availability.

ReviewCodex ran three rounds and each finding was fixed: (1) PCI guard extended to all persisted free-form fields; (2) the PAN guard hardened to catch embedded PANs (regex) and the Provider field; (3) concurrency — a soft-delete-aware unique token index + a single-default unique index + idempotent DbUpdateException convergence. On round 4 codex went silent (usage limit), so a most-capable fallback sub-agent reviewer took over and found three further real issues — most notably that the round-3 single-default index had silently destroyed the plain browse index (EF keys indexes by property set), plus a MakeDefault-on-existing-card 500 and a no-linked-party 500. All fixed; 21 service tests pass; full solution builds.

Spec 041 — Agent memory: decision-aware learning complete · PR #160

Extends the existing memory subsystem so agents learn why a choice was made, when a rationale still applies, and what has worked across a tenant's cases — without a parallel memory platform and without touching any approval/risk-tier behaviour.

  • Rationale recall — UserMemoryEntryType.Rationale; a DecisionRationaleService over IUserMemoryService stores rationale keyed decision.{type}.{subject} and applies deterministic condition relevance (Match / Partial / Mismatch), withholding inapplicable priors.
  • Pattern memory — a new tenant-scoped DecisionPattern entity + SQL-first service (reinforce / supersede-not-delete / confidence ranking, fail-closed tenant isolation).
  • Outcome extraction — DecisionResolvedEvent + an outbox handler + extraction service; a live emitter is wired at ProposalApprovalService Applied/Failed (PII-free event).
Engineering decision worth your attention The spec proposed adding three columns to UserMemoryEntry. Doing so would have forced EF to emit a destructive RenameTable against a pre-existing snapshot drift (a raw-SQL sp_rename moved the live table to AnkUserMemoryEntries but the AonikDbContext snapshot still maps UserMemoryEntry) — exactly the migration-corruption hazard CLAUDE.md warns about. I deliberately kept rationale data in the existing key/JSON (per the spec's own §5.1 key convention) so the only new table is the clean AnkDecisionPatterns. The generated migration was reviewed and contains zero UserMemory references. This drift is a latent issue regardless of this spec — see §5.

14 tests pass; no memory/proposal regressions. A fallback sub-agent review (codex out of quota) independently verified the migration-drift decision is sound, tenant isolation is airtight, the outbox wiring is correct, and RQ7 holds — no P1. One real nit was fixed (an even condition-split now stays a caveated Partial instead of being withheld). Honestly deferred in this V1: RQ3 (the recall services exist + are tested, but the User Brief doesn't yet consume them — needs active-decision-context plumbing the spec itself flags) and RQ6 (the deterministic V1 has no LLM call, so no AiRun; the model-judged distiller is the documented seam). The Proposal emitter reinforces patterns only; the WorkItemRun + Invoice-Paid emitters are additive follow-ups.

5. Urgent observations

P0 — latent migration drift on UserMemoryEntry The canonical AonikDbContext model snapshot maps UserMemoryEntry to dbo.UserMemoryEntry, but the live table is dbo.AnkUserMemoryEntries (renamed by a raw-SQL sp_rename migration that EF never reflected in the snapshot). Any future change to that entity that touches its mapping will make EF emit a RenameTable that breaks a fresh migration run. This should be reconciled deliberately — likely a one-off corrective migration authored with care — before anyone adds columns to user memory.

6. Things to be aware of

  • Commit messages are unreliable as a "what's implemented" signal. Spec 049's full implementation shipped under a docs:-prefixed commit. Recon that trusted messages would have wasted a full re-build; code-verification caught it. Consider a lightweight convention (or a spec "Status: implemented in #NN" field) so this is queryable.
  • Spec numbering collisions. There are two 041 specs (agent-memory and order-spine) and two 042 specs. This makes "the Nth spec" ambiguous; future specs may want a monotonic id.
