1. Executive summary

Abby's Table does not need a new Aonik module. Spec 042 already built the storefront skeleton: anonymous catalog browse, guest carts, build-your-own-box bundles, checkout onto the shared ProductPurchase order spine, stock reservation, guest payment intents, discounts and tax. The maker-ops series (specs 050–058) covers the kitchen side: recipes, ingredient costing, production sheets and prep lists. Abby's Table is the first storefront client of this machinery, and it exposes five capability gaps — all of them generic commerce features, none of them Abby's-Table-specific code.

Build areaWhy the storefront needs itStatus
1. Product option groups (personalisation) Portion / protein / side / heat per dish, per-dish narrowing, a recommended default ("Abby's choice"), multi-select, price deltas including negative ones missing
2. Option-dependent content Nutrition, ingredients, allergens and heating authored per combination — never calculated (a protein swap changes the allergen list) missing
3. Box-builder carts Size-priced boxes (presets + formula), line editing with merge, a hard capacity ceiling, an authoritative server quote on every write partial
4. Fulfilment promise "Earliest delivery: 6 August" appears on five pages and must be computed from cutoffs and lead times; delivery address/slots/fees follow at checkout missing
5. Merchandising & storefront config Featured dishes and curated groups, configurable filter facets, hidden search keywords, a public storefront-config document missing

The frontend is ready to receive. Every AbbysTable page resolves data through one seam (web/src/lib/aonik/client.ts): an AonikClient interface with a fixtures implementation and an HTTP implementation whose routes are explicitly labelled "first guess — reconcile with Aonik's actual routes". Swapping to real Aonik is an environment variable plus one class. The Step 2 functional spec (v1.1) additionally defines the server-side box contract — data model, quote shape and the validation rules the backend must enforce.

Platform principle (ADR-013 / ADR-014): everything lands generic. Abby's Table is a tenant with a config pack, not a product baked into platform code. "Dish" is a Product; "Abby's choice" is a recommended default whose display label is tenant configuration; "Signature" is a product surcharge attribute; heat pips are a facet over product attributes. Nothing in this plan introduces an Abby's-Table concept into Aonik source — the same features must serve any curated-retail tenant out of the box.

3.2 Integration architecture

Next.js Server Components
AbbysTable web/ → AonikClient (HTTP)
server-only, ISR-cached reads → Aonik public endpoints
/commerce/catalog/* · /commerce/carts/* → Commerce module
catalog · cart · checkout · inventory
  • All calls are server-side. The Next.js app calls Aonik from Server Components and route handlers; nothing Aonik-shaped is bundled into browser JavaScript. Public reads are cached (ISR, ~300 s) so the menu survives an Aonik blip.
  • Tenant resolution. Aonik's anonymous endpoints resolve the tenant from the X-Tenant-Id header or subdomain (Auth:TenantRouting). Day one: the storefront sends X-Tenant-Id from server config. See decision D3 for whether a storefront API-key model is needed before launch.
  • Route reconciliation is contained by design. The frontend's guessed paths (/dishes, /box-pricing, …) live in one class; they will be re-pointed at the real /commerce/* routes with no component changes.

Brand rule with an API consequence. Individual dishes never display a standalone price — only the box, personalisation deltas and signature upgrades carry prices. Dish variants still need internal prices for costing, margin reporting (spec 057) and any sum-of-components maths; the storefront DTOs simply must not be forced to expose them. Keep "price exists" and "price is displayed" independent.

6. Build plan — proposed specs

Working letters A–E here; final numbers assigned at authoring time (065 is the highest today, but the register has duplicate numbers at 041/042 — confirm free slots). Every spec follows house rules: anemic entities, module-scoped configuration classes, migrations via AonikDbContext only, generic naming per ADR-013.

Spec A size: L keystone — C and B depend on it

Commerce product option groups (configurable personalisation)

A first-class option model for configurable products, distinct from variants (discrete SKUs) and bundle slots (box composition).

Scope

  • Tenant-level option catalogue: ordered groups (key, label, help text, selection mode one/multi, sort) each holding options (key, label, note e.g. "225g", price, recommended-default flag, active).
  • Per-product narrowing: which groups apply to a product, which options within each group, an optional per-product recommended-default override, and per-product multi-select enablement. A product with no groups simply isn't personalisable.
  • Delta pricing: the adjustment for a selection is Σ(chosen option price) − (recommended default price) per group — multi-select sums every chosen option before subtracting the default once. Negative adjustments are first-class (choosing "No side" against a £2 default side is −£2).
  • Validation service: reject any selection containing an option the product does not offer (even if it exists in the catalogue), missing a required group, or violating selection mode. This is the server rule behind Step 2 AC-24.
  • Order landing: selections + computed adjustment are snapshotted onto cart lines and written into OrderItem.DetailsJson (and alongside OrderBundleSelection) so production sheets can render them. BOM-level consumption deltas (a protein swap changing ingredient demand) are explicitly phase 2 — flagged, not built here.
  • Signature-style per-unit product surcharge — a priced product attribute the quote engine reads (modelled here because it prices identically to an option delta).

Spec B size: M depends on A

Option-dependent product content (nutrition, ingredients, allergens, heating)

Authored content that changes with the customer's selection. The Step 2 spec is emphatic and right: the platform never computes nutrition. Swapping chicken for salmon changes protein, fat and the allergen declaration — no multiplier can produce that, and a wrong allergen line is a safety incident, not a display bug.

Scope

  • Default content block per product: nutrition figures, serving label, ingredients text, allergens text, heating steps.
  • Content variants: match rules over option selections ({"portion":"full"}, {"protein":"salmon"}) each carrying the authored figures and, where they differ, ingredients/allergens overrides.
  • Resolution endpoint: given a selection, return the best-matching authored variant, or the default flagged isStandardPreparation: true so the storefront shows "figures are for the standard preparation". Exact-match or default — never interpolated.
  • Admin authoring endpoints; content rides product create/update.

Sketch

ProductContent         ProductId, NutritionJson, ServingLabel, Ingredients?, Allergens?, HeatingJson
ProductContentVariant  ProductId, MatchJson, NutritionJson, ServingLabel, Ingredients?, Allergens?

GET /commerce/catalog/products/{slug}/content?selection=portion:full,protein:salmon

Structured columns over free-form AttributesJson is deliberate — see decision D2.

Spec C size: L depends on A · implements the Step 2 server contract

Box-builder carts — size pricing, line editing, authoritative quotes

Evolves the Commerce cart into the mutable "box" the Step 2 spec defines, keeping the bundle product as the catalog anchor (see decision D1).

Scope

  • Size-parameterised bundle pricing: a price schedule on the bundle product — preset rows (6→£95, 12→£170, 18→£240, each with badge/blurb merchandising copy) plus a formula (base price, base size, per-added-space price, min, max). Presets always win over the formula at their size. Min/max are configuration, never constants.
  • Cart as box session: cart gains the bundle reference + chosen size; lines gain personalisation selections, the computed adjustment snapshot, and the per-unit surcharge snapshot. Identical dish + identical selection merges into one line (multi-select compared order-insensitively).
  • Hard capacity ceiling: any write that would push total units past the size is rejected — growing the box first is the only overflow path. No silent drops when shrinking: a resize below current units is rejected with the count to remove.
  • Authoritative quote: every write returns the full box + a breakdown — box price, personalisation total, per-unit surcharges ("signature upgrades"), delivery list-vs-charged, total, units, spaces left, is-full. Client-supplied prices are ignored (Step 2 AC-22).
  • Continue gate: an endpoint that validates units == size and advances the cart; rejects otherwise (AC-20).
  • Drift handling: an option retired while sitting in a cart remaps to the product's current recommended default on load, reprices, and reports what changed.
  • Checkout materialisation: unchanged spine — one ProductPurchase order; selections land in OrderBundleSelection + DetailsJson so specs 055/056 production sheets keep working, now with personalisation detail.
  • Public routes to complete the set: update line, remove line (service exists, route doesn't), resize, quote, continue.

Spec D size: M (phase 1) · phase 2 at checkout build-out independent — can start immediately

Fulfilment promise — delivery calendar & earliest-delivery date

The most-repeated single data point in the storefront ("Earliest delivery: Wednesday 6 August" appears on five surfaces) and currently unrepresentable in Aonik.

Phase 1 — the promise

  • Per-tenant fulfilment calendar: dispatch/delivery days of week, order cutoff time, preparation lead days, optional per-day capacity, optional blackout dates.
  • A computation service: now + cutoff + lead + next eligible delivery day (+ capacity check) → earliest delivery date. Public endpoint returns it; storefront caches briefly.
  • Admin CRUD for the calendar; seedable via config pack.

Phase 2 — delivery at checkout (scoped here, built with Steps 3–5)

  • Delivery address capture on checkout (cart/checkout command has none today).
  • Customer-chosen delivery date/slot validated against the calendar; recorded on the order so kitchen planning can window on delivery date rather than order-creation time.
  • Delivery fee display semantics (list price struck through vs charged — launch: £10 → Free) feeding the quote breakdown.
FulfilmentCalendar  TenantId, DeliveryDaysMask, CutoffLocalTime, LeadDays, Timezone, CapacityPerDay?
GET /commerce/config/delivery   →  { earliestDeliveryDate: "2026-08-06" }
Spec E size: M independent — read-side; unlocks the FE swap earliest

Storefront merchandising & configuration

Everything the browse experience needs beyond raw catalog rows.

Scope

  • Collections: named, ordered, curated product groups with a kind (featured rail, curated group like "Carb-conscious") and per-item rank. This is the generic construct behind "featured dishes" and "featured groups" — and later, seasonal edits.
  • Facet configuration: per-tenant ordered facet groups, each declaring its match semantics — by category, by tag, by attribute equality, or by numeric range over an attribute (calorie bands; a future protein or salt band with zero frontend change). Public endpoint serves the definitions; browse endpoint accepts them as filters.
  • Search hardening: per-product hidden keywords — matched by search, present in no DTO (Step 2 AC-28: a customer searching "party" finds the dish; the word never renders).
  • List DTO enrichment: hero image, tags, selected attributes (spice, badges, surcharge) on the browse row so a menu grid renders without N detail calls. Explicitly not a retail price field — see the brand-rule callout in §5.
  • Public config document: one endpoint serving the storefront's tunables — box size bounds and presets (from Spec C data), delivery display values, results page size, UI trigger points — so the frontend hard-codes nothing.
  • Public category list endpoint; product update + media list/reorder admin endpoints as supporting cast.

7. Decisions to settle

D1 — Is the box a product or a cart? decided 2026-07-21
Options: (a) model every box size as its own bundle product; (b) make the cart itself the box, with the bundle product as its definition/anchor.
Decision: (b) — the cart is the box. A 6–30 formula-priced size range collapses into 25 near-identical products under (a), and the "grow the box" flow becomes a product swap. Under (b) the bundle product stays the catalog anchor (homepage box offers, kitchen integration, order recording) while size and lines live on the cart — matching the Step 2 contract exactly. Checkout still materialises the standard bundle/order shape, so nothing downstream changes.

D2 — Nutrition storage: structured entities or AttributesJson? decided 2026-07-21
Decision: structured (ProductContent/ProductContentVariant). Allergen declarations are a safety surface — they deserve schema, validation and admin screens, not a JSON blob convention. General display attributes (spice level, badges) stay in AttributesJson, which is what it's for.

D3 — Storefront authentication. decided 2026-07-21
Day one, the storefront sends X-Tenant-Id server-side — works with today's middleware and everything sensitive stays anonymous-safe (carts are token-scoped, payments are guest intents). Decision: no API-key model. Ship on X-Tenant-Id + CORS allow-list; revisit only if real traffic ever demands per-client credentials.

D4 — One taxonomy, three axes. decided 2026-07-21
The design templates carry two overlapping groupings (homepage rail categories vs menu wellness goals) — the frontend code itself flags the clash. Decision: one primary category per dish (Mains, Soups & Stews…), any number of facet tags (wellness goals, dietary, meal type, badges), and collections for curated rails. "Carb-conscious" then exists once — as a collection and/or tag — instead of ambiguously as a category.

D5 — Step 2 open product call (frontend-only, for Abby). When one dish sits in the box as two different versions, what do the card's +/− controls act on? The Step 2 spec recommends hiding the stepper in that state (quantity changes happen where the version is unambiguous). No Aonik impact — recorded here so it isn't lost.

Frontend alignment debts (AbbysTable repo, tracked here so they're not orphaned): the client cart still implements the "extras overflow" pricing that Step 2 v1.1 deleted (box size is now a hard ceiling); personalisation options are fetched globally but the contract is per-dish; and once Spec C lands, CartProvider's localStorage box becomes a cache over the server box rather than the source of truth. All are contained by the frontend's own seams.

9. Out of scope for this plan

  • Subscriptions / repeat orders — explicitly out of the Step 2 spec; revisit post-launch.
  • Gifting and the curated-box journey — distinct flows the templates reserve; nothing here precludes them (a curated box is just a bundle with fixed selections).
  • Delivery slot booking v2 — capacity-aware customer slot selection beyond the phase-2 date choice.
  • BOM consumption deltas for personalisation — protein swaps changing prep-list ingredient demand; flagged in Spec A, built when kitchen volume justifies it.
  • Customer accounts, loyalty, marketing — the whole journey is guest-first by design.
  • Frontend implementation work — tracked in the AbbysTable repo; this plan only pins the contract it consumes.
