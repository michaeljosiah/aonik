Commerce box add-on false “unavailable” on add

A defect in the Spec 071 add-extra path. POST /commerce/carts/{cartId}/extras returns the add-on it just created flagged isUnavailable: true with a corresponding reason: "unavailable" change, for an in-stock, active, priceable extra. An immediate GET of the same cart returns the same line isUnavailable: false with no changes. The add response contradicts the persisted truth, and by Spec 071 §5 / §8 X2 an unavailable line blocks continue and checkout — so a client that trusts the add response (as the quote contract says it should) is blocked from a legitimate order.

1. Summary

Spec 071 §5 states that an unavailable extra must flag (never vanish) and block continue/checkout until removed, and §8 X2 makes a priceless AddOn line unavailable. Both are correct rules. The defect is that the add-extra path applies the unavailable verdict to a line that is not unavailable: adding an in-stock, active, priceable extra returns that line flagged, together with a spurious unavailable entry in changes[].

The verdict does not persist. A GET of the same cart, in the same second, returns the line available with an empty changes[]. So the fault is in the transient state the add path computes its authoritative availability pass over — not in the stored line, which is correct. The quote contract (Spec 068 §7) is that every mutation returns the whole box, quote and changes, and clients render that response rather than re-reading; a spec-conforming client therefore surfaces the false alarm and, because the flag gates the gates, can be blocked from checking out an order that is in fact placeable.

Fixed on this branch. Root cause confirmed and corrected in BoxCartService.AddExtraLineAsync; a regression test (BoxAddOnTests.Spec085_FreshInStockExtra_IsAvailable_AndAddResponseMatchesRead) fails on the prior code and passes on the fix. Verified end to end against a live instance — the POST /extras response now returns the added line available with an empty changes[], agreeing with an immediate GET. See §5.

2. Reproduction

Captured against a local instance (tenant with the AbbysTable catalog seeded), extra variant with 497 units available. Product Active, variant IsActive, priced in the cart currency.

2.1 The extra is in stock

GET /commerce/catalog/variants/{extraVariantId}/availability
→ { "productVariantId": "…", "available": 497.0000 }

2.2 Create a box cart, then add the extra

POST /commerce/carts/box            { bundleProductId, size: 6 }        → 201, cart created
POST /commerce/carts/{cartId}/extras { productVariantId, quantity: 1 }  → 200

The POST /extras response body (trimmed to the relevant fields):

{
  "changes": [
    { "lineId": "…", "reason": "unavailable",
      "group": null, "from": null, "to": null, "priceDelta": null, "mergedIntoLineId": null }
  ],
  "box": { "lines": [
    { "name": "Puff Puff", "lineKind": "AddOn", "quantity": 1, "isUnavailable": true }
  ] }
}

2.3 Read the same cart back immediately

GET /commerce/carts/{cartId}
{
  "changes": [],
  "box": { "lines": [
    { "name": "Puff Puff", "lineKind": "AddOn", "quantity": 1, "isUnavailable": false }
  ] }
}

Same cart, same variant, nothing changed between the two calls. The add response and the read disagree about the identical persisted line.

3. Expected vs actual

SignalExpectedActual (on POST /extras)

Agreement with an immediate GETIdentical — the mutation response is the authority (068 §7)Contradicts it (GET: available, no changes)

The read is right. GET rebuilds availability from the persisted cart and returns the correct verdict, which tells us the stored line and the underlying stock are fine. Only the add path's response is wrong, and only for the just-added line.

4. Impact & severity

P1 — a launch-path correctness defect, not cosmetic. Spec 071 §5 and §8 X2 give isUnavailable teeth: an unavailable line “block[s] continue/checkout until removed”. The mutation response is defined (068 §7) as the box the client renders without re-reading. So a spec-conforming Step 3 client that gates continue/checkout on the add response will refuse to advance an order that contains a perfectly available extra — the customer is told a dish is no longer available and cannot proceed.

  • Every extras add is affected, deterministically — not an edge case. It fires for in-stock, active, priceable extras, which is the normal case.
  • It clears on the next cart load, so a client that happens to re-read before gating (rather than trusting the mutation response) escapes it — but relying on that is relying on clients to violate the 068 §7 contract.
  • It manufactures a change entry. A18's drift-stop discipline depends on changes[] meaning “the catalogue moved under you”. A spurious unavailable change on a routine add erodes that signal — the notice a customer sees is false, and a client cannot distinguish it from a real one.

5. Localisation

src/Aonik.Commerce/Services/Checkout/BoxCartService.cs → FlagUnavailableAsync, reached from the add path's authoritative pass (RunAsync finalize, the emitChanges: true call). The load path (GetBoxCartAsync → BuildDtoAsync) runs the same method over context built purely from the persisted cart and returns the correct verdict — so the divergence is in the transient state the add path holds when the pass runs, not in the pass's logic against stored data.

Confirmed root cause — the variant lookup, not X2 or X5. The pass's very first check is var variant = context.Variants.GetValueOrDefault(line.ProductVariantId) followed by var unavailable = variant is null || …. context.Variants and context.Products are populated by BuildContextAsync from the lines that existed before the mutation. AddExtraLineAsync then adds the new line to context.AddOnLines — so the pass iterates it — but never registers the new line's variant or product in those dictionaries. So GetValueOrDefault returns null, the variant is null guard fires, and the line is flagged and a change emitted. The X2 and X5 branches never run: the guard short-circuits first.

  • Why dishes escape it. AddLineCoreAsync appends a new dish only to cart.Items, never to context.BoxLines, so the post-mutation pass never iterates a freshly-added dish — it is validated by its own add-time guards and left out of the re-flag. Extras broke that pattern by joining context.AddOnLines.
  • Why the read is correct. A GET (and checkout) builds the context from the persisted cart, which already contains the line, so its variant is loaded into context.Variants and the guard passes.
  • Why the split path was already fine. A split creates a line for a variant already in the cart, so its variant is already in context.Variants; only a brand-new-to-the-cart variant exposed the gap.

Resolution

The freshly-added line already correctly joins context.AddOnLines (matching the split path); the add path now also registers its variant and product in context.Variants / context.Products, so the authoritative pass evaluates it on the same footing as every other line — active, priced (X2), and in stock (X5) — and finds it available. Purely additive; no rule, contract, or genuine unavailability behaviour changes. The alternative — excluding the new line from the pass entirely, as dishes are — was rejected as the weaker fix: it leaves the line's demand out of the same-request X5 aggregate for a variant it might share, whereas registering the variant keeps the pass whole.

6. Required behaviour

#Rule
D1Adding an active, priceable extra with sufficient stock MUST return that line isUnavailable: false and MUST NOT add an unavailable entry to changes[].
D2The POST /extras response and an immediate GET of the same cart MUST agree on every line's isUnavailable and on changes[]. The mutation response is authoritative (068 §7); it may not report a verdict the persisted cart contradicts.
D3The genuine unavailability rules are unchanged and MUST still fire: an inactive variant/product, a priceless AddOn (X2), and aggregate over-demand (X5) each still flag and still block the gates. This defect is the FALSE positive only; no true positive may be lost to the fix.
D4A regression test MUST assert the add-response/read agreement (D2) for a routine in-stock extras add, so this cannot silently return.

7. Acceptance criteria

#Given / when / then
C1Box cart; extra variant active, priced, 497 available; add quantity 1 → response line isUnavailable: false, changes[] empty; total counts the add-on.
C2The same add → an immediate GET of the cart returns the identical line state and empty changes[] (add-response = read).
C3Continue and checkout after the add succeed — no R8/unavailable block for the available extra (the §5 / X2 gate is not tripped by a false flag).
C4Regression of the real rules: an extra whose price in the cart currency was removed still flags unavailable on the next load (X2); a variant deactivated still flags; aggregate BoxDish+AddOn demand exceeding stock still flags (X5). Each still blocks the gates.
C5Add two of the same extra (merge) and split via applyToUnits → neither the merged nor the split line is falsely flagged, and the response agrees with a subsequent read.

8. Out of scope

  • Any change to the isUnavailable / changes[] contract, the blocking semantics (§5, R8), or the quote (068 §7). This spec makes the add path obey those contracts, it does not alter them.
  • Dish (BoxDish) lines — no false flag was observed there; if the fix is in shared code, the regression net (D4/C4) should still cover a dish add for safety, but the behaviour change is add-on-specific.
  • The storefront workaround. AbbysTable currently drops an unavailable change whose own payload line reports available (mapBoxCart in web/src/lib/aonik/map.ts); that guard becomes a no-op once this lands and can be retired then, not before.
