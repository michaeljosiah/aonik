Spec 056 Status: Draft Size: Medium Priority: P3 Domain: Commerce / Production

Production / work orders & the kitchen sheet — the make-side counterpart of checkout

Turns planned demand into an executed production run: a ProductionOrder that lists the dishes to prep and, on release, consumes ingredient stock by exploding each dish through its recipe. This is the make-side counterpart of checkout — where checkout (Spec 042) reserves and commits saleable variant stock, a production run commits ingredient stock, drawing down the very same generalised InventoryLevel stock checkout commits into, fanned out over recipe components instead of bundle variants. Part of the maker-operations family (050–057); the recipe explosion it consumes is defined by the keystone, Spec 050. Everything lives in Aonik.Commerce and references only SharedKernel + Aonik.Ordering — never Aonik.Finance.

1. Summary

The operations manager has already reviewed the week's production sheet and prep list (Spec 055): 40 portions jollof, 30 portions steak ⇒ 10 kg rice, 5 kg tomato, …. This spec is the kitchen-sheet moment — committing to actually make that batch. A ProductionOrder records the run: the dishes and portion counts to produce (its ProductionOrderLines), and a lifecycle from Planned to Completed.

The two state changes that carry weight:

  • Release — the moment the kitchen is told to start. Releasing the order consumes ingredient stock: each line's recipe was exploded once at creation and frozen onto the line as a per-portion snapshot (§7); release merges those snapshots into one bill and draws each ingredient's Spec 052 level down directly — the same generalised InventoryLevel rows bundle checkout commits into, fanned out over recipe components instead of component variants. Release is all-or-nothing in ONE SaveChanges on the shared scoped Commerce context, over the Spec 042 oversell guard: a shortfall consumes nothing, and a concurrent-release conflict recomputes from scratch (§9), so either every ingredient is consumed or none is.
  • Complete — the run is done. Optionally it yields finished-good stock: the produced ProductVariant's InventoryLevel.OnHand is incremented by the ProducedQuantity, closing the make-to-stock loop (finished goods that Spec 042 checkout can then sell).

The kitchen sheet is a printable/exportable projection of the order plus its per-dish recipe-component prep detail — what to prep and how much — served by a read endpoint.

Success signals An operator (or the commerce-agent) creates a production order — optionally seeded from a Spec 055 production sheet for a window — releases it and watches ingredient stock draw down through recipe explosion (fail-fast if short), completes it and (optionally) sees finished-good stock rise, and prints the kitchen sheet. Re-releasing an already-released order is a no-op — stock is never double-consumed. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering; dotnet test Aonik.sln stays green with new unit tests over release consumption, all-or-nothing shortfall, concurrent-release atomicity, snapshot invariance under a mid-flight recipe edit, idempotent re-release, and completion yield.

2. Context & motivation

Spec 055 answers what and how much to make as a read-only aggregation over incoming orders; it persists nothing and consumes no stock. But the operations manager's day does not end at a printed prep list — they commit to a batch, tell the kitchen to start, and at that moment raw materials leave the shelf. That transition — planned demand becoming a real production run that draws down inventory — is the work order, standard in any light-manufacturing / back-office ERP. It is the make-side twin of the sell-side event Spec 042 already ships: checkout. Checkout reserves and then commits saleable finished-goods stock; release commits the raw-material stock those goods are made from.

Because Spec 052 already generalised InventoryLevel to stock both finished variants and raw ingredients — and Spec 042 already has a commit path that fans one sale out over many component variants — this spec is deliberately small. It adds a work-order record and its lifecycle, and wires release to fan out over recipe components onto those same generalised levels. The only genuinely new logic is the state machine, the recipe-driven fan-out target, and the kitchen-sheet projection.

Scope discipline is explicit: this is the thin maker-ops work order the persona needs — not a full MES with routings, work centres, operation sequencing, machine scheduling, or lot genealogy. Those are noted as open extensions, not built.

4. Scope (in / out)

In scope

  • ProductionOrder + ProductionOrderLine entities + IProductionOrderService (create — optionally seeded from a Spec 055 production sheet for a window — release, complete, cancel) + admin endpoints.
  • Release consumes ingredient stock: merge each line's frozen recipe snapshot into one bill, pre-check every ingredient's Available = OnHand − Reserved, then apply every level decrement + the status flip in ONE SaveChanges on the shared scoped Commerce context, over the oversell guard; transactionally all-or-nothing — fail fast on a shortfall (nothing applied), recompute from scratch on a concurrency conflict.
  • Complete optionally yields finished goods: increment the produced variant's InventoryLevel.OnHand by ProducedQuantity (make-to-stock; optional).
  • Guarded, idempotent state transitions: consume only on the Planned → Released edge; re-release never double-consumes.
  • The kitchen sheet: a printable/exportable projection of a production order + its per-dish recipe-component prep detail, via a read endpoint.
  • New Commerce DbSets on CommerceDbContext + AonikDbContext; one tool-generated migration (CommerceProductionOrders).
  • Commerce-agent read tool for the kitchen sheet + medium-gated write tools for create / release production order.

Out of scope

  • Ingredient stock mechanics themselves (levels, reserve/commit/release, low-stock alerts) — delivered by Spec 052; this spec only draws down the levels it owns.
  • The demand aggregation and prep-list explosion — Spec 055; a production order optionally seeds from its output.
  • Ingredient cost / production-run costing / variance valuation — Spec 051 and Spec 057.
  • Routings, work centres, operation sequencing, machine/labour scheduling, lot/batch genealogy, scrap accounting — noted under Open, not built.
  • Reserving ingredient stock at Planned (a soft hold before release) — considered under Open; v1 consumes only at release.

5. Constraints & guardrails

  • No reference to Finance. Aonik.Commerce still references only SharedKernel + Aonik.Ordering. A production run touches inventory, not money; no ledger, no payment, no Finance coupling (ADR-005).
  • Anemic entities. ProductionOrder/ProductionOrderLine are { get; set; } data containers implementing ITenantScoped + AuditableEntity (ADR-002); the lifecycle, explosion wiring, and fan-out all live in IProductionOrderService, returning DTOs.
  • Single migration stream. EF-CLI-generated against AonikDbContext; Ank-prefixed tables; CommerceDbContext is runtime scoping with no migrations; agents never hand-author migrations.
  • Release consumes ingredient stock, not variant stock. A production run draws down ingredient InventoryLevel rows (Spec 052) via recipe explosion — never the finished variant's own stock. Completion is the only step that adds finished-variant stock (§10). The Spec 042 Bundle (which draws down component variant stock) is a distinct concept and untouched (§9).
  • Idempotent, guarded transitions. Consumption fires exactly once, on the Planned → Released edge; every transition validates the current status first (§8). No double-consume on re-release; no draw-down on cancel.
  • Agents propose; systems execute. The kitchen sheet is a direct agent read; create/release are medium (in-session confirmation, args-hash-bound) because release moves real inventory; every AI action records an AiRun.

7. Domain model

All entities are anemic, ITenantScoped, inherit AuditableEntity.

class ProductionOrder     { Guid Id, TenantId;
                            DateTime PlannedFor;        // when this run is scheduled to be made
                            string   Status;            // Planned | Released | InProgress | Completed | Cancelled
                            string?  Notes;
                            DateTime? ReleasedAt;       // the instant ingredient stock was consumed (§9)
                            DateTime? CompletedAt; }    // the instant the run closed (§10)

class ProductionOrderLine { Guid Id, TenantId, ProductionOrderId, ProductVariantId;
                            decimal  PlannedQuantity;   // portions to produce
                            decimal? ProducedQuantity;  // actual portions made (recorded at Complete)
                            string   RecipeSnapshotJson; } // PER-PORTION components frozen at CREATION (§9/§11)
                                                           // required — a line never carries an empty snapshot

ProductVariantId is a real intra-module reference to the Spec 042 finished ProductVariant being produced — the same variant a Spec 050 Recipe is attached to, which is exactly why a line can be exploded into ingredients. PlannedQuantity is what to make; ProducedQuantity is nullable so the record can be created and released before the actual yield is known, then reconciled at completion (planned ≠ produced is the normal case — see Risk register). RecipeSnapshotJson holds the line's per-portion exploded components (ingredient id / name / base unit / quantity-per-portion — Spec 050's ExplodeAsync(variant, 1), scale-invariant), frozen eagerly at creation; both the kitchen sheet (§11) and release consumption (§9) read this snapshot rather than re-exploding the live Spec 050 recipe, so an edit to that recipe between print and release cannot make the two diverge — and the kitchen sheet stays a pure read (no lazy freeze on a GET). A variant with no active recipe rejects creation, naming it; the from-sheet seed instead skips it and reports it in SkippedVariants — either way a line never carries an empty snapshot. It is the per-line materialisation of Spec 050's recipe-versioning open decision: until that lands, this run captures its own component bill. Status is a free string with a known-values helper (mirroring the platform's open-enum convention), driven only through the service's guarded transitions (§8).

8. Production-order lifecycle

IProductionOrderService owns a small, guarded state machine. Each transition validates the current Status before acting and is idempotent on its target edge — critically, stock is consumed exactly once, on Planned → Released.

create (optionally seed lines from Spec 055 sheet) │ ▼ ┌───────────┐ cancel │ Planned │ ─────────────┐ └───────────┘ │ │ release │ consume ingredient stock (§9) │ all-or-nothing recipe fan-out ▼ ▼ ┌─────────────┐ ┌───────────┐ │ Cancelled │ (terminal) │ Released │ └─────────────┘ └───────────┘ no stock consumed on cancel-from-Planned │ (optional) start ▼ ┌─────────────┐ │ InProgress │ └─────────────┘ │ complete (optional) yield finished-good stock (§10): variant InventoryLevel.OnHand += ProducedQuantity ▼ ┌─────────────┐ │ Completed │ (terminal) └─────────────┘ guards: release only from Planned → consume; from Released = idempotent no-op (stock untouched); any other status → conflict start only from Released → InProgress (optional sub-state; no stock effect) complete only from Released|InProgress → else conflict cancel only from Planned|Released|InProgress → else conflict; a post-release cancel does NOT auto-restore consumed stock (auto-reversal stays Open) — reconcile via a Spec 052 stock adjustment; the reason is appended to Notes

InProgress is an optional operational sub-state between release and completion (the kitchen is actively cooking); it carries no stock effect. The two stock-moving edges are release (draw down ingredients, §9) and complete (optionally add finished goods, §10). A cancel from Planned is clean; a cancel after stock has been consumed is allowed but does not restock — only the auto-reversal of the consumption remains an Open decision.

9. Consuming ingredient stock on release — recipe fan-out (grounded: direct single-commit consumption)

This is the heart of the spec, and it is almost entirely reuse. Spec 042 checkout already fans a single sale out over many stock lines: a bundle holds no stock of its own, so its sale fans out over its selected component variants, drawing each down on the shared InventoryLevel rows (Spec 042 §10/§12). A production run is the same shape with two substitutions — the fan-out source is a recipe snapshot (not a bundle selection), and the drawn-down rows are ingredient InventoryLevels (Spec 052, not variant rows). Grounded against the landed inventory API: the landed CommitAsync(holdRef) is the second half of a reserve-then-commit two-phase — two SaveChanges with a TTL'd hold between — i.e. exactly the reserve-at-Planned soft hold this spec defers (Open), and the per-ingredient CommitAsync(ingredientId, qty, ref) this section originally sketched does not exist. Release therefore consumes directly — which is stronger than the original sketch and exactly R3's all-or-nothing property:

Bundle checkout (Spec 042 §12) Production release (this spec) ──────────────────────────────── ────────────────────────────────── one box line one ProductionOrder (its lines) fans out over selection slots fans out over recipe components → component ProductVariants → frozen §7 snapshots → Ingredients reserve → commit (two-phase hold) direct draw-down, ONE SaveChanges (variant InventoryLevel rows) (ingredient InventoryLevel rows, Spec 052 — the same generalised levels, no new primitive) ReleaseAsync(productionOrderId): // landed: ProductionOrderService, direct consumption 0. guard: Status == Planned (Released ⇒ idempotent no-op; anything else ⇒ conflict) 1. bill = merge(lines: snapshot.QuantityPerPortion × PlannedQuantity) // the FROZEN snapshots (§7), → [ { IngredientId, RequiredQuantity (BaseUnit) }, … summed across dishes ] // NOT a live re-explode 2. resolve the TRACKED default-location ingredient levels // missing level = zero stock; never created here 3. pre-check availability for EVERY ingredient in one pass // Available = OnHand − Reserved → if any Available < RequiredQuantity ⇒ throw InsufficientStock naming it, consume NOTHING 4. apply ALL: level.OnHand -= required per ingredient; Status = Released; ReleasedAt = now 5. SaveChanges ONCE on the shared scoped CommerceDbContext // single-commit all-or-nothing; (every row rides its rowversion token — the Spec 042 oversell guard) ── on DbUpdateConcurrencyException: RECOMPUTE FROM SCRATCH, bounded ×3 ── reload every dirty tracked entry to committed state, then re-run from step 0: rival release won ⇒ the step-0 guard turns this call into the idempotent no-op rival drained stock ⇒ the fresh pre-check fails fast, still consuming nothing (deliberately NOT Spec 054's reload-and-reapply: a signed increment commutes with rival writes, but a guarded decrement does not — re-applying staged deltas over half-reloaded state could double-consume or slip past the availability check)

All-or-nothing is one commit, not per-line best-effort. The whole-bill pre-check (step 3) and every level decrement plus the status flip (step 4) ride one SaveChanges, and each ingredient row carries the Spec 042 oversell guard on its row concurrency token. A pre-check alone is not enough: two concurrent releases could both pass it against the same on-hand and then over-consume. Binding everything to a single commit closes that window — if any row hits a DbUpdateConcurrencyException, the whole attempt is discarded and recomputed from scratch on committed state (bounded, three attempts), so either every component line commits or none does. Negative stock at release stays out of v1 entirely — release always fails fast, naming the short ingredient with its figures; the backorder/"cook anyway" flag remains an Open escape hatch, deliberately not plumbed. The bill itself is read from each line's frozen RecipeSnapshotJson (§7), not a fresh explosion, so what release consumes is exactly what the printed kitchen sheet showed. Because consumption is bound to the single Planned → Released edge and guarded by status (step 0), a re-release is a no-op and stock is never double-consumed — the central correctness property this spec must hold.

Note This reuse is why the spec is Medium, not Large: no new inventory primitive is introduced. Spec 052 already generalised InventoryLevel and InventoryService to stock ingredients; Spec 050 already owns explosion; Spec 042 already owns the rowversion oversell guard every level row carries. This spec composes them behind one guarded transition.

10. Yielding finished goods on complete

A production run's counterpart to consuming raw materials is producing finished goods. On complete, the service optionally yields finished-good stock — for each line, it increments the produced ProductVariant's InventoryLevel.OnHand by that line's ProducedQuantity (falling back to PlannedQuantity when produced is unset). This closes the make-to-stock loop: goods made here become saleable stock that Spec 042 checkout reserves and sells.

CompleteAsync(productionOrderId, actualQuantities?, yieldFinishedGoods = true): 0. guard: Status ∈ { Released, InProgress } (else conflict) 1. record per line: ProducedQuantity = explicit actual ?? PlannedQuantity (0 = a failed batch) 2. STAGE the terminal flip on the tracked order: Status = Completed; CompletedAt = now 3. if yieldFinishedGoods: // make-to-stock foreach line with ProducedQuantity > 0: InventoryService.AdjustOnHandAsync(variant, +ProducedQuantity) // Spec 054 signed increment — the FIRST increment's SaveChanges (same scoped CommerceDbContext) commits the staged flip + produced quantities WITH the yield: the Spec 054 marker pattern — a Completed status can never claim a yield that did not land else: SaveChanges (flip + produced quantities only)

Yield is kept optional because not every tenant is make-to-stock — some cook strictly to order (each portion is already tied to a customer order and should not re-enter sellable stock). The yieldFinishedGoods flag (default on for the make-to-stock persona this family targets) keeps both postures supported without branching the entity. The yield rides the landed Spec 054 AdjustOnHandAsync path — a signed, commute-safe increment, never an overwrite — so a racing checkout commit or goods receipt loses nothing; and the documented failure direction is Spec 054's: a crash mid-yield on a multi-line run leaves a Completed order with an under-applied yield, visible against the recorded produced quantities and reconciled by a Spec 052 stock adjustment — never double-counted. The finer question — make-to-order runs that discharge specific customer orders rather than replenish anonymous stock — is an Open decision; v1 treats a run as make-to-stock and does not link a production order back to the orders it fulfils.

11. The kitchen sheet

The kitchen sheet is the human-facing artefact of a production order: a printable/exportable projection a chef works from at the pass. It is a pure read — a ProductionOrder joined to, per line, the exploded recipe-component prep detail (what to prep and how much). It is the production-run analogue of Spec 050's prep list, but scoped to one concrete run and grouped by dish rather than merged into one bill.

GET /commerce/admin/production-orders/{id:guid}/kitchen-sheet → KitchenSheet (the landed /commerce/admin/… read surface, house read policy: AdminUserPolicy) header: { productionOrderId, plannedFor, status, notes } dishes: foreach line → { productVariantId, productName, variantName, plannedQuantity, producedQuantity, components: [ { ingredientId, ingredientName, baseUnit, quantityPerPortion, requiredQuantity } // = snapshot.QuantityPerPortion × plannedQuantity … ] } // per-dish, replayed from the §7 snapshot — never a live explosion totals: merged bill of materials across all dishes // sum of the per-line snapshots — the shopping/prep summary (the snapshot was frozen at CREATION (§7); every call replays it — the kitchen sheet is a pure read)

The projection is assembled from the same per-line RecipeSnapshotJson (§7) that release consumes, so it stays consistent with what release actually draws down: creation exploded each line once (ExplodeAsync(variant, 1) per dish) and froze the per-portion result onto the line; the totals block is the merge of those same snapshots scaled by planned portions — by construction identical to the bill release consumes. Reading the snapshot rather than re-exploding is what makes the guarantee hold: if the Spec 050 recipe is edited after the sheet is printed but before release, both still replay the frozen components, so the sheet the kitchen worked from and the bill release consumes cannot diverge. Rendering to PDF/print is a frontend concern; the endpoint returns the structured KitchenSheet DTO. A variant with no active recipe never reaches a line at all: the explicit create rejects it by name and the from-sheet seed skips it and reports it in SkippedVariants (§7), so the gap surfaces at planning time — a dish on the pass can never be silently empty. Dish names resolve from the live catalog with LEFT-join semantics (the Spec 055 convention): a variant that no longer resolves still shows, with diagnostic placeholder names, never dropped.

12. Agent & tools

The existing commerce-agent gains production-order tools, classified by CommerceToolApprovalManifest and wrapped by the Spec 032 gate — no change to the gate:

ToolTierEffect
commerce_get_kitchen_sheetreadDirect execution; returns the KitchenSheet projection for a production order; tenant scope from context.
commerce_create_production_ordermediumCreates a run from explicit (variant, portions) lines; the Spec 055 from-sheet seed is an admin endpoint in v1, not a tool. In-session confirmation, args-hash-bound; records an AiRun.
commerce_release_production_ordermediumReleases a run → consumes ingredient stock (§9). Medium because it moves real inventory: in-session confirmation, args-hash-bound; records an AiRun.

Release moves stock but not money, so it is medium (in-band once, after in-session confirmation) — consistent with the family's other inventory writes (commerce_receive_goods, commerce_set_ingredient_stock) and unlike the high money tools that are marshalled into a durable Finance Proposal. Complete and cancel are admin-endpoint operations in v1; promoting them to gated tools is trivial if an agentic run-management surface is wanted.

13. CommerceDbContext & migrations

Two new Ank-prefixed tables — AnkProductionOrders and AnkProductionOrderLines — are created by one EF-CLI migration against AonikDbContext. Each entity is added to both CommerceDbContext (runtime scoping) and AonikDbContext (canonical stream); both are tenant-scoped (neither global). Configurations live in Persistence/Configurations/Production as IEntityTypeConfiguration<T> classes. No new inventory tables — release and yield reuse the Spec 052 InventoryLevel schema. 

dotnet ef migrations add CommerceProductionOrders --project src/Aonik.Infrastructure --startup-project src/Aonik.Api

15. Requirements

#Requirement
R1A ProductionOrder (planned-for date, status, optional notes) with one or more ProductionOrderLines (variant + planned portions) can be created — optionally seeded from a Spec 055 production sheet for a window, skipping demanded variants without an active recipe and reporting them (SkippedVariants), never silently dropping them — listed, and cancelled; tenant-scoped.
R2Release consumes ingredient stock: the per-line snapshots (frozen at creation from Spec 050 ExplodeAsync(variant, 1), R9) are merged into one bill — per-portion × planned, summed per ingredient — and each ingredient's Spec 052 default-location level is drawn down directly, the same generalised levels Spec 042 checkout commits into; no new inventory primitive.
R3Release is transactionally all-or-nothing across every component line: the whole-bill availability pre-check (Available = OnHand − Reserved) and every level decrement plus the status flip ride ONE SaveChanges on the shared scoped CommerceDbContext, over the Spec 042 oversell guard (row concurrency token); a shortfall throws with nothing applied, and a concurrency conflict triggers a bounded recompute-from-scratch retry (reload every dirty entry, re-guard, re-validate — never a partial re-apply) so either all ingredients are consumed or none are — concurrent releases can never over-consume shared stock. Negative stock at release stays out of v1 (no flag plumbed; Open).
R4State transitions are guarded and idempotent: consumption fires exactly once on Planned → Released; re-releasing an already-released order is a no-op that never double-consumes; cancel from Planned consumes nothing.
R5Complete optionally yields finished-good stock: each line increments the produced variant's InventoryLevel.OnHand by ProducedQuantity (fallback PlannedQuantity); the yield is toggleable for make-to-order tenants.
R6A kitchen-sheet read endpoint (under /commerce/admin/…, house read policy) returns a projection of the order + per-dish recipe-component prep detail + a merged totals bill, assembled from each line's frozen RecipeSnapshotJson (R9) so it is byte-for-byte what release consumes even if the live recipe is edited between print and release; a variant lacking a recipe never reaches a line (rejected at create by name; skipped-and-reported by the from-sheet seed, R1), so the sheet is a pure read with no empty dishes.
R9Each ProductionOrderLine stores a recipe snapshot (RecipeSnapshotJson) — the per-portion exploded components frozen at creation (ExplodeAsync(variant, 1)); required and never empty (a no-recipe variant rejects the explicit create and is skipped-and-reported by the from-sheet seed); both the kitchen sheet and release read this snapshot, never a live re-explosion. This is the per-line stand-in for the Spec 050 recipe-versioning open decision.
R7Schema changes are EF-CLI-generated against AonikDbContext; Ank prefix (AnkProductionOrders, AnkProductionOrderLines); Aonik.Commerce holds no Aonik.Finance reference.
R8Agent tools are classified (commerce_get_kitchen_sheet read; commerce_create_production_order / commerce_release_production_order medium); every medium-gated invocation records an AiRun.

17. Verification

  • dotnet build Aonik.sln green; architecture test proves Aonik.Commerce has no Aonik.Finance reference.
  • Release consumes: with rice/tomato stock on hand and a jollof recipe (yield 4 ⇒ 1 kg rice, 0.5 kg tomato), create a run of 40 portions and release it ⇒ ingredient OnHand drops by 10 kg rice / 5 kg tomato via the single-commit draw-down; order → Released.
  • All-or-nothing: set rice short of the requirement; release throws InsufficientStock and no ingredient (including tomato) is drawn down; order stays Planned.
  • Concurrent releases: two releases racing on the same ingredient stock (enough for one run only) — exactly one commits the full bill; the other's conflict recomputes from scratch and fails fast on the fresh pre-check (or no-ops if the rival was a re-release); on-hand never goes below zero (conflict injected via the Spec 054 interceptor pattern — InMemory raises no rowversion conflicts of its own).
  • Snapshot invariance: generate the kitchen sheet, edit the Spec 050 recipe (change a component quantity), then release ⇒ consumption matches the printed sheet, not the edited recipe.
  • Idempotent re-release: releasing an already-Released order is a no-op; stock is unchanged (not double-consumed).
  • Completion yield: complete the run with ProducedQuantity=38 and yieldFinishedGoods=true ⇒ the variant's OnHand rises by 38; with the flag off, finished stock is unchanged.
  • Kitchen sheet: GET …/kitchen-sheet returns per-dish prep detail matching each line's frozen snapshot and a totals block equal to the merged snapshots; RecipeSnapshotJson was populated at creation (the sheet is a pure read); a no-recipe variant never reached a line (rejected at create; skipped-and-reported by the from-sheet seed).
  • Agent: commerce_release_production_order surfaces a medium approval; commerce_get_kitchen_sheet executes directly; each records an AiRun.
  • dotnet test Aonik.sln green (xUnit + FluentAssertions, InMemory + test tenant/user providers).

19. Decisions baked in

  • Release is the consume edge; complete is the yield edge. Raw materials leave stock on Planned → Released; finished goods (optionally) enter stock on completion.
  • Consumption draws down the same generalised Spec 052 levels checkout commits into — directly, over frozen snapshot components instead of bundle component variants; no new inventory primitive, and no reserve-then-commit two-phase (its soft hold is the §20 deferral).
  • All-or-nothing at release is one commit — the whole-bill pre-check, every level decrement, and the status flip share one SaveChanges over the Spec 042 oversell guard, recomputing from scratch (bounded) on a concurrency conflict; concurrent releases cannot over-consume.
  • Transitions are guarded and idempotent; stock is consumed exactly once — no double-consume on re-release.
  • The kitchen sheet is a pure read projection assembled from a per-line recipe snapshot frozen at creation, so it and release always consume the same bill even if the recipe is later edited.
  • Grow in place in Aonik.Commerce; no Finance reference (inventory, not money); migrations stay with AonikDbContext.
  • Release/create are medium agent tools (they move inventory); the kitchen sheet is a direct read.

20. Open design decisions

Open Negative stock at release. Whether an ingredient shortfall must hard-fail (v1 default) or may be permitted to drive stock negative — a "cook anyway / backorder the raw material" posture — behind a per-tenant or per-release flag. v1 fails fast and plumbs no flag; the flag is the future escape hatch.
Open Make-to-order linkage. Whether a production order should link back to the specific customer orders it fulfils (make-to-order: each portion discharges a real demand line and does not re-enter anonymous sellable stock) rather than replenishing stock (make-to-stock, v1). Would add a soft link from ProductionOrderLine to source order lines and suppress the completion yield for tied portions.
Open Reserve at Planned (soft hold) vs. consume only at Release. v1 draws stock only at release. An alternative reserves ingredient stock at Planned (a soft hold via the Spec 052 reserve path, mirroring how checkout reserves before capture) so competing runs cannot both plan against the same raw material, converting the hold to a commit at release — exactly the landed reserve→commit two-phase §9's direct consumption deliberately avoids in v1.
Open Scrap / actual-vs-planned variance capture. Recording scrap and the delta between planned consumption and actual ingredient usage (over-portioning, trim loss) as first-class variance, feeding food-cost accuracy in Spec 057. v1 consumes against the planned bill; variance is inferred, not captured.
Open Post-release cancel reversal. Whether cancelling an order after release should automatically restore consumed ingredient stock (a compensating release). v1 requires an explicit Spec 052 stock adjustment; auto-reversal risks masking real usage and is deferred.
Open Scheduling / sequencing of runs. Ordering and time-slotting production runs across shifts, stations, or work centres (a routing / MES concern). v1 carries a single PlannedFor date and no sequencing; full scheduling is out of the thin maker-ops slice.
