Spec 056 Status: Draft Size: Medium Priority: P3 Domain: Commerce / Production

Production / work orders & the kitchen sheet — the make-side counterpart of checkout

Turns planned demand into an executed production run: a ProductionOrder that lists the dishes to prep and, on release, consumes ingredient stock by exploding each dish through its recipe. This is the make-side counterpart of checkout — where checkout (Spec 042) reserves and commits saleable variant stock, a production run commits ingredient stock, reusing the very same InventoryService commit machinery but fanning it out over recipe components instead of bundle variants. Part of the maker-operations family (050–057); the recipe explosion it consumes is defined by the keystone, Spec 050. Everything lives in Aonik.Commerce and references only SharedKernel + Aonik.Ordering — never Aonik.Finance.

1. Summary

The operations manager has already reviewed the week's production sheet and prep list (Spec 055): 40 portions jollof, 30 portions steak ⇒ 10 kg rice, 5 kg tomato, …. This spec is the kitchen-sheet moment — committing to actually make that batch. A ProductionOrder records the run: the dishes and portion counts to produce (its ProductionOrderLines), and a lifecycle from Planned to Completed.

The two state changes that carry weight:

  • Release — the moment the kitchen is told to start. Releasing the order consumes ingredient stock: each line's recipe is exploded into a merged bill of materials once, frozen onto the line as a snapshot (§7), and each ingredient's stock is drawn down through the Spec 042 InventoryService commit path — the exact machinery bundle checkout already uses to fan a box out over its component variants, only here it fans a production run out over its recipe components. Release is all-or-nothing in a single transaction over the Spec 042 oversell guard: a shortfall or a concurrent-release conflict rolls the whole run back, so either every ingredient is consumed or none is.
  • Complete — the run is done. Optionally it yields finished-good stock: the produced ProductVariant's InventoryLevel.OnHand is incremented by the ProducedQuantity, closing the make-to-stock loop (finished goods that Spec 042 checkout can then sell).

The kitchen sheet is a printable/exportable projection of the order plus its per-dish recipe-component prep detail — what to prep and how much — served by a read endpoint.

Success signals An operator (or the commerce-agent) creates a production order — optionally seeded from a Spec 055 production sheet for a window — releases it and watches ingredient stock draw down through recipe explosion (fail-fast if short), completes it and (optionally) sees finished-good stock rise, and prints the kitchen sheet. Re-releasing an already-released order is a no-op — stock is never double-consumed. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering; dotnet test Aonik.sln stays green with new unit tests over release consumption, all-or-nothing shortfall, concurrent-release atomicity, snapshot invariance under a mid-flight recipe edit, idempotent re-release, and completion yield.

2. Context & motivation

Spec 055 answers what and how much to make as a read-only aggregation over incoming orders; it persists nothing and consumes no stock. But the operations manager's day does not end at a printed prep list — they commit to a batch, tell the kitchen to start, and at that moment raw materials leave the shelf. That transition — planned demand becoming a real production run that draws down inventory — is the work order, standard in any light-manufacturing / back-office ERP. It is the make-side twin of the sell-side event Spec 042 already ships: checkout. Checkout reserves and then commits saleable finished-goods stock; release commits the raw-material stock those goods are made from.

Because Spec 052 already generalised InventoryLevel to stock both finished variants and raw ingredients — and Spec 042 already has a commit path that fans one sale out over many component variants — this spec is deliberately small. It adds a work-order record and its lifecycle, and wires release to reuse the existing commit fan-out over recipe components. The only genuinely new logic is the state machine, the recipe-driven fan-out target, and the kitchen-sheet projection.

Scope discipline is explicit: this is the thin maker-ops work order the persona needs — not a full MES with routings, work centres, operation sequencing, machine scheduling, or lot genealogy. Those are noted as open extensions, not built.

4. Scope (in / out)

In scope

  • ProductionOrder + ProductionOrderLine entities + IProductionOrderService (create — optionally seeded from a Spec 055 production sheet for a window — release, complete, cancel) + admin endpoints.
  • Release consumes ingredient stock: read each line's frozen recipe snapshot, draw every ingredient down through the Spec 042 InventoryService commit fan-out in one transaction on the oversell guard; transactionally all-or-nothing — fail fast on a shortfall, roll back and retry on a concurrency conflict.
  • Complete optionally yields finished goods: increment the produced variant's InventoryLevel.OnHand by ProducedQuantity (make-to-stock; optional).
  • Guarded, idempotent state transitions: consume only on the Planned → Released edge; re-release never double-consumes.
  • The kitchen sheet: a printable/exportable projection of a production order + its per-dish recipe-component prep detail, via a read endpoint.
  • New Commerce DbSets on CommerceDbContext + AonikDbContext; one tool-generated migration (CommerceProductionOrders).
  • Commerce-agent read tool for the kitchen sheet + medium-gated write tools for create / release production order.

Out of scope

  • Ingredient stock mechanics themselves (levels, reserve/commit/release, low-stock alerts) — delivered by Spec 052; this spec only calls commit.
  • The demand aggregation and prep-list explosion — Spec 055; a production order optionally seeds from its output.
  • Ingredient cost / production-run costing / variance valuation — Spec 051 and Spec 057.
  • Routings, work centres, operation sequencing, machine/labour scheduling, lot/batch genealogy, scrap accounting — noted under Open, not built.
  • Reserving ingredient stock at Planned (a soft hold before release) — considered under Open; v1 consumes only at release.

5. Constraints & guardrails

  • No reference to Finance. Aonik.Commerce still references only SharedKernel + Aonik.Ordering. A production run touches inventory, not money; no ledger, no payment, no Finance coupling (ADR-005).
  • Anemic entities. ProductionOrder/ProductionOrderLine are { get; set; } data containers implementing ITenantScoped + AuditableEntity (ADR-002); the lifecycle, explosion wiring, and fan-out all live in IProductionOrderService, returning DTOs.
  • Single migration stream. EF-CLI-generated against AonikDbContext; Ank-prefixed tables; CommerceDbContext is runtime scoping with no migrations; agents never hand-author migrations.
  • Release consumes ingredient stock, not variant stock. A production run draws down ingredient InventoryLevel rows (Spec 052) via recipe explosion — never the finished variant's own stock. Completion is the only step that adds finished-variant stock (§10). The Spec 042 Bundle (which draws down component variant stock) is a distinct concept and untouched (§9).
  • Idempotent, guarded transitions. Consumption fires exactly once, on the Planned → Released edge; every transition validates the current status first (§8). No double-consume on re-release; no draw-down on cancel.
  • Agents propose; systems execute. The kitchen sheet is a direct agent read; create/release are medium (in-session confirmation, args-hash-bound) because release moves real inventory; every AI action records an AiRun.

7. Domain model

All entities are anemic, ITenantScoped, inherit AuditableEntity.

class ProductionOrder     { Guid Id, TenantId;
                            DateTime PlannedFor;        // when this run is scheduled to be made
                            string   Status;            // Planned | Released | InProgress | Completed | Cancelled
                            string?  Notes; }

class ProductionOrderLine { Guid Id, TenantId, ProductionOrderId, ProductVariantId;
                            decimal  PlannedQuantity;   // portions to produce
                            decimal? ProducedQuantity;  // actual portions made (set at/before Complete)
                            string?  RecipeSnapshotJson; } // exploded components frozen at first-explode (§9/§11)

ProductVariantId is a real intra-module reference to the Spec 042 finished ProductVariant being produced — the same variant a Spec 050 Recipe is attached to, which is exactly why a line can be exploded into ingredients. PlannedQuantity is what to make; ProducedQuantity is nullable so the record can be created and released before the actual yield is known, then reconciled at completion (planned ≠ produced is the normal case — see Risk register). RecipeSnapshotJson holds the line's exploded recipe components, frozen the first time the line is exploded (at create, or when the kitchen sheet is first generated); both the kitchen sheet (§11) and release consumption (§9) read this snapshot rather than re-exploding the live Spec 050 recipe, so an edit to that recipe between print and release cannot make the two diverge. It is the per-line materialisation of Spec 050's recipe-versioning open decision: until that lands, this run captures its own component bill. Status is a free string with a known-values helper (mirroring the platform's open-enum convention), driven only through the service's guarded transitions (§8).

8. Production-order lifecycle

IProductionOrderService owns a small, guarded state machine. Each transition validates the current Status before acting and is idempotent on its target edge — critically, stock is consumed exactly once, on Planned → Released.

create (optionally seed lines from Spec 055 sheet) │ ▼ ┌───────────┐ cancel │ Planned │ ─────────────┐ └───────────┘ │ │ release │ consume ingredient stock (§9) │ all-or-nothing recipe fan-out ▼ ▼ ┌─────────────┐ ┌───────────┐ │ Cancelled │ (terminal) │ Released │ └─────────────┘ └───────────┘ no stock consumed on cancel-from-Planned │ (optional) start ▼ ┌─────────────┐ │ InProgress │ └─────────────┘ │ complete (optional) yield finished-good stock (§10): variant InventoryLevel.OnHand += ProducedQuantity ▼ ┌─────────────┐ │ Completed │ (terminal) └─────────────┘ guards: release only from Planned → else 409 (idempotent: re-release from Released = no-op) complete only from Released|InProgress → else 409 cancel only from Planned|Released|InProgress; from Released, releasing back consumed stock is an Open decision (v1: cancel allowed pre-release; post-release cancel does NOT auto-restore stock — reconcile via Spec 052 stock adjustment)

InProgress is an optional operational sub-state between release and completion (the kitchen is actively cooking); it carries no stock effect. The two stock-moving edges are release (draw down ingredients, §9) and complete (optionally add finished goods, §10). A cancel from Planned is clean; the handling of a cancel after stock has been consumed is an Open decision.

9. Consuming ingredient stock on release — recipe fan-out (reuses Spec 042 inventory commit)

This is the heart of the spec, and it is almost entirely reuse. Spec 042 checkout already fans a single sale out over many stock lines: a bundle holds no stock of its own, so commit fans out over its selected component variants, drawing each down through InventoryService.CommitAsync (Spec 042 §10/§12). A production run is the same shape with two substitutions — the fan-out source is a recipe (not a bundle selection), and the drawn-down rows are ingredient InventoryLevels (Spec 052, not variant rows):

Bundle checkout (Spec 042 §12) Production release (this spec) ──────────────────────────────── ────────────────────────────────── one box line one ProductionOrder (its lines) fans out over selection slots fans out over recipe components → component ProductVariants → RecipeComponents → Ingredients InventoryService.CommitAsync(variant) InventoryService.CommitAsync(ingredient) (ingredient InventoryLevel rows, Spec 052) ReleaseAsync(productionOrderId): 0. guard: Status == Planned (else 409; Released ⇒ no-op) 1. bill = merge(lines.Select(l => l.RecipeSnapshotJson)) // the FROZEN snapshot (§7), NOT a live re-explode → [ { IngredientId, RequiredQuantity (BaseUnit) }, … summed across dishes ] → snapshot is written at first-explode; a line with no recipe froze empty ⇒ fail (no silent under-consume) ── begin ONE transaction (all-or-nothing across every component line) ── 2. pre-check availability for EVERY ingredient in one pass // inside the txn → if any Available < RequiredQuantity ⇒ throw InsufficientStock, consume NOTHING 3. foreach ingredient in bill: // the fan-out, same txn InventoryService.CommitAsync(ingredientId, requiredQuantity, productionOrderId) (OnHand -= required; Spec 052 ingredient level; row concurrency token, Spec 042 oversell guard) 4. Status = Released // in the same commit ── SaveChanges once → commit; on DbUpdateConcurrencyException: rollback ALL, retry from step 2 ──

All-or-nothing is transactional, not per-line best-effort. The whole-bill pre-check (step 2) and the entire commit fan-out (step 3) run inside one transaction, and each ingredient row is committed through the Spec 042 oversell guard on its row concurrency token. A pre-check alone is not enough: two concurrent releases could both pass it against the same on-hand and then over-consume. Binding the commits to a single transaction closes that window — if any row hits a DbUpdateConcurrencyException mid-fan-out, the whole run rolls back and retries the pre-check on refreshed stock, so either every component line commits or none does. Whether an insufficient ingredient should hard-fail (v1 default) or be permitted to drive stock negative (a backorder/"cook anyway" posture) is gated behind a flag and called out under Open. The bill itself is read from each line's frozen RecipeSnapshotJson (§7), not a fresh explosion, so what release consumes is exactly what the printed kitchen sheet showed. Because consumption is bound to the single Planned → Released edge and guarded by status (step 0), a re-release is a no-op and stock is never double-consumed — the central correctness property this spec must hold.

Note This reuse is why the spec is Medium, not Large: no new inventory primitive is introduced. Spec 052 already generalised InventoryLevel and InventoryService to stock and commit ingredients; Spec 050 already owns explosion; Spec 042 already owns the commit-fan-out pattern. This spec composes them behind one guarded transition.

10. Yielding finished goods on complete

A production run's counterpart to consuming raw materials is producing finished goods. On complete, the service optionally yields finished-good stock — for each line, it increments the produced ProductVariant's InventoryLevel.OnHand by that line's ProducedQuantity (falling back to PlannedQuantity when produced is unset). This closes the make-to-stock loop: goods made here become saleable stock that Spec 042 checkout reserves and sells.

CompleteAsync(productionOrderId, yieldToStock = true): 0. guard: Status ∈ { Released, InProgress } (else 409) 1. if yieldToStock: foreach line: qty = line.ProducedQuantity ?? line.PlannedQuantity InventoryService → variant InventoryLevel.OnHand += qty // finished-good stock rises 2. Status = Completed

Yield is kept optional because not every tenant is make-to-stock — some cook strictly to order (each portion is already tied to a customer order and should not re-enter sellable stock). The yieldToStock flag (default on for the make-to-stock persona this family targets) keeps both postures supported without branching the entity. The finer question — make-to-order runs that discharge specific customer orders rather than replenish anonymous stock — is an Open decision; v1 treats a run as make-to-stock and does not link a production order back to the orders it fulfils.

11. The kitchen sheet

The kitchen sheet is the human-facing artefact of a production order: a printable/exportable projection a chef works from at the pass. It is a pure read — a ProductionOrder joined to, per line, the exploded recipe-component prep detail (what to prep and how much). It is the production-run analogue of Spec 050's prep list, but scoped to one concrete run and grouped by dish rather than merged into one bill.

GET /commerce/production-orders/{id}/kitchen-sheet → KitchenSheet header: { productionOrderId, plannedFor, status, notes } dishes: foreach line → { productVariantId, variantName, plannedQuantity, producedQuantity, components: [ { ingredientId, ingredientName, baseUnit, requiredQuantity } // = component.Quantity × (planned / recipe.YieldQuantity) … ] } // per-dish, via Spec 050 ExplodeAsync(variant, plannedQty) totals: merged bill of materials across all dishes // sum of the per-line snapshots — the shopping/prep summary (first call explodes each line once and freezes it into RecipeSnapshotJson (§7); later calls replay the snapshot)

The projection is assembled from the same per-line RecipeSnapshotJson (§7) that release consumes, so it stays consistent with what release actually draws down: the first kitchen-sheet call explodes each line once (ExplodeAsync per dish) and freezes the result onto the line; the totals block is the merge of those same snapshots. Reading the snapshot rather than re-exploding is what makes the guarantee hold: if the Spec 050 recipe is edited after the sheet is printed but before release, both still replay the frozen components, so the sheet the kitchen worked from and the bill release consumes cannot diverge. Rendering to PDF/print is a frontend concern; the endpoint returns the structured KitchenSheet DTO. A line whose variant has no active recipe at first-explode is surfaced with the same "no recipe" diagnostic Spec 050 explosion emits (and freezes an empty component set), so the chef sees the gap rather than a silently empty dish.

12. Agent & tools

The existing commerce-agent gains production-order tools, classified by CommerceToolApprovalManifest and wrapped by the Spec 032 gate — no change to the gate:

ToolTierEffect
commerce_get_kitchen_sheetreadDirect execution; returns the KitchenSheet projection for a production order; tenant scope from context.

commerce_release_production_ordermediumReleases a run → consumes ingredient stock (§9). Medium because it moves real inventory: in-session confirmation, args-hash-bound; records an AiRun.

Release moves stock but not money, so it is medium (in-band once, after in-session confirmation) — consistent with the family's other inventory writes (commerce_receive_goods, commerce_set_ingredient_stock) and unlike the high money tools that are marshalled into a durable Finance Proposal. Complete and cancel are admin-endpoint operations in v1; promoting them to gated tools is trivial if an agentic run-management surface is wanted.

13. CommerceDbContext & migrations

Two new Ank-prefixed tables — AnkProductionOrders and AnkProductionOrderLines — are created by one EF-CLI migration against AonikDbContext. Each entity is added to both CommerceDbContext (runtime scoping) and AonikDbContext (canonical stream); both are tenant-scoped (neither global). Configurations live in Persistence/Configurations/Production as IEntityTypeConfiguration<T> classes. No new inventory tables — release and yield reuse the Spec 052 InventoryLevel schema. 

dotnet ef migrations add CommerceProductionOrders --project src/Aonik.Infrastructure --startup-project src/Aonik.Api

17. Verification

  • dotnet build Aonik.sln green; architecture test proves Aonik.Commerce has no Aonik.Finance reference.
  • Release consumes: with rice/tomato stock on hand and a jollof recipe (yield 4 ⇒ 1 kg rice, 0.5 kg tomato), create a run of 40 portions and release it ⇒ ingredient OnHand drops by 10 kg rice / 5 kg tomato via the commit fan-out; order → Released.
  • All-or-nothing: set rice short of the requirement; release throws InsufficientStock and no ingredient (including tomato) is drawn down; order stays Planned.
  • Concurrent releases: two releases racing on the same ingredient stock (enough for one run only) — exactly one commits the full bill, the other rolls back with a concurrency/insufficient-stock error; on-hand never goes below zero (mirrors the Spec 042 oversell-guard test).
  • Snapshot invariance: generate the kitchen sheet, edit the Spec 050 recipe (change a component quantity), then release ⇒ consumption matches the printed sheet, not the edited recipe.
  • Idempotent re-release: releasing an already-Released order is a no-op; stock is unchanged (not double-consumed).
  • Completion yield: complete the run with ProducedQuantity=38 and yieldToStock=true ⇒ the variant's OnHand rises by 38; with the flag off, finished stock is unchanged.
  • Kitchen sheet: GET …/kitchen-sheet returns per-dish prep detail matching each line's frozen snapshot and a totals block equal to the merged snapshots; the first call populates RecipeSnapshotJson; a no-recipe line carries the diagnostic.
  • Agent: commerce_release_production_order surfaces a medium approval; commerce_get_kitchen_sheet executes directly; each records an AiRun.
  • dotnet test Aonik.sln green (xUnit + FluentAssertions, InMemory + test tenant/user providers).

19. Decisions baked in

  • Release is the consume edge; complete is the yield edge. Raw materials leave stock on Planned → Released; finished goods (optionally) enter stock on completion.
  • Consumption reuses the Spec 042 commit fan-out, over RecipeComponent→Ingredient instead of bundle component variants — no new inventory primitive.
  • All-or-nothing at release is transactional — the whole-bill pre-check and the commit fan-out share one transaction over the Spec 042 oversell guard, rolling back on a concurrency conflict; concurrent releases cannot over-consume.
  • Transitions are guarded and idempotent; stock is consumed exactly once — no double-consume on re-release.
  • The kitchen sheet is a pure read projection assembled from a per-line recipe snapshot frozen at first-explode, so it and release always consume the same bill even if the recipe is later edited.
  • Grow in place in Aonik.Commerce; no Finance reference (inventory, not money); migrations stay with AonikDbContext.
  • Release/create are medium agent tools (they move inventory); the kitchen sheet is a direct read.

20. Open design decisions

Open Negative stock at release. Whether an ingredient shortfall must hard-fail (v1 default) or may be permitted to drive stock negative — a "cook anyway / backorder the raw material" posture — behind a per-tenant or per-release flag. v1 fails fast; the flag is the escape hatch.
Open Make-to-order linkage. Whether a production order should link back to the specific customer orders it fulfils (make-to-order: each portion discharges a real demand line and does not re-enter anonymous sellable stock) rather than replenishing stock (make-to-stock, v1). Would add a soft link from ProductionOrderLine to source order lines and suppress the completion yield for tied portions.
Open Reserve at Planned (soft hold) vs. consume only at Release. v1 draws stock only at release. An alternative reserves ingredient stock at Planned (a soft hold via the Spec 052 reserve path, mirroring how checkout reserves before capture) so competing runs cannot both plan against the same raw material, converting the hold to a commit at release.
Open Scrap / actual-vs-planned variance capture. Recording scrap and the delta between planned consumption and actual ingredient usage (over-portioning, trim loss) as first-class variance, feeding food-cost accuracy in Spec 057. v1 consumes against the planned bill; variance is inferred, not captured.
Open Post-release cancel reversal. Whether cancelling an order after release should automatically restore consumed ingredient stock (a compensating release). v1 requires an explicit Spec 052 stock adjustment; auto-reversal risks masking real usage and is deferred.
Open Scheduling / sequencing of runs. Ordering and time-slotting production runs across shifts, stations, or work centres (a routing / MES concern). v1 carries a single PlannedFor date and no sequencing; full scheduling is out of the thin maker-ops slice.
