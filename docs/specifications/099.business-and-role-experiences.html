Scope: Aonik Admin UI, with a small extension to its existing manifest

Business-specific Admin UI

The Aonik Admin UI should show each business the screens relevant to its operations, using domain-appropriate labels. Existing permissions then narrow what each administrator sees. Abby’s Table can call its product catalogue “Menu”; Arke Kids can omit commerce and unrelated financial administration while retaining the backend modules its business needs.

This specification extends Spec 097: Per-tenant module enablement with source-controlled JSON admin profiles. It requires no new tables or database migrations.

1. Scope and decisions

Only the Aonik Admin UI is in scope: navigation, registered pages, labels, landing pages, settings, dashboard widgets and workspace panels. The existing admin API supplies the tenant context and permissions needed to render that UI.

  • Profiles are JSON files shipped with AdminUi and selected from the tenant’s existing BusinessType.
  • A profile specifies relevant screens, menu structure, labels and a preferred landing screen.
  • The screen registry owns routes, components, required backend modules and permission rules. Profiles reference that registry rather than duplicating those rules.
  • One shared visibility function combines the profile, enabled modules and current user permissions.
  • Existing API authorization and module enforcement remain authoritative. UI configuration grants no access and does not enable or disable backend modules.
  • No new tables, migrations, profile CRUD endpoints, configuration editor, assignment model, pinned profile versions or new capability framework.
  • No changes to other applications or domain execution systems. This specification does not design or integrate customer, storefront, parent or child experiences.

Normal source control and deployment version the JSON together with its registered screens. New business functionality remains separate work; adding a menu label does not implement a screen.

3. JSON profile format

Place profiles under src/Aonik.AdminUi/src/config/admin-profiles/. The first release contains a general profile, a food-commerce profile and an Arke Kids profile. These files contain data only.

{
  "id": "food-commerce",
  "landingPage": "commerce.orders",
  "screens": {
    "commerce.orders": { "label": "Food Orders" },
    "commerce.order-detail": {},
    "commerce.products": { "label": "Menu" },
    "commerce.product-detail": {},
    "commerce.delivery": { "label": "Delivery" }
  },
  "navigation": [
    {
      "id": "operations",
      "label": "Kitchen & Orders",
      "items": [
        { "screen": "commerce.orders" },
        { "screen": "commerce.products" },
        { "screen": "commerce.delivery" }
      ]
    }
  ]
}

The example is a shortened profile using registered screen IDs. Implementation must map profile entries to real registered screens; unavailable screens must not be included in shipped profiles.

FieldMeaning
idStable profile identifier. No tenant-specific identity or display-name matching.
landingPagePreferred registered screen ID. It must be included in screens and be navigable without resource parameters.
screensPositive allowlist of relevant registered screens, including detail/edit pages that should not appear in the menu. An empty object uses registry defaults.
screens[id].labelOptional screen name override, used consistently in its menu entry, breadcrumb and ordinary page title. Specific detail-page labels may be supplied on their own screen IDs.
navigationOrdered sections containing screen references. Support a labelled group with screen-reference children where the existing sidebar needs a submenu; no separate policy on a group.

The explicit screen list keeps detail pages reachable without requiring them to be menu items. It also prevents an unlisted route from becoming available merely because its parent section is displayed.

Profiles do not contain module enablement, permission grants, component names, executable code, arbitrary URLs or backend entity definitions. Required modules and permissions belong to the screen definition once, so all profiles use the same rules.

Labels must accurately describe the implemented screen. Calling products “Menu” is appropriate for food commerce; calling general stock “Ingredients” is appropriate only if the screen actually manages ingredients. Label overrides do not automatically rewrite form fields, API names, resource titles or domain behaviour. Missing overrides use registry defaults.

4. Screen registry and permissions

Extend the current module-owned route definitions instead of introducing a parallel registry service. Each logical screen has a stable ID, route pattern, component, default label, required modules and permission requirements. Reuse existing module/route requires metadata: screen availability must satisfy both the owning UI module’s requirements and any additional route requirements.

  • Use existing permission keys and the effective user permissions returned by the server. Where a route’s existing policy permits alternatives, preserve that meaning with explicit all-of/any-of metadata rather than inventing a stricter or looser rule.
  • Every included screen must declare its permission rule, including an explicit authenticated-admin-only classification where that matches its existing server policy. Missing metadata is a validation error, not unrestricted access.
  • Detail and edit pages have their own screen IDs and permission rules. Allowing a list does not automatically allow editing.
  • Navigation to create/edit screens uses the target screen’s visibility. Inline write actions use existing operation permission checks; adding a JSON profile must not bypass them.
  • Existing host/tenant audience restrictions continue to apply. The host administrator’s existing navigation remains separate; a tenant profile cannot introduce host-only screens.

For UI elements outside the router, reference the corresponding screen ID rather than duplicating business-type logic. A dashboard widget or panel making additional API calls must also satisfy those calls’ existing module and permission requirements.

Server endpoint and resource authorization remain unchanged. Removing a screen from a profile restricts presentation; it does not revoke an otherwise-authorised API permission. Grant or revoke permissions through the existing access-management system.

5. Profile selection and existing manifest

Extend GET /admin/manifest with businessType and permissions. Resolve both from the authenticated, tenant-validated server context. Reuse the existing permission service, not browser claims or caller-supplied role names. Keep the current enabledModules and other fields for compatibility.

{
  "businessType": "food-commerce",
  "permissions": ["...existing effective permission keys..."],
  "allowedPolicies": ["AdminUserPolicy", "AdminPolicy", "AdminUserWritePolicy"],
  "enabledModules": ["platform", "ordering", "ai", "agents", "finance", "commerce"]
}

This is an excerpt, not the complete response. The server evaluates its existing policies; the UI does not derive them from role names. Screen metadata may require both a policy and stored service permissions. The manifest remains an admin endpoint under its existing access policy.

A small explicit map in AdminUi selects the JSON profile:

base, simi    → general
food-commerce → food-commerce
arke-kids     → arke-kids

The Arke business-type key is proposed and must be reconciled with the actual tenant configuration during implementation. Add explicit mappings for other existing business types after inventory. Do not match on “Abby”, “Arke”, a tenant name or an email address.

For compatibility, a previously unmapped business type uses the explicit general profile, still filtered by module and permission checks. This is a known-data fallback only: a failed manifest request, missing required response fields, or an invalid profile is an error and must not select the general profile. A named profile missing from the bundle fails build validation.

The general profile preserves the reviewed existing admin screen inventory. It is not a wildcard that automatically includes every future registered screen.

No persisted profile selection is needed. If a real need later arises for two tenants of the same business type to use different profiles, a tenant-scoped AdminUi.Profile setting can use the existing settings infrastructure. That override and its editor are not part of this implementation.

6. Shared rendering rules

screen visible = profile includes screen
                 AND required modules are enabled
                 AND current user satisfies screen permissions
                 AND required existing server policy allows it
                 AND existing host/tenant audience rule allows it

Implement this rule once as a pure helper consumed by useModules and related registry helpers. A profile may narrow the available screens but cannot override module, permission or audience restrictions.

  • Menus: use profile order and labels; remove unavailable entries and empty groups/sections. The sidebar and command palette consume the same result.
  • Routes: guard before mounting a page or fetching its data. An unavailable direct link shows a neutral unavailable page and a permitted destination.
  • Landing: use the preferred screen if visible. Otherwise choose the first visible navigable screen in menu order. If none exists, show a neutral no-access page with account/sign-out controls.
  • Deep links after login: honour only a registered local route whose screen is visible. Otherwise use the resolved landing page.
  • Settings and widgets: apply the same visibility to links, tiles and registered screen content. Extra operation-specific restrictions still apply.
  • Search and quick navigation: omit unavailable screen destinations from command-palette and navigation-search results. Guard notification links at their destination. This does not redesign backend search or notification delivery.
  • Workspace panels/templates: filter against allowed screens before mounting. Suppress inaccessible saved panels without deleting the saved layout. Hide templates with no available content.
  • Labels: resolve from the profile then screen defaults. Use one label resolver for menus, breadcrumbs and page headings; do not scatter business-type conditionals through components.

Login, logout, account recovery, loading, unavailable and error pages are explicit shell routes outside the business screen list. Existing account controls remain available independently of the chosen business profile.

8. Loading, caching and errors

Reuse the existing manifest cache and refresh interval. Because the response now includes permissions, isolate cached and in-flight results by authenticated user/session and selected tenant. Clear effective navigation and mounted business content on identity/tenant changes, and discard responses belonging to the previous context.

  • Initial loading shows a neutral shell; a manifest error shows retry and account/sign-out controls. Never display every module because the manifest is absent.
  • Reuse the existing 30-second refresh and visibility-change behaviour to pick up external permission/module changes. Invalidate immediately after successful local access/module edits, logout or tenant switching.
  • A failed refresh must not expand visibility. An expired unusable manifest produces an unavailable shell rather than a permissive fallback.
  • Permission-filtered manifests must not be shared across users through an HTTP/shared cache. API authorization continues to check each request independently of the UI refresh interval.

No new revision graph, event infrastructure or profile cache service is required. JSON profiles are local static imports deployed with the UI.

9. Implementation steps

Implemented in the isolated worktree, 28 September 2026: All 96 registered routes carry screen metadata. General, food-commerce and Arke Kids JSON profiles now drive the sidebar and command palette, route guards, landing destinations, ordinary page labels, settings tiles and workspace panels/templates. The manifest includes server-resolved business type, stored permissions and evaluated existing policy results. User/tenant-scoped caching discards stale requests, refreshes before the 30-second expiry and fails closed on errors. No tables or migrations were added.

The Arke profile currently exposes existing customer, team, usage, approval and AI administration screens. There are no registered world-builder, story-writing or subscription-management screens to include; implementing those remains separate work. Repository business-type values base and simi use general; food-commerce uses food-commerce. The arke-kids mapping is ready but has not been verified against a live tenant. Host administrators retain the reviewed general inventory with host-only screens gated by the server's PlatformAdmin policy.

Workspace layouts are now stored under the authenticated identity and tenant. Existing unscoped local layouts remain untouched and are not automatically imported because their owner is unknown. Unavailable panels in a scoped saved layout render a neutral placeholder without mounting their content.

  1. Inventory: map existing routes, the sidebar and command palette, panels and settings to stable screen IDs and actual permission rules. Record existing tenant business-type values and which reference screens exist.
  2. Profiles and registry: extend existing route metadata; add JSON files and the business-type map; implement the shared visibility and label helpers.
  3. Manifest: add server-resolved business type and effective permissions to the existing admin endpoint. Deploy compatible server fields before the UI that requires them.
  4. Admin integration: use the shared result across menus, route guards, landing pages and secondary entry points; update cache identity and loading/error behaviour.
  5. Verify: exercise general, food-commerce and Arke profiles with different permissions and module sets. Confirm actual business types before relying on tailored navigation for the target tenants.

Validate JSON at build/test time: unique profile/screen IDs, known screen references, allowed schema fields, navigation references included in the profile, valid landing screens and complete screen metadata. A new route must be intentionally included in a profile before it appears there. No JSON runtime editor or server-side profile management is needed.

This change requires no schema migration or assignment backfill. Tenant business-type corrections, if needed, use existing tenant management and are not inferred from tenant names. Updating a JSON profile follows the normal application review and deployment process.

10. Acceptance criteria

  • Abby’s Table and Arke Kids administrators receive their mapped profiles through the existing admin login flow.
  • Two administrators in the same business with different permissions see correspondingly different screens and actions.
  • A profile’s screen inclusion cannot override a disabled module, missing permission or host-only restriction.
  • Arke’s required backend Finance module remains enabled even when its financial admin screens are omitted.
  • Menu labels, breadcrumbs and ordinary page titles consistently use profile overrides, falling back to registered defaults.
  • Detail/edit routes included in the screen list work without appearing as menu entries; unlisted or unauthorised routes are guarded before data fetching.
  • The sidebar and command palette, settings, registered widgets, workspace panels and navigation search apply the same visibility rules.
  • An unavailable preferred landing page selects the first permitted menu destination; zero available screens produces a useful neutral page.
  • Tenant/user switches and in-flight requests do not display the previous context’s navigation or business content.
  • Manifest loading/errors do not reveal all screens. Successful refreshes apply permission/module changes using the existing refresh cadence.
  • Existing API authorization remains unchanged and continues to reject prohibited direct requests.
  • No new tables, migrations, profile endpoints or runtime profile editor are introduced.

Verification should include pure helper tests for profile/module/permission intersections and labels, manifest API tests for tenant-specific business type and user-specific permissions, configuration validation, and focused AdminUi tests for deep links, context switches and failure states. Validation includes the full AdminUi test suite, the production UI build and focused manifest API integration tests. Live tenant configuration and end-to-end identity-provider sign-in remain deployment checks.

Design summary: JSON defines which admin screens fit a business and how they are presented. The existing screen definitions, module state and permissions determine whether those screens can be shown. Existing server policies determine what the user may do.
