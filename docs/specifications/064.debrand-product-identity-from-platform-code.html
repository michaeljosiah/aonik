Spec 064 Status: Draft (Rev 1) Size: Medium Priority: P1 (pre-Simi-launch) Domain: Platform / PersonalFinance / Ai

Extract product identity ("Simi") from platform code

Implements ADR-013: no platform code encodes a product's identity. Today "Simi" is baked into ~115 places across ~40 source files — a hard-coded persona ("You are Simi…"), product-named tools (SimiKeeperTools, simi_*), a product-named wire field (simiTool), a printed SIMI- verification-code prefix, and "Simi" comments inside Aonik.Documents / Aonik.Finance / Aonik.SharedKernel. This spec extracts all of it: the capability stays (generic, function-named); the identity moves to configuration (the tenant's Agent override + branding settings). Behaviour-preserving — Simi still reads and works exactly as before, it just stops being spelled into the engine. Best done before Simi's launch, while the wire/persisted renames can be clean.

The one-line test (ADR-013) Would a second product configured on AONIK inherit this string? If a tool name, class, DB column, structured-output field, default prompt, or printed code contains "Simi", the answer is yes and it must move to configuration or become generic. If it is a tenant id, a branding setting value, or a product client app, it is already configuration and stays.

1. Summary

AONIK is a product-agnostic platform; Simi is a product configured on it. The code drifted from that: a survey found ~115 "Simi" references across ~40 source files (after excluding ElevenLabs SimilarityBoost / Qdrant similarity, which are unrelated). This spec sorts every one into keep (already configuration), rename (generic capability that was mis-named), or move (product identity that belongs in the tenant's Agent config or a branding setting), and sequences the few that cross wire/persisted surfaces so nothing breaks. It ships no behaviour change — the Simi tenant looks and works identically; the platform simply no longer knows the word.

3. Scope (in / out)

3.1 In scope

  • Rename The simi_* tools → pf_*, the classes → generic, the simiTool field → followUpTool (§4).
  • Move The persona (name, prompt, tone) out of the compiled default and into the Simi tenant's Agent override; ship a generic default prompt (§5).
  • Move The Support Statement verification prefix into a branding setting with a neutral default (§6).
  • Reword "Simi" comments/help in platform layers to describe the generic capability (§2).
  • New An architecture test asserting no product noun appears in a platform tool name / class / field (§8).

3.2 Out of scope

  • Any behaviour change. Same tools, same reads, same outputs — only names, the persona's home, and one setting change.
  • The capabilities themselves. Care entities, commitments, payment logs, vault, circle, the describe-only read surface — all stay; they are generic platform features.
  • Renaming SIMI_TENANT_ID or the mobile brand — already correctly configuration / product layer.
  • A general theming/branding engine — the Agent override + one branding setting suffice (ADR-013, YAGNI).
  • Other products. This sweep is "Simi"; the same test (§8) will catch any future product noun.

5. Persona → configuration the core move

The seam already exists. The Agent entity supports a two-level (global + per-tenant) override of instructions, model, and enabled tools (ToolsetIdsJson), and the descriptor already consumes it — Build(chatClient, sp, instructionsOverride, allowedToolNames) + GetToolNames (Spec 033). The persona was baked into the compiled default instead of configured through it. The fix:

  1. Neutralise the default. PersonalFinanceAgentDescriptor.Instructions becomes a generic personal-finance-companion prompt — warm, calm, describe-never-prescribe, money-format and output-contract rules intact — with no product name and the <keeper> block renamed <care>. This is the fallback any tenant gets before configuring.
  2. Author "Simi" as a tenant Agent override. The Simi tenant's personal-finance-agent row carries the "Simi" name, voice, and tone as its instructions override, and its ToolsetIdsJson enables the relevant tools by their new names. Delivered as the Simi config pack — the manifest in Spec 065 (per ADR-014), not code. This de-brand authors that pack; it is the pack's first instance.
  3. Display name from config. Wherever the platform needs the agent's user-facing name, it reads the configured display name, never a literal "Simi".
Behaviour-preserving A Simi user sees the identical persona — because the identical text now lives in the Simi tenant's config instead of a C# const. A different tenant on the same platform gets the neutral default and can author its own persona. That is the whole point of the platform.

6. Branding → a setting

SupportStatementService builds the verification code as $"SIMI-{careEntityId:N}"[..13] + "-{date}". Replace the literal with a tenant branding setting — StatementVerificationPrefix — read from the tenant's configuration, defaulting to a neutral value (e.g. STMT) when unset. The Simi tenant sets it to SIMI, so issued codes are unchanged for Simi while the platform ships no product string. Keep the format forward-compatible with the (Phase 2) verification page, per Spec 048 O3. Test fixtures update to the configured value.

7. Wire & persisted compatibility the care points

Most of the sweep is a safe in-process rename. Four surfaces are load-bearing because something outside the compiler binds to the string:

  • Tool-name strings in tenant tool allow-lists. Agent.ToolsetIdsJson may list the old simi_* names. Rename the tools and update every allow-list that references them in the same change (the Simi config pack). A stale allow-list entry silently drops a tool, so this is a paired edit, not two.
  • Stored references to a tool name. Sub-agents return recommendedActions[].simiTool naming a follow-up tool to call; Compass proposals may persist one. Grep the codebase and check for any persisted simiTool values that name a simi_* tool; migrate or (pre-launch) accept that historical dev rows are disposable. The field rename to followUpTool is coordinated across every sub-agent that emits it and the orchestrator that reads it — one atomic change.
  • Printed SIMI- verification codes. Any Support Statement already issued embeds the old prefix. Simi is pre-launch, so there are no real issued statements to honour — a clean switch to the configured prefix is safe now and painful later. Do it before GA.
  • The model's tool surface. Tools resolve server-side per request, so no client pins a tool name; the model sees whatever is registered. The only prompt references to simi_* are in the instructions themselves (§5), which move to config in the same pass. No client/mobile change needed.
Why pre-launch is the moment Every one of these is cheap now and expensive after real users, issued statements, and pinned integrations exist. ADR-013 binds new work already; this spec clears the back-catalogue while the renames can still be clean rather than shimmed with aliases.

8. Enforcement

  • An architecture test (the durable guarantee): reflect over the registered agent tools + the tool/structured-output types and assert no name contains a known product noun ("simi", "payabo", "mybillafrica", "remitexchange"). It fails the build if a future symbol reintroduces a brand — the lint form of ADR-013.
  • The Spec 032 build check is a free ally. Renaming a classified mutating tool without updating its manifest key throws ToolNotClassifiedException at agent build — so a half-done rename cannot ship a silently-ungated tool.
  • Grep gate in review: a plain grep -ri "simi" src/ minus the Similarity/similarity allow-list should return only the product client app and SIMI_TENANT_ID after this lands.

9. Persistence & migration

  • No schema migration for the renames. Tool/class/field renames are code-only; the followUpTool field is a serialized contract, not a column.
  • Branding setting. StatementVerificationPrefix rides the existing tenant-settings mechanism (no new table if settings are key/value); if a dedicated branding entity is preferred, it is a single tool-generated migration against AonikDbContext (CLAUDE.md) — decide in implementation (O1).
  • Seed data changes are data, not schema: product-named seed rows move into the Simi config pack; the platform/demo seed stays generic.

10. Phasing & tasks

  1. Rename (mechanical, atomic). simi_* → pf_* across CareReadTools (was SimiKeeperTools) + registration + the PersonalFinanceToolApprovalManifest keys (if any classified) + prompt references; simiTool → followUpTool across sub-agent structured outputs + orchestrator; update Agent.ToolsetIdsJson allow-lists in the same commit.
  2. Persona to config. Neutralise the default Instructions (rename <keeper> → <care>, strip "Simi"); add the "Simi" persona to the Simi tenant Agent override seed; read the display name from config.
  3. Branding setting. StatementVerificationPrefix in SupportStatementService (default STMT); Simi tenant sets SIMI; fixtures updated.
  4. Reword comments/help in Aonik.Documents / Aonik.Finance / Aonik.SharedKernel / CLI to the generic capability.
  5. Enforcement test (§8) + a stored-reference grep/migration check (§7).

11. Acceptance criteria

  • No product noun in platform symbols. The architecture test passes; grep -ri simi src/ (minus the similarity allow-list) returns only the product client app and SIMI_TENANT_ID.
  • Behaviour identical for Simi. Logged in as a Simi user, the agent's name, tone, tools, answers, and the Support Statement verification code are unchanged (the persona + prefix now come from the Simi tenant config).
  • Generic default for a new tenant. A fresh tenant with no Agent override gets the neutral personal-finance-companion prompt and the STMT prefix — no "Simi" anywhere.
  • No dropped tool. Every renamed tool is still enabled for the Simi tenant (allow-lists updated in lockstep); no ToolNotClassifiedException; build green.
  • Wire coherence. Sub-agent followUpTool values resolve to real (renamed) tools; no persisted reference points at a dead simi_* name.

12. Open decisions

  • O1 — Branding setting shape. Whether StatementVerificationPrefix (and future branding) is a key in the existing tenant-settings store or a small dedicated TenantBranding entity. Leaning: reuse tenant settings (no migration) unless a typed branding surface is wanted soon.
  • O2 — Keeper tool suffixes. Exact new names for the five care reads (this spec proposes pf_care_*/pf_list_*); confirm against any tenant allow-list already seeded so the rename is a single coordinated edit.
  • O3 — Agent display-name field. Whether the configured persona name lives in the Agent row (a display-name column/setting) or is parsed from the instructions. Leaning: an explicit configured display name, so no code ever greps a prompt for the product's name.
