# Personal Finance Agent Capability Gap Matrix

Version: 1.0  
Target Agent: `personal-finance-agent`  
Scope: Payabo mobile conversational entry agent  
Date: 2026-04-06

---

## 1. Purpose

This document evaluates whether the current `personal-finance-agent` can answer the kinds of questions users will naturally ask in Payabo.

The goal is to identify where Simi can respond comfortably today, where she would be weak or awkward, and where we need additional domain tools, reasoning specialists, or cross-domain orchestration.

This assessment is based on:

- the current `personal-finance-agent` tool surface in `src/Aonik.Finance/Agents/Tools/PersonalFinanceTools.cs`
- the current system prompt in `src/Aonik.Finance/Agents/PersonalFinanceAgentRegistration.cs`
- the two internal reasoning specialists:
  - `pf-spending-intelligence-agent`
  - `pf-obligation-planning-agent`
- adjacent capabilities already present elsewhere in the AONIK codebase but not yet exposed to Simi

---

## 2. Rating Legend

| Rating | Meaning |
| --- | --- |
| Comfortable | Simi has a direct tool or grounded specialist path and can answer reliably. |
| Weak | Simi can partially answer, but the result would be incomplete, inferred, or operationally awkward. |
| Unsupported | Simi does not currently have the right tool path, mutation path, or cross-domain orchestration to answer safely. |
| Exists But Not Exposed | The platform has capability in the codebase, but `personal-finance-agent` cannot currently use it. |

### 2.1 Frequency Legend

| Frequency | Meaning |
| --- | --- |
| High | Likely to appear often in day-to-day Payabo usage and should heavily influence early prioritisation. |
| Medium | Important and recurring, but not as consistently frequent as core spend, balance, and bill questions. |
| Low | Valuable but less frequent, more niche, or tied to a specific cohort or workflow. |

## 4. Key Logic Gaps Already Present

These are important even before adding more domains.

### 4.1 Prompt/tool mismatch: account-level breakdown is claimed but not exposed

The prompt says Simi can provide account-level breakdowns in `src/Aonik.Finance/Agents/PersonalFinanceAgentRegistration.cs:65`, but no `pf_get_account_breakdown` tool is exposed in `src/Aonik.Finance/Agents/Tools/PersonalFinanceTools.cs:343`.

Impact:

- weak answers to account comparison questions
- prompt overstates capability

### 4.2 FX display guidance exists without server-side FX grounding

The prompt instructs Simi to use `display_fx_rate_chart` for FX questions in `src/Aonik.Finance/Agents/PersonalFinanceAgentRegistration.cs:143`, but `personal-finance-agent` has no server-side FX tool.

Impact:

- FX/remittance timing questions are not safely answerable
- display guidance exists without grounded data fetch capability

### 4.3 Current transaction query model is lookup-oriented, not investigation-oriented

`pf_list_transactions` supports date range, account, category, search, and pagination in `src/Aonik.Finance/Agents/Tools/PersonalFinanceTools.cs:70`, but not:

- amount thresholds
- weekday/weekend analysis
- average spend calculations
- anomaly explanation
- recognition/dispute-style reasoning

Impact:

- many transaction questions require brittle client-side reasoning over paged raw lists

### 4.4 Only two reasoning specialists exist today

Current specialists cover:

- spending diagnosis
- obligation planning

Missing specialist domains:

- transaction investigation
- subscription optimisation
- goal planning
- household/shared-finance reasoning
- financial-context reasoning

## 7. Recommended Sequencing

## Phase 1a: Expose high-frequency read capabilities first

- expose merchant history
- expose account breakdown
- expose account-link summary/sync tools
- expose snapshot history
- expose classification review queue

Why first:

- these are predominantly read paths
- they are high-frequency trust builders
- they should be hours-to-days of agent wiring work, not deeper domain redesign

## Phase 1b: Expose high-frequency mutation and personalisation flows

- expose bill update
- expose budget CRUD
- expose transaction classification override
- expose categorisation rule create/update/deactivate

Why next:

- these are also high-frequency asks, but they require approval wrappers and tighter UX handling
- they have more potential to affect user financial state or behavioural automation

- `pf-transaction-investigation-agent`

This would cover:

## 8. What Simi Should Explicitly Decline Today

For unsupported categories, Simi should decline clearly and redirect rather than guess, overpromise, or speak as if the workflow is available.

Recommended patterns:

- Remittance / cross-border send:
  - "I can't complete cross-border transfers from this chat yet, but I can help explain the process once that workflow is available in-app."
- Card management:
  - "I can't manage saved cards from chat right now. You'll need to use the payment methods area in the app when that surface is available."
- Login / support issues:
  - "I can't resolve login or account-access issues directly from personal finance chat. I should route you to the support flow instead."
- Bill payments via catalog:
  - "I can't initiate catalog bill payments from this chat yet, even though the platform supports bill-payment workflows elsewhere."
- Transfers and order troubleshooting:
  - "I can't inspect or act on transfer and order workflows from this chat yet, so I shouldn't guess about transfer state or failure reasons."

The operational rule is simple:

- decline unsupported actions explicitly
- say whether the gap is chat capability or platform capability
- offer the closest grounded alternative, if one exists

## 9. Bottom Line

Today, Simi is credible for:

- account and balance overview
- recent transaction lookup
- spending summaries and category/merchant breakdowns
- dashboard interpretation
- upcoming bill and obligation planning
- lightweight advisory guidance grounded in current-period data

Today, Simi is not yet credible for the full real-world Payabo question set.

The biggest issues are not that AONIK lacks capability entirely. In many places, the platform already has the domain logic. The main problem is that `personal-finance-agent` still exposes only a narrow subset of that capability and does not yet orchestrate across adjacent domains such as catalog, orders, account linking, classification review, remittance, and support.

The highest-value insight remains this:

- the platform is often capability-rich but agent-surface-poor

That means the fastest path to a much more credible Simi is usually not inventing new finance subsystems first. It is exposing the right high-frequency capabilities, then adding targeted reasoning specialists, and only after that expanding into cross-domain orchestration and longer-horizon product gaps.

That means the immediate roadmap should focus on:

1. exposing already-built personal-finance capabilities,
2. adding one or two more reasoning specialists,
3. only then extending Simi into broader cross-domain orchestration.
