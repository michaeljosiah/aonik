# Financial Life Graph - AONIK-Aligned Specification

## 1. Purpose

Implement a tenant-scoped Financial Life Graph inside AONIK's Finance module to support Payabo personal-finance reasoning across:

- personal accounts
- linked financial accounts
- personal transactions
- bills
- goals
- subscriptions
- households
- related parties
- FX context relevant to user decisions

The Financial Life Graph is a reasoning and relationship layer. It does not replace the existing relational source-of-truth models in AONIK.

---

## 2. Architectural Alignment

This specification is intentionally aligned to the current AONIK codebase.

### 2.1 Module Placement

The feature belongs in the existing Finance module, primarily under the Personal Finance domain.

Use:

- `src/Aonik.Finance/Entities/PersonalFinance`
- `src/Aonik.Finance/Services/PersonalFinance`
- `src/Aonik.Finance/Endpoints/PersonalFinance`
- `src/Aonik.Finance/Contracts/Models/PersonalFinance`
- `src/Aonik.Finance/Contracts/Services/PersonalFinance`

Do not create new top-level projects such as:

- `Payabo.Graph`
- `Payabo.Graph.Api`
- `Payabo.Graph.Tests`

### 2.2 Runtime and Persistence Alignment

Use the existing AONIK EF Core model:

- Runtime module DbContext: `FinanceDbContext`
- Canonical migration stream: `AonikDbContext`
- Shared database schema: `dbo`
- Shared module table prefix convention: `Ank*`

This means any new Financial Life Graph entities must be registered in both:

- `src/Aonik.Finance/Persistence/FinanceDbContext.cs`
- `src/Aonik.Infrastructure/Persistence/AonikDbContext.cs`

### 2.3 Multi-Tenancy Alignment

All graph operations are tenant-scoped.

The graph must resolve context from:

- `ITenantProvider`
- `ICurrentUserProvider`

Do not design graph APIs that require `UserId` as a free-form request payload for normal authenticated use.

### 2.4 API and Tooling Alignment

Use existing delivery surfaces:

- FastEndpoints in `Aonik.Api`
- Finance agent tools in `src/Aonik.Finance/Agents/Tools`
- Finance MCP tools in `src/Aonik.Finance.Mcp/Tools`

Do not create a separate API host for graph functionality.

## 3. Architectural Guardrails

### 3.1 Financial Truth

- Ledger remains the source of financial truth for material money movement.
- Orders remain business intent and are not replaced by graph nodes.
- Payments and payouts execute intent; the graph may reference them but must not become the execution model.

### 3.2 Personal Finance Scope

- Personal Finance entities remain the primary source for user budgeting and spend analysis.
- The graph is a projection and augmentation layer over existing Finance and Platform entities.

### 3.3 Identity and Relationship Canonical Sources

Use existing canonical sources wherever possible:

- `Party` and `PersonProfile` for person/business identity
- `PartyRelationship` for explicit family/friend/business relationships
- `Household` and `HouseholdMember` for shared consumer-finance groupings
- `PersonalProfile` for current user personal-finance profile context

Do not create a parallel identity graph that duplicates Platform ownership.

### 3.4 AI and Mutation Guardrails

- AI-generated graph suggestions must be auditable.
- Financially material AI outputs must capture `AiRunId`.
- AI must not directly mutate financial state.
- For material actions, retain the AONIK `Propose -> Approve -> Apply` direction using existing `Proposal` infrastructure where applicable.

## 4. Current Codebase Mapping

The graph should map to the current domain model as follows.

### 4.1 Mirror Sources

Mirror graph nodes should be projected from existing entities:

- `PersonalAccount`
- `FinancialLinkedAccount`
- `PersonalTransaction`
- `Bill`
- `Goal`
- `Subscription`
- `Household`
- `HouseholdMember`
- `Party`
- `PartyRelationship`
- `FxQuote`
- optionally `Order` and `PaymentIntent` for execution references

### 4.2 Important Current Limitations

The spec must account for current gaps in the codebase:

- `PersonalAccount` does not currently hold balance fields.
- `Bill`, `Subscription`, and `PersonalTransaction` use free-text counterparties in several places.
- There is no current backend community/ajo/esusu domain.
- There are no existing Goal/Bill/Subscription services equivalent to the Account and Insights services.
- Proposal middleware exists but approval enforcement is not fully wired yet.
- AI routing entities exist, but current runtime model selection is config-driven.

Because of this, MVP graph features should focus on relationship hydration and read-side reasoning, not autonomous execution.

## 5. Scope

### 5.1 In Scope

- Build a user-scoped in-memory financial life graph from existing relational data.
- Add optional native graph entities for user annotations and AI/user-confirmed inferred relationships.
- Expose read-side graph APIs for Payabo and internal tools.
- Add internal traversal/calculation helpers for obligations and relationship reasoning.
- Add caching using existing infrastructure.
- Add agent/MCP read tools for graph context retrieval.

### 5.2 Out of Scope for MVP

- Separate graph database
- Cross-user corpus graph analytics
- New standalone graph microservice or API host
- Community/ajo/esusu native domain modeling
- Safe-to-send calculations based on account balances before balance data exists in Personal Finance
- Autonomous AI execution of payments/orders

---

## 6. Delivery Model

The graph will be implemented in two layers:

### 6.1 Mirror Projection Layer

At hydration time, project graph nodes and edges from existing AONIK tables.

This includes:

- user -> accounts
- user -> bills
- user -> goals
- user -> subscriptions
- user -> transactions
- user -> household
- household -> members
- party -> related parties
- bill -> linked order/invoice where available
- transaction -> account
- transaction -> party when canonical linkage exists

### 6.2 Native Augmentation Layer

Persist graph-native data only for information that does not already exist in canonical relational models, such as:

- user annotations
- confirmed inferred relationships
- user-curated relationship labels
- inferred support links awaiting confirmation
- future graph-native commitments that are not yet first-class Finance entities

This avoids duplicating all mirror data into graph tables.

## 9. Graph Hydration

### 9.1 Hydration Strategy

Hydrate the graph from existing relational data first, then overlay native graph augmentations.

For performance, graph hydration must not assume unbounded transaction history loads. The graph read model should project a recent transaction window suitable for reasoning by default, and emit operational telemetry when source volumes grow unusually large.

#### Step 1: Resolve scope

From:

- current tenant
- current authenticated user
- optional household membership

#### Step 2: Load canonical source data

Read relevant Personal Finance and Platform data for the current user:

- `PersonalProfile`
- `Household`, `HouseholdMember`
- `PersonalAccount`
- `FinancialLinkedAccount`
- `PersonalTransaction`
- `Bill`
- `Goal`
- `Subscription`
- `Party`
- `PartyRelationship`
- `FxQuote` where relevant
- optional `Order` / `PaymentIntent` references when linked

Implementation note:

- personal transactions should be projected from a bounded recent-history window rather than full account history by default
- the default window should be documented and observable in logs/metrics
- if future product requirements need deeper history, add an explicit hierarchical or paged expansion path instead of silently loading the full table on each cache miss

#### Step 3: Project mirror nodes and edges

Create transient in-memory nodes and edges from source data.

#### Step 4: Load native graph augmentations

Overlay user-created or AI-confirmed native nodes and edges from:

- `FinancialLifeGraphNodes`
- `FinancialLifeGraphEdges`

#### Step 5: Return cached in-memory graph

The returned graph is read-only from the caller perspective.

### 9.2 No Repository Layer Requirement

Follow current AONIK patterns:

- services use `FinanceDbContext` directly
- avoid introducing a repository abstraction unless a later phase proves it necessary

## 10. Validation and Schema Rules

Use a lightweight internal schema definition rather than a separate ontology subsystem.

### 10.1 FinancialLifeGraphSchema

Define in C#:

- valid node types
- valid edge predicates
- allowed source entity mappings
- allowed `(fromType, predicate, toType)` combinations
- source-required vs native-only node types
- inferred-only node types and statuses

### 10.2 Validation Rules

Examples:

- `PersonalAccount`, `Bill`, `Goal`, `Subscription`, `PersonalTransaction`, `Party`, and `Household` mirror nodes must reference existing source rows.
- `RELATED_TO_PARTY` native edges must not duplicate active canonical `PartyRelationship` edges.
- `FUNDED_BY_ACCOUNT` native edges may only target `Goal` or `Bill`.
- inferred nodes/edges must capture `AiRunId`.
- material graph-native annotations must not create execution-side financial state.

## 12. Caching

Use existing Infrastructure caching patterns.

### 12.1 Cache Infrastructure

Use:

- `ICacheStore`
- `FusionCache`
- `ICacheInvalidationPublisher`

Do not build a parallel `IMemoryCache`-only subsystem.

### 12.2 Cache Key Shape

Include tenant and user in keys.

Recommended pattern:

- `personal-finance:graph:{tenantId}:{userId}`

Optional household variant:

- `personal-finance:graph:{tenantId}:{userId}:household:{householdId}`

### 12.3 Cache Set

Use a dedicated cache set name such as:

- `PersonalFinance.Graph`

### 12.4 Invalidation

Invalidate graph cache when relevant Personal Finance or native graph data changes, including:

- personal accounts
- linked accounts
- personal transactions
- bills
- goals
- subscriptions
- household membership
- native graph node/edge writes

Prefer integration with existing cache invalidation publishing patterns already used in Infrastructure.

Operational note:

- emit structured load metrics for graph hydration, including projected transaction count vs total transaction count when truncation is applied
- emit warnings when graph source volumes grow beyond expected consumer-finance ranges so the team can evaluate paging or hierarchical expansion before memory pressure becomes a production issue

## 13. API Surface

All endpoints remain within the existing FastEndpoints API.

All user-facing graph endpoints must use authenticated context and `Policies("UserPolicy")`.

### 13.1 Read Endpoints

#### Get graph

`GET /personal-finance/graph`

Returns:

- graph metadata
- nodes
- edges
- source coverage summary

#### Get graph summary

`GET /personal-finance/graph/summary`

Returns a compact summary for UI and agent consumption:

- accounts count
- upcoming bills count
- goals count
- subscriptions count
- household membership
- related parties count

#### Get upcoming obligations

`GET /personal-finance/graph/upcoming-obligations`

Returns upcoming bills/subscriptions/goals based on available due-date and renewal data.

### 13.2 Native Annotation Endpoints

Phase 2 only:

- `POST /personal-finance/graph/nodes`
- `POST /personal-finance/graph/edges`
- `DELETE /personal-finance/graph/nodes/{id}`
- `DELETE /personal-finance/graph/edges/{id}`

These endpoints are for user-confirmed annotations and graph-native links only.

Do not allow arbitrary creation of mirror nodes that duplicate canonical source tables.

## 15. AI and Audit Integration

### 15.1 Current Runtime Alignment

Use current AI integration patterns:

- `IPromptStore`
- `IChatClient`
- `IAiRunWriter`
- `IInsightWriter`

Do not block implementation on full `AiRoutePolicy` runtime enforcement, since the current runtime path is still config-driven.

### 15.2 Inference Rules

If inference is added, start with conservative, non-material use cases:

- repeated counterparty suggests relationship annotation
- recurring merchant suggests subscription annotation
- repeated due-date pattern suggests bill annotation
- transaction clustering suggests goal funding account suggestion

### 15.3 Inference Output Rules

- inferred nodes/edges start in non-applied status
- inferred nodes/edges must store `AiRunId`
- user confirmation is required before native inferred graph data becomes active
- no inferred output may directly create payment or order execution state

## 16. Calculations and Read-Side Reasoning

MVP graph calculations should align with available data.

### 16.1 Supported MVP Calculations

- list upcoming bills by due date
- list recurring subscriptions by renewal date
- summarize goals and progress
- summarize household/shared-finance context
- summarize related parties and known support relationships
- summarize personal-account and transaction connectivity

### 16.2 Deferred Calculations

Defer until balance or equivalent account-value data exists in Personal Finance:

- safe-to-send
- available-to-remit
- automated affordability scoring based on current account balance

These can be added in a later phase after account balances or derived balance snapshots are introduced.

1. Add cache-backed graph service

1. Add Finance agent tools

## 19. Acceptance Criteria

The feature is considered ready for MVP when:

- a signed-in user can retrieve a graph summary built from current Personal Finance and Party data
- the graph correctly reflects accounts, transactions, bills, goals, subscriptions, household membership, and related parties where source data exists
- graph cache entries are tenant/user scoped and invalidate on relevant writes
- graph-native annotations can be added without duplicating canonical relational entities
- AI/inferred annotations, if enabled, capture `AiRunId` and require confirmation before activation
- tests cover service hydration, validation, tenant isolation, and API behavior

## 20. Explicit Non-Goals for This Spec Revision

This spec revision intentionally does not require:

- a new `Payabo.Graph` codebase
- full ontology/DSL infrastructure
- graph-wide repository abstractions
- graph database adoption
- community savings-circle domain modeling before corresponding backend entities exist
- balance-based remittance automation before Personal Finance account balances exist

This is a repo-aligned specification for incremental delivery inside the current AONIK architecture.
