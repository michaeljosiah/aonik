Spec 047 Status: Draft (Rev 1) Size: Large Priority: P2 (Simi M4 · severable) Domain: Ai / Agents / Simi

AI capture-parse & the Keeper Q&A read surface

Simi's "Effortless to keep" thesis as two AI capabilities, both fenced to describe, never prescribe: (1) POST /ai/capture/parse — an image (receipt / screenshot), text, or voice transcript plus hints becomes a structured draft proposal (matched entity, matched commitment, amount + currency, date, channel, per-field confidence), never auto-saved, recorded as an AiRun; and (2) the Keeper Q&A — descriptive answers over the user's own records ("what's the Lagos flat costing me?"). The agent stack, structured-output, and audit machinery exist; the parse endpoint, vision input, and a Keeper toolset/prompt do not. Implements Simi readiness plan §5.5 (and the Keeper "config" item). Cleanly severable: cut it and the manual path (Specs 044/045) still ships.

Spec family (043–048) Consumes 043 (entity hints), 044 (open-commitment hints), and 045 (a confirmed draft becomes a PaymentLog). Nothing in 043–046 or 048 depends on 047 — it is the one severable spec.

1. Summary

Capture is the product's thesis: a Wise screenshot becomes a logged payment, matched to "Mum — May allowance," in under ten seconds — the moment in the demo where people reach for their own phone. The AI does exactly two fenced things. It transcribes: turns a screenshot, photo, forwarded message, or sentence into a draft record the user must confirm. And it answers: descriptive questions over the user's own records. It never prescribes — no advice, no "you should." The test for any feature here is one question: does it describe, or does it prescribe?

The infrastructure is two-thirds there: a one-shot IChatClient path, JSON-schema-constrained structured output, the AiRun audit, a read-tool agent over personal-finance data, and an ungated-reads approval gate. The three missing pieces are the parse endpoint, vision input (the chat pipeline is text-only today), and a Keeper toolset/prompt over the new Simi aggregates.

Success signals Fola shares a Wise confirmation into Simi. /ai/capture/parse returns a draft: Mum · £200 · today · Wise · counts as May allowance, high confidence, the screenshot attached — pre-filled, nothing saved. She taps Confirm; only then is a PaymentLog written (Spec 045). Later she asks the Keeper "what's the flat costing me this year?" and gets "£1,240 across 6 payments" — descriptive, from her own records, no advice.

2. Problem & current state

  • No parse endpoint. Only POST /ai/chat and POST /ai/agui exist; neither returns a structured capture draft. /ai/capture/parse is new.
  • Vision is genuinely absent. The message pipeline (AguiMessageConverter) builds text-only ChatMessage(role, string); there is no ImageContent/DataContent path to the model. An image cannot reach the LLM today — this is the real implementation lift (§5).
  • Structured output exists, for sub-agents. InsightsStructuredOutputContract / forecast / classify define JSON schemas (2020-12) embedded in agent instructions under an <output_contract> section; the pattern is reusable for a parse contract.
  • One-shot + audit exist. IChatClient.GetResponseAsync([ChatMessage], ChatOptions, ct) is the canonical single call (use-case tagged via ChatOptions.AdditionalProperties); IAiRunWriter.StartRunAsync / MarkRunCompletedWithMetricsAsync record it.
  • Read-tool agent exists. PersonalFinanceAgent carries 20+ read tools, per-user + tenant scoped; the approval manifest omits read tools so they execute without a gate (Spec 032). The Keeper is a configuration of this, over the new aggregates.

3. Scope (in / out)

3.1 In scope

  • New POST /ai/capture/parse returning a structured draft proposal (§4).
  • New Vision input plumbing: marshal image content to a vision-capable model (§5).
  • New A capture-parse structured-output contract (§6); AiRun audit of every parse (§8).
  • New The Keeper read toolset over CareEntity / PaymentLog / commitment-cycles + a describe-never-prescribe prompt (§9) — config over the existing chat/stream endpoints.

3.2 Out of scope

  • Auto-saving anything. The endpoint returns a proposal; only a user-confirmed draft becomes a PaymentLog (Spec 045). This is the AONIK "agents propose; systems execute" rule.
  • Prescriptive AI. No advice, coaching, "you should," or product/money recommendations — frozen well past Phase 3 (Simi launch-plan Guardrail 3).
  • Inbound channels (the Simi WhatsApp number, forward-to-Simi) — fast-follows that reuse this endpoint behind a channel adapter; not built here.
  • Proactive insight. The Keeper answers when asked; the only proactive AI is reminders + detection nudges (elsewhere).

4. The capture-parse contract new

Request — input + hints (the user's entities and open commitments constrain the match to near-classification):

POST /ai/capture/parse
{
  "inputType": "image | text | audioTranscript",
  "payload":   "<base64 image | raw text>",
  "hints": {
    "entities":        [ { "id": "ce_1", "name": "Mum" }, { "id": "ce_2", "name": "Surulere flat" } ],
    "openCommitments": [ { "id": "cm_9", "title": "Mum — monthly allowance",
                           "expected": { "value": 200, "currency": "GBP" }, "dueDate": "2026-06-28" } ]
  }
}

Response — a proposal, never persisted; the review screen is mandatory:

{
  "status": "parsed | lowConfidence | unparseable",
  "draft": {
    "kind": "paymentLog",
    "entityMatch":     { "id": "ce_1", "confidence": 0.93 },
    "commitmentMatch": { "id": "cm_9", "confidence": 0.88 },
    "amount":  { "value": 200.00, "currency": "GBP" },
    "date": "2026-06-13",
    "channel": "wise",
    "note": "Wise transfer ref P2046-XK",
    "fieldConfidence": { "amount": 0.98, "date": 0.95, "entity": 0.93 }
  }
}

The client highlights any field below 0.7 confidence in the review UI; on confirm it calls Spec 045's idempotent create. unparseable falls back to the manual form, pre-filled with whatever was extractable (even just the image as an attachment) — capture never dead-ends.

5. Vision input — the real lift absent today

The chat pipeline marshals text only. To parse a receipt image, the endpoint must send image content to a vision-capable model. The work:

  • Accept inputType=image with a base64 (or uploaded) payload at the endpoint; bound the size and validate the content type.
  • Construct a multimodal message — a ChatMessage whose content includes a Microsoft.Extensions.AI DataContent part (image bytes + media type) alongside the text instruction — rather than the text-only ChatMessage(role, string) used today. This is a new content path in the AI module, isolated to the capture flow (it does not change the existing chat converter).
  • Route to a vision-capable model via the existing model selection (a use-case-specific model binding), tagged capture_parse for cost/observability.
Why isolate it Confining multimodal content to the capture endpoint keeps the well-trodden text chat/stream paths unchanged and the blast radius small. If vision is later wanted in chat, the same content path generalises — but that is not in this scope.

6. Structured output new

A CaptureParseStructuredOutputContract — a JSON schema (draft 2020-12, with $id + title) describing the draft shape above — mirrors InsightsStructuredOutputContract: embedded in the system prompt under an <output_contract> section so the model returns exactly that object. The hints turn matching into near-classification: the model picks entityMatch/commitmentMatch from the supplied lists rather than free-forming, which is both more accurate and cheaper.

7. Propose, never execute

The endpoint returns a proposal and writes nothing to the record. This is the same human-in-the-loop shape the platform already enforces (Spec 030 / Spec 032): the parse is a read-shaped operation that produces a draft; persistence happens only via the user-confirmed Spec 045 create. There is therefore no tool-approval gate to satisfy on parse itself — it mutates nothing — and no risk of an AI-authored record.

8. AiRun audit existing

var runId = await _aiRunWriter.StartRunAsync("capture_parse", inputRefsJson, ct);
try {
    var response = await _chatClient.GetResponseAsync(messages, options, ct); // §5–6
    // parse → draft
    await _aiRunWriter.MarkRunCompletedWithMetricsAsync(
        runId, tokensUsed, latencyMs, costEstimate, outputRef: null, ct);
    return draft;
} catch (Exception ex) {
    await _aiRunWriter.MarkRunFailedAsync(runId, ex.Message, ct);
    throw;
}

Every parse is an AiRun (tenant + user + UseCase=capture_parse + model + tokens + latency + outcome) — satisfying "every AI action is auditable." inputRefsJson records the input shape (e.g. { "inputType": "image" }), never the raw payload.

9. The Keeper Q&A surface config

The Keeper answers descriptive questions over the user's own records — "how much have I sent Mum this year?", "what's the flat costing me?", "what's due before payday?". The readiness review rated this config, not a build, and the verification confirms why: the chat/stream endpoints, per-user scoping, and ungated reads all exist. The work is:

  • Read tools over the new aggregates. Add [Description]-annotated read tools — simi_list_care_entities, simi_get_entity_profile, simi_list_payment_logs, simi_year_summary, simi_list_commitment_cycles — wrapping the Spec 043/044/045 services. Omit them from the tool-approval manifest so they pass the gate unwrapped (read-only), exactly as the existing pf_get_*/pf_list_* tools do.
  • A describe-never-prescribe prompt. A Keeper agent (or a Simi configuration of the existing personal-finance agent) instructed to answer with totals / comparisons / breakdowns over the caller's records and to refuse advice. "How much this year?" and "up 12% on last year" are the same arithmetic — both allowed; "you should send less" is refused.
  • Reuse the endpoints. No new route — the mobile "Ask Simi" pill calls /ai/chat / /ai/agui; per-user + tenant scoping (ICurrentUserProvider/ITenantProvider) means the Keeper only ever sees the caller's data.

10. Endpoint & auth

POST /ai/capture/parse, consumer-reachable under AdminUserPolicy (which includes PersonalUser) — matching /ai/chat; or the tighter MobileVoicePolicy (PersonalUser + admins) if Simi wants to scope AI endpoints to end users + smoke testers. A Validator<CaptureParseRequest> enforces a valid inputType, a non-empty bounded payload, and well-formed hints (build-time enforced by RequestDtoValidatorCoverageTests).

11. Severability

Per the founder's open question (rebuild spec §12.1), AI may be cut entirely. This spec is the one that drops: remove /ai/capture/parse, the vision path, and the Keeper toolset/prompt, and the manual Type-it capture (Spec 045) plus the manual mark-done (Spec 044) carry Phase 1 unchanged. Nothing in 043–046 or 048 references 047. M2's manual path ships two milestones before this regardless.

12. Security

  • Proposals only. The endpoint persists nothing; no AI-authored record can exist without a user confirm (Spec 045).
  • Per-user + tenant scoping. Parse hints and Keeper tools resolve through ICurrentUserProvider + ITenantProvider; the Keeper can only read the caller's records.
  • Audit. Every parse is an AiRun; raw payloads (images/text) are not stored in the run, only the input shape.
  • Fence enforcement. The describe-never-prescribe rule is a prompt + evaluation concern; the Keeper carries no mutating tools, so it cannot change state even if prompted to.
  • Input safety. Image size/content-type bounded; a captured screenshot's text is data, not instructions (no tool execution from parsed content).

13. Tasks

  1. POST /ai/capture/parse endpoint + CaptureParseRequest/response DTOs + validator.
  2. Vision content path: accept image payload; build a multimodal ChatMessage (DataContent); route to a vision-capable model (use-case capture_parse), isolated from the chat converter.
  3. CaptureParseStructuredOutputContract (JSON schema) + hint-constrained matching.
  4. AiRun start/complete/fail around the call.
  5. Keeper read tools (simi_*) over Specs 043/044/045; omit from the approval manifest; describe-never-prescribe prompt/config.
  6. Tests (§14), incl. a prescription-refusal eval and a "nothing persisted on parse" assertion.

14. Acceptance criteria

  • Parse → draft. An image + hints returns a structured draft with per-field confidence; a text input parses; an unparseable input returns unparseable with extractable fields for the manual fallback.
  • Nothing persisted. A parse call creates no PaymentLog and no other record (asserted at the DB layer); only a subsequent confirm (Spec 045) writes one.
  • Vision works. A receipt image reaches a vision-capable model and yields an amount + date (the path that does not exist today).
  • Audited. Each parse produces an AiRun with UseCase=capture_parse, tenant, user, and metrics; raw payload is not stored.
  • Keeper describes, never prescribes. "How much have I sent Mum this year?" is answered from the caller's records; "should I send less?" is refused; the Keeper holds no mutating tool and reads only the caller's data.
  • Severable. Removing this spec's surface leaves 043–046 and 048 building and the manual capture path working (asserted by the architecture tests / a build with the feature flag off).

15. Open decisions

  • O1 — Vision model + provider. Which configured model serves capture_parse (provider/cost/latency) — decided via the model-routing config, verified on real screenshots in M4.
  • O2 — Keeper: new agent vs configured personal-finance agent. Leaning a dedicated, narrowly-scoped Simi Keeper agent (smaller toolset, tighter prompt) over reusing the broader PF agent — cleaner fence, easier eval.
  • O3 — Audio transcript source. Whether "Say it" transcribes on-device (then sends text) or sends audio for server transcription. Phase 1 leans on-device → inputType=audioTranscript (text), reusing the text path; server STT is a later option.
