Spec 089 Status: Draft (Rev 5 — sync split out to 091) Size: Medium Module: Aonik.Workspaces

Workspaces: a versioned tree of files

Implements ADR-016. A workspace is a versioned tree of files owned by a party — shareable, quota'd and syncable. An Arke world is a workspace whose Kind is world, exactly as a personal-finance household is a group whose kind is household. The platform owns the container, the tree, the revisions and the blobs. It never opens a file: what a sheet or a canon entry means belongs to the product, and if this module ever learns otherwise the seam has failed.

This spec is the server half. The protocol is Spec 091. Sync was originally specified here. Three rounds of adversarial review put the large majority of findings on the sync half while the model, the sharing seam and the quota design went quiet after round one — confirming what ADR-016 said up front: "sync is the highest-risk component in the plan, and everything else here is plumbing." Keeping both in one document made the settled half look as unfinished as the hard half and gave reviewers one budget for two different jobs. 089 is now buildable and mergeable on its own; 091 gets its own review.

1. Summary

Arke Studio is local-first: "Worlds are folders of readable files on the user's own disk… the filesystem as the only durable truth." A commercial cloud tier alongside the free product changes exactly one thing — a world must be able to exist somewhere other than one person's disk.

This spec adds the smallest platform capability that makes that true, and nothing else:

  • A Workspace — a named, tenant-scoped, party-owned container with a Kind.
  • A WorkspaceRevision — a monotonic snapshot, which is a manifest of path → hash.
  • Content-addressed blobs through the existing IFileStore, which already returns a SHA-256 on upload.
  • A pull/push sync protocol that is, in essence, "here are my hashes; which do you not have?"
  • workspace registered as a ShareResourceKind, so Spec 086's invites, expiry and revocation apply unchanged.
  • Workspace count and stored bytes as meters, so Spec 087 can price them.
The folder is the wire format Not for convenience — for independence. The free application is MIT-licensed and must not acquire a dependency on AONIK. It reads and writes folders; a sync client moves them. The local tree stays authoritative offline and the cloud holds a mirror of the same tree, so the product's domain layer never learns this module exists.

2. Why a tree, and why here

The platform has two things that look adjacent and are not:

ExistingWhat it isWhy it is not a workspace
IFileStore existing Upload a blob, get back a storage key, size, content type and SHA-256. No path, no revision, no manifest. It stores a file, not a tree over time. It is the right primitive underneath this spec, and it is reused verbatim.
Aonik.Documents existing Classification, chunking, embedding and scoped retrieval of individual documents. Built to answer "what does this document say?" A workspace answers "what did this tree look like at revision 7?" Bending one into the other gives one module two incompatible jobs.

2.1 Why the platform rather than the product

The sharing seam decides it Spec 086 §6 asks the owning module "does this owner own these ids?" through an IShareResourceResolver, on the hot path of an authorisation check. If worlds live in Arke, the platform must call the product over HTTP to answer it — inverting the dependency, for an application designed to work offline. If workspaces live here, the resolver is a query against this module's own table.

Two further consequences fall out of the same placement. Quota is only expressible if the platform knows how many workspaces exist and how large they are. And two products need it — Arke Studio and Arke Kids both have worlds, which is the same two-consumer test that put groups in the platform: one consumer is a feature, two is a capability.

3. Scope (in / out)

3.1 In scope

  • The Aonik.Workspaces middle-layer module: entities, configurations, WorkspacesDbContext, services.
  • Content-addressed blob storage over IFileStore, including deduplication and reference counting.
  • Revisions as immutable manifests; the head pointer; history.
  • Revision commit semantics: CommitId idempotency, sequence allocation and head advancement as one guarded write.
  • Divergence detection, its expression as a proposal rather than a merge, and the operation that resolves it.
  • Server-side validation of everything a commit asserts: paths, blob possession, quota, size.
  • workspace as a share resource kind, with a resolver inside this module.
  • Count and byte meters, and the enforcement point for both.

3.2 Out of scope

  • Real-time collaborative editing. Operational transform and CRDTs are a different product.
  • Merge algorithms. Divergence produces a proposal; the human decides. See §7.
  • Branching. One head per workspace.
  • Per-file permissions. A grant names a workspace, not a path.
  • Any interpretation of file contents. No parsing, no schema, no validation of what is inside a file.
  • The sync protocol itself — negotiation, resumable transfer, and applying a pull to a folder on someone's disk. That is Spec 091, and it is the larger and riskier half.
  • Server-side media dispatch and offline entitlement — the latter is Spec 090.
  • Git. Arke's specification forbids a git dependency (§2.4). Content addressing gives the dedupe without it.

5. Content addressing

A blob is identified by the SHA-256 of its bytes. 

hash = SHA-256(bytes)
storageKey = "workspaces/{tenantId:N}/blobs/{hash[0..2]}/{hash}"
P0 — IFileStore cannot do this today, and saying otherwise hides a real prerequisite

An earlier draft of this section claimed the primitive already existed because IFileStore.UploadAsync returns a SHA-256. It does — but it returns it after writing the object to a randomly-named GUID path it chose itself. There is no write-by-key and no atomic promote. The hash is therefore an output, never an input, so the key above cannot be produced by the interface as it stands.

The consequence if this is not fixed first: two identical uploads write two physical blobs, and only the database row is deduplicated — leaving the second object stranded and paid for. Concurrent uploads of the same content strand more. P3 therefore extends the storage contract before anything else: 

// New on IFileStore (P3, additive — no existing caller changes)
Task<StagedBlob> StageAsync(Guid tenantId, Stream content, CancellationToken ct);
//   streams to a temporary key, hashing as it goes; returns (hash, size, tempKey)

Task<PromoteResult> PromoteAsync(StagedBlob staged, string contentKey, CancellationToken ct);
//   atomically moves temp → content key. If the key already exists, the staged
//   copy is DISCARDED and the result reports AlreadyPresent. This is the whole
//   concurrency answer: last writer discards rather than duplicates.

With that in place, three properties follow — stated at the strength they actually hold:

  • Dedupe, and only where bytes truly repeat. An unchanged sheet is stored once across a world's whole history, not once per revision; a reference image shared by ten takes is stored once; a workspace re-synced to a second machine transfers nothing. This does not extend to the takes themselves — see the warning below.
  • Cheap sync. "Which of these hashes do you not have" is answerable without transferring anything, so an unchanged 2GB world syncs in one round trip and no bytes.
  • Integrity. A downloaded blob is verified against the hash that named it, so a corrupted or substituted object is detected by construction rather than by trust in the store.
Content addressing does not deduplicate near-identical media, and the commercial model must not assume it does SHA-256 deduplicates byte-identical blobs. Two independently generated takes of the same shot are visually near-identical and byte-wise unrelated; so are two encodes of one source. Each costs its full size. Since takes are the largest objects in a world, the honest planning assumption is that the media path barely dedupes at all and the authoring path dedupes very well. Anything better would need chunking or content-aware similarity detection, which is explicitly out of scope (§3) — so the byte ceiling in §9 must be priced against undeduplicated media.
Reference counting is not optional Deleting a revision must not delete bytes another revision still names, and deleting a workspace must not delete bytes another workspace in the same tenant deduped against. RefCount is maintained in the same transaction as the manifest write; a blob reaching zero is swept, never deleted inline. Getting this wrong destroys data silently and is discovered by a user opening an old revision to find it empty.

5.1 Sweeping must be serialised against new references

P0 — "swept, never deleted inline" describes the timing, not the race

A reference count that reaches zero is not a stable fact. The sweeper reads RefCount = 0 and selects the blob; before it deletes the object, a new commit legitimately references that hash — the row still exists, so validation passes and the count increments. The sweeper then deletes the physical object on the strength of an observation that is already stale, and the freshly committed revision points at bytes that are gone.

The symptom is the worst kind: the commit succeeded, the manifest is valid, the database is consistent, and the file is simply missing — discovered much later by a user opening a revision. Deleting lazily does not help, because the window is between the sweeper's read and its delete, wherever that sits in time.

Deletion therefore claims the blob before touching storage, and referencing refuses a claimed blob:

SWEEP                                  COMMIT (referencing a hash)
─────                                  ──────────────────────────
UPDATE WorkspaceBlobs                  read blob row
   SET State = Deleting                State == Deleting -> TREAT AS MISSING.
 WHERE ContentHash = @h                  The client re-uploads; promote finds
   AND RefCount = 0                      no object and stores it afresh, or
   AND State = Available                 finds one and reuses it. Either way
   AND RowVersion = @v                   the caller is never handed a
                                         reference to bytes being removed.
0 rows -> someone referenced it
   or another sweeper claimed it.       Incrementing RefCount is guarded on
   ABANDON. Do not delete.                State = Available in the SAME
                                         statement, so a claim that lands
1 row -> the claim is ours.               between read and write loses.
   RE-CHECK RefCount = 0 under the
   claim, delete the object, then
   delete the row.
Why a tombstone state rather than a lock or a longer delay A lock serialises every commit in a tenant against a background job, which is the wrong trade for a race this rare. A delay only moves the window. The Deleting state makes the two operations mutually exclusive by data rather than by timing: whichever writes first wins, the loser sees it and takes the safe branch, and the safe branch for a referencing client is simply "upload it again" — which costs one redundant transfer in a rare case and can never produce a dangling reference. It is the same compare-and-swap discipline as §6.2 and UsageMeter, applied to a different invariant.

6. Revisions and the head

A revision is created by presenting a complete manifest — every path in the tree with its hash — plus the parent the client believed it was building on. The server:

  1. rejects the commit if any named hash has no blob (upload first, commit second — never the reverse);
  2. compares parentRevisionId to the current head;
  3. if they match, appends the revision and advances the head — a fast-forward;
  4. if they do not, appends the revision without advancing the head and returns Diverged. See §7.

The manifest is complete rather than a delta. That is deliberate: a delta requires the server to trust the client's account of what changed, and a client that omits a deletion silently resurrects a file. A complete manifest makes the revision self-describing and the diff computable server-side.

6.1 Commit idempotency is not the sequence number

P0 — the correction

An earlier draft made the per-workspace Sequence the idempotency key a retried commit lands on. It cannot be, and the reason is that it breaks the divergence flow this spec is built around:

  • If the client chooses the sequence, two clients committing from the same head both choose N+1. The unique index rejects the second — but the second is precisely the case that is supposed to be stored as Diverged and surfaced as a proposal. The design's central mechanic would be unreachable, and the user would see a database error instead of a conflict.
  • If the server assigns the sequence, a retried commit has no stable value to identify the original by, so a timeout followed by a retry creates a second revision of identical content.

The two concerns are separated:

FieldChosen byPurposeIndex
CommitId new Client, once, before the first attempt — and reused unchanged on every retry Idempotency. A commit whose CommitId already exists returns the original outcome verbatim, including a prior Diverged. Unique (TenantId, WorkspaceId, CommitId)
Sequence Server, at commit time, inside the transaction Ordering and history only. Never sent by a client, never used to detect a retry. Unique (TenantId, WorkspaceId, Sequence)

Divergence is then detected where it belongs — by comparing the declared ParentRevisionId against the current head — rather than as a side effect of a uniqueness collision. A diverged commit still receives a sequence and is still stored; it simply does not advance the head.

6.1.1 A CommitId binds to one request, not to a name

P0 — replaying an outcome for a different tree is worse than not retrying Treating any matching CommitId as the same operation is unsafe once you consider what a client actually does after a timeout. It does not know whether the commit landed, the author may have kept working, and the client correctly reuses the CommitId — but rebuilds the manifest from a tree that has since changed. The server returns the original outcome verbatim, and the client concludes the new tree is committed when it is not. The next pull then treats those edits as absent, and the work is lost silently, with a success response on the record.

The idempotency record therefore stores a canonical request hash — SHA-256 over the workspace id, the declared parent, and the manifest as a sorted path→hash list — alongside the outcome: 

same CommitId + same request hash  -> replay the stored outcome (a true retry)
same CommitId + DIFFERENT hash     -> 409, explicitly: "this CommitId was used
                                      for a different tree; use a new one"
                                      Never a silent replay.

The failure mode becomes a loud client bug rather than quiet data loss, which is the correct trade for anything in the commit path.

6.2 Advancing the head is a compare-and-swap, not a transaction

P0 — "inside the transaction" is not the same as atomic

§7.3 said the server assigns the sequence "inside the transaction", which sounds sufficient and is not. Under SQL Server's default READ COMMITTED, two concurrent commits can both read the same head, both classify themselves as fast-forwards, and then either lose one head update or collide on the sequence index. Neither outcome is the specified one: the loser is supposed to be stored as Diverged, and instead it either vanishes or errors.

The acceptance criterion added in Rev 2 — "two clients committing concurrently from the same head both persist" — was therefore not satisfiable by the mechanism described.

P0 — the Rev 3 CAS guarded the wrong operation, and the loser still died before reaching it

Rev 3 put the compare-and-swap on the head update while leaving sequence allocation earlier and the revision INSERT earlier still. So two commits reading the same head both compute sequence N+1, and the loser collides on the unique sequence index during its insert — it fails there, and never reaches the zero-row CAS path that was supposed to reclassify it as Diverged. The fix guarded a step the loser could not get to.

Sequence allocation and head advancement are the same atomic decision and must happen in one guarded write, before any row is inserted.

Workspace therefore carries NextSequence alongside HeadRevisionId, and a single RowVersion compare-and-swap consumes the sequence and advances the head: 

read  workspace (Head = H, NextSequence = S, RowVersion = V)
classify: parent == H ? FastForward : Diverged

UPDATE Workspaces
   SET NextSequence   = S + 1,
       HeadRevisionId = (FastForward ? newRevisionId : HeadRevisionId)
 WHERE Id = @id AND RowVersion = V

0 rows -> ANOTHER COMMIT WON. Nothing has been inserted, so nothing is
   orphaned. RE-READ and RE-CLASSIFY: the parent no longer matches, so
   this commit is now Diverged — the correct answer, reached by the same
   rule rather than by an exception handler. Bounded retry; each attempt
   re-classifies from the head it actually observed.

CAS SUCCEEDED -> only now INSERT the revision with sequence S,
   in the same transaction.

The ordering is what makes it work: a sequence is only ever consumed by a successful CAS, so two revisions cannot receive the same one and the unique index never fires in normal operation — it becomes a backstop rather than the mechanism. A diverged commit consumes a sequence too (it is a real revision and must be orderable); it simply leaves HeadRevisionId untouched.

This is the identical pattern UsageMeter already uses for ceiling claims, and for the identical reason recorded there: "a point-in-time count that takes no lock and writes no row is a check-then-act race, and it over-admits under exactly the conditions a ceiling exists for." A serializable lock would also work and is rejected — it serialises every commit in a workspace to protect against a rare collision, and the CAS costs nothing when there is no contention.

7. Divergence, and how it ends

Sync reuses the product's own mechanic Arke Studio's core mechanic is the accept gate: "nothing enters the authored record without a human accept… proposals are ripple-checked against canon." A remote revision that does not descend from the local head is a proposal. It is ripple-checked and accepted exactly as a locally-drafted change is.

This is the most important design decision in the spec, and it is a decision to not build something. No merge algorithm, no three-way diff, no conflict markers, no new vocabulary for the user to learn — because the product already has a word for "a change that has not been accepted yet", and this is one.

The platform's part is deliberately small. It:

  • detects divergence (parent ≠ head) and says so;
  • stores the divergent revision, so nothing is lost while the human decides;
  • exposes the two manifests and the paths that differ.

It does not decide which side wins, because deciding would require understanding what the files mean — which is the line this module must never cross.

7.1 How a divergent revision ends

P0 — the spec stored divergent revisions and never said how they stop being divergent

"A human decides" was the whole answer, and it left two holes. There was no operation to record the decision — so after the human chose the divergent tree, no client had a specified way to advance the cloud head to it. And a rejected revision stayed referenced forever under all-history retention: its blobs were never released and its bytes were charged to the ceiling indefinitely, so a user who repeatedly rejected conflicts would accumulate unreachable, unbillable-away storage with no way to reclaim it.

Refusing to merge was right. Refusing to define termination was an omission.

ResolveAsync(workspaceId, revisionId, outcome, commitId) — the resolution is itself a commit, with the same idempotency and the same CAS as any other:

OutcomeWhat the platform doesWhy
Accept Writes a new revision carrying the divergent manifest, parented on the current head, and advances the head to it under §6.2. The divergent revision is marked Superseded and retained. History is never rewritten. The head is not repointed at a revision whose parent is not its predecessor — that would make the chain a lie and break every history read. A resolution is a normal forward step that happens to carry someone else's tree.
Reject Marks it Rejected. After a retention window (proposed: 30 days) the sweeper drops its manifest rows, decrements the blobs it uniquely held, and releases the corresponding byte claims. A rejected revision is not history — it is a change that never entered the record. Keeping it briefly makes rejection undoable; keeping it forever makes rejection expensive.
Supersede Neither side wins: the client commits a third manifest — the human's edited result — parented on the current head. The divergent revision is marked Superseded. This is what the accept gate actually produces most of the time. The platform stores the outcome; the product decided it, file by file, without the platform reading anything.
  • Unresolved divergent revisions still count against quota — they are stored bytes. They are listed with their size so the cost is visible, rather than silently accruing.
  • Resolution is idempotent on the same commitId, and resolving an already-resolved revision returns the recorded outcome rather than acting twice.
  • The platform still decides nothing. It records which of three outcomes a human chose. Everything that made that choice — ripple checks, canon, the diff the author actually read — happened in the product, on file contents this module never opened.

7.2 Which revision is true

SituationAuthority

Between machines, or with a collaboratorThe cloud head. It is the only thing both parties can see.

8. Sharing a workspace

Registered as a ShareResourceKind, so every mechanic in Spec 086 applies with no new code: opaque single-use invite tokens, expiry, immediate revocation, ownership validation, and the anonymous preview. 

ResourceKind   "workspace"
ResourceIds    ["<the-undersong>", "<copper-saints>"]
AccessLevel    Write                       ← platform-owned, closed enum, ENFORCED (§10.1)
TermsJson      { "role": "co-author",      ← the product's words; the platform never reads them
                 "canComment": true }

The resolver lives in this module and returns ShareResourceRef(Id, "workspace", Name) for workspaces the owner actually owns — omitting the rest, which is what lets grant creation detect a caller naming someone else's ids. Because it is a local query, an authorisation check costs one round trip and never leaves the platform.

8.1 Read/write is a platform concept, and an earlier draft had this dangerously wrong

P0 — the vulnerability this closes

An earlier draft said: "Whether the recipient may commit is TermsJson — the product's business, read by the product," reasoning that a platform enforcing an "editor" role would be interpreting terms, which Spec 086 §6.1 forbids.

That is a bypassable authorisation boundary and it must not ship. The commit endpoint is a platform HTTP endpoint. A recipient holding a read-only grant needs only to call it directly — with curl, or with a modified client, which for an MIT-licensed open-source product is a five-minute exercise. The product-side check is decoration; there is nothing behind it. The grant reader answers "is there a grant?", and the answer for a read-only recipient is yes.

The fix does not weaken the seam — it draws it in the right place. There is a difference between authorisation, which the platform must own because it owns the endpoint, and product semantics, which it must never open:

FieldOwnerShapeRead by the platform?
AccessLevel new Platform A closed enum: Read | Write | Owner. Three values, no extension point, no DSL. Yes — and enforced. This is the whole point.
TermsJson Product Anything. {"role":"co-author","canComment":true,"canExport":false} Never. Stored and returned verbatim, exactly as Spec 086 §6.1 requires.

IWorkspaceSyncService resolves the caller's effective access before accepting a revision, and the rule is a single line with no product involvement: 

effective = Owner            if caller party == workspace.OwnerPartyId
          | grant.AccessLevel if an active, unexpired, unrevoked grant names this workspace
          | none              otherwise

CommitAsync   requires effective >= Write     → 403 otherwise
UploadBlob    requires effective >= Write     → 403 otherwise (no quota consumption by readers)
GetManifest   requires effective >= Read
Delete/Share  requires effective == Owner
Why this does not breach the seam The platform still cannot tell you what a "co-author" is, whether comments are allowed, or what a canon entry means — TermsJson remains opaque and the product remains the only reader. What the platform now knows is whether this caller may write to this container, which is not product semantics; it is the access-control question every endpoint owner has to answer for itself. Spec 086 §6.1 forbids the platform interpreting terms. It never asked the platform to leave its own endpoints unguarded.

9. Quota and metering

MeterKindEnforced where
workspacesCeiling — one held slot per workspace, released on deleteCreate
workspace-bytesWeighted ceiling — n held bytes per stored blob, released when the blob is sweptBlob upload, before the bytes are accepted
P0 — why stored bytes are a ceiling and emphatically not a counter

An earlier draft made workspace-bytes a counter, "drawn down as blobs are stored, returned on sweep." The second half of that sentence is not implementable against Spec 087, and the code is unambiguous: CommitAsync moves the reservation out of Held and into Consumed (UsageMeter.cs:182-183), while release returns only the uncommitted Held portion (UsageMeter.cs:411). Consumed never decreases — correctly, because a counter measures a flow that has happened and cannot un-happen.

The consequence had this shipped: a customer uploads 40GB, deletes it, and has permanently burned 40GB of a 50GB allowance while using none of it. Upload-and-delete cycles would brick the account, and the support ticket would be indistinguishable from a billing fault. Storage is a level, not a flow — the same category as a seat count — and a level is what a ceiling models.

Spec 090 already carries workspace-bytes in lim — its ceilings collection — so this correction also removes a contradiction between the two specs rather than merely fixing one.

9.1 The one extension this needs from Spec 087

Ceiling claims today are unit-weighted: ClaimAsync tests Held + 1 > ceiling and increments by one, idempotently per HolderRef, under a RowVersion compare-and-increment (UsageMeter.cs:265-300). A byte ceiling needs the same lifecycle with a weight: 

ClaimAsync(subscriber, meterCode, holderRef, weight: 1)      // additive default — no caller changes
    → tests Held + weight > ceiling
    → CeilingClaim.Weight persisted so ReleaseAsync returns the right amount

HolderRef is the content hash, which makes the accounting fall out for free: claiming is idempotent per blob, so the same bytes referenced by ten revisions are charged once, and the release happens exactly when the orphan sweeper deletes the blob. Both properties come from machinery Spec 087 already has.

P0 — the weight does not fit in the column, and the numbers are not close

CeilingHolding.Held is an int (Entities/Usage/CeilingHolding.cs:24), because every ceiling to date has counted seats and profiles. int.MaxValue is 2,147,483,647. The 200GB figure in Spec 090's example payload is 214,748,364,800 — exactly one hundred times larger, and even a 3GB world overflows it.

So "just add a weight parameter" would silently overflow or truncate on ordinary paid-tier usage, not at some implausible extreme — and a wrapped aggregate does not fail loudly, it under-counts, which means the ceiling stops refusing and the storage bill is discovered later.

P6 therefore also migrates the arithmetic, not only the signature:

  • CeilingHolding.Held and CeilingClaim.Weight become long — bytes are integral and a 64-bit count reaches ~9.2 exabytes, which is not a limit anyone will meet. (EntitlementGrant.Held is already decimal; the ceiling path simply never needed the range until now.)
  • The ceiling value itself, every comparison, and EntitlementExceededException's quantity and remaining figures all widen with it. A long aggregate compared against an int limit is the same bug one layer up.
  • A migration against AonikDbContext widens the columns. Widening int → bigint is non-breaking for existing rows.
  • An explicit overflow test claiming more than int.MaxValue bytes across several blobs, in the LocalDB lane — the InMemory provider would not catch a column-width truncation.

9.2 Quota must move when ownership moves

P0 — a hole between two features that are individually correct IWorkspaceService exposes ownership transfer, and ceiling claims are held against a specific subscriber. Nothing connected the two. So transferring a workspace would leave the former owner's claims held indefinitely — paying for storage they no longer have, with no way to release it — while the recipient gets it for free, with no check that they have the capacity or even a subscription. Both halves are wrong in opposite directions, and the customer-facing symptom is a billing complaint neither party can explain.
  • The billing subscriber is stored on the workspace and is the thing claims are held against — deliberately separate from OwnerPartyId, because they can legitimately differ (an Arke Kids workspace owned by a parent may be billed to a family subscription).
  • Transfer is a claim migration, in one transaction: compute the workspace's count and byte weight, claim them against the recipient first, and only on success release the former owner's and move the billing subscriber.
  • Release the former owner's claim for a hash only when no workspace still billed to them references it.
    P0 — the elegance of HolderRef = hash is exactly what makes release ambiguous Keying the claim on the content hash gives idempotency for free — ten revisions naming one blob are charged once — but that same idempotency means a subscriber has one claim covering all their workspaces that reference the hash. So if they hold two workspaces sharing a blob and transfer only one, releasing "their claim for that hash" leaves the retained workspace's bytes completely uncharged, even though the physical blob cannot be swept and we are still paying for it. Repeat it and a subscriber can end up storing a great deal for free, entirely through legitimate use.

    Release therefore requires per-subscriber reference accounting: a count of how many workspaces billed to that subscriber reference each hash, decremented on transfer and deletion, with the ceiling claim released only at zero. It is the same reference-counting shape as WorkspaceBlob.RefCount, one level up — physical RefCount answers "may these bytes be deleted?", the per-subscriber count answers "may this subscriber stop paying for them?", and they are genuinely different questions.
  • Insufficient capacity refuses the transfer with the shortfall named. It does not proceed and over-admit, and it does not strand the workspace between owners.
  • Claim first, release second — never the reverse. Releasing first opens a window where a concurrent claim consumes the freed allowance and the transfer then fails with the original owner's claim already gone.
  • The same accounting applies to workspace deletion, which is the degenerate transfer: release both meters, once, when the sweeper has actually removed the bytes.
Metered from day one, not later A storage limit retrofitted onto users who have already uploaded 200GB is a support problem, not an engineering one. The byte ceiling is checked before an upload is accepted, so the failure is "you are out of space" rather than a surprise bill or a silent truncation. Price the ceiling against undeduplicated media — §5 explains why takes do not dedupe.

10. Persistence & migration

  • Four new tables — AnkWorkspaces, AnkWorkspaceRevisions, AnkWorkspaceFiles, AnkWorkspaceBlobs — all tenant-scoped, all Ank-prefixed in dbo.
  • Migration generated only against AonikDbContext per CLAUDE.md. WorkspacesDbContext declares none.
  • Unique index on (TenantId, WorkspaceId, Sequence) — ordering only. The server assigns it inside the transaction; no client ever sends one.
  • Unique index on (TenantId, WorkspaceId, CommitId) — this is the idempotency key a retried commit lands on, and keeping it distinct from Sequence is what allows a divergent commit to be stored rather than rejected (§6.1).
  • Unique index on (TenantId, ContentHash) for blobs, which is what makes dedupe a database guarantee rather than an application hope.
  • Unique index on (TenantId, SubscriberKind, SubscriberId, ContentHash) on AnkWorkspaceBlobPossessions — the proof-of-possession record that stops a content hash acting as a bearer capability (§14).
  • RowVersion on AnkWorkspaces, which is what makes head advancement a compare-and-swap rather than a read-then-write race (§6.2).
  • Unique index on (RevisionId, Path). A manifest naming one path twice is malformed, and the database is the right place to say so.
The LocalDB lane is mandatory here Three of the four indexes above are filtered or uniqueness-bearing, and the InMemory provider enforces no unique index at all. Per CLAUDE.md, coverage for them belongs in tests/Aonik.Database.Tests — an InMemory test asserting dedupe would pass against a schema that does not dedupe.

12. Security

RiskControl
Path traversal. A manifest path of ../../etc/passwd or a Windows device name. Paths are validated on commit: relative, forward-slash, no . or .. segment, no drive letter, no leading slash, no NTFS stream, no reserved device name. Rejected, not sanitised — silently rewriting a caller's path is how two files become one.
Reparse-point traversal. A manifest path linked/scene.txt where linked is a symlink or NTFS junction in the live tree pointing outside the workspace. Lexical validation does not cover this and Rev 2 wrongly implied it did — linked/scene.txt contains no .. and is a perfectly legal relative path, yet a pull writing to it escapes the workspace entirely. The link need not even be hostile: it can arrive from another tool, a restored backup, or the user's own convenience. Every activation operation therefore resolves the target with no-follow semantics and verifies the resolved path is still beneath the workspace root before writing; a component that is a reparse point aborts the operation rather than traversing it. Server-side, a commit whose source tree contained a reparse point is refused on the same rule. Checking the string is not checking the destination.
Filesystem-equivalent path collision. Scene.txt and scene.txt, or names differing only by trailing dot or space, are two distinct server paths that are one file on Windows. NFC alone does not give every client the same tree, which Rev 2 claimed. During pull the two entries silently overwrite each other and the resulting tree matches no manifest — which then pushes as a spurious revision. A single portable equivalence rule is applied at commit: NFC, then case-fold, then strip trailing dots and spaces per Windows rules, per path segment. A manifest containing any pair that collides under it is rejected as malformed, with both paths named. Rejecting at commit is the only option that keeps every supported client able to materialise the tree — sanitising would silently merge two authored files. The same normalisation guards the reserved .aonik/ prefix (091 §8.4).
File/directory prefix collision. A manifest containing both foo and foo/bar.txt. Equivalence checking does not catch this and Rev 3 did not consider it. The two full paths are not equal under case-folding or trailing-character normalisation, so the pair rule passes them — yet no filesystem can materialise foo as both a regular file and a directory. A revision committed with that pair fails partway through pull, and because the journal replays toward a target that can never be reached, recovery retries an impossible operation indefinitely — the tree is stuck and every subsequent read is gated behind a recovery that cannot finish. A manifest where any path is a segment-boundary prefix of another is therefore rejected at commit, evaluated under the same normalisation so Foo and foo/bar.txt are caught too. This is the class of defect worth rejecting server-side rather than trusting clients to avoid: it is cheap to check once and expensive to recover from.
Hash substitution / the hash as a bearer capability. A caller commits a manifest naming a hash they never uploaded, to reference someone else's blob and then read the bytes back through their own manifest. Tenant scope alone is not sufficient, and this is the finding that matters most in this table. Rev 2 accepted any hash with a blob in this tenant — which is fine when a tenant is one customer, and wrong for Arke Kids, where one tenant holds many unrelated families. Guessing is not required either: hashes of shared or previously-seen content are knowable, and a match turns into a read. A content hash is a name, and Rev 2 treated it as an authorisation.

A commit may therefore only name a hash the caller has demonstrated possession of:
  • uploaded by this subscriber (a BlobPossession row per subscriber per hash, written on promote — including when promote discovers the blob already exists, since they still supplied the bytes), or
  • already reachable by this caller through a workspace they can read.
Dedupe stays physical; authorisation becomes per-subscriber. The bytes are still stored once — the saving is preserved — but a reference requires proof, so the hash stops being a bearer token. A commit naming an unpossessed hash is refused as missing, never as forbidden: the distinction would confirm the blob exists and hand back the existence oracle the control just closed.
Quota bypass. Upload, then check. The byte ceiling is claimed before the stream is accepted and released on failure, using Spec 087's claim/release lifecycle rather than a post-hoc count. Callers without Write access consume no quota because they are refused before staging (§8.1).

But a pre-stream claim can only use a size the caller declared, and Rev 3 never bound the two together. StageAsync learns the authoritative size as it consumes the stream, so a direct client — not our client, a caller hitting the API — could declare 1MB, send 4GB, and store it. The claim would be honest and the storage would not.
  • A declared length is mandatory. A chunked upload with no declared total is refused; "we will find out how big it is" is not compatible with claiming quota first.
  • The read is bounded by the claim. StageAsync aborts the moment the stream exceeds the declared length rather than discovering it afterwards — which also caps the damage a hostile caller can do to disk.
  • Staged size is verified against the declaration before promote. Any difference in either direction discards the staged object and releases the claim: over-declaring to reserve headroom is as much a quota lie as under-declaring.
Zip-bomb / oversize single file. A per-file ceiling and a per-commit file-count ceiling, both configurable, both enforced before bytes are read.

14. Acceptance criteria

  1. Aonik.Workspaces references only Aonik.SharedKernel.
  2. No type in the module names a product concept — no sheet, canon, production, world except as the value of Kind.
  3. Identical bytes stored twice occupy one blob, proven on LocalDB, where the unique index is real.
  4. Deleting a revision that shares a blob with another revision leaves the bytes readable.
  5. A commit naming a hash with no blob in this tenant is refused, and no revision is created.
  6. A commit whose parent is not the head is stored, reported as Diverged, and does not advance the head.
  7. A commit retried with the same CommitId returns the original outcome and creates no second revision — including when that outcome was Diverged.
  8. Two clients committing concurrently from the same head both persist: the first advances the head, the second is stored as Diverged. Neither receives a uniqueness error.
  9. No client-supplied Sequence is accepted by any endpoint.
  10. A caller holding a Read grant receives 403 from the commit and upload endpoints called directly, with no product-side check involved.
  11. Uploading a blob consumes no quota for a caller who is not permitted to write.
  12. Deleting a workspace returns its held bytes, and the same bytes can then be uploaded again.
  13. The same content hash referenced by ten revisions is charged against the byte ceiling once.
  14. Retrying a commit with the same CommitId but a different manifest, parent or workspace is refused with 409, never replayed as success.
  15. Two clients committing concurrently from the same head: one advances the head, the other is re-classified and stored as Diverged. Neither errors, and the losing update is detected by RowVersion rather than by a uniqueness violation — proven in the LocalDB lane, since the InMemory provider enforces neither.
  16. A commit naming a hash the subscriber has neither uploaded nor can already reach is refused as missing — with the same response as a genuinely absent blob, so no existence oracle is offered.
  17. A pull whose manifest path traverses a symlink or junction writes nothing outside the workspace root; the resolved destination is verified before every write.
  18. A manifest containing Scene.txt and scene.txt — or names differing only by trailing dot or space — is rejected at commit with both paths named, rather than materialising as one file.
  19. A workspace holding more than int.MaxValue bytes is counted without truncation, and the ceiling still refuses at the limit. LocalDB lane, since InMemory would not catch a column-width truncation.
  20. Transferring ownership claims against the recipient before releasing the former owner, and refuses the transfer outright when the recipient lacks capacity — leaving both parties' claims unchanged.
  21. Two concurrent commits from the same head both persist with distinct sequences, and the loser is stored as Diverged — the sequence is consumed only by a successful CAS, so the unique index never fires. LocalDB lane.
  22. A manifest naming .AONIK/pull.journal, .aonik./x or any other equivalence-alias of the reserved prefix is refused server-side.
  23. A manifest containing both foo and foo/bar.txt is refused at commit, under the same normalisation, so no revision can exist that a filesystem cannot materialise.
  24. A blob claimed by the sweeper (State = Deleting) is reported as missing to a referencing commit rather than referenced, and a reference landing first causes the sweeper to abandon the deletion. No revision ever names bytes that were removed.
  25. Accepting a divergent revision advances the head via a new revision parented on the current head; no head ever points at a revision whose parent is not its predecessor.
  26. A rejected divergent revision releases its uniquely-held blobs and its byte claims after the retention window.
  27. A subscriber holding two workspaces that share a blob, transferring one, still holds a byte claim for the retained one.
  28. A path containing .., a drive letter, a leading slash or a reserved device name is rejected at commit.
  29. Two paths differing only in Unicode normalisation are treated as one and the commit is refused as malformed.
  30. Exceeding the byte ceiling refuses the upload before the stream is consumed, and an upload whose streamed size differs from its declared length is discarded with its claim released.
  31. A commit naming any path under .aonik/ — or any equivalence-alias of it — is refused server-side, regardless of what the client sent.
  32. A workspace shared by invite is listable, revocable and acceptable through Spec 086's existing routes with no workspace-specific code in those routes.
  33. dotnet build and dotnet test Aonik.sln green, plus the LocalDB lane.

15. Open decisions

#QuestionLeaning
O1 Should blobs dedupe across tenants? No. The storage saving is real but existence becomes probeable by timing, and one tenant's deletion affecting another's read is a support incident nobody can explain.
O2 How much history is retained? All of it until a retention policy exists. Revisions are cheap; blobs are not, so the first cost pressure will come from media, not from history depth.
O3 Does a workspace need a Group owner as well as a party? Not in v1. A studio shares a workspace through a grant; making it group-owned adds a second ownership representation, which is what ADR-015 O1 rejected for groups.
O4 Is the sync client part of the platform or the product? The product. The platform ships the protocol and the contracts; the client that walks a real filesystem belongs with the application that owns the folder.
O5 Should a divergent revision expire? Probably — an unaccepted proposal holding blobs alive indefinitely is a quota leak. Needs a number, so deferred rather than guessed.
