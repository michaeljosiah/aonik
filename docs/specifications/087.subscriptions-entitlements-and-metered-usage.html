Spec 087 Status: Draft (Rev 1) Size: Large Priority: P1 Domain: Subscriptions (new) / Ordering / SharedKernel

Subscriptions, entitlements and metered usage

A new Aonik.Subscriptions module: plans (what you sell), entitlements (what a plan confers, as named meters rather than a single credit balance), grants (allowance materialised per period, or bought outright), and metered usage with a reserve → commit lifecycle so an allowance can be enforced before work runs and settled at its true cost afterwards. It sits on the rails that already exist — an Order per billing period, an Invoice, funding via a PaymentIntent, and truth in the ledger — extended by Spec 088, which carries the six Finance changes recurring billing needs and this spec consumes. The platform can bill an invoice today but cannot sell a subscription; this closes that.

1. Summary

AONIK is a multi-product platform whose products are sold on subscription, but the platform has no notion of a plan, a subscription, an entitlement or a usage meter. Every product that wants to charge recurring money would have to invent them.

The design turns on one decision, stated up front because everything else follows from it:

Named meters, not a credit balance An entitlement is a named meter with an allowance — stories 6/month, animated-videos 2/month, child-profiles max 3, hd-styles on. A single general-purpose "credit balance" is one meter shape among several, not the model. Building the balance first and bolting quotas on afterwards is the mistake this spec exists to avoid, and it is not retrofittable — a balance has no per-unit reset policy, no ceiling semantics, and no way to sell "one more video" without selling fungible currency.

Four things in the tree sound like this spec and are not. Confusing any of them with an entitlement will produce a wrong design.

4. Scope (in / out)

4.1 In scope

  • A new Aonik.Subscriptions module: catalogue, subscription, grant, usage.
  • Three entitlement shapes (§5) covering counters, ceilings and flags.
  • Reserve → commit → release usage lifecycle with expiry sweeping.
  • Renewal producing an Order + Invoice + PaymentIntent on existing rails.
  • Two new order types: SubscriptionRenewal, EntitlementPurchase.
  • New ledger accounts and postings, contributed at provisioning.
  • SharedKernel.Abstractions.Subscriptions contracts, plus a new IJournalWriter to close the cross-module ledger gap.
  • A subscription dunning job — payment retry does not exist in the tree today (§12.5).
  • MeterOffer pricing and IEntitlementPurchaseService, so top-up prices resolve server-side (§12.4).
  • A resolver registering this module's ledger accounts and order-type mapping into Finance's settlement seam (§13.1).

4.2 Out of scope

  • Proration and mid-period plan changes. v1: a change takes effect at the next period boundary.
  • Trials. A £0 plan is a plan — the Arke Kids "Peek, free forever" tier needs no trial machinery. Time-boxed trials are a later, separate mechanism.
  • Coupons, discounts, tax calculation, multi-currency price books.
  • Post-paid / arrears usage billing (bill what was consumed). v1 is pre-paid allowance only.
  • Seat-based per-user pricing (a ceiling meter covers "up to N profiles" without per-seat billing).
  • Resellers, marketplaces, partner revenue share.
  • General-purpose dunning for all invoice types, and any use of the DunningPlan entity. This spec adds subscription payment retry only (§12.4); wiring DunningPlan into a platform-wide collections engine is separate work.
  • Any product-specific meter definition. Meters are data; Arke Kids' meters belong to its config pack.
Hard dependency on Spec 088 Six Finance capabilities this spec needs do not exist: cross-module journal posting, ledger identity, a reusable payment mandate, invoice order-link persistence, writer idempotency, and order-type-aware settlement routing. They were originally specified inline here, which made this document two specs wearing one name. They are now Spec 088. 088 P1–P5 must land before this spec's P5. Everything up to and including P4 here — catalogue, subscription lifecycle, the free tier, grants and metering — has no dependency on 088 and can proceed in parallel.

5. Three entitlement shapes

Every limit in a real pricing table is one of three things. Modelling all three now costs almost nothing; modelling one costs a rewrite.

KindSemanticsConsumed?Resets?Example
counterAn allowance drawn down by usageYesPer period, or never6 stories / month · 2 videos / month · 500 credits
ceilingA maximum concurrently held; checked, not consumedNon/aUp to 3 child profiles · 5 worlds
flagA capability that is on or offNon/aEvery art style in HD · faster helpers · early access
Why ceiling is not a counter Deleting a child profile must return the slot; deleting a story must not return the month's allowance. A single "consumed" model cannot express both, and conflating them is how a subscriber loses allowance by tidying up.

6. The catalogue

Plan ──< PlanVersion ──< PlanEntitlement code version, price, meterCode, kind, name effectiveFrom allowance, resetPolicy
EntityFieldsNotes
Plan new TenantId, Code, Name, Description, BillingInterval, Status, SortOrder BillingInterval and Status are open strings with known-values helpers, per the OrderType / BusinessType precedent.
PlanVersion new PlanId, Version, Price, Currency, EffectiveFrom, Status Grandfathering. A Subscription pins a PlanVersionId, so raising a price never silently re-prices existing subscribers. New signups take the current version. Published versions are immutable — see below.
PlanEntitlement new PlanVersionId, MeterCode, Allowance, ResetPolicy MeterCode is an open string owned by the product, validated against the tenant Meter table (§14). Kind and Unit are not duplicated here — they belong to the meter.

One authority per fact

Kind and unit live on the meter, not the entitlement. Duplicating them let a config row declare a counter meter as a flag entitlement, or attach incompatible units — leaving the reserve, ceiling and flag paths reading different authorities for the same meter, with validation that checked only that the code existed. The fields are removed from PlanEntitlement; anything needing the kind reads the meter.

A published PlanVersion is immutable. Pinning a version only grandfathers anything if the pinned row cannot then be edited. With P2's admin CRUD and no immutability rule, changing Price, Currency or an entitlement on a published version would re-price and reshape every subscriber pinned to it — precisely the guarantee it was meant to provide. Once published, price and entitlements can only change by creating a new version; only lifecycle metadata (Status, display ordering) stays mutable.

7. The subscription

EntityFields
Subscription new TenantId, SubscriberKind, SubscriberId, PlanVersionId, PendingPlanVersionId?, PendingEffectiveAt?, Status, CurrentPeriodStart, CurrentPeriodEnd, CancelAtPeriodEnd, PaymentMandateId?, StartedAt, EndedAt
SubscriptionPeriod new SubscriptionId, Sequence, StartsAt, EndsAt, OrderId?, InvoiceId?, PaymentIntentId?, Status, AttemptCount, NextAttemptAt?
Pending plan changes need somewhere to live §4.2 promises that a plan change takes effect at the next period boundary. With a single PlanVersionId there is nowhere to record that intent: overwriting it changes the current subscription immediately (the opposite of what was promised) and not writing it loses the request before renewal. PendingPlanVersionId + PendingEffectiveAt hold it; renewal applies and clears them.

SubscriptionPeriod is not bookkeeping for its own sake: it is the idempotency anchor for renewal. The renewal job keys on (SubscriptionId, Sequence), so a job that runs twice, or a process that dies between minting the order and taking payment, cannot double-bill.

Status values (open strings, known-values helper): trialing, active, past_due, cancelled, expired.

8. Grants: one entity, two behaviours

Plan allowance and purchased top-ups are the same shape with different expiry, so they are one entity with a Source discriminator rather than two tables that drift. 

EntitlementGrant
    SubscriberKind, SubscriberId    // the grant's OWNER — not the subscription
    SubscriptionId?, PeriodId?      // set for plan grants; null for purchases
    MeterCode
    Source          plan | purchase | adjustment
    Allowance       decimal
    Consumed        decimal
    Held            decimal         // reserved, not yet committed — see §9
    ExpiresAt       DateTime?       // derived from the entitlement's ResetPolicy
    Status          open | closed
    ClosedAt        DateTime?
    RowVersion      byte[]          // optimistic concurrency — see §15
    SourceOrderId?  Guid?           // purchases and adjustments trace to their order
SourceCreated byExpiresRefundable liability
planPeriod activationAt PeriodEnd — unless the entitlement's ResetPolicy is neverNo — the subscriber bought the plan, not the units
purchaseAn EntitlementPurchase orderNeverYes — deferred revenue until consumed
adjustmentAn operator, with a reasonOperator's choiceNo
Expiry follows the reset policy, not the source PlanEntitlement.ResetPolicy supports never — a plan allowance that accumulates rather than refreshing. Deriving ExpiresAt from Source = plan alone would silently discard exactly that allowance at every renewal. ExpiresAt is set from the originating entitlement's ResetPolicy: period → PeriodEnd, never → null.
Grants belong to the subscriber, not the subscription A purchased grant never expires, so it must outlive the subscription it was bought under. Keyed by SubscriptionId, a cancel-and-resubscribe would strand paid, non-expiring units on the old subscription — invisible to draw-down while their deferred-revenue liability stays on the ledger, which is both a broken promise and a misstated balance sheet. Grants are keyed by (SubscriberKind, SubscriberId); SubscriptionId/PeriodId are provenance on plan grants, not the ownership key. Draw-down queries by subscriber.

Status exists so GrantExpirySweepJob has a transition it can actually persist: expired grants move open → closed with a ClosedAt. Without it the job has nothing to write and expiry is query-derived only, which makes "how much did we break?" unanswerable.

The question this answers on day one "Do my unused plan credits roll over?" — No: plan grants expire at period end. "Do the ones I bought expire?" — No. That asymmetry is deliberate, commercially standard, and must be visible in the model rather than living in a service's if.

9. Metered usage

Work that consumes an allowance is authorised before it runs and settled at its true cost afterwards — the same authorise/capture shape the payments module already uses, for the same reason.

reserve(meter, qty) ──▶ UsageReservation [held] allowance check + hold │ │ work runs ├── commit(actualQty) ──▶ UsageRecord + grant draw-down │ ├── release() ──▶ hold returned, nothing charged └── crash / timeout └── sweep at ExpiresAt ──▶ hold returned automatically
EntityFields
UsageReservation new SubscriberKind, SubscriberId, SubscriptionId?, MeterCode, Quantity, Status (held | committed | released | expired), ExpiresAt, IdempotencyKey, RowVersion
UsageReservationAllocation new ReservationId, GrantId, Quantity — one row per grant the hold draws on
UsageRecord new SubscriberKind, SubscriberId, SubscriptionId?, MeterCode, Quantity, AllocationsJson, OccurredAt, SourceType, SourceId, ProviderCost?, ProviderCostCurrency?
A reservation must hold against specific grants A reservation carrying only a total quantity cannot work either way round. If ReserveAsync leaves grants untouched, nothing changes their RowVersion and two concurrent reservations both succeed against the last unit — the optimistic concurrency in §15 never engages. If it instead writes Consumed directly, then a release, an expiry, or a commit at a lower actual quantity has no record of which grants to restore, and the returned units land on the wrong ones.

So the hold is explicit and per-grant:

CallEffect on the grantEffect on allocations
ReserveAsyncHeld += qty (bumps RowVersion, so the race is caught)One UsageReservationAllocation per grant drawn on
CommitAsync(actual)Held -= held, Consumed += actualAllocations trimmed from the end of the draw-down order when actual < held; copied to the UsageRecord
ReleaseAsync / sweepHeld -= heldAllocations resolved, hold returned to the exact grants it came from

Available allowance on a grant is therefore Allowance − Consumed − Held, and a commit above the reserved quantity re-checks availability rather than assuming the hold covers it.

Trim from the end, never pro rata Pro-rata trimming silently violates §10. Reserve 4 plan units and 4 purchased units, then commit 4: pro rata consumes 2 of each, burning paid, non-expiring units while handing back perishable ones that then expire worthless. Allocations are ordered by the same draw-down rule at reserve time, and a short commit releases from the tail — so the consumed prefix always preserves plan-first, purchase-last.

AllocationsJson records which grants the usage drew from and how much from each. Without it, a refund or a dispute cannot be unwound, and breakage cannot be computed. SourceType/SourceId point at the thing that caused the usage — for AI work, the AiRun id, which keeps ADR-012's audit record as the join.

ProviderCost is what the run actually cost us. It is the other half of the margin figure and the reason usage lands in the ledger rather than a counter table (§13).

9.1 Ceilings need a claim; flags are a read

A point-in-time count cannot enforce a ceiling Two requests creating a profile at one slot below the limit both read the current count, both see room, and both create — neither is visible to the other until it commits. A check that takes no lock and writes no row is a check-then-act race, and it will over-admit under exactly the conditions a ceiling exists for.

Ceilings get a counted row with the same optimistic-concurrency treatment as grants:

CeilingHolding                       // the aggregate counter
    SubscriberKind, SubscriberId, MeterCode
    Held        int
    RowVersion  byte[]

CeilingClaim                         // one row per held object — the idempotency key
    CeilingHoldingId, HolderRef      // unique (CeilingHoldingId, HolderRef)
    ClaimedAt

ClaimSlotAsync(meter, holderRef)     // insert claim + compare-and-increment; throws if full
ReleaseSlotAsync(meter, holderRef)   // delete claim + decrement, only if the claim existed
The counter alone cannot be idempotent An aggregate with no holder identity double-counts under retry: a retried create increments Held twice and permanently loses a slot; a retried delete decrements twice and admits more objects than the ceiling. Sharing a transaction with the object's creation makes each individual call atomic — it does not tell the next call that this holder already claimed. The per-holder CeilingClaim row, unique on (CeilingHoldingId, HolderRef), is what makes both operations idempotent.

The claim and the object's creation share one transaction, so a failed create returns the slot and a claimed slot always corresponds to a real object. ReleaseSlotAsync is what makes deleting a child profile return its slot — the behaviour §5 distinguishes from a counter.

flag remains a pure read (HasFlagAsync) — nothing to reserve, nothing to race. Only counter uses the reserve/commit lifecycle.

10. Draw-down order

A commit draws from grants in this order, and the order is load-bearing:

  1. plan and adjustment grants with an expiry, soonest expiry first
  2. grants with no expiry — purchase last
  3. ties broken by CreatedAt, oldest first

The perishable allowance is spent before the permanent one. Reversing this quietly destroys value the subscriber paid cash for, and is the single most common way a credit system loses a customer's trust.

A commit exceeding available allowance across all grants fails; it never goes negative. Overage is an explicit purchase, not an implicit debt.

11. Who holds a subscription

SubscriberKind + SubscriberId — the same polymorphic idiom as Spec 086's ResourceKind, and for the same reason: the module must not know its consumers' entity types.

SubscriberKindPoints atCase
groupA Group (Spec 086)A family on a consumer product — one tenant, many subscribers
partyA PartyAn individual subscriber
tenantThe tenant itselfA B2B tenant on a platform plan
Storing the id opaquely is not the same as trusting it This module deliberately never dereferences SubscriberId — but tenant scoping alone does not authorise a caller to act for a particular family. In the one-tenant-many-families model that is the whole security boundary: any endpoint passing a caller-controlled SubscriberId could otherwise subscribe, cancel, inspect or consume another family's entitlements inside the same tenant.

So a kind-specific contributor validates both existence and authority, and every subscription and usage service call goes through it: 

public interface ISubscriberAuthorizer
{
    /// <summary>The subscriber kinds this authorizer owns — "group", "party", "tenant".</summary>
    IReadOnlyCollection<string> SubscriberKinds { get; }

    /// <summary>Does the subscriber exist in this tenant, and may the current caller act for it?</summary>
    Task<bool> CanActForAsync(string subscriberKind, Guid subscriberId, CancellationToken cancellationToken = default);
}

Platform supplies the group authorizer (caller's party is a member with a sufficient role) and the party one (caller is that party); tenant requires an administrative permission. An unregistered kind fails closed, matching how resource kinds behave in Spec 086.

Dependency Only the group kind depends on Spec 086, and only as data — this module stores a Guid and never dereferences it. Spec 087 can be built and tested before Spec 086 lands, using party or tenant subscribers.

12. Orders, invoices, payments

No new money machinery. Two new order types on the existing spine, per ADR-011's additive rule:

Order typeMeaningLines
SubscriptionRenewal newOne billing period of a subscriptionOne line: the plan version at its pinned price
EntitlementPurchase newUnits of a named meter bought outrightOne line per meter: Quantity × UnitPrice
Naming EntitlementPurchase, not CreditPurchase. It buys units of whichever meter — "one more animated video" and "500 credits" are the same transaction against different meters. A type named for one product's currency would need a second type the moment a second product priced differently.

A physical add-on (a printed book) is not this — it stays a ProductPurchase with Commerce fulfilment. Only entitlement units come through here.

12.1 Renewal flow

  1. Renewal job selects subscriptions with CurrentPeriodEnd <= now and Status = active and CancelAtPeriodEnd = false. A subscription with the flag set is closed (Status = cancelled, EndedAt = CurrentPeriodEnd), not renewed.
  2. Read the pending plan version if one is due — but do not apply it yet (see below).
  3. Create SubscriptionPeriod for Sequence + 1 (the idempotency anchor).
  4. IOrderService.CreateAsync with IdempotencyKey = "sub:{subscriptionId}:period:{sequence}".
  5. If the period total is zero, go to step 8. Otherwise IInvoiceWriter.CreateForOrderAsync — skipped if Period.InvoiceId is already set.
  6. Resolve the subscription's PaymentMandateId → recurring PaymentIntent; IOrderService.LinkFundingAsync. Skipped if Period.PaymentIntentId is already set. Each id is persisted on the period immediately after its writer returns.
  7. On capture: post the ledger.
  8. Only now: apply and clear the pending plan version, materialise this period's plan grants, advance CurrentPeriodStart/End, set period Status = settled, and transition the order to its completed status (§12.8).
  9. On payment failure: Status = past_due, AttemptCount++, NextAttemptAt set from the retry schedule. Grants are not materialised — an unpaid period confers no allowance.
Cancelling must actually stop the charging CancelAtPeriodEnd is the whole point of a graceful cancel. Selecting on Status = active alone leaves a cancelled subscription matching the renewal query forever, so the subscriber is billed again after explicitly cancelling. The flag is checked first, before a period is created.

12.2 Zero-price periods bypass payment entirely

The free tier cannot go through capture LedgerPostingService rejects non-positive amounts outright ("Cannot post a non-positive amount"), so a £0 plan routed through invoice → intent → capture can never settle and never receives its allowance — breaking criterion 2 and phase P3, whose entire point is that a £0 plan works end to end.

A period whose total is zero creates its order (the record of what was granted and when), then settles directly: no invoice, no PaymentIntent, no ledger posting, straight to grant materialisation. Nothing was earned and nothing moved, so there is nothing to post — the order alone carries the audit trail.

12.3 Recurring payment needs a stored mandate

IPaymentInitiator exposes only CreateGuestIntentForOrderAsync — a guest intent on the public payment path, requiring a Provider and PaymentMethodType per call. A renewal job running unattended has neither, and no PaymentMandate exists in the tree.

Specified in Spec 088 The mandate model, its lifecycle (creation, revocation, expiry, audit) and IRecurringPaymentInitiator are Finance concerns and are specified in Spec 088 §6. This spec only consumes them: Subscription.PaymentMandateId references one, and a subscription whose mandate is missing, revoked or expired moves to past_due with a distinct, non-retryable reason and is surfaced for re-authorisation — retrying cannot fix a withdrawn authorisation.

12.4 Entitlement purchases need a priced catalogue

Nothing said what a unit costs The catalogue priced plans and nothing else, and no contract resolved a top-up price. That left EntitlementPurchase with two bad options: trust a caller-supplied UnitPrice — letting anyone buy units at any price they like — or be unreachable. Neither is acceptable for a money path. 
MeterOffer                           // what a unit of a meter costs
    TenantId, MeterCode
    UnitPrice, Currency
    MinQuantity, MaxQuantity?
    Version, EffectiveFrom, Status   // versioned and immutable, like PlanVersion

IEntitlementPurchaseService.CreateAsync(subscriberRef, meterCode, quantity) resolves the current MeterOffer server-side, builds the order lines from it, and never accepts a client-supplied price. The offer version is recorded on the order line, so a later price change cannot restate a completed purchase.

12.5 Dunning: a retry path, because none exists today

Correcting an earlier claim An earlier draft said "the existing DunningPlan takes over". It does not. A repo-wide search finds DunningPlan only as an entity and its DbSet registrations — there is no service and no job. Handing off to it would strand every failed subscription permanently in past_due, invisible to the renewal selector.

SubscriptionDunningJob retries periods in past_due whose NextAttemptAt has passed, re-using the same period, order and invoice, and creating a fresh payment intent per attempt (see below). After a bounded number of attempts the subscription moves to expired with its grants left to lapse naturally (O1). Attempt count and schedule live on the period, so the state is inspectable rather than inferred.

A failed intent cannot be retried — it must be replaced PaymentService enforces its state machine explicitly: capture requires Authorized (if (currentStatus != PaymentStatus.Authorized)) and authorisation requires Pending. Failed is terminal. So "reuse the existing intent" would strand every hard decline exactly where the job is supposed to help. Each dunning attempt mints a new intent from the mandate, recorded against the same period, and SubscriptionPeriod.PaymentIntentId points at the current attempt while prior attempts remain as history. This is also why intent uniqueness is keyed on the idempotency key rather than on the order (§12.5) — multiple attempts per order are legitimate and expected.

12.6 Idempotency of the side effects, not just the anchor

The period anchor alone is not enough If the job dies after creating an invoice but before persisting its id, a retry reuses the order (which is idempotency-keyed) but calls the invoice and payment writers again — producing a duplicate invoice and a second collectible intent.

This spec owns the renewal-side half:

  • Persist InvoiceId / PaymentIntentId on the period immediately after each writer returns, and check them before calling again.
  • Pass a deterministic idempotency key derived from (SubscriptionId, Sequence, attempt).
Specified in Spec 088 The writer-side half — idempotency keys on IInvoiceWriter and the recurring initiator, the filtered unique invoice index, and the deliberate absence of order-scoped uniqueness on payment intents — is Spec 088 §8. Both halves are needed: the period check avoids the common retry, the database constraint catches the race.
An unpaid upgrade must confer nothing Applying the pending version before payment leaves a failed renewal pointing at the new plan. Counter grants are withheld, but HasFlagAsync is a pure read and ceilings consult plan allowance — so an unpaid upgrade would immediately hand over new feature flags and a higher object limit. The old version is also gone, so nothing can recover the last paid entitlement set. The pending version is therefore applied only on settlement, and every entitlement read resolves through the last settled state.

12.8 A settled period must complete its order

Orders would be left in Draft CoreOrderService creates orders with Status = OrderStatuses.Draft (CoreOrderService.cs:77). The renewal flow advanced the subscription and materialised grants without ever transitioning the order — and the zero-total path has no payment event that might do it implicitly. Both free and paid settled periods would leave the canonical record of the requested transaction sitting in Draft or PendingFunding after it had actually been fulfilled, which is precisely what rule 2 exists to prevent.

Settlement therefore calls IOrderService.TransitionAsync to the completed status and LinkFulfilmentAsync for the period, inside the same idempotent settlement workflow — using expectedFromStatus so a concurrent transition fails rather than double-applying. A re-run observes the order already completed and makes no change.

12.9 The invoice must remember its order

Specified in Spec 088 InvoiceWriter uses command.OrderId only to build the invoice number, so Invoice.OrderId persists as null — which would leave settlement routing with no order to read a type from. Persisting the link is Spec 088 §7 and is a hard prerequisite of §13.

The tenant chart of accounts is seeded by FinanceTenantProvisioningContributor (1000 Cash, 1100 AR, 2000 AP, 2100 Payments Clearing, 3000 Retained Earnings, 4000 Operating Revenue, 5000 Operating Expenses). 13.1 Routing comes from Finance; the mapping is ours

Seam in Spec 088 PostInvoiceSettlementAsync credits a hard-coded 4000 as a single line, so these accounts could not receive anything. The seam that fixes it — ISettlementRevenueResolver plus per-line splitting — is Spec 088 §9.

What belongs here is the mapping: this module registers a resolver claiming SubscriptionRenewal → 4100 and EntitlementPurchase → 2210 (a liability, not revenue, until consumed), and supplies the meterCode dimension per line. Order types we do not claim are untouched and still credit 4000.

13.3 Every line carries its meter

Without a dimension, margin is tenant-wide All meters post into the same 4110 and 5100. Subtracting two account balances therefore yields aggregate margin, not margin per meter — and criterion 11 asks for the latter from the ledger alone.

JournalEntryLine already carries DimensionsJson; the mistake was omitting it from the write contract. JournalLineSpec carries it too (§14.2), and every entitlement posting sets {"meterCode": "..."}. Margin per meter = 4110 − 5100 filtered on that dimension, from the ledger, with no join back to usage data.

Settlement must split by line, not post the invoice total PostInvoiceSettlementAsync currently posts invoice.Total as a single line. An EntitlementPurchase order can carry several meter lines — extra videos and extra stories in one checkout — and a single 2210 credit cannot carry a truthful meterCode. It would leave the deferred liability unreconcilable per meter and quietly falsify the dimension. So the routing change in §13.1 also splits the settlement credit per invoice line, attaching each line's meter. Single-line invoices are unaffected.
Revenue recognition Default policy: plan fees recognised at period start (monthly granularity makes intra-period amortisation immaterial); purchased units deferred until consumed. Plan grants carry no liability — the subscriber bought access, not units, so unused plan allowance is not owed back. This is a defensible default, not accounting advice: an operator whose auditor wants daily amortisation should treat this as configuration. Recorded as O2.

IEntitlementPurchaseServiceBuilds an EntitlementPurchase order from server-resolved MeterOffer pricing (§12.4).
IMeterDefinitionProviderModule-contributed IEnumerable<T> supplying a module's default meters at provisioning. A seeding contributor — not the validator.
MeterKinds, SubscriberKinds, SubscriptionStatuses, ResetPoliciesKnown-values helpers over open strings.
The tenant Meter table is the authority Making code-registered providers authoritative would contradict this spec's own premise: a meter delivered by a config pack has no owning module registration, so it would fail validation — and criterion 1 requires a pricing table to be expressible as data, with no code change. MeterCode validates against tenant-scoped Meter rows. Those rows arrive from two directions — a config pack (ADR-014) or a module's IMeterDefinitionProvider defaults at provisioning — and both write the same table. An unknown code still fails closed; it just fails against data rather than against compiled registrations.

14.2 Ledger writing

Specified in Spec 088 ILedgerService lives in Aonik.Finance.Contracts and no other module can post. IJournalWriter — with its required LedgerId, its DimensionsJson line field, and ILedgerResolver for callers that do not track ledgers — is Spec 088 §5.

This module consumes it: usage postings carry {"meterCode": "..."} as their dimension, and the ledger is resolved once per tenant through ILedgerResolver. Margin per meter is then 4110 − 5100 filtered on that dimension, from the ledger alone.

15. Concurrency & correctness

The race that matters Two dispatches commit against the last unit of allowance simultaneously. Without protection both succeed and the subscriber consumes more than they hold. EntitlementGrant.Consumed and UsageReservation.Status carry RowVersion optimistic concurrency, and the reserve/commit path runs in a transaction with a bounded retry on concurrency conflict.

Per CLAUDE.md, this is exactly the class of change the InMemory provider is structurally unable to fail on — it is non-relational, so RowVersion, BeginTransaction and execution strategies are all no-ops there. Coverage in tests/Aonik.Database.Tests (LocalDB) is mandatory, not optional. That lane is where the Spec 066 P1 defect would have been caught.

Required LocalDB tests:

  • Concurrent reservations against a grant with one unit remaining: exactly one succeeds. (This is the case a total-only reservation would have missed entirely — the grant's Held is what makes RowVersion engage.)
  • Concurrent commits against a grant with one unit remaining: exactly one succeeds.
  • A reservation cannot be committed twice (tenant-scoped idempotency key + status guard).
  • Reserve spanning two grants writes one allocation row per grant; release returns the hold to those grants and no others.
  • Commit at a lower actual quantity than reserved trims allocations pro-rata and returns the remainder.
  • An expired reservation cannot be committed.
  • Renewal is idempotent on (SubscriptionId, Sequence) under concurrent job execution.
  • Filtered unique indexes (§17.1): duplicate period-grant materialisation fails; a second active subscription for one subscriber fails; two cancelled subscriptions for the same subscriber are permitted.
  • Concurrent ClaimSlotAsync at one slot below a ceiling: exactly one succeeds.

Why the catalogue needs these Concurrent admin writes, a re-run provisioning contributor and an overlapping config pack can each produce a duplicate Plan or Meter row for the same code, or a second entitlement for one (PlanVersionId, MeterCode). The first two make validation ambiguous; the third doubles a subscriber's allowance at every renewal. Catalogue rows are written rarely and read on every money path, so uniqueness belongs in storage.
Two invariants that must be in the database

Grant materialisation. Payment completion is at-least-once. A status check alone lets a retried or concurrently-handled event materialise the same period's grants twice — the subscriber silently gets double allowance. The unique key on (PeriodId, MeterCode, Source) makes the second attempt fail rather than duplicate.

One active subscription. O4 says the service enforces one active per subscriber. Two concurrent Subscribe calls both pass that check and both insert, and the subscriber is then renewed — and charged — twice. The filtered unique index is what actually holds.

Idempotency keys are tenant-scoped A globally unique IdempotencyKey lets one tenant's client-generated key collide with another's, and the second tenant's insert fails against a row its query filters cannot even see. (TenantId, IdempotencyKey) matches how the rest of the repository scopes idempotency.
Note for the implementer ADR-011 is mid-migration: Order physically lives in src/Aonik.Ordering/Entities/Orders/ but still declares namespace Aonik.Finance.Entities.Orders. Expect that mismatch; do not "fix" it as a side effect of this spec.

19. Acceptance criteria

  1. A plan can express all three entitlement kinds, and the Arke Kids pricing table (£0 / £9.99 / £19.99 / £39.99, stories, videos, profiles, HD) is expressible as data, with no code change.
  2. A subscriber on a £0 plan can consume their allowance and be refused at zero.
  3. Commit draws from soonest-expiring grants first and purchased grants last, proven by a test with mixed grants.
  4. Concurrent commits against one remaining unit: exactly one succeeds, on LocalDB.
  5. A crashed dispatch's reservation is swept and the hold returned.
  6. Deleting a ceiling-metered object returns the slot; deleting a counter-metered one does not return allowance.
  7. Renewal run twice produces one order, one invoice, one payment intent and one set of grants — including when the first run is killed between creating the invoice and persisting its id.
  8. A failed renewal payment leaves past_due with no grants materialised, and is retried by SubscriptionDunningJob rather than stranded.
  9. A subscription with CancelAtPeriodEnd is not billed again; it closes at the period boundary.
  10. A £0 period settles and materialises grants without creating an invoice, a payment intent or a journal entry.
  11. A purchased grant remains usable after the subscriber cancels and resubscribes.
  12. A plan entitlement with ResetPolicy = never accumulates across renewals rather than being discarded.
  13. A pending plan change applies at the next boundary and not before.
  14. A short commit spanning plan and purchased grants consumes the plan units and returns the purchased ones — never a pro-rata split.
  15. A retried ceiling claim for the same holder does not consume a second slot; a retried release does not free one twice.
  16. A hard-declined renewal is retried with a new intent and eventually settles.
  17. A published PlanVersion cannot have its price or entitlements edited; the attempt is rejected.
  18. An entitlement purchase with a client-supplied unit price is rejected; pricing comes from the server-resolved MeterOffer.
  19. A multi-meter entitlement purchase produces one dimensioned 2210 credit per line (relies on Spec 088 §9.2).
  20. A caller cannot subscribe, cancel, read or consume for a subscriber they are not authorised to act for, within the same tenant.
  21. A failed renewal on a pending upgrade confers no new flags and no higher ceiling.
  22. Both free and paid settled periods leave their order in a completed status, never Draft.
  23. Duplicate catalogue rows (same plan code, meter code, or (PlanVersionId, MeterCode)) are rejected by the database.
  24. Raising a plan's price does not re-price existing subscribers.
  25. An unregistered MeterCode is rejected at write time.
  26. Margin for a meter over a period is derivable from ledger accounts 4110 and 5100 alone.
  27. No module gains a project reference to Aonik.Subscriptions or Aonik.Finance; all access is via SharedKernel abstractions.
  28. dotnet build Aonik.sln, dotnet test Aonik.sln, and the LocalDB lane green.

20. Open decisions

#QuestionLeaning
O1 Does an unpaid (past_due) subscription keep the previous period's unused grants? Yes until they expire naturally. Clawing back allowance already granted is hostile and hard to explain; the dunning grace period is the right lever.
O2 Revenue recognition: period-start vs daily amortisation for plan fees. Period-start in v1. Make it a setting rather than a constant so an operator's accountant can change it without a code change.
O3 Should ProviderCost live on UsageRecord or only in the ledger? Both. The ledger is truth; the denormalised column makes per-meter margin queryable without a journal scan.
O4 Can one subscriber hold two active subscriptions? Settled: no. Enforced by a filtered unique index (§17.1), not only by a service check — a service-level check loses the concurrent-Subscribe race and double-charges. Relaxing later is additive; tightening later is not.
O5 Where do meters get defined — Meter rows, or code constants? Settled: tenant-scoped Meter rows are the validator. They are written both by config packs (ADR-014) and by module IMeterDefinitionProvider defaults at provisioning; neither is privileged. Meters are product identity, and per ADR-013 that is configuration.
O6 Refunding an EntitlementPurchase whose units are partly consumed. Out of scope for v1, but AllocationsJson is designed so it is possible later. Do not drop it as an optimisation.
O7 What is a consumed purchased unit worth, for the 2210 → 4110 recognition leg? Settled in P6. The grant now records UnitValue from the offer at materialisation, so recognition uses the price the customer was actually charged. The P5 note below explains why nothing was guessed in the meantime.

Original P5 position: Recognition needs a per-unit value, and the only priced source is MeterOffer, which arrives in P6. Until then the poster falls back to the recorded provider cost per unit and posts nothing when there is no basis at all — recognising a made-up amount would be worse than recognising late, because the correction is a compensating entry against real customer revenue. P6 should replace this with the offer price recorded on the purchase order line, so the value recognised is the value actually charged.
O8 How does a settlement resolver know which meter an invoice line is for? Settled in P5: from the line's own MetadataJson, surfaced on SettlementLineContext (an addition to Spec 088 §9 this phase revealed was necessary). An invoice line carries no link back to the order line that produced it, so matching on description or position would be guesswork; the consumer tags its own lines when it raises the invoice. Unreadable metadata yields an undimensioned line, never a failed settlement.
