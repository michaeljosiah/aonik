# 024.unified-speech-config-and-composer

## Objective

Replace the two parallel singleton speech-config systems (legacy chat-speech in
`/settings/text-to-speech` and the v1 voice settings in `/settings/voice`) with a small
authoring platform for speech pipelines:

1. **Provider library** — a per-tenant catalog of configured speech providers. Each entry has
   a type (STT, TTS, or Composite), a vendor, an admin-given display name, and vendor-specific
   configuration. Many entries can coexist for the same vendor (e.g. "OpenAI TTS — alloy" and
   "OpenAI TTS HD — onyx") because they differ on configuration, not vendor.
2. **Recipe library** — a per-tenant catalog of named voice recipes built on top of the
   provider library. A chained recipe references one STT provider id and one TTS provider id
   plus pipeline tweaks (VAD, transcription filter, sentence aggregator). A composite recipe
   references one composite provider id. Default recipes ship as built-ins; admins clone and
   edit them under their own names.
3. **Active settings** — a per-tenant pointer to the currently active voice recipe (drives
   the voice WS endpoint) and the currently active TTS provider (drives chat-speech and
   helper-text TTS).
4. **Visual recipe authoring** — a stack-of-cards editor that renders the chain top-to-bottom
   with one card per pipeline step. Each STT/TTS step card has a dropdown picker that resolves
   into the provider library. ReactFlow-style canvas authoring is deferred to v1.2 when
   non-linear topology arrives.

This spec extends [022.aonik-voice-realtime](022.aonik-voice-realtime.md). It does not replace
022 — Phase 5 of 022 ("Admin Provider Settings & Voice Mode Page") explicitly defers this
work to v1.1.

## Non-Negotiable Rules

- The provider library is the single source of truth for speech provider configuration.
  Recipes carry `Guid` references into it, never inline configuration. Active-settings carry
  `Guid` references to the active recipe and active TTS provider.
- Provider credentials remain stored separately from the provider library entry itself. The
  library entry says *which* vendor and how it is tuned (model, voice, region, vendor opts);
  `IVoiceProviderCredentialResolver` says *what credential* to use for the vendor. Credentials
  are vendor-keyed; in v1.1 all library entries of the same vendor share one credential per
  tenant. Per-account credential separation is deferred to v1.2.
- Built-in recipes and built-in provider archetypes ship in code, not in the database. A
  tenant can clone a built-in into a tenant-owned, editable copy. Built-ins are immutable and
  versionless — they ship with the binary.
- Tenant-owned providers and recipes are versioned. Every Update writes a new version row;
  the previous version is retained as audit. Soft delete sets status; physical delete is a
  separate operator-only operation.
- Deleting or disabling a provider is blocked with a clear error if any active recipe
  references it. Deleting a recipe is blocked if it is the active voice recipe.
- The legacy chat-speech `TextToSpeechSettings` system is removed once consumers have moved
  to `IActiveTtsProviderResolver` (the new shim that reads from active-settings + library). It
  does not coexist long-term.
- Composite providers use Voxa's existing `OpenAIRealtimeProcessor` and
  `AzureVoiceLiveProcessor`. AONIK does not ship a parallel realtime client; it bridges the
  resolved `AIAgent` into the realtime provider's prompt + tool schema + history through a
  new `IRealtimeAgentExporter`. Mutating backend tools remain approval-gated by
  [023.server-side-ai-tool-approval](023.server-side-ai-tool-approval.md) on both chained and
  composite paths.
- The voice WebSocket protocol (envelopes defined by spec 022) is unchanged. The chained
  vs composite choice and the recipe identity are server-side pipeline details invisible to
  the client.

## Current Gap

Two parallel speech-config systems were added incrementally:

| | Legacy chat-speech | v1 voice settings |
|---|---|---|
| Page | `/settings/text-to-speech` | `/settings/voice` |
| Settings | `TextToSpeechSettings` (provider, voice, model, vendor opts, policy) | `VoiceProviderConfiguration.Chained.Tts` + `.Stt` |
| Service | `ITenantTextToSpeechSettingsService` | `ITenantVoiceProviderSettingsService` |
| Credentials | `ITextToSpeechCredentialResolver` | `IVoiceProviderCredentialResolver` |
| Used by | `VoiceSynthCoordinator` (AGUI), legacy preview | Voice WS, admin "Test STT/TTS" + "Live pipeline" |

Both are singletons — one TTS choice per tenant, one STT choice per tenant, one set of
recipe-defining options. A tenant cannot keep two TTS configurations side by side ("alloy
for general use; onyx for serious announcements"), cannot save a named recipe and switch
back to a previous one, and cannot reuse the same provider in two recipes with different VAD
settings. Composite providers (Azure Voice Live, OpenAI Realtime) are deferred entirely.

The v1 voice page also conflates provider selection with pipeline tweaks. Picking
`cost-chained-openai` writes both "use OpenAI" and "use these VAD settings" into the same
record; there is no way to pick a different provider while keeping the recipe's pipeline
tweaks, or vice versa.

## Domain Model

### Provider library

A speech provider is a configured, named, and tested vendor instance. Many can coexist per
tenant.

```csharp
public sealed record SpeechProvider(
    Guid Id,
    string DisplayName,                // admin-given, e.g. "Production OpenAI", "Brand voice clone"
    SpeechProviderType Type,           // Stt | Tts | Composite
    string Vendor,                     // "openai" | "azure" | "elevenlabs" | "mistral" | "openai-realtime" | "azure-voice-live"
    SpeechProviderConfig Config,       // strongly typed per (Type, Vendor); JSON-polymorphic
    SpeechProviderStatus Status,       // Active | Disabled | SoftDeleted
    int Version,                       // increments on every edit; previous versions in audit table
    DateTimeOffset CreatedAt,
    DateTimeOffset UpdatedAt,
    Guid? CreatedByUserId,
    Guid? LastUpdatedByUserId);

public enum SpeechProviderType { Stt, Tts, Composite }
public enum SpeechProviderStatus { Active, Disabled, SoftDeleted }

[JsonPolymorphic(TypeDiscriminatorPropertyName = "kind")]
[JsonDerivedType(typeof(OpenAIWhisperConfig), "openai-whisper")]
[JsonDerivedType(typeof(AzureSttConfig), "azure-stt")]
[JsonDerivedType(typeof(OpenAITtsConfig), "openai-tts")]
[JsonDerivedType(typeof(AzureTtsConfig), "azure-tts")]
[JsonDerivedType(typeof(ElevenLabsTtsConfig), "elevenlabs-tts")]
[JsonDerivedType(typeof(MistralTtsConfig), "mistral-tts")]
[JsonDerivedType(typeof(OpenAIRealtimeConfig), "openai-realtime")]
[JsonDerivedType(typeof(AzureVoiceLiveConfig), "azure-voice-live")]
public abstract record SpeechProviderConfig;

public sealed record OpenAIWhisperConfig(string? Model, string? Language) : SpeechProviderConfig;
public sealed record AzureSttConfig(string Region, string? Language) : SpeechProviderConfig;

public sealed record OpenAITtsConfig(string VoiceId, string? ModelId) : SpeechProviderConfig;
public sealed record AzureTtsConfig(string Region, string VoiceId) : SpeechProviderConfig;
public sealed record ElevenLabsTtsConfig(
    string VoiceId,
    string? ModelId,
    double? Stability,
    double? SimilarityBoost,
    int? OptimizeStreamingLatency) : SpeechProviderConfig;
public sealed record MistralTtsConfig(string VoiceId, string? ModelId) : SpeechProviderConfig;

public sealed record OpenAIRealtimeConfig(
    string Voice,
    string? Model,
    string? InstructionsAddendum) : SpeechProviderConfig;
public sealed record AzureVoiceLiveConfig(
    string Region,
    string Endpoint,
    string Voice,
    string? Model,
    string? InstructionsAddendum) : SpeechProviderConfig;
```

Each `SpeechProviderConfig` derived type maps 1:1 to a Voxa engine (or composite processor)
constructor. The UI knows what fields to render per `kind` discriminator.

### Recipe library

A recipe is a named, savable composition of providers + pipeline tweaks.

```csharp
public sealed record VoiceRecipe(
    Guid Id,
    string DisplayName,                // "Cost efficient", "Premium voice", "Realtime UK"
    string? Description,
    VoiceRecipeKind Kind,              // Chained | Composite
    ChainedRecipeBody? Chained,        // null when Kind=Composite
    CompositeRecipeBody? Composite,    // null when Kind=Chained
    bool IsBuiltIn,                    // built-ins ship in code; tenants clone into editable copies
    VoiceRecipeStatus Status,          // Active | Disabled | SoftDeleted
    int Version,
    DateTimeOffset CreatedAt,
    DateTimeOffset UpdatedAt,
    Guid? CreatedByUserId,
    Guid? LastUpdatedByUserId);

public enum VoiceRecipeKind { Chained, Composite }
public enum VoiceRecipeStatus { Active, Disabled, SoftDeleted }

public sealed record ChainedRecipeBody(
    Guid SttProviderId,                // ref into SpeechProvider library; Type must be Stt
    Guid TtsProviderId,                // ref into SpeechProvider library; Type must be Tts
    string? PinnedAgentId,             // null = use the client's hello.agentId; non-null = override
    string Vad,                        // "energy" | "silero" | "none"
    int? VadStopMs,
    bool TranscriptionFilter,
    bool SentenceAggregator);

public sealed record CompositeRecipeBody(
    Guid CompositeProviderId,          // ref into SpeechProvider library; Type must be Composite
    string? PinnedAgentId);            // null = use the client's hello.agentId; non-null = override
```

### Active settings

Per-tenant pointers to the currently chosen recipe and TTS provider.

```csharp
public sealed record VoiceModeSettings(
    bool Enabled,
    Guid? ActiveRecipeId);             // ref into VoiceRecipe library; null disables voice mode

public sealed record ChatSpeechSettings(
    bool Enabled,
    Guid? ActiveTtsProviderId);        // ref into SpeechProvider library; null disables chat speech
```

ChatSpeechSettings does not need a recipe — chat-speech is a single TTS step, not a chain.

### Versioning + audit

Aligned with AONIK's existing conventions: every `SpeechProvider` and `VoiceRecipe` derives
from `AuditableEntity` (soft delete, `CreatedAt/By`, `UpdatedAt/By`, `RowVersion`) + implements
`ITenantScoped`. Older versions of the live row are stored as JSON snapshots in a
`PreviousVersionsJson` column on the same row — same pattern as `AiRun.InputRefsJson`. No
separate history tables; one query returns the entity and its full edit history.

```csharp
// Internal entity (lives in Aonik.Voice/Entities)
public class SpeechProvider : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public string DisplayName { get; set; } = "";
    public SpeechProviderType Type { get; set; }
    public string Vendor { get; set; } = "";
    public string ConfigJson { get; set; } = "{}";
    public SpeechProviderStatus Status { get; set; }
    public int Version { get; set; }                  // bumped on every Update
    public string PreviousVersionsJson { get; set; } = "[]";  // ring buffer of last N snapshots
}

public sealed record SpeechProviderHistoryEntry(
    int Version,
    SpeechProviderHistoryAction Action,    // Created | Updated | StatusChanged | SoftDeleted
    string SnapshotDisplayName,
    SpeechProviderStatus SnapshotStatus,
    SpeechProviderConfig SnapshotConfig,
    DateTimeOffset At,
    Guid? ByUserId);

public enum SpeechProviderHistoryAction { Created, Updated, StatusChanged, SoftDeleted }
```

Same shape for `VoiceRecipe`. The library service reads `PreviousVersionsJson`, deserialises
each snapshot, and returns them alongside the current row. Snapshot retention defaults to 25
entries per row (configurable via `SpeechLibraryOptions.HistoryRetentionPerEntity`); older
edits are dropped from the ring buffer.

The audit log is queryable by entity id (timeline view in admin UI). A "who edited what
across the tenant" query is deferred to v1.2 — it would require a separate index over the
JSON column, which isn't worth the storage cost in v1.1.

Hard delete is operator-only and uses EF's `IgnoreQueryFilters().Where(...).ExecuteDelete()`
through a maintenance script, not exposed on the API surface.

### Built-in archetypes

Built-ins are `static readonly` records in code, exposed through a `BuiltInSpeechCatalog`
service. They are not seeded into the database. The library service merges built-ins (with a
`IsBuiltIn = true` marker and a deterministic id like `built-in:openai-whisper-default`) with
tenant-owned entries when serving list endpoints.

Tenants who want to edit a built-in click "Clone" — the library service copies the built-in's
config into a new tenant-owned `SpeechProvider` (or `VoiceRecipe`) row with a fresh `Guid`
and `IsBuiltIn = false`.

Built-in providers (initial set):

```text
built-in:openai-whisper-default   STT  openai     Whisper · whisper-1
built-in:openai-tts-alloy         TTS  openai     OpenAI TTS · alloy · tts-1
built-in:openai-tts-onyx-hd       TTS  openai     OpenAI TTS HD · onyx · tts-1-hd
built-in:azure-stt-en-us-eastus   STT  azure      Azure Speech · en-US · eastus
built-in:azure-tts-jenny-eastus   TTS  azure      Azure Jenny · en-US · eastus
built-in:elevenlabs-rachel        TTS  elevenlabs ElevenLabs · Rachel · multilingual_v2
built-in:openai-realtime          COMP openai-realtime      OpenAI Realtime · gpt-realtime-mini
built-in:azure-voice-live         COMP azure-voice-live     Azure Voice Live · uksouth · gpt-realtime-mini
```

Built-in recipes (initial set):

```text
built-in:cost-chained-openai      Chained   STT=built-in:openai-whisper-default  TTS=built-in:openai-tts-alloy   VAD=energy filter=on agg=on
built-in:premium-chained-openai   Chained   STT=built-in:openai-whisper-default  TTS=built-in:openai-tts-onyx-hd  VAD=energy filter=on agg=on
built-in:premium-chained-eleven   Chained   STT=built-in:openai-whisper-default  TTS=built-in:elevenlabs-rachel  VAD=energy filter=on agg=on
built-in:azure-only-chained       Chained   STT=built-in:azure-stt-en-us-eastus  TTS=built-in:azure-tts-jenny-eastus VAD=energy filter=on agg=on
built-in:openai-realtime          Composite Comp=built-in:openai-realtime
built-in:azure-voice-live         Composite Comp=built-in:azure-voice-live
```

Both built-in providers and built-in recipes have stable ids so a tenant's active-settings
pointer to `"built-in:openai-realtime"` survives across deploys. The IDs are reserved
strings prefixed with `built-in:`; tenant-owned entries always have `Guid` ids.

`VoiceModeSettings.ActiveRecipeId` and `ChatSpeechSettings.ActiveTtsProviderId` are typed as
`Guid?` plus a sibling `string? ActiveRecipeBuiltInId` (and same for TTS) to encode the
choice between a tenant `Guid` and a built-in string id. Or we encode both as opaque
`SpeechIdentifier` records — TBD during implementation; the user-visible behavior is the
same.

## Persistence

Two new tables in the `Ank` namespace, both tenant-scoped via the existing
`AonikDbContextBase` query filter machinery, both auditable via `AuditableEntity`:

```text
AnkSpeechProviders
    Id, TenantId, DisplayName, Type, Vendor, ConfigJson, Status, Version,
    PreviousVersionsJson,
    CreatedAt, CreatedBy, UpdatedAt, UpdatedBy, IsDeleted, DeletedAt, DeletedBy, RowVersion

AnkVoiceRecipes
    Id, TenantId, DisplayName, Description, Kind,
    ChainedSttProviderId, ChainedTtsProviderId, ChainedPinnedAgentId,
    ChainedVad, ChainedVadStopMs, ChainedTranscriptionFilter, ChainedSentenceAggregator,
    CompositeProviderId, CompositePinnedAgentId,
    Status, Version, PreviousVersionsJson,
    CreatedAt, CreatedBy, UpdatedAt, UpdatedBy, IsDeleted, DeletedAt, DeletedBy, RowVersion
```

Each row carries its own audit trail in `PreviousVersionsJson`. The single migration generated
by `dotnet ef migrations add AddSpeechLibrary --project src/Aonik.Infrastructure
--startup-project src/Aonik.Api` adds both tables to the canonical `AonikDbContext`.

Two new platform-settings keys (existing key/value persistence, not a new table):

```text
voice/active                    -> VoiceModeSettings JSON
chat-speech/active              -> ChatSpeechSettings JSON
```

Existing tables / settings remain in place during the deprecation window:

- Legacy `tenant/settings/text-to-speech` key — read-only fallback, removed one release after
  migration ships.
- Existing `tenant/settings/voice` key (`VoiceProviderConfiguration`) — read-only fallback for
  the same window.

Migration of existing tenants runs lazily on first read of any new endpoint:

1. If the tenant has neither a `SpeechProviders` row nor an active-settings entry, run the
   migration once. Idempotent — wrapped in a per-tenant lock.
2. Migrate legacy `TextToSpeechSettings.DefaultProfile` into a new tenant-owned
   `SpeechProvider` row of `Type = Tts`. Set `ChatSpeechSettings.ActiveTtsProviderId` to the
   new row's id.
3. Migrate `VoiceProviderConfiguration.Chained.Stt` and `.Tts` into two new tenant-owned
   `SpeechProvider` rows. Synthesize a `VoiceRecipe` row that references those two providers
   with the existing VAD / filter / aggregator settings; set `VoiceModeSettings.ActiveRecipeId`
   to the synthesized recipe's id, and `Enabled` from the legacy `Enabled` flag.
4. Emit a `speech.library.migrated` telemetry event with provider counts and recipe id.

Legacy reads continue to work post-migration so a rollback is possible. After one release
cycle, the legacy persistence is deleted in a follow-up.

```csharp
    VoiceRecipe Recipe,
    SpeechProvider? Stt,
    SpeechProvider? Tts,

```

Validation rules enforced in the `Create` / `Update` paths:

- `SpeechProvider.Config` discriminator must match `(Type, Vendor)` — e.g. a `Type = Tts`
  provider with `Vendor = "openai"` must carry `OpenAITtsConfig`.
- `VoiceRecipe.Chained.SttProviderId` must resolve to a non-deleted `SpeechProvider` of
  `Type = Stt`. Same for `TtsProviderId` (Tts) and `CompositeProviderId` (Composite).
- `SetStatusAsync(Disabled | SoftDeleted)` on a provider is rejected if any active recipe
  references it. The error response carries a `RecipesUsingThisProvider` list so the UI can
  link directly to the blockers.
- `SetStatusAsync(Disabled | SoftDeleted)` on a recipe is rejected if it is currently the
  active voice recipe.
- `ChatSpeechSettings.ActiveTtsProviderId` must resolve to an active `SpeechProvider` of
  `Type = Tts`.
- `VoiceModeSettings.ActiveRecipeId` must resolve to an active `VoiceRecipe`.

## Voice Pipeline Resolution

```csharp
// In AonikVoicePipelineFactory
public async Task<Pipeline> BuildAsync(VoicePipelineBuildRequest request, CancellationToken ct)
{
    var resolved = await _activeVoiceMode.ResolveActiveAsync(ct);
    if (resolved is null || !resolved.Recipe.Status.IsActive())
    {
        throw new VoiceConfigurationException("Voice mode has no active recipe configured for this tenant.");
    }

    return resolved.Recipe.Kind switch
    {
        VoiceRecipeKind.Chained   => BuildChained(request, resolved),
        VoiceRecipeKind.Composite => BuildComposite(request, resolved),
        _ => throw new VoiceConfigurationException($"Unsupported recipe kind: {resolved.Recipe.Kind}")
    };
}
```

`BuildChained` constructs `WebSocketAudioSource → VAD → STT → AonikVoiceAgent →
SentenceAggregator? → SpeechTextNormalizer → TTS → WebSocketAudioSink` exactly as today, but
the STT and TTS engine factory inputs come from `resolved.Stt.Config` and `resolved.Tts.Config`
rather than from `VoiceProviderConfiguration.Chained`. Each `SpeechProviderConfig` derived
type maps cleanly to its Voxa engine constructor.

`BuildComposite` constructs `WebSocketAudioSource → CompositeProcessor →
WebSocketAudioSink` where `CompositeProcessor` is one of:

```csharp
new OpenAIRealtimeProcessor(new OpenAIRealtimeOptions
{
    ApiKey       = ResolveCredential(resolved.Composite.Vendor),
    Model        = ((OpenAIRealtimeConfig)resolved.Composite.Config).Model ?? "gpt-realtime-mini",
    Voice        = ((OpenAIRealtimeConfig)resolved.Composite.Config).Voice,
    Instructions = ComposeInstructions(export.Instructions, ((OpenAIRealtimeConfig)resolved.Composite.Config).InstructionsAddendum),
    Tools        = export.Tools.Select(MapToRealtimeTool).ToList(),
})
```

`export` is the result of `IRealtimeAgentExporter.ExportAsync(request.VoiceAgent, persistedThreadId, ct)`
— defined in [022.aonik-voice-realtime](022.aonik-voice-realtime.md) §"Composite Providers
Deferred" as the v1.1 prerequisite.

Same shape for `AzureVoiceLiveProcessor` with `AzureVoiceLiveConfig`.

## Realtime Agent Exporter

```csharp
namespace Aonik.Agents.Contracts.Services;

public interface IRealtimeAgentExporter
{
    Task<RealtimeAgentExport> ExportAsync(
        AIAgent agent,
        Guid? persistedThreadId,
        CancellationToken cancellationToken = default);
}

public sealed record RealtimeAgentExport(
    string Instructions,
    IReadOnlyList<RealtimeToolDeclaration> Tools,
    IReadOnlyList<RealtimeConversationItem> History);

public sealed record RealtimeToolDeclaration(
    string Name,
    string Description,
    string ParametersJsonSchema,
    bool IsFrontend);

public sealed record RealtimeConversationItem(
    string Role,                      // "user" | "assistant" | "tool"
    string Content,
    string? ToolCallId);
```

`Aonik.Agents.Services.RealtimeAgentExporter` is the production implementation. It reuses
`IAgentContextualizer` (resolves system instructions + user-brief preamble) and
`IChatThreadManager` (loads prior turns). For tool schemas, it reads `agent.GetTools()` and
uses `Microsoft.Extensions.AI.AIFunctionMetadata` to extract JSON schemas. Frontend / backend
classification reuses the existing `IVoiceFrontendToolCatalog`.

Realtime tool calls emerge from the Voxa processors as `ToolCallRequestFrame` and round-trip
the same way as the chained path — clients send a `toolResult` envelope back over the
WebSocket; the processor receives it through Voxa's existing `IFrontendToolGateway`.

Backend tool execution on the realtime path goes through `AIFunction.InvokeAsync` like any
other call site, so the [023.server-side-ai-tool-approval](023.server-side-ai-tool-approval.md)
wrapper applies unchanged.

## Admin UI

Single consolidated page at `/settings/speech`. Four tabs:

### Tab 1: Providers

Top: filter pills (All / STT / TTS / Composite), search box, "Add provider" button.

Body: a list (or grid) of provider cards, sorted by Type then DisplayName. Each card shows:

- Type icon + vendor logo
- Display name (large)
- Vendor + config summary ("OpenAI · whisper-1 · en")
- Status badge (Active / Disabled)
- "Used by N recipes" indicator (clickable, opens a popover listing the recipes)
- Action menu: Edit, Test, Clone (built-ins only — for tenant-owned entries, edit is in place),
  Disable / Enable, Soft delete

Edit / Add opens a side panel (or modal) with the per-vendor form. The form is generated from
the `/speech-vendors` schema response so adding a vendor doesn't require a UI rebuild for new
fields. Includes inline credential entry (API key) per vendor.

Test panel renders inline at the bottom of the edit panel. STT: mic record + transcribe
button; result appears below. TTS: text input + play button. Composite: read-only "test via
Live pipeline tab" hint (composite test requires a full WebSocket round-trip; would duplicate
the live pipeline tab).

History viewer is a small "View history" link next to the version number; opens a side panel
with the timeline.

## Risks & Open Items

1. **Per-vendor form schema service.** The `/speech-vendors` endpoint serves the form schema
   the UI uses to render every Edit panel. The schema must encode field types, required
   flags, and per-field defaults. JSON Schema is the obvious choice; we'd want to confirm the
   AdminUi has (or wants) a JSON-Schema-driven form renderer. Fallback: hand-author one TSX
   form component per vendor in `vendorFormSchema.ts` (less elegant, less coupling between
   backend and UI render logic).

2. **History table size.** Versioning every edit unbounded grows quickly for active tenants.
   v1.1 ships without retention; v1.2 adds a sliding-window cleanup (keep last N or last M
   days). The history rows are append-only and not on the read path so the cost is storage
   only.

3. **Built-in id collision.** The `built-in:` prefix on recipe / provider ids assumes tenants
   never name a tenant-owned entry with that prefix. Validation in `CreateAsync` rejects any
   tenant-owned id starting with `built-in:`.

4. **Vendor mismatch confusion.** A tenant who picks the built-in
   `cost-chained-openai` recipe and then edits the active TTS provider for chat speech to a
   non-OpenAI vendor doesn't break voice mode (voice mode reads from the recipe; chat speech
   reads from active TTS). But the labelling in the UI must avoid implying that the active
   chat-speech TTS controls voice. Tab 4 displays "This is your chat-speech voice — voice
   mode uses the recipe selected on the Voice mode tab" inline.

5. **Cross-vendor JSON schema for realtime tools.** OpenAI Realtime accepts JSON Schema for
   parameters; `Microsoft.Extensions.AI.AIFunctionMetadata` exposes parameter schemas as
   `JsonElement` nodes. Mapping is straightforward but lossy in edge cases (e.g. polymorphic
   schemas). Tested in `RealtimeAgentExporterTests`.

6. **History format mismatch on composite.** OpenAI Realtime's `conversation.item.create`
   accepts a flat list of role + text + tool-call items. Mapping from `ChatMessage` (with
   nested `TextContent`, `FunctionCallContent`, `FunctionResultContent`) is mechanical but
   loses some structure. Documented in `RealtimeConversationItem` mapping.

7. **Approval flow on composite.** The realtime processor invokes tools via
   `AIFunction.InvokeAsync`; the
   [023.server-side-ai-tool-approval](023.server-side-ai-tool-approval.md) wrapper plugs into
   the same interface so the approval flow is preserved without a special composite path.
   Verify in an integration test that an `ApprovalRequiredAIFunction` invoked from
   `OpenAIRealtimeProcessor` blocks until a `confirmAction` frontend tool result resolves the
   approval.

8. **Composer for composite is deferred.** "Custom composite" (build a composite recipe by
   picking a vendor + voice + instructions inline without going through the provider library
   first) is not in v1.1. Tenants pick the built-in composite recipes and override
   voice / instructions / model on the recipe edit panel; that covers 90% of the use cases.
   Composer for composite is a v1.2 candidate alongside the ReactFlow canvas.

9. **Per-account credentials within the same vendor.** v1.1 ships with vendor-keyed
   credentials — every library entry of vendor `openai` shares the tenant's OpenAI key.
   Tenants who need separate OpenAI accounts (e.g. dev vs prod) cannot model that in v1.1.
   v1.2 candidate: per-provider credential override that falls back to the vendor key.

10. **Voice override defaults on composite.** OpenAI Realtime ships voices distinct from
    OpenAI TTS (`alloy`/`ash`/`ballad`/`coral`/`echo`/`sage`/`shimmer`/`verse`). The
    Composite provider edit panel must surface that catalog, not the chained TTS catalog.
    Same for Azure Voice Live (Voice Live has its own voice list distinct from Azure
    Speech). The `/speech-vendors` endpoint encodes this per vendor.

11. **Recipe references that go stale.** Soft-deleting a provider that was once in an active
    recipe is blocked, but a tenant could disable a provider that's referenced by an
    *inactive* (disabled) recipe. The library service allows that and surfaces a "this recipe
    will not run until you re-enable its provider" warning when the user later tries to
    activate the recipe.

12. **ReactFlow upgrade path.** The stack editor's recipe model is identical to what a
    canvas editor would persist (`ChainedRecipeBody` + `CompositeRecipeBody`). Switching to
    ReactFlow in v1.2 only changes the renderer; no backend changes needed.

## Phasing & Effort

| Phase | Scope | Effort |
|---|---|---|
| **A** Provider library: domain, persistence, history, validation, endpoints, Providers tab + provider edit panel + test sections + per-vendor form schema | ~4 days |
| **B** Recipe library: domain, persistence, history, validation, endpoints, Recipes tab + stack editor | ~3 days |
| **C** Active settings + rewire `AonikVoicePipelineFactory` and `TextToSpeechService` to read from the library, Voice mode + Chat speech tabs, lazy migration | ~2.5 days |
| **D** Composite recipes: `IRealtimeAgentExporter`, OpenAI Realtime + Azure Voice Live branches, recipe + provider built-ins for composite, composite kind in stack editor | ~2 days |
| **E** Polish: history viewer, audit log query, usage guard UX, recipe-level test button, deprecate legacy persistence | ~1.5 days |
| Tests + spec follow-ups | parallel, ~1 day |
| **Total** | **~14 days** (about 2.5–3 weeks) |

Phase A is the critical path. Phase B depends on A. Phase C depends on A and B. Phase D
depends on the `IRealtimeAgentExporter` (independent of A/B/C in implementation but only
useful once C lands). Phase E is cleanup, can be deferred.

Suggested dev-deploy cadence: A → B → C as one rollout (full library + rewire), then D as a
follow-up rollout (composite), then E one release later (cleanup).
