Spec 040 Status: Draft Size: Large Priority: P2 Domain: Finance / Partners / Catalog Issue: TBD

Partner biller catalogue import (Flutterwave v3 bills)

Adds the missing IPartnerBillPaymentConnector implementation for Flutterwave and a tenant-scoped biller import flow: an operator opens the Admin UI, previews the live biller catalogue exposed by a configured partner connector, selects the billers/services they want, and imports them into the AONIK CatalogBiller / CatalogBillerService tables, wiring each to its provider codes through ConnectorBillerMapping. The import is idempotent and upsert-based — re-running it creates no duplicates, refreshes mutable fields, and soft-deactivates billers the partner has dropped. The spec is grounded twice, exactly like Spec 037: against the in-repo abstraction and entities (the catalogue, the connector ports, the mapping table, and one working SimulatedPartnerConnector already exist) and against the actual Flutterwave Bills API documentation (developer.flutterwave.com/docs/bill-payment).

1. Summary

AONIK already models a biller catalogue as a first-class domain — CatalogBillerCategory → CatalogBiller → CatalogBillerService, with admin CRUD pages and /catalog/billers endpoints. It also already defines the partner abstraction that knows how to ask a partner "what billers do you support?": IPartnerBillPaymentConnector.GetBillerCatalogAsync, resolved by ProviderCode through PartnerConnectorResolver, with the provider-specific codes deliberately confined to ConnectorBillerMapping (ProviderBillerCode / ProviderItemCode) so a logical biller can route to many partners. Today the only implementation of that port is SimulatedPartnerConnector, which returns two fake billers (SIM-ELEC, SIM-TELCO).

This spec closes the loop. It adds (1) a real FlutterwaveBillPaymentConnector whose GetBillerCatalogAsync reads the live Flutterwave biller catalogue, and (2) a BillerImportService + two endpoints + an Admin UI wizard that turn that catalogue into persisted CatalogBiller/CatalogBillerService rows and their ConnectorBillerMapping routing rows. The import is idempotent (the mapping table is the identity key, so re-import never duplicates) and upsert (it refreshes changed names/amounts and soft-deactivates dropped billers). No money moves; this is a reference-data sync, permission-gated on Catalog.Write.

Success signals An operator with Catalog.Write opens Catalog → Billers, clicks Import from partner, picks a configured Flutterwave connector, and sees the live NG biller catalogue (MTN, DSTV, IKEDC…) grouped by category, each row tagged new / mapped / changed against what is already imported. They select a subset and confirm; the catalogue list refreshes with the new billers, each carrying a ConnectorBillerMapping to the Flutterwave connector. Running the same import again reports 0 created, N updated, 0 duplicates. A biller Flutterwave later drops is shown Inactive on the next import, not deleted (its history and any orders survive).

3. Headline finding — Flutterwave bills are v3, not v4

The one fact that shapes this whole spec The existing FlutterwavePayoutConnector targets the Flutterwave v4 API: OAuth 2.0 client-credentials tokens, base URL developersandbox-api.flutterwave.com, an { status, message, data } envelope, and per-call X-Idempotency-Key / X-Trace-Id headers (Spec 037). But the v4 API exposes no bill-payment or airtime endpoints at all — Spec 037 §5.11 and §3.2 call this out explicitly, and our own research confirms it. Bill payment lives only on the older Flutterwave v3 API, which uses a static secret key (Authorization: Bearer FLWSECK-…), base URL https://api.flutterwave.com/v3, and a { status, message, data } envelope with no idempotency-key requirement. Consequence: the FlutterwaveBillPaymentConnector cannot reuse the v4 FlutterwaveClient / FlutterwaveTokenProvider / FlutterwaveAuthHandler. It needs its own v3 typed client, secret-key auth handler, options, and config provider. The two Flutterwave connectors share only a ProviderCode string ("Flutterwave") — which is fine, because the resolver searches each port's list independently (§6.4).

This is the kind of distance Spec 037 had to close for v3→v4 on the payout side; here it runs the other way (v4→v3) and on a different port. Treating the bill connector as "just add a method to the existing Flutterwave connector" would be wrong — different API version, different auth, different base URL, different lifecycle. §5 walks the v3 Bills surface; §6 maps it onto our port.

Geographic note (grounded) Flutterwave's Bills API currently supports Nigerian billers only (developer.flutterwave.com/docs/bill-payment). That is exactly the Payabo UK→NG launch wedge corridor, so the constraint is a fit, not a blocker — but the connector must hard-default country=NG and not pretend to multi-country breadth it cannot serve.

4. Scope (in / out)

4.1 In scope

  • New FlutterwaveBillPaymentConnector : IPartnerBillPaymentConnector (ProviderCode => "Flutterwave") — GetBillerCatalogAsync (the import read; the priority of this spec), plus ValidateCustomerAsync / PayBillAsync / GetBillPaymentStatusAsync mapped onto v3 validate / POST /bills / GET /bills/{reference} so the port is fully implemented (the pay path is Phase 2 within this spec — §6.6).
  • New v3 transport — FlutterwaveBillsClient (typed wrapper over https://api.flutterwave.com/v3, {status,message,data} envelope, non-2xx → FlutterwaveException, timeout → TimeoutException), FlutterwaveBillsAuthHandler (DelegatingHandler stamping the static secret key), FlutterwaveBillsOptions + FlutterwaveBillsConfigProvider (settings with appsettings fallback, mirroring the v4 FlutterwaveConfigProvider).
  • New IBillerImportService / BillerImportService — PreviewAsync (resolve connector → GetBillerCatalogAsync → annotate each entry against existing mappings; persists nothing) and ImportAsync (the idempotent upsert of categories, billers, services, and mappings — §8).
  • New Two endpoints — POST /catalog/billers/import/preview and POST /catalog/billers/import, both gated Catalog.Write (FastEndpoints, the AdminUserWritePolicy the existing catalog writes use).
  • New Import DTOs — request/response records in Contracts/Models/Catalog/ for the preview list (with per-entry import status) and the import summary (created/updated/deactivated counts).
  • New Admin UI import wizard — a dialog/flow composed from ImportDemoDataDialog + CatalogBillersPage patterns, plus a billerImportService.ts client.
  • Edit FinanceModule.ConfigureServices — a "Flutterwave bills connector" DI block registering the v3 client + connector alongside the simulated bill connector (do not remove Simulated — it stays the fallback ProviderCode), and the import service.
  • Edit PartnerGatewaySettingNames + appsettings.json — add Finance.Partners.Flutterwave.Bills.{Enabled,BaseUrl,SecretKey} keys (secret supplied via environment / user-secrets, never committed).
  • New Tests mirroring FlutterwaveConnectorTests (hand-rolled HttpMessageHandler): catalogue mapping, happy-path import, idempotent re-import, upsert of a changed name/amount, soft-deactivation of a dropped biller, partner 500, timeout.

4.2 Out of scope

  • Scheduled / automatic sync. This spec delivers operator-triggered import only. A Quartz job that re-runs ImportAsync nightly is a natural follow-up but is deferred (the upsert is built to make it a trivial add later — §8, O3).
  • The bill-payment order flow. Creating a BillPayment order, posting the ledger, and the PartnerBillPayment execution record already exist / belong to the order pipeline. This spec wires the connector's pay methods (so the port is whole) but does not touch order orchestration or money-action logging — those stay at the caller per money-action-logging.md.
  • Non-Flutterwave bill partners (eTranzact / Interswitch). The import is partner-agnostic by construction — it resolves any IPartnerBillPaymentConnector by code — but only the Flutterwave connector is built here.
  • Schema changes. Every table this import writes already exists. The import adds no migration. The one candidate — a unique index on the mapping's provider codes to make the idempotency lookup an index seek and a hard constraint — is raised as an open decision (§8.4, O1) and, if taken, MUST be tool-generated (dotnet ef migrations add), never hand-written, per CLAUDE.md.
Scope & sequencing — honest priority Per the Payabo launch plan, the MVP wedge is the UK→NG remittance corridor (~Aug 2026), and platform breadth is explicitly flagged as drift to freeze (payabo-august-launch-plan.html). Bill payment is a natural Payabo B2C surface and NG-only bills fit the corridor, but it is not on the remittance critical path. This spec is therefore marked P2 and should be sequenced after the remittance rail is GA (Specs 036 / 037 / 039). Whether biller import lands pre- or post-launch is a product call, not an engineering one — flagged here rather than silently assumed (O5).

5. Flutterwave v3 Bills API walkthrough

Grounded against developer.flutterwave.com/docs/bill-payment and the official v3 SDK docs. Auth is a static secret key passed as a bearer token; base URL https://api.flutterwave.com/v3; envelope { status, message, data }. The catalogue read the import depends on is the three-step categories → billers → items flow.

Verify at integration time v3 REST paths and SDK helper names diverge in Flutterwave's own docs (e.g. validate is documented as both a GET on /bill-items/{item_code}/validate and a POST in the Node SDK). The field shapes below are taken verbatim from the documented responses; confirm the exact verbs/paths against the live reference and the sandbox when implementing. The connector isolates this: paths live in one client, so a doc correction is a one-file change.

5.1 Bill categories — GET /v3/top-bill-categories?country=NG

The densest single call: each row already carries a biller code, an item code, and the customer field label.

GET https://api.flutterwave.com/v3/top-bill-categories?country=NG
Authorization: Bearer FLWSECK-...

→ 200 { "status": "success", "data": [
  {
    "id": 1, "biller_code": "BIL099", "name": "MTN Nigeria", "item_code": "AT099",
    "short_name": "MTN", "biller_name": "AIRTIME", "is_airtime": true,
    "default_commission": 0.02, "fee": 0, "country": "NG", "label_name": "Mobile Number"
  }, ...
]}

(GET /v3/bill-categories returns the fuller, un-curated list with the same row shape.)

5.2 Billers under a category — GET /v3/billers / products

// agencies (billers) for a category/country
→ { "status": "success", "data": [ { "code": "BIL136", "name": "Genesis Group Payment" }, ... ] }

// products (packages) under a biller — GET /v3/billers/{biller_code}/items (a.k.a. products)
→ { "status": "success", "data": {
     "biller_code": "BIL136",
     "products": [ { "code": "OT150", "name": "GENESIS GROUP ACCOMODATION", "amount": "0.0", "fee": "0.0",
                     "description": "..." }, ... ] } }

A product with a non-zero amount is a fixed-price package (a data bundle); amount = "0.0" means the customer chooses the amount (a variable service such as airtime or a postpaid bill). The richer amt_to_be_paid response also returns an items[] array of required input fields (name, type, required, length) — the raw material for BillCustomerField / FieldsJson.

{ "item_code": "AT099", "code": "BIL099", "customer": "08038291822" }
→ { "status": "success", "data": {
     "response_code": "00", "response_message": "Successful", "name": "MTN",
     "biller_code": "BIL099", "customer": "08038291822", "product_code": "AT099",
     "fee": 0, "maximum": 0, "minimum": 0 } }

Maps onto ValidateCustomerAsync → BillCustomerValidationResult (CustomerName from name; maximum/minimum bound a variable amount). Used by the pay flow, not by import.

6. FlutterwaveBillPaymentConnector design

6.1 Shape & placement

New folder src/Aonik.Finance/Services/Partners/Connectors/Flutterwave/Bills/ (kept apart from the v4 payout files to make the version boundary obvious). The connector is internal sealed, stateless, and throws typed failures — never swallows them — exactly like the payout connector. 

internal sealed class FlutterwaveBillPaymentConnector : IPartnerBillPaymentConnector
{
    public string ProviderCode => "Flutterwave";   // same code, different port list (§6.4)

    // NG-only bills (grounded §3). Resolver matches BillPayment + AirtimeTopup lanes by code.
    public IReadOnlyCollection<PartnerConnectorCapability> Capabilities { get; } = new[]
    {
        new PartnerConnectorCapability(PartnerServiceCategory.BillPayment,  new[]{"NG"}, new[]{"NGN"}, new[]{"Bill"}),
        new PartnerConnectorCapability(PartnerServiceCategory.AirtimeTopup, new[]{"NG"}, new[]{"NGN"}, new[]{"Airtime","Data"}),
    };

    public FlutterwaveBillPaymentConnector(FlutterwaveBillsClient client, IFlutterwaveBillsConfigProvider config) { ... }
    // GetBillerCatalogAsync / ValidateCustomerAsync / PayBillAsync / GetBillPaymentStatusAsync
}

6.2 GetBillerCatalogAsync — the import read

Fail closed if not configured (mirror FlutterwavePayoutConnector.EnsureConfiguredAsync). Otherwise read categories (§5.1), and for each biller optionally expand its products (§5.2) to capture multi-package billers; map to BillerCatalogEntry (§7). The BillerCatalogQuery.CategoryCode filter is applied client-side after the read (v3's category param is coarse). Country is forced to NG; a non-NG query returns empty rather than calling the API.

6.3 Classification rules (grounded)

DecisionRule from v3 data
ServiceCategoryis_airtime == true (or category in {airtime, data}) → AirtimeTopup; else BillPayment.
BillItem.AmountTypeproduct amount > 0 → Fixed (carry FixedAmount); amount == 0 → Variable (min/max left null at import, resolved per-customer at validate).
CustomerFieldsone BillCustomerField from label_name (e.g. "Meter Number"), plus any required items[] input fields.
CurrencyNGN (bills are NG-only).

6.4 Coexistence with the v4 payout connector

Both connectors return ProviderCode => "Flutterwave". This is safe and intended: the resolver keeps a separate list per port — ResolveBillPaymentConnector("Flutterwave") searches only IEnumerable<IPartnerBillPaymentConnector>, where the only "Flutterwave" entry is this connector; the payout connector lives in a different list. One vendor, one code, two ports, two transports (v3 secret key for bills, v4 OAuth for payout). The Admin UI and the operator see a single "Flutterwave" partner.

6.5 Pay-path methods (Phase 2, within scope)

ValidateCustomerAsync → §5.3, PayBillAsync → §5.4, GetBillPaymentStatusAsync → §5.5. Implemented so the port is complete and the connector is usable by the order pipeline, but not exercised by the import. Status strings map through the same normalized PartnerTransactionStatus ladder the payout connector uses (response_code "00" → Succeeded).

8. Import service — idempotent upsert

This is the heart of the spec and the explicit requirement: idempotent and upsert. Two ideas make it robust:

  1. Identity is the mapping, not the name. "Have I imported this provider biller before?" is answered by looking up ConnectorBillerMapping on (TenantId, ConnectorId, ProviderBillerCode) — biller-level rows have CatalogBillerServiceId == null; service-level rows carry both the service id and ProviderItemCode. Names and amounts drift; provider codes are stable, so the mapping is the correct idempotency anchor.
  2. Upsert, never duplicate, never hard-delete. Found → update mutable fields and re-activate. Not found → insert biller/service + mapping. Present last time but absent now → soft-deactivate (IsActive = false) — FKs are Restrict and any orders/history must survive, so we never delete.

8.1 Algorithm

ImportAsync(connectorId, selectedEntries):
  connector = load Connector(connectorId)        // → ConnectorType (ProviderCode) + PartnerId
  tenantId  = ITenantContext.TenantId            // never from the request
  selected  = dedupe(selectedEntries by BillerCode)   // run-level dedupe (provider may repeat)
  summary   = { billersCreated, billersUpdated, servicesCreated, servicesUpdated, deactivated }

  for entry in selected:
     category = UpsertCategory(tenantId, entry.Country, entry.CategoryName)   // natural key (Tenant,Country,Name)

     // ── biller identity = the biller-level mapping (ServiceId == null) ──
     bMap = ConnectorBillerMappings.SingleOrDefault(
                Tenant==tenantId, ConnectorId==connectorId,
                ProviderBillerCode==entry.BillerCode, CatalogBillerServiceId==null)
     if bMap == null:
         biller = new CatalogBiller { Name=entry.BillerName, CountryCode=entry.Country,
                      CategoryId=category.Id, CorrespondentPartnerId=connector.PartnerId, IsActive=true }
         add biller; add ConnectorBillerMapping { CatalogBillerId=biller.Id, CatalogBillerServiceId=null,
                      ConnectorId=connectorId, ProviderBillerCode=entry.BillerCode, IsActive=true }
         summary.billersCreated++
     else:
         biller = load CatalogBiller(bMap.CatalogBillerId)
         biller.Name=entry.BillerName; biller.CategoryId=category.Id; biller.IsActive=true   // upsert
         bMap.IsActive=true; summary.billersUpdated++

     seen = {}                                   // service-mapping ids touched this run for this biller
     for item in entry.Items:
         sMap = ConnectorBillerMappings.SingleOrDefault(
                    Tenant==tenantId, ConnectorId==connectorId, CatalogBillerId==biller.Id,
                    ProviderItemCode==item.ItemCode)        // i.e. service-level row
         if sMap == null:
             svc = new CatalogBillerService { BillerId=biller.Id,
                      ServiceCode=GenerateLogicalCode(biller, item),   // AONIK-owned, NOT the vendor code
                      Name=item.Name, Type=entry.ServiceCategory, Currency="NGN",
                      AmountType=item.FixedAmount!=null?"Fixed":"Variable", FixedAmount=item.FixedAmount?.Amount,
                      MinAmount=item.MinAmount?.Amount, MaxAmount=item.MaxAmount?.Amount,
                      RequiresValidation=(entry.ServiceCategory==BillPayment),
                      FieldsJson=serialize(entry.CustomerFields), IsActive=true }
             add svc; add ConnectorBillerMapping { CatalogBillerId=biller.Id, CatalogBillerServiceId=svc.Id,
                      ConnectorId=connectorId, ProviderBillerCode=entry.BillerCode,
                      ProviderItemCode=item.ItemCode, IsActive=true }
             summary.servicesCreated++; seen.add(new svc mapping)
         else:
             svc = load CatalogBillerService(sMap.CatalogBillerServiceId)
             svc.Name=item.Name; svc.AmountType=...; svc.FixedAmount=...; svc.IsActive=true   // upsert
             sMap.IsActive=true; summary.servicesUpdated++; seen.add(sMap)

     // ── soft-deactivate services this connector no longer offers for this biller ──
     for stale in ServiceMappings(connectorId, biller).Where(m => m not in seen && m.IsActive):
         stale.IsActive=false; load(stale.service).IsActive=false; summary.deactivated++

  SaveChanges()      // single transaction; catch unique-violation → treat as concurrent re-run (8.3)
  return summary

8.2 Preview (no persistence)

PreviewAsync(connectorId, query) resolves the connector, calls GetBillerCatalogAsync, then annotates each entry by the same mapping lookups without writing: new (no mapping), mapped (mapping exists, fields match), changed (mapping exists, name/amount differs). This is what powers the operator's "preview what's available, then select" experience and lets them see a re-import would be a no-op before committing.

8.3 Idempotency under concurrency

The lookup-then-insert is correct for sequential re-runs (a clean no-op). Two concurrent imports of the same connector could both miss the lookup and then collide on the mapping's unique index (TenantId, ConnectorId, CatalogBillerId, CatalogBillerServiceId) — SQL Server allows only one row with a NULL CatalogBillerServiceId per (Tenant, Connector, Biller), so the second insert throws DbUpdateException. Mitigation: catch the unique-violation and re-resolve as an update (the same lookup-then-insert race documented for the webhook inbox in Spec 037 §4). For an operator-triggered admin action, a coarse per-(tenant, connector) import lock is also acceptable and simpler.

8.4 Recommended index (optional migration)

The biller-level identity lookup is by (TenantId, ConnectorId, ProviderBillerCode), which the existing unique index does not cover (it keys on CatalogBillerId, not the provider code). The import is correct without a new index (the query just scans the tenant's mappings for that connector), but for performance and a hard uniqueness guarantee, a unique index on (TenantId, ConnectorId, ProviderBillerCode, ProviderItemCode) is recommended. If taken, it MUST be generated by dotnet ef migrations add against AonikDbContext and reviewed before commit — never hand-authored (CLAUDE.md, "Migrations Must Be Tool-Generated Only"). Raised as O1.

10. Admin UI

An Import from partner button on CatalogBillersPage opens a multi-step dialog modelled on ImportDemoDataDialog:

  1. Source — pick a configured partner connector (a Flutterwave connector row).
  2. Preview — call /import/preview; render the catalogue grouped by category with per-row status chips (New / Mapped / Changed) and checkboxes; "select all new" / category filters.
  3. Confirm — show counts ("12 new, 3 updated"), call /import, then refresh the billers list.

New client src/Aonik.AdminUi/src/services/billerImportService.ts with preview() / import() over lib/api.ts (auth + tenant headers are automatic). Detailed visual design is deferred to implementation; the patterns are established.

13. Acceptance criteria

  • Connector. A configured FlutterwaveBillPaymentConnector resolves via ResolveBillPaymentConnector("Flutterwave") while "Simulated" still resolves the fake; GetBillerCatalogAsync calls v3 top-bill-categories/billers and returns normalized BillerCatalogEntry items with correct ServiceCategory and AmountType.
  • Version isolation. The bill connector uses a v3 secret-key client distinct from the v4 OAuth payout client; no shared transport. Not-configured → fails closed.
  • Preview. /import/preview returns the live catalogue with each entry tagged New / Mapped / Changed and persists nothing.
  • Idempotent. Importing the same selection twice yields billersCreated == 0 and no duplicate CatalogBiller / CatalogBillerService / ConnectorBillerMapping rows.
  • Upsert. A changed provider name/amount updates the existing rows in place; identity is preserved through the mapping.
  • Soft-deactivate. A biller the partner drops becomes IsActive = false on the next import; nothing is hard-deleted.
  • Invariant held. CatalogBillerService.ServiceCode is an AONIK logical code; provider codes appear only in ConnectorBillerMapping.
  • No migration (unless O1 is taken, and then tool-generated).
  • Tests cover happy path + idempotent re-run + upsert + deactivate + partner 500 + timeout.
