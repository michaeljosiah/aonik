PaymentLog — acts of support & bank corroboration

The "Effortless to keep / Provable forever" half of Simi: a PaymentLog is one real-world act of support — attached to a commitment (rolling it forward) or standalone (the one-off plumber) — recorded in its original currency, optionally with a receipt, and optionally linked back to the bank transaction that corroborates it. It is the one new aggregate the Simi launch plan already budgeted. Today only spending transactions exist (a different object with no CareEntity attribution, no commitment roll-forward, no receipt linkage). Implements Simi readiness plan §5.3.

Spec family (043–048) Depends on Spec 043 (the entity a log is for) and pairs with Spec 044 (mark-done writes a log). Receipts attach via Spec 046; the Support Statement and the circle read these logs (Spec 048).

1. Summary

Simi never moves money — the user pays via bank, Wise, or cash as they always have, then captures that it happened. A PaymentLog is that capture: who/what it was for (a CareEntity), what it honoured (a commitment cycle, or nothing), how much in which currency, through which channel, with an optional receipt and note, and how it was recorded (manual, a captured screenshot, a voice note, a mark-done, or — later — a detected bank debit). It is the unit the year totals sum, the rows a Support Statement prints, and the proof a circle member sees.

Success signals Fola marks Mum's allowance done: a PaymentLog for £200 (GBP) is written against the "Mum" entity and the May cycle, with the Wise screenshot filed as its receipt. The plumber is a standalone ₦85,000 log against the Surulere flat with no commitment. Her year total reads "£4,250 + ₦1.2m" — never a fabricated converted sum. When her linked account later shows the same £200 Wise debit, the matcher links it to her existing log (one record, marked "verified against linked account") instead of double-counting.

2. Problem & current state

  • No PaymentLog aggregate exists. The closest object is PersonalTransaction — a spending record (signed Amount, SourceType Plaid/Manual, category, ImportFingerprint for dedup). It has no CareEntity attribution, no commitment link, no roll-forward, no per-currency support totals, and its receipts (TransactionAttachment) are spending-scoped. Reusing it would smuggle the generic-PFM model into the keeper (Guardrail 1).
  • The launch plan already budgets it. Simi launch-plan §7 lists "payment-log CRUD" as the one new backend module; rebuild spec §8.1/§8.3 give the model and repository.
  • The transaction-link pattern is established. PersonalRecurringBill already carries a nullable SourceTransactionId, and PersonalTransaction carries a nullable AiRunId / FinancialContextId — so "hang a nullable reference to a transaction off a record" is an existing idiom we reuse for corroboration (§6).

3. Scope (in / out)

3.1 In scope

  • New PaymentLog entity + CRUD, original currency, channel, origin, receipt links, note (§4).
  • New A nullable SourceTransactionId + CorroborationStatus — the bank-evidence link (§6).
  • New Per-currency year/period summaries (§7).
  • New Idempotent create for the offline capture queue; soft-delete + restore (§8).

3.2 Out of scope

  • Money movement & FX. A log records what was paid elsewhere; it never funds or converts. The optional ApproxGbp is a user-entered, display-only label — no rates, no engine.
  • The fuzzy matcher that auto-links a transaction to a log (Plaid auto-capture / corroboration) is a fast-follow (readiness Phase E). This spec ships the schema (the nullable FK + status) and the confirm-gated link/unlink endpoint so nothing is rebuilt; the matching job lands later (§6).

4. PaymentLog entity new

public class PaymentLog : AuditableEntity, ITenantScoped
{
    public Guid    TenantId     { get; set; }
    public Guid    UserId       { get; set; }
    public Guid    CareEntityId { get; set; }   // → CareEntity (Spec 043); always attributed
    public Guid?   CommitmentId { get; set; }   // → the commitment it honours; null for one-offs (Spec 044)
    public Guid?   CommitmentCycleId { get; set; } // the specific cycle marked Paid (Spec 044 §6)

    // ── Money that keeps its origin (never converted) ─────────────
    public decimal Amount     { get; set; }     // positive magnitude (a log is an outflow of support)
    public string  Currency   { get; set; } = string.Empty; // ISO-4217, as actually paid
    public decimal? ApproxGbp { get; set; }     // optional user-entered label only — NOT computed

    public DateTime Date    { get; set; }             // date-only semantics (DateTime, per codebase convention)
    public string   Channel { get; set; } = "bank";   // bank | wise | cash | other
    public string   Origin  { get; set; } = "manual"; // manual | captureImage | captureText | captureVoice | markDone | plaidDetected
    public string?  Note    { get; set; }

    // ── Bank corroboration (schema now; matcher is a fast-follow, §6) ──
    public Guid?   SourceTransactionId { get; set; } // → PersonalTransaction.Id
    public string  CorroborationStatus { get; set; } = "none"; // none | matched | confirmed

    // ── Offline-safe create & soft delete ───────────────────────
    public Guid?     IdempotencyKey { get; set; } // client-supplied; unique (TenantId, UserId, IdempotencyKey)
    public DateTime? DeletedAt      { get; set; } // soft delete, 30-day restore window
}

Receipts are Documents linked to the log (§10), not embedded blobs — so a receipt is a first-class vault item. A log always has a CareEntityId; CommitmentId is optional (the one-off plumber attaches to the flat entity but no commitment).

5. The three-layer model

The crucial modelling point (readiness §5.3): a bank transaction does not link directly to a commitment — it links through the act. Three layers, each with one job:

PersonalTransaction PaymentLog Commitment (+ Cycle) "bank evidence" ──────▶ "the act, this cycle" ──────▶ "the rhythm" £200 Wise debit CareEntity=Mum, May cycle Mum — monthly allowance SourceType=Plaid Currency=GBP, receipt 📎 NextDue rolls 28 May → 28 Jun (Spec 028 / linked acct) SourceTransactionId ───┘ (Spec 044) CorroborationStatus=confirmed

Linking a transaction straight to a commitment would lose per-cycle granularity ("which month did this £200 satisfy?"). Routing it through the PaymentLog — which already knows its CommitmentCycleId — keeps the history exact and gives one place to dedupe.

6. Corroboration & dedup the dedup key

The nullable SourceTransactionId + CorroborationStatus unlock three things:

  1. Auto-capture nudge — a detected linked-account debit becomes a proposed PaymentLog (Origin = plaidDetected) against an open commitment cycle; one tap confirms (readiness Phase E).
  2. Bank-corroborated statements — a "verified against linked account" marker on Support Statement rows whose log is linked (Spec 048 reserves the column).
  3. Deduplication — the one the rebuild spec doesn't name. If the user manually captures a payment and Plaid imports the same debit, the link collapses them into one log instead of double-counting and corrupting the year total. SourceTransactionId is the dedup key (unique per non-null value, mirroring PersonalTransaction.ImportFingerprint).
The matcher proposes; it never auto-links silently Matching is fuzzy: a £200 instruction posts as £198.50 + £1.50 fee, settles two days late, GBP debit vs NGN receipt. A wrong auto-link would corrupt the proof. So: this spec ships the schema (the nullable FK + the three-state status) and a confirm-gated link/unlink endpoint; the matching job is a fast-follow that only ever proposes a link (matched) for the user to accept (confirmed) — never settles a link on its own. none → matched → confirmed is one-way to confirmed; unlink returns to none.

7. Per-currency summaries recorded, never computed

A PaymentLogSummaryService exposes per-currency rollups — the Today hero ("£4,250 · 6 people & places" + "+ ₦1.2m recorded in naira") and each CareEntity profile total (Spec 043 §8/§9): 

public record YearSummary(int Year, IReadOnlyList<CurrencyTotal> Totals, int EntityCount);
public record CurrencyTotal(string Currency, decimal Total, int Count);
// GROUP BY Currency — one row per currency, summed. NEVER a converted grand total.

Corroboration-deduped logs count once. There is no FX anywhere: a converted figure is never produced, in keeping with the absolute multi-currency-computation freeze (Simi launch-plan §10).

8. Idempotent create & offline new

The mobile capture queue saves locally and syncs on reconnect (rebuild spec §7.5 acceptance), so a create can be replayed. The client supplies an IdempotencyKey (a stable GUID per captured act); a unique index on (TenantId, UserId, IdempotencyKey) makes a replayed create return the existing log rather than inserting a duplicate. Delete is soft (DeletedAt) with a 30-day restore window — "never delete history" (rebuild spec §2.4); the vault and statements treat soft-deleted logs as absent.

9. API surface

Customer-scoped (UserPolicy), under /personal-finance/payment-logs:

RouteVerbPurpose
/personal-finance/payment-logsPOSTCreate a log (idempotent). Standalone, or via commitment mark-done (Spec 044 calls this internally).
/personal-finance/payment-logsGETList (filter: careEntityId, commitmentId, year; paged). Powers "Recently handled" + profile history.
/personal-finance/payment-logs/{id}GET / PUT / DELETEGet / edit / soft-delete (+ restore within window).
/personal-finance/payment-logs/{id}/transaction-linkPOST / DELETEConfirm or remove a corroboration link (confirmed ↔ none); the matcher proposes matched (§6).
/personal-finance/summary/year?year=GETPer-currency year summary for the Today hero (§7).

Every request DTO ships a Validator<T> (build-time enforced). CreatePaymentLogRequest validates a positive Amount (.PositiveMoney()), a .CurrencyCode(), a channel/origin from the allowed sets, and that CareEntityId (and CommitmentId when present) belong to the caller.

10. Receipts

A receipt is a Document (Spec 035) linked to the log via the entity/receipt linking added in Spec 046. A mark-done or capture-confirm that carries an image creates the Document and links it; PaymentLogResponse returns receipt DocumentRefs (id + thumbnail URL), never bytes. Before Spec 046 lands, a log can still be created without a receipt (the link is optional), so 045 is independently shippable.

11. Persistence & migration

  • New table PaymentLog → dbo.AnkPaymentLogs via MapFinanceTable (AonikDbContext) + MapTable (PersonalFinanceDbContext); DbSets on both contexts (every new DbSet lives on the canonical AonikDbContext, CLAUDE.md); IEntityTypeConfiguration with indexes on (TenantId, UserId, CareEntityId, Date) and (TenantId, UserId, CommitmentId), a unique filtered index on (TenantId, UserId, IdempotencyKey) WHERE not null, and a unique filtered index on SourceTransactionId WHERE not null (dedup).
  • No backfill. New table; existing spending transactions are not migrated into logs (different object). A future convenience could offer "log this transaction as support," but that is user-driven, not a migration.
  • Tool-generated migration only against AonikDbContext (CLAUDE.md).

12. Security & audit

  • Tenant + user scoping on every read and write; CareEntityId/CommitmentId validated to the caller. A circle member's access to another user's logs is governed entirely by Spec 048's visibility filter (including the "docs-only, no amounts" rule).
  • UserPolicy; no admin path.
  • A PaymentLog records a payment but moves no money — it is not a money action in the Issue #142 sense (no quote/capture/settle/webhook), so that logging convention does not apply. Create / edit / delete / corroboration-link changes are ordinary audited writes.

14. Acceptance criteria

  • Attributed acts. A standalone log (plumber, ₦85,000, flat entity, no commitment) and a mark-done log (£200, Mum, May cycle) both persist; both carry original currency; the cycle log links its CommitmentCycleId.
  • Per-currency totals. Logs in GBP + NGN yield two CurrencyTotal rows; no converted grand total is produced.
  • Idempotent offline create. Two creates with the same IdempotencyKey yield one log (the second returns the first).
  • Corroboration + dedup. Confirming a transaction link sets CorroborationStatus = confirmed; a manual log + a Plaid transaction for the same act, once linked, count once in the year total; the matcher never auto-confirms a link.
  • Soft delete. A deleted log disappears from lists/summaries/statements but restores within 30 days; history is never hard-deleted.
  • Build & migration. dotnet build green; tool-generated migration adds only AnkPaymentLogs with the specified indexes.

15. Open decisions

  • O1 — Corroboration match confidence on the link. Whether to store the matcher's confidence + the mismatch deltas (fee, settlement lag, currency) on the link for the review UI. Leaning yes (cheap, aids the confirm decision); finalised with the Phase E matcher.
  • O2 — Cross-currency corroboration. A GBP debit corroborating an NGN-received log. Phase 1: link is allowed (currencies differ legitimately); the statement shows the recorded currency and notes the linked-account currency. No conversion.
  • O3 — Restore window length. 30 days proposed; trivially configurable.
