Spec 090 Status: Draft (Rev 3) Size: Medium Module: Aonik.Subscriptions

Offline-verifiable entitlement

A paid feature in a local-first application must be checkable with no network. Today IEntitlementReader is a live server read against SubscriptionsDbContext, which is correct for a web product and unusable for a desktop one. This spec adds a signed, short-lived entitlement token the client can verify by itself, and says plainly what happens when it expires — because the two failure modes here are a licence anyone can forge and an application that stops working on a flight, and both are easy to reach by accident.

1. Summary

Spec 087 answers "what is this subscriber entitled to?" with a database query. Arke Studio is "free, MIT-licensed, local-first… nothing leaves the machine except approved dispatches." A commercial tier on top of it needs the same question answered on a laptop with no connection.

This spec adds:

  • An entitlement token — a compact, signed, short-lived statement of what a subscriber may do, verifiable with a public key alone.
  • Ed25519 signing with published, rotatable public keys, so a client verifies without ever holding a secret.
  • A refresh lifecycle with an explicit grace window and a defined behaviour at its end.
  • A statement of what this mechanism cannot do — meter credits — and why that is correct rather than a gap.
The failure this spec exists to prevent A licence check that phones home on every launch turns an offline-capable product into an online one, and the first flaky airport wifi turns a paying customer into an angry one. A licence check with no expiry turns one leaked token into a permanent free tier. Everything below is the narrow path between those two.

2. Why the server read is not enough

PropertyIEntitlementReader todayNeeded offline
Answered byA query against SubscriptionsDbContextThe client, unaided
Requires networkYes, every callNo, for days
FreshnessExact — the row is the truthBounded staleness, deliberately chosen
Tamper resistanceServer-side; nothing to tamper withSignature, because the artefact is on the user's disk

The server read stays exactly as it is and remains authoritative. This spec adds a projection of it that can travel — the same relationship a cached read has to its source, with the addition that this one is signed because it lands somewhere the user controls.

3. Scope (in / out)

3.1 In scope

  • Token format, claims, signing and verification.
  • Key generation, publication, rotation and revocation.
  • Issue and refresh endpoints; the grace window and its expiry behaviour.
  • Device binding, and its deliberate limits.
  • The revocation list and why it is small by design.
  • The client-side verification contract, as a specification other codebases implement.

3.2 Out of scope

  • Offline metering of credits. See §10 — this is a correctness boundary, not a deferral.
  • Anti-tamper, obfuscation or anti-debugging. The client is MIT-licensed and open; pretending otherwise would be theatre. See §4.
  • Per-seat hardware locking. Device binding is a friction, not a boundary.
  • A new identity system. Tokens are issued to an authenticated subscriber through the existing IdP.

4. What we are defending against

Say the quiet part first The desktop client is MIT-licensed and open source. Anyone determined can delete the check and compile their own build. No signing scheme changes that, and a spec that pretends otherwise leads to expensive obfuscation work that buys nothing.

So the goal is not "unbreakable". It is:

DefendedNot defended
Editing a JSON file on disk to grant yourself ProRecompiling the client with the check removed
Copying one customer's token to a hundred machines, indefinitelyOne person using their own licence on a machine we did not expect
Continuing to use a paid tier months after cancelling or charging backContinuing for the remainder of a paid period, which is correct anyway
A support burden of "why did my licence stop working" caused by usDetermined piracy, which is a pricing and goodwill problem, not a cryptographic one

In other words: make the honest path effortless and the casual dishonest path pointless. Everything beyond that costs more than it returns.

5. The token

A compact JSON payload with an Ed25519 signature — deliberately not a general-purpose JWT library dependency on the client, because verification must be a hundred lines a reviewer can read. 

{
  "v":    1,
  "jti":  "<uuid — unique per issued token>",
  "sub":  "<subscriber kind>:<subscriber id>",
  "tid":  "<tenant id>",
  "plan": "studio-pro",
  "feat": ["long-form-video", "cloud-sync", "voice-hd"],
  "lim":  { "workspaces": 25, "workspace-bytes": 214748364800 },
  "use":  { "workspaces": 18, "workspace-bytes":  91234567890 },
  "iat":  1786...,
  "exp":  1786...,
  "gra":  1786...,
  "dev":  "<device fingerprint, optional>",
  "kid":  "2026-08-a"
}
ClaimMeaning
jti added Rev 2Unique per issued token. Without it, §9's per-token revocation cannot work at all — the client would have no way to correlate the token it holds with a token-specific revocation entry, leaving only subscriber-wide revocation. It is also what links a token to its audit row, which is what makes "one token on a hundred machines" observable.
featFlag meters, resolved. The client asks "may I?" and never re-derives it from a plan name.
limCeiling meters, resolved to numbers. Enough to refuse a 26th workspace offline — on this device; see §11.1 for why that qualifier is load-bearing.
use added Rev 3Advisory snapshot of ceiling usage across all devices at the moment of issue. Rev 2's §11.1 promised the refreshed token would carry "the true count" and then specified a payload that could not — this is that promise made real. Never authoritative: it may only make the client refuse or warn earlier, and may never be used to permit anything the server has not confirmed. See below for why this is not the counter §10 prohibits.
expWhen the token stops being fresh. Short — days, not months.
graWhen the grace ends. Long — see §8.
devOptional device fingerprint. Present so a token copied to a hundred machines is visible, not so it is impossible. It is only a control if the verifier compares it — §11 step 4.
kidWhich public key verifies this. Rotation without invalidating everything.

5.1 The wire format, specified to the byte

P0 — "a detached Ed25519 signature" is not an interoperable specification

An earlier draft described the format in prose and then asked, in its acceptance criteria, that an independent implementation in a second language verify the same tokens. Those two things were incompatible. The prose fixed neither the envelope, nor the exact bytes covered by the signature, nor the character encoding, nor the signature encoding, nor — the one that silently breaks everything — whether the JSON is verified as received or re-serialised first.

Two correct implementations would then disagree about key order, whitespace and number formatting, and reject each other's valid tokens. That failure appears only when the second implementation is written, which is long after the format has shipped.

The token is a single ASCII string in exactly two parts:

token = SIGNING_INPUT "." BASE64URL(signature)

SIGNING_INPUT  BASE64URL(payload_bytes) — the LEFT-HAND PART OF THE TOKEN,
               variable length, EXACTLY AS TRANSMITTED

payload_bytes  UTF-8 encoding of the JSON object, with no BOM

signature      Ed25519 over ALL the ASCII bytes of SIGNING_INPUT — every byte
               up to but NOT including the "." separator. Never over
               payload_bytes, never over a re-serialisation, and never over a
               fixed-length prefix of any kind.

BASE64URL      RFC 4648 §5, unpadded ("-" and "_", no "=")
Correction — an earlier Rev 2 draft said "the 64 ASCII-safe bytes" 64 is the length of an Ed25519 signature, not of the encoded payload, which is variable and far longer than 64 bytes for any real token. An implementer following that sentence literally would have signed only a 64-byte prefix and failed every conforming verifier — and in an interoperability specification that is exactly the class of error that survives until someone writes the second implementation. The message is all the bytes of SIGNING_INPUT.
Why signing the encoded part, not the JSON, removes the entire problem Canonicalisation is not required and must not be attempted. The verifier splits on the single ".", verifies the signature over the left-hand substring exactly as it arrived, and only then base64url-decodes and parses it for use. Key order, whitespace and number formatting become irrelevant, because no implementation ever re-encodes anything. This is the one design choice that makes a second-language implementation genuinely mechanical — and it is the same reason JWS is specified this way.

The two passes over the payload, and the rule that makes them safe

P0 — the prescribed order was impossible to execute Rev 2 told the client to "verify the signature against the public key named by kid … only then decode and parse." But kid lives inside the encoded payload. You cannot select the verification key without decoding, and you were told not to decode before verifying. The algorithm had a circular dependency, and an implementer would have resolved it however seemed natural — which is precisely the divergence §5.1 exists to prevent.

The format keeps kid in the payload rather than adding a third header part, so the resolution is to make the two passes explicit and asymmetric: 

PASS 1 — UNTRUSTED, for key selection ONLY
  decode SIGNING_INPUT, parse JSON, read "kid" AND NOTHING ELSE.
  A payload that will not decode or parse -> reject.
  An unknown or absent "kid"              -> reject.
  No other claim may be read, cached, logged or acted upon in this pass.

PASS 2 — verify
  Ed25519 over ALL bytes of SIGNING_INPUT with the key named by that kid.
  Failure -> reject. Nothing from PASS 1 survives a failure.

PASS 3 — TRUSTED
  Re-read EVERY claim, including "kid", from the now-verified payload.
  If the re-read "kid" differs from the one used in PASS 1 -> reject.

The pass-3 re-read of kid is not redundant paranoia: it is what makes pass 1's untrusted read unable to influence the outcome. An attacker controls the whole payload before verification, so the only safe posture is that pass 1 selects a candidate key and nothing more, and every decision is made from bytes a signature has already covered. This is the same discipline JWS applies to its protected header.

  • Rejection rules. More or fewer than two parts; any character outside the base64url alphabet; padding present; a payload that is not a JSON object; an unrecognised v. All are rejected before parsing, with no partial acceptance.
  • Unknown claims are ignored, so claims can be added without breaking old clients. Unknown kid is not ignored — it is a hard failure (§6).
  • Timestamps are integer seconds since the Unix epoch, UTC. Never strings, never milliseconds.
  • Test vectors ship in P4: a valid token, one with a flipped payload byte, one with a flipped signature byte, one with padding, one with an unknown kid, one expired, one in grace. An implementation is conformant when all seven produce the specified verdict.
Counters are conspicuously absent There is no credit balance in the token, and that is §10's subject. A number that can be spent cannot be safely stated in an artefact the spender holds.

5.2 Why use is a level, not a balance

Adding a usage figure to a token that pointedly excludes credit balances needs justifying, because the two look alike and are not.

use — a ceiling levelA credit balance — prohibited
What the client does with itRefuses earlier. It can only ever be more restrictive than no knowledge at all.Spends it. Permission to act is derived from it.
Where the real check happensServer-side at claim time, under RowVersion compare-and-increment. Always.Nowhere — the client's copy is the decision.
Effect of a stale valueThe client is wrong in the customer's favour and the server corrects it on the next claim.The customer spends the same credits twice — on two machines, or by restoring yesterday's file.
Effect of tamperingNothing is gained. Editing use down does not create workspace slots; the server still refuses.Everything is gained. Editing the balance up is free money.
The test that separates them Ask what a forged value buys. A forged credit balance buys compute the customer has not paid for, because nothing downstream re-checks it. A forged use buys nothing at all, because the ceiling claim is enforced server-side at the moment of creation and an offline creation is provisional until it is (§11.1). That asymmetry is the whole distinction, and it is why this claim can be carried while a balance cannot.

6. Keys and rotation

  • Ed25519. Small signatures, small keys, no parameter choices to get wrong.
  • The private key never leaves the server and is held through the existing ISettingValueProtector / DataProtection path.
  • Public keys ship with the client and are fetchable, so a rotation reaches an old build without an update.
  • kid selects the key. Several are valid at once, which is what makes rotation a non-event.
  • A compromised key is withdrawn: removed from the published set, and every token bearing its kid fails verification at the next check.

6.1 The safe-retirement invariant

P0 — "several keys valid at once" does not by itself make rotation safe

Overlapping keys stop a rotation invalidating tokens at the moment of rotation. They say nothing about retirement. If a signing key reaches its NotAfter, or is dropped from the published set, while tokens it signed are still inside their grace window, then every offline paying customer holding one silently degrades to the free tier — with a valid, unexpired, unrevoked token in hand.

It would look exactly like a licensing bug to the customer and exactly like correct rotation to us, and it would land on the users least able to recover: the ones who are offline.

The invariant, which is a scheduling rule rather than a mechanism:

A non-compromised verification key MUST remain published until

    max(gra) over every token it has ever signed

has passed. With exp = 7d and gra = 30d, a key stops SIGNING at T and
stops VERIFYING no earlier than T + 30d.
  • NotAfter on AnkEntitlementSigningKeys therefore has two distinct meanings and needs two fields: SigningNotAfter (stop issuing with this key) and VerifyNotAfter (stop publishing it), with the second at least the maximum grace beyond the first.
  • The audit rows make this computable rather than assumed: the true retirement date is MAX(gra) across AnkEntitlementTokenIssues for that kid.
  • Compromise is the deliberate exception. A leaked private key is withdrawn immediately and the breakage is accepted, because the alternative is honouring forged tokens. That is a decision to make loudly, with support forewarned — not a scheduled event.
A shipped public key is not a secret and must not be treated as one It verifies; it cannot sign. The mistake to avoid is deriving anything else from it — an obfuscated "secret" in the client is a secret published to everyone who runs strings.

7. Issue, refresh, expiry

  1. Issue. The client authenticates through the existing IdP and requests a token. The server reads entitlement exactly as Spec 087 does today, projects it, signs it.
  2. Store. The client keeps the token on disk. It is not a secret — it says what someone bought — but it is bound and short-lived.
  3. Refresh. Opportunistically, well before exp, whenever the network happens to be there. Never on a blocking path, never as a launch gate.
  4. Expire. After exp the token is stale but still honoured until gra.
  5. Lapse. After gra, paid features are unavailable. See below for exactly what that means.

8. Grace, and the day the network is gone

The rule that decides the product's character Lapsing removes paid features. It never removes the user's work, and it never removes the free product. Arke Studio without a subscription is Arke Studio — the thing that exists today, free and MIT. A lapsed token returns the user to that, with every world still on their disk and every file still readable.
StateWindowBehaviour
Freshuntil expEverything works. No network needed.
Staleexp → graEverything still works. The client mentions, quietly and once, that it would like to check in.
Lapsedafter graPaid features off. Local authoring, all worlds, all files: unchanged. Cloud sync pauses; it does not delete.

Suggested defaults: exp at 7 days, gra at 30. Long enough for a holiday, a hospital stay or a bad month of connectivity; short enough that a cancelled subscription does not fund a year of use. Both configurable per tenant, because a studio on a locked-down network is a different case from a hobbyist.

9. Revocation

Short expiry is the revocation mechanism for almost everything: cancel today, and within a week the token stops refreshing and within a month it lapses. A published revocation list exists only for the cases where a week is too long — chargeback fraud, a leaked token in circulation, an account compromise.

  • Keyed on token jti or subscriber, published alongside the public keys.
  • Consulted when the client is online anyway. Never a launch gate; an offline client cannot fetch it and must not be punished for that.
  • Small by design. A list that grows without bound is a list nobody ships. Entries are removed once the token they revoke would have expired regardless.

10. Metered credits are not entitlements

A hard boundary, not a phase-two item A flag ("may use long-form video") and a ceiling ("at most 25 workspaces") are statements that stay true until the subscription changes, so they travel safely in a signed artefact. A counter ("1,200 credits remaining") is a number that changes every time it is used — and an offline client holding it can spend the same credits on two machines, or restore yesterday's file and spend them again. That is not a bug to fix with better client code; it is what an offline balance is.

Therefore:

  • Counter meters are never issued offline. The token carries flags and ceilings only.
  • Anything that spends credits requires the network — which is already true, because it calls a provider.
  • Local dispatch on the user's own provider keys is unmetered by us, and should be. They are spending their own money with FAL; AONIK has no claim on it and no business counting it.

This is what makes the whole design honest: the offline story covers what the user may do, and the online story covers what they spend. Trying to make one mechanism carry both is where offline licensing schemes go wrong.

11. What the client must do

The client is a separate codebase — possibly not even C#. This section is the specification it implements, and it is short on purpose.

  1. Split on the single ".", then run the three passes of §5.1: an untrusted decode that reads kid and nothing else, Ed25519 verification over all bytes of the left-hand part exactly as received, then a trusted re-read of every claim from the verified payload. Reject an unknown kid.
  2. Reject a token whose sub or tid does not match the signed-in subscriber.
  3. Compare exp and gra against the system clock, then apply §8.
  4. If dev is present, compare it with the current device fingerprint and refuse the token on mismatch — see below.
  5. Enforce lim against locally visible holdings only, and treat the result as provisional (§11.1).
  6. Treat a missing, malformed or unverifiable token as free tier — never as an error, and never as a reason to refuse to start.
  7. Refresh opportunistically and in the background. Never block the UI on it.
  8. Independently of refresh, whenever the network is reachable, fetch the revocation list and compare the held token against both its jti and its sub (§9). See below — this ordering is load-bearing.
P0 — the revocation check must not depend on refresh succeeding

Rev 2 attached the revocation check to a successful refresh. That defeats it in the one scenario it exists for. A copied or leaked token is being used by someone who does not have the subscriber's IdP session — so their refresh cannot succeed, so under that ordering they would never consult the revocation list at all, and the revoked token would stay usable for the whole grace window. The check was gated on the very thing an attacker cannot do.

It also only mentioned jti, while §9 supports subscriber-wide revocation for account compromise — which is the case where the attacker may hold several tokens and revoking one at a time is useless.

  • The revocation list is public and unauthenticated — it names revoked jtis and subscribers, not secrets — so fetching it needs no session and cannot be blocked by lacking one.
  • It is fetched opportunistically whenever online, on the same trigger as refresh but not conditional on it, and either match refuses the token immediately.
  • It is never consulted offline and its absence is never a reason to degrade — an offline client cannot fetch it and must not be punished for that (§9).
Step 4 was missing, and an unchecked claim is worse than an absent one An earlier draft listed dev as a claim whose purpose was to make copying visible, then specified a verifier that checked only signature, subscriber, tenant and timestamps. The token would therefore pass unchanged on any machine, and the issue audit row records only the original issuance — so neither half of the advertised control existed. A claim nobody checks is not a weak control; it is a documented control that is absent, which is how a mitigation gets counted twice in a threat model.

Either the verifier compares it, or the claim and every copy-detection statement in this spec come out. This revision takes the first option — while keeping §4's honesty: a modified open-source client can report any fingerprint it likes. dev stops a file being copied between machines. It does not stop someone who edits the client, and it is not claimed to.

11.1 Offline ceiling checks are provisional, and must say so

P0 — a ceiling is global; an offline client sees one device

lim was described as "enough to refuse a 26th workspace offline." It is not. The ceiling counts the subscriber's workspaces everywhere; an offline client can only see the ones on the machine it is running on. On a second or freshly-installed device the local count starts at zero, so the client happily admits another twenty-five — and the customer discovers the problem only at the next sync, as a quota rejection on work they have already done.

That is the worst possible ordering: the refusal arrives after the effort, not before it.

  • Offline creation is provisional. A workspace created while offline is marked as such locally, and the client says so plainly — "will be confirmed when you next connect" — rather than implying an entitlement it cannot check.
  • The authoritative claim happens on first sync, through the server-side ceiling with its RowVersion compare-and-increment. That is the only place the global count is knowable.
  • A rejected provisional workspace is never deleted. It stays local and fully usable — the free product has no workspace limit — and it simply does not sync. The customer is told they are over their plan's limit and offered the two real choices: upgrade, or free a slot.
  • The refreshed token carries use — the across-all-devices snapshot from §5.2 — so the second offline session starts from reality rather than from zero. The client compares use against lim and counts its own provisional creations on top, which means the second device warns at 18 rather than admitting another 25. It is advisory: it may refuse or warn earlier, never permit.
Why this is the right trade rather than a compromise The alternative is refusing to create anything offline that might exceed a limit the client cannot verify — which breaks the local-first promise for every honest customer in order to inconvenience a dishonest one who could edit the client anyway. Provisional creation errs toward the user, keeps their work, and moves the enforcement to the one place it can actually be enforced.
The clock A user can set their clock back. Mitigation is proportionate rather than clever: the client records the highest timestamp it has seen and treats a large backward jump as suspicious, degrading to free tier until it can check in. It does not try to be a trusted time source, because it cannot be one.

12. Persistence

  • AnkEntitlementSigningKeys — Kid, algorithm, public key, protected private key, NotBefore, SigningNotAfter, VerifyNotAfter, status. The two NotAfter fields are the §6.1 invariant made structural, so a routine rotation cannot strand an offline customer by accident.
  • AnkEntitlementTokenIssues — an audit row per issued token: subscriber, jti, kid, device, issued, ExpiresAt and GraceUntil. This is what makes "one token on a hundred machines" observable.
    P0 — GraceUntil must be persisted, not derived Rev 2 stored only issuance and expiry, while §6.1's retirement invariant needs MAX(gra) per kid. exp and gra are distinct claims, and the grace window is tenant-configurable and can change after a token is signed — so recomputing gra from ExpiresAt plus today's configuration gives the wrong answer for exactly the tokens that matter. The invariant would have been unenforceable and a routine rotation could still have withdrawn a key while one of its tokens was in grace. Store the value that was actually signed.
  • AnkEntitlementRevocations — jti or subscriber, reason, added, and the point at which the entry may be swept.
  • All tenant-scoped, Ank-prefixed, migration generated only against AonikDbContext.

15. Acceptance criteria

  1. A token verifies offline with the public key alone, and no network call occurs on the verification path.
  2. Editing any byte of the payload invalidates the signature.
  3. A token signed by a withdrawn kid fails verification.
  4. Two signing keys can be valid simultaneously, and rotation invalidates no outstanding token.
  5. A key whose SigningNotAfter has passed still verifies tokens it signed until VerifyNotAfter, and VerifyNotAfter cannot be set earlier than MAX(GraceUntil) over the persisted issue rows for that kid — enforced at write time, not by convention. Changing the tenant's grace configuration does not retroactively move an already-signed token's GraceUntil.
  6. Signature verification covers every byte of the left-hand token part; a token truncated after 64 bytes of signing input fails.
  7. A payload whose kid differs between the untrusted pass-1 read and the verified pass-3 read is rejected.
  8. A revoked token is refused by a client that cannot refresh — the revocation fetch requires no session and is not gated on refresh succeeding.
  9. Subscriber-wide revocation refuses every outstanding token of that subscriber, not only the one most recently issued.
  10. Editing use downward in a stored token grants no additional workspaces: the server-side ceiling still refuses at the limit.
  11. Every issued token carries a unique jti, and revoking that jti refuses exactly that token and no other token of the same subscriber.
  12. A token issued with dev is refused on a machine whose fingerprint differs.
  13. A token differing from a valid one only in JSON key order or whitespace still verifies, because no implementation re-serialises — and a token with one payload byte flipped does not.
  14. A token with base64 padding, three parts, or one part is rejected before parsing.
  15. A workspace created offline beyond the ceiling is marked provisional, is not deleted when the server later refuses it, and remains usable locally.
  16. A token whose sub does not match the signed-in subscriber is refused.
  17. Between exp and gra, paid features continue to work with no network.
  18. After gra, paid features stop, every local world remains readable, and the application still starts.
  19. A missing or corrupt token yields the free tier, not an error dialog and not a failure to launch.
  20. No counter meter appears in any issued token, enforced by a test over the projection.
  21. A revoked token fails at the next online check and is not consulted offline.
  22. The published vectors verify in an independent implementation.
  23. dotnet build and dotnet test Aonik.sln green.

16. Open decisions
