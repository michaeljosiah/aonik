Spec 032 Status: Draft Size: Large Priority: P0 Domain: Agents / Finance / Platform

Tiered AI mutation approval

Makes “agents propose, humans approve, systems execute” a real server-side boundary for every mutating agent tool, replacing today's prompt-and-UI honour system. A single ApprovalRequiredAIFunction decorator wraps every mutating tool, and the tool's risk tier selects the enforcement path: low-risk writes are audited and run in-band, medium-risk writes require an explicit in-session confirmation before running in-band, and high-risk money movement never runs in-band at all — it is marshalled into a durable Proposal and executed only by the Spec 030 dispatcher after approval. Unifies the unbuilt decorator (Spec 023) with the shipped proposal pipeline (Spec 030) under one classification model.

1. Summary

AONIK's foundational rule is that agents propose, humans approve, systems execute — CLAUDE.md states it as a non-negotiable: “Agents propose; systems execute — never bypass human-in-the-loop for mutations.” Today that rule is enforced in exactly one place — the Proposal pipeline (Spec 030) — and that pipeline is wired to only two low-stakes producers (financial-life-graph annotations and insights). Every money-movement agent tool — create payment intent, capture payment, cancel payment, post to the ledger, mark an invoice paid — is registered directly as a callable AIFunction and is ungated on the server. The only thing standing between the model and a captured payment is a system-prompt instruction to call a frontend confirmAction tool first. That is UX, not a boundary.

This spec closes the gap by making the boundary structural and uniform. A single decorator, ApprovalRequiredAIFunction, wraps every mutating tool at the one composition seam where tools are assembled (*AgentDescriptor.GetTools). The decorator's behaviour is selected by the tool's declared risk tier:

TierExample actionsEnforcement path
Low Save a memory, dismiss an insight, rename a label, recategorise a personal note Audited, auto-approved, runs in-band; non-blocking “done” card
Medium Create invoice, create bill, update budget, recategorise a transaction Explicit in-session confirm with fresh-presence step-up; then runs in-band
High Capture / cancel payment, transfer, payout, refund, pay bill, ledger posting, partner API call Never runs in-band. Marshalled into a durable Proposal; executed only by the Spec 030 dispatcher after approval

The high-risk path is exactly the design the platform's ethos implies and that was sketched informally early on: the agent is never handed the real mutation tool — it is handed a tool whose only effect is to create a proposal for the mutation. The proposal's IProposalHandler is the single code path that ever touches the domain service. The decorator makes that true automatically for any tool classified High, with no per-tool bespoke wiring.

Success signals No mutating agent tool can reach a domain service without a recorded approval decision. A money-movement tool call produces a Proposal the user can approve in the same turn or from the approvals queue, and the funds move only inside the dispatcher's handler. Registering a new mutating tool without classifying it fails the build. confirmAction still renders the same card it does today — but it is now a view over a server-owned decision, not the gate itself.

2. Problem: the false boundary

The documentation asserts a server-side control that does not exist. CLAUDE.md's “Code Patterns” section states:

False claim “Mutating tools (CreateInvoice, IssueInvoice, CreatePaymentIntent, etc.) are wrapped with ApprovalRequiredAIFunction.” — No such class exists anywhere in the codebase. A grep for ApprovalRequiredAIFunction returns only the (markdown) Spec 023 proposal. The wrapper was specified and never built; the docs describe the intended state as if it shipped.

The concrete as-is state, confirmed by reading the code:

Layer What it actually does Is it a boundary?
System prompt (orchestrator.v1.system.md, MasterOrchestratorService) Instructs the model: “you MUST first call the confirmAction tool … BEFORE invoking the domain agent.” No — a prompt instruction the model can ignore or be injected around.
confirmAction frontend tool + ToolCallClassifier.RequiresApproval RequiresApproval returns true only for the literal string "confirmAction". AguiStreamPipeline sets a stream metadata flag from it. No — it flags a UI card. It never blocks a backend mutating tool from executing.
Finance money tools (PaymentTools, InvoiceTools, LedgerTools) Registered directly, e.g. yield return AIFunctionFactory.Create(tools.CapturePayment, name: "finance_capture_payment"); Comment reads “Mutating — approval enforced via the confirmAction frontend tool.” No — the comment asserts an enforcement that the registration does not provide. If the model calls the tool, it runs.
Proposal pipeline (Spec 030) A real server-side approve-then-execute boundary, via IProposalHandler keyed by ProposalType. Yes — but only FLG annotations and insights flow through it. No money tool does.

Three consequences follow:

  • Money can move without a server-verified human decision. A prompt injection, a model error, or a future agent surface that doesn't render confirmAction can drive finance_capture_payment straight to IPaymentService.CapturePaymentAsync. The ledger is the source of financial truth; nothing in the tool path guarantees a human authorised the posting.
  • The control is unevenly applied and unenforceable. Whether a mutation is gated depends on the model choosing to emit confirmAction and on the active client rendering it. Voice and any non-AG-UI surface have no equivalent, which is why voice v1 is restricted to read-only tools as a workaround.
  • The docs give false assurance. A reader (human or agent) trusts the CLAUDE.md claim and reasons as if mutations are gated. Spec 023 itself names this: “Prompt instructions and frontend UX are not a security boundary.”

3. Two mechanisms, one principle

AONIK already contains the two primitives needed to fix this. They were designed independently and at different times, but they express the same principle from two angles: the gated/handler code is the only path that reaches the domain service.

Spec 023 decorator Spec 030 dispatcher
Status Unbuilt markdown proposal Shipped and in use
Shape ApprovalRequiredAIFunction wraps an AIFunction; intercepts InvokeAsync; waits for a decision before calling the inner tool. IProposalHandler keyed by ProposalType; runs domain logic when a durable Proposal is approved.
When the human decides In-band — within the agent turn, synchronously. Out-of-band — later, from the approvals UI (or in-session, once this spec lands).
Durability Transient consent tied to one tool call (plus an audit row). Durable row that survives the turn, the session, and process restarts.
Right for Reversible, fast, low/medium-stakes writes the user wants done “now.” Money movement and anything that must be auditable, deferrable, and durable.

Neither alone is sufficient. The decorator alone would force money movement into a transient, in-process wait — wrong for an operation that may be approved by a different operator hours later and must never silently re-run. The dispatcher alone would force every trivial “save this note” mutation through a durable proposal row and an approvals queue — far too heavy, and it offers no in-band path for the everyday writes a conversational agent should just do after a quick confirm.

The synthesis: one decorator at the tool boundary, whose behaviour is selected by the tool's risk tier. Low and medium tiers resolve in-band (the decorator's own consent flow); the high tier defers to the durable proposal pipeline (the decorator becomes a proposal-marshaller and never calls the inner tool). Both tiers share one front-door service and one audit substrate, so a tool author attaches behaviour in one place and the routing is automatic.

4. Risk-tier model & routing

Risk tier is a property of the tool, declared at registration, not a property of the agent. (Today AgentConfigurationService.IsMutatingToolName assigns a tier to the agent via an incomplete verb heuristic — that stays only as a seed/lint, see §7.2.) Four classes:

ClassDefinitionDecorator behaviour
Read only No state change. get_, list_, search_, describe_, summarize_, graph traversal. Not wrapped. Executes directly, as today.
Low Reversible personal-state writes with no financial effect and no cross-party impact. Save a memory/preference, dismiss an insight, rename/retag a personal label. Records a ToolApprovalRequest, auto-approves, runs the inner tool in-band, surfaces a non-blocking “done” card. No human wait.
Medium Real domain writes that are reversible and do not move money or post to the ledger. Create invoice/bill, update budget, recategorise a transaction, add a line to a draft. Creates a ToolApprovalRequest, publishes an approval card, blocks the turn awaiting an explicit decision (short timeout), then runs the inner tool in-band only if approved. Requires fresh user presence (step-up).
High Money movement, ledger posting, refunds/payouts/transfers, or any external partner API call. Capture/cancel payment, pay bill, mark invoice paid, post journal entry, partner remittance. Never invokes the inner tool. Creates a durable Proposal (status Proposed), publishes an approval card, returns a “queued for approval” result to the agent. Execution happens only inside the Spec 030 dispatcher's IProposalHandler once the proposal is approved.

4.1 The routing rule, in one line

If a tool can move money, post to the ledger, or call a partner — it is High and must become a Proposal. Everything else that writes state is Medium (confirm in-session) unless it is a trivial reversible personal-state write, which is Low (audit-only). Anything not classified is treated as High and the build fails — fail closed.

4.2 Why this split

  • Money movement is inherently durable and deferrable. It may be approved by a different authorised operator (B2B), minutes or hours later; it must survive a process restart; and a failed attempt must never silently re-run. Those are the properties of a Proposal row, not an in-process await. Forcing money through the in-band decorator would be a regression dressed as a feature.
  • Everyday domain writes should feel conversational. “Create an invoice for £1,250” should complete in the turn after one confirmation, not land in an approvals queue. Medium tier preserves the responsive UX the confirmAction card was reaching for — but now the wait and the decision are enforced on the server.
  • Trivial writes shouldn't nag. Saving a preference or dismissing an insight is reversible and carries no financial weight. Gating it behind a blocking confirmation trains users to approve reflexively, which erodes the value of the medium/high prompts. Low tier audits the action and moves on. (This preserves today's deliberate exemption of user_memory_save from confirmAction, while still recording it.)
Tier is a floor, not a ceiling A tool author may classify up (mark a Medium tool High because the tenant's policy is conservative) but never down below the rule in §4.1. Money movement is High, full stop. The classification manifest is reviewed as a security artefact (see §7.2).

5. Scope (in / out)

5.1 In scope

  • New ApprovalRequiredAIFunction — the single tier-driven decorator over AIFunction, in Aonik.Agents. Preserves the inner tool's name, description, and JSON schema so the model sees an unchanged tool.
  • New IToolApprovalService — the unifying front door. Given a gated invocation, routes by tier: auto-approve (Low), in-band wait (Medium), or marshal-to-Proposal (High). Returns a uniform ToolGateOutcome.
  • New ToolApprovalRequest entity + EF configuration in the owning module; DbSet added to AonikDbContext (migration via the single stream only). Audit/correlation record for every gated call; for High it carries the spawned ProposalId.
  • New IToolApprovalGateway — transport-neutral bridge that publishes an approval card to the active client (AG-UI SSE / voice Voxa envelope) and routes the decision back. Presentation only; never decides authorisation.
  • New Per-module tool classification manifest (IToolApprovalManifest) declaring each tool's tier + ToolApprovalOptions (ActionKind, SummaryTemplate, RequiresFreshUserPresence, optional ProposalType for High). Aggregated by a central IToolClassification.
  • New Fail-closed composition seam. A central gate applied at every *AgentDescriptor.GetTools that wraps mutating tools, passes read-only tools, and throws for unclassified tools — making an ungated mutation structurally impossible to expose.
  • Edit FinanceAgentDescriptor.GetTools (and any other descriptor exposing mutating tools) to route through the gate. Remove the false “approval enforced via confirmAction” comments from PaymentTools / InvoiceTools / LedgerTools.
  • New IProposalHandler implementations in Aonik.Finance for each migrated High tool (capture/cancel payment, mark invoice paid, ledger posting). These become the only code path to the corresponding IPaymentService / ledger method.
  • Edit Precondition Split ProposalStatus into Proposed → Approved → Applied / Failed (with Rejected terminal). Mandated by Spec 030 §6.4 before any money-movement proposal type. See §8.1.
  • Edit Precondition Replace the blanket AdminUserPolicy on /ai/proposals/{id}/approve with policy-based authorisation (IProposalApprovalPolicy) over actor / ownership / tenant / risk tier / proposal type. Mandated by Spec 030 §3.2. See §8.2.
  • Edit In-session approval surface: allow the requesting user to approve a freshly-created High proposal from within the active session, routing the decision through the same policy + dispatcher path as the queue.
  • Edit confirmAction / ToolCallClassifier / AguiStreamPipeline: demote confirmAction to a presentation surface over a server-owned ToolApprovalRequest / Proposal; the frontend decision routes to IToolApprovalService.DecideAsync.
  • New Unit, integration, and safety tests (see §13).

5.2 Out of scope

  • Spoken approval. Voice renders and collects the decision through the existing Voxa toolCall envelope; no “say yes to approve.” (Per Spec 023 non-goals.)
  • Multi-approver / segregation-of-duties beyond “self or one authorised operator.” Q2 requires that a High proposal be approvable by the requesting user or an authorised operator (B2B). Richer N-of-M workflows, maker-checker thresholds, and delegation are a later spec.
  • Background retry / dead-letter for failed money proposals. A Failed proposal is terminal; retry means raising a new proposal (operator/user-driven). An outbox-backed retry pipeline is separate work. (Note: Spec 030 ships an outbox for integration events; reusing it for proposal execution retry is explicitly deferred.)
  • Redesigning domain services. This spec gates access to IPaymentService, the ledger, etc.; it does not change their internals or invariants.
  • New proposal types beyond the money-tool migration. FLG/insights stay working; the Finance money tools are migrated; net-new proposal types are their own specs built on this substrate.
  • Per-tenant tier overrides at runtime. Tiers are declared in code/manifest in v1. A tenant-configurable risk policy is a later enhancement (the manifest is the seam it would plug into).

6. Guardrails

Must not change Must follow Ask before
  • The tool name, description, and JSON schema the model sees — the decorator is transparent to the LLM.
  • The IProposalHandler contract and the Spec 030 dispatch flow — this spec feeds it, it does not fork it.
  • The ledger / payment / order invariants — approval sits in front of domain services, never replaces their checks.
  • The single migration stream (AonikDbContext only); ToolApprovalRequest and the ProposalStatus change ship as tool-generated migrations.
  • The wrapped/handler code is the only path to the domain service. For High, the inner AIFunction is never invoked — the IProposalHandler is.
  • Unknown / unclassified mutating tools fail closed — the build fails and the composition seam throws, so an ungated mutation cannot be exposed.
  • Enforcement is transport-neutral: AG-UI, voice, and the admin playground all flow through IToolApprovalService; transports only present and collect.
  • For consumer (Payabo) flows, the approving user MUST equal the requesting user. Tenant boundary is mandatory for every decision.
  • The decorator and dispatcher emit OpenTelemetry spans: aonik.tools.approval (tags tool.name, tool.risk_tier, approval.outcome, approval.request_id, proposal.id) composing with Spec 030's aonik.proposals.dispatch.
  • Classifying any money-moving tool below High.
  • Adding a bounded in-band blocking wait for High tools (the “synchronous money” temptation — see §15).
  • Letting a transport adapter make an authorisation decision instead of presenting one.
  • Adding columns to Proposal beyond the status-model change in §8.1.
  • Reusing a single approval decision for changed arguments (replay).

7. Component design

7.1 One decorator, tier-driven behaviour

ApprovalRequiredAIFunction wraps an inner AIFunction and holds its ToolApprovalOptions (which carry the tier). It does not itself contain tier logic — it delegates to IToolApprovalService and acts on the returned ToolGateOutcome. This keeps the routing in one testable service and the decorator thin. 

namespace Aonik.Agents.Approval;

internal sealed class ApprovalRequiredAIFunction : AIFunction
{
    private readonly AIFunction _inner;
    private readonly ToolApprovalOptions _options;
    private readonly IToolApprovalService _approvals;

    // Transparent passthrough — the model sees the original tool unchanged.
    public override string Name => _inner.Name;
    public override string Description => _inner.Description;
    public override JsonElement JsonSchema => _inner.JsonSchema;

    public override async ValueTask<object?> InvokeAsync(
        AIFunctionArguments arguments,
        CancellationToken ct = default)
    {
        var outcome = await _approvals.GateAsync(
            new ToolGateContext(_inner.Name, _options, arguments), ct);

        return outcome switch
        {
            // Low/Medium, approved: the inner tool IS the domain call. Run it in-band.
            { Decision: GateDecision.ApprovedInline } =>
                await _inner.InvokeAsync(arguments, ct),

            // High: a durable Proposal was created. The inner tool is NEVER called here;
            // the IProposalHandler will execute it on approval. Tell the agent it's queued.
            { Decision: GateDecision.Queued } =>
                ToolGateResult.Queued(outcome.ProposalId!.Value, outcome.Summary),

            // Rejected / expired / failed-to-gate: structured refusal back to the model.
            _ => ToolGateResult.Refused(outcome.Decision, outcome.Reason),
        };
    }
}
The High invariant, made structural For a High tool, _inner.InvokeAsync is unreachable inside the decorator. The domain mutation lives only in the matching IProposalHandler. This is the “expose the proposal-creating tool, never the mutation tool” design, achieved without writing a second proposal-creating function per tool — the decorator is the proposal-creator, and the inner function's metadata (name, schema) is reused as the proposal's payload shape.

7.2 Classification & fail-closed composition seam

Classification is explicit and module-owned. Each module contributes an IToolApprovalManifest mapping its tool names to a tier and options; a central IToolClassification aggregates them. The wrapping is applied at the one place tools are assembled — the descriptor seam — so it cannot be forgotten: 

// Aonik.Finance/Agents/FinanceAgentRegistration.cs (post-change)
private IEnumerable<AITool> GetTools(IServiceProvider sp)
{
    var classification = sp.GetRequiredService<IToolClassification>();
    return classification.GateAll(
        InvoiceTools.CreateAll(sp)
            .Concat(LedgerTools.CreateAll(sp))
            .Concat(PaymentTools.CreateAll(sp)));
}

// IToolClassification.GateAll, per tool:
//   read-only (allow-listed prefix or explicit RO classification) → pass through
//   classified Low/Medium/High                                     → wrap in ApprovalRequiredAIFunction
//   unclassified mutating-looking tool                             → throw ToolNotClassifiedException
public AITool Gate(AITool tool) => _manifest.Classify(tool.Name) switch
{
    ToolClass.ReadOnly        => tool,
    { } c when c.IsMutating   => new ApprovalRequiredAIFunction((AIFunction)tool, c.Options, _approvals),
    _                         => throw new ToolNotClassifiedException(tool.Name),
};

The legacy verb heuristic (IsMutatingToolName: _create_, _archive_, _cancel_, _issue_, _mark_, _capture_) is retained for two jobs only, never as the runtime authority:

  • Seed — it pre-fills a draft tier for a newly added tool so the manifest entry is one edit, not a blank.
  • Lint trip-wire — a startup/build test asserts that any tool whose name matches a mutation verb is not classified read-only, catching misclassification. (The heuristic is intentionally widened in this check to include _update_, _delete_, _apply_, _pay_, _transfer_, _payout_, _refund_, _set_, _override_, _sync_, which the current heuristic misses.)
Why a manifest and not just inline .WithApprovalRequired Spec 023 proposed attaching options inline at registration. That is ergonomic but fails open: a developer who registers a tool the normal way (as every Finance money tool does today) silently ships an ungated mutation. Routing the wrap through a central, completeness-validated classification makes the safe path the only path. Inline options can still be the authoring ergonomics — but the gate, not the call site, is the authority.

7.3 Low & Medium: in-band gating

In-band path (Low / Medium) ──────────────────────────── Agent calls finance_create_invoice(args) ↓ ApprovalRequiredAIFunction.InvokeAsync ↓ IToolApprovalService.GateAsync(ctx) ├─ persist ToolApprovalRequest (tenant, user, thread, agent, run, tool, args-hash, redacted args, summary) ├─ Low? → auto-approve, status Approved, return ApprovedInline (non-blocking "done" card) └─ Medium? → publish approval card via IToolApprovalGateway ├─ require fresh user presence (step-up); short expiry (≈2 min) ├─ await IToolApprovalService.DecideAsync(requestId, decision) │ • approved (same user, fresh) → ApprovedInline │ • rejected / expired / disconnect → Refused └─ replay guard: decision is bound to the args-hash ↓ ApprovedInline → decorator calls _inner.InvokeAsync(args) → domain service runs → result to agent Refused → structured refusal to agent ("not approved"), turn continues

Medium blocks the turn because the user wants the result now and the action is reversible — a bounded wait is acceptable and matches the existing confirmAction mental model. The wait, the identity check, the freshness check, and the replay guard are all server-side. Low never blocks; it exists in the decorator only so the “every mutation is classified and audited” invariant holds without exception.

7.4 High: marshal into a durable Proposal

High path (money movement) ────────────────────────── Agent calls finance_capture_payment(args) ↓ ApprovalRequiredAIFunction.InvokeAsync ↓ IToolApprovalService.GateAsync(ctx) [tier = High] ├─ persist ToolApprovalRequest ├─ create Proposal via IAgentProposalStore.CreateManyAsync: │ ProposalType = options.ProposalType (e.g. "Finance.CapturePayment") │ PayloadJson = serialized tool arguments │ RiskTier = "High", ProposedByAgentId, AiRunId, ImpactSummary │ Status = Proposed ├─ store ProposalId on the ToolApprovalRequest ├─ publish approval card via IToolApprovalGateway (same surface as Medium) └─ return Queued(proposalId) ← inner tool NEVER invoked here ↓ Decorator returns "queued for approval (proposal {id})" → agent tells user it's pending ⋮ (in-session OR later, from the approvals queue) User / authorised operator approves ↓ POST /ai/proposals/{id}/approve (policy-checked — §8.2) ↓ ProposalApprovalService.ApproveAsync ├─ Proposed → Approved (stamp approver + time) [§8.1 status split] ├─ IProposalDispatcher.DispatchAsync → IProposalHandler.HandleAsync │ └─ FinanceCapturePaymentHandler → IPaymentService.CapturePaymentAsync ← the ONLY domain call ├─ Applied=true → status Applied; surface result back into the session └─ throws / Applied=false → status Failed (terminal; retry = new proposal)

The agent's turn does not block on a money decision. The decorator returns immediately with a queued result, and the agent reports “I've prepared the payment capture — it's waiting for your approval.” When the decision lands — in the same session seconds later, or from the approvals queue hours later — the dispatcher executes and the outcome is delivered back into the conversation as a follow-up event (AG-UI tool-result event / voice envelope), not as the original tool call's return value.

The ProposalType for each migrated tool is declared in the manifest (e.g. "Finance.CapturePayment"), and the matching IProposalHandler deserialises PayloadJson back into the domain request and calls the domain service. This is precisely the Spec 030 contract — this spec simply makes the decorator the producer of those proposals.

7.5 IToolApprovalService — the unifying front door

namespace Aonik.Agents.Approval;

public interface IToolApprovalService
{
    /// Routes by the tool's tier. Persists a ToolApprovalRequest for every call.
    ///   Low    → auto-approved, ApprovedInline
    ///   Medium → publish card, await decision, ApprovedInline | Refused
    ///   High   → create Proposal (Proposed), publish card, Queued(proposalId)
    Task<ToolGateOutcome> GateAsync(ToolGateContext context, CancellationToken ct = default);

    /// Records a decision for a pending in-band (Medium) request, or routes a High
    /// proposal decision through ProposalApprovalService. Enforces identity, tenant,
    /// freshness, expiry, and args-hash replay protection.
    Task<ToolApprovalDecision> DecideAsync(
        Guid approvalRequestId, ToolApprovalDecisionInput decision, CancellationToken ct = default);
}

public sealed record ToolGateOutcome(
    GateDecision Decision,          // ApprovedInline | Queued | Rejected | Expired | Failed
    Guid ApprovalRequestId,
    Guid? ProposalId,               // set only for High
    string? Summary,
    string? Reason);

One service, one dependency for the decorator, two persistence substrates behind it: ToolApprovalRequest (the universal audit/correlation row, present for all tiers) and — for High only — a Proposal (the durable execution record). The two stay purpose-built rather than awkwardly merged: the ToolApprovalRequest answers “what did this conversation ask for and who consented”; the Proposal answers “what durable money operation is pending and what executed it.” They are linked by ProposalId.

7.6 confirmAction demoted to presentation

confirmAction stops being the gate and becomes one renderer of a server-owned decision request. Concretely:

  • ToolCallClassifier.RequiresApproval no longer carries enforcement meaning; the server decides via IToolApprovalService. The classifier's confirmAction recognition remains only to route the frontend's card rendering.
  • AguiStreamPipeline surfaces a server-created ToolApprovalRequest / Proposal as the existing confirmAction card shape, so the frontend UX is unchanged.
  • The frontend's approve/reject click routes to IToolApprovalService.DecideAsync — which, for High, calls the policy-checked /ai/proposals/{id}/approve path. The card is a view; the decision is owned by the server.
  • The orchestrator prompt's “you MUST call confirmAction first” instruction is downgraded to guidance about narrating intent; it is no longer load-bearing for safety, because the server enforces regardless of what the model emits.

7.7 Transport neutrality

IToolApprovalGateway is the only transport-aware seam, and it only presents and collects:

  • AG-UI (SSE): approval card surfaced as the existing confirmAction frontend tool event; decision posted back to DecideAsync.
  • Voice (WebSocket / Voxa): approval card as a Voxa toolCall envelope with name: "confirmAction"; the client's toolResult routes to DecideAsync. Because enforcement is now server-side, voice can expose Medium and High tools — lifting the read-only-only restriction for agents whose mutating tools are classified.
  • Admin playground: renders the same payload.

No transport decides whether a mutation runs. A decision arriving over any transport is treated as a request to decide, validated server-side for identity, tenant, freshness, expiry, and args-hash before it has any effect.

8. Mandated preconditions (from Spec 030)

Spec 030 shipped the dispatcher but explicitly deferred two things, naming them hard preconditions for any money-movement proposal type. This spec introduces exactly those proposal types, so both must land with the High path — they are not optional follow-ups.

8.1 Status split: Proposed → Approved → Applied / Failed

Spec 030 §6.4 documents that the three-value enum collapses two distinct facts and must be split before money movement. With money, “a human approved this” and “the system moved the funds” are different states with different recovery semantics.

StateMeaningTransitions to
ProposedCreated by the decorator; awaiting a decision.Approved, Rejected
ApprovedA human/policy approved; execution not yet confirmed.Applied, Failed
AppliedDispatcher ran the handler; it returned Applied = true. Terminal success.—
FailedHandler threw or returned Applied = false. Terminal failure.— (retry = a new proposal)
RejectedDismissed without execution. Terminal.—
Behavioural change vs Spec 030 Spec 030's revert-on-failure rule (handler throws ⇒ status goes back to Proposed) is unsafe for money: it invites an operator to re-approve a capture whose first attempt's outcome is unknown, risking a double movement. For High proposals, a failed dispatch lands in Failed (terminal), not back in Proposed. Recovery is an explicit new proposal after the operator confirms the prior attempt's real outcome with the partner. Low-stakes proposal types (FLG) may keep the revert behaviour; the status field supports both because Approved is now an explicit intermediate.

This is a tool-generated migration against AonikDbContext (add the two enum values; existing rows are unaffected since Approved previously meant approved-and-applied — a data note documents that historical Approved rows predate the split).

8.2 Policy-based authorisation

Spec 030 §3.2 retains a blanket AdminUserPolicy on the approve endpoint “only because the FLG migration is the sole live consumer,” and names policy-based authorisation a hard precondition for money-movement types. The “in-session + queue” approver model (§9) makes it unavoidable: who may approve depends on the actor, the subject's ownership, the tenant, the risk tier, and the proposal type — not a single role. 

public interface IProposalApprovalPolicy
{
    // Decides whether `actor` may approve `proposal`. Evaluated for both the
    // in-session approval and the approvals-queue endpoint — one rule set, two surfaces.
    Task<ApprovalAuthorization> EvaluateAsync(
        ApprovalActor actor, ProposalAuthorizationContext proposal, CancellationToken ct);
}

v1 rules:

  • Tenant boundary is mandatory — actor and proposal must share a tenant. No cross-tenant approval, ever.
  • Consumer (Payabo) flows: self-approval only. The approver MUST equal the proposal's originating user. An agent acting on a user's own money can only be approved by that user.
  • B2B flows: authorised operator. An operator holding the right permission within the same tenant may approve a proposal raised on that tenant's behalf. (Optional SoD — approver ≠ proposer for high-value — is a manifest/policy knob, defaulted off in v1.)
  • Risk tier / proposal type may demand step-up — fresh authentication within a window before a High approval is accepted.

The /ai/proposals/{id}/approve endpoint drops Policies("AdminUserPolicy") and instead calls IProposalApprovalPolicy.EvaluateAsync; an unauthorized actor gets 403. The in-session approval surface calls the identical policy.

9. Approver model: in-session + queue

A High proposal can be resolved two ways, both routed through the same policy + dispatcher path:

ModeWhoWhenMechanics
In-session The requesting user (self). Immediately, in the active turn/session. The approval card the decorator published is acted on right away; DecideAsync routes to ApproveAsync; the dispatcher runs synchronously and the result is surfaced back into the conversation.
Queue The same user, or an authorised operator (B2B). Later — minutes or hours. The proposal sits Proposed in the approvals queue; approved from the admin/approvals UI via /ai/proposals/{id}/approve; same policy, same dispatcher.

The crucial property: in-session and queue differ only in who triggers the decision and when — the authorisation rule and the execution path are identical. There is no “fast lane” that skips policy for in-session approvals. This is what forces §8.1 (a money decision must persist as Approved independently of whether execution has happened yet) and §8.2 (the “self or authorised operator” rule is policy, not a role gate).

10. Migrating the Finance money tools

The Finance agent's mutating tools move off direct registration. Each is classified and, for High, gets an IProposalHandler. Proposed classification of the current tools (rule from §4.1):

Migration steps per High tool (mechanical, mirrors Spec 030 §7):

  1. Add a manifest entry: tier High, ActionKind, SummaryTemplate, ProposalType.
  2. Write Finance{Action}ProposalHandler : IProposalHandler in Aonik.Finance that deserialises PayloadJson into the existing domain request and calls the existing IPaymentService / ledger method — returning ProposalHandlerResult(Applied: true, AppliedResourceType, AppliedResourceId) on success, Applied: false for expected business failures, and throwing for unexpected ones. Make it idempotent (Spec 030 §6.1): derive deterministic IDs from the payload; treat “already captured” as success.
  3. Register the handler keyed by ProposalType.
  4. The inner AIFunction stays exactly as written — it is the payload-shape source and is never invoked for a High tool.
  5. Delete the false “approval enforced via confirmAction” comment.
No duplicate domain code The handler and the inner tool both ultimately want to call the same domain method. The inner tool's body is reused as documentation of the call shape; the handler does the call. We do not fork IPaymentService — both routes converge on the one domain service, preserving its invariants (the ledger stays the single source of truth).

11. Failure, idempotency & money safety

  • Idempotent handlers (High). The dispatcher may be retried (“approve again” in the queue is still possible for a Proposed row). Handlers must derive deterministic downstream IDs and treat “already done” as success — never Guid.NewGuid() for a captured payment.
  • Failed is terminal for money. Per §8.1, a failed High dispatch does not revert to Proposed. This prevents the double-movement hazard inherent in re-approving an operation whose first attempt's outcome is uncertain.
  • Args-hash replay guard. A decision is bound to a hash of the arguments it was shown. If the agent re-calls the tool with changed arguments, the prior decision does not apply — a fresh request is created. (Spec 023 state-machine rule, retained.)
  • Expiry & disconnect. Medium in-band requests expire on timeout; a socket disconnect before decision cancels or expires the request. High proposals do not expire with the session — they persist in the queue (a separate, longer proposal-level expiry policy is an open decision, §15).
  • Not cross-module ACID. As Spec 030 §6.3 notes, the proposal row and the domain mutation live in different DbContexts. The status split narrows the blast radius (an Approved-but-not-Applied row is an explicit, queryable state for an operator) but does not make it a distributed transaction. Crash mid-handler is operator-recoverable, not auto-recovered, in v1.

12. Security & audit

  • Every gated call is recorded. A ToolApprovalRequest captures tenant, user, thread, agent, AI run, tool name, tool-call id, redacted arguments, args hash, risk tier, summary, decision, deciding user, and timestamps (requested / decided / for High, linked ProposalId).
  • Identity & tenant on every decision. The deciding user must match the expected user (consumer self-approval) or hold the operator permission (B2B), and must share the proposal's tenant. Enforced in DecideAsync and IProposalApprovalPolicy — never in a transport adapter.
  • No data leakage in cards. Approval payloads carry human-readable summaries and material change details (old → new for updates), never secrets, credentials, full account numbers, or unnecessary PII.
  • The wrapper is the only registration path for mutating tools. Enforced structurally by the composition seam (§7.2) and verified by the fail-closed completeness test.
  • Observability. aonik.tools.approval spans compose with Spec 030's aonik.proposals.dispatch so a money movement is traceable end-to-end: tool call → gate → proposal → approval → dispatch → domain call.

14. Acceptance criteria

  • dotnet build Aonik.sln and dotnet test Aonik.sln succeed.
  • Fail-closed: adding a mutating-looking tool (name matches the widened verb set) without a manifest entry fails the build; the composition seam throws ToolNotClassifiedException at agent build time.
  • High never runs in-band: a unit test asserts ApprovalRequiredAIFunction for a High tool never calls _inner.InvokeAsync and instead creates a Proposal and returns Queued.
  • Money flows only through the handler: an integration test drives finance_capture_payment via the agent, asserts no funds move until approval, then approves the resulting proposal and asserts IPaymentService.CapturePaymentAsync ran exactly once and the proposal is Applied.
  • Medium in-band: finance_create_invoice blocks for a decision; approving (same user, fresh presence) runs the inner tool once and returns the invoice; rejecting/expiring runs it zero times.
  • Low audit-only: a Low tool runs in-band without blocking and produces a ToolApprovalRequest in Approved state.
  • Status split: a failed High dispatch lands the proposal in Failed (terminal), not back in Proposed; an FLG proposal still reverts to Proposed on handler failure.
  • Policy: a decision by a different user (consumer flow) or a different tenant is rejected; a B2B operator with the permission is accepted; AdminUserPolicy is no longer the gate.
  • In-session = queue: approving a High proposal in-session and approving the identical proposal from the queue produce the same authorisation checks and the same execution path.
  • Replay: a decision bound to one args-hash does not authorise a call with changed arguments.
  • Transport parity: AG-UI and voice both create a server-side request and wait for a validated decision; neither transport can execute a mutation by itself.
  • Docs: CLAUDE.md no longer claims mutating tools are already wrapped; it describes the tiered model and links this spec.

15. Open decisions

Resolved Tier routing. Three tiers with “money-move = proposal”: Low → inline audited decorator; Medium → in-session confirm with step-up; High (any money movement / ledger posting / partner call) → durable proposal pipeline. Approver model. “In-session + queue”: the requesting user may approve a High proposal in the turn, or it waits in the queue for the same user or an authorised B2B operator — both via one policy and one dispatch path. These two decisions are the spine of the spec.
Open Bounded in-band wait for High? Should a High tool optionally block the turn for a few seconds so a self-approving consumer sees the result inline, instead of always returning “queued”? Tempting for UX, but it reintroduces a synchronous money wait and a partial-failure window inside the agent turn. Recommendation: defer — keep High strictly non-blocking; deliver the result as a follow-up session event.
Open Proposal-level expiry for queued High proposals. A money proposal left unapproved for days may reference stale amounts or a closed order. Should proposals carry an ExpiresAtUtc and auto-transition to a terminal Expired state? Likely yes, but the duration is product/compliance-driven; confirm before implementing.
Open Audit taxonomy. Spec 030 §10 already flags the proposal audit event taxonomy as undecided. This spec adds tool-gate events (tool.gate_requested, tool.gate_auto_approved, tool.gate_decided, tool.gate_queued). Land both taxonomies together against the existing IAuditLogWriter rather than piecemeal.
Open Per-tenant tier overrides. The manifest is code-owned in v1. Some tenants may want a more conservative policy (e.g. Medium → High for invoice creation). The manifest is the natural seam for a tenant-scoped override table, but the configuration surface and precedence rules are deferred.
