Per-tenant module enablement

AONIK is modular by construction (ADR-005) but not yet by operation. Every module is registered for every tenant, the Admin UI's module manifest is a hard-coded list, and nothing on the server knows or cares whether a tenant has a module switched on. This spec makes module enablement a per-tenant, runtime property with one vocabulary end to end: a module catalogue, a persisted enablement row, a tenant-scoped manifest the Admin UI reads, gating of navigation, settings and tabs on that manifest, and a server-side gate so a disabled module is denied, not merely hidden.

1. Summary

This spec adds:

  • One module vocabulary. A ModuleCatalog in SharedKernel with canonical ids, a core flag, and a declared dependency graph. Backend module names, config-pack module lists, and Admin UI module ids all align to it.
  • Persisted per-tenant enablement. A TenantModule row per (tenant, module), seeded by the tenant's config pack at provisioning and toggled by admins afterwards.
  • A real manifest. GET /admin/manifest becomes authenticated and tenant-scoped, and the Admin UI fetches it through the shared API client so the server knows which tenant is asking.
  • UI that follows the manifest. Every sidebar subtree, settings tile and module-owned tab carries a module id and disappears when its module is off. Deep links to a disabled module land on an explanatory page, not a dead route.
  • Hide and deny. A global FastEndpoints pre-processor resolves every endpoint to its module by assembly and returns 403 module.disabled for a tenant that has it off. Agents, scheduled jobs, event handlers and provisioning contributors honour the same set.
Nothing is torn down Every module stays compiled and registered in every host. Enablement is a runtime property of a tenant, resolved per request from a cached read, and can change without a deployment. The current behaviour of every existing tenant is preserved by default (§4).

2. The ask and the success signal

The product requirement, as stated: users should be able to turn specific modules on or off, and that should immediately change the menu system, so that modules not turned on do not have their menu items, settings or configuration available.

Success signal

A host admin opens a tenant and switches Commerce off. On the tenant admin's next navigation the Commerce section is gone from the sidebar, its settings tiles are gone, the Commerce tab on a customer record is gone, and a bookmarked /commerce/products shows "Commerce is not enabled for this organisation" with a link the host admin can act on. Every /commerce/* API call for that tenant returns 403 module.disabled. The commerce agent no longer appears in the agent list, and the low-stock scan job skips that tenant. Switching Commerce back on restores all of it. No deployment happened at any point.

4. Decisions

QuestionDecision
Unit of enablement The tenant, at runtime. Many tenants share one deployment, so a deployment-scoped switch would not deliver the ask. All modules remain compiled and registered in every host; enablement is data. Deployment-level exclusion is out of scope (§18).
Vocabulary One catalogue, canonical kebab-case ids (§5). Backend assemblies declare their id with an assembly attribute; packs use the same ids; UI modules map to backend ids through a requires list rather than being renamed, because one UI module legitimately spans several backend modules and some backend modules have no UI.
Core modules platform, ordering, ai and agents cannot be disabled. Platform is identity and tenancy; Ordering is the order spine both Finance and Commerce stand on (ADR-011) and has no UI or endpoints of its own. AI and Agents are core because the platform is AI-native: every domain module contributes agents, approvals and the run queue are cross-cutting, and a tenant that wants fewer AI surfaces configures its agents (Spec 033) rather than switching the substrate off. Decided 2026-09-02.
Defaults Absent row means the catalogue default, and every module defaults to on. Existing tenants therefore behave exactly as today with no data migration. Provisioning a new tenant with a pack that declares modules writes explicit rows (§13).
Dependencies Declared in the catalogue as hard (the module cannot function without it) or soft (the module degrades gracefully). Hard dependencies are enforced on toggle: the request is rejected with the missing or dependent modules listed. Never cascade silently; the UI shows the cascade and resubmits with the full set.
Hide and deny The manifest hides; the HTTP gate denies. The UI keeps its fail-open behaviour on a transport failure, which is acceptable precisely because the server enforces.
Store A dedicated TenantModule row, not a reserved name in TenantFeature. Modules are a first-class concept with a dependency graph and a UI of their own; the feature store has expiry semantics that do not fit and free-text names. Feature flags remain the within-module layer (a follow-up wires IFeatureManager to real callers).
Who toggles Host admins only. Changing module state is a PlatformAdmin action on the tenant's detail page. Tenant admins can see their module state (read-only, under AdminPolicy) so the disabled-module page can explain itself, but cannot change it. Decided 2026-09-02.
Disabled endpoint status 403 with a typed body { error, code: "module.disabled", moduleId }, not 404. The UI can name the module and offer the fix; an operator debugging a customer report can tell "disabled" from "does not exist" (§19.1).
Principle worth recording "Module enablement is tenant configuration, resolved at runtime, enforced on the server" is a platform-wide rule in the spirit of ADR-013. If the team wants it recorded, it is a one-page ADR-017; this spec does not depend on that.

5. The module catalogue

Aonik.SharedKernel.Modules.ModuleCatalog new is a static, code-defined list of ModuleDescriptor records. It lives in SharedKernel so every host, module and the CLI can read it without a back-pointing dependency on Platform. It is the single source of truth for ids, display names, core status and dependencies; nothing else is allowed to spell a module id as a bare string.

Where the table says "verify", the implementer confirms at the seam and adjusts the descriptor; the graph must remain acyclic, and a startup self-check (with a unit test) proves it.

Assembly attribute

Each module assembly declares its id once: [assembly: AonikModule(ModuleIds.Commerce)] new. Everything that needs to know "which module does this type belong to" (the HTTP gate, agent descriptors, job definitions, event handlers) resolves it from Type.Assembly. This is what makes the gate complete by construction: an endpoint cannot be forgotten, because it lives in an assembly. Aonik.Api, Aonik.Application, Aonik.Infrastructure and Aonik.SharedKernel carry no attribute and are never gated.

IModule hygiene

IModule gains static abstract string Id (returning the catalogue id) and Groups, Workspaces and Documents implement the interface like the other nine. This is cosmetic today but stops the vocabulary drifting again. The FastEndpoints assembly list in Api Program.cs adds Aonik.Subscriptions while we are there.

7. Resolution and caching

IModuleEnablementReader new, Aonik.SharedKernel.Modules:

public interface IModuleEnablementReader
{
    Task<ModuleEnablementSet> GetAsync(Guid tenantId, CancellationToken ct = default);
    Task<IReadOnlyList<Guid>> FilterEnabledTenantsAsync(
        IEnumerable<Guid> tenantIds, string moduleId, CancellationToken ct = default);
}

public sealed class ModuleEnablementSet
{
    public Guid TenantId { get; }
    public IReadOnlySet<string> Enabled { get; }
    public bool IsEnabled(string moduleId) => Enabled.Contains(moduleId);
}

Implemented in Platform by TenantModuleService, which also owns the writes (§9). Resolution:

  1. Start from the catalogue: every module with DefaultEnabled, plus every core module.
  2. Overlay the tenant's rows: an explicit IsEnabled wins over the default.
  3. Force core modules on regardless of rows.
  4. Take the dependency closure: a module whose hard dependency resolved off is reported off, even if its own row says on. The resolved set is always dependency-consistent, so callers never need to reason about the graph.
  • Cache: FusionCache, key tenant-modules:{tenantId}, 60-second TTL with fail-safe, removed on every write. The reader is registered scoped and memoises within a request, so the HTTP gate, the manifest and the agent resolver share one lookup. Rev 3: the TTL was reduced from five minutes because the outbox is dispatched by the Worker, so a second API replica learns of a toggle only when its cache entry expires; one minute is the documented propagation bound.
  • Cross-host invalidation: TenantModulesChangedEvent (§14) is published on write, in-process in the API that handled the toggle and through the transactional outbox for the Worker; a Platform handler removes the cache entry wherever it runs. Until then, the Worker or another API replica may act on the previous state for at most one TTL, which is acceptable.
  • Failure: a database failure surfaces as an exception. The reader never answers "all on" or "all off" on an error; that is the caller's decision, and for the HTTP gate the request fails.

8. The manifest

GET /admin/manifest mutate:

  • AllowAnonymous() is replaced by Policies("AdminUserPolicy"). The tenant is resolved by the existing TenantContextMiddleware from the bearer token and X-Tenant-Id; the endpoint reads it from ITenantProvider.
  • enabledModules now carries canonical backend ids from the reader, sorted.
  • New modules[]: the catalogue projected with state, { id, name, description, isCore, isEnabled, dependsOn }, so the UI can render module management and explain a disabled route without a second call.
  • featureFlags, disabledRoutes and disabledNavItems keep their current shape and, for now, their hard-coded values. Wiring featureFlags to the tenant feature store is the within-module follow-up, not this spec.

useModules() mutate:

  • Replaces the bare fetch() with api.get('/admin/manifest') from src/lib/api.ts, which attaches the bearer token and the selected tenant's X-Tenant-Id. The fetch runs only once the user is authenticated; signed-out routes such as the login page and the setup guides render fail-open with no manifest, so the authenticated call can never bounce a first-run visitor to the login page.
  • The module-level cache is keyed by tenant id and invalidated on tenant switch (alongside invalidateTenantBootstrap) and after a successful module toggle.
  • Fail-open on transport failure stays. A 401/403 from the manifest itself is treated the same way (the app's auth flow handles the session; the server gate handles safety).

Mapping UI modules to backend modules

9. Admin API

EndpointPolicyBehaviour
GET /admin/tenants/{tenantId}/modules new AdminPolicy Returns TenantModuleListResponse(TenantId, Modules[]) where each item is { ModuleId, Name, Description, IsCore, DependsOn[], SoftDependsOn[], IsEnabled, Source: "core" | "default" | "pack" | "explicit", Reason, UpdatedAt, UpdatedBy }. Every catalogue module appears, whether or not a row exists.
PUT /admin/tenants/{tenantId}/modules new PlatformAdmin Body TenantModuleUpdateRequest(Modules[]: { ModuleId, IsEnabled, Reason? }). Validator: known ids only, no core ids, no duplicates. Applied as one transaction; returns the full list as above. Host admins only: a TenantAdmin caller receives 403.

Service rules, evaluated against the resulting set:

  • Enabling a module whose hard dependencies would not all be enabled → 409 { code: "module.dependency_missing", moduleId, missing[] }.
  • Disabling a module that an enabled module hard-depends on → 409 { code: "module.dependents_enabled", moduleId, dependents[] }.
  • Both are thrown as ModuleDependencyException and mapped in ExceptionHandlerConfiguration next to the existing PermissionDeniedException branch.
  • On the GET, the tenancy guard is the same one the /features endpoints use: a tenant admin may only read their own tenant, a cross-tenant read needs the Tenants.Read permission, and an unknown tenant is a 404. The PUT needs no tenancy guard because only PlatformAdmin reaches it.
  • Every successful update writes AuditEventNames.TenantModulesUpdated (with before/after per module and the reason) and publishes TenantModulesChangedEvent.
  • Enabling provisions (Rev 3, review finding P1-1): before anything is persisted, the service runs every ITenantProvisioningContributor whose ModuleName maps to a module that transitions off → on in the resolved set (a dependency the cascade switches on counts), dependencies first, with the ambient tenant switched to the target and the scoped memo pre-seeded with the post-toggle set so Finance's ILedgerAccountContributor gating sees the set being committed. Contributors are idempotent, so re-enabling an already-provisioned module is a no-op. A throwing contributor is audited as AuditEventNames.TenantModulesProvisioningFailed, nothing is persisted, and the request fails with ModuleProvisioningException → 500 { error, code: "module.provisioning_failed", moduleId, contributor }, which the caller may simply retry.
  • One transaction (Rev 3, review finding P1-2): the module rows, the outbox message and the audit row commit together — the audit writer saves through the same scoped context inside an explicit transaction opened under the execution strategy — so a failure between them leaves no half-applied, unaudited state. The cache entry for the tenant is invalidated only after the commit, and always after it, even if the in-process event publish that follows throws.

10.2 Settings tiles and in-page gates

  • SettingsTile gains moduleId? extend: payment gateways and FX → finance; speech → voice; AI policies stay untagged (core). The landing page filters tiles through the manifest; a section with no tiles left is not rendered.
  • useModuleEnabled(moduleId): boolean new for buttons, cards and dashboard widgets that belong to a module (fail-open when the manifest is absent, like everything else).
  • Customer detail tabs keep their existing tab.module gate; the values are already canonical.

10.3 Module management

  • Host view: a "Modules" card on TenantDetailPage lists the catalogue for that tenant with a switch per non-core module, its dependency line ("needs Finance"), the reason field, and who changed it last. Core modules render as locked. The card is editable only for host admins (the same portal-admin resolution the sidebar uses); any other viewer of the page sees it read-only. A 409 from the API renders inline as "Also enable Finance and Ordering?" / "Disable Commerce first" with a one-click resubmit that includes the cascade.
  • Tenant view: the same component behind a new /settings/modules tile ("Modules", section Platform) for the selected tenant, always read-only: it shows what is on and off and says that the host administrator manages it. Only host admins change module state, and only from the tenant detail page.
  • On success both views invalidate the manifest cache so the sidebar updates on the spot, which is the "immediately" in the ask.

10.4 Disabled-module page and API interceptor

  • ModuleDisabledPage new. useModules() already strips a disabled UI module's routes, so a deep link currently falls to the generic "Page Not Found". Instead, the catch-all route asks the registry whether the path belongs to any registered UI module; if it does and that module is disabled, it renders "Commerce is not enabled for this organisation", naming the module from manifest.modules and linking to /settings/modules (or the tenant's detail page for host admins).
  • The API client's error interceptor maps a 403 with code === "module.disabled" to the same page only when the current path belongs to a UI module that requires the refused backend module, so a stale tab that still shows a disabled module cannot keep calling it. Anywhere else, the dashboard for instance, the call is rejected with a user-facing message and no navigation; otherwise a widget calling a disabled module would redirect-loop the home page. Dashboard widgets that call a module's endpoints gate themselves with useModuleEnabled.

10.5 Tests

The repo's vitest environment is node, so the logic is extracted into pure functions with tests: filterNavByModules(sections, enabledSet), resolveEnabledUiModules(registry, enabledIds), and resolveDisabledModuleForPath(registry, manifest, path). Component behaviour is verified manually through the AppHost run (§16).

11. Server-side enforcement (HTTP)

ModuleEnablementMiddleware new, registered once in Api Program.cs immediately after tenant validation and before FastEndpoints, so it runs for every endpoint with no per-endpoint opt-in. Rev 2 refinement: the gate is ASP.NET Core middleware rather than a FastEndpoints pre-processor because Program.cs also maps minimal-API and WebSocket endpoints from module assemblies (the Voice endpoints, for one) that a pre-processor would never see. Routing has already resolved the endpoint by the time the middleware runs, so both kinds are visible through HttpContext.GetEndpoint(). Order of resolution:

  1. Resolve the owning type: FastEndpoints exposes an EndpointDefinition in the endpoint metadata (its EndpointType); minimal APIs expose the handler's MethodInfo (its DeclaringType); delegate-mapped endpoints such as the Voice WebSocket map expose neither, so the middleware falls back to the mapped RequestDelegate's declaring type, walked out of any compiler-generated closure to its outermost type. Then the assembly's AonikModuleAttribute. No attribute (Api-hosted endpoints, Platform) → continue the pipeline.
  2. Core module → continue.
  3. Endpoint carries ModuleGateExempt metadata (Options(x => x.WithMetadata(new ModuleGateExempt()))) → continue. This exists so that an exemption is a visible, reviewable decision rather than an accident; no endpoint is expected to need it at launch.
  4. Tenant not resolved → continue. There is nothing to gate against, and the tenant middleware already decides who may be anonymous. Storefront and other public endpoints that resolve the tenant anonymously by header or subdomain are gated, which is the correct outcome for a shop whose Commerce module is off. Rev 3 (review finding P1-3): this pass-through is deliberate, and its counterpart is IModuleGate (SharedKernel, implemented in Platform over the reader): an anonymous processor that only learns its owning tenant from the payload re-checks enablement the moment it does, before any write — see §12.5.
  5. Reader says disabled → throw ModuleDisabledException(moduleId), mapped to 403 { error, code: "module.disabled", moduleId } in ExceptionHandlerConfiguration.
  • Cost is one cached read per request, shared with the manifest and the agent resolver through the scoped memo.
  • The resolved module id is pushed into the request log scope as ModuleId, so a denied call is one query away in observability.
  • The Commerce.Enabled pack setting is removed from the food-commerce pack; the module row is the only switch.
Why the gate keys on the assembly Route prefixes are not a reliable module boundary here: Platform serves /personal-finance/* routes, Finance serves /admin/*, /host/* and /public/*, and PersonalFinance serves /admin/* too. An endpoint's assembly is the one fact that is always right and can never be forgotten when a new endpoint is added. Per-endpoint attributes would reintroduce the "unclassified tool" failure mode that Spec 032 had to close with a build-time exception.

12. Beyond HTTP: agents, jobs, events, provisioning

12.1 Agents

  • IDomainAgentDescriptor gains string ModuleId extend with a default implementation that reads the attribute from GetType().Assembly. No descriptor needs editing.
  • DomainAgentResolver, ListAgentsEndpoint, PlaygroundStreamingEndpoint, AgentConfigurationService and MasterOrchestratorService filter descriptors through the reader for the current tenant. A disabled module contributes no agent and therefore no tools; the orchestrator cannot delegate to it.
  • Voice pipelines resolve agents through the same resolver and inherit the behaviour.
  • By-name paths go through the same filter: resolving, upserting or deleting an agent override for a disabled module's agent is refused, and the playground gate runs before the response stream starts so the 403 is observable.
  • Approved proposals (Spec 030) are subject to the same rule: before executing, the dispatcher resolves the handler's module from its assembly and the proposal's tenant set; a disabled non-core module fails the proposal with a module.disabled reason in the audit record and returns 403 to the approver, and the handler never runs.

12.2 Scheduled jobs

  • IScheduledJobDefinition (Worker) gains string? ModuleId extend. Jobs that iterate tenants pass their id list through FilterEnabledTenantsAsync; jobs with no tenant loop check the reader per tenant-scoped unit of work.
  • Starting assignment, to be confirmed job by job at implementation: LowStockScan, InventoryReservationSweep, BoxCartAbandonSweep → commerce; SubscriptionJobs → subscriptions; CustomerInsightSnapshot, CustomerInsightAiSummary, FinancialConnectionRecurringSync → personal-finance; DocumentIngestionBackfill → documents; WorkspaceBlobSweep → workspaces; GroupPartyBackfill → groups; CanonicalLedgerBackfill → finance; AiCostGuard → ai; AgeTransition, SafetyRetention, StaleSessionDetector, WorkItemDispatch → none (Platform).
  • The job still fires on schedule; it simply does nothing for tenants that have its module off, and records that in its execution result.
  • Filter before batching. A job that selects a bounded batch of due work must filter the tenant set through the reader before taking the batch; otherwise a disabled tenant's due rows occupy the batch on every run and starve enabled tenants. Review found exactly this on the recurring bank-sync and document-backfill jobs; both now query only rows whose tenant is enabled and never advance a disabled tenant's schedule.

12.3 Integration event handlers

  • ITenantScopedEvent : IIntegrationEvent { Guid TenantId { get; } } new. Existing events that carry a tenant id (TenantProvisionedEvent, the order and party events) adopt it.
  • Handlers are not gated. Rev 3 reversal: an earlier draft had the dispatcher skip a handler whose module was disabled for the event's tenant. Review found that this loses committed work permanently. An integration event announces something that already happened, and both dispatchers record each delivery, so a skip is a discard, not a deferral. Disabling Subscriptions between a usage drawdown committing and its outbox message draining would have dropped the revenue-recognition and provider-cost journal entries for good, leaving entitlement state diverged from the ledger even after the module came back on. Since the ledger is the source of financial truth, a reaction to committed work must complete.
  • The rule this settles: the module gate belongs at the entry points, where new activity is refused (HTTP, agents, jobs, proposals), not on the reaction to work already done. A handler keeping its module's data consistent with what happened is not the module doing new work; refusing to run it corrupts that state rather than protecting it.

12.4 Provisioning and demo seed

  • TenantProvisioner resolves the module set before the contributor loop (today the pack applier runs after it; the module step moves ahead) and skips any ITenantProvisioningContributor whose ModuleName maps to a disabled module. Commerce's own manifest check becomes redundant and can be removed.
  • IDemoSeedContributor is skipped on the same rule, so a demo toggle never seeds sample rows for a module the tenant does not have.
  • ILedgerAccountContributor is skipped on the same rule inside Finance's provisioning contributor, so a disabled module's ledger accounts are not created for the tenant.
  • Ledger accounts are contributed across modules, so enabling a module must run more than its own contributor. Subscriptions supplies its account codes through an ILedgerAccountContributor, and that seam is walked by Finance's provisioning contributor. When a module transitioning on contributes ledger accounts, the owner of that seam runs too, otherwise the toggle reports success and the first posting fails on a missing account code.
  • ModuleName on those seams is aligned to the catalogue ids in the same change (the values are currently PascalCase module names).

12.5 Late-resolving provider callbacks

Rev 3 (review finding P1-3). Four anonymous endpoints in non-core assemblies resolve their tenant from the payload rather than from the request, so the HTTP gate in §11 passes them through. Each now calls IModuleGate.EnsureEnabledAsync(tenantId, moduleId) as soon as the owning tenant is known and before any write, answering 403 module.disabled and persisting nothing:

  • POST /partners/webhooks/{providerCode} — RemittanceOrderService.ProcessWebhookAsync, gated on the located payout's tenant, before the inbox row and before the signature is trusted (finance).
  • POST /personal-finance/account-links/webhooks/plaid and POST /admin/accounts/webhooks/plaid — both Plaid processors, gated on the connection's tenant right after it is found (personal-finance).
  • POST /ai/codeact/call-tool/{nonce} — gated on the tenant carried by the signed nonce, before any budget is spent, answered in the bridge's own envelope (personal-finance).

Left alone on purpose: the storefront and other /public/* endpoints (they resolve the tenant before the middleware, so the HTTP gate already covers them), core-module endpoints, and the read-only circle-invite preview, whose DTO does not expose the owning tenant.

13. Config packs

  • ConfigPackManifest.Modules values become catalogue ids. The applier validates them against the catalogue and fails the pack load on an unknown id.
  • Semantics for a new tenant. A pack that declares modules is authoritative: the declared modules, their transitive hard dependencies and the core modules are on; every other module is off. A pack that declares no modules (the base pack) leaves the catalogue defaults, so a generic tenant gets everything, as today.
  • ConfigPackApplier.ApplyModulesAsync new writes an explicit row for every catalogue module with Source = pack only during initial provisioning (the tenant has no module rows yet and no applied pack version). Every other application, including a re-apply of a newer pack version and the CLI, is additive only: it creates or enables rows for newly declared modules and their dependencies, never creates a disabling row, and never touches an explicit row, matching the applier's existing "never overwrite admin edits" rule. Rev 2 clarification: without this distinction, re-applying a declaring pack to an existing tenant that relied on defaults would silently narrow its module set.
Pack lists must be revised in the same change Today simi.pack.json declares only PersonalFinance and food-commerce.pack.json only Commerce, because nothing consumed the lists. Under the semantics above, a freshly provisioned Simi tenant would have AI, agents, voice, documents and groups off, and its mobile app would start receiving 403 module.disabled. The pack revision is therefore part of P1, not a follow-up. Starting point: simi → personal-finance, groups, documents, ai, agents, voice; food-commerce → commerce, ai, agents (Finance and Ordering are implied). Existing tenants are unaffected either way, because they have no rows and resolve to the defaults.

17. Acceptance criteria

  1. Every module assembly carries an AonikModuleAttribute whose id is in ModuleCatalog; a unit test enumerates the solution's module assemblies and fails on a missing or unknown id.
  2. The catalogue's hard-dependency graph is acyclic, and no core module hard-depends on a non-core one.
  3. A tenant with no TenantModule rows resolves to exactly the set that is enabled today (all modules), so no existing tenant changes behaviour on deploy.
  4. GET /admin/manifest returns 401 unauthenticated and, when authenticated, an enabledModules list that differs between two tenants with different rows.
  5. The Admin UI fetches the manifest with the bearer token and X-Tenant-Id, and re-fetches on tenant switch and after a toggle.
  6. With Commerce off: no Commerce sidebar entry, no Commerce settings tile, no Commerce customer tab, and /commerce/products renders ModuleDisabledPage naming Commerce. With Finance off: Orders, Bill Payments, Remittances, Billing, Ledger, payment-gateway and FX tiles are gone, and Customers remains.
  7. PUT /admin/tenants/{id}/modules returns 403 for a TenantAdmin, rejects a core module (including ai and agents), a missing hard dependency and an enabled dependent with the specified 409 codes, and applies a valid request atomically with an audit event and a published TenantModulesChangedEvent.
  8. For a tenant with a module off, any endpoint in that module's assembly returns 403 { code: "module.disabled", moduleId }; the same request returns its normal response once the module is on again, without a restart.
  9. Storefront endpoints that resolve the tenant anonymously are gated the same way.
  10. A disabled module's agents are absent from /ai/agents, the playground and the orchestrator's delegation set for that tenant.
  11. A scheduled job with a module id skips tenants that have the module off and records the skip in its execution result.
  12. Provisioning a tenant from a pack that declares modules yields explicit rows for every catalogue module, with the declared set plus dependencies plus core on and everything else off; provisioning from the base pack yields no rows.
  13. The revised Simi and food-commerce packs provision tenants whose mobile and storefront flows do not hit module.disabled.
  14. dotnet test Aonik.sln and dotnet build Aonik.sln are green, and the Database.Tests lane covers the index and the row version.

18. Out of scope

  • Deployment-level exclusion (not registering a module's services at all). A future Modules:Disabled host setting could layer on top of the same catalogue, but nothing here needs it.
  • Per-user module visibility. Roles and permissions already govern who sees what within an enabled module.
  • Mobile client manifests for Payabo and Simi. The reader and the HTTP gate apply to them already; a consumer-facing manifest endpoint is a follow-up.
  • The MCP hosts (Aonik.Finance.Mcp, Aonik.Platform.Mcp). They are separate processes serving one configured tenant and do not run the API pipeline; gating their tool lists on that tenant's module set is a small follow-up on the same reader.
  • Entitlement-driven enablement (a plan that turns modules on). Spec 087 can feed the same toggle later.
  • Wiring feature flags beyond leaving the manifest's featureFlags shape intact.
  • Spec 059's navigation consolidation into module-contributed arrays.
  • A pack marketplace, operator-authored modules, or a module DSL.

19. Open decisions

  1. 403 vs 404 for a disabled module's endpoints. The spec picks 403 with a typed code so the UI and operators can name the module. 404 would be the choice if not revealing which modules exist mattered more; it does not for an admin-facing platform.
  2. Tenant-admin self-service. Decided 2026-09-02: host admins only. The PUT is PlatformAdmin; the tenant view is read-only.
  3. Should ai and agents be core? Decided 2026-09-02: yes. Both are core; a tenant that wants fewer AI surfaces configures its agents rather than disabling the substrate.
  4. Finish Spec 059 now? Rendering the module-contributed navigation arrays instead of sidebarNav.ts would make tagging unnecessary, but it is a larger IA change with its own review. The spec tags the live tree and leaves consolidation separate.
  5. Workspaces → Subscriptions: hard or soft? Workspaces imports the Subscriptions contracts for entitlement checks. If those reads degrade to "unlimited" when Subscriptions is off, relax to soft; if they block creation, keep hard.
