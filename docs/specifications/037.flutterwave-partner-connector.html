Spec 037 Status: Draft Size: Large Priority: P1 Domain: Finance / Partners Issue #129

Flutterwave partner connector (real v4 implementation)

Replaces the simulated partner gateway with a real FlutterwavePartnerConnector that executes money movement through the live Flutterwave v4 API. Implements the Spec 031 connector ports — payout (the Spec 036 remittance rail, and Payabo's UK→NG launch wedge), collection, and the webhook translator — against Flutterwave v4's Quote / Initiate / Status / Webhook surface (Issue #129). The spec is grounded twice: against the in-repo abstraction and entities (most of Spec 031's proposed schema has since landed) and against the actual Flutterwave v4 documentation (developer.flutterwave.com). The headline finding: Spec 031 mapped the ports against Flutterwave v3 (static FLWSECK- secret key, /transfers, tx_ref/flw_ref); the current v4 API is materially different — OAuth 2.0 client-credentials tokens, an entity-first resource model (customers, payment methods, recipients), required idempotency keys, AES-GCM card encryption, HMAC-SHA256 webhook signatures, and no bill-payment endpoints at all. §5 walks the v4 API end to end; §6 verifies port-by-port fit and raises every gap.

1. Summary

Spec 031 defined a partner-agnostic abstraction (ports, normalized DTOs, a capability resolver, a webhook translator contract) and proved it with one SimulatedPartnerConnector. That abstraction — and most of the persistence it proposed — is now landed in the tree: Payout carries the full connector shape (ConnectorId, ClientReference, ProviderReference, FX / fee fields, RawResponseJson, PartnerTransactionStatus string status); the PartnerWebhookEvent idempotent inbox exists with both filtered-unique dedupe indexes; and Spec 036 defines the caller — a remittance order service that resolves a route, creates a Payout, posts the ledger debit, then calls IPartnerPayoutConnector.InitiatePayoutAsync and records a Transmission.

What is still simulated is the connector itself. Issue #129 asks for the first real IPartnerConnector — a FlutterwavePartnerConnector supporting Quote, Initiate, Status, and Webhook ingestion against the Flutterwave sandbox, with signature verification, idempotent processing, retryable/non-retryable failure mapping, and tests covering happy path + partner 5xx + timeout. This spec is the implementation plan for that connector, written so an engineer can build it without re-reading the Flutterwave portal.

Headline gap — v3 vs v4 Spec 031's §4 baseline table maps the ports against Flutterwave v3: a static Authorization: Bearer FLWSECK-... secret key, POST /transfers with inline account_bank/account_number, POST /charges, a /bills family, and a verif-hash plaintext webhook header. The live v4 API — the one behind the URL in the task — is a different product: OAuth 2.0 client-credentials tokens (10-minute lifetime), an entity-first resource model (customers → payment-methods → charges; transfers/recipients → transfers), a required X-Idempotency-Key header, AES-256-GCM card encryption, HMAC-SHA256 webhook signatures, and — critically — no bill-payment / airtime endpoints in the v4 surface at all (§5.11). Every design decision below flows from closing that v3→v4 distance. The Spec 031 ports still fit — but several DTOs are missing fields v4 requires (§6).

3.2 Out of scope

  • Flutterwave bill-payment / airtime. The v4 API exposes no bill or airtime endpoints (§5.11). IPartnerBillPaymentConnector stays simulated for Flutterwave; a real bill connector would target Flutterwave v3 or a bill-specialist vendor (eTranzact / Interswitch per Spec 031) under a separate spec.
  • The orchestration caller, the webhook endpoint + inbox + settlement, + ledger wiring — all already shipped (PR #147). RemittanceOrderService + PartnerWebhookEndpoint own quote/confirm/transmit, signature verification, dedupe, inbox persistence, and payout settlement. 037 plugs the connector + translator into those existing seams; it adds no endpoint and no inbox code (§4, §7.5).

  • Schema changes. Spec 031 already landed the entities this connector feeds. This spec adds no migration. The one possible exception — a field for transfer_purpose / sender KYC — is raised as an open decision (§6 G3, §11) and, if taken, rides Spec 036's order-side work, not here.

4. Who calls the connector

The connector is a stateless port implementation. It is called by Spec 036's remittance order service; it does not own orders, ledger, or money-action logging (those live at the caller, per money-action-logging.md — "OrderId lives at the caller; the connector stays vendor-agnostic"). The boundary:

Spec 036 RemittanceOrderService (caller) Spec 037 FlutterwavePayoutConnector (this) ───────────────────────────────────── ────────────────────────────────────────── load locked PricingQuote + ExternalPayoutAccount resolver.ResolvePayoutConnector("Flutterwave") ──▶ (selected here) create Payout(status=Pending, ClientReference) post ledger debit (idempotent, BEFORE the call) MoneyActionLog.PaymentTransmitted scope opens connector.InitiatePayoutAsync(instruction) ──────▶ POST /direct-transfers (+ X-Idempotency-Key) ◀────── PayoutInitiationResult(Reference, Status, Fee, Raw) update Payout + Order, persist Transmission ...later, async (settlement) — ALL shipped in #147... [036] POST /partners/webhooks/flutterwave translator.VerifySignature(env, secret) ProcessWebhookAsync: resolve translator, ──▶ translator.Translate(env) ─▶ PartnerWebhookEvent verify, dedupe (ProviderCode,PayloadHash), ◀─ (037 translator, resolved by ProviderCode) persist inbox, settle Payout/Order/ledger

Two consequences for this spec: (a) the connector returns rich normalized results (reference duality, fee, raw response) and never swallows a failure — it throws a typed FlutterwaveException / TimeoutException so the caller can log PaymentTransmitFailed / PaymentTransmitTimeout; (b) the webhook endpoint, signature verification, dedupe, inbox persistence, and settlement all ship in PR #147 — 037 supplies only the IPartnerWebhookTranslator that ProcessWebhookAsync resolves by ProviderCode and calls. So the translator's contract must be exact: it operates on the raw body + case-insensitive headers the endpoint hands it, and — critically — its Translate must produce a Reference.ClientReference that equals the payout's stored ClientReference (REM-{orderId:N}), or the shipped LocateRemittancePayoutAsync match fails and nothing settles (G17).

Five gaps in the shipped #147 path this connector depends on A code review of PR #147 surfaced five issues in the caller/endpoint that 037 must work around or get fixed upstream — listed so they aren't silently assumed away:
  1. Configured Flutterwave is NOT auto-selected (routing — G18). Confirm calls ResolvePayoutConnector(request.ProviderCode, …); if the request omits ProviderCode, it falls to the capability query, whose FirstOrDefault returns the first-registered connector — Simulated (registered at FinanceModule:140-141, before Flutterwave). So merely setting credentials does not route to Flutterwave, and the chosen code is then persisted on the order. Fix (pick one): require explicit ProviderCode = "Flutterwave" on the confirm request for launch; register Flutterwave before Simulated; or add route priority. The earlier "flips automatically with credentials" claim is withdrawn.
  2. The connector can't reach a raw account or VaultRef (dispatch data — G19). BuildPayoutInstruction puts ProviderBeneficiaryId (or, when absent, the masked identifier) into the destination account field and does not pass VaultRef or a raw number. So real dispatch is only possible when ProviderBeneficiaryId is a usable Flutterwave recipient id — the recipient_id flow is effectively required, not optional; a name-enquiry-only destination (masked id, no token) cannot be paid. Fix: register the beneficiary with Flutterwave first and store its rcp_… in ProviderBeneficiaryId; or have 036 pass VaultRef + the resolvable raw value. But that registration flow doesn't exist yet — SaveBeneficiaryAsync hardcodes IsVerified = false and never calls a connector, and the save DTO excludes raw rail details — so a verify-and-register path (transient raw input → resolve → register → persist) is itself a prerequisite (§7.4.1, G20). (This re-answers the task's beneficiary question — see §5.4.)
  3. HMAC runs over a re-decoded string, not the wire bytes (fidelity — G7 caveat). The endpoint reads the body with StreamReader.ReadToEndAsync() and PartnerWebhookEnvelope.Body is a string, so the translator HMACs UTF8.GetBytes(Body). Fine for clean UTF-8 JSON (the normal case), but a BOM or non-round-tripping byte sequence would break verification. Robust fix: carry byte[] in the envelope (a contract change) or verify in the endpoint over the original bytes. 037 documents the assumption and tests round-trip fidelity.
  4. Translate runs before the signature branch (robustness). ProcessWebhookAsync calls translator.Translate before it checks signatureValid, so a malformed/adversarial unsigned body that throws in Translate becomes a 500 instead of a stored "Failed" row. 037 mitigation (required): FlutterwaveWebhookTranslator.Translate MUST be non-throwing on malformed JSON — return a PartnerWebhookEvent with Unknown status / empty references. Upstream fix: move the invalid-signature branch before Translate.
  5. Dedupe is lookup-then-insert, not race-safe (idempotency). Concurrent redeliveries can both pass the (ProviderCode, PayloadHash) lookup and then collide on the filtered unique index, throwing an uncaught DbUpdateException. Sequential redelivery is a clean no-op; concurrent is not. Upstream fix: catch the unique-violation in ProcessWebhookAsync if #129's idempotency bar must cover concurrent delivery.
Items 1–2 are launch blockers; 3–5 are correctness hardening. 037 owns the item-4 mitigation and the item-3 round-trip test; items 1, 2, 5 are recommended 036/#147 fixes this spec depends on.

5. Flutterwave v4 API walkthrough

Everything below is from the live v4 docs (developer.flutterwave.com, AI index at /llms.txt). Read this once; §6 maps it onto our ports.

5.1 Authentication — OAuth 2.0 client credentials

v4 does not use a static secret key. You exchange a client id + secret for a short-lived bearer token at the Keycloak IdP: 

POST https://idp.flutterwave.com/realms/flutterwave/protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id={CLIENT_ID}&client_secret={CLIENT_SECRET}

→ 200
{ "access_token": "…", "expires_in": 600, "token_type": "Bearer", "scope": "…" }

The token lives 600 seconds (10 minutes); the docs advise refreshing "at least one minute before it expires." The IdP host is the same for sandbox and production — only the API host differs (§5.2). Implication: a connector-internal token provider that caches and refreshes (§7.2) — a concept the current ports and the Plaid precedent do not have (Plaid sends client_id + secret in every request body; there is no token to cache).

5.4 The entity-first resource model — "do we create a customer / beneficiary first?"

This is the question the task raised, and the answer is nuanced. v4 is designed entity-first: you create reusable customers, payment-methods, and transfer recipients/senders, then reference them by id. But for both collection and payout, v4 also offers a direct / orchestration path that accepts the entity inline in one call — so pre-creation is optional, not mandatory.

Recommendation Use the direct / inline path (POST /direct-transfers for payout, POST /orchestration/direct-charges for collection) for a fresh destination, because it matches our stateless PayoutInstruction / CollectionInstruction DTOs. But note what PR #147 actually passes: BuildPayoutInstruction never sends a raw account number — it puts ExternalPayoutAccount.ProviderBeneficiaryId (the connector's reusable token; comment: "real rails resolve from VaultRef at execution") into the destination's account field. So for a saved beneficiary the connector should prefer the orchestrator recipient_id flow (POST /transfers with payment_instruction.recipient_id = ProviderBeneficiaryId), and only fall to /direct-transfers with a real account resolved from VaultRef when there is no beneficiary token. But the /direct-transfers-with-VaultRef fallback isn't actually reachable from the shipped instructions — BuildPayoutInstruction never passes VaultRef or a raw account; a token-less destination arrives only as a masked identifier, which Flutterwave can't pay (G19, §4). So, re-answering the task's question with the shipped caller in hand: yes — for real Flutterwave remittance you must pre-register the beneficiary as a Flutterwave recipient and store its rcp_… in ProviderBeneficiaryId (the destination is also gated on IsVerified). The recipient_id flow is the required path for real dispatch, not just an optimization. Decide in O4.

  • transfer_purpose is a required enum: family_maintenance, personal, education, medical, donation, business, salary_payment, investment, loan_repayment, bill_payment, travel, gift, other. Our PayoutInstruction has no field for it (§6, G3).
  • amount.applies_to chooses whether value is in source or destination currency — this is the "you send" vs "they receive" toggle, central to remittance quoting.
  • The recipient.type discriminator is currency-specific (bank_ngn, bank_usd, bank_eur, mobile_money_ghs, wallet, cash_pickup, crypto) and some types require extra fields (USD/EUR/GBP bank recipients require phone/email/address; EGP requires national_identification). Our flat BankAccountDestination / MobileMoneyDestination / WalletDestination don't carry those (§6, G2).
  • Initiation returns NEW; settlement is asynchronous — the real outcome arrives via the transfer.disburse webhook (§5.9) or by polling GET /transfers/{id}.
  • fee and debit_information.rate_used come back on the transfer response — the realized fee/FX, which maps onto PayoutInitiationResult.Fee and Payout.FxRate/Fee.
Reference round-trip — the load-bearing webhook detail (G13, G17) PR #147 stores ClientReference = "REM-{orderId:N}" (a hyphen + 32 hex) and the shipped LocateRemittancePayoutAsync matches it verbatim (p.ClientReference == reference.ClientReference) against the webhook's translated ClientReference. v4's body reference is documented as 6–42 alphanumeric. So:
  • If Flutterwave accepts the hyphen (verify first in sandbox), send ClientReference as-is; it is echoed in the webhook; the translator maps it straight back → exact match. No problem.
  • If it rejects the hyphen, the connector must sanitize ("REM-…" → "REM…") for the outbound reference — but then the webhook echoes the sanitized string, which ≠ the stored "REM-…", so LocateRemittancePayoutAsync finds nothing and the remittance silently never settles. Fix: carry the original ClientReference in the transfer meta (e.g. meta.aonik_client_reference) and have Translate read it back from the echoed meta (fallback to data.reference) so the inbound ClientReference is reconstructed exactly. Verify Flutterwave echoes meta on transfer.disburse.
The cleaner long-term fix is Spec 036 minting an already-alphanumeric reference (O8). Either way the invariant is hard: the translator's inbound ClientReference MUST equal the stored REM-{orderId:N}, or settlement breaks with no error (G17).

Orchestrator (two-step) alternative: POST /transfers/recipients → save data.id (rcp_…), then POST /transfers with payment_instruction.recipient_id. Same status vocabulary. Use only when reusing a saved beneficiary (§5.4 recommendation).

Status poll: GET /transfers/{id} returns the same status + fee + debit_information + provider_response. Retry: a failed transfer can be re-driven with action: "retry" (or POST /transfers/{id}/retry).

Fee — a one-line, additive, source-compatible change that aligns the quote result with the already-nullable initiation/status results; or (b) always return a concrete fee (a /fees lookup, or a zero-fee sentinel the caller treats as "fee known at execution"). This spec recommends (a); see §3.1 and O3.

5.11 Bills & airtime — not in v4

7.3 Auth header + per-call idempotency (G5, G12)

Split the two concerns. The DelegatingHandler stamps only the request-agnostic Authorization: Bearer (from the token provider). The X-Idempotency-Key is NOT derived in the handler — several request DTOs (PayoutQuoteRequest, AccountResolutionRequest, CollectionRefundInstruction) carry no ClientReference, so a blanket handler would have nothing to hash and would NRE. Instead the connector computes the key per-method (it alone knows the call's semantics) and passes it explicitly to the client helper: 

// FlutterwaveClient — idempotency key is an explicit per-call argument, not handler magic.
Task<T> PostAsync<T>(string path, object body, string idempotencyKey, CancellationToken ct);
Task<T> GetAsync<T>(string path, CancellationToken ct);
// PostAsync stamps X-Idempotency-Key = idempotencyKey, AND X-Trace-Id = idempotencyKey
//   (it is already 32-hex → satisfies X-Trace-Id's alphanumeric 12–255 rule, G12-adjacent).

// The connector decides the key:
//   InitiatePayoutAsync     → IdempotencyKey.FromReference(instruction.ClientReference)        // deterministic
//   InitiateCollectionAsync → IdempotencyKey.FromReference(instruction.ClientReference)        // deterministic
//   RefundCollectionAsync   → IdempotencyKey.From(original.ClientReference, amount, reason)    // deterministic
//   QuotePayoutAsync        → IdempotencyKey.Fresh()   // read-like POST: random, replay-harmless
//   ResolveAccountAsync     → IdempotencyKey.Fresh()   // read-like POST: random, replay-harmless
// FromReference(s) = 32-hex of SHA-256(s) (alphanumeric, satisfies 12–255); Fresh() = hyphen-stripped GUID.

Deterministic keys mean a caller retry of the same instruction re-sends the same key, so Flutterwave de-dupes — which is exactly what makes the shared 5xx-retry resilience handler safe on money-moving POSTs (G11). Read-like POSTs get a fresh random key because a replay of a quote / name-enquiry is harmless. X-Trace-Id has the same alphanumeric-ASCII 12–255 constraint as the idempotency key, so it too must not be the raw ClientReference (which may be short/hyphenated like PAYOUT-1): the client stamps the 32-hex idempotency key as the trace id on POSTs, and a sanitized/padded reference (or a fresh id) on GETs. The client is registered through AddHttpClient<FlutterwaveClient>(…).AddHttpMessageHandler<FlutterwaveAuthHandler>(), inheriting the resilience pipeline from ServiceDefaults.

7.4.1 Beneficiary registration — the missing integration path (G19, G20)

Adding RegisterRecipientAsync to the port is necessary but not sufficient: nothing in the app calls it, and the shipped beneficiary path can't feed it. Concretely, today:

  • PayoutBeneficiaryService.SaveBeneficiaryAsync persists with IsVerified = false hardcoded and only copies a pre-supplied ProviderBeneficiaryId from the request — it never resolves an account or calls a connector. So no saved beneficiary passes the remittance IsVerified gate (RemittanceOrderService.cs:249) on its own.
  • SavePayoutBeneficiaryRequest deliberately excludes raw rail details (only MaskedAccountIdentifier + optional token) per the Spec 031 sensitive-data rule — but Flutterwave /transfers/recipients needs the real account number + bank code (or MSISDN + network). So registration needs a transient raw-details input that is never persisted.

So the prerequisite for G19/G20 is a verify-and-register flow: accept raw rail details transiently → ResolveAccountAsync (name enquiry) → RegisterRecipientAsync (create the Flutterwave recipient) → persist the masked identifier + the returned ProviderBeneficiaryId and flip IsVerified = true. The connector method + its DTOs are defined here; the service / endpoint wiring is the prerequisite (see scope note below). DTOs (§5.3 reuses PayoutDestination as the transient raw carrier — it already holds full values):

7.5 Webhook translator — the only webhook code 037 owns

PR #147 ships the endpoint, signature plumbing, dedupe, inbox persistence, and settlement (§5.9). 037 adds one class: the "Flutterwave" IPartnerWebhookTranslator that ProcessWebhookAsync resolves by ProviderCode and calls. No endpoint, no inbox code. 

internal sealed class FlutterwaveWebhookTranslator : IPartnerWebhookTranslator
{
    public string ProviderCode => "Flutterwave";

    public bool VerifySignature(PartnerWebhookEnvelope e, string signingSecret) {
        var header = LookupIgnoreCase(e.Headers, "flutterwave-signature");   // case-insensitive, G15
        if (string.IsNullOrEmpty(signingSecret) || header is null) return false;
        var computed = Convert.ToBase64String(HMACSHA256.HashData(           // UTF-8 bytes of e.Body (string, §4 item 3)
            Encoding.UTF8.GetBytes(signingSecret), Encoding.UTF8.GetBytes(e.Body)));
        return CryptographicOperations.FixedTimeEquals(
            Encoding.UTF8.GetBytes(computed), Encoding.UTF8.GetBytes(header));
    }

    public PartnerWebhookEvent Translate(PartnerWebhookEnvelope e) {
        // "transfer.disburse" → Category=Payout; map data.status → PartnerTransactionStatus.
        // CRITICAL (G17): Reference.ClientReference MUST reconstruct the stored "REM-{orderId:N}" so
        //   LocateRemittancePayoutAsync matches. Read data.meta.aonik_client_reference first, then
        //   fall back to data.reference. Reference.ProviderReference ← data.id (trf_…).
        // No ProviderEventId needed — the shipped inbox dedupes by PayloadHash (G14).
    }
}
Three hard invariants for the translator (1) Signature: HMAC-SHA256 base64 over UTF8.GetBytes(envelope.Body) — Body is a string under the current endpoint, so this is the decoded-then-re-encoded byte sequence, not the raw wire bytes (§4 item 3) — case-insensitive flutterwave-signature lookup, constant-time compare. The shipped ProcessWebhookAsync passes the secret from Finance:Partners:Webhooks:Flutterwave:SigningSecret and stores the row as Failed (no settlement) when this returns false — so a wrong/empty secret silently blocks settlement; keep it deployed alongside the API client secret. (2) Reference reconstruction (G17): the translated Reference.ClientReference must equal the payout's stored REM-{orderId:N} or LocateRemittancePayoutAsync finds nothing. Carry our reference in the transfer meta on the way out and read it back here. (3) Translate must never throw on a malformed/adversarial body — the shipped ProcessWebhookAsync calls Translate before it branches on signature validity (§4, item 4), so a throw becomes a 500 instead of a stored "Failed" row. Parse defensively; on bad JSON return Category=Payout, Status=Unknown, empty references. Test all three invariants directly — they are the whole webhook contract for 037.

The error classifier maps (HTTP status, Flutterwave error.code) → { retryable, isTimeout } per §5.10. FlutterwaveException carries the type/code/message + Retryable flag so a caller (and the standard resilience handler) can act on it.

7.7 Tests

Mirror PlaidAccountLinkProviderGatewayTests — a nested RecordingHttpMessageHandler : HttpMessageHandler with a queue of canned responses, capturing LastRequest/LastRequestBody. xUnit + FluentAssertions, no DI, no DbContext (the connector is pure I/O). Cases (Issue #129 acceptance point 4):

  • Happy path — InitiatePayoutAsync posts to /direct-transfers with the expected body + an X-Idempotency-Key header derived from ClientReference; maps NEW → Pending, surfaces trf_ as ProviderReference + the fee.
  • Partner 5xx — a queued 500 → FlutterwaveException { Retryable = true }.
  • Timeout — a handler that throws TaskCanceledException/TimeoutException → the connector surfaces a timeout (so the caller logs PaymentTransmitTimeout).
  • 4xx non-retryable — a 422 → FlutterwaveException { Retryable = false } with the parsed error code.
  • Status mapping — GetPayoutStatusAsync maps each v4 status to the normalized enum (table §8).
  • Webhook translator — VerifySignature passes for a correctly-HMAC'd body and fails for a tampered one and for an empty secret; Translate turns a transfer.disburse sample into PartnerWebhookEvent(Payout, …, Succeeded) and reconstructs Reference.ClientReference == "REM-{orderId:N}" from the echoed meta.aonik_client_reference (G17) — the invariant the shipped LocateRemittancePayoutAsync depends on.
  • Resolver — with both registered, ResolvePayoutConnector("Flutterwave") returns the real connector and ResolvePayoutConnector("Simulated") still returns the simulated one (the fallback the remittance service needs); when not configured, only Simulated is registered.
  • Token provider — caches a token, refreshes after expiry, and forces one refresh on a 401.
  • Translate is non-throwing — a malformed/garbage body returns Status=Unknown (no exception), so the shipped pre-signature-branch call can't 500 (§4 item 4).
  • HMAC round-trip fidelity — VerifySignature accepts a body whose signed bytes equal UTF8.GetBytes(Body) (assert a representative transfer.disburse JSON verifies through the string round-trip; §4 item 3).
