Spec 059 Status: Draft Size: Medium Priority: P2 Domain: AdminUi / Commerce

Commerce admin surface — module, navigation & the vertical-labeling seam

Gives Aonik.Commerce a real presence in the production admin UI (src/Aonik.AdminUi) — today it has none. Fixes a navigation-plumbing gap discovered in the process (every module already declares a navigation array; the sidebar doesn't read it), scaffolds the Commerce module against the real module contract, defines its nav tree and routes (with one real path collision to avoid), and lays a small, forward-compatible labeling seam so the same engine can later serve a hardware, apparel, or any other maker-vertical tenant without a rewrite. Page-by-page implementation is explicitly out of scope — this spec is the shell everything else hangs on.

1. Summary

Specs 050–057 implemented the maker-operations backend end-to-end (recipes, costing, inventory, suppliers, purchase orders, receipts, planning, production, margin). Spec 058 designed the make-side screens on the design-prototype starter kit. Neither shipped anything into the real admin UI: src/Aonik.AdminUi has zero Commerce routes, zero Commerce pages, and zero Commerce nav entries today — confirmed by inspection, not inferred.

While grounding that gap, a second one surfaced: the real AdminUi already has a module contract (AdminModule { navigation, routes, panels, breadcrumbs }) that every existing module (Finance, Platform, Core, Agent Command Center, Agent Extensions) implements — but the rendered sidebar doesn't read the navigation field from any of them. It's a static, hand-maintained file (sidebarNav.ts) that happens to duplicate what those modules already declare. Adding Commerce the "correct" way (declare a navigation array) would silently do nothing.

Success signals A new tenant admin sees a "Commerce" section and a "Commerce · Make" section in the sidebar, entirely sourced from modules/commerce/index.ts's own navigation array — no parallel edit to sidebarNav.ts required, because the sidebar now reads useModules().navigation (manifest filtering intact) for every module, existing ones included, with their rendered tree matching today's exactly — reconciled on icon vocabulary and content first, not merely relocated. Commerce's catalog pages live at /commerce/catalog, not colliding with Finance's existing /catalog/*. No page, nav label, or breadcrumb renders a hardcoded string — every Commerce-facing string routes through one small labels module, so a future vertical preset is a data change, not a find-and-replace across components.

2. Context & motivation

The operations-manager day-in-the-life is fully buildable on the backend and fully designed on the starter kit. What's missing is the bridge: real tenant admins running Commerce today have no page to click into. This spec is that bridge's foundation — the navigation, routing, and module registration that every subsequent page-implementation spec will build inside.

It also answers a question raised alongside the navigation request: the maker-ops backend was built and demoed against a food-service tenant (jollof rice, wellness boxes), but nothing in the domain model is food-specific — Ingredient.BaseUnit is a generic unit-of-measure enum (kg/g/L/ml/each), Recipe.YieldUnit is a free string the tenant sets, and the BOM-explosion / costing / procurement / work-order mechanics are standard light-manufacturing primitives. A PC-builder's bill of materials (1 CPU + 1 GPU + 2 RAM + 1 case) explodes through the exact same ExplodeAsync path as a jollof recipe. The gap is entirely in the presentation layer — but it runs deeper than loose strings: it's baked into C# type and method names across every layer (the whole KitchenSheetDto/KitchenSheetDishDto/KitchenSheetComponentDto family, GetKitchenSheetAsync, the /kitchen-sheet route) and into several (at least four) agent tool [Description] attributes reading "food cost per portion," "the kitchen is cooking," and similar. This spec lays the seam that keeps the UI-facing half of that swappable without touching the backend; §8 is explicit about which half it does not reach.

3. Grounding: the real AdminUi today

Verified against src/Aonik.AdminUi directly (2026-07-03), not the starter kit.

  • Shell: React 19 + Vite + Tailwind + React Router (BrowserRouter on web, HashRouter in Electron). Dockview powers one optional sub-feature — a /workspace page where pages/micro-apps can be arranged into dockable panel layouts — it is not the primary app shell. The primary shell is a conventional sidebar (AonikSidebar) + top bar, same visual family as the starter kit.
  • The module contract exists and is real — every registered module implements: 
    interface AdminModule {
  id: string; name: string;
  navigation: NavigationSection[];   // declared by every module — NOT wired to the sidebar (see §4)
  routes: ModuleRouteConfig[];       // IS wired — App.tsx stitches these into React Router
  panels: WorkspacePanelConfig[];    // IS wired — feeds the /workspace Dockview registry
  panelComponents: Record<string, ComponentType<WorkspacePanelRenderProps>>;
  breadcrumbs: ModuleBreadcrumb[];
}
    Registered today, in this exact order (modules/registry.ts's allModules array): core, agent-command-center, agent-extensions, finance, platform. Order is not incidental — the registry's own comment states "Order matters for navigation rendering", because it drives the section-merge iteration order inside getAggregatedNavigation(). Routes and workspace panels ARE module-driven and correctly stitched by the registry.
  • The sidebar is NOT module-driven. components/layout/aonik/sidebarNav.ts exports a static SIDEBAR_NAV array that AonikSidebar renders directly. The file's own comment: "the per-module navigation arrays in modules/*/index.ts are aggregated by getAggregatedNavigation() but are not currently wired into the rendered sidebar — this file is the live source." Finance and Platform both have fully-implemented pages/routes today, and both have their nav items hand-duplicated into SIDEBAR_NAV rather than sourced from their own navigation field — and not a faithful duplicate: see the icon-vocabulary finding immediately below.
  • The two representations have already diverged — confirmed, not hypothetical. sidebarNav.ts spreads Finance's items across three top-level sections with a closed, hand-authored lowercase icon vocabulary (home, receipt, building…). Finance's own navigation field (modules/finance/index.ts) uses a different section shape (one section, childGroups) and a different icon vocabulary — PascalCase Lucide-style names (Building2, ClipboardList, BookOpen…). The renderer, AonikTemplateIcon.tsx, is a closed lookup table keyed to the lowercase vocabulary: const paths = ICON_PATHS[name]; if (!paths) return null;. None of Finance's or Platform's own PascalCase icon names exist in that table today. Reading navigation directly, unreconciled, would render every Finance and Platform icon blank — confirmed by direct inspection of both files, not inferred. §4 addresses this explicitly.
  • Commerce: zero presence. No modules/commerce/, no Commerce routes in the registry, no pages/commerce/, no Commerce nav entries.
  • PersonalFinance: zero presence, and it's deliberate — sidebarNav.ts carries an explicit comment: "Personal Finance nav entry intentionally omitted — no dedicated PF admin surfaces exist today ... Re-add when real PF admin pages land." Out of scope here; noted only because it's the same shape of gap Commerce is in, and confirms "declared in a spec, not yet in AdminUi" is an established, named state in this codebase — not an oversight.
  • Route collision risk, confirmed: Finance already owns the /catalog/* prefix — /catalog/billers, /catalog/categories, /catalog/countries, /catalog/partners (bill-payment billers/categories, remittance corridors/partners). Commerce's product catalog cannot reuse that prefix.
  • No i18n / label-abstraction layer anywhere in AdminUi — zero i18next/intl usage, no locales/ or strings config, for any module. Every existing module hardcodes English strings inline. This is a platform-wide gap, not a Commerce-specific one; §8 scopes what this spec does and does not attempt to fix about it.
  • Nav item shape — the real NavItem type (src/Aonik.AdminUi/src/types/index.ts) is richer than SIDEBAR_NAV's current usage suggests: 
    interface NavItem {
  id: string; label: string; icon: string;
  href?: string; badge?: string; children?: NavItem[];
  audience?: 'host' | 'tenant' | 'all';
  childGroups?: NavItemGroup[]; viewAllHref?: string; viewAllLabel?: string;
}
    badge?: string is confirmed supported — §6's badge notes are not speculative. audience: 'host' gates host-operator-only items (Tenants, Observability, global Settings) out of tenant-admin view — confirmed real, currently used. childGroups also exists and is already used by Finance's and Platform's own navigation fields (a 2-level grouping richer than SIDEBAR_NAV's flat children) — this spec's flat-two-sections nav tree (§6) does not use it, kept as the conservative default; whether AonikSidebar reliably renders childGroups nesting beyond what SIDEBAR_NAV exercises today remains open (§13 T1, narrowed).

4. The navigation-wiring gap, and the decision to fix it

Three ways to add Commerce's nav: (a) hand-edit sidebarNav.ts, matching how Finance and Platform did it — cheapest, but perpetuates the exact duplication the module contract exists to avoid, and leaves Commerce's own navigation field dead on arrival, same as every other module's; (b) leave the gap and give Commerce a special case; (c) fix the wiring — make the sidebar render every module's own navigation, and migrate the four other modules' existing entries into their own navigation fields.

Decision: (c) — but it is not the cheap, purely mechanical move first drafted here. Direct inspection surfaced two compounding problems that make this a real reconciliation, not a data-relocation refactor:

  • Icon vocabulary must be reconciled, not just relocated (§3). Finance's and Platform's own navigation fields already use a PascalCase icon vocabulary that does not exist in AonikTemplateIcon's lookup table — reading them as-is renders every icon in both sections blank. Fix by rewriting navigation.icon values in finance/index.ts and platform/index.ts to the lowercase vocabulary AonikTemplateIcon already supports (cheaper and safer than extending a shared lookup two ways), before switching the sidebar's read source.
  • Content, not just presentation, has diverged for every module — not only Finance/Platform. Core's navigation field labels the root route "Dashboard"; the live sidebar shows "My Space." Agent Command Center's and Agent Extensions' own navigation fields include AI links (/ai/runs, /ai/models, /ai/prompts, /ai/routing, /ai/traces, /ai/agent-extensions) that are not in the live sidebar at all today. Reconciliation covers all five existing modules, not two — either bring each module's navigation field in line with what's actually live today, or treat a specific, reviewed content change as an intentional improvement and say so explicitly; do not assume silence means identity.
  • The sidebar should read through useModules(), not the raw aggregator. modules/useModules.ts already wraps getAggregatedNavigation() with per-tenant manifest filtering — manifest.enabledModules (confirmed: useModules.ts returns manifest.enabledModules) and disabledNavItems. Calling the raw aggregator directly, as first drafted, would bypass that filtering and default every tenant to all build-time-registered modules regardless of what their manifest disables. AonikSidebar must consume useModules().navigation.
  • The backend manifest must add Commerce, or none of this matters. The manifest useModules() filters against comes from GetAdminManifestEndpoint, which currently hardcodes its enabled-modules list without commerce. Registering Commerce in the frontend and fixing the sidebar's read source both do nothing for any tenant if the backend manifest still filters Commerce out. This is a required, coupled backend change, not an AdminUi-only spec.

Doing this now, while there is a concrete reason to touch navigation, is still cheaper than justifying it later as a standalone refactor with no immediate visible motivation — but §11's tasks and §13's risk register now reflect the real shape of the work, not the originally-assumed mechanical move.

6. The Commerce navigation tree

Two flat top-level sections (not nested under "Products" — Commerce is 14 leaf destinations, larger than the entire existing Products group, and nesting three deep risks the same rendering ceiling the starter kit hit for real: its NavPopover renders only one child level. Confirm the real AonikSidebar's depth support before nesting further — §13 T1). No audience restriction on any Commerce item — this is tenant-scoped business functionality, not host-operator tooling. The Route column below is the NavItem.href — a concrete leaf path, never a wildcard (* patterns belong only in route declarations for the router, e.g. matching /commerce/catalog/products; AonikSidebar passes href straight to <Link>, so a literal /commerce/catalog/* href would navigate nowhere useful).

8. The labeling seam (v1) & the vertical strategy (future)

v1 (this spec's scope): one small module, src/Aonik.AdminUi/src/modules/commerce/labels.ts — a single CommerceLabels object of named strings (ingredientSingular, ingredientPlural, recipeSingular, productionOrderVerb, workOrderSheetTitle, …) with English, food-default values. Every new Commerce page — and COMMERCE_NAVIGATION itself, plus COMMERCE_BREADCRUMBS and any panel titles — imports from this module; none inlines a label string it doesn't own. Nav labels are exactly as vertical-sensitive as page copy ("Ingredients," "Recipes," "Production sheet" would all need to change under a Hardware preset), so leaving the nav tree out of the seam would leave the sidebar saying food-flavored terms while page copy had already moved — this costs almost nothing to include now and guarantees the future step (below) is a data change to one file, not a grep-and-replace across a dozen components plus the nav config.

Future (explicitly not built now): a per-tenant vertical preset system —

  • A Commerce-owned tenant-scoped setting (CommerceTenantSettings.Vertical, known-values string: Food | Hardware | Apparel | Generic — Commerce cannot reference Platform's tenancy entities, per the existing architecture boundary, so this lives in Commerce, not Platform).
  • A small number of curated preset label sets, not open-ended per-tenant freeform editing — a handful of internally-consistent presets beats an unbounded surface where "Ingredient" gets renamed but "Kitchen Sheet" doesn't.
  • Resolved at runtime, per logged-in tenant (an API the AdminUi calls), never at deployment/build time — AONIK is multi-tenant, so a food tenant and a hardware tenant may share one running deployment.
  • Genericity is already sound at the mechanics level — Ingredient.BaseUnit (kg/g/L/ml/each) and Recipe.YieldUnit (a free string) need no schema change to serve a PC-builder's BOM. The real gap is vertical-specific attributes (expiry/lot tracking for food; serial/warranty for hardware) — unmodeled today, and deliberately not designed here; it becomes its own spec the day a real tenant needs it.
  • Agent tool descriptions ([Description("...food cost per portion...")] on CommerceAgentTools) are static C# attributes resolved at reflection time, not per-tenant runtime strings — making these vertical-aware is real engineering, deferred until a second-vertical tenant actually has an active agent.

9. Scope (in / out)

In scope

  • The nav-wiring fix (§4): AonikSidebar reads getAggregatedNavigation(); Finance's and Platform's existing entries relocate into their own modules' navigation fields, rendered tree unchanged.
  • Commerce module scaffolding (§5): registered in modules/registry.ts, contributing navigation, routes, panels, breadcrumbs per the established contract.
  • The full route table (§6) wired into React Router — as route declarations pointing at placeholder/skeleton page components, not full page implementations.
  • The CommerceLabels v1 seam (§8).
  • The page inventory (§7) as a hand-off artifact for follow-up implementation specs/tasks.

Out of scope

  • Full page implementations — real data-fetching, forms, tables, drawers against the live Commerce API for all 14 routes. That is comparable in size to Spec 058 itself and belongs to dedicated follow-up work, page-group by page-group, using §7 as the hand-off contract.
  • The vertical preset system (§8, future) — entity, presets, resolution API, tool-description templating.
  • Vertical-specific attributes (expiry/lot, serial/warranty) — no tenant needs them yet.
  • Any change to Core, Agent Command Center, or Agent Extensions' navigation content — only the mechanism they render through changes; their entries move, unchanged, into their own modules.

14. Decisions baked in

  • Fix the nav-wiring gap now, reconciling all five existing modules (icon vocabulary and content, not just relocation) and reading through useModules() plus the backend manifest — not a Commerce-only workaround, and not the purely mechanical move first assumed (§4).
  • Two flat top-level nav sections (Commerce, Commerce · Make), not Commerce nested under Products — sized by leaf-item count, guarded against an unconfirmed depth ceiling (§6).
  • Kitchen Sheet and Goods Receipt are drill-down destinations, not nav items — but Production Orders itself is, exactly as Purchase Orders keeps a nav item while Goods Receipt (its own drill-down) does not (§6).
  • Route prefix /commerce/* throughout, with catalog explicitly /commerce/catalog/* to avoid the confirmed Finance collision (§3, §6).
  • Labels seam ships now; the vertical-preset system does not — cheap infrastructure now, expensive infrastructure deferred until a real second vertical needs it (§8).
  • This spec stops at routing + scaffolding, not full pages — sized against the 050–057 precedent of one coherent slice per spec, not a re-run of Spec 058's full build in one shot (§9).

15. Open design decisions

Open Page-implementation sequencing. Whether follow-up specs implement §7's rows one at a time, grouped by the same phase boundaries Spec 058 used (foundations → sourcing loop → planning/production → margin), or as one larger effort mirroring how 058 itself was built (parallel agents on disjoint page groups).
Open The vertical-preset system itself (§8 future) — entity shape, the initial preset list beyond Food/Hardware/Apparel/Generic, whether presets are hardcoded dictionaries or DB-configurable, and the agent-tool-description templating mechanism. Deferred until a real second-vertical tenant exists to design against.
Open Orders & carts as one route with tabs vs. two leaf nav items — a small UX call left to whoever implements that page, informed by whether Carts and Orders share enough chrome to justify one page.
