Spec 033 Status: Draft Size: Large Priority: P1 Domain: Agents / Platform / Finance

Tenant-managed agent extensibility

Lets a tenant administrator extend their agents — not just re-prompt and toggle them — by uploading MAF Agent Skills, registering remote MCP servers, and declaring HTTP/OpenAPI tools, then testing each in a sandboxed harness before it goes live. Every extension is built on the framework-native primitives that already ship in Microsoft.Agents.AI 1.5.0 (AgentSkillsProvider, AgentSkillsSource, the AIContextProvider seam) and on the existing storage / secret-protection abstractions — and every tenant-contributed tool is routed through the Spec 032 fail-closed approval gate, so a tenant can add capability but can never add an ungated mutation. Tenant-contributed mutating tools default to High (durable proposal); only a platform administrator may lower a tier or enable code execution.

1. Summary

AONIK already lets a tenant configure agents: the Agent entity supports a two-level override model (a global row plus a per-tenant copy) so a tenant can change an agent's instructions, model, and which of the existing code-defined tools are enabled (ToolsetIdsJson is an allow-list). What a tenant cannot do today is add a capability the platform did not compile in. Tools are AIFunctionFactory.Create(...) calls in C#; MCP servers are read from appsettings (Agents:McpServers) as a process-global, stdio-only list; and there is no skills surface wired into any agent at all. The “add additional tools / add additional skills” capability the platform's story implies simply isn't there for a tenant operator.

This spec adds that capability on top of two things that already exist and must not be weakened: the framework-native Agent Skills API that ships in our pinned Microsoft.Agents.AI 1.5.0, and the Spec 032 fail-closed approval gate (IToolApprovalGate.GateAll) that every agent tool already passes through. The design has one spine:

The spine A tenant may add where a capability comes from (an uploaded skill, a remote MCP server, a declared HTTP tool) but never how a mutation is authorised. Every tenant-contributed tool is composed at the same descriptor seam and routed through IToolApprovalGate.GateAll(...), exactly like the built-in Finance tools. An unclassified, mutating-looking tenant tool throws ToolNotClassifiedException at agent-build time — so “a tenant added an ungated money tool” is structurally impossible, not merely discouraged.

Three extension surfaces, one safety model, one test harness:

SurfaceWhat a tenant addsFramework / platform basis
Agent Skills A SKILL.md package (instructions + optional references / assets / scripts) that teaches an agent a procedure via progressive disclosure. AgentSkillsProvider + a tenant AgentSkillsSource over IFileStore, attached via ChatClientAgentOptions.AIContextProviders.
Remote MCP servers An HTTP/SSE Model Context Protocol endpoint whose tools become callable by the tenant's agents. HttpClientTransport (replacing stdio) + a tenant-scoped MCP resolver; tools routed through the gate.
HTTP / OpenAPI tools A declared REST call (method, URL template, parameter schema, auth) exposed as a single tool — no code, no server to run. A declarative AIFunction factory; tools routed through the gate.

All three are inert until a tenant administrator activates them, and a mutating tool from any of them defaults to High — it becomes a durable Proposal and never runs in-band. Lowering a tier, or enabling a skill's executable scripts, requires a PlatformAdmin review. The Admin UI gains a management surface and a sandboxed test harness so a tenant can validate a skill's frontmatter, dry-run an MCP connection and see the tools it exposes (and how each was auto-classified), preview the exact instruction text a skill injects, and exercise a new tool in the playground before it touches production data.

2. Problem: configurable, not extensible

The as-is state, confirmed by reading the code:

CapabilityWhat exists todayGap for a tenant operator
Re-prompt / re-model an agent Agent supports a per-tenant override row (instructions, ModelId, IsActive). — works. This is the configuration ceiling.
Choose which tools an agent has ToolsetIdsJson is an allow-list; FinanceAgentDescriptor.Build(…, allowedToolNames) filters the compiled tools. Can only toggle tools the platform already compiled. A tenant cannot introduce a new one.
Add a new function tool Tools are AIFunctionFactory.Create(tools.CapturePayment, name: "finance_capture_payment") in module C#. Requires a code change + deploy. Not a tenant action by design — arbitrary in-process code on a money-handling monolith is a non-starter.
Add an MCP server McpToolProvider binds Agents:McpServers from IConfiguration; registered as a singleton; StdioClientTransport only. Process-global (not tenant-scoped), config-file-only (not an admin action), and stdio means spawning a local child process — unacceptable for tenant-supplied servers.
Add a skill Nothing. No AIContextProvider / AgentSkillsProvider is wired into any descriptor's Build. The entire skills surface is unused, even though the API ships in our pinned MAF version.

Two consequences:

  • Tenants outgrow the platform. A tenant with a bespoke billing procedure, an internal pricing API, or a domain playbook has no path to teach their agent without filing a platform feature request. The product promises an AI-native platform; today the AI surface is closed at the tenant boundary.
  • The one extension point that exists is unsafe to open to tenants. MCP-by-appsettings is global and stdio-based. Naively letting tenants write to it would let one tenant's server affect all tenants and would run tenant-controlled local processes inside the API host. The safe version is a different shape entirely (tenant-scoped, remote-only, gated), which is most of this spec.

3. What MAF gives us natively

A guiding constraint from the outset: build on Microsoft's own approach, not a bespoke re-implementation. The pinned Microsoft.Agents.AI 1.5.0 assembly already contains the entire skills surface — verified by enumerating the public types in the shipped Microsoft.Agents.AI.xml. We adopt these directly:

MAF type (1.5.0)RoleHow we use it
AgentSkillsProvider An AIContextProvider that performs progressive disclosure: injects a skills catalogue and exposes load_skill / read_skill_resource / run_skill_script. One per agent build, composed from the tenant's enabled skills; attached via AIContextProviders.
AgentSkillsSource (abstract; GetSkillsAsync) Where skills come from. Concrete: AgentFileSkillsSource, AgentInMemorySkillsSource, AggregatingAgentSkillsSource, DeduplicatingAgentSkillsSource, FilteringAgentSkillsSource. We add a TenantBlobSkillsSource : AgentSkillsSource that reads tenant SKILL.md packages from IFileStore, and aggregate it with the global source.
AgentSkillsProviderBuilder Fluent composition: UseSource, UseSkills, UseFilter(Func<AgentSkill,bool>), UseScriptApproval(bool), UseFileScriptRunner, UsePromptTemplate, UseOptions, Build. The assembly point for a tenant's provider; UseFilter enforces the per-tenant enabled set, UseScriptApproval gates scripts.
AgentSkillFrontmatter Name, Description, License, Compatibility, Metadata, AllowedTools; ships ValidateName / ValidateDescription / ValidateCompatibility + max-length constants. Server-side upload validation reuses these validators verbatim; AllowedTools is intersected with the agent's tool allow-list (§8.1).
AgentSkillsProviderOptions ScriptApproval, DisableCaching, SkillsInstructionPrompt. ScriptApproval is on unless a PlatformAdmin enabled scripts for the tenant skill.
ChatClientAgentOptions.AIContextProviders The list of AIContextProviders attached to a ChatClientAgent. The single seam where the skills provider attaches — the only change to the descriptor's Build path (§8.6).
HttpClientTransport / HttpClientTransportOptions (ModelContextProtocol.Client) Remote (streamable-HTTP / SSE) MCP client transport. Replaces StdioClientTransport for tenant MCP servers — no local process spawn (§8.3).
We do not adopt the framework's passive approval MAF 1.5.0 also ships ToolApprovalAgent / ToolApprovalRule / UseToolApproval(…) — a passive approval marker the model can be steered around, analogous to the confirmAction honour system Spec 032 replaced. We deliberately keep AONIK's enforcing ApprovalGatedAIFunction / IToolApprovalGate as the boundary and route tenant tools through it, rather than swapping in the framework's softer surface. Building on Microsoft's primitives does not mean downgrading our enforcement.

4. Three extension surfaces

These three were chosen as the safe, framework-aligned surfaces. The deliberately excluded fourth — uploading arbitrary in-process .NET function tools — is out of scope for the money-handling monolith (§5.2). Each surface trades capability for a different containment story:

SurfaceCapabilityContainmentDefault mutation tier
Skill (instructions only) Procedural knowledge; can reference existing tools via allowed-tools. No code runs; injects text + can only invoke tools the agent already has. n/a (adds no new tool)
Skill (with scripts) Executable helper scripts (data transforms, deterministic calculations). ScriptApproval on; disabled until PlatformAdmin review; sandboxed runner, extension allow-list. script run = approval-gated event
Remote MCP server A whole toolset from an external HTTP/SSE server. Remote-only (no local process); tenant-scoped; per-server egress allow-list; all tools gated. High for any mutating tool
Declarative HTTP / OpenAPI tool One external REST call as a tool. No code; fixed method + URL template; declared parameter schema; gated. High unless an obvious read

5. Scope (in / out)

5.1 In scope

  • New TenantBlobSkillsSource : AgentSkillsSource — reads a tenant's active SKILL.md packages from IFileStore and yields AgentSkills. Composed with the existing global source via AggregatingAgentSkillsSource + DeduplicatingAgentSkillsSource.
  • New Per-request ITenantSkillsProviderFactory — builds the tenant's AgentSkillsProvider (filtered to enabled skills, ScriptApproval set from platform review) via AgentSkillsProviderBuilder, cached per tenant + invalidated on edit.
  • Edit FinanceAgentDescriptor.Build (and the shared descriptor build path): switch to the ChatClientAgentOptions overload and set AIContextProviders to include the tenant skills provider. No change to the GateAll tool composition.
  • New ITenantMcpToolProvider (scoped) + tenant remote-MCP connection management using HttpClientTransport; tools discovered per tenant and routed through IToolApprovalGate.GateAll.
  • New Declarative HTTP/OpenAPI tool factory that turns a TenantHttpTool row into a gated AIFunction with the declared JSON schema.
  • New TenantToolApprovalManifest : IToolApprovalManifest — classifies tenant-contributed tools (MCP + HTTP) from their DB registry so they flow through the same gate as built-ins. Mutating-by-default; tier read from the (platform-reviewed) row.
  • New Tenant-scoped entities: TenantSkill, TenantMcpServer, TenantHttpTool (+ EF configs, DbSets on AonikDbContext, tool-generated migration in the single stream).
  • New FastEndpoints under /ai/tenant-skills, /ai/tenant-mcp-servers, /ai/tenant-http-tools for CRUD, validate, test, submit-for-review, and (PlatformAdmin) approve.
  • New Encrypted credential handling for MCP/HTTP auth via ISettingValueProtector (write-only from the frontend's perspective).
  • New Admin UI workspace panel(s) for managing the three surfaces + a test harness (validate frontmatter, dry-run MCP connect & list, preview injected skill text, sandbox tool invocation), registered in workspace/registry.ts + panelComponents.ts.
  • New Unit + integration tests (gate routing for tenant tools, fail-closed on unclassified tenant tools, frontmatter validation, tenant isolation, credential non-exposure).

5.2 Out of scope

  • Tenant-uploaded in-process .NET tools. Arbitrary compiled code in the API host is excluded for a money-handling monolith. New native function tools remain a platform code change. (Skills scripts are the one narrow, sandboxed, PlatformAdmin-gated exception — and they are off by default.)
  • Local / stdio MCP for tenants. Tenant servers are remote (HTTP/SSE) only; no tenant may cause a local child process to spawn. The existing appsettings stdio path stays for first-party platform servers (e.g. Aonik.Finance.Mcp) and is unchanged.
  • Lowering a tenant mutating tool below High by the tenant. Only a PlatformAdmin may reclassify after review (§7). A tenant can request, not grant.
  • A general code sandbox. v1 ships skill-script execution as “off by default + PlatformAdmin enable + extension allow-list + the framework ScriptApproval hook.” A hardened isolation runtime (container / WASM / seccomp) is its own spec; until it lands, scripts stay opt-in per skill.
  • A public skill marketplace / cross-tenant sharing. Skills are tenant-scoped. Curation, publishing, and ratings are later work.
  • Changing the Spec 032 gate or the proposal pipeline. This spec produces tools for the existing gate; it does not modify ApprovalGatedAIFunction, IToolApprovalService, or the dispatcher.

6. Guardrails

Must not change Must follow Ask before
  • The Spec 032 gate contracts (IToolApprovalGate, IToolApprovalManifest, ToolClassification, ApprovalGatedAIFunction) — tenant tools use them, they are not forked.
  • The descriptor's GateAll(…) tool-composition seam — tenant tools join the same sequence; nothing bypasses the gate.
  • The single migration stream (AonikDbContext only); the three new entities ship as one tool-generated migration.
  • The existing first-party stdio MCP path and Agents:McpServers config — untouched for platform servers.
  • Ledger / payment / order invariants — tenant tools sit in front of, never inside, domain services.
  • Every tenant-contributed tool passes through IToolApprovalGate.GateAll; an unclassified mutating-looking one throws ToolNotClassifiedException — fail closed.
  • Tenant-contributed mutating tools default to High (durable proposal). Only PlatformAdmin may lower a tier.
  • A skill's allowed-tools is intersected with the agent's existing tool allow-list — a skill never grants a tool the agent lacks.
  • Skill scripts are off by default; enabling requires PlatformAdmin review; ScriptApproval stays on for tenant skills.
  • MCP/HTTP credentials are stored ISettingValueProtector-encrypted, decrypted only server-side at call time, and never returned to any client.
  • Everything is tenant-scoped: a tenant sees and uses only its own extensions; ITenantScoped + tenant filter on every entity and connection cache key.
  • Allowing any tenant MCP/HTTP egress to a host not on the platform allow-list.
  • Enabling skill-script execution for a tenant skill (PlatformAdmin action, audited).
  • Classifying a tenant mutating tool below High.
  • Letting a skill or MCP server reference a money-moving built-in tool via allowed-tools.
  • Caching a tenant MCP connection across tenants or beyond a credential rotation.

7. Trust & authorization model

Authority is tiered by risk, mapped onto the existing roles (PlatformAdmin, TenantAdmin, Operations, ReadOnly, …). The rule: a tenant administrator may add and test capability for their own tenant, but anything that runs code, moves money, or reaches a new network destination needs platform review.

ActionRequired roleWhy
Create / edit / upload / delete a tenant skill, MCP server, or HTTP tool (own tenant)TenantAdminTenant owns its own agent surface.
Validate a skill, dry-run an MCP connection, sandbox-test a toolTenantAdminRead-only / sandboxed; no production effect.
Activate a skill / MCP server / HTTP tool (make it live for agents)TenantAdmin, after the row is ApprovedActivation is a tenant choice; eligibility is gated by review.
Approve a tenant MCP server / HTTP tool for activation (validates egress host, default tiers)PlatformAdminNew network egress + tool surface crosses the tenant trust boundary.
Enable executable scripts on a tenant skillPlatformAdminCode execution on the host; the one narrow exception to “no tenant code.”
Lower a tenant mutating tool below HighPlatformAdminTiers are a security artefact (Spec 032 §4.2); a tenant cannot self-grant a faster money path.

7.1 Approval state machine

Tenant extension lifecycle (skill / MCP server / HTTP tool) ─────────────────────────────────────────────────────────── Draft ──submit──▶ PendingPlatformReview ──approve──▶ Approved ──(TenantAdmin)──▶ Active ▲ │ │ │ └──reject──▶ Rejected (reason recorded) │ └──────────────────────── edit (any change re-enters Draft) ◀──── deactivate ───┘

A skill that adds no new tool and no scripts (pure instructions referencing already-allowed tools) MAY auto-approve to Approved on a clean frontmatter validation — it carries no capability the agent didn't already have. A skill with scripts, any MCP server, and any HTTP tool always requires explicit platform review. Editing an Active extension returns it to Draft and deactivates it until re-reviewed (an edit can change behaviour, so prior approval no longer holds).

8. Component design

8.1 Agent Skills: upload → store → source → provider

A skill is a SKILL.md package: YAML frontmatter (name, description, optional license, compatibility, metadata, allowed-tools) plus optional references/, assets/, and scripts/ directories. Lifecycle:

Upload (TenantAdmin) ↓ Validate frontmatter server-side → AgentSkillFrontmatter.ValidateName / ValidateDescription / ValidateCompatibility │ + MaxNameLength / MaxDescriptionLength / MaxCompatibilityLength ├─ allowed-tools ∩ agent tool allow-list (reject tools the agent doesn't have; reject money-moving built-ins) └─ scripts present? → require PlatformAdmin enable; default ScriptsEnabled = false ↓ Store package bytes: IFileStore.UploadAsync(tenantId, skillId, stream, "SKILL.md", contentType) → FileUploadResult (StorageKey, Sha256) ↓ Persist TenantSkill row (FrontmatterJson, AllowedToolsJson, StorageKey, Sha256, ApprovalState=Draft|Approved) ↓ At agent build: TenantBlobSkillsSource.GetSkillsAsync() reads active skills for the tenant from IFileStore ↓ AggregatingAgentSkillsSource(globalSource, tenantSource) → DeduplicatingAgentSkillsSource ↓ AgentSkillsProviderBuilder .UseSource(deduped) .UseFilter(skill => tenantEnabledNames.Contains(skill.Name)) .UseScriptApproval(true) // off only if PlatformAdmin enabled scripts for the skill .Build() → AgentSkillsProvider (an AIContextProvider) ↓ Attached via ChatClientAgentOptions.AIContextProviders (§8.6)

The provider performs MAF's standard progressive disclosure: it injects a compact catalogue of available skills into the agent's context and exposes load_skill / read_skill_resource / run_skill_script so the model pulls detail on demand rather than front-loading every skill body.

The allowed-tools intersection is the key safety property A skill cannot widen an agent's authority. At validation, the frontmatter's allowed-tools is intersected with the agent's existing tool allow-list (Agent.ToolsetIdsJson); any tool the agent doesn't already have is rejected with a clear error, and any money-moving built-in (e.g. finance_capture_payment) is rejected outright. A skill is procedural knowledge over existing capability, never a back door to new capability. New capability comes only from the MCP/HTTP surfaces — which are themselves gated.

8.2 Skill scripts: sandboxed & platform-gated

Scripts are the only place a tenant artefact can execute. Containment is layered:

  • Off by default. A freshly uploaded skill has ScriptsEnabled = false; its run_skill_script calls are refused. The skill's instructions and references still work.
  • PlatformAdmin enable. Turning scripts on is a reviewed, audited PlatformAdmin action recorded on the row — the operator has read the scripts.
  • Framework ScriptApproval stays on for tenant skills (AgentSkillsProviderOptions.ScriptApproval / builder.UseScriptApproval(true)), so even an enabled script's execution is an approval event, not silent.
  • Extension allow-list. AgentFileSkillsSourceOptions.AllowedScriptExtensions / AllowedResourceExtensions constrain what is treated as a runnable script vs an inert resource.
  • Constrained runner. The AgentFileSkillScriptRunner used for tenant skills runs with no implicit network egress, a wall-clock + output-size limit, and a working directory scoped to the skill — never the host filesystem.
Hard limit for v1 Until a hardened isolation runtime lands (its own spec — §14), skill scripts are a deliberately small, opt-in, platform-reviewed surface. If a tenant's need can be met by a declarative HTTP tool or by referencing an existing tool from instructions, prefer that — it runs no tenant code at all.

8.3 Tenant-scoped remote MCP servers

The existing McpToolProvider is a singleton that binds Agents:McpServers and uses StdioClientTransport. Tenant MCP needs a different shape on three axes: scoped (per tenant, not global), persisted (DB rows, not config), and remote (HTTP/SSE, not a spawned process). 

// New: scoped resolver alongside the unchanged singleton McpToolProvider.
internal sealed class TenantMcpToolProvider : ITenantMcpToolProvider
{
    private readonly ITenantProvider _tenant;
    private readonly ITenantMcpServerStore _store;          // reads TenantMcpServer rows
    private readonly ISettingValueProtector _protector;     // decrypts auth at connect time
    private readonly IToolApprovalGate _gate;               // §8.5 — gate every discovered tool

    public async Task<IReadOnlyList<AITool>> GetToolsAsync(IServiceProvider sp, CancellationToken ct)
    {
        var servers = await _store.GetActiveApprovedAsync(_tenant.TenantId, ct);
        var tools = new List<AITool>();
        foreach (var s in servers)
        {
            var transport = new HttpClientTransport(new HttpClientTransportOptions
            {
                Name = s.Name,
                Endpoint = new Uri(s.Endpoint),                        // remote — no process spawn
                AdditionalHeaders = BuildAuthHeaders(s, _protector),   // decrypted here, never sent to a client
            });
            var client = await McpClient.CreateAsync(transport, cancellationToken: ct);
            var discovered = (await client.ListToolsAsync(cancellationToken: ct)).Cast<AITool>();
            // Every MCP tool is classified + wrapped exactly like a built-in (§8.5).
            tools.AddRange(_gate.GateAll(discovered, sp));
        }
        return tools;
    }
}
  • Remote only. HttpClientTransport (verified present in ModelContextProtocol.Client, Core 0.9.0-preview.2) connects to a URL. No tenant input ever becomes a local command line.
  • Egress allow-list. A server's Endpoint host must be on a platform-curated allow-list, checked at PlatformAdmin approval and re-checked at connect. This is the network half of “ask before” in §6.
  • Tenant-scoped lifecycle. Connections are cached per (tenantId, serverId, credentialVersion); a credential rotation or edit invalidates the cache. Never shared across tenants.
  • All tools gated. Discovered MCP tools are passed straight into IToolApprovalGate.GateAll with the tenant manifest (§8.5). An MCP tool whose name looks mutating and isn't classified throws — fail closed, same as a built-in.

8.4 Declarative HTTP / OpenAPI tools

The lightest surface: a tenant declares one external REST call — method, URL template with typed parameters, a JSON parameter schema, and an auth reference — and it becomes a single tool. No server to run, no code to upload. A factory turns the TenantHttpTool row into an AIFunction whose JsonSchema is the declared parameter schema and whose invocation performs the HTTP call (auth injected server-side from the encrypted reference), then the tool is routed through the gate like any other.

Default classification is High for any method that is not a plainly read-only GET; a GET with no side effects may be Read only after PlatformAdmin review. Because the schema is declared, the parameter surface the model sees is fixed — the model cannot smuggle arbitrary fields into the call.

8.5 Reconciling every tenant tool with the Spec 032 gate

This is the spine. The gate already aggregates module manifests and wraps classified mutating tools; we add one manifest for tenant-contributed tools, populated from the DB registry, so tenant MCP/HTTP tools are indistinguishable from built-ins at the gate: 

internal sealed class TenantToolApprovalManifest : IToolApprovalManifest
{
    private readonly ITenantToolClassificationStore _store;   // reads tier per (tenant, toolName)
    public string Module => "Tenant";

    public ToolClassification? Classify(string toolName)
    {
        var row = _store.Find(toolName);          // tenant-scoped lookup
        if (row is null) return null;             // not ours → gate's default rules apply (fail closed if mutating-looking)

        return row.IsReadOnly
            ? ToolClassification.ReadOnly
            // Tenant mutating tools default High; only a PlatformAdmin review can set Medium/Low.
            : ToolClassification.Mutating(new ToolApprovalOptions(row.Tier, row.ActionKind, row.ProposalType));
    }
}

The resulting behaviour matches the built-in Finance tools exactly:

Tenant toolClassificationRuntime behaviour (via existing gate)
Read-only MCP/HTTP tool (e.g. a lookup)Read onlyPasses through; executes directly.
Everyday write, PlatformAdmin-approved downMediumPersists a Pending ToolApprovalRequest; runs in-band once after a server-validated confirm (args-hash bound).
Mutating tool, defaultHighMarshalled into a durable Proposal; never runs in-band; executes only after approval.
Mutating-looking, unclassified—ToolNotClassifiedException at build — the agent won't start exposing it. Fail closed.
Why this is the whole safety argument Because tenant tools enter through the same GateAll seam and the same manifest contract, the Spec 032 invariant — “no mutating agent tool reaches a domain service without a recorded approval decision” — extends to tenant tools for free. We did not build a second approval path for tenant extensions; we made tenant extensions feed the one that already exists and fails closed.

8.6 Wiring into the agent build seam

The descriptor's Build currently calls new ChatClientAgent(chatClient, name, instructions, tools) with no context providers. Two additive changes, both at the one composition point:

  1. Tools: concatenate the tenant MCP + HTTP tools into the same sequence already passed to gate.GateAll(…). No new gating path — they ride the existing one.
  2. Skills: switch to the ChatClientAgentOptions overload and set AIContextProviders to include the tenant's AgentSkillsProvider.
// FinanceAgentRegistration.Build (shape; instructions/model unchanged)
var skills = tenantSkillsProviderFactory.Create(serviceProvider);   // null/empty → no providers added
var options = new ChatClientAgentOptions
{
    Name = Name,
    // existing instructions/model resolution unchanged
    AIContextProviders = skills is null ? [] : [ skills ],
};
var tools = gate.GateAll(
    InvoiceTools.CreateAll(sp)
        .Concat(LedgerTools.CreateAll(sp))
        .Concat(PaymentTools.CreateAll(sp))
        .Concat(tenantMcp.GetTools(sp))        // §8.3 — already gated inside, but GateAll is idempotent for RO/wrapped
        .Concat(tenantHttp.GetTools(sp)),      // §8.4
    sp);
return new ChatClientAgent(chatClient, options /* + tools wired per the options' ChatOptions */);
Keep the change at one seam Both additions live where tools are already assembled. Agents with no tenant skills and no tenant tools build exactly as today (empty provider list, unchanged tool sequence), so the change is inert for tenants that don't use it — and there is still only one place a reviewer must look to confirm gating is applied.

9. Data model & migrations

Three new tenant-scoped entities, all AuditableEntity + ITenantScoped, all Ank-prefixed tables, all added as DbSets on AonikDbContext and shipped in one tool-generated migration (single stream — never hand-authored, per CLAUDE.md).

EntityKey fieldsNotes
TenantSkill TenantId, Name, Version, Description, StorageKey, Sha256, FrontmatterJson, AllowedToolsJson, ScriptsEnabled, ApprovalState, ReviewedByUserId?, IsActive Package bytes in IFileStore; row holds metadata + review state. ScriptsEnabled flips only via PlatformAdmin.
TenantMcpServer TenantId, Name, Endpoint, TransportType (Http/Sse), AuthKind, ProtectedAuthJson, AllowedToolPrefixesJson, DefaultRiskTier, ApprovalState, IsActive, CredentialVersion ProtectedAuthJson is ISettingValueProtector-encrypted. CredentialVersion keys the connection cache.
TenantHttpTool TenantId, Name, Description, Method, UrlTemplate, ParameterSchemaJson, AuthKind, ProtectedAuthJson, RiskTier, ActionKind, ProposalType?, ApprovalState, IsActive One row = one tool. RiskTier defaults High for non-GET; PlatformAdmin may set RO/Medium.

The per-tool classification the TenantToolApprovalManifest reads (§8.5) is derived from TenantMcpServer (its discovered tools inherit DefaultRiskTier unless individually overridden) and TenantHttpTool (its own RiskTier). No separate classification table is needed in v1; if per-MCP-tool overrides prove necessary, a child table is the seam.

10. Admin UI: manage & test

A new workspace app — “Agent extensions” — registered in workspace/registry.ts and panelComponents.ts, alongside the existing AgentConfigPanel / AgentFleetPanel / AiPlaygroundPanel. Three managed lists (Skills, MCP servers, HTTP tools) plus a shared test harness.

10.1 Management

  • Skills: upload a SKILL.md package; see parsed frontmatter, the allowed-tools intersection result, scripts-present + enablement state, and approval state; activate/deactivate.
  • MCP servers: add endpoint + transport + auth (auth is a write-only field — shows “configured”, never the value); see approval state and the discovered toolset with each tool's auto-classification.
  • HTTP tools: declare method / URL template / parameter schema / auth; see the proposed risk tier.

10.2 Test harness (before anything goes live)

  • Validate skill: runs AgentSkillFrontmatter validators + the allowed-tools intersection server-side; shows pass/fail with field-level errors. No persistence required.
  • Dry-run MCP connect: connects with the supplied credentials, lists tools, and renders each tool's name, description, and the tier the gate would assign — without activating the server.
  • Preview injected text: renders the exact skills catalogue / instruction text the AgentSkillsProvider would inject, so the admin sees what the model sees (and can spot prompt-injection-shaped content before it ships).
  • Sandbox invoke: reuses the existing playground (AiPlaygroundPanel / IPlaygroundScenarioService) to call the new tool in a throwaway thread and observe the gate's behaviour — a High tool returns the “queued / requires approval” result rather than mutating, proving the gate is in force.
Testing parity with house workflow The harness is server-truthful: validation, connection, classification, and gating all run the same server code paths that production will, so a “passes in the harness” result means the real wiring works — not a mock. UI verification of these panels follows the project's AppHost + browser workflow.

11. Security & audit

  • Fail-closed gating is the primary control. Every tenant tool routes through IToolApprovalGate.GateAll; unclassified mutating-looking tools throw at build (ToolNotClassifiedException), and tenant mutating tools default High. A tenant cannot add an ungated or self-lowered money tool.
  • Tenant isolation everywhere. Entities are ITenantScoped; skills sources, MCP connections, and tool registries are keyed by tenant; the source factory only ever reads the current tenant's active rows. No cross-tenant skill, tool, or connection reuse.
  • Credentials never leave the server. MCP/HTTP auth is ISettingValueProtector-encrypted at rest, decrypted only at connect/call time, and the API never returns the value — the UI shows a configured/not-configured flag and accepts writes only.
  • Egress is allow-listed. Remote MCP/HTTP destinations must be on a platform-curated host allow-list, checked at approval and re-checked at call, preventing SSRF-style use of a tenant tool to reach internal services.
  • Code execution is the narrow, reviewed exception. Skill scripts are off by default, enabled only by a PlatformAdmin who has read them, kept under the framework ScriptApproval hook and a constrained runner. Enabling is audited on the row.
  • The allowed-tools ceiling. A skill is intersected down to the agent's existing tools and can never name a money-moving built-in, so “upload a skill” can't become “grant the agent capture-payment.”
  • Audit. Upload, edit, submit, approve/reject, activate/deactivate, script-enable, and credential rotation are recorded against the existing audit substrate; gated tool invocations from tenant tools already produce a ToolApprovalRequest / proposal like any other.

12. Preconditions

Two dependencies must be acknowledged because tenant mutating tools rely on the Spec 032 enforcement paths actually executing end-to-end:

  • High execution path. Tenant mutating tools default to High → durable Proposal. Per the shipped ToolApprovalTier.High doc comment, the durable-proposal execution path is deferred from the focused Spec 032 slice (it depends on the Spec 030 dispatcher integration + the ProposalStatus split). Tenant High tools can be created and queued regardless, but they will not execute until that path lands. This spec should ship its High classification behind the same milestone, or explicitly accept “queued but not yet executable” for tenant High tools in an interim.
  • Medium confirm presentation. The Medium in-session confirm card + DecideAsync routing is the still-pending Spec 032 transport/presentation slice (per CLAUDE.md). A PlatformAdmin-lowered Medium tenant tool depends on it to be approvable in-session; until then a tenant tool classified Medium behaves as a persisted-but-unpresented request. High (queued) and Read-only need nothing further.
Verify before implementing Pin the exact remote MCP transport surface in the project's referenced ModelContextProtocol version (the Core 0.9.0-preview.2 client exposes HttpClientTransport / HttpClientTransportOptions; older lines expose SseClientTransport). Confirm the property names (Endpoint, AdditionalHeaders) against the referenced assembly before writing the connection code in §8.3.

14. Acceptance criteria

  • dotnet build Aonik.sln and dotnet test Aonik.sln succeed; the migration applies cleanly from the single stream.
  • Skills upload & inject: a TenantAdmin uploads a valid SKILL.md; it validates, stores via IFileStore, and (when active) appears in the agent's injected skills catalogue via AgentSkillsProvider — verified by the preview showing the injected text.
  • allowed-tools ceiling: a skill naming a tool the agent lacks, or any money-moving built-in, is rejected at validation with a field-level error.
  • MCP remote + gated: a tenant remote MCP server connects via HttpClientTransport, its tools are discovered, and a mutating one is classified High by default and marshalled to a proposal (never run in-band) — proven in the sandbox invoke.
  • Fail-closed for tenant tools: a tenant MCP/HTTP tool whose name looks mutating with no classification causes ToolNotClassifiedException at agent build — the agent does not expose it.
  • HTTP tool: a declared non-GET HTTP tool defaults to High; a PlatformAdmin can reclassify a side-effect-free GET to Read only; a TenantAdmin cannot lower any tier.
  • Scripts gated: an uploaded skill's scripts are inert until a PlatformAdmin enables them; ScriptApproval remains on for tenant skills; enabling is audited.
  • Credentials hidden: no endpoint returns a stored MCP/HTTP credential; the value round-trips through ISettingValueProtector and is usable at connect time only.
  • Tenant isolation: tenant A cannot see, test, or invoke tenant B's skills/servers/tools; the source factory and connection cache never cross tenants.
  • No regression for non-users: an agent with no tenant extensions builds and runs identically to today (empty provider list, unchanged gated tool sequence).
  • Built on MAF: the implementation uses AgentSkillsProvider / AgentSkillsSource / AgentSkillsProviderBuilder and HttpClientTransport directly — no bespoke re-implementation of skills or MCP transport.

15. Open decisions

Resolved Surfaces. Skills + remote MCP + declarative HTTP tools; no tenant in-process .NET code. MCP mode. Remote HTTP/SSE only (no tenant-spawned local processes). Trust. Tiered — TenantAdmin adds/tests; PlatformAdmin approves egress, enables scripts, and lowers tiers; tenant mutating tools default High. Shape. One phased spec (033) on top of the Spec 032 gate, reusing the shipped contracts.
Open Egress allow-list governance. Who curates the permitted MCP/HTTP host list, at what grain (global vs per-tenant), and how a tenant requests an addition? A global list is simplest for v1; per-tenant lists are more flexible but need an approval workflow of their own.
Open Skill-script isolation runtime. v1 is “off by default + PlatformAdmin enable + constrained runner.” The hardened sandbox (process/container/WASM, seccomp, egress policy, resource caps) is deferred to its own spec. Confirm the interim is acceptable, or gate scripts off entirely until the sandbox lands.
Open Skill versioning & rollback. TenantSkill.Version exists, but the upgrade/rollback story (keep N versions? pin an agent to a version? diff on re-upload?) is unspecified. Likely a follow-up once the single-version path is proven.
Open Provider cache invalidation granularity. The per-tenant AgentSkillsProvider and MCP connections are cached for performance. Confirm the invalidation triggers (edit, activate/deactivate, credential rotation, review-state change) and whether invalidation is push (on write) or TTL-based.
Open Can allowed-tools reference tenant MCP/HTTP tools? v1 intersects against built-ins the agent already has. Whether a skill may also reference a tenant's own (gated) MCP/HTTP tool — and how that composes with activation order — needs a decision; default to “built-ins only” unless required.
