Spec 027 Status: Draft Size: Large Priority: P1 Domain: Architecture / Finance

Extract PersonalFinance into its own module (Aonik.PersonalFinance)

Promotes the PersonalFinance subdomain — today a folder hierarchy inside Aonik.Finance — into a sibling module Aonik.PersonalFinance, so the B2C Payabo product evolves independently of Aonik's core money plumbing (Ledger, Orders, Payments, Billing, Pricing, Partners, Catalog). Database physical layout, table names, migration ownership, and the /personal-finance/* HTTP contract all stay unchanged.

1. Summary

Aonik.Finance has accreted seven distinct subdomains. FinanceModule.cs is ~280 lines of registrations, with PersonalFinance making up roughly half the surface area. PersonalFinance is the strongest candidate for a clean module split:

  • It is the entire substrate of one product (Payabo).
  • It owns its own bounded vocabulary (Household, PersonalAccount, PersonalTransaction, Bill, Subscription, DebtRepayment, Budget, Goal, FinancialContext, FinancialLifeGraph, CustomerInsightSnapshot, StatementImport, FinancialConnection).
  • It owns its own AI surface — five agent descriptors plus the CodeAct sandbox plumbing.
  • Its cross-module integration already passes through six SharedKernel.Abstractions.* adapters — it is already pretending to live elsewhere.
  • Its release cadence (Payabo) decouples cleanly from the slower-changing Ledger / Orders / Billing core that powers MyBillAfrica and RemitExchange.

This spec is scoped narrowly: it moves project structure and DI ownership, not database physical layout. PersonalFinance keeps writing to the same physical SQL database with Ank-prefixed tables, migrations continue to flow through AonikDbContext per ADR-005, and the public /personal-finance/* HTTP contract is preserved unchanged so the Payabo mobile / web clients are unaffected.

Success signals dotnet build Aonik.sln succeeds with Aonik.Finance containing no using Aonik.*.PersonalFinance references; the API exposes a byte-identical OpenAPI surface in the /personal-finance/* region; dotnet test Aonik.sln stays green; the Payabo mobile app continues to function against an unchanged base URL.

2. Context & motivation

ADR-005 anticipated this: “module boundaries make selective service extraction feasible if scale requires it.” The architecture is now at that point for one specific subdomain.

Symptom Evidence
FinanceModule.cs is becoming a god-registration ~280 lines, 7 subdomains, ~25 PersonalFinance services registered (lines 122–213 of FinanceModule.cs).
Two release cadences live in one csproj Payabo product churn (FinancialLifeGraph, CustomerInsight, household, commitments) keeps recompiling Ledger and Billing.
Module already half-extracted at the contract layer 6 SharedKernel.Abstractions.* adapters already broker PF’s outbound dependencies on Platform / Ai / Agents.
Distinct AI agent surface 5 agent descriptors are PF-specific: PersonalFinanceAgentDescriptor, FinancialLifeGraphAgentDescriptor, PfInsightsAgentDescriptor, PfForecastAgentDescriptor, PfClassifyAgentDescriptor.

3. Scope (in / out)

3.1 In scope

  • New src/Aonik.PersonalFinance/Aonik.PersonalFinance.csproj (net10.0) with the standard module anatomy.
  • Move all 26 PersonalFinance entities, 24 EF configurations, ~48 services / builders, 24 service contracts, ~10 model contracts.
  • Move 57 user endpoints and 5 admin endpoints under /personal-finance/*.
  • Move 5 agent descriptors, agent tool files, structured-output schemas, and the CodeAct sandbox provider tree.
  • New PersonalFinanceDbContext (sibling to FinanceDbContext) with the 26 PersonalFinance DbSets and the CategorisationRule.Scope == "System" global-entity carve-out.
  • New SharedKernel read contracts (ICustomerOrderHistoryReader, ICustomerInvoiceHistoryReader, ICustomerPaymentHistoryReader) implemented in Aonik.Finance and consumed in Aonik.PersonalFinance.
  • Move PersonalFinance-specific seed phases and the global seed contributor.
  • New tests/Aonik.PersonalFinance.Tests/ project, populated by moving the PF subtree out of Aonik.Application.Tests.
  • Edit Aonik.Api/Program.cs, Aonik.Worker/Program.cs, and Aonik.AppHost to reference the new module.
  • Edit CLAUDE.md, docs/architecture/module-organization.md, and write ADR-006 documenting the split.

3.2 Out of scope

  • No database schema change. Tables keep their names and Ank prefix; no data migration.
  • No EF migration shifted out of AonikDbContext. Canonical migration stream stays.
  • No change to /personal-finance/* URL contract or DTOs visible to mobile / web.
  • No splitting of Ledger, Orders, Payments, Billing, Pricing, Partners, or Catalog.
  • No new microservice or process boundary. The deployable unit is still a single monolith.
  • No renaming of ModuleTablePrefixes or introduction of an AnkPf prefix — all module prefixes resolve to "Ank" today and that stays.

6. Outbound coupling on Orders / Billing / Payments

Critical finding An initial sweep claimed “zero outbound dependencies” from PersonalFinance. That was wrong. Seven PersonalFinance files reach into Aonik.Finance.Entities.{Orders, Billing, Payments}, and at least one of them queries _dbContext.Orders directly. These reach-ins must be resolved via SharedKernel read contracts before the project reference from Aonik.PersonalFinance to Aonik.Finance can be dropped. 9. SharedKernel read contracts

The PersonalFinance insight pipeline and the FinancialLifeGraph loader read Orders, Invoices, and Payments directly today. After extraction they cannot — Aonik.PersonalFinance will not reference Aonik.Finance. Three thin read contracts in SharedKernel resolve this: 

// src/Aonik.SharedKernel/Abstractions/Finance/ICustomerOrderHistoryReader.cs
namespace Aonik.SharedKernel.Abstractions.Finance;

public interface ICustomerOrderHistoryReader
{
    Task<IReadOnlyList<OrderHistoryItem>> GetForCustomerAsync(
        Guid customerId,
        DateOnly fromUtc,
        DateOnly toUtc,
        CancellationToken cancellationToken = default);
}

public sealed record OrderHistoryItem(
    Guid OrderId,
    string OrderType,
    string Status,
    decimal Amount,
    string Currency,
    DateTimeOffset CreatedAt,
    DateTimeOffset? FulfilledAt,
    string? CounterpartyName,
    string? CategoryHint);

Equivalent shapes for ICustomerInvoiceHistoryReader (returning InvoiceHistoryItem) and ICustomerPaymentHistoryReader (returning PaymentHistoryItem). DTOs carry only what PersonalFinance actually consumes — they are not entity projections.

Implementations live in Aonik.Finance and are registered in FinanceModule.ConfigureServices: 

// src/Aonik.Finance/Services/Finance/Readers/CustomerOrderHistoryReader.cs
namespace Aonik.Finance.Services.Finance.Readers;

internal sealed class CustomerOrderHistoryReader : ICustomerOrderHistoryReader
{
    private readonly FinanceDbContext _dbContext;

    public CustomerOrderHistoryReader(FinanceDbContext dbContext) => _dbContext = dbContext;

    public async Task<IReadOnlyList<OrderHistoryItem>> GetForCustomerAsync(
        Guid customerId,
        DateOnly fromUtc,
        DateOnly toUtc,
        CancellationToken cancellationToken = default)
    {
        var fromTs = fromUtc.ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc);
        var toTs   = toUtc.ToDateTime(TimeOnly.MaxValue, DateTimeKind.Utc);

        return await _dbContext.Orders
            .AsNoTracking()
            .Where(o => o.CustomerId == customerId
                     && o.CreatedAt >= fromTs
                     && o.CreatedAt <= toTs)
            .OrderBy(o => o.CreatedAt)
            .Select(o => new OrderHistoryItem(
                o.Id,
                o.OrderType.ToString(),
                o.Status.ToString(),
                o.TotalAmount,
                o.Currency,
                o.CreatedAt,
                o.FulfilledAt,
                o.CounterpartyName,
                o.CategoryHint))
            .ToListAsync(cancellationToken);
    }
}

PersonalFinance switches its callers:

// before — src/Aonik.Finance/Services/PersonalFinance/CustomerInsight/CustomerInsightSourceDataLoader.cs

…
return await _dbContext.Orders

// after — src/Aonik.PersonalFinance/Services/PersonalFinance/CustomerInsight/CustomerInsightSourceDataLoader.cs

19. Decisions baked in

DEC-1 Single migration stream stays in AonikDbContext. ADR-005 and CLAUDE.md mandate it; splitting streams would invite snapshot drift and forfeit the “tool-generated only” guarantee. The cost is a one-way reference Aonik.Infrastructure → Aonik.PersonalFinance, which is acceptable since Infrastructure already references all modules.
DEC-2 Read contracts live under SharedKernel/Abstractions/Finance/, not /PersonalFinance/. Read direction is PF → Finance. Contracts are named for the bounded context they expose, not the consumer.
DEC-3 No AnkPf* table prefix. ModuleTablePrefixes.* already collapses to "Ank" for every module; the prefix is a database-physical concern unrelated to project layout. Keeping tables on Ank avoids data migration and preserves existing query and indexing plans.
DEC-4 No /personal-finance/* URL change. The Payabo mobile app and web app depend on the path. Extraction is a project-structure refactor, not an API redesign.
DEC-5 CodeAct sandbox providers move with PersonalFinance. The three providers exist today to back PF analytical sub-agents specifically. If a future module (e.g. an extracted Pricing) needs CodeAct, the providers can be lifted into a dedicated Aonik.CodeAct runtime module then. Premature extraction would create churn for hypothetical reuse.
DEC-6 Defer splitting Pricing and Billing. The order / payment / ledger triangle is too tightly coupled inside Aonik.Finance for a low-risk split today. PersonalFinance is the highest-payoff, lowest-coupling-cost extraction. Reassess Pricing after this lands.

20. Open design decisions

Open · O-1 CodeAct ownership long term. The CodeAct sandbox plumbing (Hyperlight, ACA Sessions, Null providers) backs PF sub-agents today, but is generic runtime infrastructure that any future analytical agent could reuse. We keep it inside Aonik.PersonalFinance for now (DEC-5), but should revisit if a second consumer appears.
Open · O-2 NuGet pinning strategy. Five PF-specific package references currently live on Aonik.Finance.csproj (Hyperlight ×3, Azure.Identity, Azure.Core). Move them with the module, but should we also introduce Central Package Management (Directory.Packages.props) at the repo root to prevent drift between Aonik.Finance and Aonik.PersonalFinance? Recommend yes, but out of scope for this spec.
Open · O-3 Cutover strategy for downstream consumers. Aonik.Platform.Endpoints.Admin.Customers.ListCustomerInsightsEndpoint references the PF contract by namespace today. Do we change the using statement at the same time the contract moves (single commit), or introduce a transitional re-export from Aonik.Finance? Recommend single-commit cutover — the diff is small, and a transitional shim adds dead weight.
Open · O-4 Test project consolidation. Should Aonik.Application.Tests retain shared base classes / fixtures that PF tests use today, or should those move into Aonik.PersonalFinance.Tests too? Bias: copy what is genuinely PF-only; share what is generic (e.g. TestTenantProvider) via a common test-utilities project (out of scope here, but track as follow-up).
