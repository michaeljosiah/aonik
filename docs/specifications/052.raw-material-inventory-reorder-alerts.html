Spec 052 Status: Draft Size: Medium Priority: P3 Domain: Commerce / Inventory

Raw-material inventory + reorder points + low-stock alerts

Lets the raw-material Ingredients introduced by the maker-operations keystone, Spec 050, actually hold stock, carry a reorder point, and raise a low-stock alert when they run down — the "only 2 kg of rice left" moment on the operations manager's desk. It does this by generalizing the finished-goods InventoryLevel that Spec 042 already ships so one level row can stock either a saleable ProductVariant or a raw Ingredient — reusing the same reserve/commit/release machinery rather than building a parallel one. Everything lives in Aonik.Commerce and references only SharedKernel + Aonik.Ordering — never Aonik.Finance.

1. Summary

Spec 050 gave the maker an Ingredient master and a Recipe that says what a finished product is made of. What it deliberately left out is the next thing the operations manager asks: do we have enough of it, and when do we buy more? This spec answers exactly that — no more. It lets an ingredient carry a stock level, a reorder point, and (optionally) a reorder quantity, and it raises a low-stock alert the moment available stock falls at or below the reorder point.

The design is a generalization, not a rebuild. Spec 042 already has a stock primitive — InventoryLevel (OnHand, Reserved, keyed by ProductVariantId) — plus an InventoryService that reserves, commits, and releases, and an InventoryReservationSweepJob that frees expired holds. Rather than clone all of that for ingredients, this spec widens the key of a level so one row can stock either a finished variant or a raw ingredient, and reuses the existing service and sweep unchanged in behaviour. Two things are genuinely new: the LowStockAlert entity and a Quartz LowStockScanJob that raises it idempotently.

Success signals An operator (or the commerce-agent) can set an ingredient's on-hand quantity and its reorder point, and when consumption drives available stock at or below that point, a single LowStockAlert appears in the existing admin realtime inbox — "Rice: 2 kg on hand, reorder at 5 kg". Re-running the scan does not pile up duplicate alerts (at most one Open per ingredient). Existing finished-goods stock keeps working exactly as before. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering; dotnet test Aonik.sln stays green with new tests over the generalized level, the scan, and alert idempotency.

2. Context & motivation

In the operations manager's day-in-the-life (see Spec 050 §2), between reading the prep list and printing the kitchen sheet sits a recurring interrupt: a low-stock alert — "we're nearly out of rice" — which prompts a reorder. That single moment is what this spec makes real. It is the hinge between the make-side data model (recipes, prep lists) and procurement: an alert is the signal that a purchase order (Spec 053) should be raised, and receiving that PO (Spec 054) is what stocks the ingredient back up and resolves the alert.

The keystone already established that ingredient stock is a distinct source of truth from saleable-variant stock — a Recipe draws down ingredient stock, a Spec 042 Bundle draws down variant stock, and the two never collapse. This spec honours that boundary while still refusing to duplicate machinery: the honest way to have "two kinds of stock that behave the same" is one stock table discriminated by what it stocks, not two parallel tables and two parallel services. So we generalize the level's key and keep a single reservation/commit/sweep engine.

Scope discipline, as everywhere in this family: build the thin slice this persona needs — a scalar on-hand count, a threshold, and an alert. Not a multi-warehouse WMS, not lot/batch tracking, not an append-only movement ledger (an open question, echoing Spec 042). Reorder points feed procurement; they do not themselves place orders (that is Spec 053).

4. Scope (in / out)

In scope

  • Generalize InventoryLevel: make ProductVariantId nullable, add nullable IngredientId, add a StockItemKind discriminator, and enforce exactly one of {ProductVariantId, IngredientId} via a DB CHECK (§8). Additive, tool-generated, safe backfill of existing rows to StockItemKind = "ProductVariant".
  • Add nullable ReorderPoint and optional ReorderQuantity to the level (§9).
  • Extend IInventoryService so reserve / commit / release / set-on-hand address a stock item (variant or ingredient), reusing the same reservation rows and sweep job (§8).
  • LowStockAlert entity + ILowStockAlertService (raise-or-update, acknowledge, list) returning DTOs.
  • Quartz LowStockScanJob: scan levels where available (= OnHand − Reserved) ≤ ReorderPoint; raise or update one Open alert per ingredient (idempotent) (§9).
  • Alerts surface through the existing Spec 016 admin realtime inbox (§10).
  • Admin endpoints: set ingredient on-hand, set reorder point, list low-stock alerts, acknowledge alert.
  • Commerce-agent read tools (check stock, list low-stock) + medium-gated write tools (set stock, set reorder point).
  • New DbSet on CommerceDbContext + AonikDbContext; one tool-generated migration (CommerceRawMaterialInventory).

Out of scope

  • Placing a reorder — suppliers and purchase orders are Spec 053; goods receipt (which resolves an alert) is Spec 054. An alert here is a signal only.
  • Ingredient cost — Spec 051. This spec is quantities only, no money.
  • Multi-location / multi-warehouse stock as first-class routing — Location stays a free string as in Spec 042; cross-location netting is Open.
  • An append-only stock-movement ledger (audited every-delta history) — v1 keeps scalar counter columns; the ledger is Open (echoing Spec 042).
  • Reserving ingredient stock for planned production — the reservation machinery is reused, but production consumption is Spec 056.

5. Constraints & guardrails

  • No reference to Finance. Aonik.Commerce still references only SharedKernel + Aonik.Ordering. This spec is quantities, thresholds, and alerts — it moves no money and adds no cross-module coupling (ADR-005).
  • Anemic entities. The generalized InventoryLevel and the new LowStockAlert stay { get; set; } data containers implementing ITenantScoped + AuditableEntity (ADR-002); the scan and raise/acknowledge logic lives in services.
  • Exactly one stock item per level. A level row stocks either a ProductVariant or an Ingredient, never both and never neither — enforced by a DB CHECK, not just app code (§8).
  • One source of truth per concept. Ingredient stock and variant stock are different rows in one table discriminated by StockItemKind; they never collapse. A Recipe draws down ingredient stock, a Bundle draws down variant stock (Spec 050 §9).
  • Reuse, don't fork, the reservation engine. Ingredients use the existing InventoryService reserve/commit/release and the existing InventoryReservationSweepJob. No second reservation system.
  • Single migration stream. EF-CLI-generated against AonikDbContext; Ank-prefixed tables; the level change is additive (nullable columns + CHECK) so existing finished-goods rows are untouched apart from a discriminator backfill; agents never hand-author migrations.
  • Idempotent alerting. The scan raises at most one Open alert per ingredient; re-running it updates the existing open alert's snapshot rather than creating another. Agents propose; every AI write records an AiRun.

7. Domain model

The generalized level and the new alert are anemic, ITenantScoped, inherit AuditableEntity. New/changed members are marked; unmarked members are the existing Spec 042 shape. 

class InventoryLevel  { Guid Id, TenantId;
                        Guid?  ProductVariantId;   // CHANGED: was non-null; now nullable
                        Guid?  IngredientId;       // NEW: set iff this level stocks a raw material
                        string StockItemKind;      // NEW: "ProductVariant" | "Ingredient" (discriminator)
                        string? Location;
                        decimal OnHand;
                        decimal Reserved;          // Available = OnHand - Reserved
                        decimal? ReorderPoint;     // NEW: raise a low-stock alert at/below this available level
                        decimal? ReorderQuantity;  // NEW (optional): suggested top-up qty (feeds Spec 053)
                        // DB CHECK: exactly one of {ProductVariantId, IngredientId} is non-null }

class LowStockAlert   { Guid Id, TenantId, IngredientId;
                        decimal AvailableAtRaise;  // snapshot of Available when first raised / last refreshed
                        decimal ReorderPoint;      // snapshot of the threshold that fired
                        string  Status;            // Open | Acknowledged | Ordered | Resolved
                        DateTime RaisedAt; }

StockItemKind is a free string with a known-values helper ("ProductVariant", "Ingredient") — additive, mirroring how OrderType and other discriminators are modelled across the platform. LowStockAlert.Status is likewise a known-values string (Open → Acknowledged → Ordered → Resolved, §10). AvailableAtRaise and ReorderPoint are snapshots so the alert reads meaningfully in the inbox even after stock later moves; the live figure is always the level itself.

8. Generalizing InventoryLevel to stock items (with the exactly-one CHECK)

Today InventoryLevel is keyed by a non-null ProductVariantId, with a unique index on (TenantId, ProductVariantId, Location). To stock ingredients too, we widen the key rather than add a table:

  1. Make ProductVariantId nullable and add nullable IngredientId. A level now points at exactly one of the two.
  2. Add StockItemKind as an explicit discriminator ("ProductVariant" | "Ingredient") so queries and the scan filter cheaply without null-probing.
  3. Add a DB CHECK enforcing exactly one of {ProductVariantId, IngredientId} is set (and matches StockItemKind) — the invariant lives in the database, not just the service.
  4. Revise the unique index to a pair of filtered unique indexes so uniqueness holds within each kind: (TenantId, ProductVariantId, Location) where IngredientId IS NULL, and (TenantId, IngredientId, Location) where ProductVariantId IS NULL.
AnkInventoryLevels (one table, discriminated) Id | TenantId | StockItemKind | ProductVariantId | IngredientId | Location | OnHand | Reserved | ReorderPoint | ReorderQuantity ── | ──────── | ─────────────── | ──────────────── | ──────────── | ──────── | ────── | ──────── | ──────────── | ─────────────── … | T1 | "ProductVariant"| V-abc | NULL | NULL | 120 | 4 | NULL | NULL ← existing finished-goods row (backfilled) … | T1 | "Ingredient" | NULL | I-rice | NULL | 2.0 | 0 | 5.0 | 25.0 ← new raw-material row (below reorder point) CHECK ( (ProductVariantId IS NOT NULL AND IngredientId IS NULL AND StockItemKind = 'ProductVariant') OR (ProductVariantId IS NULL AND IngredientId IS NOT NULL AND StockItemKind = 'Ingredient') )
Safe additive migration Every change is additive: the new columns are nullable, the CHECK and the filtered indexes are new objects, and the only touch to existing rows is a one-time backfill of StockItemKind = "ProductVariant" (which the migration performs before the CHECK is enforced, since every legacy row already has a non-null ProductVariantId). No finished-goods data is rewritten or dropped. The migration is EF-CLI tool-generated; the reviewer confirms the diff is exactly "two nullable columns + one string column + one CHECK + revised indexes + backfill" before it merges.

Reusing the reservation engine by stock item

With levels generalized, the existing InventoryService is extended so its methods address a stock item (a variant or an ingredient) instead of only a variant. The reserve-before-order / commit-on-capture / release-on-cancel-or-expiry contract, the InventoryReservation rows, and the InventoryReservationSweepJob are unchanged in behaviour — a reservation simply records which stock item it holds. This is the crux of the spec: ingredients get reservations for free. Spec 056 will fan a production run's recipe explosion out over ingredient reservations exactly as Spec 042 fans a bundle checkout out over component-variant reservations — one engine, two callers.

Do not build a parallel reservation system It is tempting to give ingredients their own hold table because "ingredients aren't sold". Resist it. The reservation semantics (atomic all-or-nothing hold, TTL, commit, sweep) are identical; forking them would double the surface, split the sweep job, and re-introduce the very drift the single-engine design avoids.

9. Reorder points & the low-stock scan

A level gains two optional fields: ReorderPoint (the available quantity at or below which the ingredient is "low") and ReorderQuantity (an optional suggested top-up, consumed by Spec 053 when it drafts a purchase order — this spec stores it but does not act on it). A null ReorderPoint means "no alerting for this item" — finished-goods rows leave it null and are never scanned.

A new Quartz job, LowStockScanJob, is the raiser. It sweeps across tenants under a system context (like the reservation sweep) and, for every Ingredient level with a non-null ReorderPoint whose available quantity has fallen to or below it, raises or refreshes exactly one Open alert:

LowStockScanJob.Execute() // Quartz, [DisallowConcurrentExecution], per interval for each tenant: levels ← AnkInventoryLevels where StockItemKind = "Ingredient" and ReorderPoint is not null and (OnHand - Reserved) <= ReorderPoint // Available at/below threshold for each level: existing ← LowStockAlert where IngredientId = level.IngredientId and Status = "Open" if existing is null: raise new LowStockAlert(Open, AvailableAtRaise=Available, ReorderPoint) → notify (Spec 016) else: refresh existing.AvailableAtRaise = Available // IDEMPOTENT: no duplicate // items back above their reorder point are NOT auto-resolved here — see §10

Idempotency is the load-bearing property. The invariant "at most one Open alert per ingredient" is enforced two ways: the scan checks for an existing open alert before inserting, and a filtered unique index on (TenantId, IngredientId) where Status = "Open" makes a duplicate impossible even under a concurrent or double-fired scan. A newly-raised alert is pushed to the admin inbox once (§10); a refresh updates the snapshot silently.

The scan is set-based and read-mostly: one indexed query per tenant over ingredient levels, then at most one write per breaching item. It never touches variant levels. Cadence is configurable (default a few minutes) via the same ScheduledJobOptions pattern the reservation sweep uses, so it can be tuned or disabled per environment.

10. Alert lifecycle & the admin inbox (Spec 016)

A LowStockAlert moves through four states; transitions are how the reorder loop is tracked across this spec and the procurement specs that follow:

Open ──acknowledge──▶ Acknowledged ──PO raised (Spec 053)──▶ Ordered ──goods received (Spec 054)──▶ Resolved ▲ │ └────────────────────────┘ (an operator may re-open / it stays Open until acted on)
StatusMeaningSet by
OpenAvailable is at/below the reorder point and nothing has been done yet.LowStockScanJob (raise).
AcknowledgedAn operator has seen it and is handling it; suppresses re-notification noise.Admin endpoint / commerce_list_low_stock follow-up.
OrderedA purchase order for the ingredient has been raised.Spec 053 (PO create references the alert).
ResolvedStock has been received and is back above the reorder point.Spec 054 (goods receipt flips it).

This spec owns Open and Acknowledged only; Ordered and Resolved are written by the later specs (documented here so the state machine reads whole). Deliberately, the scan does not auto-resolve an alert when stock happens to climb back above the reorder point on its own — resolution is a procurement event, not a stock wobble — which keeps the loop auditable (whether auto-close-on-restock should also be allowed is Open).

Surfacing through the existing inbox

Alerts are not given a bespoke UI. When the scan raises a new Open alert, it emits a notification through the existing admin notifications / realtime inbox (Spec 016) — the same channel operators already watch — carrying the ingredient, the on-hand/available figure, and the reorder point. The Admin UI thus shows "Rice: 2 kg available, reorder at 5 kg" in the operator's normal notification stream, with acknowledge available inline. Reusing Spec 016 means no new realtime transport, and low-stock alerts sit alongside every other operational signal instead of in a siloed screen.

11. Agent & tools

The existing commerce-agent gains stock/reorder tools, classified by CommerceToolApprovalManifest and wrapped by the Spec 032 gate — no change to the gate:

Acknowledging an alert is an admin-endpoint action for now; it can be added as a third medium tool later without disturbing the gate.

12. CommerceDbContext & migrations

One new Ank-prefixed table — AnkLowStockAlerts — is created, and the existing AnkInventoryLevels table gains columns, a CHECK, and revised indexes, by a single EF-CLI migration against AonikDbContext. LowStockAlert is added to both CommerceDbContext (runtime scoping) and AonikDbContext (canonical stream); it is tenant-scoped (not global). The InventoryLevelConfiguration is extended with the new columns, the CHECK, and the two filtered unique indexes; a new LowStockAlertConfiguration adds the filtered unique index on one Open alert per ingredient. 

dotnet ef migrations add CommerceRawMaterialInventory --project src/Aonik.Infrastructure --startup-project src/Aonik.Api
Review the diff Because this migration alters an existing, populated table, the reviewer verifies it contains only: AddColumn for IngredientId (nullable), StockItemKind, ReorderPoint (nullable), ReorderQuantity (nullable); AlterColumn making ProductVariantId nullable; the backfill UPDATE; the CHECK constraint; the index swap; and the CreateTable for AnkLowStockAlerts — nothing else. If EF emits anything unexpected, fix the model, migrations remove, and regenerate — never hand-edit.

18. Decisions baked in

  • Generalize, don't clone. One InventoryLevel table stocks both variants and ingredients, discriminated by StockItemKind with an exactly-one CHECK — not two parallel tables.
  • One reservation engine. Ingredients reuse InventoryService reserve/commit/release and the existing sweep job, re-keyed by stock item; no parallel hold system.
  • Reorder point is a scalar threshold on the level; a null point means no alerting; ReorderQuantity is stored for Spec 053 but not acted on here.
  • Alerting is idempotent — at most one Open alert per ingredient, enforced by check + filtered unique index.
  • Alerts reuse the Spec 016 admin inbox; no bespoke realtime transport or siloed screen.
  • Resolution is a procurement event (Spec 054 goods receipt), not an incidental-restock side effect; the scan owns raise, not close.
  • Quantities only, no money — costing stays in Spec 051; Aonik.Commerce keeps no Finance reference; migrations stay with AonikDbContext.

19. Open design decisions

Open Counter columns vs. a stock-movement ledger. v1 keeps OnHand/Reserved as mutable scalar counters (matching Spec 042). An append-only StockMovement ledger (every receipt, consumption, adjustment as an immutable row, with the level as a projection) would give full auditability and reconciliation — echoing the same open question Spec 042 raised for finished goods. Deferred; if adopted, it should cover variants and ingredients uniformly, since they now share one table.
Open Multi-location stock. Location remains a free string (as in Spec 042); a first-class multi-warehouse model — per-location reorder points, cross-location netting, transfers — is not built. The reorder scan currently treats each (ingredient, location) level independently.
Open Auto-creating a purchase order from an alert. An Open alert (with its ReorderQuantity) could directly draft a PO to the ingredient's default supplier. Deferred to Spec 053, which owns suppliers and the PO spine; this spec deliberately stops at the signal so the human stays in the reorder loop.
Open Reserving ingredient stock for planned production. The reservation engine is reused, so a planned ProductionOrder could hold ingredient stock ahead of a run (making "available" reflect committed production). That belongs with production/work orders in Spec 056; here reservations exist only for the existing checkout/commit flow.
Open Auto-close on restock. Whether the scan should also flip an Open alert to a terminal state when available climbs back above the reorder point on its own (vs. requiring the procurement loop to resolve it). v1 keeps resolution a procurement event to preserve an auditable reorder trail.
