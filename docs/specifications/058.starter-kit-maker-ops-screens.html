Spec 058 Status: Draft Size: Large Priority: P3 Domain: Commerce / Design / AdminUi

Admin starter kit — maker-operations screens (the day-in-the-life surface)

Extends the design-prototype starter kit at Templates/aonik-admin-starterkit with the make-side screens that let an operations manager run the full day-in-the-life on Aonik: production sheet → prep list → low-stock alerts → suppliers & purchase orders → goods receipt → production orders & kitchen sheet → margin report → ingredient repricing. Every screen is a mock artboard on the existing canvas (Babel-in-browser, no build), faithful to the landed semantics of Specs 050–057 — the status vocabularies, honest unknown-COGS states, and frozen-snapshot rules the implemented services actually enforce. Also gives Commerce its missing home in the shell navigation.

1. Summary

The maker-operations backend is implemented end-to-end (Specs 050–057, PRs #165–#173 — merged through #167 at the time of writing, the remainder an open stacked chain this spec's branch stacks on, so every family cross-reference below resolves against the amended specs and the landed code, not the pre-implementation drafts): recipes, ingredient costing, raw-material stock with alerts, suppliers and purchase orders on the Order spine, goods receipt, production planning, production orders with kitchen sheets, and the margin report. The admin design surface has none of it: the starter kit's Commerce section covers only the sell-side (overview, catalog, inventory, carts/orders, discounts). An operations manager's day cannot be walked through on an artboard.

This spec adds one new canvas section — Commerce · Make — with 9 screen files / 11 artboards, a Commerce navigation group in the shell (today the sell-side screens have no sidebar home at all — they exist only as breadcrumbed artboards), and the mock datasets that make every state on those screens demonstrable, in the same wellness-food domain the kit already uses — including the exact jollof economics the Spec 050/051/057 tests pin (₦400/portion cost, 80% margin), so docs, code, tests, and design all tell one story.

Success signals Opening Templates/aonik-admin-starterkit/index.html shows the new "Commerce · Make" section with all 11 artboards rendering cleanly in light and dark themes; the sidebar carries the new Commerce group; every status pill on the new screens uses the landed vocabulary (alerts Open|Acknowledged|Ordered|Resolved; POs Draft|Pending|Complete|Cancelled; production Planned|Released|InProgress|Completed|Cancelled); the margin screen shows an unknown-COGS row with a null margin — never a fake zero; and the kitchen sheet states its frozen-snapshot guarantee.

2. Context & motivation

The 050–057 family was driven by a concrete day-in-the-life: the operations manager reviews orders, reads the aggregated production sheet, consults the ingredient prep list, reacts to a low-stock alert, places a purchase order, receives stock, prints the kitchen sheet, reviews the profit report, and updates ingredient costs when suppliers reprice. Every one of those moments now has a real API and agent tool. The starter kit is where Aonik's admin UX is designed before it is built in src/Aonik.AdminUi — so the day-in-the-life needs its screens there first, both as the design contract for the production build and as the demo surface for the wellness-food tenant story that Spec 042 started.

A secondary motivation surfaced during grounding: the existing Commerce screens are registered as artboards with breadcrumbs like ['Commerce', 'Inventory'], but SIDEBAR_NAV in kit/shell-aonik.jsx has no Commerce group — commerce has no place in the app's information architecture. This spec fixes that for the sell-side and make-side together (§7).

3. Grounding: how the starter kit works

Verified against the template (2026-07-02); the spec's tasks assume exactly this machinery.

  • Runtime: static index.html, CDN React 18.3 + Babel standalone — JSX transpiled in-browser, no build step. Screens load via <script type="text/babel" src="screens/…"> tags in a fixed order (kit → screens → canvas → app).
  • Canvas: design-canvas.jsx renders DCSections of DCArtboards (typically 1480×980). Artboards wrap screens via the mkShell(activeNavId, breadcrumbs, ScreenComponent) helper in the main app script, which composes AonikShell. Artboard order/labels persist to .design-canvas.state.json.
  • Screen anatomy (per commerce-inventory.jsx / commerce-orders.jsx, the closest siblings): one function ScreenX() per artboard; local useState for tabs/filters/selection; page header (22px/700 title + 13px secondary subtitle); a 4-tile KPI grid; a segmented tab/filter control; a CSS-grid data table (header row on --surface-inset, clickable rows); a conditionally-rendered right-side drawer for detail/edit; status pills driven by { tone, label } lookup objects.
  • Kit: Icon (Tabler/Lucide-style, ~80 names + icons-extra.jsx), Avatar, Pill (tones: default/tint/muted/success/warning/danger/pending), KPI, Card, Tabs, FilterBar, DataTable, PageHeader, .btn/.input classes, drawer pattern. Design tokens in tokens.css (brand teal --brand-primary #055a60, status colors, dark theme via data-theme="dark").
  • Mock data: global-scope mock-data.js — CM_* UPPERCASE datasets, cm* helper functions, *_TONE-style status lookups; wellness-food domain (granolas, cold-brew, wellness shots, build-your-own boxes; NGN/GBP pricing; Lagos DC / Abuja DC locations).
  • Not production code: the starter kit is a design prototype. Screens do not map 1:1 to src/Aonik.AdminUi; there is no API wiring and none is added here.

6. Constraints & guardrails

  • Semantics fidelity is the point. Every status vocabulary, state, and rule shown must match what Specs 050–057 landed — not what early drafts sketched. Concretely: alerts are Open | Acknowledged | Ordered | Resolved and Open+Acknowledged is one active set; POs are Draft | Pending | Complete | Cancelled (there is no "Submitted/Received" status — submitted lands on Pending, partial receipt is a derived progress bar, never a status); production orders are Planned | Released | InProgress | Completed | Cancelled; margins with unknown COGS are null ("—"), never zero, and excluded from the aggregate; the kitchen sheet consumes the frozen creation-time snapshot, stated on the artboard.
  • Mock-only. No fetch, no backend, no new dependencies; all interactivity is local useState theatre, as on the existing screens.
  • House patterns only. Tokens for every color (both themes must render); kit components over bespoke ones; CSS-grid tables; drawers for detail/edit; { tone, label } lookups for statuses; cmMoney() for money.
  • Domain continuity. The wellness-food catalog (jollof, granola, rice, tomato, Lagos/Abuja DCs, NGN-first) carries through; the demo numbers reuse the family's pinned test economics (§9) so a reader can trace a figure from spec → test → artboard.
  • Additive registration. New screens append; existing artboard ids, labels, and the state sidecar are not disturbed.

7. Navigation & IA — the Commerce group

Two new sibling parent items in SIDEBAR_NAV's Products band after Billing — deliberately one level of nesting each: the shell's sidebar renders exactly parent.children and its active-state lookup checks one child level (kit/shell-aonik.jsx — grandchildren get a chevron but are never rendered), so a nested "Make" sub-group would be unreachable. Splitting sell-side and make-side into two parents keeps the IA without any shell code change. Badge counts come from the mock datasets (active alerts; POs pending receipt).

8. Screen inventory

Nine files, eleven artboards, each 1480×980 under mkShell. For every screen: the day-in-the-life moment it serves, its artboards and layout, the states that MUST be demonstrated (the mock data is designed to produce them), and the API mapping the production build will wire. Two small shared helpers are permitted (kit-level, reused across screens): WindowPicker (from/to date-range chip row used by Planning + Margin) and ProgressCells (received-vs-ordered / margin-vs-target mini bars in table rows).

Moment: "updates ingredient costs in the system if suppliers change prices."

  • KPIs: ingredients count · below reorder point · avg cost movement (30d) · uncosted ingredients.
  • Table: name+emoji, base unit, category, current cost (cmMoney/unit), stock available (OnHand−Reserved), reorder point, status pill (Active/Inactive).
  • Drawer (row click): identity (name/sku/unit/category, unit locked with a "referenced by recipes/costs" note — the landed 050/051 guard); cost history as an effective-dated timeline (closed windows, the current window, and one scheduled future cost — the 051 window-split semantics); a reprice form (new cost + effective-from) with the backdate-rejected error state; stock & reorder-point editing (052).
  • Must demonstrate: a scheduled future cost rendered distinctly; the unit-change-blocked note; an uncosted ingredient flagged.

16. Decisions baked in

  • The starter kit is the design contract for the production AdminUi build — hence the R8 per-screen API-mapping comments and the semantics-fidelity guardrails.
  • One new canvas section, nine files, eleven artboards — mirrors the family's screen-per-moment shape; planning and production get two artboards each.
  • Commerce finally gets a nav group, covering sell-side and make-side; make-side nests under a "Make" child.
  • Landed semantics over draft semantics — the screens teach the implemented rules (status codes, honest nulls, frozen snapshots, derived partials).
  • Demo numbers = test numbers — the pinned economics carry from the 050–057 suites onto the artboards.
