Spec 026 Status: Draft Priority: P0 Domain: Platform / Identity

User Lifecycle Closure

Closes the three P0 gaps in the Admin UI user-management lifecycle so we can document and ship a credible user-administration guide: (1) invite email via the Aonik notification stack, (2) GDPR-strict hard delete with audit-log redaction covering the IdP user record, and (3) token revocation via a SQL blocklist cached in FusionCache. After this spec lands, the Admin UI can take a user from invite to deletion entirely in-product without any out-of-band communication or manual IdP-dashboard work.

1. Summary

The user-lifecycle audit in May 2026 found the Admin UI at ~75% complete for user management. Provision, invite-as-placeholder, role assignment, profile edits, deactivation, and audit logging all work end-to-end. Three P0 gaps block a credible operator-facing user-management guide:

  1. Invite email — InviteUserEndpoint creates a placeholder user but does not send an invitation email. Operators must communicate the login URL out-of-band (Slack, manual email, etc.). The "invite a user" user story has no completion path in-product.
  2. Hard delete — no DELETE /admin/users/{id} endpoint exists. Operators can only deactivate. GDPR right-to-be-forgotten and contractor offboarding are unsupported.
  3. Token revocation — no token blocklist or session-revocation endpoint. JWTs remain valid until expiry even after deactivation. Security incident response is broken.

This spec defines the implementation of all three. Each is independently shippable. Total estimate: ~6–9 engineering days (excluding documentation).

3. Goals & non-goals

Goals

  • An operator can take a user from invite to deletion entirely from the Admin UI without copying URLs into Slack, opening the Auth0 / Entra dashboard, or running SQL.
  • A user's first sign-in completes the loop the operator started — the invite link in the email lands them in a flow that maps their IdP identity onto the placeholder.
  • On hard delete, no personally identifiable information (PII) remains in AnkUsers, AnkAuditLogs, or the configured IdP's user store for the affected user. Foreign-key integrity for audit history is preserved via tombstoning.
  • On revoke, the affected bearer token stops authenticating within the FusionCache refresh window (≤ 30 s by default, ≤ 5 s on every replica after explicit cache invalidation).
  • Every action above writes a tamper-evident audit log entry with the operator's user-id, action, target user-id (or tombstone reference after delete), and correlation-id.

Non-goals

  • Operator-triggered password reset (P1, deferred). Users self-serve via the public forgot-password flow.
  • Effective-permissions computation endpoint (P1, deferred). Today the UI shows a permission count; the rollup is computable client-side from the roles list.
  • Pre-provisioning users in Auth0 / Entra on invite. JIT linking continues to be the canonical flow. Pre-provisioning is tracked in §17 as a future P1.
  • Bulk operations (CSV import, multi-user role updates). P2, deferred.
  • Multi-factor authentication enrolment management. The IdP owns MFA today; surfacing it in the Admin UI is out of scope.

4. Decisions baked in

Four decisions were locked in during scoping. The rest of the spec assumes them.

QuestionDecision
Invite email transport Aonik notification stack (consistent with existing email + phone OTP templates).
Hard-delete semantics GDPR-strict: hard-delete platform row, redact PII in audit logs to a tombstone, delete the IdP user via the provider's management API.
Token-revocation mechanism SQL blocklist + FusionCache. UserId-keyed entries, validated in the auth middleware on every request.
P1 / P2 gaps Documented as roadmap; not built in this spec.

5. Part 1 · Invite email

Outcome

When an operator invites a new user from the Admin UI, the invitee receives a branded email from Aonik containing a tenant-specific sign-in link, an expiry time, and the role they have been granted. A "Resend invite" button is available on the user detail page for users still in the Invited status.

Notification template

Add a new template key in NotificationTemplateNames:

// src/Aonik.Platform/Services/Notifications/NotificationTemplateNames.cs
public const string AdminUserInvitation = "admin.user-invitation";

Template variables (rendered server-side, identical to the existing registration.email-confirmation contract):

VariableSource
{{tenantName}}Tenant.DisplayName
{{inviteeDisplayName}}Operator-supplied at invite time; falls back to the email local-part.
{{operatorDisplayName}}The inviting user's DisplayName.
{{rolesGranted}}Comma-separated list of role names assigned at invite.
{{inviteUrl}}Tenant-scoped sign-in URL with an ?invite=<token> query parameter (see below).
{{expiryUtc}}ISO-8601 timestamp, default 72 hours after invite creation.

Invite token

The placeholder user record gains a one-shot invite token. The token is opaque to the IdP — it does not function as a bearer token. Its only purpose is to identify the placeholder when the invitee returns and authenticates. 

// New columns on AnkUsers (or a new AnkUserInvites table — see §9)
InviteToken             nvarchar(64)   // ULID, indexed
InviteExpiresUtc        datetime2
InviteEmailSentUtc      datetime2
InviteEmailSendCount    int default 0  // for "Resend" rate-limiting

When the invitee clicks the link, the front-end (Admin UI sign-in or the public registration page) posts the token to POST /identity/invite/accept alongside the IdP token. The platform verifies that:

  1. The invite token exists, is not expired, and is not consumed.
  2. The email claim in the IdP token matches the placeholder's email (or the operator allowed mismatched-email accept — see §17).
  3. The placeholder is in the Invited status.

On success, the placeholder is transitioned to Active, the IdP identity (ExternalIssuer + ExternalSubject) is linked, and the invite token is marked consumed. The user is now logged in.

Resend invite

Existing endpoint InviteUserEndpoint is extended to accept a resend: true flag that re-uses the existing placeholder, regenerates the invite token, increments InviteEmailSendCount, and re-sends the email. Rate-limit to a soft cap of 5 sends per user per 24 hours; harder cap enforced by the existing audit-log rate limiter.

Endpoints

MethodPathPurposeStatus
POST/admin/users/inviteCreate placeholder + send email. Existing; extend to also send.existing
POST/admin/users/{userId}/resend-inviteResend the invite email.new
POST/identity/invite/acceptConsume invite token + link IdP identity.new

Admin UI changes

  • "Invite user" dialog gains a confirmation message: "Sent invite to <email>. Expires <expiryUtc>."
  • UserDetailPage gains a "Resend invite" button visible only when status is Invited; greyed out with tooltip when rate-limited.
  • User list shows the "Invited" status badge in amber until accepted.

6. Part 2 · Hard delete

Outcome

An operator with the user.delete permission can permanently remove a user. After deletion the user no longer appears in any list, cannot sign in, cannot be reactivated, and their PII is removed from AnkUsers, audit logs, and the IdP user store. A tombstone preserves foreign-key integrity for historical references.

Steps performed by the delete service

  1. Verify caller has user.delete on this tenant.
  2. Reject delete if the user is the last TenantAdmin (prevents lockout).
  3. Revoke all active sessions (use the §7 mechanism inline).
  4. Call the IdP management API to delete the IdP user record (Auth0 DELETE /api/v2/users/{id} or Microsoft Graph DELETE /users/{id}).
  5. Insert a row into AnkUserTombstones with the deleted user-id, deletion UTC, and operator user-id.
  6. Update every AnkAuditLogs row where ResourceId or ActorId equals the deleted user-id, setting:
    • ResourceLabel → "(deleted user)"
    • ActorEmail, ActorDisplayName → NULL
  7. Cascade-delete the user's roles, photo blob, profile, and verification records.
  8. Delete the row from AnkUsers.
  9. Write a final audit-log entry: action="user.deleted", resourceId=<tombstone-id>, actorId=<operator>, with the operator-supplied deletion reason in the data column.
Note Steps 4 and 6 are both required for true right-to-be-forgotten. The IdP holds the source-of-truth identity; the audit log holds the action history. Either alone is insufficient under GDPR Article 17.

Tombstone table

// New table
AnkUserTombstones {
  Id                 uniqueidentifier PK    // separate from the original UserId
  OriginalUserId     uniqueidentifier        // for foreign-key remapping
  TenantId           uniqueidentifier        // tenant scope
  DeletedUtc         datetime2
  DeletedByUserId    uniqueidentifier        // operator
  Reason             nvarchar(500)           // operator-supplied
}

Endpoints

MethodPathPurposeStatus
DELETE/admin/users/{userId}Hard-delete with operator-supplied reason.new
GET/admin/users/tombstonesList recent deletions (for compliance review).new

IdP management API access

Calling the IdP management API requires elevated credentials separate from the tenant-level OAuth client.

ProviderMechanismConfiguration
Auth0 Client-credentials grant against https://<tenant>/oauth/token with audience=https://<tenant>/api/v2/. Token cached for ≤ 24h. Auth:Auth0:ManagementClientId, Auth:Auth0:ManagementClientSecret

A new IIdentityProviderManagementClient abstraction in Aonik.Platform.Services.Identity.Provisioners hides the per-provider details. Implementations: Auth0ManagementClient, AzureAdManagementClient.

Admin UI changes

  • UserDetailPage gains a destructive "Delete user" button at the bottom of the actions panel, red, with a confirm dialog.
  • The confirm dialog requires the operator to type the user's email exactly and supply a deletion reason (≥ 10 characters).
  • Successful delete navigates back to the user list with a green toast: "User permanently deleted. Tombstone <id> created."
  • A new "Deleted users" page under Compliance lists tombstones with date, operator, and reason.

7. Part 3 · Token revocation

Outcome

An operator can force a user offline within seconds. Internally a UserId-keyed blocklist row is created. The auth middleware checks the blocklist (via FusionCache) on every request; if the requesting user is blocked the request returns 401 Unauthorized with WWW-Authenticate: Bearer error="invalid_token".

Blocklist table

// New table
AnkUserSessionBlocklist {
  Id                 uniqueidentifier PK
  TenantId           uniqueidentifier
  UserId             uniqueidentifier         // indexed
  RevokedUtc         datetime2
  RevokedByUserId    uniqueidentifier         // operator (NULL if system-initiated)
  Reason             nvarchar(200)            // free-form
  // A row exists from RevokedUtc until 14 days later (max JWT lifetime).
  // After that the auth middleware no longer needs to check; row may be pruned.
  ExpiresUtc         datetime2
}

An UNIQUE index on (TenantId, UserId, RevokedUtc) means a user can be revoked multiple times in their lifecycle; only the most recent entry is consulted.

Middleware behaviour

The existing JWT-bearer authentication middleware in Aonik.Infrastructure.Authentication gains a single hook: 

// pseudocode
if (await blocklist.IsRevokedAsync(tenantId, userId, tokenIssuedAt)) {
  return Forbidden();
}

The check is implemented as a FusionCache lookup with a 30-second TTL and a 5-second jitter. Read-heavy: cache hits are O(1). On POST /admin/users/{userId}/revoke-sessions, the platform writes the row and invokes FusionCache.RemoveAsync across all replicas via the existing backplane so the next request sees the new state within one TTL.

Note The check compares the JWT's iat (issued-at) claim to RevokedUtc. Tokens issued after a revocation are allowed — the operator's intent is "kill the current sessions," not "ban the user permanently." Permanent ban is achieved by deactivation (existing).

Endpoints

MethodPathPurposeStatus
POST/admin/users/{userId}/revoke-sessionsAdd a blocklist row + invalidate cache.new
GET/admin/users/{userId}/sessionsList active sessions (best-effort, based on recent token iats observed in audit logs).new

Auto-revoke on deactivate

DeactivateUserEndpoint calls the revocation pipeline inline. This closes the historical foot-gun where deactivating a user did not invalidate their bearer token.

Admin UI changes

  • UserDetailPage gains a "Revoke sessions" button next to "Deactivate." Confirm dialog requires a free-form reason.
  • The new "Sessions" tab on UserDetailPage shows the most recent iat per session (from audit logs) with a per-row revoke button.
  • Status badge changes to "Sessions revoked" for users who have been revoked but not deactivated.

8. The closed loop

Once all three parts ship, the user-lifecycle diagram looks like this — every arrow is in-product, no out-of-band steps:

Operator Invitee IdP ┌─────────┐ │ Invite │── POST /admin/users/invite ─────────┐ └────┬────┘ │ │ ▼ │ ┌──────────────────────┐ │ │ AnkUsers placeholder │ │ │ status=Invited │ │ │ InviteToken=ULID │ │ └──────────┬───────────┘ │ │ │ email: admin.user-invitation │ ▼ │ ┌────────────────────┐ │ │ Email inbox │ │ │ Click link → │ │ └────────┬───────────┘ │ │ │ GET /signin?invite=<token> │ ▼ │ ┌────────────────────┐ │ │ Admin UI │ │ │ redirect to IdP │ │ └────────┬───────────┘ │ │ │ IdP login (Auth0 / Entra) │ │ │ ▼ │ ┌────────────────────┐ │ │ POST /identity/ │ │ │ invite/accept │ │ └────────┬───────────┘ │ │ │ link IdP identity to placeholder │ status=Active, token consumed │ │ Active session ◄─────────────────────────────┘ ──── later ──── ┌──────────────┐ │ Revoke now │── POST /admin/users/{id}/revoke-sessions └──────┬───────┘ │ ▼ AnkUserSessionBlocklist row + FusionCache.RemoveAsync │ ▼ Next request from that bearer token → 401 ──── eventually ──── ┌──────────────┐ │ Hard delete │── DELETE /admin/users/{id} (reason required) └──────┬───────┘ │ inline revoke → IdP DELETE → tombstone → redact audit log → cascade delete → AnkUsers row gone

9. Data-model changes

Three new tables, two columns added to AnkUsers. All migrations generated through AonikDbContext per the single-migration-stream rule.

ChangeDetail
Extend AnkUsers Add InviteToken, InviteExpiresUtc, InviteEmailSentUtc, InviteEmailSendCount. Index InviteToken for token-lookup.
New AnkUserInviteLog Per-send audit row (for "Sent 5 minutes ago" timestamp on the UI). Foreign-key to AnkUsers.
New AnkUserSessionBlocklist UserId-keyed blocklist as described in §7.
New AnkUserTombstones Permanent record of deletions as described in §6.
Decision AnkUserInviteLog is a separate table rather than an audit-log specialisation. Audit logs are tamper-evident and append-only; the invite log can be pruned with the user record at deletion time and so deserves its own table with a cascading delete relationship.

13. Migration & rollout

  1. Generate migrations against AonikDbContext in src/Aonik.Infrastructure using dotnet ef migrations add UserLifecycleClosure.
  2. Seed the new permissions (user.delete, user.revoke-sessions) through the existing permissions seeder in TenantProvisioner. Grant on upgrade for TenantAdmin; do not auto-grant on Operations for user.delete.
  3. Roll out part 1 (invite email) first behind a tenant feature flag UserLifecycle.InviteEmail. Migrate template translations as needed.
  4. Roll out part 3 (token revocation) second; auto-revoke wiring on deactivate is behind feature flag UserLifecycle.AutoRevokeOnDeactivate until the blocklist is verified at scale.
  5. Roll out part 2 (hard delete) last. Requires the IdP management credentials to be provisioned per environment (manual operator step).

14. Testing strategy

Mandatory test coverage before merge to main:

  • Unit tests in Aonik.Application.Tests for the invite token lifecycle (create, expire, consume), blocklist cache hits/misses, and the tombstone-creation flow. Follow the existing xUnit + FluentAssertions conventions.
  • Integration tests in Aonik.Api.Tests for every new endpoint using CustomWebApplicationFactory with UseInMemoryDatabase=true. Coverage includes: invite + resend + accept round-trip, delete-with-tombstone, revoke-then-immediately-call-secured-endpoint returns 401, deactivate triggers revoke.
  • End-to-end test against Auth0 dev tenant (Auth0 only — Entra ID e2e blocked by automation-account constraint). Covers the closed loop from invite through accept.
  • GDPR delete test that asserts post-delete: no AnkUsers row, no PII in AnkAuditLogs for the deleted user, IdP user mock was called.

17. Open decisions

Open · O-1 Mismatched-email accept. If the invitee authenticates with a different email than the placeholder, do we (a) reject the accept (current behaviour, safest), or (b) let the operator pre-flag the placeholder as "accept any IdP identity that uses this invite token"? Option (b) is friendlier for ops teams that pre-provision users by employee ID rather than email but loses email-based verification.
Open · O-2 IdP pre-provisioning on invite. Should InviteUserEndpoint call Auth0 / Entra to create the IdP user record upfront, or wait for JIT linking? Pre-provisioning makes the password-reset flow work before the invitee has ever logged in, but adds a hard dependency on the IdP being reachable at invite time. Recommend keeping JIT in this spec and tracking pre-provisioning as spec 027.
Open · O-3 Tombstone retention. Tombstones contain the deleted user-id and the operator's user-id. How long do we retain them? GDPR requires a finite period — propose 7 years (typical financial regulator audit horizon) with a scheduled purge job. Open: confirm the legal team's view.
Open · O-4 Blocklist max-age. Blocklist rows are pruned 14 days after creation (matching the longest acceptable JWT lifetime). Confirm 14 days is sufficient — if any deployment issues longer-lived bearer tokens, this needs to extend.
