Customer detail — domain lenses as tabs on one party

Updates src/pages/customers/CustomerDetailPage.tsx (/customers/:partyId). Design of record: the unified detail on the starterkit (PR #268). One party, every lens: the tab strip gains Commerce, the Orders tab unifies on the order spine with type chips, and tabs render per the tenant's enabled modules — a billing-only tenant never sees a Commerce tab, and no second customer view ever exists.

2 · The Orders tab — one spine

  • Source: the spine list the app already consumes (orderService → GET /orders) filtered to this party and not filtered by type. Columns: order id (mono) · type (Pill: ProductPurchase tint · BillPayment muted · MoneyTransfer pending · other default) · what (human line: box size + extras summary for purchases; counterparty/corridor for payments) · date (mono) · status (Pill dot) · amount (mono, right).
  • Caption: "Every order, one spine — boxes, bill payments and transfers share the Order record (ADR-011); filter by type, never by screen." A type filter chip-row is optional v1; the unified list is mandatory.
  • Consistency rule (review-hardened): whatever the registry row (Spec 080) states as order count/value must be derivable from this tab's dataset — both read the spine; the UI must not maintain two divergent totals.

3 · The Commerce tab — Spec 072 made visible

  1. Guest→account adoption card — a three-step vertical timeline (built cart as guest → registered → cart adopted, guest token retired) rendered when the party's storefront history includes an adoption; hidden otherwise. This is Spec 072's one clever moment made visible to operators.
  2. Storefront profile card — boxes ordered, storefront value (the ProductPurchase subset of the spine — must equal the box history's sum), usual size, most-ordered item, active cart (size + fullness or "None").
  3. Box history card — the party's checked-out storefront orders: id (mono) · date · size + extras summary · status pill · total (mono). Caption: "Party-scoped — exactly what the customer sees in their own account."

5 · Implementation instructions

  • Files: modify CustomerDetailPage.tsx (TabKey, TABS, gating); create src/pages/customers/commerce/CommerceTab.tsx (+ AdoptionTimeline.tsx, BoxHistoryCard.tsx) mirroring the existing customers/finance/ sub-folder pattern; create src/pages/customers/OrdersSpineTab.tsx replacing the old orders tab body.
  • Gating: const commerceEnabled = useModules().isModuleEnabled?.('commerce') ?? true — follow however useModules exposes enablement; fail open exactly as it does.
  • Derivations (unit-tested, src/pages/customers/lib/spineDerivations.ts): storefrontSubset(orders), storefrontValue(orders), usualSize(orders) — pure functions over the spine list so profile figures can never disagree with the rendered rows.
  • Amounts per-currency mono (mixed currencies render per-row; totals only within one currency — a mixed-currency profile value shows the dominant currency's subtotal with a "+ n other currencies" note rather than a fake sum).

6 · Acceptance

  1. A commerce-enabled tenant shows the Commerce tab; disabling the module in the manifest hides it with no dead tab; manifest-absent fails open.
  2. The Orders tab lists mixed types with correct chips, and its ProductPurchase subset equals the Commerce tab's box history row-for-row.
  3. Storefront value equals the sum of rendered box-history totals (single-currency case) — the two can never diverge by construction.
  4. Adoption/active-cart cards are hidden until their data source exists; nothing renders placeholder or invented data.
  5. Existing tabs (Finance, Insights, Documents, Activity) behave exactly as before.
