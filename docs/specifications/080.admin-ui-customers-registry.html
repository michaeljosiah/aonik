Customers — one top-level registry for every product line

Updates the existing /customers page (src/pages/customers/CustomersListPage.tsx). Design of record: the unified-customers decision recorded in PR #268 and the starterkit registry artboard. Principle: a tenant selling merchandise and financial services has one customer base — Customers is the universal counterparty registry beside Orders; domain lenses are chips here and tabs on the detail (Spec 081), never separate customer views.

2 · API contract

CallNotes
GET /admin/customers?… (existing, customerService.list)The registry keeps its existing paged source. This spec adds two derived needs:
  • Registry read-model extension — the shipped CustomerListItem carries none of the new columns' data: no country, no order count, no total value, no domains. The required server-side extension therefore covers all four: country, domains: string[] (derived from module ownership records: billing accounts, storefront carts/orders via Cart.BuyerPartyId, personal-finance enrolment), spine-wide orderCount, and totalValue reported per currency ([{ currency, amount }] — never a cross-currency sum).
  • Degraded mode — until the extension ships, every dependency-gated column (Country, Products, Orders, Total value) is hidden entirely; the registry still functions with ID · Customer · Type and the reshaped nav/tabs. Columns degrade by absence, never by placeholder zeros.
Dependency callout. The read-model extension above is a Platform addition, not shipped today. The nav move, tab reshape and base columns are implementable now; the four data columns light up when the extension lands. It is listed as a follow-up backend item, deliberately NOT smuggled into a UI spec.
