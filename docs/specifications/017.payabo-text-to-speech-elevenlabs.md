## Objective

Implement a provider-agnostic, tenant-configurable text-to-speech architecture for Payabo chat that:

1. uses ElevenLabs as the primary backend-managed TTS provider
2. keeps the mobile app dependent on an internal abstraction rather than a specific TTS vendor
3. streams synthesized audio from the AONIK backend to the Android app
4. allows each tenant to configure its own voice and provider settings
5. falls back to Android native TTS on failure while preserving logs and auditability

## Problem Statement

Payabo currently performs chat voice playback using `flutter_tts`, which delegates to the device platform TTS engine. This works as a baseline, but it does not meet the intended product direction.

Current issues:
- `apps/payabo_mobile/lib/features/chat/domain/chat_voice_service.dart` mixes speech recognition, speech synthesis, and local thinking-loop playback in one service.
- The current Flutter chat stack is directly coupled to device TTS behavior rather than a product-owned abstraction.
- There is no backend-managed TTS provider layer, so ElevenLabs cannot be introduced cleanly without leaking vendor details into the app.
- There is no tenant-level voice configuration model for brand voice selection.
- There is no secure admin-managed secret storage path for host defaults and tenant-specific ElevenLabs credentials.
- There is no durable backend audit trail for TTS generation requests.
- There is no structured fallback flow that logs provider failure and then uses device TTS.
- The current chat UX uses TTS word progress for speaking pulse animation, which is not required for the target provider model.

## Goals

- Introduce a clean TTS abstraction on both backend and mobile.
- Use ElevenLabs through the backend only.
- Preserve a clean provider swap path for future TTS engines.
- Support streaming audio playback to the Android app.
- Support tenant-scoped voice configuration and provider options.
- Support a platform-managed ElevenLabs credential plus optional tenant override without exposing secrets back to clients.
- Preserve chat text streaming independently of audio playback.
- Log and audit failures before falling back to Android native TTS.
- Keep the first implementation focused on chat TTS while making the abstraction reusable elsewhere.

## Non-Goals

- Replace on-device speech recognition in this phase.
- Redesign the AG-UI chat streaming protocol to carry binary audio.
- Support iOS in phase 1.
- Add word or character timing synchronization.
- Expose ElevenLabs credentials to the mobile app.
- Build a generalized voice-cloning workflow in the MVP.

## Architectural Principles

- The mobile app depends on product-owned abstractions, not vendor SDKs.
- Provider-specific logic stays behind backend interfaces.
- Tenant configuration resolves the active voice and provider behavior.
- Credential resolution is backend-only and prefers tenant override, then host default, then configuration fallback.
- AG-UI continues to stream text as the conversational source of truth; TTS is a separate playback concern.
- Spoken output is a server-authored render of the assistant turn, not a naive readout of the full display text.
- Backend-managed provider failure is logged before native fallback occurs.
- Raw assistant text should not be stored in audit fields when references and hashes are sufficient.
- The smallest correct change is to preserve the current chat text transport and add a side-channel speech payload plus a simple authenticated TTS endpoint.

## MVP Simplifications

- Support Android only.
- Support TTS only; keep STT on-device using the current Flutter stack.
- Use ElevenLabs as the only backend provider in phase 1, but behind a generic interface.
- Keep the current sentence or stable-chunk queueing model in the chat UI.
- Use a separate authenticated mobile TTS endpoint instead of embedding audio into AG-UI SSE.
- Replace word-driven speaking animation with a simpler playback-state pulse.
- Use server-authored speech text for audio mode via AG-UI `CUSTOM` events.

## Target Architecture

The target design is a four-part TTS architecture.

### 1. Mobile composition model
`ChatVoiceService` + `TextToSpeechService`

The chat UI keeps using a single orchestration facade, but the actual TTS behavior is delegated to a dedicated abstraction with interchangeable implementations.

### 2. Tenant configuration model
Tenant TTS settings

The active provider, voice, locale, output format, and fallback behavior are tenant-scoped configuration resolved by the backend.

### 2b. Credential management model
Host default plus tenant override

Persisted ElevenLabs credentials are stored separately from normal tenant TTS JSON settings. The backend resolves credentials in this order:

1. tenant-scoped override
2. host-managed default
3. configuration fallback for bootstrap and local development

### 3. Backend provider model
`ITextToSpeechProvider`

Provider-specific integrations such as ElevenLabs implement a backend abstraction and are resolved through registration rather than hard-coded selection.

### 4. Mobile delivery model
Speech render + synth endpoint

The mobile app receives a server-authored speech render alongside the normal AG-UI chat stream and sends that speech text to an authenticated backend synth endpoint that returns audio bytes for playback.

## Recommended Mobile Refactor

The current `ChatVoiceService` should remain as the UI-facing entry point, but its responsibilities should be split internally into three components:

- `SpeechRecognitionService`
- `TextToSpeechService`
- `ThinkingLoopAudioService`

This keeps the current chat screen integration small while creating a reusable seam for TTS provider changes.

### Recommended Flutter TTS contract

```dart
abstract class TextToSpeechService {
  Future<void> speak(
    String text, {
    VoidCallback? onStart,
    VoidCallback? onComplete,
    VoidCallback? onCancel,
    ChatVoiceErrorCallback? onError,
    String? localeTag,
  });

  Future<void> stop();
  Future<void> dispose();
}
```

### Recommended Flutter implementations

- `BackendTextToSpeechService`
- `NativeTextToSpeechService`
- `FallbackTextToSpeechService`

`FallbackTextToSpeechService` should attempt backend synthesis first and fall back to native TTS only when backend generation or playback fails. User-initiated stop and cancel paths should not trigger fallback.

## Backend Design

### Module ownership

- `Aonik.Platform` owns tenant TTS settings and tenant admin endpoints.
- `Aonik.Ai` owns provider abstraction, provider implementation, and execution audit concerns.
- `Aonik.Api` exposes authenticated mobile-facing TTS endpoints.

### Dependency injection ownership

- `Aonik.Ai` should register `ITextToSpeechProvider`, `ITextToSpeechService`, HTTP clients, and provider-specific options in module-level service registration.
- `Aonik.Platform` should register the typed tenant TTS settings service and admin settings endpoints.
- `Aonik.Api` should only compose modules and expose endpoints; it should not contain provider-specific wiring beyond normal module startup.
- This keeps provider implementation details out of host startup and matches the existing module-first registration style.

### Recommended backend contracts

```csharp
public record TextToSpeechVoiceProfile(
    string Provider,
    string VoiceId,
    string? ModelId,
    string? Locale,
    string? OutputFormat,
    Dictionary<string, string?> ProviderOptions);

public record TextToSpeechSettingsSnapshot(
    bool Enabled,
    bool FallbackToNativeOnFailure,
    TextToSpeechVoiceProfile DefaultProfile);

public interface ITextToSpeechProvider
{
    string Name { get; }

    Task<TextToSpeechStreamResult> SynthesizeAsync(
        TextToSpeechProviderRequest request,
        CancellationToken cancellationToken = default);

    Task<IReadOnlyList<TextToSpeechVoiceOption>> GetVoicesAsync(
        CancellationToken cancellationToken = default);
}

public interface ITextToSpeechService
{
    Task<TextToSpeechSynthesisResult> SynthesizeAsync(
        TextToSpeechSynthesisRequest request,
        CancellationToken cancellationToken = default);
}
```

### Provider resolution

- Register TTS providers with `IEnumerable<ITextToSpeechProvider>`.
- Resolve the active provider from tenant settings.
- Keep ElevenLabs-specific request and response mapping inside `ElevenLabsTextToSpeechProvider`.
- Do not let controller or endpoint code branch on provider-specific behavior.

## Cost Controls And Policy Limits

ElevenLabs is usage-billed, so the MVP must include lightweight guardrails even if it does not implement full billing integration.

### Required policy controls

- Maximum text length per utterance.
- Maximum TTS utterance creation requests per user per minute.
- Optional monthly tenant character budget.
- Clear rejection responses when a tenant or user exceeds policy.

### MVP behavior

- Apply limits before provider synthesis begins.
- Treat policy-limit rejections as non-provider failures.
- Allow native fallback only for provider or transport failures, not for rate-limit or budget rejection by default.

## Tenant Settings Model

Use the existing tenant settings infrastructure and expose a typed TTS settings service above the generic key-value store.

The simplest backend shape is one tenant-scoped JSON setting.

The tenant setting should also carry optional policy controls such as maximum utterance length and request limits.

### Required tenant admin endpoints

- `GET /tenant/settings/text-to-speech`
- `PUT /tenant/settings/text-to-speech`
- `GET /tenant/settings/text-to-speech/voices?provider=ElevenLabs`

- `GET /tenant/settings/text-to-speech/credentials`

### Required host admin endpoints

- `GET /admin/settings/text-to-speech/credentials/host`
- `PUT /admin/settings/text-to-speech/credentials/host`

These endpoints should be platform-admin protected and return credential presence and effective-source metadata only.

## Credential Storage And Protection

Persisted ElevenLabs API keys are encrypted before storage using ASP.NET Core Data Protection with the shared purpose used by the settings protection flow.

### Protection rules

- Persist the shared Data Protection key ring to the database, not local machine storage only.
- Use a consistent application name so all app instances share the same key ring.
- Store TTS provider secrets outside generic `SettingDefinitions` to avoid accidental exposure through generic settings APIs.
- Never return raw saved API keys from backend read endpoints.

## Mobile-Facing Backend Endpoints

Use a single authenticated synth endpoint for the MVP.

### Recommended endpoint

- `POST /mobile/text-to-speech/synthesize`

### Why the simple authenticated shape is preferred for MVP

- It keeps the implementation smaller and easier to verify.
- It avoids extra transport-state machinery such as utterance stores and signed stream URLs.
- The client still talks only to the AONIK backend, never directly to ElevenLabs.
- It preserves the option to move to direct stream playback later if latency demands it.

### Example synth request

```json
{
  "speechText": "Your transport spending went up this week. I've highlighted the details on screen.",
  "locale": "en-US",
  "threadId": "abc123",
  "messageId": "msg456"
}
```

### Example response

- HTTP 200 with audio bytes in the response body
- `Content-Type: audio/mpeg`
- optional response headers for provider and `AiRunId`

## AG-UI Speech Side-Channel

The backend should not rely on the client to derive spoken output from raw display text. Instead, the backend should emit a dedicated speech payload alongside the normal AG-UI stream.

### Recommended AG-UI extension

Emit a `CUSTOM` event named `speech.render`.

### Example AG-UI custom event

```json
{
  "type": "CUSTOM",
  "name": "speech.render",
  "value": {
    "messageId": "msg456",
    "speechText": "Your transport spending went up this week. I've highlighted the details on screen.",
    "requiresVisualAttention": true,
    "requiresApproval": false
  }
}
```

### Why this shape is preferred

- AG-UI text remains the canonical display stream.
- Tool calls remain separate structured events.
- Spoken output can be shorter, safer, and more action-aware than display text.
- The app can cue the user to inspect the thread when visual detail or explicit approval is required.

## Streaming Model

The recommended runtime flow is:

1. Payabo chat continues to receive assistant display text from `/ai/agui` using the existing SSE path.
2. The backend also emits `speech.render` custom events containing server-authored spoken text.
3. The mobile app prefers `speech.render.speechText` over raw assistant display text for audio mode.
4. The mobile app sends that speech text to `POST /mobile/text-to-speech/synthesize`.
5. The backend forwards the request to ElevenLabs and returns audio bytes.
6. The app plays the returned audio.
7. If the TTS request or playback fails, the app logs the error and falls back to native TTS if tenant configuration allows it.

This preserves the existing AG-UI contract and avoids introducing binary audio into the current chat event protocol.

### Concurrency behavior

- The chat speech queue should remain sequential.
- The mobile app should request the next synthesis only after the current chunk has started playback or failed.
- More advanced pipelining can be added later if latency becomes a UX issue.

## Audit And Telemetry

Each backend TTS request should be auditable.

### Minimum audit behavior

- Create an `AiRun` or equivalent execution record for each backend TTS request.
- Use a dedicated use case such as `payabo.chat.tts`.
- Persist references such as `threadId`, `messageId`, tenant, user, provider, voice, locale, text hash, and text length.
- Avoid storing raw text in audit fields unless there is a later explicit requirement.
- Mark success and failure explicitly.
- Log provider status codes and diagnostic details suitable for operations without leaking secrets.
- Distinguish policy rejection, transport failure, provider failure, and client cancellation in logs and outcomes.

### Important implementation note

The current `IAiRunWriter` and `AiRun` model are oriented toward existing chat and prompt flows. The implementation may need a small extension so TTS executions can record provider-specific model attribution more accurately instead of relying on the current default-model behavior.

## Failure And Fallback Model

Fallback behavior is required, but it must be explicit.

### Rules

- Backend generation failure should be logged on the server.
- Mobile playback failure should be logged on the client.
- If tenant settings allow fallback, the app should switch to Android native TTS for that chunk.
- User-triggered stop or cancel should not be treated as provider failure and should not activate fallback.
- Tenant policy rejection should not automatically activate fallback in the MVP.
- Chat text must continue flowing even if TTS fails entirely.

## UI Integration Notes

The current chat UI in `apps/payabo_mobile/lib/features/chat/presentation/chat_screen.dart` already maintains a speech queue and drains stable chunks sequentially. That flow should remain.

The main UI changes should be:

- stop depending on per-word TTS progress for speaking pulse animation
- prefer `speech.render` content over raw assistant display text when speaking
- use a simpler playback-state pulse animation
