Spec 034 Status: Draft Size: Large Priority: P1 Domain: Platform (+ Finance / PersonalFinance / Agents)

Task & WorkItem scheduling

A general-purpose, data-defined task primitive any module can use to say “do this thing, about this subject, at this time (or on this cadence)” — remind a customer their insurance is due, nudge them before a recurring family-support payment, or hand an agent a standing job set by the system owner. A durable WorkItem row is the source of truth; a single Quartz heartbeat in the Worker is the clock; and the action a due task performs is dispatched to a keyed ITaskActionHandler that each module contributes — the same extensibility shape as the shipped IProposalHandler pipeline (Spec 030). High-risk actions never run in-band: they marshal into a Proposal and execute only after approval, preserving “agents propose; systems execute.” The system lives inside the Platform module, beside Notifications, and is consumed cross-module through one SharedKernel.Abstractions.Tasks.ITaskService contract.

1. Summary

AONIK can schedule code (Quartz jobs, Spec 014), send notifications (Platform INotificationService), run agents, and marshal high-risk mutations into proposals (Spec 030). What it cannot do today is let a user, a module, or the system owner declare a data-defined unit of future work — “remind me 14 days before this policy renews,” “every month, two days before payday, prompt me to send money home,” “every Monday have the finance agent draft a cash-position summary.” Each of those is a row a non-engineer should be able to create at runtime, not a cron-wired IJob a developer compiles.

This spec introduces that primitive: a WorkItem — an objective, about a subject, due on a schedule, that fires an action when due. It is deliberately not a workflow engine and not a replacement for Quartz jobs. It is the thin, reusable “what should happen, and when” layer that sits above notifications, proposals, and agents and routes due work to them. Three pieces make it general:

PieceResponsibilityReuses
WorkItem / WorkItemRun entities Durable, tenant-scoped record of the task and each execution occurrence. Anemic entity + AonikDbContext migration stream conventions.
ITaskActionHandler (keyed by ActionType) The pluggable “what to do when due.” Each module registers its own. Exact shape of IProposalHandler keyed-DI dispatch.
WorkItemDispatchJob (one Quartz heartbeat) Polls due rows, leases them, dispatches to the handler, re-arms recurrences. Worker host + lease pattern from OutboxProcessor.
Success signals A module schedules future work with one ITaskService.ScheduleAsync call and never touches Quartz. A due reminder posts a notification; a due “pay the bill” task produces a Proposal a human approves — money never moves from the scheduler itself; a due agent job runs the agent and records an AiRun. Adding a new kind of task action is one new ITaskActionHandler in the owning module, with no change to the scheduler.

2. Problem: no task primitive

Everything needed to act on future work already exists; what is missing is the durable, user-/module-authored declaration of the work itself. The current building blocks and why none of them is the primitive:

Existing capabilityWhat it givesWhy it isn't a task primitive
Quartz scheduled jobs (Spec 014) Cron-driven recurring code, clustered, persisted. A job is compiled by a developer and runs the same logic for the whole platform. There is no per-tenant, per-user, runtime-created instance with its own subject and payload.
Notifications (Platform INotificationService) Deliver an in-app/push/email/SMS message now. No notion of “later” or “repeating.” It is the delivery channel a reminder task would call when due, not the schedule.
Proposals (Spec 030) Durable approve-then-execute boundary for a mutation. A proposal is created reactively by an agent turn. There is no time/recurrence dimension and nothing creates one on a schedule.
Agent workflows (graph executors) Orchestrate multi-step agent runs. Heavyweight, agent-centric, and triggered, not a lightweight “remind me” row a customer creates in Payabo.

The three concrete asks that motivate this — an insurance-due reminder, a recurring family-support payment nudge, and a system-owner-assigned agent job — today would each require bespoke entities, bespoke jobs, and bespoke endpoints in three different modules. They are the same shape. Building it three times is the problem.

3. One shape behind three scenarios

Strip the three scenarios to their dimensions and they coincide:

DimensionInsurance reminderFamily-support paymentAgent job
About (subject)a policy / billa payee / orderanything, or nothing
When (schedule)one-off, lead-time before duerecurring, monthlynow, or recurring
Who acts (assignee)SystemSystem → humanAgent
What happens (action)notify the customernotify, or raise a payment proposalrun the agent; agent proposes mutations

So a task is fully described by four fields — subject, schedule, assignee, action — plus lifecycle. That is the entire conceptual model. The variation between scenarios collapses into different values of ActionType and different action handlers, not different entities.

Naming The CLR entity is named WorkItem, not Task, to avoid colliding with System.Threading.Tasks.Task in every service signature. The product / API vocabulary remains “task” (routes are /tasks/*, the contract is ITaskService, DTOs are ScheduleTaskRequest/TaskResponse). “WorkItem” is an internal implementation name.

4. Domain model

Two anemic, tenant-scoped entities (AuditableEntity, ITenantScoped), following the Finance/PersonalFinance grain. They live in the Platform module under src/Aonik.Platform/Entities/Tasks/.

new WorkItem — the durable task

public class WorkItem : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }

    // What & why
    public string Title { get; set; } = string.Empty;
    public string? Description { get; set; }
    public string Kind { get; set; } = string.Empty;        // Reminder | ScheduledAction | AgentAssignment

    // About (polymorphic soft reference — NOT a cross-module FK)
    public string? SubjectType { get; set; }                // "Bill" | "Order" | "Party" | ...
    public Guid? SubjectId { get; set; }

    // Who acts
    public string AssigneeType { get; set; } = string.Empty; // System | User | Agent
    public Guid? AssigneeId { get; set; }                    // userId, or null for System
    public string? AssigneeKey { get; set; }                 // agent descriptor name when Agent

    // What happens when due — the extensibility seam
    public string ActionType { get; set; } = string.Empty;   // "notify_user" | "create_payment_proposal" | "run_agent" | ...
    public string ActionPayloadJson { get; set; } = "{}";    // handler-specific arguments

    // When
    public string ScheduleType { get; set; } = string.Empty; // OneOff | Recurring
    public DateTime? NextRunAtUtc { get; set; }              // null once terminal
    public string? RecurrenceCron { get; set; }              // Quartz/cron expression when Recurring
    public string? Timezone { get; set; }                    // IANA id for cron evaluation
    public DateTime? StartAtUtc { get; set; }
    public DateTime? EndAtUtc { get; set; }
    public int RunCount { get; set; }
    public int? MaxRuns { get; set; }

    // Lifecycle
    public string Status { get; set; } = string.Empty;       // Scheduled | InProgress | Completed | Cancelled | Failed | Paused
    public int Priority { get; set; }
    public string SourceModule { get; set; } = string.Empty; // origin: "PersonalFinance", "Platform", ...
    public string? CorrelationId { get; set; }

    // Clustering safety (claim-before-execute lease — mirrors OutboxMessage)
    public DateTime? LeasedUntilUtc { get; set; }
    public string? LeasedBy { get; set; }
    public int AttemptCount { get; set; }
    public string? LastError { get; set; }
}

new WorkItemRun — one execution occurrence

Every dispatch writes a run row (mirrors WorkflowRun / AiRun): the audit trail and the idempotency anchor for recurring items. 

public class WorkItemRun : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid WorkItemId { get; set; }
    public DateTime ScheduledForUtc { get; set; }            // the occurrence instant this run satisfies
    public DateTime StartedAtUtc { get; set; }
    public DateTime? CompletedAtUtc { get; set; }
    public string Outcome { get; set; } = string.Empty;      // Succeeded | Failed | Skipped | Proposed
    public string? ResultJson { get; set; }                  // handler result summary
    public string? Error { get; set; }
    public Guid? AiRunId { get; set; }                       // set when the action invoked AI
    public Guid? ProposalId { get; set; }                    // set when the action raised a Proposal
}

(WorkItemId, ScheduledForUtc) is unique — the dispatcher will not create two runs for the same occurrence even if two workers race or the heartbeat double-fires.

5. The action-handler seam

The one design choice that makes this general rather than three special cases: a due task does not contain its own execution logic. It carries an ActionType string, and the dispatcher resolves a keyed ITaskActionHandler for it — the identical pattern AONIK already uses for IProposalHandler (keyed by ProposalType). The contract lives in SharedKernel so any module can implement one without depending on the Tasks code: 

// src/Aonik.SharedKernel/Abstractions/Tasks/ITaskActionHandler.cs
public interface ITaskActionHandler
{
    string ActionType { get; }   // DI key, e.g. "notify_user"

    Task<TaskActionResult> ExecuteAsync(TaskActionContext context, CancellationToken cancellationToken = default);
}

public sealed record TaskActionContext(
    Guid TenantId,
    Guid WorkItemId,
    Guid RunId,
    string Kind,
    string? SubjectType,
    Guid? SubjectId,
    string AssigneeType,
    Guid? AssigneeId,
    string? AssigneeKey,
    DateTime ScheduledForUtc,
    string ActionPayloadJson);

public sealed record TaskActionResult(
    TaskActionOutcome Outcome,           // Succeeded | Failed | Skipped | Proposed
    string? ResultJson = null,
    string? Error = null,
    Guid? AiRunId = null,
    Guid? ProposalId = null);

Handlers register as keyed scoped services in their owning module. The dispatcher resolves by the row's ActionType: 

// Platform module
services.AddKeyedScoped<ITaskActionHandler, NotifyUserTaskActionHandler>("notify_user");
// Finance module
services.AddKeyedScoped<ITaskActionHandler, CreatePaymentProposalTaskActionHandler>("create_payment_proposal");
// Agents module
services.AddKeyedScoped<ITaskActionHandler, RunAgentTaskActionHandler>("run_agent");
Why handlers, not events A due task could simply publish a WorkItemDueEvent on the outbox and let modules subscribe. We chose direct keyed dispatch as the primary path because it returns a structured result (so the run row records what happened, including a spawned proposal / AI run), supports retry with attempt counting, and gives clear failure semantics — none of which fire-and-forget events provide. A WorkItemDueEvent may additionally be published for passive observers (see Open decisions), but it is not the execution mechanism.

6. Scheduling & dispatch

Two layers: the durable rows are the source of truth for what is due; one Quartz job is the clock. We deliberately do not create one Quartz trigger per task — that does not scale to many tenants × many reminders and complicates clustering.

WorkItemDispatchJob (Quartz, every 1 min, [DisallowConcurrentExecution], system-tenant context) │ │ 1. SELECT due: Status = Scheduled AND NextRunAtUtc <= now AND (LeasedUntilUtc IS NULL OR expired) ▼ ┌───────────────────────────────────────────────────────────────┐ │ for each due WorkItem (batched): │ │ 2. CLAIM lease (LeasedUntilUtc = now+N, LeasedBy = instance) │ ── clustering-safe, like OutboxProcessor │ 3. INSERT WorkItemRun (WorkItemId, ScheduledForUtc) [unique] │ ── idempotent per occurrence │ 4. resolve ITaskActionHandler by ActionType ───────────────▶ │ NotifyUser / CreatePaymentProposal / RunAgent ... │ 5. ExecuteAsync(context) ──▶ TaskActionResult │ │ 6. record outcome on run; bump RunCount/AttemptCount │ │ 7. RE-ARM: if Recurring & under MaxRuns/EndAt → │ │ NextRunAtUtc = nextCronFire(now); Status = Scheduled │ │ else → Status = Completed; NextRunAtUtc = null │ └───────────────────────────────────────────────────────────────┘

Key behaviours:

  • Lease before execute. A claimed row is invisible to other workers until the lease expires, so a clustered Worker fleet never double-fires. On crash mid-execution the lease lapses and the occurrence is retried (bounded by AttemptCount / a max-attempts option).
  • Occurrence idempotency. The unique (WorkItemId, ScheduledForUtc) run row is the dedupe key; a handler that itself mutates must still be idempotent (GET-before-act), exactly as proposal handlers are.
  • Recurrence. RecurrenceCron + Timezone drive the next fire time, computed with Quartz's CronExpression (already a dependency). One-off tasks complete after a single successful run. MaxRuns / EndAtUtc bound recurrences.
  • System-tenant scan. The job seeds null tenant context to see all tenants' due rows (the established pattern in FinancialConnectionRecurringSyncJob), then sets the row's TenantId into context before invoking the handler so all downstream writes are correctly tenant-scoped.
  • Granularity. Minute-level. Reminders and nudges do not need sub-minute precision; if a future case does, that case is a Quartz job, not a WorkItem.

7. The propose-don't-execute guarantee

The scheduler is a powerful new thing that can fire on its own clock with no human in the loop at the moment of firing. The non-negotiable rule (“Agents propose; systems execute — never bypass human-in-the-loop for mutations”) therefore applies with full force. The discipline:

Action riskExamplesWhat the handler does when due
Low Send a reminder/notification, dismiss a stale item, write an audited personal-state flag Runs in-band; writes an audit/run record. Safe — reversible, no money.
Medium Create a draft invoice/bill on a schedule Runs in-band but writes a draft requiring downstream confirmation; never auto-finalised.
High Capture a payment, pay a bill, payout, post to the ledger, partner call Never runs in-band. The handler creates a Proposal (Spec 030) and returns Outcome = Proposed; the money moves only when a human approves it and the Spec 030 dispatcher executes the IProposalHandler.
Hard rule A WorkItem action handler must not call a high-risk domain service (payment capture, payout, ledger posting, partner API) directly. Its only permitted effect for such actions is to create a Proposal. This keeps the scheduler from becoming a backdoor around the Spec 030 / Spec 032 mutation boundary. The “pay mum's bill automatically” case is therefore “on schedule, raise a proposal the customer (or an autonomy-tiered policy) approves” — not “the scheduler moved money.”

8. Cross-module contract

Modules schedule and manage tasks through one contract in SharedKernel.Abstractions.Tasks — they never reference Platform's task entities, mirroring how PersonalFinance reads Finance only through SharedKernel contracts (ADR-006). 

// src/Aonik.SharedKernel/Abstractions/Tasks/ITaskService.cs
public interface ITaskService
{
    Task<TaskResponse> ScheduleAsync(ScheduleTaskRequest request, CancellationToken ct = default);
    Task<TaskResponse?> GetAsync(Guid taskId, CancellationToken ct = default);
    Task<IReadOnlyList<TaskResponse>> ListForSubjectAsync(string subjectType, Guid subjectId, CancellationToken ct = default);
    Task<IReadOnlyList<TaskResponse>> ListForAssigneeAsync(string assigneeType, Guid? assigneeId, CancellationToken ct = default);
    Task PauseAsync(Guid taskId, CancellationToken ct = default);
    Task ResumeAsync(Guid taskId, CancellationToken ct = default);
    Task CancelAsync(Guid taskId, CancellationToken ct = default);
}

public sealed record ScheduleTaskRequest(
    string Title,
    string Kind,                       // Reminder | ScheduledAction | AgentAssignment
    string ActionType,                 // must match a registered ITaskActionHandler
    string ActionPayloadJson,
    string AssigneeType,
    Guid? AssigneeId = null,
    string? AssigneeKey = null,
    string? SubjectType = null,
    Guid? SubjectId = null,
    DateTime? RunAtUtc = null,         // OneOff
    string? RecurrenceCron = null,     // Recurring
    string? Timezone = null,
    DateTime? StartAtUtc = null,
    DateTime? EndAtUtc = null,
    int? MaxRuns = null,
    string? Description = null,
    int Priority = 0,
    string? CorrelationId = null);

Implemented by WorkItemService in Platform and registered Scoped. A consumer example — PersonalFinance arming an insurance reminder when a bill with a due date is created: 

await _taskService.ScheduleAsync(new ScheduleTaskRequest(
    Title: $"Insurance due: {bill.Name}",
    Kind: "Reminder",
    ActionType: "notify_user",
    ActionPayloadJson: JsonSerializer.Serialize(new {
        userId, severity = "Warning",
        title = "Insurance renewal coming up",
        body  = $"{bill.Name} is due on {bill.DueDate:d}." }),
    AssigneeType: "System",
    SubjectType: "Bill", SubjectId: bill.Id,
    RunAtUtc: bill.DueDate.AddDays(-14).ToUniversalTime(),
    CorrelationId: bill.Id.ToString()), ct);

9. Walking the three scenarios

9.1 “Remind me when my insurance is due”

  • Row: Kind=Reminder, ScheduleType=OneOff, NextRunAtUtc = dueDate − leadTime, AssigneeType=System, ActionType="notify_user", payload = { userId, title, body }.
  • When due: dispatcher → NotifyUserTaskActionHandler → INotificationService.CreateForUserAsync(...). Outcome Succeeded; one-off, so the WorkItem completes.
  • Annual policy? Set ScheduleType=Recurring, RecurrenceCron for the yearly lead-time date; it re-arms after each run.

9.2 “Nudge me before mum's monthly payment”

  • Reminder flavour: identical to 9.1 but Recurring monthly — the customer is prompted and acts manually.
  • Scheduled-payment flavour: ActionType="create_payment_proposal", SubjectType="Order". When due, the Finance handler creates a Proposal (high risk) and returns Outcome=Proposed with the ProposalId stamped on the run. The customer approves it (in Payabo / approvals queue) and the Spec 030 dispatcher captures the payment. The scheduler never moved money.

9.3 “System owner assigns an agent a standing job”

  • Row: Kind=AgentAssignment, AssigneeType=Agent, AssigneeKey="finance-agent", ActionType="run_agent", payload = { agentName, brief, inputRefs }; Recurring (e.g. weekly).
  • When due: dispatcher → RunAgentTaskActionHandler → resolves the IDomainAgentDescriptor, runs the agent, records an AiRun (stamped on the run via AiRunId). Any mutation the agent wants flows through the normal proposal path — the agent task does not get a privileged execution route.

10. Placement & module wiring

The system lives inside the Platform module, beside Notifications — it is cross-cutting platform infrastructure consumed by many modules, and reuses PlatformDbContext rather than standing up a new module + DbContext. Layout follows the vertical-slice convention: 

src/Aonik.Platform/
├── Entities/Tasks/{WorkItem.cs, WorkItemRun.cs}
├── Services/Tasks/{WorkItemService.cs, WorkItemDispatcher.cs, RecurrenceCalculator.cs}
├── Contracts/Services/Tasks/   (Platform-internal extras, if any)
├── Contracts/Models/Tasks/     (API DTOs)
├── Endpoints/Tasks/{ScheduleTaskEndpoint.cs, ListTasksEndpoint.cs, CancelTaskEndpoint.cs, PauseResumeTaskEndpoint.cs}
└── Persistence/Configurations/Tasks/{WorkItemConfiguration.cs, WorkItemRunConfiguration.cs}

src/Aonik.SharedKernel/Abstractions/Tasks/
├── ITaskService.cs            (+ ScheduleTaskRequest, TaskResponse)
└── ITaskActionHandler.cs      (+ TaskActionContext, TaskActionResult, TaskActionOutcome)

src/Aonik.Worker/Jobs/WorkItemDispatchJob.cs   (the heartbeat)

Registration in PlatformModule.ConfigureServices: bind ITaskService → WorkItemService, WorkItemDispatcher, the "notify_user" keyed handler, and add WorkItem/WorkItemRun DbSets to PlatformDbContext. The dispatch job registers in the Worker via the existing ScheduledJobDefinitions factory with a cron of 0 * * * * ? (every minute) and a ScheduledJobOptions entry so it can be tuned/disabled per environment (Spec 014 pattern).

11. Persistence & migration

Per CLAUDE.md's single-migration-stream rule:

  • Add DbSet<WorkItem> and DbSet<WorkItemRun> to the canonical AonikDbContext and to PlatformDbContext (runtime read/write path).
  • Configurations as IEntityTypeConfiguration<T> in Aonik.Platform/Persistence/Configurations/Tasks/ — not inlined.
  • Tables dbo.AnkWorkItems, dbo.AnkWorkItemRuns (the Ank prefix convention).
  • Indexes: (Status, NextRunAtUtc) for the due-scan (the hot query), (SubjectType, SubjectId), (AssigneeType, AssigneeId), CorrelationId; unique (WorkItemId, ScheduledForUtc) on runs.
  • Migration is tool-generated only against AonikDbContext (dotnet ef migrations add AddWorkItems --project src/Aonik.Infrastructure --startup-project src/Aonik.Api), reviewed, and the .cs + .Designer.cs committed together. No hand-authored migrations.

12. Security, tenancy & audit

  • Tenancy. Both entities are ITenantScoped; query filters apply. The dispatch job scans across tenants under system context but stamps the row's TenantId into the ambient context before invoking a handler, so every downstream write is tenant-correct.
  • Authorisation. User-facing endpoints are policy-gated. A user may schedule/cancel only their own tasks; AgentAssignment tasks set by the system owner require an admin policy. ActionType is validated against the set of registered handlers at schedule time — an unknown action is rejected, not stored.
  • Audit. Every occurrence yields a WorkItemRun; high-risk actions additionally produce a Proposal and (for agents) an AiRun, so the full chain “task → run → proposal/AI run → approval → execution” is traceable by CorrelationId.
  • Payload safety. ActionPayloadJson is opaque to the scheduler and is handler-validated; handlers must treat it as untrusted input (it may originate from an agent or an end-user).

15. Acceptance criteria

  • A module schedules future work via a single ITaskService.ScheduleAsync call without referencing Platform task entities or Quartz.
  • A one-off reminder fires once at its time and the WorkItem becomes Completed; a recurring one re-arms to the next cron occurrence.
  • In a clustered Worker, a due task executes exactly once per occurrence (lease + unique run row verified under concurrent dispatch).
  • A high-risk action (create_payment_proposal) produces a Proposal and moves no money until approved; the run records Outcome=Proposed + ProposalId.
  • Scheduling an unknown ActionType is rejected at the API boundary.
  • Migration is tool-generated, applies cleanly, and tables are dbo.AnkWorkItems / dbo.AnkWorkItemRuns.

16. Open decisions

Open O1 — Also emit WorkItemDueEvent? Handler dispatch is the execution path; do we additionally publish a due event on the outbox for passive observers (analytics, other modules)? Leaning yes, but only after Phase 5 if a consumer needs it.
Open O2 — Recurrence expression. Quartz CronExpression (zero new deps, but no “every 2 weeks from date X”) vs. an RRULE library (richer calendar recurrence). Proposal: start with cron; add RRULE only if a product needs it.
Open O3 — Autonomy for high-risk recurring tasks. Should a customer be able to pre-authorise a recurring payment so the proposal auto-approves under a risk-tier policy (Spec 032), or must every occurrence be approved? Default to per-occurrence approval; revisit with the autonomy-tier work.
Open O4 — Retry/back-off policy. Max attempts and back-off curve for failed occurrences (and whether a failed occurrence blocks the next recurrence or is skipped). Proposal: bounded attempts, skip-and-continue for recurring, surface failures in the admin list.
