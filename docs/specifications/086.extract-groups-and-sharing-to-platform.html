Spec 086 Status: Draft (Rev 1) Size: Large Priority: P1 Domain: Platform / PersonalFinance / SharedKernel

Extract groups and sharing to Platform

Implements ADR-015. Group membership (Household, Spec 020) and scoped sharing (CircleGrant, Spec 048) are generic capabilities currently owned by Aonik.PersonalFinance. This spec relocates them to a Groups slice in Aonik.Platform and generalises them along exactly three axes: a member is a Party, not a User; a shared resource is a ResourceKind + ids pair rather than a typed foreign key; and domain-specific grant terms move into an opaque TermsJson blob the platform never reads. Every existing route and DTO is preserved and delegated, so Simi's mobile app and the CLI observe no change.

1. Summary

Two capabilities that every product on the platform needs — a group of people with roles and scoped, revocable, invite-based sharing — are implemented once, correctly, inside the wrong module. A second product cannot reach them: ADR-005 forbids direct cross-module references, and depending on Aonik.PersonalFinance from a non-finance product would be wrong even if it did not.

This spec moves them to Aonik.Platform and changes three things about their shape. Nothing else.

Why this is cheaper than it looks Every module maps to the same table prefix (ModuleTablePrefixes sets Platform = Finance = Ai = Agents = Commerce = "Ank") and the runtime schema is dbo for all of them. Relocating code between modules changes no table name and moves no row. The entire schema delta in this spec is two added columns and one nullability change.

3. Scope (in / out)

3.1 In scope

  • A Groups vertical slice in Aonik.Platform: Group, GroupMember, ShareGrant, ShareInvite + configurations + services.
  • The three model generalisations: party member, resource kind, terms blob.
  • Two extension seams: IGroupMemberRemovalGuard and IShareResourceResolver.
  • Contracts in SharedKernel.Abstractions.Groups.
  • Rewiring Aonik.PersonalFinance to delegate, keeping every route, DTO and status code identical.
  • Relocating the Household* integration events out of FinanceEvents.cs.
  • Schema: PartyId added, UserId made nullable, ResourceKind and TermsJson added; backfills.

3.2 Out of scope

  • Nested groups, groups owning resources, per-field ACLs, a permission DSL, cross-tenant sharing.
  • Removing PermissionsJson.
  • Renaming any table or column (properties are renamed; storage names are pinned by explicit mapping).
  • Making GroupMember.PartyId required — phase two, after backfill is confirmed everywhere.
  • A Guardian relationship type and verifiable-consent fields on PartyConsent. Both are real gaps (see §16) and belong with the product specs that need them.
  • Any Arke Kids feature. This spec is product-neutral and would be worth doing on its own merits.

4. The target model

Aonik.Platform / Entities / Groups ├── Group TenantId, Kind, Name, Members ├── GroupMember GroupId, PartyId, UserId?, Role, invitation lifecycle ├── ShareGrant OwnerPartyId, MemberPartyId?, GroupId?, Scope, │ ResourceKind, ResourceIdsJson, TermsJson, Status └── ShareInvite Token, Scope, ResourceKind, ResourceIdsJson, TermsJson, Channel?, ExpiresAt, Status, ConsumedAt, GrantId?
EntityWasNotes
Group renamed Household Gains Kind, an open string with a known-values helper (household, family) — the OrderType / BusinessType precedent. Existing rows backfill to household.
GroupMember renamed HouseholdMember PartyId added; UserId becomes nullable and is retained through phase one. PermissionsJson carried verbatim, deprecated.
ShareGrant renamed CircleGrant OwnerUserId/MemberUserId become party ids; ResourceKind and TermsJson added; NoAmounts moves into terms.
ShareInvite renamed CircleInvite Token semantics unchanged: opaque, 256-bit, cryptographically random, single-use, expiring, unique per tenant, the row being the record of truth.
Naming Platform code says Group and ShareGrant. "Circle", "household" and "family" are product vocabulary and stay in product UIs and their DTOs, per ADR-013. Renaming the platform entity does not rename anything a user reads.

5. A member is a Party

This is the decision the spec turns on. GroupMember points at a Party, not a User. Users already resolve to parties through ICurrentPartyResolver; a person who never authenticates is simply a party with no user.

Three things fall out of it for free, all already present in Aonik.Platform/Entities/Party:

NeedExisting entity
A person in a group who cannot log inParty — open PartyType, DisplayName, no user coupling
Kinship and authority edgesPartyRelationship + PartyRelationshipTypes
Consent recordsPartyConsent thin — see §16
An address the sharer must not seePartyAddress on the recipient's own party
Migration precondition The backfill assumes every existing HouseholdMember.UserId resolves to a party. This must be verified per environment before the backfill runs, and any orphan must be resolved or explicitly quarantined. Do not let the backfill silently skip rows — an unbackfilled member is an invisible loss of access.

6. Resource-kind polymorphism

A grant names what is shared as a ResourceKind (open string) plus a list of ids. The platform stores the pair and never interprets it. Each module registers a resolver for the kinds it owns: 

public interface IShareResourceResolver
{
    /// <summary>The resource kinds this resolver owns, e.g. "care-entity".</summary>
    IReadOnlyCollection<string> ResourceKinds { get; }

    /// <summary>Display refs for the given ids, owner-scoped. Unknown or non-owned ids are omitted.</summary>
    Task<IReadOnlyList<ShareResourceRef>> ResolveAsync(
        string resourceKind,
        Guid ownerPartyId,
        IReadOnlyCollection<Guid> resourceIds,
        CancellationToken cancellationToken = default);
}

public record ShareResourceRef(Guid Id, string Kind, string DisplayName);

Aonik.PersonalFinance registers care-entity. The invite preview asks the resolver for names rather than querying CareEntity directly, which is precisely the line the preview already splits along.

Validation A grant whose ResourceKind has no registered resolver is rejected at write time. This keeps the open string from becoming a typo sink, and mirrors how ToolNotClassifiedException fails closed in the agent approval gate.

6.1 Terms

TermsJson carries whatever the owning module needs and the platform stores opaquely. PersonalFinance moves NoAmounts into it: 

{ "noAmounts": true }

The platform must never branch on a term. Reading terms is the owning module's job, exactly as ADR-013 keeps product identity out of platform code.

7. The two extension seams

Both follow the module-contributed IEnumerable<T> DI pattern already used by the seeding and provisioning contributors.

7.1 IGroupMemberRemovalGuard

The one domain coupling in HouseholdService (HouseholdService.cs:658) becomes a contributed guard. PersonalFinance registers the PersonalAccounts check; the platform asks every guard and refuses removal if any objects, surfacing the reason. 

public interface IGroupMemberRemovalGuard
{
    /// <summary>Null when removal is allowed; otherwise a human-readable reason.</summary>
    Task<string?> CheckAsync(Guid groupId, Guid memberPartyId, CancellationToken cancellationToken = default);
}

7.2 IShareResourceResolver

As §6. Registered per module, keyed by ResourceKinds; duplicate ownership of a kind is a startup failure, not a last-writer-wins.

10. Persistence & migration

10.1 Table and column names are pinned, not renamed

Classes are renamed; storage is not. Configurations pin the existing names explicitly so the rename produces no DDL: 

builder.ToTable("Households", SchemaNames.Default);          // Group
builder.ToTable("HouseholdMembers", SchemaNames.Default);    // GroupMember
builder.ToTable("CircleGrants", SchemaNames.Default);        // ShareGrant
builder.ToTable("CircleInvites", SchemaNames.Default);       // ShareInvite

builder.Property(x => x.ResourceIdsJson).HasColumnName("EntityIdsJson");

Table prefixing continues through the existing helper; because ModuleTablePrefixes.Platform and .Finance are both "Ank", the physical names are identical before and after. Renaming storage to match the classes is deliberately deferred — pure churn, no functional content.

10.2 Schema delta

TableChangeBackfill
AnkHouseholdsadd Kind nvarchar'household'
AnkHouseholdMembersadd PartyId uniqueidentifier NULLresolved from UserId
AnkHouseholdMembersUserId → nullable—

NoAmounts is retained through phase one so a rollback needs no data recovery; the service reads terms and writes both. Owner/member id columns keep their names (OwnerUserId, MemberUserId) and are re-pointed to party ids by the same backfill, mapped to OwnerPartyId/MemberPartyId properties.

Migration rules The migration is CLI-generated only, against AonikDbContext, per CLAUDE.md. The backfills are not written into a migration body — hand-authoring migrationBuilder.Sql(…) is exactly the prohibited pattern. Backfill runs as an idempotent one-off Worker job that can be re-run, reports rows touched and rows skipped, and fails loudly on an unresolvable UserId. Order of operations: generate migration → apply → run backfill job → verify zero unbackfilled rows → flip services to read PartyId.

10.3 DbContext registration

  • AonikDbContext — the four DbSets stay (it owns all sets); the mapping helper changes from MapFinanceTable to MapPlatformTable, which is a no-op physically since both prefixes are "Ank".
  • PersonalFinanceDbContext — the four DbSets are removed; the module reaches groups through SharedKernel.Abstractions.Groups.
  • PlatformDbContext — the four DbSets are added. Its frozen migration folder is not touched.

11. Wire compatibility

The safety property Simi is live. No route, request body, response body, status code or error shape changes in this spec. Every existing endpoint stays at its current path and delegates. The Aonik.Cli circle command and its models are untouched. The proof is that the existing API and CLI tests pass with no edits.

IHouseholdService and ICircleService survive as PersonalFinance's own facades. Their implementations become thin: translate the module's DTOs, call the platform service, apply the domain projection. Callers inside PersonalFinance keep injecting the same interfaces.

12. Integration events

The Household* events are currently declared in SharedKernel/Events/Integration/FinanceEvents.cs — HouseholdCreatedEvent, HouseholdMemberInvitedEvent, HouseholdInvitationAcceptedEvent, HouseholdInvitationDeclinedEvent, HouseholdMemberRemovedEvent, HouseholdMemberLeftEvent. They move to a new PlatformEvents.cs (or GroupEvents.cs) in the same namespace.

Record names and payload shapes are unchanged in this pass. Renaming a published event contract is a separate decision with subscriber impact, and there is no reason to bundle it here.

13. Seeding & demo data

  • PersonalFinance/Services/Seeding/Phases/HouseholdsSeedPhase.cs moves to Platform's seeding phases; the DemoSeedPhase.Households enum value and the HouseholdIds / HouseholdMemberIds result keys in IDemoSeedContributor keep their names.
  • PersonalFinanceDemoDataReverser.ReverseHouseholdsAsync and IPersonalFinanceDemoDataReverser — the reversal moves with the phase; the interface method is retained and delegates, preserving the reversible-seed contract.
  • PlatformDemoSeedNames, PartySeedPhase, ReverseSeedPhase, DemoSeedService — updated references only.
  • Seeded members must now also seed a Party per member, or reuse the party PartySeedPhase already creates. Phase ordering: parties before groups.

14. Configuration sections

CircleInviteOptions.SectionName is "PersonalFinance:Circle". The generic half moves to "Platform:Sharing". To avoid a silent behaviour change on deployments that already set the old section, bind both, preferring the new one, and log a startup warning when only the legacy section is present. Removing the fallback is a follow-up.

16. Acceptance criteria

  1. Aonik.PersonalFinance contains no Household, HouseholdMember, CircleGrant or CircleInvite entity, and no DbSet for them.
  2. No module has a project reference to Aonik.Platform added by this change; all access is via SharedKernel.Abstractions.Groups.
  3. GroupMember.PartyId is populated for every row; UserId is nullable and still populated (phase one).
  4. A Group can hold a member whose Party has no User, end to end, proven by a test.
  5. A ShareGrant with an unregistered ResourceKind is rejected at write time.
  6. Removing a member who owns a shared PersonalAccount is still refused, now through IGroupMemberRemovalGuard, with the same message.
  7. Invite tokens keep their security properties: 256-bit random, opaque, single-use, expiring, unique per tenant, row-as-truth.
  8. CircleEndpointsTests, CliApplicationTests, FakeAonikCliApiClient and UserBriefProjectorTests pass with no edits. Any required edit is a wire break and must be justified or reverted.
  9. The generated migration contains only the six additive changes in §10.2 — no table rename, no drop, no unexpected operation.
  10. The demo seed still applies and reverses cleanly with households present.
  11. dotnet build Aonik.sln and dotnet test Aonik.sln green, plus the LocalDB lane.

17. Open decisions

#QuestionLeaning
O1 Does Group need an explicit owner, or is ownership a Role on GroupMember? Role. TransferHouseholdOwnershipEndpoint already works that way; do not add a second representation.
O2 Should ShareGrant.GroupId survive? It is nullable and optional today (Spec 048's open decision O2). Keep as-is. Removing it is a behaviour change dressed as a refactor.
O3 Do the Household* integration event names change to Group*? Not here. Subscriber impact, no functional gain, and it can ride a later change.
O4 Can one party be a member of several groups of the same kind? Allowed by the model; today's household rules enforce one. Keep the rule in GroupMembershipRules and make it kind-scoped, so family can differ from household later.

17.1 Gaps found, deliberately not fixed here

GapDetailHome
No Guardian relationship type PartyRelationshipTypes has Mother, Father, Child, Spouse, Sibling, Friend, Business, Other, Recipient, Self. Parental authority is not always parenthood, and Codes is a closed validation set, so adding one is a code change. The product spec that needs guardianship.
PartyConsent is thin Carries PartyId, ConsentType, GrantedAt, RevokedAt. A verifiable consent record also needs granted-by party, verification method and terms version. It also does not implement ITenantScoped (it is scoped through its party) — correct, but worth knowing. The product spec with a consent requirement.
PermissionsJson unenforced Carried across verbatim and deprecated. A later cleanup with its own migration.
