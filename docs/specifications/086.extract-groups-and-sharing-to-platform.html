Spec 086 Status: Draft (Rev 2) Size: Large Priority: P1 Domain: Platform / PersonalFinance / SharedKernel

Extract groups and sharing into a platform module

Implements ADR-015. Group membership (Household, Spec 020) and scoped sharing (CircleGrant, Spec 048) are generic capabilities currently owned by Aonik.PersonalFinance. This spec relocates them to a middle-layer Aonik.Groups module and generalises them along exactly three axes: a member is a Party, not a User; a shared resource is a ResourceKind + ids pair rather than a typed foreign key; and domain-specific grant terms move into an opaque TermsJson blob the platform never reads. Every existing route and DTO is preserved and delegated, so Simi's mobile app and the CLI observe no change.

1. Summary

Two capabilities that every product on the platform needs — a group of people with roles and scoped, revocable, invite-based sharing — are implemented once, correctly, inside the wrong module. A second product cannot reach them: ADR-005 forbids direct cross-module references, and depending on Aonik.PersonalFinance from a non-finance product would be wrong even if it did not.

This spec moves them to Aonik.Groups and changes three things about their shape. Nothing else.

Correction to Rev 1 Rev 1 placed the extracted code in a vertical slice inside Aonik.Platform, on the reasoning that Platform already owns the people layer and four entities do not warrant their own project. The reasoning is sound; the placement is impossible. Aonik.Platform already has a ProjectReference to Aonik.PersonalFinance, while Aonik.PersonalFinance references only SharedKernel — the absence Spec 027 §10 calls load-bearing. A Groups slice in Platform would therefore require PersonalFinance → Platform, inverting an existing edge into a cycle, and the build would not compile.

Rev 2 places it in a middle-layer Aonik.Groups module instead: referencing only SharedKernel, with Platform, PersonalFinance and Infrastructure depending on it downward. That is exactly where Aonik.Ordering sits (ADR-011), and it is the only placement the reference graph admits. Nothing else in this spec changes: the contracts still live in SharedKernel.Abstractions.Groups, and no consumer references the module directly.
Why this is cheaper than it looks Every module maps to the same table prefix (ModuleTablePrefixes sets Platform = Finance = Ai = Agents = Commerce = "Ank") and the runtime schema is dbo for all of them. Relocating code between modules changes no table name and moves no row. The schema delta is a handful of added columns, one nullability change, and — unavoidably — one unique-index replacement, because the existing index would reject a second member without a login (§10.2).

3. Scope (in / out)

3.1 In scope

  • A middle-layer Aonik.Groups module: Group, GroupMember, ShareGrant, ShareInvite + configurations + GroupsDbContext + services.
  • The three model generalisations: party member, resource kind, terms blob.
  • Two extension seams: IGroupLifecycleContributor (veto and react) and IShareResourceResolver.
  • Contracts in SharedKernel.Abstractions.Groups.
  • Rewiring Aonik.PersonalFinance to delegate, keeping every route, DTO and status code identical.
  • Relocating the Household* integration events out of FinanceEvents.cs.
  • Schema: party-id columns added alongside (never replacing) the user-id columns, UserId made nullable, the unique index replaced with filtered equivalents, ResourceKind and TermsJson added; backfill plus a dual-write window.

3.2 Out of scope

  • Nested groups, groups owning resources, per-field ACLs, a permission DSL, cross-tenant sharing.
  • Removing PermissionsJson.
  • Renaming any table or column (properties are renamed; storage names are pinned by explicit mapping).
  • Making GroupMember.PartyId required — phase two, after backfill is confirmed everywhere.
  • A Guardian relationship type and verifiable-consent fields on PartyConsent. Both are real gaps (see §16) and belong with the product specs that need them.
  • Any Arke Kids feature. This spec is product-neutral and would be worth doing on its own merits.

5. A member is a Party

This is the decision the spec turns on. GroupMember points at a Party, not a User. Users already resolve to parties through ICurrentPartyResolver; a person who never authenticates is simply a party with no user.

Three things fall out of it for free, all already present in Aonik.Platform/Entities/Party:

NeedExisting entity
A person in a group who cannot log inParty — open PartyType, DisplayName, no user coupling
Kinship and authority edgesPartyRelationship + PartyRelationshipTypes
Consent recordsPartyConsent thin — see §16
An address the sharer must not seePartyAddress on the recipient's own party
Migration precondition The backfill assumes every existing HouseholdMember.UserId resolves to a party. This must be verified per environment before the backfill runs, and any orphan must be resolved or explicitly quarantined. Do not let the backfill silently skip rows — an unbackfilled member is an invisible loss of access.

6. Resource-kind polymorphism

A grant names what is shared as a ResourceKind (open string) plus a list of ids. The platform stores the pair and never interprets it. Each module registers a resolver for the kinds it owns: 

public interface IShareResourceResolver
{
    /// <summary>The resource kinds this resolver owns, e.g. "care-entity".</summary>
    IReadOnlyCollection<string> ResourceKinds { get; }

    /// <summary>Display refs for the given ids, owner-scoped. Unknown or non-owned ids are omitted.</summary>
    Task<IReadOnlyList<ShareResourceRef>> ResolveAsync(
        string resourceKind,
        Guid ownerPartyId,
        IReadOnlyCollection<Guid> resourceIds,
        CancellationToken cancellationToken = default);
}

public record ShareResourceRef(Guid Id, string Kind, string DisplayName);

Aonik.PersonalFinance registers care-entity. The invite preview asks the resolver for names rather than querying CareEntity directly, which is precisely the line the preview already splits along.

Validation must check ownership, not just existence Requiring only that a resolver exists is not enough — it would let a caller persist another party's resource ids into a grant, and IShareGrantReader would then answer authorisation checks from the stored ids alone. That is a straightforward privilege escalation: share what you do not own, then read it.

At grant and invite creation the service:

  1. Rejects a ResourceKind with no registered resolver — keeping the open string from becoming a typo sink, and failing closed the way ToolNotClassifiedException does in the agent approval gate.
  2. Calls that resolver scoped to OwnerPartyId and rejects the write unless the returned id set exactly matches the requested set. A resolver omits ids the owner does not own, so any shortfall is an ownership failure.

Equality is the test, not containment: a resolver returning more than was asked for is a resolver bug, and accepting it silently would defeat the check.

6.1 Terms

TermsJson carries whatever the owning module needs and the platform stores opaquely. PersonalFinance moves NoAmounts into it: 

{ "noAmounts": true }

The platform must never branch on a term. Reading terms is the owning module's job, exactly as ADR-013 keeps product identity out of platform code.

7. The two extension seams

Both follow the module-contributed IEnumerable<T> DI pattern already used by the seeding and provisioning contributors.

7.1 IGroupLifecycleContributor

A veto cannot carry a side effect Rev 1 proposed a guard returning "allowed or a reason". That shape silently drops real behaviour: removing a member today clears PersonalProfile.HouseholdId, unshares every owned PersonalAccount, emits HouseholdAccountUnsharedEvent, and invalidates the financial life graph — and creation and invitation-acceptance write the profile link too. A refusal interface has nowhere to put any of it, and the existing RemoveMemberAsync_Should_ClearProfileAndUnshareOwnedAccounts test would fail.

The seam is therefore a lifecycle contributor: modules both veto and react.

public interface IGroupLifecycleContributor
{
    /// <summary>Null when the transition may proceed; otherwise a human-readable reason.</summary>
    Task<string?> VetoAsync(GroupTransition transition, CancellationToken cancellationToken = default);

    /// <summary>
    /// React to a committed transition — profile links, unsharing, cache invalidation, events.
    /// Runs inside the same transaction as the membership write, so a failure rolls the whole
    /// transition back rather than leaving a half-applied membership.
    /// </summary>
    Task OnCommittedAsync(GroupTransition transition, CancellationToken cancellationToken = default);
}

public sealed record GroupTransition(
    string Kind,          // created | member-added | invite-accepted | member-removed | ownership-transferred
    Guid GroupId,
    Guid? MemberPartyId,
    Guid? MemberUserId,   // null for party-only members — contributors must tolerate this
    Guid ActorPartyId);

PersonalFinance registers one contributor carrying every side effect listed above. The MemberUserId being nullable is load-bearing: a PersonalFinance profile is user-keyed, so its contributor skips party-only members rather than failing on them — a child has no personal-finance profile to link, and that is correct rather than an error.

7.2 IShareResourceResolver

As §6. Registered per module, keyed by ResourceKinds; duplicate ownership of a kind is a startup failure, not a last-writer-wins.

9.1 Adding a member who has no login

Without this, criterion 4 is unreachable Every existing membership path is an invitation, and an invitation is accepted by an authenticated principal. A child party has no login and can never accept one — so with the invite flow alone there is no way to put a party-only member into a group at all, and the central acceptance criterion of this spec cannot be met through the cross-module contract. 
/// <summary>
/// Add a party directly as a member — no invitation, because the party may have no user to accept one.
/// Authorised against the CALLER's ownership/admin role in the group, never against the added party.
/// </summary>
Task<GroupMemberDto> AddMemberAsync(
    Guid groupId,
    Guid partyId,
    string role,
    CancellationToken cancellationToken = default);

AddMemberAsync is the owner-authorised path, and the authorisation check is on the caller: a party is added by someone with the right, never by itself.

Two constraints, or this becomes a consent bypass An unconstrained partyId would let an owner add any user-backed adult straight into a group, skipping the invitation whose entire purpose is that person's consent — and would accept a party from another tenant unless the implementation invents an unstated lookup. Both are rejected at the contract:
  • The party must resolve in the current tenant; a foreign or unknown id is rejected, not silently accepted.
  • The party must not be linked to a user. A party with a login belongs on the invitation path, which is where its consent is recorded.

So the two paths partition cleanly rather than overlapping: invitation for anyone who can consent, direct addition for anyone who cannot. Neither can be used to do the other's job.

10. Persistence & migration

10.1 Table and column names are pinned, not renamed

Classes are renamed; storage is not. Configurations pin the existing names explicitly so the rename produces no DDL: 

builder.ToTable("Households", SchemaNames.Default);          // Group
builder.ToTable("HouseholdMembers", SchemaNames.Default);    // GroupMember
builder.ToTable("CircleGrants", SchemaNames.Default);        // ShareGrant
builder.ToTable("CircleInvites", SchemaNames.Default);       // ShareInvite

builder.Property(x => x.ResourceIdsJson).HasColumnName("EntityIdsJson");

Table prefixing continues through the existing helper; because ModuleTablePrefixes.Platform and .Finance are both "Ank", the physical names are identical before and after. Renaming storage to match the classes is deliberately deferred — pure churn, no functional content.

The index is not additive — and it would break child members HouseholdMemberConfiguration declares HasIndex(TenantId, HouseholdId, UserId).IsUnique(). SQL Server treats NULL as a value in a unique index and permits only one per key, so the moment UserId goes nullable a second party-only member in the same group fails to insert — the exact case criterion 4 requires. The unique index must be dropped and replaced with a filtered one, plus party-based uniqueness. This spec therefore performs one non-additive index change; §16's migration criterion is written accordingly.
Party ids are new columns, not re-pointed ones An earlier draft re-pointed OwnerUserId/MemberUserId in place. That is not rollback-safe and breaks production between phases: the deployed CircleService compares those columns against the authenticated user id (CircleService.cs lines 82, 92, 102, 128, 238, 319), so a P3 backfill writing party ids would make every grant and invite vanish — unrevocable, unacceptable — until the P5 reader cutover shipped. Instead: add separate party columns, dual-write both through the transition, cut readers over in P5, and drop the user columns in a later spec once no reader remains.

NoAmounts is likewise retained through the transition so a rollback needs no data recovery; the service reads terms and writes both.

Migration rules The migration is CLI-generated only, against AonikDbContext, per CLAUDE.md. The backfills are not written into a migration body — hand-authoring migrationBuilder.Sql(…) is exactly the prohibited pattern. Backfill runs as an idempotent one-off Worker job that can be re-run, reports rows touched and rows skipped, and fails loudly on an unresolvable UserId. Order of operations: generate migration → apply → run backfill job → verify zero unbackfilled rows → flip services to read PartyId.

10.3 DbContext registration

  • AonikDbContext — the four DbSets stay (it owns all sets); the mapping helper changes from MapFinanceTable to MapPlatformTable, which is a no-op physically since both prefixes are "Ank".
  • PersonalFinanceDbContext — the four DbSets are retained through P2–P6 and removed only in P7. Rev 1 scheduled the removal in both §10.3 and P7, which was self-contradictory.
  • PlatformDbContext — the four DbSets are added. Its frozen migration folder is not touched.

11. Wire compatibility

The safety property Simi is live. No route, request body, response body, status code or error shape changes in this spec. Every existing endpoint stays at its current path and delegates. The Aonik.Cli circle command and its models are untouched. The proof is that the existing API and CLI tests pass with no edits.

IHouseholdService and ICircleService survive as PersonalFinance's own facades. Their implementations become thin: translate the module's DTOs, call the platform service, apply the domain projection. Callers inside PersonalFinance keep injecting the same interfaces.

12. Integration events

The Household* events are currently declared in SharedKernel/Events/Integration/FinanceEvents.cs — HouseholdCreatedEvent, HouseholdMemberInvitedEvent, HouseholdInvitationAcceptedEvent, HouseholdInvitationDeclinedEvent, HouseholdMemberRemovedEvent, HouseholdMemberLeftEvent. They move to a new PlatformEvents.cs (or GroupEvents.cs) in the same namespace.

Record names and payload shapes are unchanged in this pass. Renaming a published event contract is a separate decision with subscriber impact, and there is no reason to bundle it here.

12.1 Party-based events are additive, not a rename

The old payloads cannot describe the new model Every Household* event carries a UserId. A party-only member has no user, so a platform operation that adds, removes or transfers ownership to one has no legal payload to publish — the moved contracts literally cannot represent the lifecycle this spec introduces.

Both sets exist, with a clear division:

Event setPublished byCarriesAudience
Household* unchanged The PersonalFinance compatibility facade UserId Existing subscribers. Emitted only when the member has a user, preserving today's contract exactly.
GroupMember* new The Platform group service PartyId (+ UserId?) New consumers. Emitted for every membership change, user-backed or not.

A user-backed change therefore emits both — the generic event for new consumers and the legacy event for existing ones. That duplication is the price of not breaking a live subscriber, and it ends when the legacy set is retired.

16. Acceptance criteria

  1. Aonik.PersonalFinance contains no Household, HouseholdMember, CircleGrant or CircleInvite entity, and no DbSet for them.
  2. Aonik.Groups references only Aonik.SharedKernel, and no module gains a project reference to Aonik.Platform from this change; behavioural access is via SharedKernel.Abstractions.Groups.
  3. GroupMember.PartyId is populated for every row; UserId is nullable and still populated (phase one).
  4. A Group can hold a member whose Party has no User, added through AddMemberAsync, end to end, proven by a test.
  5. Two party-only members can be added to the same group — the filtered-index case, proven on LocalDB (the InMemory provider does not enforce unique indexes and will pass regardless).
  6. A grant created before the P3 backfill remains listable, revocable and acceptable after the P5 reader cutover.
  7. A ShareGrant with an unregistered ResourceKind is rejected at write time.
  8. A ShareGrant naming a resource the owner does not own is rejected at write time, and never becomes readable through IShareGrantReader.
  9. AddMemberAsync rejects a party from another tenant, and rejects a party that has a user — the latter must go through the invitation flow.
  10. Removing a member still clears PersonalProfile.HouseholdId, unshares owned PersonalAccounts, emits HouseholdAccountUnsharedEvent and invalidates the life-graph cache — proven by the existing RemoveMemberAsync_Should_ClearProfileAndUnshareOwnedAccounts test passing unmodified.
  11. Creating a group and accepting an invitation still write PersonalProfile.HouseholdId.
  12. A lifecycle transition for a party-only member runs without the PersonalFinance contributor failing on the absent profile.
  13. Invite tokens keep their security properties: 256-bit random, opaque, single-use, expiring, unique per tenant, row-as-truth.
  14. CircleEndpointsTests, CliApplicationTests, FakeAonikCliApiClient and UserBriefProjectorTests pass with no edits. Any required edit is a wire break and must be justified or reverted.
  15. The generated migration matches §10.2 exactly: the additive columns plus the single unique-index drop/replace. No table rename, no column drop, no other operation.
  16. The demo seed still applies and reverses cleanly with households present.
  17. dotnet build Aonik.sln and dotnet test Aonik.sln green, plus the LocalDB lane.

17. Open decisions

#QuestionLeaning
O1 Does Group need an explicit owner, or is ownership a Role on GroupMember? Role. TransferHouseholdOwnershipEndpoint already works that way; do not add a second representation.
O2 Should ShareGrant.GroupId survive? It is nullable and optional today (Spec 048's open decision O2). Keep as-is. Removing it is a behaviour change dressed as a refactor.
O3 Do the Household* integration event names change to Group*? Not here. Subscriber impact, no functional gain, and it can ride a later change.
O4 Can one party be a member of several groups of the same kind? Allowed by the model; today's household rules enforce one. Keep the rule in GroupMembershipRules and make it kind-scoped, so family can differ from household later.

17.1 Gaps found, deliberately not fixed here

GapDetailHome
No Guardian relationship type PartyRelationshipTypes has Mother, Father, Child, Spouse, Sibling, Friend, Business, Other, Recipient, Self. Parental authority is not always parenthood, and Codes is a closed validation set, so adding one is a code change. The product spec that needs guardianship.
PartyConsent is thin Carries PartyId, ConsentType, GrantedAt, RevokedAt. A verifiable consent record also needs granted-by party, verification method and terms version. It also does not implement ITenantScoped (it is scoped through its party) — correct, but worth knowing. The product spec with a consent requirement.
PermissionsJson unenforced Carried across verbatim and deprecated. A later cleanup with its own migration.
