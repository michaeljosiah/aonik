Spec 043 Status: Draft (Rev 1) Size: Medium Priority: P1 (Simi M2 spine) Domain: PersonalFinance / Simi

CareEntity — people & assets you look after

The foundational object for the Simi mobile app: a CareEntity is a person ("Mum") or an asset you look after — a property, land, a vehicle, a business stake, a foreign account — each with a country, that owns commitments, payment history, documents, and per-currency totals. Today the Party model only types as Person | Organization (no asset of any kind), and the only neutral customer-facing entity CRUD is the generic financial-life-graph node API. This spec introduces a first-class, tenant- and user-scoped CareEntity in the PersonalFinance module with customer CRUD and a one-call profile projection. Implements Simi readiness plan §5.1.

Family of specs (043–048) This is the first of six specs that make AONIK "Simi-ready," one per identified backend gap. CareEntity is the spine the other five hang off: Spec 044 (commitment cycles), Spec 045 (payment logs), Spec 046 (vault linking), Spec 047 (capture parse), and Spec 048 (the circle). Build order starts here.

1. Summary

Simi is "the keeper of a cross-border life." Everything in it hangs off the people and the things a user looks after across borders. The Simi rebuild spec (§3.2) names this object a CareEntity and models it as person or place; the readiness review widened "place" to asset — a property, but equally land, a car, a business stake, or a foreign account — because the founding insight is inheritance and continuity ("anything a loved one would leave"), not location. From the system's point of view every CareEntity behaves identically: a named thing, in a country, that owns commitments, a payment history, documents, and per-currency totals.

No such neutral, customer-owned object exists today. This spec adds CareEntity to the PersonalFinance module (sibling to Finance, ADR-006), with consumer CRUD and a single-call profile projection that the People & Places screen renders from alone.

Success signals A consumer creates "Mum" (person, Nigeria) and "the Surulere flat" (asset / property, Nigeria) from the mobile app with a PersonalUser JWT — no admin surface, no remittance-beneficiary coupling. Tapping either one returns its whole profile in one call: per-currency year totals, its commitments, its recent payment logs, and its document thumbnails. A car, a plot of land, or a business stake is created the same way and behaves the same way. Nothing in the model says "Nigeria" or "remittance," so a Toronto→Kochi caregiver and a Leeds→Lagos flat are both first-class with zero corridor-specific code.

2. Problem & current state

Confirmed against the tree. Three facts shape the design:

  • Party cannot model an asset — and is not user-owned. Entities/Party/Party.cs carries a free-string PartyType, validated to "Person" | "Organization" only (PlatformValidators.cs:570 — the same rule repeats in FinanceValidators.cs:136: .Must(t => t is "Person" or "Organization")). There is no place/property/vehicle concept anywhere in the codebase. And Party has no UserId — it is tenant-scoped, a shared platform object, not a private per-user record.
  • The only neutral customer CRUD is generic graph nodes. POST /personal-finance/graph/nodes (UserPolicy) creates arbitrary financial-life-graph nodes (NodeType, DisplayName, MetadataJson) — untyped, with no country, no profile, no first-class fields. The direct /parties create is technically consumer-reachable (AdminUserPolicy includes the PersonalUser role) — but it writes the tenant-global platform Party above, with no per-user ownership, so it cannot serve as a private keeper object. The customer-facing Recipients surface is likewise reachable, but it is explicitly the "payout-beneficiary party graph (Spec 008)" — remittance-coupled, and exactly what Simi's mobile "great deletion" (M0) removes.
  • No one-call entity profile. The People profile screen needs entity + totals + commitments + recent logs + document refs in a single round-trip (rebuild spec §7.6 acceptance). Today that would be several queries against the graph; the graph returns the whole life graph, not one entity's rollup.

3. Scope (in / out)

3.1 In scope

  • New CareEntity entity (§5) — tenant + user scoped, in PersonalFinance.
  • New A kind = person | asset discriminator with an open assetType taxonomy and an attributesJson bag (§6).
  • New Customer CRUD endpoints: list, get, create, update, archive (§7).
  • New A one-call GET …/care-entities/{id}/profile projection (§8).
  • New Per-currency totals over payment logs (§9; depends on Spec 045, degrades gracefully before it).

3.2 Out of scope the guardrail

  • Asset management of any kind. No valuations, no net-worth rollup, no depreciation, no rent ledgers, no yield, no per-type tooling. An asset gets only the five primitives — commitments, documents, payment history, totals, circle-scope — exactly as a person does. A car gets an insurance commitment and a logbook document, not a maintenance scheduler. The moment "asset" means "a thing to value" rather than "a thing to pay for and document," the product drifts into a net-worth tracker (Simi launch-plan Guardrail 1). This spec deliberately ships no field or endpoint that invites valuation.
  • Money movement. CareEntity is record-keeping. It never funds, settles, or routes a payment.
  • Relationship graph beyond a label. A free-text relationship/label ("mother", "co-owned rental") is in; a typed kinship/ownership graph is not.

4. The object model

Five objects, three verbs (capture, remind, prove). CareEntity is the hub; the other four specs attach to it:

CareEntity (this spec — person | asset, country, attributes) ├── Commitment Spec 044 "what I owe this entity, on a rhythm" (CareEntityId FK) ├── PaymentLog Spec 045 "an act that honoured it" (CareEntityId FK) ├── Document Spec 046 "the proof" (CareEntityId link) └── CircleGrant Spec 048 "who may see this entity" (scope → CareEntityId[]) GET /care-entities/{id}/profile ──▶ one call returns: entity + per-currency totals + commitments + recent logs + document refs (§8)

The entity is intentionally thin: identity, type, country, presentation, and an extensibility bag. All behaviour (totals, history, rhythms) lives in services and the dependent aggregates, per the AONIK anemic-entity rule (CLAUDE.md).

5. CareEntity entity new

An anemic, tenant- and user-scoped entity in src/Aonik.PersonalFinance/Entities/PersonalFinance/, inheriting AuditableEntity and implementing ITenantScoped — matching the shape of the module's existing PersonalAccount / Bill entities: 

public class CareEntity : AuditableEntity, ITenantScoped
{
    public Guid   TenantId { get; set; }
    public Guid   UserId   { get; set; }            // owner; scoped per user like Bill/PersonalAccount

    // ── Identity & type ───────────────────────────────────────────
    public string Kind        { get; set; } = "person";   // person | asset   (§6)
    public string? AssetType  { get; set; }               // property|land|vehicle|business|account|other
    public string Name        { get; set; } = string.Empty;
    public string CountryCode { get; set; } = string.Empty; // ISO-3166 alpha-2 → flag + default currency

    // ── Presentation & meaning ────────────────────────────────────
    public string? Relationship { get; set; }   // "mother", "co-owned rental", free text (avoid bank-speak)
    public string? Emoji        { get; set; }   // avatar fallback
    public Guid?   PhotoDocumentId { get; set; } // optional avatar, stored via Documents (Spec 035)

    // ── Extensibility (no schema churn for new asset types) ────────
    public string AttributesJson { get; set; } = "{}"; // type-specific: vehicle reg, property address, …

    // ── Lifecycle ─────────────────────────────────────────────────
    public bool Archived { get; set; }          // hidden from grids; history preserved (never hard-delete)
}

An IEntityTypeConfiguration<CareEntity> in Persistence/Configurations/PersonalFinance/ sets Name/Kind/AssetType max-lengths, a CountryCode length of 2, and an index on (TenantId, UserId, Archived) for the grid query. No unique constraint on name — two children can both be "Tope."

6. Kind & asset taxonomy

Two top-level kinds, because a person and a thing carry different presentation and meaning:

KindMeaningCarriesExamples
personSomeone you look after / support / administer for.A relationship ("mother", "niece").Mum, Tope, Appa
assetA thing you are responsible for, pay for, and document.An assetType + an ownership label.Surulere flat, the Hilux, family land, a business stake

For kind = asset, assetType is a small curated, open enum: property · land · vehicle · business · account · other. The curated set drives the avatar glyph, default reminder copy, and the Support Statement noun ("expenses against the Surulere flat" vs "…the Hilux"). other + a free label covers the long tail (a boat, livestock, equipment) without a migration; type-specific optional metadata (a vehicle registration, a property address, a land title number) lives in attributesJson — the same idiom as PersonalTransaction.TagsJson and Document attributes. Validation accepts any string for assetType but the UI offers the curated list first.

Restraint, restated as a rule Adding an assetType must never add a capability. The taxonomy is for icons, copy, and statement language — not for unlocking valuation, scheduling, or analytics. If a proposed asset type would only make sense alongside a new management feature, that feature is out of scope (§3.2), and so is the type until Simi has paying users asking for it.

7. API surface

FastEndpoints, customer-scoped (Policies("UserPolicy")), under /personal-finance/care-entities, following the module's existing Endpoint<TRequest,TResponse> + positional-record-DTO idiom (e.g. CreateBillEndpoint). Every request DTO ships a Validator<T> — enforced at build time by RequestDtoValidatorCoverageTests.

RouteVerbPurpose
/personal-finance/care-entitiesGETList the user's entities (filter: kind, assetType, includeArchived).
/personal-finance/care-entitiesPOSTCreate a person or asset.
/personal-finance/care-entities/{id}GETGet one entity (lightweight).
/personal-finance/care-entities/{id}PUTUpdate name / relationship / country / type / attributes / photo.
/personal-finance/care-entities/{id}/archivePOSTArchive (soft; history preserved).
/personal-finance/care-entities/{id}/profileGETThe one-call profile (§8).

DTOs (records)

public record CreateCareEntityRequest(
    string Kind, string? AssetType, string Name, string CountryCode,
    string? Relationship, string? Emoji, Guid? PhotoDocumentId,
    IReadOnlyDictionary<string, string>? Attributes);

public record CareEntityResponse(
    Guid Id, string Kind, string? AssetType, string Name, string CountryCode,
    string? Relationship, string? Emoji, Guid? PhotoDocumentId,
    IReadOnlyDictionary<string, string> Attributes, bool Archived,
    DateTime CreatedAt, DateTime UpdatedAt);

Validation (FluentValidation)

public sealed class CreateCareEntityRequestValidator : Validator<CreateCareEntityRequest>
{
    public CreateCareEntityRequestValidator()
    {
        RuleFor(x => x.Kind).Must(k => k is "person" or "asset");
        RuleFor(x => x.Name).RequiredText(120);
        RuleFor(x => x.CountryCode).Length(2);
        RuleFor(x => x.AssetType)
            .NotEmpty().When(x => x.Kind == "asset")     // an asset has a type
            .Must(BeNullOrEmpty).When(x => x.Kind == "person"); // a person does not
        RuleFor(x => x.Relationship).MaximumLength(80);
        RuleFor(x => x.PhotoDocumentId).ValidIdWhenSupplied();
    }
}

8. Profile projection new

The People profile screen "renders fully from one repository call" (rebuild spec §7.6). A CareEntityProfileService composes the rollup server-side: 

public record CareEntityProfileResponse(
    CareEntityResponse Entity,
    IReadOnlyList<CurrencyTotal>   YearTotals,    // per-currency, never converted (§9)
    IReadOnlyList<CommitmentSummary> Commitments,  // open commitments for this entity (Spec 044)
    IReadOnlyList<PaymentLogSummary> RecentLogs,   // last N acts (Spec 045)
    IReadOnlyList<DocumentRef>      Documents);    // linked vault items (Spec 046)

public record CurrencyTotal(string Currency, decimal Total, int Count);

The projection is assembled from the dependent aggregates as each ships. Before Spec 045 lands, YearTotals/RecentLogs are empty arrays and the screen shows its "nothing recorded yet" state — so 043 is independently shippable and the profile grows richer as 044–046 land. The route is one GET; no N+1 round-trips from the client.

9. Per-currency totals currency is recorded, never computed

A core Simi rule (rebuild spec §2.3 Move 3): money keeps its origin and is never auto-converted. Year totals are therefore a list, one row per currency — "£2,400 + ₦85,000," not a fabricated grand total. YearTotals groups the entity's payment logs by currency and sums; the Today hero and every profile total use the same shape. There is no FX engine, no rates table, and no converted figure anywhere in this spec — that freeze (Simi launch-plan §10) is absolute. (An optional user-entered "≈ £" lives on the individual PaymentLog, Spec 045, and is display-only.)

10. Relationship to Party / graph

Why a new entity rather than extending Party or reusing graph nodes (readiness Decision D1):

  • Decoupling. The remittance party/Recipients graph is what Simi's mobile M0 deletes from the app surface; binding the keeper's core object to the payout-beneficiary model would re-couple them. CareEntity is a clean, neutral, B2C object owned by PersonalFinance.
  • Type fit. Party is people/organizations; an asset is neither. Widening PartyType to carry vehicles and land would distort a finance-domain concept used by orders and compliance.
  • Scope fit. CareEntity is user-scoped (Fola's people and assets), like Bill/PersonalAccount — not tenant-global like Party.
Bridge, if needed later If a cross-module read contract ever needs CareEntities (e.g. an agent reasoning over "who Fola supports"), the cleanest bridge is to mirror a CareEntity to a Party node lazily, or expose a SharedKernel.Abstractions read contract — not to make CareEntity a Party up front. Deferred; no consumer needs it for Phase 1.

11. Persistence & migration

Follow the module's exact persistence recipe (verified against the tree):

  1. Entity in Entities/PersonalFinance/CareEntity.cs; IEntityTypeConfiguration in Persistence/Configurations/PersonalFinance/CareEntityConfiguration.cs (auto-discovered by ApplyConfigurationsFromAssembly in both contexts).
  2. Add DbSet<CareEntity> CareEntities to PersonalFinanceDbContext (module runtime context) and map it there: MapTable<CareEntity>(modelBuilder, "CareEntities") → Ank-prefixed (ModuleTablePrefixes.Finance).
  3. Register in AonikDbContext.ApplyDboPrefixedTableNames: MapFinanceTable<CareEntity>(modelBuilder, "CareEntities") → table dbo.AnkCareEntities — exactly as the existing PF entities are mapped there (MapFinanceTable<PersonalRecurringBill>, MapFinanceTable<Household>, …) — and add the DbSet<CareEntity> on AonikDbContext too: every new DbSet lives on the canonical context (CLAUDE.md). This is the context that owns migrations.
  4. Tool-generated migration only: dotnet ef migrations add AddCareEntity --project src/Aonik.Infrastructure --startup-project src/Aonik.Api; review; database update to verify; commit the .cs + .Designer.cs (CLAUDE.md — never hand-author migrations).

No backfill. New table, no existing data to migrate. (Importing existing remittance beneficiaries into CareEntities is a possible later convenience, deferred — and would be a one-way copy, not a coupling.)

12. Security

  • Tenant + user isolation. Every query filters .Where(e => e.TenantId == tenantId && e.UserId == userId) via ITenantProvider + ICurrentUserProvider; an entity is visible only to its owner (and, later, to circle members granted scope — Spec 048, which enforces its own filter).
  • Authz. UserPolicy (consumer). No admin surface; no cross-user read.
  • Photos via Documents. An avatar is a Document (Spec 035) referenced by PhotoDocumentId, inheriting its encryption-at-rest and signed-URL read — no separate blob path.
  • No secrets, no money. CareEntity holds no credentials and moves no funds; the money-action-logging convention does not apply.

14. Acceptance criteria

  • Customer CRUD. A PersonalUser JWT creates, lists, updates, and archives both a person and an asset entity; no admin role is required and no remittance-beneficiary row is created.
  • Asset generality. Creating kind=asset with assetType of property, vehicle, land, business, account, and other+label all succeed and round-trip attributesJson; a person with an assetType is rejected, and an asset without one is rejected.
  • One-call profile. GET …/{id}/profile returns entity + per-currency totals + commitments + recent logs + document refs in a single response; before Specs 044–046 it returns the entity with empty dependent arrays (asserted).
  • Per-currency, never converted. An entity with logs in GBP and NGN yields two YearTotals rows; no converted grand total is produced anywhere.
  • Isolation. User A cannot read or mutate User B's CareEntity (404, not 403 — existence not revealed).
  • Build & migration. dotnet build Aonik.sln green; the tool-generated migration applies cleanly with only AnkCareEntities added.

15. Open decisions

  • O1 — Mirror CareEntity to a Party for cross-module reads? (OPEN, leaning no for Phase 1.) Only build the bridge (§10) when a concrete cross-module consumer appears.
  • O2 — Relationship vocabulary: free text vs a small suggested set? Spec ships free text with UI suggestions ("mother", "co-owned rental"); a controlled vocabulary can come later if statements need normalised wording. Avoid "beneficiary"/"dependant" (rebuild spec §2.4).
  • O3 — Tab label. Backend-neutral, but flagged: with assets beyond places, the mobile fallback label "Yours" (rebuild spec §12.4) reads better than "People & Places." Not a backend decision; noted so copy and DTO names ("care-entities") stay label-agnostic.
