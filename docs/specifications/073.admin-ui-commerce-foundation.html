Spec 073ImplementedAdmin UIAonik.AdminUi

Admin UI commerce module foundation

The scaffold every storefront admin page (Specs 074–084) stands on: a new commerce frontend module, its navigation section, service and type layout, and the four shared visual components the page specs reuse. The approved designs live in Templates/aonik-admin-starterkit (PR #268, sections "Commerce · Storefront · Specs 066–072"); this spec turns the app-level plumbing they assume into concrete files.

Current implementation · 2026-10-09. Commerce module registration, route navigation, service clients, DTOs and shared components are available. Navigation and permissions follow the tenant- and identity-bound manifest and Admin profiles (Spec 098). Workspace panels remain outside this specification's scope.

1 · Why a foundation spec

At the original design baseline, the Admin UI had no commerce module; its "Catalog" was the bill-payment catalog. Specs 074–084 shared the need for module registration, navigation, a data-layer shape and reusable components. That foundation is now implemented. The original scaffold and page scope below remain the design record; Spec 098 supersedes its original navigation and manifest assumptions.

4 · Data layer

No react-query and no codegen exist; follow the house pattern (hand-written services returning unwrapped res.data via api.* from src/lib/api.ts, which already attaches Authorization and X-Tenant-Id).

FileContents
src/types/commerce.tsCreate. All commerce DTO interfaces, hand-written to mirror the API contracts quoted in Specs 074–084 (camelCase JSON of the C# records — e.g. OptionGroupDto, EffectiveOptionGroupDto, ResolvedContentDto, BoxPlanDto, FulfilmentCalendarDto, AdminCollectionDto, FacetGroupDto, StorefrontConfigDto, AdminProductDetailDto, and a Commerce-specific CommercePagedResult<T> { items, totalCount, page, pageSize } — the Commerce API's envelope differs from the app's PagedResult (pageNumber/totalPages), so list services normalize (map page → pageNumber, compute totalPages) before handing data to DataTablePagination; never cast the raw envelope to @/types' PagedResult). Amounts are number decimals in the tenant currency — the admin displays them as-is with the currency code the DTO carries; it never converts.
src/services/commerceCatalogService.tsCreate. Products list/detail/patch, media replace, option groups CRUD + choices + recommended-default, product narrowing + surcharge (base path /commerce/admin).
src/services/commerceContentService.tsCreate. Content block upsert, confirm-review, content-variants CRUD, coverage.
src/services/commerceStorefrontService.tsCreate. Size plan, fulfilment calendar, collections, facet groups, storefront config, public reads used for previews (/commerce/config/storefront, /commerce/config/delivery, /commerce/catalog/extras).
Policy reality. Endpoint policies and service permissions remain enforced server-side; staff reads that expose customer information use AdminReadPolicy. The frontend reuses useModules().allowsPolicy() and hasPermission() to gate controls, and surfaces the interceptor's userMessage for rejected requests. Client visibility never replaces server authorization.

6 · Page skeleton convention

Every page in the series follows the modern lineage (CustomersListPage/OrdersListPage):

  • Container flex flex-col gap-5 p-6 md:px-8; PageHeader (eyebrow Commerce, page title, one-line subtitle); KPI row of exactly four KpiTiles when the page is a dashboard-like list; content in AonikCards; DataTable + DataTablePagination for lists; Sheet for create/edit, Dialog for destructive confirms; inline error banner from err.userMessage with Retry; PageLoadingScreen on initial load; sonner toast on successful writes.
  • State: local hooks + loadData/useCallback/useEffect with a requestIdRef race guard — no new state libraries.
  • Theme through var(--color-*) tokens only; ids/amounts in mono; no decorative separators; both themes verified (the [data-theme] mechanism is already global).
  • Visual language per the aonik-design skill: teal primary, coral reserved for agent-apply moments, numbers right-aligned mono.

7 · Out of scope

  • Backend changes — with exactly one exception: the one-line server-manifest registration above, without which the module cannot render at all. Every endpoint the series consumes is shipped; the genuine API gaps are called out as explicit dependencies in their page specs, not smuggled in here.
  • Workspace/Dockview panels — pages are plain routes; WorkspacePanelConfig exposure can follow later per page.
  • Component/DOM tests: the repo's vitest environment is node; the series specs logic-level tests only (formatters, scale derivation, state mappers).

8 · Acceptance

  1. commerceModule is registered; all routes above resolve to implemented pages without breaking tsc -b. Remaining page-specific scope is recorded in each page specification.
  2. The Commerce nav section renders with working icons in both themes, disappears when the manifest omits the module, and fails closed when the manifest is unreachable.
  3. src/types/commerce.ts compiles and matches the JSON casing of the shipped DTOs (spot-check against a live GET /commerce/admin/option-groups and GET /commerce/config/storefront); list services return the normalized pagination shape, with a unit-tested mapper.
  4. The four shared components exist with the exact props above, render in light and dark, and SignedAmount has unit tests covering positive/negative/zero.
  5. Electron/hash-router compatibility: all new links use router navigation (no window.location.pathname reliance).
