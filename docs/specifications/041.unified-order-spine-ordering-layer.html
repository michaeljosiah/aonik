Spec 041 Status: Draft Size: Large Priority: P1 Domain: Architecture / Ordering / Commerce

Unify the Order spine into a shared Ordering layer (Order as a core concept)

Promotes Order — today a Aonik.Finance-private concept framed narrowly as “a requested financial service” — into a core, cross-cutting concept: the contract and the anemic entities move into Aonik.SharedKernel, the generic order machinery into a new middle-layer module Aonik.Ordering, and Aonik.Finance keeps only its type-specific orchestration. A product purchase becomes just another OrderType alongside bill payment, transfer and remittance — unlocking a future Aonik.Commerce retail module that reuses one order spine, one lifecycle, one audit trail, and the agentic / payment rails, without any sibling-module coupling. Follows the Spec 027 / ADR-006 relocation precedent so the move needs no migration.

1. Summary

AONIK wants a B2C commerce capability (selling physical wellness-food products) that reuses the platform's agentic, multi-tenant, audited foundations. The cleanest home is a new Aonik.Commerce module — but it collides with where Order lives.

Order sits inside Aonik.Finance (src/Aonik.Finance/Entities/Orders/) and is doctrinally framed as “the canonical record of a customer's intent to use an AONIK financial service.” Yet the entity is already generic: OrderType is an open string, OrderItem.DetailsJson is a type-discriminated container, OrderFulfilmentRef already fans out to multiple fulfilment kinds under a one-of CHECK, and orders already link to both Invoice and PaymentIntent. A product purchase is structurally just another order type.

The blocker is ownership and layering, not the entity. The modular-monolith rule (ADR-005) forbids a new Aonik.Commerce from referencing Aonik.Finance, so an Order trapped inside Finance cannot be reused by a peer domain. This spec makes Order core:

  • The contract (IOrderService, DTOs, OrderType / OrderStatuses / OrderPartyRoles constants, order events) → SharedKernel.Abstractions.Ordering.
  • The anemic entities + EF configs → Aonik.SharedKernel, extending the precedent that SharedKernel already hosts persisted cross-cutting entities (OutboxMessage / InboxMessage).
  • The generic machinery (the OrderService implementation, lifecycle endpoints, order agent tools, a scoped OrderingDbContext) → a new middle-layer module Aonik.Ordering.
  • Aonik.Finance keeps only its type-specific orchestration (FX quoting, compliance screening). A later Aonik.Commerce adds its own (product, inventory, cart).
Success signals dotnet build Aonik.sln succeeds with the Order spine living in SharedKernel + Aonik.Ordering and Aonik.Finance holding no Order entity; a product-purchase order can be created, invoiced, and paid through the existing Invoice + PaymentIntent rails; Aonik.Finance and a future Aonik.Commerce never reference each other; tables keep their Ank prefix and the relocation produces no migration (only the new nullable OrderItem columns do); dotnet test Aonik.sln stays green.

2. Context & motivation

AONIK is an AI-native platform powering three products (Payabo B2C, MyBillAfrica B2B, RemitExchange remittance). A wellness-food storefront is a fourth surface whose differentiating value is the platform's agentic infrastructure — domain agents, tiered tool approval (Spec 032), durable proposals (Spec 030), AiRun audit — plus multi-tenancy, the Party system, and a payment-capable PaymentIntent with a public guest-checkout path. Selling products is mostly net-new domain (catalog, inventory, cart), but the order at the centre of it already exists.

ObservationEvidence
OrderType is an open string, not a closed enum Order.cs line 8 (public string OrderType); the OrderType.cs enum is only a known-values helper. Adding ProductPurchase is additive.
Line items already carry a type-discriminated payload OrderItem.cs line 11 (DetailsJson) — bill-pay lines hold meter numbers, remittance lines hold recipient detail.
Fulfilment is already polymorphic OrderFulfilmentRef.cs — three typed nullable FKs under a “exactly one set” CHECK. A future ShipmentId is a fourth, not a new paradigm.
Orders are already invoiced and funded Invoice.OrderId links billing; OrderFundingRef.cs links a PaymentIntent.
Order is owned by the wrong layer for sharing Entities under src/Aonik.Finance/Entities/Orders/; a sibling Aonik.Commerce cannot ProjectReference Finance per ADR-005.
Doctrine never actually excluded product purchases CLAUDE.md / Spec 005 “Not Orders” list is: imported bank transaction, manual categorisation, ledger correction — a product purchase is not among them.

ADR-005 anticipated selective restructuring once a concept earns its own boundary, and Spec 027 / ADR-006 established the mechanics for relocating entities without a migration (preserve namespaces so Designer.cs snapshot FQN strings stay valid). Order now meets the bar to become a core concept: it is shared by two peer domains and has its own lifecycle, audit, and agent surface that belongs to no single product.

3. Scope (in / out)

In scope

  • Generalise the Order domain model: add ProductPurchase to OrderType; add nullable Quantity, UnitPrice, ProductId, Sku to OrderItem.
  • Generalise the doctrine in CLAUDE.md and Spec 005 (Order = intent to transact; OrderType discriminates).
  • Define SharedKernel.Abstractions.Ordering (IOrderService, DTOs, events, constants).
  • Relocate the Order entities + EF configs into SharedKernel (namespace-preserving).
  • Create the Aonik.Ordering module: OrderingDbContext, the generic OrderService, lifecycle endpoints, and order agent tools + an IToolApprovalManifest.
  • Refactor Aonik.Finance to keep only type-specific order orchestration, building on the shared core.
  • One EF-CLI migration against AonikDbContext for the new OrderItem columns + the enum value.

Out of scope

  • Building the Aonik.Commerce retail domain itself (product catalog, inventory, cart, storefront UI) — specified at a high level in §14 and delivered as a follow-up (Phase 4 / its own spec).
  • Shipping / carrier / delivery-tracking and a tax-calculation engine (the ShipmentId fulfilment slot is noted as a forward extension).
  • Discounts / coupons / promotions (a future Commerce concern).
  • Changing the physical SQL database, table names (Ank prefix), or migration ownership — migrations stay with AonikDbContext per ADR-005.
  • Any change to /orders/* HTTP contracts for existing callers.
  • Collapsing or altering the Order / Payment / Ledger separation.

4. Constraints & guardrails

  • No sibling cross-module references. Aonik.Finance and Aonik.Commerce never reference each other. They depend downward on SharedKernel.Abstractions.Ordering and, where the generic impl is needed, on Aonik.Ordering. Depending on a shared lower layer is sanctioned by ADR-005; sibling-to-sibling coupling is not.
  • Single migration stream. All schema deltas are EF-CLI-generated against AonikDbContext in Aonik.Infrastructure. OrderingDbContext is a runtime scoping context with no migrations. Agents never hand-author migrations or edit .Designer.cs.
  • Relocation must not produce a migration. C# namespaces are preserved when files move (per the Spec 027 Phase 2 rationale); tables keep their Ank names; only the new columns + enum value generate a migration.
  • Anemic entities. Order* stay { get; set; } data containers implementing ITenantScoped and inheriting AuditableEntity (ADR-002); all logic lives in OrderService returning DTOs.
  • SharedKernel discipline. Only the anemic entities, their EF configs, and the contract live in the kernel. No OrderService, no endpoints, no FastEndpoints surface in SharedKernel.
  • Tenant scoping is an invariant. Every order query is filtered by TenantId; cross-tenant writes fail closed via AonikDbContextBase.
  • Order ≠ Payment ≠ Ledger. The non-negotiable separation is preserved. A product purchase is funded by a PaymentIntent and proven by ledger entries — the Order is still only the requested-service record.
  • Agents propose; systems execute. Order reads are direct agent tools; order mutations are governed by the Spec 032 tiers, with money movement marshalled into durable proposals (Spec 030).

6. The three-layer split

The core move recognises that “Order” conflates three responsibilities with different homes:

ContractEntity + configGeneric machineryType-specific orchestration
WhatIOrderService, DTOs, events, constantsOrder, OrderItem, … + EF configsOrderService impl, lifecycle endpoints, order tools, OrderingDbContextCreate-bill-payment, create-remittance (FX, compliance); create-product-purchase (inventory)
HomeSharedKernel.Abstractions.OrderingAonik.SharedKernelAonik.Ordering (new middle layer)Aonik.Finance / Aonik.Commerce
PrecedentADR-006 read contractsOutbox/Inbox entities already in SharedKernelper-module scoping DbContext (Spec 027)existing domain services

This mirrors the platform's Order vs Payment vs Ledger discipline: distinct responsibilities are not collapsed just because they co-occur. The kernel owns the durable shape; the middle layer owns the generic behaviour; the domains own only what is unique to their order type.

7. Why a neutral Ordering layer, not “Commerce”

The shared layer is named after what is common to everything that depends on it — ordering — not after one consumer. Naming it Commerce would force Aonik.Finance to depend on a module that also owns products, inventory, and cart, leaking retail concepts into a remittance path; and a module named “Commerce” owning bill-payment and remittance orders reads wrong to the next engineer. Aonik.Commerce remains a real module — the retail domain on top of the ordering core, not the owner of the order spine. The decision is reversible (a module rename is mechanical and touches no data), so we pick the label that ages best.

10. Domain model & entity changes

Entities stay anemic, ITenantScoped, and inherit AuditableEntity. Existing fields are unchanged; new fields are marked new.

OrderItem — add nullable retail columns

public class OrderItem : AuditableEntity, ITenantScoped
{
    // ── existing (unchanged) ─────────────────────────────────
    public Guid TenantId { get; set; }
    public Guid OrderId { get; set; }
    public string ItemType { get; set; } = string.Empty;
    public int ItemIndex { get; set; }
    public string DetailsJson { get; set; } = "{}";
    public string Status { get; set; } = string.Empty;
    public Guid? ReceiverPartyId { get; set; }
    public decimal AmountIn { get; set; }          // reused as the line total (Quantity × UnitPrice)
    public string CurrencyIn { get; set; } = string.Empty;
    public decimal AmountOut { get; set; }
    public string CurrencyOut { get; set; } = string.Empty;
    public decimal FeesTotal { get; set; }
    public Guid? PricingQuoteId { get; set; }

    // ── new: retail line shape (nullable; populated only for product lines) ──
    public decimal? Quantity   { get; set; }       // new — e.g. 3
    public decimal? UnitPrice  { get; set; }       // new — e.g. 4500.00
    public Guid?    ProductId  { get; set; }       // new — SOFT reference, no FK (cf. Order.PayerPartyId → Party)
    public string?  Sku        { get; set; }       // new — e.g. "WELL-GRANOLA-500G"
}
  • No LineTotal column. AmountIn already means “amount in source currency”; for a product line it carries Quantity × UnitPrice. Adding a second total invites drift.
  • ProductId is a soft reference — a plain Guid? with no FK constraint, exactly how Order.PayerPartyId points at a Party in another module. This keeps the kernel from depending on the (future) Commerce product table.

Order header — reused as-is for product purchases

No new header columns. For a ProductPurchase: AmountIn / CurrencyIn = order total + currency; AmountOut / CurrencyOut / FxQuoteId / OriginCountry / DestinationCountry / PurposeCode are left null (they were always nullable — FX/remittance baggage simply unused). PayerPartyId is the buyer; an OrderPartyRole of Receiver/Payee can carry the merchant.

OrderFulfilmentRef — forward extension

When shipping lands (out of scope here), a nullable ShipmentId is added under the existing “exactly one set” CHECK alongside PayoutId / PaymentIntentId / PartnerBillPaymentId. A product order's immediate fulfilment ref is its PaymentIntentId; physical dispatch is modelled later.

12. SharedKernel contracts & events

Consumption flows through Aonik.SharedKernel.Abstractions.Ordering. Shapes are illustrative; final signatures accept CancellationToken cancellationToken = default and return DTOs (records), never entities. 

namespace Aonik.SharedKernel.Abstractions.Ordering;

public sealed record OrderItemCommand(
    string ItemType, int ItemIndex,
    decimal AmountIn, string CurrencyIn,
    Guid? ReceiverPartyId = null,
    decimal? Quantity = null, decimal? UnitPrice = null,   // retail
    Guid? ProductId = null, string? Sku = null,            // retail (soft ref)
    string? DetailsJson = null);

public sealed record CreateOrderCommand(
    string OrderType,                 // "ProductPurchase", "BillPayment", …
    Guid? PayerPartyId,
    string CurrencyIn,
    IReadOnlyList<OrderItemCommand> Items,
    string? IdempotencyKey = null,
    string? ProvenanceJson = null);

public interface IOrderService
{
    Task<OrderDto> CreateAsync(CreateOrderCommand cmd, CancellationToken ct = default);
    Task<OrderDto?> GetAsync(Guid orderId, CancellationToken ct = default);
    Task<PagedResult<OrderListItem>> ListAsync(ListOrdersQuery query, CancellationToken ct = default);
    Task<OrderDto> TransitionAsync(Guid orderId, string toStatus, string reason, CancellationToken ct = default);
    Task LinkFundingAsync(Guid orderId, Guid paymentIntentId, CancellationToken ct = default);
    Task LinkFulfilmentAsync(Guid orderId, OrderFulfilmentLink link, CancellationToken ct = default);
}

Type-specific creation (bill payment with FX + compliance, product purchase with inventory reservation) stays in the owning domain and composes IOrderService.CreateAsync for persistence + lifecycle — the domain adds its own pre/post steps around the core call.

Integration events (in SharedKernel, raised by Ordering):

  • OrderCreatedEvent(TenantId, OrderId, OrderType, PayerPartyId, AmountIn, CurrencyIn) — the existing event, re-homed; consumers (PersonalFinance life-graph, insights) already subscribe.
  • OrderStatusChangedEvent(TenantId, OrderId, FromStatus, ToStatus).
  • OrderFulfilledEvent(TenantId, OrderId, FulfilmentKind).

13. Finance refactor

Finance loses ownership of the Order spine but keeps everything that is finance-specific:

  • The generic OrderService (CRUD, status transitions, history, funding/fulfilment linking) moves to Aonik.Ordering.
  • The bill-payment and remittance creation services stay in Finance and are refactored to call IOrderService.CreateAsync for persistence, wrapping it with FX quoting, pricing, and compliance screening (their unique value).
  • Generic /orders/{id}, list, cancel, and history endpoints re-home to Aonik.Ordering (routes unchanged); the /orders/bill-payments and /orders/remittances creation endpoints stay in Finance.
  • FinanceDbContext drops the generic Order DbSets (they live on OrderingDbContext + AonikDbContext); Finance reads order data it needs via IOrderService / ICustomerOrderHistoryReader.
  • ICustomerOrderHistoryReader + OrderHistoryItem move from Abstractions.Finance to Abstractions.Ordering (they were never Finance-specific); the implementation re-homes to Aonik.Ordering. PersonalFinance consumers are unaffected (same contract, new namespace).

14. The Commerce consumer (Phase 4 — high level)

Delivered as a follow-up (its own spec), Aonik.Commerce is the retail domain that motivates this work. It owns what does not exist today — product catalog, inventory, cart — and reuses everything below it:

  • New entities: Product, ProductVariant, InventoryLevel, Cart, CartItem (+ later discounts, shipping).
  • Orders: a CreateProductPurchaseOrderService reserves inventory then calls IOrderService.CreateAsync with OrderType = ProductPurchase and product line items.
  • Billing & payment: reuse Invoice (via Invoice.OrderId) and the public guest-checkout PaymentIntent path — no new payment plumbing.
  • Customers: reuse the Party system (open PartyType, typed shipping addresses, tiers) via the existing IPartyReader contract.
  • Agentic surface: a commerce-agent (IDomainAgentDescriptor) with approval-gated tools (commerce_create_product → medium; price/inventory writes → medium; refunds / payment capture → high → durable proposal) per Spec 032.

The proof this spec must guarantee: a product-purchase order can be created, invoiced, and paid end-to-end using only the relocated spine + existing rails, with no Finance ↔ Commerce reference.

15. Agentic reuse

Order agent tools move to Aonik.Ordering and are classified by a new OrderingToolApprovalManifest (IToolApprovalManifest): reads (ordering_get_order, ordering_list_orders) pass through; ordering_cancel_order and other generic mutations are medium (in-session confirmation, args-hash-bound). Money movement is never an Ordering concern — it stays with the funding PaymentIntent tools in Finance/Commerce, which are high and marshalled into durable proposals (Spec 030). Because the gate aggregates every module's manifest, the Ordering tools are wrapped uniformly the moment the module registers — no change to the gate itself.

17. OrderingDbContext

A module-scoped context over the same physical database, exposing the Order sets. It inherits AonikDbContextBase (tenancy, audit, soft-delete) and declares no migrations — AonikDbContext remains the single migration stream and continues to own every DbSet. 

internal sealed class OrderingDbContext : AonikDbContextBase
{
    public DbSet<Order> Orders => Set<Order>();
    public DbSet<OrderItem> OrderItems => Set<OrderItem>();
    public DbSet<OrderPartyRole> OrderPartyRoles => Set<OrderPartyRole>();
    public DbSet<OrderFundingRef> OrderFundingRefs => Set<OrderFundingRef>();
    public DbSet<OrderFulfilmentRef> OrderFulfilmentRefs => Set<OrderFulfilmentRef>();
    public DbSet<OrderHistoryEvent> OrderHistoryEvents => Set<OrderHistoryEvent>();
    public DbSet<OrderNote> OrderNotes => Set<OrderNote>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        base.OnModelCreating(b);
        b.HasDefaultSchema(SchemaNames.Default);
        // Order configs live in SharedKernel; apply from there + map Ank-prefixed tables.
        b.ApplyConfigurationsFromAssembly(typeof(Order).Assembly);
    }
}

18. Migration & data strategy

Tables keep their Ank-prefixed names (AnkOrders, AnkOrderItems, …). The relocation is project-structure-only: C# namespaces are preserved on the move (e.g. files keep namespace Aonik.Finance.Entities.Orders even under SharedKernel), so the Designer.cs snapshot FQN strings stay valid and the move yields no migration — the same technique Spec 027 used. A namespace rename to Aonik.SharedKernel.Ordering can land later as an isolated change.

The only schema delta is in Phase 1, before any relocation:

  • AnkOrderItems: add nullable Quantity, UnitPrice, ProductId, Sku.
  • ProductPurchase is an application-level enum value (the column is already nvarchar) — no column change.
Migration rule The delta is generated only by the EF CLI against AonikDbContext: dotnet ef migrations add OrderItemRetailColumns --project src/Aonik.Infrastructure --startup-project src/Aonik.Api, then reviewed (expect only the four nullable AnkOrderItems columns) and applied with dotnet ef database update. No hand-authored migrations; no edits to the .Designer.cs snapshot. When entities relocate in Phase 3, the configs move first (so the model still compiles), the DbSets stay on AonikDbContext, and a no-op re-generation confirms an empty diff.

19. Phased rollout

Phase 1 — Generalise in place (shippable alone)

Prove “just another order type” against the real schema before moving anything.
  • Add nullable Quantity / UnitPrice / ProductId / Sku to OrderItem; add ProductPurchase to OrderType.
  • One tool-generated migration against AonikDbContext; review + apply.
  • Update CLAUDE.md + Spec 005 doctrine. No relocation. Fully reversible.

Phase 2 — Promote the contract

Introduce the seam without moving entities.
  • Add SharedKernel.Abstractions.Ordering (IOrderService, DTOs, commands, events, constants).
  • Route Finance's existing order callers through IOrderService; keep the impl in Finance for now.

Phase 3 — Relocate the spine

Order becomes core; no migration.
  • Move Order* entities + EF configs into SharedKernel (namespace-preserving).
  • Create Aonik.Ordering: OrderingDbContext, generic OrderService, /orders/* lifecycle endpoints, order tools + OrderingToolApprovalManifest.
  • Aonik.Infrastructure → Aonik.Ordering reference; register the module + FastEndpoints assembly in the composition root.
  • Finance retains only bill-pay / remittance creation, composing the core; re-home ICustomerOrderHistoryReader to Abstractions.Ordering.

Phase 4 — Build Aonik.Commerce (own spec)

The retail domain on top.
  • Product / Inventory / Cart entities + services; commerce-agent + approval-gated tools.
  • Product-purchase orders via IOrderService; billing via Invoice; funding via the public PaymentIntent path.

24. Decisions baked in

  • Order is a core concept — unified one spine, not duplicated per domain.
  • Contract + anemic entities in SharedKernel; generic machinery in a new Aonik.Ordering middle layer — the kernel stays orchestration-free.
  • Neutral Ordering layer, Commerce as a consumer on top — named for the superset, not one consumer.
  • Product purchase is an OrderType, with nullable retail columns and AmountIn reused as the line total; ProductId is a soft reference.
  • Relocation produces no migration (namespaces preserved); only the new columns do; migrations stay with AonikDbContext.
  • Order / Payment / Ledger separation preserved; the “Not Orders” exclusions are unchanged.
  • Phase 1 ships in place to prove the model before the larger relocation.

25. Open design decisions

Open Entity placement: SharedKernel vs Aonik.Ordering. This spec places the anemic entities + configs in SharedKernel (faithful to the Outbox precedent; lets read-only consumers avoid referencing Aonik.Ordering). The alternative keeps the entities inside Aonik.Ordering so they travel with their service and the kernel stays leaner — at the cost that any consumer touching the entity type must reference the module. Reversible; decide before Phase 3.
Open Namespace rename timing. Whether to rename Aonik.Finance.Entities.Orders → Aonik.SharedKernel.Ordering immediately (one regenerated no-op snapshot revision) or defer it as an isolated later change (as ADR-006 did).
Open Where product-purchase order creation composes the core. A thin CreateProductPurchaseOrderService in Aonik.Commerce (preferred, keeps inventory logic with its domain) vs a generic typed-creation extension point on Aonik.Ordering.
Open Shipping fulfilment modelling. Whether a future ShipmentId on OrderFulfilmentRef suffices or commerce fulfilment warrants its own entity — deferred to the Commerce spec.
