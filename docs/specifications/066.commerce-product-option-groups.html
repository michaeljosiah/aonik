Commerce product option groups (configurable personalisation)

A first-class option model for configurable catalog products: a tenant-level option catalogue, per-product narrowing, recommended defaults, single/multi selection, and difference-based price adjustments (including negative ones) — plus a per-unit product surcharge. Keystone of the storefront plan (Abby's Table storefront capability plan, Spec A): Specs B (option-dependent content) and C (box-builder carts) both consume the contracts defined here.

1. Summary

Storefront tenants sell products a customer can configure at add-to-cart time — portion size, protein, side, heat level — where each choice carries a price delta relative to a recommended default, some choices reduce the price, some products allow several choices in one group, and each product offers its own subset of the tenant's option catalogue. Today Commerce can express none of this: variants are discrete SKUs and bundle slots compose boxes, not per-product options.

This spec adds three entities (OptionGroup, OptionChoice, ProductOptionGroup), one column on Product (UnitSurcharge), two services (authoring/resolution and selection validation/pricing), public read endpoints, admin authoring endpoints, and a canonical selection JSON contract that carts (Spec C) and orders (OrderItem.DetailsJson) will carry so kitchen production sheets can render "Jollof — Full table · salmon ×2".

Product-agnostic by construction (ADR-013). Nothing here says "dish", "Abby's choice" or "signature". The platform models a recommended default and a per-unit surcharge; tenant vocabulary ("Abby's choice", "Signature") is presentation, supplied via config-pack settings (§15). The same entities must serve a coffee roaster's grind options or a florist's wrap choices unchanged.

2. Motivation & why existing constructs don't fit

Driven by the Abby's Table storefront (first client of Commerce as a storefront backend). Its Step 2 functional spec (v1.1, FR-11 / §6.4) requires, verbatim in spirit:

  • An ordered, back-end-owned catalogue of option groups — groups and options are configuration, editable without a release (FR-11.2).
  • Per-product narrowing: which groups a product offers, which options within them, a per-product default override; a product with no groups is simply not personalisable (FR-11.5, AC-25).
  • Multi-select groups on flagged products, minimum one selection (FR-11.3).
  • Delta pricing against the recommended default, with negative adjustments first-class (§3.2: default side costs £2, choosing "No side" is −£2; AC-9).
  • Server-side rejection of any option a product does not offer, even when the option exists in the catalogue (AC-24).

Why not variants?

Enumerating combinations as SKUs explodes immediately (2 portions × 4 proteins × 4 sides × 4 heats = 128 variants per product) and cannot represent multi-select at all (choose 2 of 4 proteins adds another 6 combinations per remaining axis). Variants stay what they are: discrete purchasable SKUs (a 500g vs 1kg bag). Option groups are orthogonal: a selection layered on whatever is being bought.

Why not bundle slots?

BundleSlot/BundleSlotOption compose a box out of other variants — the box's contents. Personalisation configures one line itself and must work for simple products too. Different axis; both will be active at once in the box flow (a bundle line whose component lines each carry a selection).

4. Terminology

TermMeaning
Option groupA tenant-level axis of configuration ("Portion", "Protein"), ordered, with a selection mode.
Option choiceOne selectable value in a group ("Full table", note "450g", price 10.00).
Recommended defaultThe choice applied when the customer doesn't choose. Tenant vocabulary may label it ("Abby's choice"). Exactly one per group; overridable per product.
NarrowingA product's declaration of which groups apply and which choices within them are offered.
Effective optionsThe result of catalogue ∩ narrowing for one product: what the storefront renders and the validator accepts.
SelectionA customer's chosen option per offered group, in canonical form (§7).
AdjustmentThe signed price delta of a selection vs the all-defaults selection (§8). Negative is legitimate.
Unit surchargeA per-unit price added on top of container pricing for a specific product ("signature upgrade"). Independent of the selection.

5. Domain model

All entities are anemic (AuditableEntity, ITenantScoped), live in src/Aonik.Commerce/Entities/Catalog/, and follow existing Commerce conventions.

public class OptionGroup : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public string Key { get; set; } = string.Empty;        // stable, kebab/lower ("portion")
    public string Label { get; set; } = string.Empty;      // display ("Portion")
    public string? HelpText { get; set; }                  // "How much food arrives…"
    public string SelectionMode { get; set; } = OptionSelectionModes.One;  // One | Multi
    public string Currency { get; set; } = "GBP";          // all choice prices in this group
    public int SortOrder { get; set; }
    public bool IsActive { get; set; } = true;
    public List<OptionChoice> Choices { get; set; } = new();
}

public class OptionChoice : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid OptionGroupId { get; set; }
    public string Key { get; set; } = string.Empty;        // stable within group ("full")
    public string Label { get; set; } = string.Empty;      // "Full table"
    public string? Note { get; set; }                      // secondary line ("450g")
    public decimal Price { get; set; }                     // absolute option price; deltas derived §8
    public bool IsRecommendedDefault { get; set; }
    public int SortOrder { get; set; }
    public bool IsActive { get; set; } = true;
}

/// Join: which groups/choices one product offers. Absence of a row = group not offered.
public class ProductOptionGroup : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid ProductId { get; set; }
    public Guid OptionGroupId { get; set; }
    public string? AllowedChoiceKeysJson { get; set; }     // JSON array; null = all active choices
    public string? DefaultChoiceKey { get; set; }          // per-product default override
    public string? SelectionModeOverride { get; set; }     // null = inherit; One | Multi
    public int SortOrder { get; set; }
}

Invariants enforced in services, not the schema (anemic model, and several are conditional on IsActive): exactly one active recommended default per active group; DefaultChoiceKey and every entry of AllowedChoiceKeysJson must reference an existing choice key of that group; a narrowing whose effective default would be unresolvable (§6 step 4) is rejected at authoring time, never discovered at render time.

6. Effective-options resolution

For one product, resolution produces the ordered list the storefront renders and the validator accepts:

  1. Load the product's ProductOptionGroup rows, ordered by SortOrder. No rows ⇒ the product is not personalisable — DTOs carry an empty list and storefronts hide the personalisation UI entirely (Step 2 AC-25).
  2. For each row, load the group (skip if inactive) and its active choices ordered by SortOrder.
  3. Intersect with AllowedChoiceKeysJson when present (unknown keys were rejected at authoring; a key whose choice has since been deactivated simply drops out).
  4. Effective default = DefaultChoiceKey if set and still offered, else the group's recommended default if offered, else the row is invalid — authoring validation (§9) prevents saving this state; if data drift ever produces it at read time, the group is omitted from the effective list and a warning is logged (fail safe: the product loses an axis rather than rendering a default-less group).
  5. Effective selection mode = SelectionModeOverride ?? group.SelectionMode.

Widening (single-select group made multi for one product — Step 2's multi-protein dishes) and tightening (multi made single) are both legitimate uses of the override.

7. Selection contract & canonical form

A selection is a JSON object keyed by group key. Single-select groups map to a string; effective multi-select groups map to a non-empty array:

{ "portion": "full", "protein": ["chicken", "salmon"], "side": "none", "heat": "medium" }

Normalisation (performed by IOptionSelectionService; consumers store only the normalised form):

  • Groups the product offers but the input omits are filled with the effective default — the stored selection is always complete, so orders are self-describing even if defaults later change.
  • Multi-select arrays are de-duplicated and sorted ordinally — two selections are the same selection regardless of pick order (Step 2 FR-6.2: "protein order does not matter"). This makes canonical-JSON string equality a valid line-merge key for Spec C.
  • Single-select values provided as one-element arrays are unwrapped; anything else shape-invalid is rejected (§9), never coerced.

A normalisation result also reports isDefault — true when every group equals its effective default (storefronts render the recommended-default marker instead of listing choices, per Step 2 FR-5.3 state B).

8. Adjustment pricing

Per group, over the normalised selection:

groupAdjustment = Σ price(chosen choice)  −  price(effective default choice)   // subtract once
adjustment      = Σ groupAdjustment over all offered groups
  • Prices are the absolute option prices from the catalogue; deltas are always derived, never stored — repricing an option or changing a default reprices every future quote with no data rewrite.
  • Negative group adjustments are first-class (default side 2.00, chosen "none" 0.00 ⇒ −2.00) and must survive end-to-end: DTOs, quote breakdowns, order envelopes.
  • Multi-select sums every chosen price before subtracting the default's price once (Step 2 §3.2 formula).
  • The all-defaults selection prices to exactly 0 by construction.
  • Product.UnitSurcharge is not part of the adjustment — it is returned alongside it (unitSurcharge) and applied per unit by the quote engine (Spec C). Independence is deliberate: both can apply to the same unit (Step 2 FR-12.2).
  • Currency: every group involved must share one currency; a mixed-currency resolution is an authoring-time error. The priced result carries the currency explicitly.

The pricing result exposes a per-group breakdown (group key, chosen keys, group adjustment) so storefronts can render "+£10 Full table · −£2 No side" without re-deriving maths client-side.

10. Services

Interfaces in Aonik.Commerce.Contracts.Services.Catalog, implementations in Services/Catalog/, registered in CommerceModule. DTOs out, entities never. All methods take CancellationToken cancellationToken = default.

public interface IProductOptionService
{
    // authoring
    Task<OptionGroupDto> CreateGroupAsync(CreateOptionGroupCommand command, CancellationToken ct = default);
    Task<OptionGroupDto> UpdateGroupAsync(Guid groupId, UpdateOptionGroupCommand command, CancellationToken ct = default);
    Task<OptionChoiceDto> AddChoiceAsync(Guid groupId, UpsertOptionChoiceCommand command, CancellationToken ct = default);
    Task<OptionChoiceDto> UpdateChoiceAsync(Guid choiceId, UpsertOptionChoiceCommand command, CancellationToken ct = default);
    Task SetProductOptionGroupsAsync(Guid productId, SetProductOptionGroupsCommand command, CancellationToken ct = default); // full replace
    // reads
    Task<IReadOnlyList<OptionGroupDto>> GetCatalogueAsync(bool includeInactive = false, CancellationToken ct = default);
    Task<IReadOnlyList<EffectiveOptionGroupDto>> GetEffectiveOptionsAsync(Guid productId, CancellationToken ct = default);
}

public interface IOptionSelectionService
{
    /// Validate against the product's effective options, fill defaults, canonicalise,
    /// and price. Throws OptionSelectionValidationException (V1–V5) on invalid input.
    Task<OptionSelectionResult> NormalizeAndPriceAsync(
        Guid productId, JsonDocument? selection, CancellationToken ct = default);
}

public record OptionSelectionResult(
    string CanonicalSelectionJson,       // complete, sorted — the merge key and the stored form
    bool IsDefault,
    decimal Adjustment,                  // signed
    string Currency,
    decimal? UnitSurcharge,              // from Product; null = none
    IReadOnlyList<OptionGroupAdjustment> Breakdown);

public record OptionGroupAdjustment(string GroupKey, IReadOnlyList<string> ChosenKeys, decimal Amount);

11. API surface

Public (AllowAnonymous — tenant via existing header/subdomain resolution)

RouteReturns
GET /commerce/catalog/options The active option catalogue, ordered: groups with choices, prices, notes, recommended default, selection mode, currency. (The storefront's global personaliser reference.)
GET /commerce/catalog/products/{slug} (extended) ProductDto gains effectiveOptionGroups (this product's resolved groups/choices/default/mode — empty list = not personalisable) and unitSurcharge. One call renders a complete product page (Step 2 FR-11.5: the card sub-line names only the groups this product offers).
POST /commerce/catalog/products/{slug}/selection-quote Body: a selection. Returns OptionSelectionResult — lets the storefront show authoritative deltas while the customer toggles options, before any cart exists. Read-only semantics (POST for the body); no state is created.

12. Order-landing contract (DetailsJson envelope)

Defined here, written by Spec C at checkout. OrderItem.DetailsJson for a line with a selection carries:

{
  "personalisation": {
    "selection":   { "portion": "full", "protein": ["salmon"], "side": "none", "heat": "medium" },
    "summary":     "Full table · Salmon · No side",   // differs-from-default only; "" when isDefault
    "isDefault":   false,
    "adjustment":  8.00,                              // signed, per unit
    "currency":    "GBP",
    "breakdown":   [ { "group": "portion", "chosen": ["full"], "amount": 10.00 },
                     { "group": "side",    "chosen": ["none"], "amount": -2.00 } ]
  },
  "unitSurcharge": 4.00                               // omitted when null
}
  • The stored selection is the complete canonical form — a later default change never rewrites history, and production sheets (specs 055/056) can render lines without joining back to the live catalogue.
  • summary lists only what differs from the default at order time (Step 2 FR-11.4); it is presentation convenience, the selection is the truth.
  • The envelope is additive within DetailsJson — other order concerns may add sibling keys; nothing may nest inside personalisation.

14. Security & tenancy

  • All three entities are ITenantScoped; global tenant query filters apply via AonikDbContextBase. No cross-tenant reads are possible through the services.
  • Public endpoints are read-only (selection-quote computes, never writes), serve Active/IsActive data only, and resolve tenant exactly as the existing anonymous catalog endpoints do (X-Tenant-Id header / subdomain — plan decision D3: no API-key layer).
  • Admin writes require AdminWritePolicy, reads AdminUserPolicy, matching existing Commerce admin endpoints.
  • No PII anywhere in this model. Price data is tenant-commercial, already the sensitivity level of ProductPrice.

15. Config-pack & tenant vocabulary

  • New tenant setting Commerce.Storefront.RecommendedChoiceLabel — the display label storefronts render beside the recommended default. Default: "Recommended". The Abby's Table tenant configures "Abby's choice". Served to storefronts via the storefront config document (Spec E); until E lands, the frontend may hold it.
  • The food-commerce pack MAY seed a starter option catalogue (portion/protein/side/ heat with zero prices) so a fresh tenant demos personalisation. Seeding rides CommerceTenantProvisioningContributor, idempotent, gated on the Commerce module — never on business type. Optional task; not a blocker.

Naming: NormalizeAndPriceAsync_Should_ReturnNegativeAdjustment_When_ChosenPriceBelowDefault.

18. Acceptance criteria

#Given / when / then
A1A group with default side priced 2.00; a selection choosing a 0.00 side → adjustment includes −2.00 and total adjustment reflects it (Step 2 AC-9 analogue).
A2A product narrowed to exclude choice "chicken" while "chicken" exists in the catalogue; a selection containing it → HTTP 400 naming V2 (Step 2 AC-24).
A3A product with no ProductOptionGroup rows → effectiveOptionGroups: [] on the DTO; selection-quote with any non-empty selection → 400 (Step 2 AC-25).
A4A product overriding a single-select protein group to multi; selection ["salmon","chicken"] → both surcharges summed, default subtracted once; the same keys in reverse order produce byte-identical canonical JSON.
A5A multi-select group with zero chosen → 400 naming V4.
A6Empty/omitted selection on a personalisable product → normalises to all defaults, isDefault: true, adjustment 0.
A7Repricing a choice via admin → the next selection-quote reflects it with no other write (deltas are derived, not stored).
A8Deactivating the only resolvable default for a product's narrowing → authoring 400 naming the product (V9).
A9UnitSurcharge set on a product → returned on DTO and selection-quote, excluded from adjustment.
A10All new endpoints tenant-isolated: tenant B never sees tenant A's groups regardless of ids supplied.

19. Open decisions

O1 — Money representation in public DTOs. Internal storage is decimal (consistent with ProductPrice). The storefront works in integer minor units. Whether public Commerce DTOs serve minor units globally is the plan's "money at the API edge" wiring item — this spec follows whatever that decides; until then DTOs serve decimals and the frontend's client class converts.

O2 — Multi-currency option pricing. Currency lives on the group (launch-simple, one storefront currency). If a tenant ever runs one catalogue across currencies, choices need per-currency prices like ProductPrice. Deliberately deferred; the group-level field keeps the door open without the join today.

O3 — Choice-level media. Step 2 renders text-only options. If option photography is ever wanted, OptionChoice gains a media reference then — not speculatively now.
