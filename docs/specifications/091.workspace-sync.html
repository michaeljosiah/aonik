Workspace sync: moving a tree between a folder and the cloud

Spec 089 defines what the platform stores and enforces: workspaces, blobs, revisions, sharing, quota. This spec defines how a tree gets in and out — the negotiation, the transfer of large media, and the part that is genuinely hard, which is applying a pull to a folder on someone's disk without ever losing their work. It was split out of 089 because three rounds of review put almost every finding on this half while the model underneath went quiet.

1. Summary

A world is a folder. Spec 089 gives the platform somewhere to keep a copy of it — content-addressed blobs, revisions as manifests, a head. This spec is the moving part:

  • Negotiation. "Which of these hashes do you not have?" — answered relative to the caller, so an unchanged 2GB world syncs in one round trip and no bytes.
  • Transfer. Multipart, resumable, streaming-hashed, because the largest objects in a world are video takes and a 4GB upload that fails at 3.9GB must not start again.
  • Application. Writing a pulled revision into a live folder that editors, backup agents and the author are all touching — without losing anything.
The one sentence this spec exists for Sync must never destroy authored work. Everything difficult here follows from that, in a product whose premise is "nothing enters the authored record without a human accept." A sync that loses a scene is not a bug in a feature — it is a breach of the product's central promise, and it will be discovered by the person who wrote the scene.

2. Why this is its own specification

089 originally carried both halves. Three rounds of adversarial review produced 44 findings, 31 of them P1, and the distribution is the argument:

AreaFindingsReading
Model, sharing seam, quota designQuiet after round 1Settled. Buildable. Ordinary platform work.
Sync, transfer, pull applicationThe large majority, and round 3's were mostly consequences of round 2's fixesA distributed-systems problem wearing a storage problem's clothes.

ADR-016 said as much before any of it was written: "Sync is the highest-risk component in the plan, and everything else here is plumbing." Three rounds of review agreeing with that is confirmation rather than news — and the practical consequence is that one document was making the settled half look as unfinished as the hard half, and giving reviewers one budget for two very different jobs.

What the split buys 089 can be built and merged while this is still being argued about. The container, revisions, sharing and quota are what Arke Kids needs first and what the commercial storage tier is priced on. Sync is what Arke Studio needs, it is later in the sequence anyway, and it now gets its own review budget instead of sharing one with the plumbing.

3. Scope (in / out)

3.1 In scope

  • The push and pull protocols, and the negotiation that precedes both.
  • Resumable multipart upload for large media, and the memory discipline that goes with it.
  • Applying a pulled revision to a local folder: staging, journalling, conditional replay, recovery.
  • The reserved .aonik/ metadata subtree.
  • What the client must do when the local tree is dirty, and when another program has touched it.
  • The client's side of divergence — the server's side is 089 §7.

3.2 Out of scope

  • Everything 089 owns: the model, blob storage, revision commit semantics, sharing, quota, and all server-side validation.
  • Real-time collaborative editing, operational transform, CRDTs. A tree at a time, by a human's decision.
  • Merge algorithms of any kind. §9 is emphatic about this.
  • Server-side execution of Arke's job queue, and any platform understanding of file contents.
  • Partial or selective sync of a subtree. A workspace moves whole.

4. The four quadrants

Arke's specification warns that conflating the authoring path (OpenCode, file edits) with the media path (the job queue, providers) is the main architectural risk it exists to prevent. Local-versus-remote crosses both, giving four combinations where the product currently reasons about two. This spec fixes which it supports:

AuthoringMedia
Local unchanged OpenCode in a staging directory, as today. Free tier, offline. unchanged The local job queue calls providers with the user's own keys.
Remote this spec Sync only. The cloud stores and serves the tree; it does not run OpenCode. not v1 Server-side dispatch is a separate subsystem and is where credits are consumed. Named in ADR-016's follow-ups.
The cloud does not author Remote authoring would mean running the harness server-side, which needs the provider keys, the staging directory, the accept gate and the ripple check — that is the whole product, rebuilt on a server. v1 syncs a tree and nothing more. Everything anyone does to a world still happens on a machine they control.

5. The protocol

PUSH PULL ──── ──── 0. recover any pending journal first 0. recover any pending journal first (§7.2.2 — no read path skips this) AND classify local vs RECORDED HEAD: 1. client builds manifest of local tree dirty + remote ahead -> commit the EXCLUDING .aonik/ (§7.2.3) dirty tree FIRST, so it diverges 2. POST manifest hashes -> server as a proposal (§7.2.1) server replies: missing[] 1. client asks for head revision 3. client uploads only missing blobs 2. server returns manifest (multipart, resumable — §7.1) 3. diff against local tree 4. client commits (manifest + parent + 4. download missing blobs TO .aonik/ client CommitId + request hash, staging, verifying each hash §7.3); server head advance is a 5. write .aonik/pull.journal, apply, RowVersion CAS (§7.4) record head, delete journal, server: FastForward | Diverged sweep staging — IN THAT ORDER

Two round trips before any byte moves, and the second is empty when nothing changed. There is no long-lived connection, no server-side session and no lock: a client that dies mid-upload has uploaded blobs that nothing references yet, which the sweeper reclaims.

6. Negotiation is scoped to the caller

P0 — missing[] is relative to the caller, never to physical storage

Once possession is required at commit (089 §12), answering the negotiation from physical blob existence breaks in both directions for a hash that exists but belongs to another subscriber:

  • Answer "present" → it leaks the existence oracle §14 just closed, and the client skips the upload; commit then refuses the hash as unpossessed and the client is deadlocked — it has been told the server has the bytes and told the bytes are missing, with no action that resolves it.
  • Answer "missing" → correct, but only if the resulting upload can actually establish possession.

So the definition is: missing[] contains every hash the caller does not possess and cannot reach, regardless of whether the bytes are physically stored. Negotiation and commit then answer the same question, which is what makes the protocol terminate.

The upload of an already-stored blob is the path that closes the loop, and it is why PromoteAsync reporting AlreadyPresent must still write the possession row (089 §5): the caller supplied the bytes, so they have demonstrated possession, and the physical object is simply reused. The cost is one redundant upload the first time a subscriber independently produces content another already holds — which is the correct price for not turning a hash into a bearer token, and it is invisible in the common case where the caller uploaded the blob themselves. This exact path is a named acceptance criterion, because it is the one an implementation is most likely to "optimise" back into a leak.

7. Large blobs need a real resume protocol, not whole-blob retry

P0 — the correction

An earlier draft claimed hash-naming made "a resumable large-media sync possible without any resume protocol," because a client can simply ask again which hashes are missing. That is resume between blobs, not within one. A 4GB video take that fails at 3.9GB is missing, so the whole 4GB transfers again — on a domestic uplink that is hours, repeatedly, and it is the single most likely reason a customer concludes sync does not work.

There is a second, sharper problem on the server side: FileStore.UploadAsync copies a non-seekable stream into a MemoryStream before writing. A handful of concurrent multi-gigabyte uploads is then not a slow request — it is an out-of-memory kill of the API process. This is a correctness issue before it is a performance one.

P3 therefore specifies the media path explicitly:

  • Streaming hash. StageAsync hashes as it writes and never materialises the object in memory. No MemoryStream on any path that can carry a take.
  • Multipart with checkpoints. A blob above a threshold (proposed: 32MB) uploads in parts. The server records which parts it holds against the staging id, so a resumed upload asks "which parts of this blob do you not have" — the same question as the manifest negotiation, one level down.
  • Staging expiry. An abandoned staging id and its parts are swept on the same job as orphan blobs. Incomplete uploads must not be billable and must not accumulate.
  • Verification on promote, not on trust. The assembled parts are hashed and compared to the hash the client declared. A mismatch discards the staged object — this is also the hash-substitution defence in 089 §12.

8. Applying a pull must be crash-safe

P0 — the failure this prevents Step 5 originally read "client writes files, records head." Interrupt that on a large manifest — a crash, a battery, a force-quit — and the folder holds a mixture of two revisions and the head pointer still names the old one. On restart the tree matches neither manifest, and the next push presents that mixture as a legitimate third revision: silently reverting deletions and overwriting accepted work, with the accept gate none the wiser because it only sees a well-formed proposal. This is the worst outcome in the entire design — it destroys authored work while looking like normal operation.

The application of a pull is therefore a four-phase commit against the local disk:

  1. Precondition: the tree must be clean. Before anything else, compare the live tree against the locally recorded head manifest. See §8.1 — skipping this destroys uncommitted work.
  2. Stage. Every needed blob is downloaded into .aonik/staging/ (§8.3) and verified against its hash. Nothing in the live tree is touched. This phase is fully restartable and idempotent — a re-run downloads only what is still missing.
  3. Journal. Write .aonik/pull.journal naming the target revision and the complete set of file operations (add, replace, delete). Written and flushed before the first mutation of the live tree. Its presence is also the in-progress marker of §8.2.
  4. Activate, then record, then clear. Apply the operations, record the new head, delete the journal, then sweep staging — strictly in that order.

Recovery is then mechanical rather than heuristic: a journal present at startup means a pull was interrupted. The client re-applies it from the beginning (every operation is idempotent — the source blobs are still staged and hash-verified), records the head, and deletes the journal.

8.1 A pull must never overwrite uncommitted local work

P0 — the most destructive gap remaining after Rev 2

The PULL sequence diffed the remote manifest against the live tree and activated. It never compared the live tree against the locally recorded head. So if the author had uncommitted edits — a rewritten scene, a new sheet, a deletion — and another machine had advanced the cloud head, the pull would quietly overwrite or delete that work.

And it would never enter the divergence flow at all. §8's whole promise is that a conflicting change becomes a proposal a human accepts; uncommitted local work would have been destroyed before reaching the mechanic designed to protect it. Everything else in this spec assumes the local tree is either clean or has been committed; nothing enforced it.

Pull therefore begins by classifying the local tree against its recorded head:

Local tree vs recorded headRemote headWhat happens
Clean (matches)AheadFast-forward. Stage, journal, activate. The ordinary case.
CleanSameNothing to do.
Dirty (differs)SameNothing to do — local work is simply uncommitted, which is normal and not sync's business.
DirtyAheadCommit the dirty tree as a local revision first, parented on the recorded head. That commit then diverges from the remote head by construction — so it reaches 089 §7 as a proposal and the human decides, which is exactly what should happen.
Why snapshotting beats a clean-tree precondition Refusing to pull until the user commits is defensible but hostile: it makes sync fail with homework attached, and a creative tool's users do not think in commits. Snapshotting first is strictly better — no work is ever at risk, the divergence machinery already exists and is the product's own accept gate, and the user sees the question they should see ("these two versions differ, which do you want?") rather than an instruction to tidy up before they are allowed to sync.

8.2 What the invariant actually is

P0 — Rev 2 overstated this, and the overstatement mattered

Rev 2 claimed "a local tree is never in a state that is not either revision N or N+1." That is false and the journal does not make it true. If the process dies after the first journal operation and before the last, the folder is a mixture. The journal makes that state recoverable; it does not make it unobservable, and another process — the derived index, a text editor, a backup agent, a second client instance — can read the mixture in the meantime.

An atomic root swap would make it literally true, but not for this product: the workspace is a folder the user has open in editors and Explorer, and swapping it out from under a live multi-gigabyte tree means either a full copy or breaking every open handle. So the honest move is to state the weaker invariant and enforce it, rather than assert the stronger one and rely on it.

The invariant, restated so it is true:

A mixture is possible ON DISK, and is NEVER OBSERVED, because:

  the journal exists  ⟺  the tree may be mid-application

and EVERY operation that reads or publishes the tree — index build,
push, manifest construction, export, opening the workspace — MUST
run recovery to completion first, or refuse.

There is no read path that inspects the tree without checking for
a journal. That check is the enforcement; the invariant is its
consequence.

Concretely: the client refuses to build a manifest, refuses to push and refuses to serve a file read while a journal is present, completing recovery first. Recovery is fast — the blobs are already staged and verified, so it is local file moves — so "refuse then repair" is measured in seconds, not a user-visible outage. And the acceptance criterion is written against what is actually guaranteed: recovery completes before any read or push, not that the filesystem is atomic.

8.2.1 Programs we do not control, and the edit we must not destroy

P0 — the §7.2.2 gate only binds operations that go through us

§7.2.2 admitted that an editor, a backup agent or a second client instance can observe a partial tree, then specified an invariant enforced only on paths routed through the sync client. Those programs do not call our code and will never run recovery. And the sharper half is not the reading at all: an edit made by the author during a partial activation is silently destroyed when the journal replays, because replay was specified as unconditional.

The workspace is deliberately a plain folder — that is the product's premise and is not negotiable — so the honest position is that we cannot make external access impossible, and must instead make it non-destructive.

The guarantee splits in two, because the two halves are not equally achievable:

GuaranteeHow
Reading a partial tree Not prevented. Stated plainly rather than papered over. A backup agent that copies mid-activation gets a mixture. We narrow the claim to what is true: no operation we control observes one, and the window is seconds. A .aonik/pull.journal present is a machine-readable "syncing" marker any well-behaved tool can honour, and the app's own UI blocks its editing surface for the duration.
Destroying an external edit Prevented outright. This is the part that actually matters. Every journal operation is conditional on the observed pre-state. See below. 
Each journal entry records: path, expected-hash-before, target-hash-after.

On apply or replay, hash the file that is actually there:

  matches expected-before -> apply. The ordinary case.
  matches target-after    -> already applied. Skip. (This is what makes
                             replay idempotent without being destructive.)
  matches NEITHER         -> SOMEONE ELSE CHANGED IT. Do not overwrite.
                             Move it to .aonik/conflicts/<path>, apply the
                             target, and surface it to the user as a
                             conflict — which is a mechanic the product
                             already has (§8).
  absent, expected present -> same treatment: record and surface.
Why conditional replay is the right shape It costs one hash per touched file — negligible next to the I/O already being done — and it converts the entire class of "something else touched the tree mid-pull" from silent data loss into a conflict the user is shown. It also makes replay safe after an arbitrarily long interruption: a machine that crashes mid-pull and is resumed a week later, with edits in between, still cannot lose those edits. The weaker invariant is honestly stated; the stronger promise — we never destroy an edit we did not expect — is the one worth actually holding.

8.3 Sync state lives outside the manifest

P0 — a defect Rev 2's own fix introduced Rev 2 put the staging directory inside the workspace and had recovery delete only the journal. But push builds its manifest from the workspace directory — so after a successful or recovered pull, the next push would treat the leftover staged blobs as authored files, upload them, add them to the manifest and charge them against the byte ceiling. A pull would silently inflate the world with copies of its own internals, and the more sync ran the worse it would get.
  • All sync state lives under a single reserved subtree: .aonik/ — journal, staging, the recorded head, the part-upload state from §7.
  • Manifest construction excludes .aonik/ unconditionally, and the exclusion is in the manifest builder rather than in each caller, so there is one place to get it right.
  • A commit naming any path under .aonik/ is refused server-side as malformed. A client cannot smuggle sync state into a world, deliberately or by regression, and the server does not rely on the client's exclusion being correct.
  • The reserved-prefix check runs on the normalised path, not the literal one.
    P0 — a literal prefix check lets the manifest overwrite the recovery journal A manifest path of .AONIK/pull.journal passes a literal "starts with .aonik/" test and is the same file on a case-insensitive Windows client. The portable-equivalence rule in §14 does not save this, because that rule rejects colliding pairs and a hostile manifest need contain only the one alias. During pull it would overwrite pull.journal — the very file recovery depends on — turning a crash into an unrecoverable tree. Trailing-dot and trailing-space variants (.aonik./) behave the same way. The reserved-prefix check therefore applies the same normalisation as §14 — NFC, case-fold, strip trailing dots and spaces, per segment — and rejects every alias.
  • Staging is swept after a successful activation and on recovery completion — not left for the next run to trip over.

9. Divergence, from the client's side

The server detects divergence, stores the revision and offers three resolutions (089 §7). The client's job is smaller than it looks, and deliberately so.

Sync reuses the product's own mechanic Arke Studio's core mechanic is the accept gate: "nothing enters the authored record without a human accept… proposals are ripple-checked against canon." A remote revision that does not descend from the local head is a proposal. It is ripple-checked and accepted exactly as a locally-drafted change is.

This is the most important design decision across both specs, and it is a decision to not build something. No merge algorithm, no three-way diff, no conflict markers, no new vocabulary for the user to learn — because the product already has a word for "a change that has not been accepted yet", and this is one.

So the client, on receiving Diverged:

  1. Does not apply the remote head. Nothing about the local tree changes.
  2. Fetches both manifests and computes the differing paths — a set comparison over path → hash, needing no understanding of contents.
  3. Hands them to the product, which ripple-checks and presents them through the accept gate it already has.
  4. Calls 089's ResolveAsync with whichever of Accept / Reject / Supersede the human chose.

Nothing in that list requires the platform or the sync client to know what a canon entry is. The client moves bytes and set-differences; the product decides; the platform records. That separation is what keeps the seam in ADR-016 honest under the one operation most likely to break it.

10. Phasing & tasks

Sequenced after 089 P1–P4, which this depends on entirely, and after 090, which gates whether any of it is a paid feature.

PhaseWorkShips when
S1 — negotiation The missing[] endpoint, scoped to caller possession (§6); manifest construction excluding .aonik/. An unchanged 1GB workspace reports nothing missing; a hash held only by another subscriber is reported missing and the follow-up upload establishes possession.
S2 — transfer Multipart upload with server-recorded part state, streaming hash, staging expiry, declared-length enforcement. A 4GB upload interrupted at 90% resumes without re-sending the first 90%; no path materialises a blob in memory; a caller declaring 1MB and streaming 4GB is aborted at the bound.
S3 — push Manifest build, upload of the missing set, commit with a client CommitId. A world authored offline for a week pushes in one pass; a retried push creates no second revision.
S4 — pull The whole of §8: clean-tree classification, staging, the journal, conditional replay, recovery-before-read, .aonik/. The acceptance list in §11 passes in full. This is the phase the split exists for and it should not be rushed to meet a date.
S5 — divergence Manifest diff for the accept gate, and the ResolveAsync round trip. A divergent revision is surfaced with its differing paths and resolved all three ways.

11. Acceptance criteria

The destructive cases first, because they are the ones that matter.

  1. A pull onto a tree with uncommitted local edits, where the remote head has advanced, commits the local work as a revision first — that commit diverges and reaches the accept gate. No local edit is overwritten or deleted without a human decision.
  2. A journal replay whose target file was modified externally does not overwrite it: the file is moved to .aonik/conflicts/ and surfaced. This holds after an arbitrarily long interruption — crash mid-pull, resume a week later with edits in between.
  3. A replay over an already-applied file is a no-op.
  4. A pull interrupted between the journal write and completion is recovered to completion before any read, index build, manifest construction or push is permitted. No read path inspects the tree without first checking for a journal.
  5. A staged blob failing hash verification is discarded and never enters the live tree.
  6. A push after a completed or recovered pull carries no .aonik/ content.
  7. A 4GB upload interrupted at 90% resumes without re-transferring the first 90%.
  8. No upload path buffers a whole blob in memory — proven by uploading a file larger than the process working set.
  9. An upload declaring 1MB and streaming 4GB is aborted at the declared bound, discarded, and its claim released, with no partial object promoted.
  10. missing[] lists a hash the caller does not possess even when the bytes are physically stored for another subscriber; the subsequent upload establishes possession although promote reports AlreadyPresent, and the commit then succeeds. Tested end to end.
  11. An unchanged workspace of at least 500MB completes a sync with zero blob transfers.
  12. A divergent commit is surfaced with its differing paths, never applied, and resolvable all three ways.
  13. dotnet build and dotnet test Aonik.sln green.

12. Open decisions

#QuestionLeaning
S-O1 Multipart threshold? 32MB. Below it the part bookkeeping costs more than the retry it saves; above it a failed transfer is painful on a domestic uplink.
S-O2 Does the client watch the folder, or sync on demand? On demand first. A file watcher over a tree an AI harness is actively writing produces a storm of partial states, and the product already knows when a change has been accepted — which is the only moment worth syncing.
S-O3 How long do staged blobs survive an abandoned pull? 24 hours. Long enough to resume after a laptop is closed overnight, short enough that abandoned staging is not a storage class of its own.
S-O4 Should a pull be attemptable while the product has files open? Yes, with §8.2.1's conditional replay as the safety net. Refusing until every editor is closed is unenforceable on a plain folder and would make sync feel broken.
S-O5 Is there a size or file-count above which we refuse to sync a workspace at all? Not a hard refusal, but a warning. The byte ceiling (089 §9) is the real limit, and a second one here would be two places to be wrong.
