Spec 028 Status: Draft Size: Medium Priority: P2 Domain: Finance / Accounts

AccountTransaction auto-categorization in Aonik.Finance

Replaces the current pass-through of raw Plaid category strings on AccountTransaction with a deterministic four-step classification pipeline (lock check → provider mapping → merchant memory → fallback) that runs during every sync, assigns a Chronicle canonical category and optional sub-category, and records the method and confidence so manual overrides survive subsequent syncs. Mirrors the Midday auto-categorization model against Aonik's African-consumer taxonomy without introducing AI/LLM classification.

1. Summary

Today AccountTransactionSyncOrchestrator.ApplyProviderTransaction copies the raw provider category string onto AccountTransaction.Category (transaction.Category = TrimNullable(providerTransaction.Category), AccountTransactionSyncOrchestrator.cs:242). That string is the unmapped Plaid personal_finance_category.primary (e.g. "FOOD_AND_DRINK") and is unusable for reporting, budgeting, or agent reasoning.

This spec wires the existing TransactionCategoryReference taxonomy into the sync orchestrator, adds three persisted fields on AccountTransaction (SubCategory, CategoryMethod, CategoryConfidence, CategoryLockedAt), introduces a per-tenant merchant memory table, and exposes endpoints for manual overrides and bulk re-classification. Migration ownership stays in AonikDbContext per ADR-005.

Success signals After deployment, no row inserted by AccountTransactionSyncOrchestrator carries a non-Chronicle value in Category; every new row has a non-null CategoryMethod; manually-overridden transactions survive three consecutive syncs; the bulk re-categorization endpoint maps existing legacy rows from raw Plaid strings to canonical codes with zero hand-written migrations.

2. Context & motivation

Midday's auto-categorization (see midday.ai/docs/auto-categorization/) runs a four-step process — analyse merchant, check history, consider patterns, assign category — and feeds manual corrections into per-merchant memory. Their taxonomy is 14 B2B categories (Revenue, COGS, Operations). Aonik's Chronicle taxonomy is 26 purpose-driven categories built for African consumer and cross-border money contexts. The pipeline logic translates directly; the taxonomy does not.

Specific problems this spec solves:

ProblemEvidence
AccountTransaction.Category stores the raw Plaid primary, not a Chronicle code. AccountTransactionSyncOrchestrator.cs:242 — pass-through assignment with no mapping.
No SubCategory, so the Plaid detailed field is dropped on the floor. AccountTransaction.cs — entity has neither SubCategory nor any of the new fields.
No record of how a category was assigned, so manual overrides are silently overwritten on the next sync. Every sync runs ApplyProviderTransaction on existing rows; no lock or method field gates the assignment.
No per-tenant merchant memory, so corrections are not learnt. No AccountTransactionMerchantCategory table exists; corrections live only on the corrected row.
Reuse opportunity TransactionCategoryReference already ships the full 26-category taxonomy, sub-category metadata, and the PlaidPrimaryCategoryMap / PlaidDetailedCategoryMap dictionaries with a single entry point MapPlaidCategoryWithSubCategory(primary, detailed). No taxonomy work is needed — only wiring and a small set of new persisted fields.

3.1 In scope

  • Edit AccountTransaction to add SubCategory, CategoryMethod, CategoryConfidence, CategoryLockedAt.
  • New AccountTransactionMerchantCategory entity + EF configuration + DbSet on AonikDbContext and FinanceDbContext.
  • New IAccountTransactionCategorizer service and MerchantKeyNormalizer helper.
  • Edit AccountTransactionSyncOrchestrator to call the categorizer during sync, pre-fetch merchant rules, and stop pass-through assignment.
  • New EF migration AddAccountTransactionCategorization against AonikDbContext.
  • New admin endpoints: PATCH /admin/accounts/transactions/{id}/category, DELETE /admin/accounts/transactions/{id}/category/lock, GET /admin/accounts/merchant-categories, DELETE /admin/accounts/merchant-categories/{id}.
  • New bulk re-categorization endpoint: POST /admin/accounts/connections/{connectionId}/transactions/recategorize.
  • New unit tests for the categorizer and integration tests for the endpoints + orchestrator extension.

3.2 Out of scope

  • AI / LLM-based classification (Midday's Step 3). Deferred to Phase 2; would slot between merchant memory and fallback and report CategoryMethod = "ai_classifier".
  • Cross-tenant merchant signals. Aonik stays strictly tenant-scoped in Phase 1 — no shared global merchant dictionary.
  • The PersonalFinance PersonalTransaction entity, which has its own richer classification model (ConfidenceScore, CategorisedBy, ClassificationMethod, ReviewStatus). A future unification spec will align both modules.
  • Category-management UI / CRUD. Chronicle categories stay code-defined.
  • Reporting and burn-rate analytics. Downstream consumers; their spec lives elsewhere.
  • Webhook-triggered re-categorization on Plaid correction events. The current PlaidAccountWebhookProcessor already triggers transaction syncs — the categorizer runs on every sync, so corrected categories propagate naturally. Bespoke webhook handling is unnecessary in Phase 1.

7. Plaid → Chronicle mapping

TransactionCategoryReference ships two dictionaries:

  • PlaidPrimaryCategoryMap — 18 Plaid primary values → Chronicle top-level codes. Used as fallback when no detailed match exists.
  • PlaidDetailedCategoryMap — composite "PRIMARY.DETAILED" keys → (category, subCategory?) tuples. Provides both category and optional sub-category in a single lookup.

The entry point is TransactionCategoryReference.MapPlaidCategoryWithSubCategory(primary, detailed). Behaviour:

  • Both inputs null/empty → (null, null).
  • Detailed key matches PlaidDetailedCategoryMap → that entry's (category, sub).
  • Detailed key absent but primary present in PlaidPrimaryCategoryMap → (canonical, null).
  • Primary unrecognised → ("other", null).

8. Schema changes

8.1 AccountTransaction — four new columns

ColumnTypeNullableDescription
SubCategory nvarchar(100) Yes Chronicle sub-category code; must be valid for the assigned Category. Null when no sub-category applies.
CategoryMethod nvarchar(50) Yes One of provider_mapped, merchant_rule, manual, fallback. Null on legacy rows that pre-date this spec.
CategoryConfidence decimal(5,4) Yes 0.0–1.0. Used to sort uncertain transactions for manual review. Null on legacy rows.
CategoryLockedAt datetime2 Yes When a user manually set the category. Non-null locks the category against future sync overwrites.

The existing Category column stays in place but its semantics change: it must henceforth hold a Chronicle canonical code or be null. The raw provider string is consumed transiently inside the categorizer and not persisted.

Legacy rows Existing rows that hold raw Plaid strings in Category (e.g. "FOOD_AND_DRINK") are left untouched by the migration. The bulk re-categorization endpoint (§14) is run once per connection after deployment to normalise them. Run once, not repeatedly — see the re-categorization callout.

9. Classification pipeline

Four ordered steps. The first step that yields a confident result wins; subsequent steps are skipped.

┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ Step 1 │ → │ Step 2 │ → │ Step 3 │ → │ Step 4 │ │ Lock check │ │ Provider map │ │ Merchant │ │ Fallback │ │ (CategoryLocked│ │ Plaid → │ │ memory │ │ "other" or │ │ At not null)│ │ Chronicle │ │ tenant rule │ │ "uncategorized"│ └──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘

Step 1 — Lock check

If AccountTransaction.CategoryLockedAt is not null, the transaction was manually categorized. Return unchanged. This guarantees a sync never overwrites a deliberate user decision.

Step 2 — Provider mapping

var (category, subCategory) =
    TransactionCategoryReference.MapPlaidCategoryWithSubCategory(
        providerTransaction.Category,      // Plaid primary
        providerTransaction.SubCategory);  // Plaid detailed
  • category non-null and not "other" → apply with method = "provider_mapped", confidence = 0.85. Stop.
  • category == "other" → continue to Step 3 with "other" held as a candidate.
  • category == null (no provider data) → continue to Step 3.

Step 3 — Merchant memory

Normalise providerTransaction.Merchant (falling back to providerTransaction.Description if Merchant is null) into a merchant key. Look it up in the per-tenant rule dictionary the orchestrator pre-fetched for the sync run.

  • Match found → apply rule's Category + SubCategory with method = "merchant_rule", confidence = 0.90. Stop.
  • No match → continue to Step 4.

Merchant-rule confidence is higher than provider mapping because the tenant explicitly set this rule — it reflects human intent rather than a probabilistic Plaid signal.

Step 4 — Fallback

  • Step 2 returned "other" → category = "other", method = "provider_mapped", confidence = 0.40.
  • Step 2 returned null (no provider data at all) → category = "uncategorized", method = "fallback", confidence = 0.00.

Confidence and method summary

MethodConfidenceMeaning
manual1.00User explicitly set; locked against future sync.
merchant_rule0.90Tenant merchant memory match.
provider_mapped (specific)0.85Plaid detailed yielded a specific Chronicle code.
provider_mapped (other)0.40Plaid primary mapped to "other"; no merchant rule.
fallback0.00No provider data; requires manual review.

10. Categorizer service

Interface

namespace Aonik.Finance.Services.Accounts;

internal interface IAccountTransactionCategorizer
{
    /// Classifies a single transaction in place. No-ops if CategoryLockedAt is set.
    void Classify(
        AccountTransaction transaction,
        AccountLinkProviderTransactionResult providerTransaction,
        AccountTransactionMerchantCategory? merchantRule);
}

Implementation

internal sealed class AccountTransactionCategorizer : IAccountTransactionCategorizer
{
    public void Classify(
        AccountTransaction transaction,
        AccountLinkProviderTransactionResult providerTransaction,
        AccountTransactionMerchantCategory? merchantRule)
    {
        // Step 1 — respect manual locks
        if (transaction.CategoryLockedAt is not null)
            return;

        // Step 2 — provider mapping
        if (!string.IsNullOrWhiteSpace(providerTransaction.Category))
        {
            var (cat, sub) = TransactionCategoryReference
                .MapPlaidCategoryWithSubCategory(
                    providerTransaction.Category,
                    providerTransaction.SubCategory);

            if (cat is not null && cat != TransactionCategoryReference.Other)
            {
                Apply(transaction, cat, sub, "provider_mapped", 0.85m);
                return;
            }
        }

        // Step 3 — merchant memory
        if (merchantRule is not null)
        {
            Apply(transaction, merchantRule.Category, merchantRule.SubCategory,
                  "merchant_rule", 0.90m);
            return;
        }

        // Step 4 — fallback (carry "other" from Step 2 if we had provider data)
        var hadProviderData = !string.IsNullOrWhiteSpace(providerTransaction.Category);
        if (hadProviderData)
            Apply(transaction, TransactionCategoryReference.Other, null,
                  "provider_mapped", 0.40m);
        else
            Apply(transaction, TransactionCategoryReference.Uncategorized, null,
                  "fallback", 0.00m);
    }

    private static void Apply(
        AccountTransaction tx,
        string category,
        string? subCategory,
        string method,
        decimal confidence)
    {
        tx.Category           = category;
        tx.SubCategory        = subCategory;
        tx.CategoryMethod     = method;
        tx.CategoryConfidence = confidence;
    }
}

DI registration

Register as scoped in FinanceModule.ConfigureServices: 

services.AddScoped<IAccountTransactionCategorizer, AccountTransactionCategorizer>();

11. Merchant memory

MerchantKeyNormalizer — static helper

Centralises key normalisation so the same key is produced at classification time and at override time. Lives at src/Aonik.Finance/Services/Accounts/MerchantKeyNormalizer.cs. 

internal static class MerchantKeyNormalizer
{
    private static readonly Regex WhitespaceRun = new(@"\s+", RegexOptions.Compiled);
    private static readonly Regex NoiseSuffix   = new(
        @"\b(ltd|limited|inc|plc|llc|corp|corporation)\b",
        RegexOptions.Compiled | RegexOptions.IgnoreCase);
    private static readonly Regex NonAlpha      = new(@"[^a-z0-9 \-]", RegexOptions.Compiled);

    public static string? Normalize(string? raw)
    {
        if (string.IsNullOrWhiteSpace(raw)) return null;

        var s = raw.ToLowerInvariant().Trim();
        s = NoiseSuffix.Replace(s, "");
        s = NonAlpha.Replace(s, " ");
        s = WhitespaceRun.Replace(s, " ").Trim();

        if (s.Length == 0) return null;
        return s.Length <= 200 ? s : s[..200];
    }
}

Examples (verify in unit tests):

  • "SPOTIFY AB" → "spotify ab"
  • "NETFLIX.COM" → "netflix com" (dot becomes space via NonAlpha, whitespace then collapsed)
  • "Acme Coffee Ltd " → "acme coffee" (noise suffix stripped, whitespace collapsed)
  • " &&& " → null (nothing left after stripping)

Lookup in the orchestrator

Pre-fetch all merchant rules for the tenant once before iterating transactions — the per-transaction loop only does dictionary lookups: 

var merchantRules = await _financeDbContext.AccountTransactionMerchantCategories
    .Where(r => r.TenantId == tenantId)
    .ToDictionaryAsync(
        r => r.MerchantKey,
        StringComparer.OrdinalIgnoreCase,
        cancellationToken);

// Inside the per-transaction loop:
var merchantKey =
    MerchantKeyNormalizer.Normalize(providerTransaction.Merchant)
    ?? MerchantKeyNormalizer.Normalize(providerTransaction.Description);

merchantRules.TryGetValue(merchantKey ?? "", out var merchantRule);
_categorizer.Classify(transaction, providerTransaction, merchantRule);

12. Sync integration

Edits to AccountTransactionSyncOrchestrator are surgical:

  1. Constructor-inject IAccountTransactionCategorizer as _categorizer.
  2. After fetching existingTransactionsByRef and before the per-transaction loop, pre-fetch merchant rules for the tenant into the dictionary shown above.
  3. Compute merchantKey and look up merchantRule inside the loop (once per provider transaction).
  4. Call _categorizer.Classify(transaction, providerTransaction, merchantRule) immediately after ApplyProviderTransaction.
  5. Remove transaction.Category = TrimNullable(providerTransaction.Category) from ApplyProviderTransaction (line 242). Category assignment is owned solely by the categorizer.
Updated paths When a sync updates an existing transaction, the categorizer still runs. If CategoryLockedAt is non-null, Step 1 returns and the manual category is preserved. If the row is unlocked, the category may be updated — intentional, because Plaid often refines its categorization on subsequent syncs.

13. API endpoints

PATCH /admin/accounts/transactions/{id}/category

Manually override a single transaction's category.

Request

public record SetAccountTransactionCategoryRequest(
    Guid Id,
    string Category,
    string? SubCategory,

    /// When true, upsert an AccountTransactionMerchantCategory rule
    /// so future transactions from this merchant categorize the same way.
    bool RememberForMerchant
);

Validation

  • Category → TransactionCategoryReference.IsValidCategory(...) must return true.
  • SubCategory non-null → TransactionCategoryReference.IsValidSubCategory(Category, SubCategory) must return true.
  • Transaction must belong to the caller's tenant.

Behaviour

  1. Load AccountTransaction by Id + tenant. 404 if missing.
  2. Set Category, SubCategory, CategoryMethod = "manual", CategoryConfidence = 1.00m, CategoryLockedAt = DateTime.UtcNow.
  3. If RememberForMerchant = true and the transaction has a non-null Counterparty (falling back to Description):
    • Compute merchantKey via MerchantKeyNormalizer.Normalize.
    • Upsert AccountTransactionMerchantCategory by (TenantId, MerchantKey).
  4. Save and return 200 OK with the updated transaction.

Response

public record AccountTransactionCategoryResult(
    Guid Id,
    string Category,
    string? SubCategory,
    string CategoryMethod,
    decimal CategoryConfidence,
    DateTime? CategoryLockedAt,
    bool MerchantRuleCreated
);

14. Re-categorization

Bulk endpoint to normalize legacy transactions (raw Plaid strings in Category) and replay the pipeline against the current merchant memory.

POST /admin/accounts/connections/{connectionId}/transactions/recategorize

Request

public record RecategorizeAccountTransactionsRequest(
    Guid ConnectionId,

    /// When true, re-classify even transactions with CategoryLockedAt set.
    /// Requires explicit opt-in to prevent accidental unlock of manual overrides.
    bool IncludeLocked = false,

    /// Limit to transactions whose CategoryMethod is null, "fallback", or whose
    /// Category is null. Excludes already-categorised provider-mapped rows.
    bool UnresolvedOnly = true
);

Behaviour

  1. Load AccountTransaction rows for the connection, filtered by IncludeLocked and UnresolvedOnly.
  2. Pre-fetch merchant rules for the tenant.
  3. For each transaction, construct a synthetic AccountLinkProviderTransactionResult using the row's existing Category as the raw Plaid primary and null for detailed (legacy rows did not preserve the detailed value). Run _categorizer.Classify(...).
  4. Save in a single SaveChangesAsync call.
  5. Return { Processed, Updated, Skipped }.
Footgun Idempotent but lossy on stale data. Re-categorization on legacy rows uses the row's old raw Plaid string as provider input. After the first run the transaction carries a canonical code and the raw string is gone. A second run will feed the canonical code into MapPlaidCategoryWithSubCategory, which does not recognise it (canonical codes are not Plaid keys) and will fall back to uncategorized unless a merchant rule matches. Run once per connection immediately after deployment, not repeatedly. Endpoint should guard with UnresolvedOnly = true by default and reject if IncludeLocked = true without a confirmation flag.

15. Module-boundary strategy

TransactionCategoryReference lives in Aonik.PersonalFinance, not Aonik.Finance. The new categorizer needs to call it from inside Aonik.Finance. Three options were considered:

OptionCostVerdict
A — Ride the Spec 027 transitional shim. Use the existing transitional ProjectReference (Aonik.Finance → Aonik.PersonalFinance) and the existing transitional InternalsVisibleTo Aonik.Finance. Builds today, no new surface area. Couples Spec 028 to Spec 027 Phase 3 sequencing. Chosen for Phase 1. Both transitional grants already exist; both are tagged for removal at the end of Spec 027 Phase 3. Spec 028 Phase 2 below removes the dependency cleanly.
B — Promote TransactionCategoryReference to public and rely on the transitional ProjectReference. Widens the public surface of Aonik.PersonalFinance. Locks in a cross-module coupling that Spec 027 wants to remove. Rejected. The grant is explicitly transitional.
C — Move the Plaid map and category constants to SharedKernel immediately. Pre-empts a Spec 027 Phase 3 decision and forces a refactor of every existing PF consumer of TransactionCategoryReference. Rejected for now; revisit if Spec 027 Phase 3 decides the taxonomy belongs in SharedKernel.

Resolved: Option (2) — promote the slice to SharedKernel

Decision · resolved Option (1) was rejected because AccountTransaction stays in Aonik.Finance (it's a Finance-domain entity supporting tenant-scoped bank linking, not exclusive to PersonalFinance). The categorizer therefore stays next to its entity. Option (2) — promoting the cross-boundary slice of TransactionCategoryReference to SharedKernel — was chosen and pre-positioned during Spec 028 implementation, ahead of Spec 027 Phase 3.

The promoted slice lives at SharedKernel/Abstractions/Finance/Categorization/:

  • IChronicleCategoryMapper — MapPlaidCategory, IsValidCategory, IsValidSubCategory.
  • PlaidCategoryMapping — (Category, SubCategory) result record.
  • ChronicleCategoryCodes — the Other + Uncategorized string constants the pipeline branches on.

PersonalFinance registers a singleton implementation (ChronicleCategoryMapper) that delegates to the existing TransactionCategoryReference. The Finance categorizer and category manager inject IChronicleCategoryMapper; neither references Aonik.PersonalFinance namespaces or the internal TransactionCategoryReference any more.

Net effect on Spec 027 Phase 3: when the transitional InternalsVisibleTo Aonik.Finance and the Aonik.Finance → Aonik.PersonalFinance ProjectReference are dropped, the Spec 028 categorizer keeps compiling. The taxonomy display metadata, sub-category dictionary, and PF-internal helpers stay in PersonalFinance.

22. Decisions baked in

DEC-1 The categorizer is rule-based, not AI. Midday's full process includes an AI step. Aonik defers it. The four-step rule pipeline reaches feature parity with Plaid mapping plus tenant memory, and any AI step slots in as Step 3.5 without re-shaping the entity.
DEC-2 Category assignment is the categorizer's exclusive responsibility. ApplyProviderTransaction stops writing Category. No other service writes Category, CategoryMethod, or CategoryConfidence. Locking flows only through the admin override endpoint.
DEC-3 Manual override sets CategoryLockedAt. Without locking, the next sync would silently overwrite the user's choice. Unlock is a separate explicit action (DELETE .../category/lock).
DEC-4 Single Plaid map. The categorizer consumes TransactionCategoryReference directly. We do not duplicate the dictionaries in Aonik.Finance.
DEC-5 The Plaid gateway stays a thin HTTP adapter. Mapping happens after the gateway returns. Alternative providers (Mono, Okra, etc.) plug in by emitting raw (primary, detailed) in AccountLinkProviderTransactionResult; the categorizer handles translation.
DEC-6 Bulk re-categorization is opt-in and single-shot per connection. No automatic backfill at startup; no scheduled job. The runbook calls it explicitly once per connection during the migration window.

23. Open design decisions

Resolved · O-1 Phase 6 boundary direction. Chose Option (2): promote the slice to SharedKernel.Abstractions.Finance.Categorization. See §15 for the implementation. Pre-positioned during Spec 028 itself rather than waiting on Spec 027 Phase 3.
Open · O-2 Confidence schema. 0.40 for "other" may be too high. Observed distribution after Phase 3 will tell us whether the value should drop to 0.20 or 0.10. Out of scope to tune in Phase 1; record actuals once enough syncs have run.
Open · O-3 Sub-category coverage for the long-tail Plaid detailed entries. Several GENERAL_SERVICES.* entries currently map to other with no sub-category. As real transaction volumes flow through, candidate sub-category additions should be tracked. Out of scope for Phase 1.
Open · O-4 Should the override response surface the normalised merchant key? Yes by recommendation (so users see what they are committing RememberForMerchant to). Confirm with product before T7 lands.
