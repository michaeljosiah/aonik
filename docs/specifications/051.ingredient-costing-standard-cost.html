Spec 051 Status: Draft Size: Medium Priority: P3 Domain: Commerce / Production / Costing

Ingredient costing & product standard-cost rollup

Gives each Ingredient an effective-dated unit cost and rolls a Recipe — the bill of materials the keystone spec Spec 050 defined — up into a product's standard cost (food cost / COGS). This is the second spec of the maker-operations family (050–057): it turns "what a product is made of" into "what it costs to make", enabling the operations manager's "update ingredient costs when suppliers reprice" and "profit report" moments. Everything lives in Aonik.Commerce and references only SharedKernel + Aonik.Ordering — never Aonik.Finance.

1. Summary

Spec 050 gave AONIK the ability to describe how a finished product is made — an Ingredient master and a Recipe (bill of materials) that says which ingredients, and how much of each, one yield-unit of a ProductVariant consumes. What it deliberately left out is cost: a recipe with quantities but no prices cannot answer "what does a portion of jollof cost to make?" or "am I hitting my target margin?". This spec adds that missing dimension.

It introduces one new anemic entity and two services in Aonik.Commerce:

  • IngredientCost — an effective-dated, audited unit cost for an ingredient (per its BaseUnit), modelled exactly like the retail ProductPrice from Spec 042. Setting a new cost closes the prior open row and inserts a new one (with a future effectiveFrom kept as a scheduled row that does not price today), so "a supplier repriced" is a first-class, historied action — not an in-place overwrite.
  • IProductCostingService.RollupStandardCostAsync — values a variant's active recipe at current ingredient cost by reusing Spec 050's IRecipeService.ExplodeAsync: the standard unit cost is Σ(RecipeComponent.Quantity × active IngredientCost.UnitCost), returned as a per-component breakdown plus a total cost per portion (per yield-unit).
Success signals An operator (or the commerce-agent) can set an ingredient's cost, reprice it later and see the prior cost preserved in history, and read back a product variant's standard cost as a line-by-line breakdown ("jollof portion = 0.25 kg rice @ £1.20 + 0.12 kg tomato @ £0.90 + … = £X/portion"). A component whose ingredient has no active cost is flagged, never silently zeroed. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering; dotnet test Aonik.sln stays green with new unit tests covering repricing history, rollup arithmetic, and the no-cost / no-recipe diagnostics.

2. Context & motivation

Two artefacts in the food-production operations manager's day-in-the-life (see Spec 050 §2) are pure cost projections and cannot exist without this spec:

  • "Update ingredient costs when suppliers reprice." Rice went from £1.10/kg to £1.20/kg — the operator records the new cost, and every product that uses rice reflects it going forward, while last month's cost stays on the record for historical reporting.
  • "Review a profit report (actual food cost vs. target margin)." The margin report (Spec 057) is revenue − COGS; COGS is exactly the standard-cost rollup this spec computes, multiplied by quantity sold.

Both reduce to one primitive: a recipe valued at ingredient cost. Spec 050 already owns the reusable explosion that turns a recipe into per-ingredient quantities; this spec decorates that explosion's output with cost. That is the deliberate seam — costing does not re-implement BOM traversal, it values it. Keeping the two specs separate keeps each small and independently shippable, and means a future change to how recipes explode (e.g. multi-level BOMs) automatically flows into costing.

Scope discipline mirrors the family: build the thin costing slice this persona needs — a single standard (latest-effective) cost per ingredient and a straight recipe rollup — not a full cost-accounting engine with moving-average valuation layers, labour and overhead absorption, or multi-currency FX. Those are noted as open extensions, not built.

4. Scope (in / out)

In scope

  • IngredientCost entity + IIngredientCostService (SetCost, GetCurrentCost, ListHistory) + admin endpoints.
  • Effective-dated write semantics: SetCost closes the prior open row (EffectiveTo set, IsActive=false) and inserts a new open row — repricing is an audited, historied action. Current-cost resolution is date-aware (a future effectiveFrom is a scheduled row that does not price today), and the single open/current row is enforced by a DB-level filtered unique index.
  • IProductCostingService.RollupStandardCostAsync(productVariantId, currency, atUtc): explode the variant's active recipe (Spec 050) and value each component at its active IngredientCost.UnitCost; return a per-component breakdown and a total unit cost (cost per portion / per yield-unit).
  • Diagnostics: a variant with no active recipe returns a "no recipe" diagnostic; a component whose ingredient has no active cost is flagged on its line — never a silent zero.
  • New Commerce DbSet on CommerceDbContext + AonikDbContext; one tool-generated migration (CommerceIngredientCosts, one table AnkIngredientCosts).
  • Commerce-agent read tool for product cost + a medium-gated write tool for updating ingredient cost.

Out of scope

  • Actual / moving-average cost. v1 uses a single standard (latest-effective) cost. Goods receipt writing an actual received cost is Spec 054 — which simply calls SetCost here; the valuation method stays standard.
  • Multi-currency ingredient cost + FX conversion. Each rollup call is single-currency (§9); an ingredient cost carries the currency it was recorded in, and a mismatch is a diagnostic, not an on-the-fly FX conversion. Noted under Open.
  • Labour, overhead, packaging in product cost. v1 is food cost (ingredient cost) only. Absorbed labour/overhead is under Open, not built.
  • The margin / profit report itself — Spec 057 consumes this rollup; it is not built here.
  • Cost snapshot at sale time for historical-margin stability — noted under Open and linked to Spec 057; not built here.

5. Constraints & guardrails

  • No reference to Finance. Aonik.Commerce still references only SharedKernel + Aonik.Ordering. Cost is a Commerce concern; it never posts to the ledger and adds no cross-module coupling (ADR-005).
  • Anemic entity. IngredientCost is a { get; set; } data container implementing ITenantScoped + AuditableEntity (ADR-002); all logic — including the close-prior/open-new repricing transition — lives in IIngredientCostService, returning DTOs.
  • Single migration stream. EF-CLI-generated against AonikDbContext; Ank-prefixed table; CommerceDbContext is runtime scoping with no migrations; agents never hand-author migrations.
  • History is append-only in effect. Repricing never mutates a past cost row's value; it closes it and inserts a new one, so any point-in-time cost is recoverable. This is the same discipline as ProductPrice.
  • Never silently zero a cost. A missing ingredient cost or a missing recipe is a surfaced diagnostic on the rollup result, so callers (Spec 057) never report a falsely-cheap product.
  • Agents propose; systems execute. Cost reads are direct agent tools; commerce_update_ingredient_cost is medium (in-session confirmation, args-hash-bound); every AI action records an AiRun.
  • One currency per rollup call. Costing is not an FX engine; a rollup that would mix currencies flags the offending line rather than converting (§9).

7. Domain model

One new anemic entity, ITenantScoped, inheriting AuditableEntity. It mirrors the Spec 042 ProductPrice shape one-for-one — the only differences are it attaches to an Ingredient (not a ProductVariant) and its UnitCost is denominated per the ingredient's BaseUnit. 

class IngredientCost { Guid Id, TenantId, IngredientId;
                       string   Currency;      // ISO-4217, e.g. "GBP"
                       decimal  UnitCost;      // cost per the ingredient's BaseUnit (e.g. £/kg)
                       DateTime EffectiveFrom;  // when this cost takes effect (required — SetCost defaults it to now)
                       DateTime? EffectiveTo;   // when superseded (null = still the open/current cost)
                       bool     IsActive; }     // convenience/soft-delete flag — NOT the "current" selector

IngredientCost.IngredientId is an intra-module reference to the Spec 050 Ingredient; the ingredient's BaseUnit is the unit UnitCost is quoted in (so a kg-based ingredient has a £/kg cost). The EffectiveFrom/EffectiveTo pair is what makes a supplier reprice a historied event rather than a destructive edit — identical to how ProductPrice models a retail price change, and it is the effective dates (not IsActive) that resolve which row is current on any given date (§8). IsActive is a convenience/soft-delete flag only. The rollup services (§8) hold no persisted state of their own; a product's standard cost is always computed from the current recipe and current costs, never stored.

8. Effective-dated cost (mirrors ProductPrice)

IngredientCost reuses, verbatim, the effective-dated pattern Spec 042 already ships for retail prices. IIngredientCostService owns the transition:

IIngredientCostService.SetCostAsync(SetIngredientCostCommand(ingredientId, currency, unitCost, effectiveFrom?)) → let from = effectiveFrom ?? now → find the open (tail) row for (ingredientId, currency) // EffectiveTo IS NULL → if none: insert a new open row (EffectiveFrom = from, EffectiveTo = null, IsActive = true) → if from >= tail.EffectiveFrom: set tail.EffectiveTo = from, IsActive = false // close prior and insert a new open row (EffectiveFrom = from, EffectiveTo = null, IsActive = true) // open new → if from < tail.EffectiveFrom (a scheduled row starts after 'from'): SPLIT the containing window — reject if no window contains 'from', or if the containing window has already fully elapsed (a 'from' earlier than the start of the window effective at now — that history already priced the past) set containing.EffectiveTo = from, IsActive = false, and insert the new row CLOSED at the successor's EffectiveFrom (the earliest row starting after 'from' — at minimum the tail), so the scheduled row is preserved and stays the single open row → (all writes in one transaction; the audit trail records who repriced and when) → a future 'from' is stored as a SCHEDULED row: it does not become "current" until its date arrives (the prior row is closed AT the future date, so date-aware reads keep returning it until then) IIngredientCostService.GetCurrentCostAsync(ingredientId, currency, atUtc? = now) → the row where EffectiveFrom <= atUtc AND (EffectiveTo IS NULL OR atUtc < EffectiveTo), ordered by EffectiveFrom DESC // DATE-AWARE — IsActive is NOT the selector → or null ("no active cost") if none is effective at atUtc IIngredientCostService.ListHistoryAsync(ingredientId, currency?) → all rows newest-first: the full reprice timeline ("£1.10 → £1.20 on 2026-06-01")

This makes "a supplier repriced" a first-class, audited action: the old cost is never overwritten, so a report can ask "what did rice cost on 1 May?" and get the row that was effective then. Current-cost resolution is date-aware — GetCurrentCostAsync selects the row whose [EffectiveFrom, EffectiveTo) window contains atUtc (ordered by EffectiveFrom descending), not the row where IsActive=true. A cost set with a future effectiveFrom is therefore stored as a scheduled row: it is persisted immediately but does not supersede the current cost (and does not price today's rollups) until its date arrives. Scheduling a future cost does not lock out corrections: an effectiveFrom landing before the scheduled row's start splits the window containing it — the containing row is closed at effectiveFrom and the new row is inserted already closed at the successor's EffectiveFrom, so the scheduled row is preserved and stays the single open row. Only fully-elapsed windows are immutable: an effectiveFrom earlier than the start of the window effective at "now" (history that already priced the past) is rejected as a history rewrite; correcting the currently-effective window or any future window is allowed. IsActive is a convenience/soft-delete flag, kept in sync for cheap "the newest open row" reads, but the effective dates are the source of truth for "current". Spec 054 (goods receipt) reuses this exact entry point — when a PO line records an actual received unit cost, it simply calls SetCostAsync, producing a new effective-dated row with no special-casing.

Note "At most one open/current row per (TenantId, IngredientId, Currency)" (the row with EffectiveTo IS NULL) is enforced at the database by a filtered unique index — (TenantId, IngredientId, Currency) filtered to EffectiveTo IS NULL (§12) — not by the service alone, so two concurrent reprices cannot both insert a current row. The service still closes the prior row in the same transaction; the DB index is the backstop. v1 expects a single currency per ingredient in practice; the Currency discriminator on the uniqueness key leaves room for a future multi-currency cost without a schema change (see Open).

9. Standard-cost rollup

The one piece of logic this spec owns beyond the effective-dated CRUD is the rollup — the reusable primitive the margin report (Spec 057) calls. It reuses Spec 050's explosion and only adds valuation:

IProductCostingService.RollupStandardCostAsync(productVariantId, currency, atUtc) → explode ONE yield-unit of the variant's active recipe via IRecipeService.ExplodeAsync(productVariantId, portions: 1) // REUSE Spec 050 → if no active recipe → return { HasActiveRecipe = false, CostComplete = false, UnitCost = null } → for each exploded line { IngredientId, IngredientName, BaseUnit, RequiredQuantity }: cost = GetCurrentCostAsync(IngredientId, currency, atUtc) // DATE-AWARE; ignores scheduled rows if no cost effective at atUtc → flag the line { HasCost = false }, LineCost = null // NOT zero else → LineCost = RequiredQuantity × cost.UnitCost → CostComplete = every line HasCost → UnitCost = CostComplete ? Σ LineCost : null // withheld when incomplete — never partial/zero → return StandardCostDto { ProductVariantId, Currency, AsOfUtc, // AsOfUtc = the resolved atUtc (?? now) HasActiveRecipe, CostComplete, Lines: [ ComponentCostDto { IngredientId, IngredientName, BaseUnit, QuantityPerYieldUnit, UnitCost?, LineCost?, HasCost } ], UnitCost // cost per portion / per yield-unit }

The result is a per-component breakdown plus a total unit cost. Because explosion is done for one yield-unit, TotalUnitCost is directly the cost per portion — the number Spec 057 multiplies by quantity sold to get COGS. Two diagnostics are surfaced, never swallowed:

  • No active recipe ⇒ HasActiveRecipe = false and UnitCost = null; the caller shows "no recipe defined for this product" instead of a £0 cost.
  • A component ingredient with no active cost ⇒ that line's HasCost = false and LineCost = null, and the result's CostComplete = false with UnitCost = null. The total is withheld rather than presented as a partial number, while the priced lines keep their per-line LineCost — so a report never presents an artificially-cheap product as complete.

The rollup is pure and read-only: it stores nothing and touches no stock. atUtc is threaded straight into the date-aware GetCurrentCostAsync, so the rollup already values the recipe at the costs effective on atUtc (defaulting to now) and a future-dated (scheduled) cost never leaks into today's total — a point-in-time rollup at a past date is the same call with a different atUtc (see Open on point-in-time and sale-time snapshots).

10. Currency handling

A rollup is computed in exactly one currency, passed by the caller. Costing is not an FX engine (that lives in Finance, which Commerce does not reference), so:

  • Each component is valued at its active IngredientCost in the requested currency.
  • If an ingredient has an active cost only in a different currency, the line is flagged HasCost = false (a "no cost in {currency}" diagnostic) — the rollup does not convert on the fly. This is a conscious v1 boundary: one currency in, one currency out, no silent cross-rate.
  • The uniqueness key (IngredientId, Currency) means a tenant could record the same ingredient's cost in two currencies, but v1 tooling and the day-in-the-life assume a single operating currency per tenant. Multi-currency cost with FX conversion is an explicit Open decision, deferred to keep this spec ≤ ~8 points.
Note For a UK→NG maker, the practical shape is: record costs in the tenant's operating currency (e.g. GBP), roll up in that currency, and let any customer-facing FX happen at the selling layer, not the costing layer. Costing answers "what did this cost me, in my books' currency?".

11. Agent & tools

The existing commerce-agent gains costing tools, classified by CommerceToolApprovalManifest and wrapped by the Spec 032 gate — no change to the gate:

ToolTierEffect

This is the agentic surface for the two moments: commerce_update_ingredient_cost is "update ingredient costs when suppliers reprice", and commerce_get_product_cost feeds the profit-report conversation (with the full report itself arriving in Spec 057). There is no high-tier tool here — costing never moves money, so nothing marshals into a Finance Proposal.

12. CommerceDbContext & migrations

One new Ank-prefixed table — AnkIngredientCosts — is created by one EF-CLI migration against AonikDbContext. The entity is added to both CommerceDbContext (runtime scoping) and AonikDbContext (canonical stream); it is tenant-scoped (not global). The configuration lives in Persistence/Configurations/Sourcing as an IEntityTypeConfiguration<IngredientCost>. It declares a filtered unique index on (TenantId, IngredientId, Currency) filtered to EffectiveTo IS NULL (HasFilter("[EffectiveTo] IS NULL")), so the database — not the service alone — guarantees at most one open/current cost per ingredient/currency and two concurrent reprices cannot both create a current row. A second (non-unique) index on (TenantId, IngredientId, Currency, EffectiveFrom) keeps the date-aware "current cost at atUtc" lookup (hit on every rollup component) cheap, and UnitCost precision is decimal(19,4) to match money columns elsewhere. The filtered unique index is still authored in the config and emitted by the one tool-generated migration against AonikDbContext — never hand-written. No additional migration is needed for the rollup services — they are pure compute over existing tables. 

dotnet ef migrations add CommerceIngredientCosts --project src/Aonik.Infrastructure --startup-project src/Aonik.Api

13. Phased rollout

Phase 1 — Effective-dated ingredient cost

Give each ingredient a historied unit cost; make repricing a first-class action.
  • IngredientCost entity + IngredientCostConfiguration + DbSets on CommerceDbContext and AonikDbContext; the CommerceIngredientCosts migration (creates AnkIngredientCosts); IIngredientCostService (SetCost close-prior/open-new, GetCurrentCost date-aware, ListHistory) returning DTOs; the filtered unique index (EffectiveTo IS NULL) in the config; admin endpoints; unit tests for the repricing transition, the single open/current-row invariant, and a future-dated (scheduled) cost not superseding the current one.

Phase 2 — Standard-cost rollup

Value a recipe at cost; return a per-portion breakdown.
  • IProductCostingService.RollupStandardCostAsync(variantId, currency, atUtc) reusing IRecipeService.ExplodeAsync; per-component breakdown + total unit cost; the no-recipe and missing-cost diagnostics; admin read endpoint; unit tests for rollup arithmetic, the yield-unit basis, and both diagnostics (never a silent zero).

Phase 3 — Commerce-agent tools

The agentic surface.
  • commerce_get_product_cost (read) + medium-gated commerce_update_ingredient_cost added to CommerceAgentTools and classified in CommerceToolApprovalManifest; routed through IToolApprovalGate.GateAll (fails closed); each records an AiRun.

16. Verification

  • dotnet build Aonik.sln green; architecture test proves Aonik.Commerce has no Aonik.Finance reference.
  • Repricing: SetCost(rice, GBP, 1.10) then SetCost(rice, GBP, 1.20) ⇒ GetCurrentCost returns 1.20, and ListHistory shows two rows (the 1.10 row closed with an EffectiveTo), with exactly one open (EffectiveTo IS NULL) row.

18. Decisions baked in

  • Ingredient cost is effective-dated and audited, mirroring ProductPrice: setting a new cost closes the prior open row and opens a new one, so repricing is a first-class historied action.
  • "Current" is resolved by effective dates, date-aware, not by IsActive — GetCurrentCost picks the row whose [EffectiveFrom, EffectiveTo) window contains atUtc; a future-dated cost is a scheduled row that does not price today's rollups. The single open/current row is guaranteed at the database by a filtered unique index (EffectiveTo IS NULL), so concurrent reprices cannot create two current rows.
  • Standard cost is computed, not stored — a product's cost is always Σ(recipe component × current ingredient cost), freshly rolled up from the current recipe and costs.
  • Rollup reuses Spec 050 explosion and only adds valuation; it never re-traverses the BOM, so multi-level BOMs (a future Spec 050 extension) flow through automatically.
  • Never a silent zero — a missing recipe or a missing ingredient cost is a surfaced diagnostic on the result, so downstream margin reporting cannot present a falsely-cheap product.
  • One currency per rollup call; costing performs no FX conversion and holds no Finance reference.
  • v1 is standard (latest-effective) cost, food-cost only — no moving-average, no labour/overhead; extensions are Open.
  • Grow in place in Aonik.Commerce (no new module); migrations stay with AonikDbContext.

19. Open design decisions

Open Standard vs. moving-average / actual cost. v1 values products at the latest-effective standard cost. A future option is a moving-average (or FIFO) valuation that blends actual received costs from goods receipts (Spec 054) into the cost used for the rollup. Deferred; Spec 054 still records the actual received unit cost via SetCost, so the data to compute a moving average later already accrues.
Open Multi-currency ingredient cost + FX conversion. Allowing an ingredient to hold costs in several currencies and having the rollup convert to the requested currency via an FX rate. v1 is single currency per rollup call and flags a currency mismatch rather than converting — the (IngredientId, Currency) key already leaves room, but the conversion (and where the rate comes from without referencing Finance) is out of scope.
Open Labour & overhead in product cost. A per-recipe or per-portion labour/overhead absorption on top of food cost, to give a fully-loaded cost. v1 is food cost (ingredient cost) only; a loaded-cost model would decorate the rollup result with additional cost components.
Open Cost snapshot at sale time for historical-margin stability. Capturing the standard cost onto an order line at the moment of sale, so a historical margin report is stable even after ingredients later reprice. This links directly to Spec 057: v1 Spec 057 can either re-roll cost at report time (using the effective-dated history and the atUtc parameter this rollup already threads) or read a captured snapshot. The snapshot entity is deferred to Spec 057's design.
