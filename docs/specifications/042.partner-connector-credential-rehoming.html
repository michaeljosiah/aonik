Spec 042 Status: Draft Size: Large Priority: P2 (post-launch) Domain: Finance / Partners / Platform

Partner connector credentials & configuration re-homing

Implements ADR-010. Today a connector's credentials live in a provider-singleton settings silo (Finance.Partners.Flutterwave.*) read by the connector config providers, while the Partner Network module carries a parallel, unconsumed PartnerConnector.CredentialsRef. This spec re-homes connector configuration onto the partner's connector instance, backed by a central write-only credential store addressed by CredentialsRef — removing the one-account-per-provider assumption, unifying the two config surfaces, and giving the Spec 040 v3 bills connector an operator-facing config path it does not have today. The change is designed to land additively after launch: the existing keys stay as a read fallback.

1. Summary

Spec 031 landed a partner-agnostic connector abstraction; Spec 037 (v4 OAuth payout) and Spec 040 (v3 secret-key bills) added the first real connectors. Configuring them revealed that connector credentials are modelled as a tenant-global singleton per provider, which does not scale to multiple accounts, per-partner isolation, or the coming roster (eTranzact, Wise, iPay). ADR-010 decides that credentials are owned by the partner's connector instance, with secret bytes in a central write-only store addressed by CredentialsRef. This spec is the implementation plan.

Success signals An operator opens a Partner (e.g. Flutterwave), adds a flutterwave-payout-v4 connector and a flutterwave-bills-v3 connector, binds each to a named credential bundle, toggles Enabled, and saves — with no global Finance.Partners.Flutterwave.* key involved. ResolvePayoutConnector and ResolveBillPaymentConnector resolve the right connector for that partner from its bound bundle; a second Flutterwave account is a second partner/connector with its own bundle; the biller-import wizard lists the v3 connector as a source; and a read of any settings snapshot returns hasXxx badges, never secret values. The pre-existing Finance.Partners.Flutterwave.* keys still resolve as a fallback for any connector not yet migrated.

2. Problem & current state

Confirmed by reading the tree. Two representations of "connector config" exist and do not agree:

AreaState todaySource
Provider-singleton settings FlutterwaveConfigProvider (v4) and FlutterwaveBillsConfigProvider (v3) read ISettingProvider by fixed keys, with IOptions/appsettings fallback. Services/Partners/Connectors/Flutterwave/**/Flutterwave*ConfigProvider.cs
Setting keys Finance.Partners.Flutterwave.{Enabled,BaseUrl,IdpTokenUrl,ClientId,ClientSecret,EncryptionKey,DefaultTransferPurpose}, Finance.Partners.Webhooks.Flutterwave.SigningSecret, Finance.Partners.Flutterwave.Bills.{Enabled,BaseUrl,SecretKey} — one set per provider, per tenant. Gateway UI v4 set editable at Settings → Payment Gateways → Flutterwave (write-only, "Configured" badges, secret-source indicator). gap The v3 bills set has no UI. AdminUi/.../settings/payment-gateways
Partner connector entity Partner → Connectivity tab adds PartnerConnector { ConnectorType, Status, CredentialsRef, ConfigJson } with the note "CredentialsRef points to gateway settings; never paste secrets here." Partner Network module (/catalog/partners/{id})
Resolution IPartnerConnectorResolver resolves by provider code against the singleton settings. PartnerConnector.CredentialsRef is not consumed by the config providers. Services/Partners/Connectors/PartnerConnectorResolver.cs
Root cause Credentials are an attribute of an account, and accounts are held with partners. The provider-singleton model collapses "account" into "provider", so it cannot represent two accounts of one provider, cannot isolate one partner's secret from another's, and forces every new connector to invent yet another global key family. The PartnerConnector.CredentialsRef field is the seam ADR-010 builds on — it is the right shape, simply not yet wired to resolution.

3. Scope (in / out)

3.1 In scope

  • New A credential bundle abstraction: a named, encrypted, write-only secret set in the central store, addressed by CredentialsRef. Bundles are typed by connector (the connector declares the field schema it needs).
  • Edit FlutterwaveConfigProvider + FlutterwaveBillsConfigProvider resolve their values from the bound bundle (via CredentialsRef), falling back to the legacy Finance.Partners.Flutterwave.* keys when no bundle is bound (transition).
  • Edit IPartnerConnectorResolver resolution becomes partner-aware: (tenant, partner, providerType) → connector instance → bundle. The capability-query fallback and the "Simulated" default are preserved (per Spec 037 rev 3).
  • New Admin UI: a credential editor on the partner Connectivity tab (write-only fields keyed to the connector's declared schema), and the reframing of Settings → Payment Gateways into a credential-bundle manager (list / create / rotate bundles) — or its retirement once entry moves to the partner.
  • Extend Model the integration providers (Flutterwave first) as Partners; seed the Flutterwave partner with its v4 payout + v3 bills connector instances.
  • Edit A back-compat seed/migration that lifts existing provider-singleton values into a default bundle bound to the Flutterwave partner's connectors. Any schema change is tool-generated (CLAUDE.md migration discipline).

3.2 Out of scope

  • The launch. Phase 0 ships on the existing keys; this spec is Phase 1, post-launch (ADR-010 Phasing). Nothing here blocks the Payabo UK→NG wedge.
  • Azure Key Vault. The central store stays the encrypted settings store; a vault move is a separate platform change (same stance as ADR-007).
  • Routing. Destination-aware routing (Spec 037 G18/O11) is a separate concern; this spec only changes where credentials live, not how a destination selects a connector.
  • New connector code. No new provider integration is written here; this is a re-homing of configuration for the connectors that exist.

4. Target model

A Partner owns one or more Connector instances; each connector binds a provider type (code) to a credential bundle (secret bytes) plus non-secret ConfigJson. The provider type is shipped, not configured; the operator binds credentials and toggles Enabled.

Partner (Flutterwave) central credential store (encrypted, write-only) ├─ Connector: flutterwave-payout-v4 ──ref──▶ bundle "fw-uk-oauth" { clientId, clientSecret, encKey, … } │ ConfigJson { baseUrl, idpTokenUrl, defaultTransferPurpose } │ Enabled = true └─ Connector: flutterwave-bills-v3 ──ref──▶ bundle "fw-ng-v3" { secretKey (FLWSECK-…) } ConfigJson { baseUrl, country=NG } Enabled = true resolve(tenant, partner=Flutterwave, type=payout-v4) ─▶ connector ─▶ bundle ─▶ live client

A second Flutterwave account is simply a second partner (or a second connector instance) bound to a different bundle. No global key is touched.

5. Credential store & CredentialsRef

  • Write-only. Bundle fields are set blank-to-keep (the convention already on the gateway page); no read API returns a secret value — only hasXxx / "Configured" and a secret-source indicator (bundle / legacy-key / missing).
  • Encrypted at rest via the existing settings-store protection (IDataProtection where a value is persisted), same as today.
  • CredentialsRef is a stable opaque handle to a bundle; rotating a bundle's secret leaves the ref unchanged so bound connectors pick up the new value on the next call (runtime pickup, no redeploy — preserves Spec 038's acceptance).
  • Per-connector schema. Each connector type declares the fields its bundle needs (v4: clientId/clientSecret/encKey/signingSecret; v3: secretKey), so the UI renders the right form and validation.

6. Connector resolution

IPartnerConnectorResolver gains partner-aware resolution. Order of precedence, preserving Spec 037 rev 3 guarantees:

  1. Explicit (partner, providerType) → the partner's enabled connector instance → its bound bundle.
  2. Legacy fallback: if the connector has no bound bundle, read the provider-singleton keys (transition only).
  3. Capability query → first enabled connector for the requested service category.
  4. "Simulated" default (must remain registered — the remittance fallback resolves it by code).

7. Config provider refactor

FlutterwaveConfigProvider and FlutterwaveBillsConfigProvider currently build their options from fixed keys. They are changed to accept a CredentialsRef (and connector ConfigJson) and resolve the bundle, with the existing key read retained as the fallback branch. IsConfigured() semantics are unchanged (Enabled + transport + secret present) but now evaluate against the resolved bundle. No transport, DTO, or HTTP behaviour changes — only the source of the values.

8. Admin UI

  • New Connectivity tab credential editor. For each connector instance, a write-only form keyed to the connector's declared schema, a "Configured"/"Not set" badge per field, a secret-source indicator, a Test connection action, and an Enabled toggle. This is where the gap v3 bills config finally gets a home.
  • Edit Settings → Payment Gateways is reframed as a credential-bundle manager (list / create / rotate bundles, show which connectors bind each), or retired in favour of per-connector entry on the partner. The "never paste secrets here / CredentialsRef points to gateway settings" note is removed once the two surfaces unify.
  • No new client data-fetching pattern; reuse the existing settings/service conventions.

9. Migration & back-compat

  • Seed the Flutterwave partner (or rename the existing demo partner) with two connector instances: flutterwave-payout-v4 and flutterwave-bills-v3.
  • Lift existing values into a default bundle. A one-time, idempotent step reads the current Finance.Partners.Flutterwave.* values and writes them into a default bundle bound to those connectors. Existing secrets are re-encrypted into the bundle, not copied in plaintext.
  • Fallback during transition. Until a connector has a bound bundle, the legacy keys resolve (§6 step 2), so a partially-migrated environment keeps working.
  • Schema. If a new column/table is required (e.g. a CredentialBundle table or a PartnerConnector.CredentialsRef FK), it is tool-generated against AonikDbContext only, reviewed to contain only the expected changes (CLAUDE.md).

10. Security

  • Secrets remain write-only and never returned by any read endpoint; snapshots expose only hasXxx + secret-source.
  • Authz: only admins may create/rotate bundles or edit connector credentials; non-admins get 401/403.
  • Every bundle write / connector credential change emits an audit event recording the changed field names and the bound connector — never secret values (extends Spec 038's audit guarantee).
  • Per-partner isolation: reading or rotating one partner's bundle has no effect on another's.

11. Tasks

  1. Introduce the credential-bundle abstraction (entity or settings-store convention) + CredentialsRef resolution; tool-generated migration if a table is added.
  2. Refactor FlutterwaveConfigProvider + FlutterwaveBillsConfigProvider to resolve by CredentialsRef with legacy-key fallback.
  3. Make IPartnerConnectorResolver partner-aware (§6), preserving the capability + Simulated fallbacks.
  4. Admin UI: Connectivity-tab credential editor (per-connector schema, write-only, Test connection) + reframe/retire the Payment Gateways page.
  5. Seed the Flutterwave partner + its two connector instances; idempotent lift of existing keys into a default bundle.
  6. Audit events for bundle/credential writes (names only).
  7. Tests: resolution precedence (bundle → legacy → capability → Simulated), write-only snapshot, two-account isolation, v3 bills now resolvable via the partner, fallback path for an unmigrated connector.

12. Acceptance criteria

  • Partner-owned config. An admin configures Flutterwave entirely from the partner's Connectivity tab (both connectors), with no global Finance.Partners.Flutterwave.* key touched; resolution uses the bound bundles.
  • Two accounts. A second Flutterwave partner/connector with a distinct bundle resolves independently; rotating one leaves the other unchanged.
  • v3 bills has a home. The bills connector is configurable from the UI and appears in the biller-import wizard's sources once enabled (closes Spec 040's gap).
  • Secrets never leave the server. No read API returns a secret value; a service + endpoint test asserts hasXxx-only.
  • Back-compat. With no bundle bound, the legacy keys still resolve; behaviour is identical to pre-migration (no regression for a launched environment).
  • Runtime pickup. Rotating a bundle is honoured on the next connector call without redeploy; webhooks verify against the bundle's signing secret.
  • Build & migration. dotnet build Aonik.sln + npm run build green; any migration is tool-generated and applies cleanly.

13. Open decisions

  • O1 — Flutterwave as Partner vs rail-under-partner. ADR-010 recommends modelling integration providers as Partners. The existing "Gold Coast Bill Hub" seed (biller-hub partner with Flutterwave as a sub-connector) is a different abstraction; both may coexist (rail partners + biller-hub partners). Must be settled before onboarding the next connector.
  • O2 — Bundle as entity vs settings-store convention. A first-class CredentialBundle table gives clean FKs and audit; a settings-store key convention avoids a migration. Lean entity for clarity; decide at task 1.
  • O3 — Reframe vs retire the Payment Gateways page. Keep it as a global bundle manager, or move all entry to the partner and retire it. Lean reframe (a bundle manager is useful for cross-partner rotation/audit).
