Spec 042 Status: Draft (Rev 2) Size: Large Priority: P2 (post-launch) Domain: Finance / Partners / Platform

Partner connector credentials & configuration re-homing

Implements ADR-010. Today a connector's credentials live in a provider-singleton settings silo (Finance.Partners.Flutterwave.*) read by the connector config providers, while the persisted Connector entity already carries an unconsumed CredentialsRef. This spec re-homes connector configuration onto a persisted, partner-owned connector instance, bound at runtime to a first-class CredentialBundle via CredentialsRef, and propagates ConnectorId through every downstream money record so two accounts of one provider never alias. The change lands additively after launch; the existing keys remain a read fallback for one explicitly-migrated default connector only.

Rev 2 — implementation review incorporated (2026-06-09) This revision answers an eight-point readiness review. The material changes:
  • Connector terminology is now precise (§4): provider code vs connector kind vs port/capability vs connector instance are separate concepts, formalised as a connector registry.
  • Runtime connectors become context-bound (§7): the config providers take a CredentialsRef; DI moves from one-per-port singletons to a factory that returns a connector bound to a specific Connector row.
  • ConnectorId propagates downstream (§9): beneficiary, payout, transmission, bill-payment, and webhook records carry the connector identity, not just ProviderCode.
  • CredentialBundle is a first-class entity (§6) — the open decision is closed. The settings store only encrypts statically-defined keys, so bundles use explicit IDataProtection.
  • Fallback fails closed (§7.2), bundles are tenant-scoped (§6), ConfigJson is schema-validated (§10), and webhook secret rotation gets a dual-validation window (§11).

1. Summary

Spec 031 landed a partner-agnostic connector abstraction; Spec 037 (v4 OAuth payout) and Spec 040 (v3 secret-key bills) added the first real connectors. Their credentials are modelled as a tenant-global singleton per provider, which cannot express multiple accounts, per-partner isolation, or the coming roster (eTranzact, Wise, iPay). ADR-010 decides that credentials are owned by the partner's persisted connector instance, bound to a first-class write-only CredentialBundle addressed by CredentialsRef. This spec is the implementation plan, tightened to answer the readiness review.

Success signals An operator opens a Partner (Flutterwave), adds a flutterwave-payout-v4 connector and a flutterwave-bills-v3 connector, binds each to a named bundle, toggles Enabled, and saves — no global Finance.Partners.Flutterwave.* key involved. A second Flutterwave account is a second connector row with its own bundle and a distinct ConnectorId; beneficiary registration, payouts, transmissions, bill payments, and webhook correlation all carry that ConnectorId, so the two accounts never alias. A connector with no bound bundle fails the call rather than borrowing the global account; rotating a bundle is picked up on the next call; and no read API ever returns a secret value. The legacy keys keep working for the one migrated default connector.

2. Problem & current state

Confirmed against the tree. Three facts shape the design:

  • The persisted connector row already exists. Entities/Partners/Connector.cs is tenant-scoped (AuditableEntity, ITenantScoped) and already carries Id, PartnerId, ConnectorType, CredentialsRef, ConfigJson, Status. The Connectivity-tab "Add connector" form writes it today. The gap is that nothing at runtime consumes it — resolution and the config providers read global keys instead.
  • Config providers are not context-aware. FlutterwaveConfigProvider.GetAsync(ct) and FlutterwaveBillsConfigProvider.GetAsync(ct) take only a CancellationToken and read fixed PartnerGatewaySettingNames.* keys. DI in FinanceModule registers one connector implementation per port. There is no way to ask for "the connector for this account."
  • Runtime connectors expose only ProviderCode. IPartnerConnector has ProviderCode + Capabilities and nothing else; BillerImportService and the resolver key on ProviderCode == "Flutterwave". Downstream records (RemittanceOrderService, PayoutBeneficiaryService) store/route by provider code, which becomes ambiguous the moment a tenant has two Flutterwave accounts.
Encryption gotcha (closes the bundle open-decision) Bundles cannot be a settings-store key convention. SettingService only protects a value when its static SettingDefinition.IsEncrypted is true (SettingService.cs:258): definition?.IsEncrypted == true ? _protector.Protect(...) : normalized. A dynamic, per-bundle key has no definition, so its secret would persist in plaintext. Bundles therefore must be a first-class entity that protects its own fields with IDataProtection (§6).

3. Scope (in / out)

3.1 In scope

  • New CredentialBundle entity (§6) + a connector registry (§4).
  • New An IPartnerConnectorFactory that materialises a runtime connector bound to a persisted Connector row and its bundle (§7).
  • Edit FlutterwaveConfigProvider + FlutterwaveBillsConfigProvider to resolve from a passed CredentialsRef + ConfigJson, with a fail-closed legacy fallback (§7–8).
  • Edit IPartnerConnectorResolver to resolve a connector row for (tenant, partner, port), not a DI singleton by provider code (§7).
  • Edit Persist ConnectorId (and PartnerId) on ExternalPayoutAccount, Payout, Transmission, PartnerBillPayment, and webhook correlation (§9). Tool-generated migration.
  • New ConfigJson schema validation per connector kind (§10); webhook secret versioning (§11).
  • New Admin UI: per-connector credential editor on the Connectivity tab; reframe Payment Gateways into a bundle manager (§12).
  • Edit Idempotent migration of existing Flutterwave keys into one default bundle + default connector (§13).

3.2 Out of scope

  • The launch. Phase 0 ships on existing keys; this is Phase 1 (ADR-010). Nothing here blocks the Payabo UK→NG wedge.
  • Azure Key Vault (deferred, ADR-007 stance); destination-aware routing (Spec 037 G18/O11); new connector code — this is a config re-homing only.

4. Terminology & connector registry review #1

Four concepts the current code conflates under "Flutterwave"; the spec keeps them distinct:

ConceptMeaningExampleLives in
Provider codeThe vendor brand. Coarse; one per vendor.FlutterwaveIPartnerConnector.ProviderCode (unchanged)
Connector kindA specific integration shipped in code: transport + auth scheme + port. Many per provider.flutterwave-payout-v4, flutterwave-bills-v3New registry entry

A connector registry (static, code-owned) declares each kind: 

ConnectorKind        ProviderCode   Port         CredentialSchema            ConfigSchema
flutterwave-payout-v4  Flutterwave   Payout       {clientId, clientSecret,    {environment, defaultTransferPurpose}
                                                   encryptionKey, signingSecret}
flutterwave-bills-v3   Flutterwave   BillPayment  {secretKey}                 {environment, country}

The registry is the single source of truth for "what credential fields does this kind need" (drives the UI form and bundle validation) and "what non-secret config is allowed" (§10). Connector.ConnectorType stores the connector kind; the registry maps kind → provider code + port + schemas.

5. Target model

A Partner owns one or more persisted Connector rows; each binds a connector kind to a CredentialBundle (via CredentialsRef) plus schema-validated non-secret ConfigJson. At runtime, a factory materialises the connector code for that kind, injected with that row's resolved bundle and config.

Partner (Flutterwave) CredentialBundle (entity, tenant-scoped, IDataProtection) ├─ Connector row ConnectorId=C1 ──ref──▶ bundle "fw-uk-oauth" { clientId, clientSecret, encKey, signingSecret } │ ConnectorType = flutterwave-payout-v4 │ ConfigJson { environment=sandbox, defaultTransferPurpose } Enabled=true └─ Connector row ConnectorId=C2 ──ref──▶ bundle "fw-ng-v3" { secretKey (FLWSECK-…) } ConnectorType = flutterwave-bills-v3 ConfigJson { environment=sandbox, country=NG } Enabled=true factory.Create(connectorRow=C1) ─▶ FlutterwavePayoutConnector bound to bundle("fw-uk-oauth") downstream records created by C1 carry ConnectorId=C1 (never just ProviderCode="Flutterwave")

6. CredentialBundle entity review #4 (closed)

A first-class, tenant-scoped entity (matching Connector's scope — review #6):

  • Id, TenantId, Name (human label), ConnectorKind (validates the field set), audit fields.
  • ProtectedSecretsJson — the secret field map, encrypted with IDataProtection explicitly (not the settings store). Decrypted only server-side at connector-build time.
  • FieldMetadata — which fields are set (for hasXxx badges) without exposing values; plus a per-field version for rotation (§11).
  • Uniqueness: (TenantId, Name) unique. Connector.CredentialsRef is an FK-by-reference to a bundle in the same tenant; reference validation rejects a save that points at a missing or cross-tenant bundle.
  • Schema change is tool-generated against AonikDbContext only (CLAUDE.md).

7. Resolution & binding review #2

7.1 Factory, not singleton

DI stops registering one connector per port as a tenant-global singleton. Instead an IPartnerConnectorFactory takes a persisted Connector row and returns a runtime connector bound to that row — the config provider is invoked with the row's CredentialsRef + ConfigJson, the typed client is built against the resolved bundle, and the returned object knows its own ConnectorId. IPartnerConnectorResolver resolves the right row for (tenant, partner, port) and hands it to the factory.

7.2 Precedence — fail closed review #5

  1. Bound bundle. The resolved connector row has a CredentialsRef → resolve the bundle → build. This is the only path for a partner-specific connector.
  2. Legacy fallback — default connector only. The legacy Finance.Partners.Flutterwave.* keys (DB setting → appsettings/env) resolve only for the single connector explicitly flagged IsLegacyDefault by the migration (§13). Any other connector with no bound bundle throws — it does not borrow the global account.
  3. Capability query → first enabled connector for the service category (only when no partner/connector was specified).
  4. "Simulated" default (must stay registered — the remittance fallback resolves it by code, Spec 037 rev 3).
Why fail-closed matters The naive "fallback to legacy keys when no bundle is bound" would let a misconfigured partner-specific connector silently route money through the global Flutterwave account. Restricting the fallback to one explicitly-migrated default connector makes a missing binding a loud failure, not a wrong-account payout.

8. Config provider refactor

IFlutterwaveConfigProvider.GetAsync / IFlutterwaveBillsConfigProvider.GetAsync gain a CredentialsRef (and the connector's ConfigJson): they resolve and decrypt the bundle, overlay the validated config, and return the same FlutterwaveOptions / FlutterwaveBillsOptions shape. The only legacy-key read path is the default-connector branch (§7.2). Transport, DTOs, and HTTP behaviour are unchanged — only the source of values moves. IsConfigured() evaluates against the resolved bundle.

9. ConnectorId propagation review #3

Multiple accounts require connector identity in downstream state, not just ProviderCode. Add ConnectorId (and PartnerId where useful) to:

Webhook resolution becomes: reference → payout → ConnectorId → that connector's bundle signing secret (§11). Migration backfills ConnectorId on existing rows to the default connector.

10. ConfigJson schema review #7

ADR-010 holds that transport/auth is shipped, not operator-authored. So ConfigJson is not free-form, and base/token URLs are not operator text fields. Each connector kind declares a typed config schema of non-secret fields only — e.g. { environment: sandbox|production, country, defaultTransferPurpose }. Transport endpoints (base URL, IdP token URL) are derived from environment by the connector code. Saving a connector validates ConfigJson against the kind's schema and rejects unknown keys. (This narrows the v4 page's current free-text Base/IdP URL fields to an environment selector.)

11. Webhook secret rotation review #8

Runtime pickup is good, but replacing a signing secret outright breaks webhooks already in flight signed with the old one. The bundle keeps a versioned signing secret: current + an optional previous with a short TTL (e.g. 24h). Verification accepts a signature matching either during the window; rotation sets previous = old, current = new, and the window expires previous. Same dual-window applies to any rotated verifier.

12. Admin UI

  • New Connectivity-tab credential editor. For each connector instance, a write-only form generated from the kind's credential schema (§4), per-field "Configured"/"Not set" badge, secret-source indicator, environment + config fields (§10), Test connection, and Enabled toggle. This is where the gap v3 bills config finally gets a home.
  • Edit Settings → Payment Gateways → a credential-bundle manager (list / create / rotate bundles, show which connectors bind each). The "never paste secrets here / CredentialsRef points to gateway settings" note is removed once the surfaces unify.
  • Reuse existing settings/service conventions; no new client data-fetching pattern.

13. Migration & back-compat

  • Schema (tool-generated): CredentialBundle table; ConnectorId/PartnerId columns on the §9 records; an IsLegacyDefault flag on Connector.
  • Seed the Flutterwave partner with two connector rows (flutterwave-payout-v4, flutterwave-bills-v3), one flagged IsLegacyDefault per port.
  • Idempotent lift: read the current Finance.Partners.Flutterwave.* values, write them (re-encrypted via IDataProtection) into a default bundle bound to those rows. Plaintext is never copied.
  • Backfill ConnectorId on existing ExternalPayoutAccount / Payout / Transmission / PartnerBillPayment / webhook rows to the default connector.
  • Fail-closed fallback applies only to the IsLegacyDefault connector during transition (§7.2).

14. Security

  • Bundle secrets are write-only, encrypted via IDataProtection, and never returned by any read endpoint; snapshots expose only hasXxx + secret-source + field versions.
  • Authz: only admins create/rotate bundles or edit connector credentials; non-admins get 401/403.
  • Every bundle write / rotation / connector credential change emits an audit event recording field names + bound ConnectorId — never values (extends Spec 038's audit guarantee).
  • Per-tenant + per-bundle isolation: cross-tenant CredentialsRef is rejected (§6); reading/rotating one bundle never affects another.

16. Acceptance criteria

  • Partner-owned config. Flutterwave is configured entirely from the partner's Connectivity tab (both connectors); resolution uses the bound bundles; no global key is touched.
  • Two accounts, same provider code, different connector ids. Two flutterwave-payout-v4 connectors with distinct bundles resolve independently; a payout via C1 uses C1's credentials and records ConnectorId=C1 (asserted).
  • Beneficiary registration isolation. A beneficiary registered via C1 stores ConnectorId=C1; re-verify and dispatch route to C1; a beneficiary of C2 is never payable via C1.
  • Payout dispatch isolation. Concurrent payouts on C1 and C2 each authenticate with their own bundle; rotating C1's secret leaves C2 unchanged.
  • Webhook secret rotation. After rotation, a webhook signed with the previous secret still verifies within the window; after the window it is rejected; a webhook is correlated to the owning ConnectorId.
  • Fail closed. A non-default connector with no bound bundle throws (no legacy borrow); the IsLegacyDefault connector still resolves via legacy keys.
  • No plaintext secret. A bundle secret is stored encrypted (asserted at the DB layer); no read API returns a value; ConfigJson with an unknown key is rejected.
  • Build & migration. dotnet build Aonik.sln + npm run build green; tool-generated migration applies cleanly with only the expected changes.

17. Open decisions

  • O1 — Flutterwave as Partner vs rail-under-partner. (OPEN) ADR-010 recommends integration providers are Partners; the "Gold Coast Bill Hub" seed (biller-hub partner with a sub-connector) is a different abstraction. Both may coexist (rail partners + biller-hub partners). Must be settled before onboarding the next connector; it determines whether ConnectorId hangs off the rail-partner or the hub-partner.
  • O2 — Bundle as entity vs settings convention. (CLOSED → entity.) Settled by review #4 / SettingService.cs:258: the settings store only encrypts statically-defined keys, so bundles are a first-class entity (§6).
  • O3 — Bundle scope. (RESOLVED → tenant-scoped.) Matching Connector; partner isolation needs it. A host/global bundle for shared sandbox creds is a possible later addition, not the default.
  • O4 — Reframe vs retire Payment Gateways page. (OPEN, leaning reframe) Keep as a cross-partner bundle manager (useful for rotation/audit) vs move all entry to the partner.
