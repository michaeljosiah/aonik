Spec 029 Status: Draft Size: Medium Priority: P2 Domain: Platform / Authentication

Keycloak as a first-class auth provider (operator choice)

Adds Keycloak as a third occupant of the existing pluggable IdP abstraction in Aonik.Infrastructure.Authentication, alongside Auth0 and Azure AD. Operators of an Aonik deployment pick one provider via Auth.Provider; Keycloak handles upstream federation (Okta, AD FS, social) so Aonik itself stays single-OIDC-talking. No multi-tenant federation surface is introduced.

1. Summary

Aonik already has a pluggable identity-provider abstraction. Six capability surfaces — JWT validation, management-API client, user provisioning, password reset, account service, and token exchange — each have a single interface in Aonik.Platform.Contracts.Services.Authentication plus a factory in Aonik.Infrastructure.Authentication that dispatches to the active provider based on the Auth.Provider setting. Auth0 and Azure AD are the two existing parallel implementations.

This spec adds Keycloak as a third occupant of that pattern. It is the lowest-cost way for Aonik to be deployable without a paid IdP, and it gives operators a clean "BYO upstream IdP via Keycloak federation" story without Aonik itself growing a multi-IdP surface. Selection is operator-level (one provider per deployment), not per-tenant.

Success signals dotnet build Aonik.sln succeeds; an Aonik API instance configured with Auth.Provider=Keycloak validates JWTs issued by a Keycloak realm, resolves tenant + user, and serves authenticated requests; user lifecycle (invite, password reset, delete) works against the Keycloak Admin API; docker compose -f compose.keycloak.yml up produces a one-command local-dev environment.

2. Context & motivation

Driver Evidence / detail
Operator deployability without a paid IdP Auth0 pricing scales aggressively; Aonik powers products targeting cost-sensitive and regulated markets (MyBillAfrica, RemitExchange). A self-hostable IdP option widens the deployable surface.
Data residency / sovereignty Some operator deployments need user-credential data inside their own jurisdiction. Self-hosted Keycloak gives full control over storage location, retention, and backup.
Federation is a Keycloak strength, not Aonik's job Keycloak natively federates upstream to Okta, AD FS, Google, GitHub, SAML 2.0 providers, and arbitrary OIDC IdPs. Pushing federation into Keycloak means Aonik only ever talks one OIDC dialect — the upstream zoo is Keycloak's problem.
Local dev ergonomics Today, contributor onboarding requires Auth0 tenant configuration to exercise the authentication path. docker compose up keycloak with a pre-seeded realm is dramatically simpler.
Forcing function for the abstraction Adding a third implementer of the existing IdP interfaces will surface any residual Auth0-shaped assumptions (claim namespaces, password-ticket semantics, connection IDs) that have leaked through.

3. Scope (in / out)

3.1 In scope

  • New KeycloakAuthOptions POCO and a new section under Auth.Keycloak in AuthOptions.
  • Edit AonikAuthenticationSetup — register a third JwtBearer scheme ("Keycloak") and extend GetProviderForIssuer / SelectScheme to recognise Keycloak realm issuers.
  • New KeycloakManagementClient : IIdentityProviderManagementClient (delete user, with realm + access-token plumbing).
  • New KeycloakUserProvisioner : IIdpUserProvisioner (create user, set initial password, send verify-email action).
  • New KeycloakPasswordResetService : IIdpPasswordResetService (execute-actions-email with UPDATE_PASSWORD).
  • New KeycloakAccountService : IIdpAccountService (update email / profile via Admin API).
  • New KeycloakAuthTokenService : IAuthTokenService (direct-grant token exchange against the realm's token_endpoint).
  • Edit the four existing factories (IdentityProviderManagementClientFactory, IdpUserProvisionerFactory, IdpPasswordResetServiceFactory, IdpAccountServiceFactory, AuthTokenServiceFactory) to add the "Keycloak" switch arm.
  • New KeycloakSettingsSnapshot and KeycloakSettingsUpdate in AuthProviderSettingsModels; extend AuthProviderSettingsService, GetAuthProviderSettingsEndpoint, UpdateAuthProviderSettingsEndpoint, and GetPublicAuthProviderSettingsEndpoint.
  • Edit AuthSettingNames — add the seven Keycloak setting keys (see §7).
  • Edit SettingDefinitions.cs — register Keycloak settings (including the secret one).
  • Edit SettingsAuthenticationPage.tsx — add Keycloak field group + secret-toggle UI, mirroring the Auth0 and Azure AD sections.
  • Edit AuthProvider.tsx / authConfig.ts in Aonik.AdminUi — admin-UI login path must work against a Keycloak OIDC client when VITE_AUTH_PROVIDER=Keycloak.
  • New compose.keycloak.yml + a pre-seeded realm export under infra/keycloak/realm-export.json for local-dev.
  • New Operator runbook: docs/operations/keycloak-setup.md (realm, clients, roles, mapper config, federation cookbook).
  • New docs/decisions/007-keycloak-as-auth-provider.md (ADR-007).
  • New Unit tests parallel to existing Auth0 / Azure AD coverage: KeycloakManagementClientTests, KeycloakUserProvisionerTests, KeycloakAuthTokenServiceTests, KeycloakPasswordResetServiceTests.
  • New Integration test gated behind an env var that exercises the full auth pipeline against the dockerised Keycloak from compose.keycloak.yml.

3.2 Out of scope

  • Per-tenant IdP choice. Auth.Provider stays platform-level. A tenant inside a deployment cannot pick a different IdP than its host's; that requires re-shaping GetActiveProviderAsync, the issuer routing, and the trust-store, and is intentionally deferred.
  • Identity migration tooling. Operators moving existing users between Auth0 / Azure AD / Keycloak get a documented playbook (export users, bulk-import via Admin API, instruct users to reset password) but no in-product migration tool.
  • Two-IdP-side-by-side mode. The active provider is single-valued. Issuer routing already supports multiple registered schemes, but only one is treated as the platform's authoritative IdP at a time.
  • Aonik-side federation. Aonik does not gain knowledge of upstream IdPs. Federation is configured inside Keycloak and is invisible to Aonik.
  • Keycloak hosting / packaging. Operators self-host Keycloak. Aonik does not ship a managed Keycloak. The repo's compose.keycloak.yml is local-dev only, not a production deployment artifact.
  • SCIM / cross-domain user sync. Provisioning stays one-way: Aonik → Keycloak Admin API. No SCIM endpoint exposed.

4. Constraints & guardrails

Must not change Must follow Ask before
  • The shape of IIdentityProviderManagementClient, IIdpUserProvisioner, IIdpPasswordResetService, IIdpAccountService, IAuthTokenService (additions OK; method-signature changes not OK).
  • ICurrentUserContext claim sources (ExternalIssuer / ExternalSubject) — remain JWT-derived.
  • The Aonik-side user record's ExternalIssuer + ExternalSubject identity (tuple stays the source of cross-provider uniqueness).
  • Auth.Provider as a single-valued platform-level setting (not a list).
  • OIDC discovery (/.well-known/openid-configuration) for endpoint resolution — never hard-code Keycloak paths.
  • Settings stored under the existing Auth.Keycloak.* namespace; secret settings flagged in SettingDefinitions.
  • The existing AonikAuthenticationSetup pattern: per-provider ConfigureJwtBearerOptions branch and per-provider issuer check inside HandleTokenValidatedAsync.
  • Same role-claim normalisation path: ClaimsRoleMapper.ExtractRoles — if Keycloak emits roles in a non-standard location, add a mapper in Keycloak (not a custom claim-reader in Aonik).
  • Introducing a Keycloak-specific claim namespace.
  • Changing factory dispatch from a string switch to a registry / list pattern.
  • Persisting Keycloak admin-client credentials anywhere other than the settings store.
  • Adding a new top-level config section outside Auth.Keycloak.

5. Architectural baseline

The codebase already has a fully formed multi-provider abstraction. The table below enumerates the existing implementations — Keycloak fills the third column.

Capability Interface Factory Existing impls
JWT validation (none — JwtBearer scheme registration) AonikAuthenticationSetup policy scheme + SelectScheme "Auth0", "AzureAd" JwtBearer schemes
Management client IIdentityProviderManagementClient IdentityProviderManagementClientFactory Auth0ManagementClient, AzureAdManagementClient
User provisioning IIdpUserProvisioner IdpUserProvisionerFactory Auth0UserProvisioner, AzureAdUserProvisioner
Password reset IIdpPasswordResetService IdpPasswordResetServiceFactory Auth0PasswordResetService, AzureAdB2cPasswordResetService
Account service IIdpAccountService IdpAccountServiceFactory Auth0AccountService, AzureAdAccountService
Token exchange IAuthTokenService AuthTokenServiceFactory Auth0AuthTokenService, AzureAdAuthTokenService

5.1 Setting surface today

AuthSettingNames exposes Auth.Provider plus two per-provider blocks (Auth.Auth0.*, Auth.AzureAd.*). AuthProviderSettingsSnapshot exposes both blocks to the admin UI; the SettingsAuthenticationPage has parallel form sections for Auth0 and Azure AD. The Keycloak addition mirrors this per-section pattern exactly.

5.2 Issuer routing

The "Aonik" policy scheme registered by AonikAuthenticationSetup.AddAonikAuthentication inspects the incoming bearer token's iss claim and forwards to the matching JwtBearer scheme via SelectScheme → GetProviderForIssuer. Keycloak fits this pattern unchanged — the issuer for a Keycloak realm is https://<keycloak-host>/realms/<realm-name>, which is a stable prefix usable for StartsWith matching.

7.1 AuthSettingNames additions

public const string KeycloakAuthority           = "Auth.Keycloak.Authority";

public const string KeycloakClientId            = "Auth.Keycloak.ClientId";

Naming follows the existing Auth0 / Azure AD pattern exactly. Authority is the full realm URL (e.g. https://keycloak.example.com/realms/aonik); derived endpoint URLs are resolved at runtime from the realm's OIDC discovery document, not stored statically.

8. Component design

8.1 AonikAuthenticationSetup changes

Three call sites need touching. They are small — the pattern already exists for Auth0 / Azure AD and these are copy-with-modifications.

  1. AddAonikAuthentication registers a third AddJwtBearer("Keycloak", ...) alongside the existing "AzureAd" and "Auth0" bearer schemes.
  2. ConfigureJwtBearerOptions gains a third branch (else if (provider == "Keycloak")) that sets options.Authority = authOptions.Keycloak.Authority and the same TokenValidationParameters shape used by the other two branches.
  3. GetProviderForIssuer gains a third StartsWith check against authOptions.Keycloak.Authority.TrimEnd('/') and returns "Keycloak".

The HandleTokenValidatedAsync body is unchanged — it works in terms of the generic iss, sub, email, roles claims and is provider-agnostic by design. The only work needed there is to confirm Keycloak emits sub + email in the access token (it does, by default).

8.2 KeycloakManagementClient : IIdentityProviderManagementClient

Wraps the Keycloak Admin REST API. Mirrors Auth0ManagementClient in shape: read settings → acquire an admin token (client_credentials grant against the same realm using the admin-client credentials, or against the master realm depending on operator choice; see §9) → call DELETE /admin/realms/{realm}/users/{userId}. 

public sealed class KeycloakManagementClient : IIdentityProviderManagementClient
{
    public string Provider => "Keycloak";

    public async Task<IdpDeleteUserResult> DeleteUserAsync(
        string externalSubject,
        string? externalTenantId,
        CancellationToken cancellationToken = default)
    {
        // 1. Resolve settings (Authority, Realm, AdminClientId, AdminClientSecret).
        // 2. POST <authority>/protocol/openid-connect/token  (client_credentials grant)
        //    → access_token for Admin API.
        // 3. DELETE <authority root>/admin/realms/<realm>/users/<externalSubject>
        //    Returns 204 (deleted) | 404 (already gone) → success.
        //    All other statuses → failure with body excerpt.
    }
}

externalSubject is the Keycloak user UUID (the sub claim). No need to URL-escape it because Keycloak UUIDs are alphanumeric + hyphens, but the implementation does Uri.EscapeDataString defensively to match the Auth0 client's hygiene.

8.3 KeycloakUserProvisioner : IIdpUserProvisioner

Provisioning flow: POST /admin/realms/{realm}/users with a user representation containing username, email, firstName, lastName, enabled: true, emailVerified: false, plus an initial credentials entry of type password if a temporary password is being set. The response is 201 Created with the new user's UUID in the Location header (Keycloak does not include the user in the response body — the location header is the canonical source).

Optional follow-up: PUT /admin/realms/{realm}/users/{id}/execute-actions-email with body ["VERIFY_EMAIL"] to dispatch the verify-email mail through Keycloak's configured SMTP. The provisioner exposes this via an IIdpUserProvisioner method that already exists for parity with the Auth0 implementation.

8.4 KeycloakPasswordResetService : IIdpPasswordResetService

Keycloak's password reset flow is the same execute-actions-email endpoint, with body ["UPDATE_PASSWORD"]. Keycloak sends the email, generates the action token, and handles the reset UI. The service's job is to look up the user by email or external subject (GET /admin/realms/{realm}/users?email=...&exact=true) and POST the action.

8.5 KeycloakAccountService : IIdpAccountService

Update-email and update-profile call PUT /admin/realms/{realm}/users/{id} with the partial user representation. Keycloak's API is PUT-with-full-object semantics in older versions but accepts partial in current versions (24+); the implementation does a GET then PUT to preserve unrelated fields.

8.6 KeycloakAuthTokenService : IAuthTokenService

Implements direct-grant token exchange against {authority}/protocol/openid-connect/token with grant_type=password, username, password, client_id, client_secret, and scope=openid email profile. Returns the access token + refresh token + expiry as the existing TokenResponse shape.

Note Direct-grant ("Resource Owner Password Credentials") is disabled by default in Keycloak. Operators who use KeycloakAuthTokenService must enable it on the client config (Direct Access Grants Enabled = ON). The operator runbook documents this and the security trade-off — direct grant bypasses the realm's login flows (MFA, terms acceptance, identity-broker challenge).

8.7 Factory changes

Each of the five factories adds a single switch arm: 

return provider switch
{
    "Auth0"    => _auth0Client,
    "AzureAd"  => _azureAdClient,
    "Keycloak" => _keycloakClient,   // NEW
    _          => null,
};

No factory base class is being introduced. Five three-line edits is less code than a new abstraction would impose, and the symmetry stays readable.

8.8 DI registration

All six new Keycloak classes register in Aonik.Infrastructure.DependencyInjection.AddAuthentication alongside the existing Auth0 / Azure AD registrations. The two that hit external HTTP (KeycloakManagementClient, KeycloakAuthTokenService) register via AddHttpClient<T> with a configured base address derived from the realm authority — same pattern used by Auth0ManagementClient.

9. Keycloak realm & client setup

An operator running Aonik against Keycloak provisions one realm containing two clients:

Client Access type Purpose Aonik setting
aonik-spa Public (no secret) — standard OIDC code+PKCE Admin UI and Payabo SPA login. Issues access tokens with audience aonik-api. Auth.Keycloak.ClientId
aonik-admin Confidential, service-accounts enabled, with realm-management roles manage-users, view-users, view-realm Aonik's Admin API client. Used by all six Keycloak* classes to provision, delete, password-reset, and update users in the realm. Auth.Keycloak.AdminClientId + Auth.Keycloak.AdminClientSecret

9.1 Realm-level configuration

  • Realm name — operator-chosen (e.g. aonik, aonik-prod). Goes into Auth.Keycloak.Realm.
  • SMTP — configured at the realm so Keycloak can dispatch verify-email and password-reset mails. Aonik never sees those mails.
  • Sign-in theme — operator chooses or leaves default. Aonik is theme-agnostic.
  • Refresh-token rotation — operator's call; the JWT validation pipeline doesn't care.
  • Audience — the aonik-spa client is configured with an audience mapper that emits aud: ["aonik-api"] on access tokens, matching Auth.Keycloak.Audience. This is the one mapper that must exist; without it, Aonik's ValidateAudience=true rejects the token.

9.2 Roles & claim mappers

Aonik's ClaimsRoleMapper.ExtractRoles reads roles from the roles claim and from realm_access.roles (which is where Keycloak puts realm-level roles by default). The operator runbook directs realm configuration so that the aonik-spa client emits a roles claim containing the user's relevant realm roles.

9.3 Admin client permissions

The aonik-admin service-account client must have the following client-level roles from the built-in realm-management client of the same realm:

  • manage-users — create / update / delete users.
  • view-users — lookup by email or external subject.
  • view-realm — read realm metadata.

Aonik does not need realm-admin. The runbook explicitly documents the principle of least privilege here — granting realm-admin would let a compromised Aonik instance modify the realm itself, federation configuration, and other clients.

10. Claims mapping

Keycloak's default OIDC claims align well with Aonik's existing HandleTokenValidatedAsync:

Aonik consumes Keycloak emits (default) Action
iss {authority} — full realm URL None.
sub Keycloak user UUID None.
email email None — ClaimsEmailResolver already accepts standard email.
roles realm_access.roles (nested array) Confirm ClaimsRoleMapper.ExtractRoles reads realm_access.roles; if not, add a path it traverses. Alternative: configure a Keycloak protocol mapper to flatten roles into a top-level roles claim.
tid (tenant ID, Azure AD-shaped) not emitted None — HandleTokenValidatedAsync already treats tid as optional; tenant resolution falls back to ResolveFromUserAssociationAsync via the Aonik-side user record.
iat iat None — used by Spec 026 token-revocation blocklist.

The roles mapping is the only judgement call. The spec defaults to configure a flattening mapper inside Keycloak rather than teaching ClaimsRoleMapper a new path. Rationale: Keycloak protocol mappers are the canonical extensibility point for shaping access-token contents, and the runbook is the right place for that operator instruction.

11. Federation playbook

This section is documentation, not code. It captures the operator-facing message that “Aonik + Keycloak = BYO upstream IdP.”

Upstream IdP Keycloak configuration User-experience flow
Okta Identity Providers → Add → OpenID Connect v1.0. Provide Okta's authorization, token, userinfo, JWKS URLs. User clicks “Sign in with Okta” on Keycloak's login page → redirected to Okta → redirected back → Keycloak issues an access token. Aonik sees a Keycloak-issued JWT.
AD FS / Azure AD Identity Providers → Add → OpenID Connect v1.0 against Microsoft's well-known endpoint. Same as Okta; Microsoft's hosted login is the federation target.
Google / GitHub (social) Identity Providers → Add → Google / GitHub (built-in social providers). One-click social login on Keycloak's login page; Aonik sees Keycloak.
Enterprise SAML 2.0 IdP Identity Providers → Add → SAML v2.0. Upload IdP metadata XML. SAML round-trip handled by Keycloak; Aonik sees Keycloak-issued OIDC JWT.

Aonik gains zero code for any of these. The federation contract is “Aonik talks OIDC to Keycloak; Keycloak talks $whatever to upstream.”

13. Phased rollout

Phase 1 — Authentication only (~1 week)

Aonik accepts and validates Keycloak-issued JWTs. No user-management surface yet.

  • Add KeycloakAuthOptions and the Auth.Keycloak.* setting keys.
  • Edit AonikAuthenticationSetup — third JwtBearer scheme + issuer routing.
  • Local-dev docker-compose + realm export.
  • Admin UI AuthProvider.tsx learns Keycloak's OIDC config.
  • Smoke: log into admin UI against local Keycloak, hit a tenant-scoped endpoint, see 200.

Phase 2 — Management plane (~2–3 weeks)

User lifecycle works end-to-end against the Keycloak Admin API.

  • Six new Keycloak* classes + DI registration.
  • Five factory switch-arm edits.
  • Unit tests parallel to Auth0 / Azure AD coverage.
  • End-to-end: invite a new user, accept invite via emailed Keycloak action link, reset password, delete user.

Phase 3 — Admin UI & runbook (~3–4 days)

Operator-facing surfaces and documentation.

  • SettingsAuthenticationPage.tsx gains the Keycloak section + form validation.
  • AuthProviderSettingsService + endpoints round-trip Keycloak settings.
  • docs/operations/keycloak-setup.md — realm setup, client roles, mapper config, SMTP.
  • ADR-007 — this spec's decisions captured.
  • Federation playbook section added to the runbook.

Phase 4 — Hardening & integration test (~1 week)

Confidence work, not feature work.

  • Integration test gated behind AONIK_TEST_KEYCLOAK=1 that spins up the dockerised realm, exercises invite + reset + delete, asserts the Aonik user state matches at each step.
  • Soak test: 1000 logins against a local Keycloak, confirm no token-cache leaks.
  • Federation smoke: configure Google as a federated IdP in the local realm, prove the end-to-end path works.
  • Auth0 → Keycloak migration playbook (export users, bulk-import, dispatch reset-password mails, document the user-visible "your password was reset, please set a new one" experience).

14. Requirements

14.1 Functional

IDRequirement
R1When Auth.Provider=Keycloak, the API accepts and validates JWTs issued by the configured realm.
R2The full user lifecycle (provision, password reset, email update, delete) succeeds against the Keycloak Admin API.
R3An Aonik admin can flip Auth.Provider at runtime via the admin UI without redeploying the API, provided the target provider's settings are fully populated. (Issuer-based scheme routing tolerates issuing tokens from the previously-active provider while the switchover happens.)
R4OIDC discovery is the source of token / JWKS endpoints; no static path is hard-coded in code.
R5Direct-grant token exchange is available behind the same IAuthTokenService.ExchangeAsync contract Auth0 / Azure AD already implement.
R6Spec 026 token-revocation blocklist works unchanged against Keycloak-issued tokens (relies on iat, which Keycloak emits by default).
R7The admin UI auth-settings page exposes Keycloak settings under a Keycloak section mirroring the existing Auth0 / Azure AD sections.
R8A first-time contributor can run docker compose -f compose.keycloak.yml up and authenticate against the local realm without external configuration steps.

14.2 Non-functional

IDRequirement
NFR1Admin-API admin tokens are cached for their expires_in window minus 30 seconds; refresh failure surfaces as a single retry, then a structured failure.
NFR2All Keycloak HTTP calls have a 10-second per-request timeout. The Admin API is not in the user-facing critical path; failures are reported, not allowed to block the calling pipeline.
NFR3No secret material is logged. The settings page only displays a boolean indicating whether a secret is set; logs never echo client secrets or admin-API access tokens.
NFR4The compose.keycloak.yml profile is dev-only and documented as such; production deployments are operator-owned.
NFR5Adding Keycloak must not increase API cold-start time measurably (target: < 50 ms delta on Aonik.Api startup).

16. Verification

16.1 Unit-test signals

  • Each Keycloak* service has tests that mock HttpClient and assert request URL, headers (including Authorization: Bearer <admin-token>), and body shape against the documented Keycloak Admin REST contract.
  • Failure-path tests: 401 admin-token expiry triggers one refresh-then-retry; 404 user-not-found on delete still returns Deleted=true (matching Auth0 client semantics); 5xx returns Deleted=false with the truncated response body in FailureReason.
  • Factory tests: "Keycloak" setting resolves to the Keycloak* client; unknown provider resolves to null; missing setting falls back to authOptions.Provider default.

16.2 Integration-test signals (gated)

  • Spin up compose.keycloak.yml in a CI service container. Run a focused test that invites a user via the Aonik API, accepts the invite via Keycloak's action-token URL, logs in via direct grant, hits a tenant-scoped endpoint, and asserts 200 with the expected user identity.
  • Run the same test against Auth0 (when the suite is gated by AONIK_TEST_AUTH0=1) and Azure AD (AONIK_TEST_AZUREAD=1); the only delta should be the provider configuration.

16.3 Manual smoke (deploy-dev flow)

  • Operator runbook walkthrough: stand up a fresh Keycloak instance, configure the realm per the runbook, flip Auth.Provider=Keycloak via the admin UI, log out, log back in, confirm the access token's iss is the Keycloak realm URL.
  • Federation smoke: add Google as a federated IdP in the realm; click "Sign in with Google" on the Keycloak login page; confirm the resulting Aonik access token carries the Google email and a Keycloak sub.

18. Decisions baked in

  1. Operator-choice, not tenant-choice. Auth.Provider stays platform-level. Per-tenant IdP is explicitly out of scope and would require re-shaping GetActiveProviderAsync and the trust-store. Re-evaluate only if a concrete customer commitment demands it.
  2. Federation lives in Keycloak, not Aonik. Aonik talks one OIDC dialect. The story for upstream Okta / AD FS / SAML / social IdPs is "configure them inside Keycloak." This keeps Aonik's abstraction surface flat.
  3. No new abstraction layer. The existing six interfaces + five factories are right-sized. Keycloak is a third occupant, not the trigger for a registry / strategy refactor.
  4. Roles via Keycloak protocol mapper, not custom ClaimsRoleMapper path. Mapper config is operator runbook territory; ClaimsRoleMapper stays provider-agnostic.
  5. Admin client uses fine-grained realm-management roles, not realm-admin. Least privilege; documented at three roles (manage-users, view-users, view-realm).
  6. OIDC discovery, not hard-coded paths. Aonik never assembles /realms/{realm}/protocol/openid-connect/token by hand; the JwtBearer middleware fetches /.well-known/openid-configuration for endpoint resolution. Aonik-side classes (KeycloakAuthTokenService) call the discovered token_endpoint.
  7. Direct-grant available but opt-in. Operators who don't enable direct grant on the aonik-spa client can't use KeycloakAuthTokenService.ExchangeAsync; that's their explicit security choice.
  8. Local-dev profile is dev-only. compose.keycloak.yml ships unsigned, ephemeral, with weak default credentials baked in. Production deployments are operator-owned; the repo does not ship a hardened Keycloak.
  9. No SCIM / no two-way sync. Provisioning is one-way: Aonik → Keycloak Admin API. Aonik is always the source of truth for the Aonik-side user record's lifecycle state.

19. Open design decisions

Open Admin client realm. Two options: (a) the admin client lives inside the aonik realm with realm-management role grants, or (b) the admin client lives in the master realm and operates cross-realm. Option (a) is simpler and keeps everything in one realm; option (b) is the only path if a single Aonik deployment ever needs to manage multiple Keycloak realms (which would only happen if we revisit the per-tenant decision). Default to (a). Revisit only if (1) becomes a real requirement.
Open JWKS caching strategy. JwtBearer middleware caches JWKS by default. If operators rotate Keycloak signing keys, do we surface a way to force a re-fetch without restarting the API? Likely answer: no — rely on the middleware's TTL (default 24h) and document the operational expectation. Open until we have evidence of operator pain.
Open Admin UI behavior when no Auth.Provider is set. Today the admin UI assumes Auth0 at compile time via Vite env vars. Phase 3 will make the OIDC config dynamic, but the "no provider configured" UX needs a design pass — should the UI present a setup wizard? Render a config-needed banner? Refuse to load entirely? Defer to Phase 3 design review.
Open Auth0 → Keycloak user migration. Spec covers "documented playbook" only. A scripted migration tool (export from Auth0 Management API, transform, bulk-import into Keycloak) is plausibly a separate spec if multiple operators ask for it. Out of scope here, captured for tracking.
Open End-user-facing language for "your provider changed". If an operator flips providers, existing users whose tokens were issued by the previous provider will eventually need to re-authenticate. The user-visible message is a product-copy decision, not an engineering one — deferred to product / ops.
