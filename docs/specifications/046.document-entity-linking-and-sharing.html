Spec 046 Status: Draft (Rev 1) Size: Medium Priority: P2 (Simi M3) Domain: Documents / PersonalFinance / Simi

Vault — document entity-linking, filter & selective share

Makes Spec 035's Documents module entity-aware for Simi's Vault: a consumer links a receipt / contract / deed to a CareEntity and to a PaymentLog, filters by person/asset/type/year, and (with Spec 048) shares selected documents with a scoped circle member. Storage, upload, and consumer access already exist; entity/receipt linking and filter-by-entity are the gap — today a document only carries an OwnerPartyId and an untyped TagsJson. Implements Simi readiness plan §5.4.

Spec family (043–048) Builds on Spec 043 (the entity a document is "for") and Spec 045 (the log a receipt proves). The selective-share enforcement lives in Spec 048; this spec makes documents query-scopable by entity so that gate has something to filter on.

1. Summary

Simi's Vault is "Provable forever": receipts file themselves against people and assets, and one tap finds "the school-fee receipt from last term." The Documents module (Spec 035) already gives blob storage, upload, listing, and consumer-reachable access — but a document can only be owned by a party and tagged with free-form JSON. It cannot be linked to a Simi CareEntity or to the PaymentLog it proves, and there is no filter-by-entity query. This spec adds a small, module-respecting link + a read contract, a typed Vault doc-type, the filter, and the consumer read path — and reserves selective sharing for Spec 048.

Success signals Fola uploads a repair invoice, tags it receipt, links it to "the Surulere flat" — and it appears on the flat's profile and in the Vault filtered to that entity + year in three taps. Marking Mum's allowance done with a screenshot auto-files that screenshot as a receipt, pre-linked to Mum and to the PaymentLog. Mr Bello (documents-only, Spec 048) sees the flat's documents and no amounts anywhere.

2. Problem & current state

  • Consumer access already works — and is not admin-only despite the policy name. Create (POST /documents) and upload (POST /documents/{id}/files) use AdminUserWritePolicy, which includes the PersonalUser role; list/get use AdminUserPolicy (also includes PersonalUser), owner-scoped so a customer sees only their own documents. Erase (DELETE /documents/{id}) is AdminPolicy — platform/tenant admin only — consistent with the Vault's archive-not-delete posture. Storage is real: DocumentFileStore over FluentStorage, tenant-scoped blob keys, SHA-256 hashing; IDocumentReader issues time-limited signed read URLs.
  • The gap is linking + filtering. Document carries OwnerPartyId, Classification, and an untyped TagsJson — but no link to a CareEntity or a PaymentLog, and no consumer filter "documents for entity X." Re-linking, the Vault's typed filter, and the receipt↔log association all need building.
  • Module boundary. CareEntity / PaymentLog live in PersonalFinance; Document lives in the Documents module. Modules don't ProjectReference each other — so the link is a soft association by Guid + a SharedKernel read contract, exactly as PersonalFinance already reads Finance data (ADR-006).

3. Scope (in / out)

3.1 In scope

  • New A DocumentLink association (document → CareEntity / PaymentLog / commitment) in the Documents module, by opaque Guid (§4).
  • New An IDocumentLinkReader added to the existing SharedKernel.Abstractions.Documents contract set, so PersonalFinance & Spec 048 can list "documents for entity X" without a cross-module reference (§4).
  • New Vault doc-types as validated values of the existing DocumentType field (receipt · contract · deed · id · other) + a new Title column (§5).
  • New Consumer filter-by-entity/type/year list + a confirmed consumer read/download path (§6–7).
  • Edit Receipt auto-file on mark-done / capture-confirm (§8).

3.2 Out of scope

  • Selective-share enforcement — the docs-only, no-amounts circle role lives in Spec 048. This spec only makes documents entity-scopable so that gate can filter (§9).
  • Re-storage / OCR changes. Blob storage, hashing, and text-extraction status are Spec 035 as-is.
  • Versioning history queries beyond what Spec 035 provides — deferred.

4. DocumentLink & read contract new

A thin association entity in the Documents module — a document can link to several targets (a contract for a co-owned flat links to the flat entity; a receipt links to the entity and the PaymentLog): 

public class DocumentLink : AuditableEntity, ITenantScoped
{
    public Guid   TenantId   { get; set; }
    public Guid   DocumentId { get; set; }          // → Document.Id (same module → real FK)
    public string TargetType { get; set; } = "";    // careEntity | paymentLog | commitment
    public Guid   TargetId   { get; set; }          // opaque Guid into PersonalFinance — NO cross-module FK
}

PersonalFinance never references the Documents module directly. The SharedKernel.Abstractions.Documents contract set already exists and is rich — IDocumentReader, IDocumentWriter, IDocumentFileStore, IDocumentSearch, IDocumentTextExtractor, DocumentContracts (incl. DocumentFileDto) — implemented by the Documents module, mirroring the SharedKernel.Abstractions.Finance pattern PersonalFinance reads Finance through (ADR-006). This spec adds one interface alongside IDocumentReader, letting the CareEntity profile (Spec 043 §8) and the circle gate (Spec 048) read links: 

namespace Aonik.SharedKernel.Abstractions.Documents;
public interface IDocumentLinkReader
{
    // Document refs (id + filename + type + thumbnail URL) linked to a target — never bytes.
    Task<IReadOnlyList<DocumentRef>> GetForTargetAsync(string targetType, Guid targetId, CancellationToken ct = default);
    Task<IReadOnlyDictionary<Guid, int>> CountForEntitiesAsync(IReadOnlyList<Guid> careEntityIds, CancellationToken ct = default);
}

5. Doc type & tagging

The Vault filter needs a small typed dimension: receipt · contract · deed · id · other. Grounding note: Document already carries a free-string DocumentType — it is on CreateDocumentRequest(OwnerPartyId, DocumentType, Status, …), whose contracts and validator still live in Platform's compliance models (Aonik.Platform/Contracts + PlatformValidators.cs, a Spec 035 extraction leftover). So the Vault adds no new type column: Simi documents use validated values of the existing DocumentType, coexisting with the platform's compliance kinds, and Classification (a platform RAG/indexing concept) stays untouched. The mobile upload's 3-field tag sheet (title, entity, type — rebuild spec §7.7) maps to: a new nullable Title column (the entity has reference metadata — IssuerName, ReferenceNumber, IssuedOn — but no display title today), a DocumentLink to the entity (§4), and a DocumentType value. Tagging stays tiny but required, because it is what makes the Vault searchable.

6. Filter & list new

Consumer list, owner-scoped, filterable by the dimensions the Vault grid exposes:

RouteVerbPurpose
/documents?careEntityId=&type=&year=GETFilter the Vault by entity, doc-type, and year (the "find the school-fee receipt ≤ 3 taps" query). Extends the existing list.
/documents/{id}/linksGET / POST / DELETEList / add / remove a document's links (re-link a contract, attach a receipt to a log).

"Documents for an entity" is served two ways: the consumer Vault calls the filtered list; PersonalFinance's CareEntity profile and the circle gate call IDocumentLinkReader (§4) — same data, no cross-module reference. New request DTOs ship validators (build-time enforced).

7. Consumer read / download confirm / expose

The Vault viewer needs to fetch content. IDocumentReader.GetReadUrlAsync(fileId, ttl) already issues a time-limited signed blob URL at the service layer; this spec confirms a consumer-reachable endpoint exposes it — GET /documents/{id}/files/{fileId}/read-url (or a streaming /content) under PersonalUser, owner-scoped (an unknown/foreign id yields 404, never revealing existence). No bytes pass through the API for large files; the client fetches the signed URL directly.

8. Receipt auto-file extend

When a mark-done (Spec 044) or a capture-confirm (Spec 047) carries an image, the flow:

capture/mark-done with image → Documents: create Document (DocumentType=receipt, Title from context) + upload file (existing endpoints) → DocumentLink → careEntity (the log's entity) and → paymentLog (the new log) → PaymentLogResponse returns the receipt DocumentRef (Spec 045 §10) "Saved. Receipt filed under Mum." — pre-tagged, zero extra taps.

The receipt is a real Vault item from birth, discoverable by the entity/year filter, and printable in the Support Statement appendix (Spec 048).

9. Selective share — deferred to Spec 048

Simi's circle includes a documents-only member (a property manager) who sees an asset's documents and no amounts anywhere. That visibility rule is a circle-grant concern, enforced by Spec 048's single visibility filter. This spec's contribution is the prerequisite: documents are linked to entities (§4), so 048 can resolve "the documents this member may see" as "documents linked to the entities in their grant." A docs-only response returns DocumentRefs only — no PaymentLog, no totals — so there is no amount to leak.

10. Persistence & migration

  • New table DocumentLink in the Documents module: DbSets on AonikDbContext — which maps the document family via MapPlatformTable<T> (Document, DocumentFile, DocumentVersion, … → dbo.AnkDocuments etc.), so DocumentLink follows: MapPlatformTable<DocumentLink>(modelBuilder, "DocumentLinks") — and on the internal DocumentsDbContext (its MapTable / ModuleTablePrefixes.Default). Indexes on (TenantId, TargetType, TargetId) and (TenantId, DocumentId).
  • Title as a new nullable column on Document, and Vault doc-types as validated values of the existing DocumentType string (§5) — one tool-generated migration covers both.
  • No backfill required — existing documents simply have no links yet; the Vault shows them under "untagged" until linked.
  • Tool-generated migration only against AonikDbContext (CLAUDE.md).

11. Security

  • Owner scoping preserved. A consumer sees only their own documents; an unknown id yields an empty list / 404 (Spec 035's guarantee), never revealing existence.
  • Links are caller-validated. A DocumentLink may only target a CareEntity / PaymentLog that belongs to the caller (checked via the PersonalFinance read side), preventing a document from being attached to someone else's entity.
  • Encryption & signed URLs inherit from Spec 035 (at-rest encryption, time-limited read URLs); the viewer honours the app's biometric lock client-side.
  • No-amounts guarantee for docs-only sharing is owned and tested by Spec 048; this spec keeps the document response amount-free by construction.

13. Acceptance criteria

  • Link & filter. A consumer uploads a document, links it to a CareEntity with DocumentType = "receipt", and finds it via ?careEntityId=&type=receipt&year=; it also appears on that entity's profile via IDocumentLinkReader.
  • Re-link. A document can be re-linked to a different entity and to a PaymentLog; removing a link leaves the document intact.
  • Auto-file. A mark-done with an image produces a receipt document pre-linked to the entity and the log, returned as a DocumentRef on the PaymentLog.
  • Read path. A consumer fetches a signed read URL for their own file; a foreign file id yields 404.
  • Module boundary. PersonalFinance reads document links only through IDocumentLinkReader — no ProjectReference to the Documents module (architecture test holds).
  • Build & migration. dotnet build green; tool-generated migration adds AnkDocumentLinks + the Title/DocumentType change only.

14. Open decisions

  • O1 — Vault vocabulary on the existing DocumentType. Simi types (receipt/contract/deed/id/other) become validated values of the existing free-string DocumentType, coexisting with the platform's compliance kinds — vs introducing a parallel Simi-only field. Leaning the former; confirm no compliance flow filters on DocumentType in a way Vault values would pollute.
  • O2 — Relocate the document request contracts? CreateDocumentRequest + validator still live in Platform's compliance models despite the Spec 035 extraction. Adding Title/links touches them; decide whether to move them into Aonik.Documents contracts as part of this spec or leave the relocation for a cleanup pass.
  • O3 — Document ownership: party vs user. Spec 035 owns by OwnerPartyId; Simi documents are user-scoped via their links. Confirm the owner-party resolution for a consumer at implementation (likely the user's own party).
