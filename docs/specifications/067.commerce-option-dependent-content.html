Commerce option-dependent product content

Authored product content — nutrition figures, ingredients, allergen declarations, preparation/heating guidance — that changes with the customer's option selection and is never computed. Build area B of the Abby's Table storefront capability plan; implements plan decision D2 (structured entities, not AttributesJson).

Revision 1.1 (Codex review round 1). (1) Variants are now keyed by the complete canonical selection, not a diff — identity survives recommended-default changes (§5); a default change flags the default block for review instead of silently re-labelling content (§6). (2) Fallback for a non-default selection withholds ingredients & allergens — declarations are exact-authored or absent, never substituted (§5). (3) V-C6 reversed: adding a default figure re-validates every active variant. (4) Uniqueness moves to a fixed-length SelectionHash (SQL index key limit). (5) Products without a default block are a defined state (null content, 404 resolution). (6) Figures validated finite and non-negative. (7) ContentVersion + cache-key rules bound public cache staleness (§8). (8) Resolution history honesty: content resolves against current authoring; snapshot-at-checkout and revisions are explicit open decisions (§15).

Revision 1.2 (Codex review round 2). (9) Variant declarations and heating are explicit-or-withheld — dynamic inheritance from the default block is gone (§4/§5). (10) Fallback withholds heating like declarations — substituted timings are unsafe food, not a caption problem (§5). (11) v is validated: only the current version is publicly cacheable, killing future-version cache poisoning; setting RequiresReview bumps ContentVersion atomically; content caches vary by tenant (§8). (12) Product DTO embeds the resolved standard preparation, not the raw block (§8). (13) A currency-free NormalizeAsync is specified as a Spec 066 amendment (§7). (14) Cross-row invariants serialize on the ProductContent concurrency token (§9). (15) Selection columns are nvarchar(max); coverage is bounded to single-choice deviations (§8/§10).

1. Summary

A product's displayed facts can depend on how it is configured: a portion change alters every nutrition figure; a protein swap alters protein, fat and the allergen declaration. This spec adds a default content block per product (ProductContent) and authored variants per complete selection combination (ProductContentVariant), a resolution service keyed on the canonical selection form defined in Spec 066, and a public resolution endpoint. When no variant is authored for a requested combination, nutrition figures fall back to the default flagged isStandardPreparation: true — but ingredients and allergen declarations are withheld, not substituted. Nothing is ever scaled, multiplied, merged or derived.

2. Motivation & safety stance

The Abby's Table Step 2 spec (FR-10.2) corrected its own v1.0 on exactly this point: it had said "multiply nutrition by 2 for a full portion", which is wrong in general and dangerous in particular — a multiplier can never produce a changed allergen list. The platform rules this spec encodes:

Authored, or absent. Never derived, never substituted. Nutrition figures shown for a selection are either authored for exactly that combination or are the default figures explicitly captioned as describing the standard preparation. Ingredients and allergen declarations are stricter still: they are served only when authored for exactly the requested combination (or when the request is the standard preparation) — otherwise they are withheld and the storefront shows its "not yet published for this combination" state. A customer who chose salmon must never read the standard preparation's shellfish declaration under their selection, footnote or not. This data gets structured entities and admin validation rather than a JSON-blob convention (plan decision D2) for the same reason.

4. Domain model

Anemic, tenant-scoped, in src/Aonik.Commerce/Entities/Catalog/. Nutrition figures are dedicated nullable decimal columns (not JSON) per decision D2 — they are the facts admin validation operates on. Heating steps are display content and stay JSON.

/// Default ("standard preparation") content for one product. At most one per product.
public class ProductContent : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid ProductId { get; set; }
    public string ServingLabel { get; set; } = string.Empty;   // "Light table 225g"
    public decimal? Kcal { get; set; }
    public decimal? ProteinGrams { get; set; }
    public decimal? CarbsGrams { get; set; }
    public decimal? FatGrams { get; set; }
    public decimal? FibreGrams { get; set; }
    public decimal? SugarsGrams { get; set; }
    public decimal? SaltGrams { get; set; }
    public string? Ingredients { get; set; }                   // full declaration text
    public string? Allergens { get; set; }                     // allergen declaration text
    public string HeatingJson { get; set; } = "[]";            // [{ "method": "...", "body": "..." }]
    /// The canonical all-defaults selection this block describes, captured at authoring
    /// time. Resolution cross-checks it against the product's current all-defaults selection —
    /// a mismatch behaves exactly like RequiresReview even if the flag write was missed, so the
    /// binding is self-verifying, not only event-driven.
    public string DescribesSelectionJson { get; set; } = "{}";
    /// Set when the product's effective default combination changes after this block was
    /// authored (§6). While true, non-variant resolutions are flagged stale and declarations are
    /// withheld. Cleared by re-upserting the block or explicitly confirming review (both of which
    /// re-capture DescribesSelectionJson).
    public bool RequiresReview { get; set; }
    /// Monotonic version covering this product's whole content set (default + variants).
    /// Bumped on every content write; participates in the public cache key (§8).
    public int ContentVersion { get; set; }
}

/// Authored content for one exact, complete selection combination of one product.
/// Keyed by the complete canonical selection (Spec 066 §7) — identity is therefore stable when a
/// recommended default later changes.
public class ProductContentVariant : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid ProductId { get; set; }
    /// The complete canonical selection this content describes. Authoring input may be
    /// partial; it is normalised through Spec 066 (omitted groups filled with the then-current
    /// defaults) and stored complete.
    public string SelectionJson { get; set; } = "{}";
    /// SHA-256 (hex, lower) of SelectionJson. Fixed-length uniqueness key — a 1024+ char
    /// JSON string cannot participate in a SQL Server nonclustered unique index (1,700-byte key
    /// limit).
    public string SelectionHash { get; set; } = string.Empty;
    public string ServingLabel { get; set; } = string.Empty;
    public decimal? Kcal { get; set; }
    public decimal? ProteinGrams { get; set; }
    public decimal? CarbsGrams { get; set; }
    public decimal? FatGrams { get; set; }
    public decimal? FibreGrams { get; set; }
    public decimal? SugarsGrams { get; set; }
    public decimal? SaltGrams { get; set; }
    /// Explicit or withheld — never dynamically inherited. Null = WITHHELD for this
    /// combination (the storefront shows its "not yet published" state); non-null = the authored
    /// declaration for exactly this combination. Admin UI may prefill from the default block as a
    /// copy at authoring time, but what is stored is what is served: a later default-block edit
    /// can never silently change what a variant declares (the salmon variant returning the
    /// standard preparation's shellfish line via inheritance is exactly the §2 incident).
    public string? Ingredients { get; set; }
    public string? Allergens { get; set; }
    /// Same rule as the declarations: explicit or withheld, never inherited. Heating is
    /// option-dependent content too — a full portion served the light portion's timings is
    /// undercooked food, not a display nit.
    public string? HeatingJson { get; set; }
    public bool IsActive { get; set; } = true;
}

Nutrition figures are nullable per field, all-or-flagged per block. A variant either supplies every figure the default block publishes, or admin validation rejects it (§9 V-C2) — a panel mixing default kcal with variant protein would be a derived panel by the back door. A variant may publish more figures than the default, never fewer. The nullable columns exist so a tenant that publishes no sugars figure at all can stay consistent, not to allow per-variant partial panels.

5. Resolution: exact-selection matching

Given a product and a selection:

  1. If the product has no ProductContent row, resolution returns not-found (HTTP 404 on the endpoint; content: null on the product DTO). Content is optional per product; absence is a defined state, never an empty panel presented as fact.
  2. Normalise the selection via Spec 066 (IOptionSelectionService) — complete, canonical, validated. Invalid selections fail there first (V1–V5).
  3. Variant lookup: find the active variant whose SelectionHash / SelectionJson equals the normalised complete selection. Found → serve it: authored figures and serving label; its declarations and heating serve only when explicitly authored on the variant — null means withheld (declarationsWithheld / heatingWithheld), never inherited from the default block. isStandardPreparation: false.
  4. No variant. Compute the diff: the groups where the selection differs from the current effective default — compared by keys, never by price (two £0 proteins are still a diff, and a diff is exactly what can change an allergen list; multi-select values compare as sorted arrays).
  5. Empty diff (the request is the standard preparation) → serve the default block, isStandardPreparation: false. If the block RequiresReview, figures are flagged isStale: true and declarations are withheld (§6).
  6. Non-empty diff → serve the default block's figures with isStandardPreparation: true (caption: "figures are for the standard preparation") — and withhold ingredients, allergens and heating (declarationsWithheld: true, heatingWithheld: true). Heating is as option-dependent as the declarations — light-portion timings on a full portion is undercooked food; the caption qualifies figures, it does not make substituted preparation instructions safe. The storefront renders its existing "not yet published for this combination" states. RequiresReview additionally flags the figures stale.

Why exact, not best-partial. If variants exist for the full-portion combination and the salmon combination and the customer picks full + salmon, neither was authored for that combination — a "closest" pick would present a half-truth as fact (salmon allergens with light-portion figures, or doubled figures without the fish declaration). Step 2 FR-10.2 names this exactly: "never present a guess as fact". The cost is authoring combined variants where combinations matter; the coverage listing (§8, admin) makes those gaps visible instead of silent.

6. Reacting to default changes

Content meaning is entangled with defaults in exactly one place: the default block describes "the standard preparation", and which combination that is changes when a recommended default moves (Spec 066's atomic SetRecommendedDefaultAsync, a product-level DefaultChoiceKey override, or a narrowing change that shifts the effective default). Complete-selection variants are immune — their content describes an absolute combination that remains true regardless of which combination is currently "default". Two consequences:

  • Variants stay reachable and correct. After the protein default moves chicken → salmon, the variant authored for the salmon combination still serves for salmon selections — now including the all-defaults selection, which §5 step 3 resolves to it before any default-block fallback. Nothing silently re-labels.
  • The default block becomes suspect. When a product's effective default combination changes, this spec sets RequiresReview = true on its ProductContent (subscribing to the affected-products enumeration Spec 066's operation returns; product-level override and narrowing writes trigger the same flag). While flagged: exact variant matches serve normally; every resolution that would use the default block serves figures flagged isStale: true and withholds declarations and heating. The flag clears when an admin re-upserts the block or calls the explicit confirm endpoint ("reviewed, still correct") — both re-capture DescribesSelectionJson. Belt and braces: the block stores the canonical all-defaults selection it was authored for, and resolution treats any mismatch between that and the current all-defaults selection exactly as RequiresReview — a missed hook (or a default shifted by a path that never fired one) can still never serve old standard-prep content as the new standard preparation. Wrong-but-flagged beats wrong-presented-as-fact; withheld beats both for declarations.

7. Service

public interface IProductContentService
{
    // authoring
    Task<ProductContentDto> UpsertContentAsync(Guid productId, UpsertProductContentCommand command, CancellationToken ct = default);
    Task<ProductContentDto> ConfirmContentReviewAsync(Guid productId, CancellationToken ct = default); // clears RequiresReview
    Task<ProductContentVariantDto> AddVariantAsync(Guid productId, UpsertContentVariantCommand command, CancellationToken ct = default);
    Task<ProductContentVariantDto> UpdateVariantAsync(Guid variantId, UpsertContentVariantCommand command, CancellationToken ct = default);
    Task DeactivateVariantAsync(Guid variantId, CancellationToken ct = default);
    // reads
    Task<ResolvedContentDto?> ResolveAsync(Guid productId, JsonDocument? selection, CancellationToken ct = default); // null = no default block
    Task<ContentCoverageDto> GetCoverageAsync(Guid productId, CancellationToken ct = default);
}

public record ResolvedContentDto(
    string ServingLabel,
    NutritionDto Nutrition,            // the published figures, nulls preserved
    string? Ingredients,               // null when withheld or not authored
    string? Allergens,                 // null when withheld or not authored
    bool DeclarationsWithheld,         // true = no exact-authored declaration for this combination
    IReadOnlyList<HeatingStepDto> Heating,   // empty when withheld
    bool HeatingWithheld,              // true = no exact-authored heating for this combination
    bool IsStandardPreparation,        // default figures shown for a different combination
    bool IsStale,                      // default block awaiting review after a default change
    string CanonicalSelectionJson,     // what was resolved for (post-normalisation)
    string? MatchedVariantSelectionJson,  // the variant that matched; null when default served
    int ContentVersion);

Amendment to Spec 066 §10 (to fold into 066 at implementation): content resolution is currency-independent, but 066's only strict operation is NormalizeAndPriceAsync(productId, selection, currency) — using it here would either invent a currency or fail valid content requests on pricing rule V10. IOptionSelectionService therefore additionally exposes NormalizeAsync(productId, selection): identical validation and canonicalisation (V1–V5), no pricing, no currency parameter. This resolver — and any other content-only consumer — uses it.

8. API surface & caching

Public (AllowAnonymous)

RouteReturns
GET /commerce/catalog/products/{slug} (extended) ProductDto gains content — the resolved standard-preparation content (the §5 resolution of the empty selection, carrying its flags), not the raw default row — and contentVersion. Embedding the raw block would bypass §5/§6: after a default move, the variant that now describes the standard combination must win, and a suspect block must arrive stale-flagged with declarations withheld. null when no default block is authored. A product page renders its panels from the first call; no second request until an option changes.
GET /commerce/catalog/products/{slug}/content?selection=<url-encoded canonical JSON>&v={contentVersion} ResolvedContentDto for the selection. Omitted/empty selection resolves the standard preparation. 404 when the product has no default block.

Caching (bounded staleness — safety content is cacheable only with an eviction story)

  • ContentVersion increments on every content write for the product: default upsert, review confirm, variant add/update/deactivate/reactivate — and the §6 default-change reaction that sets RequiresReview. The flag exists precisely to change what resolution returns, so setting it must invalidate cached responses like any other content write; the flag-set and version-bump commit atomically, or a cached response could keep serving declarations with isStale: false after the default moved.
  • The storefront obtains contentVersion from the product DTO and includes it as the v parameter — the version is part of the cache key, so any authoring correction changes the URL and previously cached responses become unreachable rather than stale-served.
  • v is validated, not ignored. Origin computes the correct current response either way, but only stamps Cache-Control: public, max-age=300 when v equals the current ContentVersion; an absent or mismatched v gets Cache-Control: no-store. Otherwise an anonymous caller could pre-poison a shared cache by requesting future versions (v=N+1 while current is N) and have the stale body served after a correction bumps to N+1 — defeating the changed-URL guarantee A15 relies on.
  • Cache partitioning is tenant-aware. Under header tenant routing two tenants share host and path and differ only by X-Tenant-Id, so cacheable responses emit Vary: X-Tenant-Id (subdomain routing partitions naturally by host). One tenant's allergen content served to another's customers is not a tolerable cache quirk.
  • Worst-case staleness after an admin correction is bounded by the product-page revalidation window (which refreshes contentVersion) plus 300 s — not "until the CDN feels like it". The bound is asserted in the acceptance criteria (A15).

Admin (writes AdminWritePolicy, reads AdminUserPolicy)

RoutePurpose
PUT /commerce/admin/products/{productId:guid}/contentUpsert the default block (clears RequiresReview)
POST /commerce/admin/products/{productId:guid}/content/confirm-reviewClear RequiresReview without editing ("reviewed, still correct")
POST /commerce/admin/products/{productId:guid}/content-variantsAuthor a variant for a combination (input may be partial; stored complete)
PUT /commerce/admin/content-variants/{variantId:guid}Update a variant
DELETE /commerce/admin/content-variants/{variantId:guid}Soft-retire (sets IsActive=false)
GET /commerce/admin/products/{productId:guid}/content-coverage Coverage listing: every authored variant combination, plus the single-choice-deviation gaps — for each offered group, each offered non-default choice substituted alone into the standard selection (a multi-select group contributes each single choice alone, not its power set). Bounded by Σ|offered choices| per product, never combinatorial — a large multi-select group must not turn an admin read into a 2N enumeration. Multi-choice and multi-group combinations are authored on demand and appear in the authored list.

9. Validation rules (authoring)

#Reject when…
V-C1The variant's selection fails Spec 066 validation for this product (unknown group/choice, not offered, selection-mode violation) — or, after normalisation, equals the current all-defaults selection (that content belongs on the default block, and authoring it as a variant would shadow the block's review lifecycle). Authoring input is normalised through Spec 066 exactly like customer input, so partial input and any redundant default-valued entries resolve into the stored complete canonical form — there is no separate "diff hygiene" to police.
V-C2The variant's figure set would produce a mixed panel: for every figure the product's default block publishes, the variant must publish it too. (More is allowed; fewer is not.)
V-C3ServingLabel missing — every block must caption which preparation it describes (FR-10.2).
V-C4A second active variant would exist for the same complete canonical selection (uniqueness on SelectionHash; the service compares SelectionJson on hash conflict before failing).
V-C5Hard-deleting anything: variants soft-retire only — the rows remain for admin history, audit and reactivation. (Note this is authoring history, not resolution history: resolution always reflects current authoring — see Open decision O3.)
V-C6A default-content upsert adds a published figure that any active variant does not publish — the write is rejected naming those variants (update them first, or in the same batch). Removing a figure from the default is allowed: variants may over-publish, and every variant that was complete stays complete.
V-C7Any nutrition figure is negative, non-finite, or exceeds the column bound (decimal(9,2)) — on the default block and on variants alike. SQL would happily store −500 kcal; the service must not.
V-C8Adding a variant to a product that has no default block — the block is the baseline V-C2 is defined against.

Cross-row invariants are serialized, not hoped for. V-C2 and V-C6 span the default block and every active variant, and no single database constraint can express them: a default upsert racing a variant write could each validate against the other's old state and commit an inconsistent pair. Every content write for a product — default upsert, confirm-review, variant add/update/deactivate — therefore runs in one transaction that performs its validation and updates ProductContent.ContentVersion under the row's optimistic-concurrency token (rowversion, already stamped by AonikDbContextBase.ConfigureRowVersions). Concurrent content writes to the same product conflict on that token; the loser revalidates against fresh state and retries once, then fails cleanly. The version bump the cache needs (§8) doubles as the serialization point.

10. Persistence & migration

  1. Configurations in src/Aonik.Commerce/Persistence/Configurations/Catalog/ — indexes per §4; ServingLabel 128, Ingredients/Allergens nvarchar(max), figures decimal(9,2), SelectionJson and DescribesSelectionJson nvarchar(max) — Spec 066 bounds neither group count nor multi-select width, so a fixed cap could reject a valid canonical selection at persistence after it passed validation; only the hash is ever indexed — SelectionHash char(64) (the unique key — TenantId + ProductId + hash is ~96 bytes, comfortably inside SQL Server's 1,700-byte nonclustered key limit; the JSON itself is never indexed).
  2. DbSets in AonikDbContext + CommerceDbContext, with MapTable entries (ProductContents, ProductContentVariants).
  3. Tool-generated migration on the canonical stream: 
    dotnet ef migrations add AddCommerceProductContent --project src/Aonik.Infrastructure --startup-project src/Aonik.Api
    Expect two new tables, nothing else. Review, apply locally, and commit all three generated artifacts — the migration .cs, its .Designer.cs, and the updated AonikDbContextModelSnapshot.cs (an uncommitted snapshot makes the next migration rediscover these tables). Hand-written migrations are prohibited (CLAUDE.md). No backfill: existing products simply have content: null until authored (§5 step 1).

11. Security & tenancy

  • Tenant-scoped entities behind the global query filters; public reads serve active data of Active products only; tenant resolution as per the existing anonymous catalog endpoints.
  • Admin split identical to Spec 066 (AdminWritePolicy / AdminUserPolicy).
  • No PII. Content is public-by-intent data; the sensitivity is correctness, which is what §5, §6 and §9 exist for.

12. Testing

  • Unit — resolution: exact-selection hit; combined selection with only single-group variants authored → default figures + note + withheld declarations; empty diff serves the block unflagged; equal-price swaps still miss the block (key-based diff); multi-select order-insensitivity via canonical form; inherit-vs-replace for text and heating; no default block → null/404; RequiresReview: variant matches serve normally, block-based resolutions flag stale + withhold declarations.

14. Acceptance criteria

#Given / when / then
A1A variant authored for the full-portion combination; customer selects full → the authored figures return with its serving label — not the default figures doubled (Step 2 AC-19).
A2Variants exist for the full-portion and salmon combinations separately; customer selects full + salmon → no exact match: default figures return with isStandardPreparation: true and declarationsWithheld: true; ingredients/allergens are null. Neither partial variant is served.
A3The salmon-combination variant replaces the allergen text → resolution for that combination returns the fish declaration; the default's shellfish declaration is nowhere in the response.
A4Selection equal to the standard preparation → default block, isStandardPreparation: false, declarations served.
A5Two £0 choices swapped (chicken → prawns, both zero-priced) → still a non-default combination; resolution goes through variant lookup and, absent one, withholds declarations rather than assuming price-neutral means content-neutral.
A6Multi-select combination {protein: ["chicken","salmon"]} matched regardless of authoring or selection order of the two keys.
A7Authoring a variant referencing a choice the product's narrowing excludes → 400 naming V-C1.
A8Authoring a variant missing a figure the default publishes → 400 naming V-C2 and the missing figure.
A9Deactivated variant's combination selected → fallback semantics (withheld declarations); reactivating restores authored resolution with no other write.
A10Coverage endpoint lists every offered single-group non-default combination without a variant; authoring one removes it from the gap list.
A11The protein default moves chicken → salmon (Spec 066 atomic operation): the salmon-combination variant now serves for the all-defaults selection with full declarations; the default block is flagged — an all-chicken selection returns isStale: true with declarations withheld until re-upsert or confirm-review.
A12Product with no default block → ProductDto.content is null; the content endpoint returns 404; adding a variant → 400 naming V-C8.
A13Authoring kcal −500 (or any negative/non-finite figure) → 400 naming V-C7.
A14Default upsert adding a sugars figure while an active variant lacks it → 400 naming the variant (V-C6); removing a figure the variants still publish succeeds.
A15An allergen correction on the default block bumps contentVersion; the storefront's next product-DTO revalidation yields a new v and therefore a new cache key — total staleness ≤ product-page revalidation window + 300 s, verified by the changed URL.
A16Authoring a variant whose normalised selection equals the current all-defaults selection → 400 naming V-C1.
A17A request with v ≠ current ContentVersion (including a future value) returns the correct body with Cache-Control: no-store; only v == current gets public, max-age=300 — a pre-poisoned future-version cache entry is impossible.
A18A default change setting RequiresReview bumps ContentVersion in the same transaction — the next product-DTO read advertises a new v and no cached response can keep serving isStale: false.
A19A variant authored with figures but null declarations → its resolution returns declarationsWithheld: true even though the default block has declarations; editing the default block's allergens changes nothing about what that variant serves.
A20Fallback for a non-default combination withholds heating (heatingWithheld: true, empty steps) exactly as it withholds declarations; a variant with authored heating serves it.
A21Concurrent default-upsert (adding a figure) and variant-add race → one commits, the other conflicts on the ProductContent token, revalidates, and is correctly rejected/accepted against the fresh state — a variant missing a now-published figure can never persist.

15. Open decisions

O1 — Figure precision & units. Figures are unit-fixed by column name (grams, kcal) with decimal(9,2). If a tenant ever needs per-100g alongside per-serving, that is a second figure set, not a unit column — deferred until a real tenant asks.

O2 — Localisation. Ingredients/allergens are single-language text. Multi-locale content would add a locale key to both entities; out of scope until a multi-locale storefront exists.

O3 — Reproducing what a shopper saw. Resolution is always against current authoring; orders store the selection, not the content, so an allergen correction changes what a historical selection resolves to (deliberately — the correction is the truth). If displayed-content-at-purchase must ever be reproducible (dispute, regulation), the clean options are (a) Spec 068 snapshotting the resolved content into the order envelope at checkout, or (b) immutable content revisions with effective dates. Neither is built here; choosing between them is deferred until the requirement is real.
