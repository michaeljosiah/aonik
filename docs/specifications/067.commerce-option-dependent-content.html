Commerce option-dependent product content

Authored product content — nutrition figures, ingredients, allergen declarations, preparation/heating guidance — that changes with the customer's option selection and is never computed. Build area B of the Abby's Table storefront capability plan; implements plan decision D2 (structured entities, not AttributesJson).

1. Summary

A product's displayed facts can depend on how it is configured: a portion change alters every nutrition figure; a protein swap alters protein, fat and the allergen declaration. This spec adds a default content block per product (ProductContent) and authored variants per selection combination (ProductContentVariant), a resolution service keyed on the canonical selection form defined in Spec 066, and a public resolution endpoint. When no variant is authored for a combination, the default is returned flagged isStandardPreparation: true — the storefront shows the figures with a "standard preparation" caption. Nothing is ever scaled, multiplied, merged or derived.

2. Motivation & safety stance

The Abby's Table Step 2 spec (FR-10.2) corrected its own v1.0 on exactly this point: it had said "multiply nutrition by 2 for a full portion", which is wrong in general and dangerous in particular — a multiplier can never produce a changed allergen list. The platform rule this spec encodes:

Authored or default-with-note. Never derived. Content shown for a selection is either (a) content a human authored for exactly that combination, or (b) the product's default content explicitly flagged as describing the standard preparation. There is no third state. An allergen line presented for a combination nobody authored is a safety incident, not a display bug — which is also why this data gets structured entities and admin validation rather than a JSON-blob convention (plan decision D2).

4. Domain model

Anemic, tenant-scoped, in src/Aonik.Commerce/Entities/Catalog/. Nutrition figures are dedicated nullable decimal columns (not JSON) per decision D2 — they are the facts admin validation and future coverage tooling operate on. Heating steps are display content and stay JSON.

/// Default ("standard preparation") content for one product. At most one per product.
public class ProductContent : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid ProductId { get; set; }
    public string ServingLabel { get; set; } = string.Empty;   // "Light table 225g"
    public decimal? Kcal { get; set; }
    public decimal? ProteinGrams { get; set; }
    public decimal? CarbsGrams { get; set; }
    public decimal? FatGrams { get; set; }
    public decimal? FibreGrams { get; set; }
    public decimal? SugarsGrams { get; set; }
    public decimal? SaltGrams { get; set; }
    public string? Ingredients { get; set; }                   // full declaration text
    public string? Allergens { get; set; }                     // allergen declaration text
    public string HeatingJson { get; set; } = "[]";            // [{ "method": "...", "body": "..." }]
}

/// Authored content for one exact selection combination of one product.
public class ProductContentVariant : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid ProductId { get; set; }
    /// Canonical diff this variant is authored for (§5): group key → choice key or
    /// sorted array. Canonicalised at write time; unique per product.
    public string MatchJson { get; set; } = "{}";
    public string ServingLabel { get; set; } = string.Empty;
    public decimal? Kcal { get; set; }
    public decimal? ProteinGrams { get; set; }
    public decimal? CarbsGrams { get; set; }
    public decimal? FatGrams { get; set; }
    public decimal? FibreGrams { get; set; }
    public decimal? SugarsGrams { get; set; }
    public decimal? SaltGrams { get; set; }
    /// Null = inherit the default's text; non-null = replace it wholesale. There is no
    /// merging of ingredient or allergen text — inherit or replace, nothing in between.
    public string? Ingredients { get; set; }
    public string? Allergens { get; set; }
    public string? HeatingJson { get; set; }                   // null = inherit default steps
    public bool IsActive { get; set; } = true;
}

Nutrition figures are nullable per field, all-or-flagged per block. A variant either supplies the figures it changes plus every figure needed for a complete panel, or admin validation rejects it (§8 V-C2) — a panel mixing default kcal with variant protein would be a derived panel by the back door. The nullable columns exist so a tenant that publishes no sugars figure at all can stay consistent, not to allow per-variant partial panels.

5. Resolution: exact-diff matching

Given a product and a selection:

  1. Normalise the selection via Spec 066 (IOptionSelectionService) — complete, canonical, validated. Invalid selections fail there first (V1–V5).
  2. Compute the diff: the subset of groups whose chosen value differs from the effective default, compared by keys, never by price — two £0 proteins are still a diff, and a diff is exactly what can change an allergen list. Multi-select values compare as sorted arrays; the default of a multi-select group is the one-element array of its default choice.
  3. Empty diff → return the default block with isStandardPreparation: false (the figures genuinely describe this preparation — it is the standard one).
  4. Non-empty diff → find the active variant whose canonical MatchJson equals the diff exactly (string equality of canonical forms). Found → return it, with null text/heating fields inherited from the default, isStandardPreparation: false.
  5. Not found → return the default block with isStandardPreparation: true. The storefront must caption accordingly ("figures are for the standard preparation").

Why exact, not best-partial. If variants exist for {portion: full} and {protein: salmon} and the customer picks both, neither was authored for the combination — a "closest" pick would present a half-truth as fact (salmon allergens with light-portion figures, or doubled figures without the fish declaration). Step 2 FR-10.2 names this exactly: "never present a guess as fact". The cost is authoring combined variants where combinations matter; the coverage listing (§7, admin) makes those visible instead of silent.

6. Service

public interface IProductContentService
{
    // authoring
    Task<ProductContentDto> UpsertContentAsync(Guid productId, UpsertProductContentCommand command, CancellationToken ct = default);
    Task<ProductContentVariantDto> AddVariantAsync(Guid productId, UpsertContentVariantCommand command, CancellationToken ct = default);
    Task<ProductContentVariantDto> UpdateVariantAsync(Guid variantId, UpsertContentVariantCommand command, CancellationToken ct = default);
    Task DeactivateVariantAsync(Guid variantId, CancellationToken ct = default);
    // reads
    Task<ResolvedContentDto> ResolveAsync(Guid productId, JsonDocument? selection, CancellationToken ct = default);
    Task<ContentCoverageDto> GetCoverageAsync(Guid productId, CancellationToken ct = default);
}

public record ResolvedContentDto(
    string ServingLabel,
    NutritionDto Nutrition,            // the seven figures, nulls preserved
    string? Ingredients,
    string? Allergens,
    IReadOnlyList<HeatingStepDto> Heating,
    bool IsStandardPreparation,        // true = default shown for an unauthored combination
    string CanonicalSelectionJson,     // what was resolved for (post-normalisation)
    string? MatchedVariantDiffJson);   // the diff that matched; null when default served

7. API surface

Public (AllowAnonymous)

RouteReturns
GET /commerce/catalog/products/{slug} (extended) ProductDto gains content — the default block. A product page renders its panels from the first call; no second request until an option changes.
GET /commerce/catalog/products/{slug}/content?selection=<url-encoded canonical JSON> ResolvedContentDto for the selection. Omitted/empty selection resolves the default. GET (not POST) deliberately: deterministic per selection string, so ISR and CDN caching work per combination.

Admin (writes AdminWritePolicy, reads AdminUserPolicy)

RoutePurpose
PUT /commerce/admin/products/{productId:guid}/contentUpsert the default block
POST /commerce/admin/products/{productId:guid}/content-variantsAuthor a variant for a diff
PUT /commerce/admin/content-variants/{variantId:guid}Update a variant
DELETE /commerce/admin/content-variants/{variantId:guid}Soft-retire (sets IsActive=false)
GET /commerce/admin/products/{productId:guid}/content-coverage Coverage listing: every authored variant diff, plus the single-group diffs the product's effective options make possible that have no variant. (Full combinatorial coverage is unbounded; single-group gaps are the practical authoring checklist. Multi-group combos are authored on demand and simply appear in the authored list.)

8. Validation rules (authoring)

#Reject when…
V-C1MatchJson references a group or choice the product's effective options do not offer (066 resolution is the authority), or is empty (the empty diff is the default block, not a variant).
V-C2The variant's figure set would produce a mixed panel: for every figure the product's default publishes, the variant must publish it too (nulls only where the default is also null).
V-C3ServingLabel missing — every block must caption which preparation it describes (FR-10.2).
V-C4A second active variant would exist for the same canonical diff (MatchJson canonicalised — sorted keys, sorted arrays — before the uniqueness check).
V-C5Hard-deleting anything: variants soft-retire only. Orders reference selections, and yesterday's shopper may still have the page open — content history stays queryable.
V-C6Default-content upsert removes a figure that any active variant still publishes (would silently flip V-C2 for existing variants; the error names them).

9. Persistence & migration

  1. Configurations in src/Aonik.Commerce/Persistence/Configurations/Catalog/ — indexes per §4; ServingLabel 128, Ingredients/Allergens nvarchar(max), figures decimal(9,2), MatchJson 1024.
  2. DbSets in AonikDbContext + CommerceDbContext, with MapTable entries (ProductContents, ProductContentVariants).
  3. Tool-generated migration on the canonical stream: 
    dotnet ef migrations add AddCommerceProductContent --project src/Aonik.Infrastructure --startup-project src/Aonik.Api
    Expect two new tables, nothing else. Review, apply locally, commit both files. Hand-written migrations are prohibited (CLAUDE.md).

10. Security & tenancy

  • Tenant-scoped entities behind the global query filters; public reads serve active data of Active products only; tenant resolution as per the existing anonymous catalog endpoints.
  • Admin split identical to Spec 066 (AdminWritePolicy / AdminUserPolicy).
  • No PII. Content is public-by-intent data; the sensitivity is correctness, which is what §8 exists for.

11. Testing

  • Unit — diff computation: key-based (equal-price swaps still diff); multi-select array ordering irrelevant; empty diff for all-defaults; diff against per-product default overrides (not the group default).
  • Unit — matching: exact hit; combined-diff miss falls to default with IsStandardPreparation=true even when both single-group variants exist; inactive variant never matches; inherit-vs-replace for text and heating fields.
  • Service — authoring invariants (InMemory, TestTenantProvider): V-C1…V-C6, including V-C6's cross-check naming affected variants.
  • API (CustomWebApplicationFactory): resolution round-trip with URL-encoded selection; default embedded on product DTO; admin authz; tenant isolation.
  • Full-solution dotnet test Aonik.sln before PR.

13. Acceptance criteria

#Given / when / then
A1Variant authored for {portion: full}; customer selects full → the authored figures return with its serving label — not the default figures doubled (Step 2 AC-19).
A2Variants exist for {portion: full} and {protein: salmon} separately; customer selects both → default block returns with isStandardPreparation: true; neither partial is served.
A3Variant for {protein: salmon} replaces the allergen text → resolution for that diff returns the fish declaration; the default's shellfish declaration is nowhere in the response.
A4Selection equal to all defaults → default block, isStandardPreparation: false.
A5Two £0 choices swapped (chicken → prawns, both zero-priced) → still a diff; resolution looks for a variant rather than assuming price-neutral means content-neutral.
A6Multi-select diff {protein: ["chicken","salmon"]} matched regardless of authoring or selection order of the two keys.
A7Authoring a variant referencing a choice the product's narrowing excludes → 400 naming V-C1.
A8Authoring a variant missing a figure the default publishes → 400 naming V-C2 and the missing figure.
A9Deactivated variant's diff selected → default + note; reactivating restores authored resolution with no other write.
A10Coverage endpoint lists every offered single-group diff without a variant; authoring one removes it from the gap list.

14. Open decisions

O1 — Figure precision & units. Figures are unit-fixed by column name (grams, kcal) with decimal(9,2). If a tenant ever needs per-100g alongside per-serving, that is a second figure set, not a unit column — deferred until a real tenant asks.

O2 — Localisation. Ingredients/allergens are single-language text. Multi-locale content would add a locale key to both entities; out of scope until a multi-locale storefront exists.
