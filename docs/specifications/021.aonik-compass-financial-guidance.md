# Summary

AONIK Compass is a personal-finance guidance capability for Payabo that helps users define goals, generate grounded plans, understand how much they can safely spend, and review recommended next actions through Simi. It builds on the existing personal finance agent infrastructure, `CustomerInsightSnapshot`, `UserBrief`, the proposal system, and the existing structured sub-agent pattern.

This specification intentionally defines a **lean V1** that is grounded in the current codebase:

- extend `Goal` rather than creating a parallel goal model
- add a persisted `CompassPlan` because plans need explicit lifecycle and history
- compute safe-to-spend deterministically from existing snapshot and obligation data
- reuse `Proposal` for recommendations rather than introducing multiple new Compass-specific action tables up front
- follow the existing `IDomainAgentDescriptor` + structured-output specialist pattern

V1 does **not** introduce a new daily persistence table, a new feedback-state table, or a learning job until the core goal -> plan -> guidance -> proposal loop is proven.

# Context

## What exists today

AONIK's personal finance domain already provides substantial infrastructure:

**Insight pipeline** (SPEC-015, complete): `CustomerInsightSnapshot` computes a deterministic, versioned per-user financial snapshot covering balances, inflows, outflows, categories, merchants, obligations, budgets, goals, and behavioural signals. `CustomerInsightAiSummary` generates an AI interpretation. Both feed the `UserBrief` that grounds the personal finance agent's context.

**Agent infrastructure**: The `MasterOrchestratorService` routes user intent to domain agents including `personal-finance-agent`, which already delegates to `pf-spending-intelligence-agent` and `pf-obligation-planning-agent`. Specialist sub-agents are registered as `IDomainAgentDescriptor` implementations and, where appropriate, return schema-bound structured outputs.

**Dashboard and cash guidance primitives**: `DashboardService` already computes a practical "available to spend" style figure from liquid balances minus upcoming obligations. `CustomerInsightSnapshotGenerator` already computes cash position, obligations, budgets, goals, and behavioural signals. The current dashboard calculation uses the user's primary currency and does not perform trusted FX normalization, so Compass V1 must make mixed-currency behavior explicit.

**Proposals**: The `Proposal` entity captures proposal type, risk tier as a string, impact summary, payload, status, and approval metadata. Existing frontend tooling includes `display_autopilot_proposal`, and mutation flows currently rely on the `confirmAction` frontend tool by agent instruction and tool usage convention. `Proposal` does not currently include first-class `UserId` or `GoalId` columns, so Compass V1 must define an explicit proposal scoping pattern for current-user retrieval.

**Goals**: The `Goal` entity exists but is minimal: `Name`, `TargetAmount`, `Currency`, `TargetDate`, `ProgressAmount`, `Status`, and `FundingAccountId`. There is no dedicated goal service, goal endpoint, or goal agent tool surface yet.

**Background jobs**: `CustomerInsightSnapshotJob` and `CustomerInsightAiSummaryJob` already run on Quartz using resumable checkpoint-based batching.

**AI audit trail**: `AiRun`, `AiTrace`, and `AiFeedback` already exist and must remain the audit mechanism for Compass AI operations.

## What the problem is

Despite this foundation, the personal finance experience is still reactive.

1. There is no first-class goal management service or API surface for guidance-oriented goals.
2. There is no planning layer that turns a goal plus financial context into a structured, reviewable roadmap.
3. There is no dedicated safe-to-spend service that combines balances, obligations, and plan commitments into a user-facing guidance response.
4. There is no Compass-specific proposal generation flow for turning guidance into recommended actions.
5. The current risk-tier model is inconsistent across the broader platform and should not be partially normalized only for Compass without an explicit platform-level decision.
6. Compass guidance depends on snapshot availability and freshness, but first-run and missing-snapshot behavior is not yet defined for this feature.

## Why it matters now

SPEC-018 identifies advisory, planning, and proactive personal-finance help as a major capability gap. Compass closes that gap best if it starts with a thin, grounded implementation that reuses the current architecture instead of inventing a second planning platform.

# Constraints And Guardrails

- Must not change: Ledger remains the source of financial truth. Orders remain the canonical record of financial service requests.
- Must not change: `CustomerInsightSnapshot` pipeline. Compass reads snapshots and dashboard primitives; it does not duplicate them.
- Must not change: Existing `personal-finance-agent` tools. Compass adds tools; it does not remove or rename current ones.
- Must follow: Anemic entity pattern. Logic stays in services, not entities.
- Must follow: Existing `IDomainAgentDescriptor` specialist-agent pattern, including typed request/response contracts and `OutputSchemaJson` where structured output is required.
- Must follow: `AiRun` audit trail for all AI-generated plans and recommendations.
- Must follow: Single migration stream via `AonikDbContext`.
- Must preserve: Existing `Goal` data. Extend the entity; do not replace it.
- Must preserve: Existing `Proposal` entity. Compass recommendations use proposals; they do not bypass the proposal system.
- Must preserve: Existing `Proposal` schema in V1 unless a separate additive schema change is explicitly approved.
- Must acknowledge current reality: mutation approval is currently enforced by `confirmAction` prompt/tool convention, not yet by universal `ApprovalRequiredAIFunction` wrappers in the codebase.
- Ask for approval before: New NuGet dependencies, new Quartz job schedules, or widening V1 into platform-wide risk-tier normalization.

# Approach

Compass V1 is implemented as **one new specialist planning sub-agent** plus **deterministic domain services** and **minimal new persistence**.

## 1. Goal Extension

Extend `Goal` with nullable Compass programme fields:

```text
GoalType         (string?)  — "cashflow", "savings", "debt_reduction", "purchase"
Strategy         (string?)  — short strategy summary
RiskAppetite     (string?)  — "conservative", "moderate", "aggressive"
Priority         (int?)     — relative priority across goals
MilestonesJson   (string?)  — JSON array of milestone items
ActivePlanId     (Guid?)    — FK to current CompassPlan
```

These fields preserve backward compatibility and allow existing goals to remain valid.

## 2. New Persisted Entity: CompassPlan

`CompassPlan` is the only new required Compass entity in V1 because the plan itself needs lifecycle, versioning, and explicit linkage to its grounding inputs.

```text
Id               (Guid)
TenantId         (Guid)
UserId           (Guid)
GoalId           (Guid)
Version          (int)
Status           (string)   — "Active", "Superseded", "Completed", "Cancelled"
PlanJson         (string)   — structured plan payload
HorizonStartUtc  (DateTime)
HorizonEndUtc    (DateTime)
SnapshotId       (Guid?)
AiRunId          (Guid?)
SupersededById   (Guid?)
```

## 3. New Services

### IGoalService

Add a first-class goal service because Compass needs a supported goal API before it can plan against goals.

- `CreateGoalAsync(...)`
- `UpdateGoalAsync(...)`
- `GetGoalAsync(...)`
- `ListGoalsAsync(...)`

### ICompassPlanService

- `GeneratePlanAsync(Guid goalId, CancellationToken)`
- `GetCurrentPlanAsync(Guid goalId, CancellationToken)`
- `GetPlanHistoryAsync(Guid goalId, CancellationToken)`
- `SupersedePlanAsync(Guid planId, CancellationToken)`

### ICompassGuidanceService

This service computes safe-to-spend and recommendation context **without** introducing a new daily persistence table in V1.

- `GetSafeToSpendAsync(DateTime asOfDate, CancellationToken)`
- `GetGoalGuidanceAsync(Guid goalId, CancellationToken)`
- `CreateCompassProposalAsync(Guid goalId, ..., CancellationToken)`

Service context rules:

- user-facing Compass services resolve the current user via `ICurrentUserProvider` and tenant via `ITenantProvider`, following existing personal-finance service patterns
- if future scheduled or administrative workflows need arbitrary-user execution, that should be a separate internal workflow or service method rather than the default interactive contract

The service reads:

- latest `CustomerInsightSnapshot`
- active `CompassPlan`
- existing obligation sources
- current goal data
- optionally the existing dashboard metrics primitives

Snapshot fallback rules:

- if a current snapshot exists, Compass uses it
- if no current snapshot exists, Compass may generate one on demand using the existing snapshot generator pattern before computing guidance or plan context
- if required source data is still insufficient after snapshot generation, the service returns partial guidance with explicit warnings rather than fabricating a precise safe-to-spend amount

Currency handling rules for V1:

- V1 safe-to-spend is computed only when relevant liquid balances, obligations, and plan commitments can be expressed in a single operating currency
- the operating currency defaults to the user's primary currency using the same heuristic as `DashboardService`
- if required balances, obligations, or plan commitments span multiple currencies without trusted FX normalization, Compass returns warning-based partial guidance instead of a blended amount
- V1 must not silently sum cross-currency amounts into one number

## 4. Risk Tier Handling In V1

V1 does **not** convert `Proposal.RiskTier` to an enum because risk tier is broader than Compass and already appears in multiple modules.

Instead, Compass V1 must:

- use normalized string values: `low`, `medium`, `high`
- centralize mapping/validation in one Compass service or shared helper
- reserve a future platform-wide spec for full enum migration
- treat normalized risk-tier validation as an application concern rather than a schema enum migration

## 5. New Agent

### CompassPlannerAgent (sub-agent: `pf-compass-planner-agent`)

Registered as `IDomainAgentDescriptor` with `AgentType = SubAgent`.

This agent must follow the same pattern as the existing specialist agents:

- typed request DTO
- typed result DTO
- schema contract with `OutputSchemaJson`
- tool wrapper returning both parsed result and serialized JSON

**Input**

- goal details
- latest `CustomerInsightSnapshot`
- current obligations and budgets
- optional household context when available through existing data

**Output**

Structured plan output used to populate `CompassPlan.PlanJson`, including:

- narrative summary
- recommended steps
- suggested amounts and timing
- rationale and confidence
- entity references
- warnings for missing data

## 6. Tools On personal-finance-agent

Add to `PersonalFinanceTools.cs`:

### Read tools

- `pf_list_goals`
- `pf_get_goal`
- `pf_get_goal_plan`
- `pf_get_safe_to_spend`
- `pf_run_compass_planner`

### Mutation tools

- `pf_create_goal_programme`
- `pf_update_goal_programme`
- `pf_generate_goal_plan`
- `pf_create_compass_proposal`

Mutation tools follow the **current** product pattern: the agent must use `confirmAction` before executing the mutation.

Because V1 follows prompt/tool convention rather than a universal hard wrapper, high-risk Compass mutations must also be kept behind explicit mutation flows in services and endpoints. Read-style guidance tools must not directly execute high-risk actions.

## 7. Proposal Model Reuse

Compass recommendations reuse `Proposal`.

V1 proposal scoping rules:

- Compass proposals must use a distinct `ProposalType` namespace such as `CompassRecommendation`
- Compass payloads must include `userId`, and include `goalId` and `planId` when applicable
- current-user Compass proposal retrieval must filter by tenant, `ProposalType`, and payload linkage for the current user, or another explicitly approved additive linkage mechanism
- V1 must not rely on broad free-text payload scanning to discover Compass proposals

V1 proposal payloads should include goal and plan references when applicable:

```json
{
  "userId": "...",
  "goalId": "...",
  "planId": "...",
  "actionType": "savings_transfer",
  "amount": 150.00,
  "currency": "GBP",
  "rationale": "..."
}
```

No separate `CompassActionRecord` is required in V1 unless implementation reveals a real gap in how outcome data is captured.

## 8. Payabo UI

V1 should not overload the current bill-pay dashboard implementation.

Preferred shape:

- add a Compass route or dashboard section backed by Compass DTOs
- show active goals
- show current safe-to-spend guidance
- show latest active plan summary
- show pending Compass proposals

This keeps Compass from being coupled to the existing order-centric dashboard API.
