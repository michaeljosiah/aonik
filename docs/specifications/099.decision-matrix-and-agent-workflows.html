1. Summary

Enable Aonik to discover, create, update, validate, simulate and delete workflow drafts, then propose publication through the existing approval system. Published workflows contain deterministic decision tables that route invoices to the correct authorized reviewer and action. A published revision remains immutable; a running workflow keeps its exact revision and action arguments across approval waits and process restarts.

Expose Gmail read and write actions through the same registered capabilities used by agents and workflow Tool nodes, enabling each action only after its delivery and approval controls are verified. Users may connect their own mailbox; tenants may provision an organizational account with explicit grants. When a required connector, account, consent or grant is missing, Aonik can create a durable connection request and report its real status. A connection request never grants access by itself.

Success means an operator can configure and explain an invoice route, Aonik can perform the complete draft lifecycle, an authorized reviewer can approve the exact domain action, and missing connections can be requested and fulfilled without bypassing tenant policy. The full epic also includes the seven automation areas previously deferred: automatic triggers, complex control flow, richer rules/shared libraries, Gmail writes, automated financial intake, unattended identities and a curated connector marketplace. The initial manual invoice/read-only Gmail pilot is a delivery milestone, not the epic's completion boundary.

Implementation boundaries that remain

  • No arbitrary script/SQL evaluation, unrestricted executable package loading, unbounded loops/recursion or user-supplied egress destinations.
  • No second workflow runtime, scheduler, generic policy engine, ledger or identity provider. Reuse MAF, WorkItem/Quartz, existing approval/authorization services and domain services.

All seven formerly deferred areas are now completion requirements. Their delivery order limits implementation risk; it does not leave them outside the epic. Each capability remains unavailable at runtime until its corresponding tests and controls pass.

4. Constraints And Guardrails

  1. Preserve financial boundaries. Ledger is immutable financial truth; Orders remain business intent. Agents propose; domain services execute. A rule match, workflow publication or connection approval never authorizes a payment or ledger mutation.
  2. Reuse first. Extend WorkflowService, the graph builder, ToolApprovalService, ProposalDispatcher, WorkItem, outbox/inbox, settings, audit, current authorization and editor components. Every proposed new persistence type or abstraction must name the missing capability it supplies.
  3. Keep one representation. The editor draft graph is the authoring source. Published DefinitionJson is its immutable executable snapshot, including decision rows and connection bindings. Shared decision libraries use the same draft/publish/version services with a definition-kind discriminator, not a second matrix persistence engine or editable serialization.
  4. Keep logic plain. Use typed DTOs, small application services and ordinary validation/branching. No generic repository, event-sourcing framework, policy DSL, mediator pipeline or abstract connector hierarchy introduced for this feature. Keep curated package manifests declarative and use ordinary registered handlers.
  5. Add interfaces where they earn their place. Follow existing service interface conventions; use SharedKernel contracts only for actual cross-module consumers and provider boundaries. Keep local helpers concrete/internal.
  6. Fail closed. Enforce tenant, user, permissions, capability availability, connection grants and approval at the server service boundary. Hide unavailable UI actions as convenience, not enforcement.
  7. Respect existing schema rules. Entities remain anemic; use existing AuditableEntity.RowVersion and tenant filters. Configure entities in their owning module and add canonical DbSets. Only EF CLI-generated migrations against AonikDbContext are permitted.
  8. Preserve AI routing and audit. Every actual LLM call uses AiRoutePolicy and records an AiRun. Financially material AI output retains its AiRunId. Deterministic execution does not fabricate an AiRun.
  9. Bound changes. No unrelated dependency upgrades, module rewrite, new queue product or broad UI redesign. Keep existing tenant custom tool allowlists; do not silently expand them.

Implementation instructions: read the linked current code before changing it; deliver the smallest complete vertical slice; record material deviations under Decision Log with a concrete reason; leave requirements open until verified. Resolve routine choices within these constraints without creating an extra approval process.

6.3 State and update semantics

  • Create: duplicate tenant slug is a conflict; POST must not edit an existing workflow. Slug is stable after creation for the pilot.
  • Update: requires expected RowVersion; unknown workflow is not found; stale edits conflict. Return canonical graph and fresh token. UI and agent use the same DTO/service.
  • Validate: drafts may report unresolved connections, but invalid syntax, unknown kinds or malformed references cannot be published. Save and validate remain distinct so a draft can be completed incrementally.
  • Publish: propose the exact draft token and canonical content hash. Authorized approval revalidates and atomically stores the immutable snapshot and active pointer. Editing the draft invalidates an older publish proposal. Hash canonical server DTO serialization, not client whitespace.
  • Retire: approved retirement blocks new runs. A run rechecks retirement before its next effect and stops as Cancelled if retired; already dispatched effects reconcile to their actual outcome. Retirement cannot undo an invoice or payment.
  • Delete: soft-delete an unpublished draft with no executable published version, run or active reference. Preserve any draft-save audit/history; such metadata alone does not prevent deleting an unused draft. Published workflows use retirement; never erase financial or execution history through an agent tool.
  • Rollback: propose activation of an earlier executable snapshot through the same publication handler. Revalidate current capabilities, grants and policy; rollback is not permission to restore revoked access.

Existing saved graphs remain drafts until validated and explicitly published. Preserve their graph data and history metadata; do not invent historical snapshots or activate seeded examples. Keep legacy keyed workflows in an explicit legacy namespace/path so names cannot bypass publication. Update affected clients with the API semantics change.

7. Decision table contract

7.1 Deliberately limited evaluator

  • The foundation hit policy is FirstMatch. Sort rows by unique numeric priority, evaluate in order, select one route. A mandatory default route handles no match.
  • Each row contains an all list of typed comparisons. Support eq, ne, gt, gte, lt, lte, in and isMissing only. OR is expressed as another row. The foundation has no nested boolean tree. T11 adds bounded compound predicates and explicit scoring as defined in section 14; arbitrary scripts, regex and dynamic function invocation remain excluded.
  • Facts come from an allowlisted schema. Live invoice facts are loaded by tenant-authorized domain services from the supplied InvoiceId; users/models cannot replace amount, currency, status or risk checks in live input.
  • Money uses decimal and an explicit ISO currency. Numeric constants serialize invariantly, with monetary values as decimal strings to avoid JavaScript floating-point round trips. No cross-currency comparison or automatic conversion.
  • Schema declares required facts. A missing required fact, invalid value, absent currency configuration or fact-provider failure yields NeedsManualReview/Blocked with a reason before any mutation. Missing optional facts make comparisons false except isMissing; they do not become zero or false facts.
  • String comparisons are ordinal and schema-defined; IDs/enums/currency are normalized by the facts provider. UTC timestamps are typed if a later allowed field needs them.
  • Reject duplicate row IDs/priorities, empty routes and unknown fields/operators. Warn about identical/shadowed rows where cheaply detectable; a full overlap theorem prover is not required.
  • Record the evaluated rows, compared values or protected references, match/default reason and selected route on the decision step. Stop evaluation after the first match.

9. Execution, approvals and recovery

9.1 Trusted execution context and run states

Replace string-only financial routing with a typed context carrying RunId, WorkflowVersionId, actor type/ID, initiating user when present, subject references, verified fact snapshot/version and typed step outputs. Restore tenant/actor execution context from the persisted run in every worker scope; T8 extends this to a real AutomationIdentity without impersonating a user. A persisted identity is not perpetual authorization: recheck membership, roles, module state and connection grants before each continuation/effect. Missing or disabled agents fail with an explicit error, not advisory success text.

Queued -> Running -> Completed | Failed | Cancelled
                  -> WaitingForApproval -> Queued
                  -> WaitingForConnection -> Queued
                  -> WaitingForTime | WaitingForHuman | WaitingForChildren -> Queued
                  -> NeedsAttention

Completed has an outcome such as Issued, NeedsManualReview or Blocked; it does not invent an Invoice Approved state. Rejection/expiry terminates the requested action with a recorded reason. NeedsAttention is used for uncertain effect outcomes or incompatible checkpoints; an operator resolves/reconciles it explicitly.

9.2 Reuse the existing approval boundary

  • Read actions run only after normal authorization. Medium actions require one durable, argument-bound, unexpired decision. High actions produce existing domain Proposals and execute only through the approved dispatcher/handler.
  • Tool nodes must use the same enforcing gate/approval service as agent tools. Invoking a domain method from a workflow is not an exemption. Extract a small shared invocation method from the gate only where necessary; do not implement a second policy engine.
  • For the pilot IssueInvoice step, store a trusted reviewer requirement selected by the published route: current role/permission and optional prohibition on self-approval. Extend ToolApprovalService's requester-equality rule only for these server-created workflow requests. Do not let a caller supply arbitrary reviewer roles to its own request.
  • One authorized reviewer confirmation satisfies the medium action's requirement when it covers the exact IssueInvoice arguments and subject version. Avoid a generic human review followed by a second identical confirmation. Additional distinct domain approvals remain separate.
  • Publication/retirement proposal handlers require WorkflowPublish authority and configured separation of duties. Extend ProposalApprovalPolicy/authorization context for these operations; protect both direct proposal decisions and ToolApprovalRequest decisions.
  • High money actions keep their current classification regardless of invoice amount. No low-value auto-payment rule, connection grant or published workflow may downgrade it.
  • Bind requests to tenant, initiating user, run, node, immutable definition, action contract, arguments hash, subject version and expiry. Revalidate the reviewer and operation at execution. Changed material facts make approval stale; resume must not re-use it with new data.

9.3 Durable continuation without another scheduler

  1. Persist run admission and an outbox wake-up in the same database transaction. Use the existing EnqueueIntegrationEvent/SaveChanges pattern; do not schedule only after committing the run.
  2. An idempotent subscriber schedules the existing WorkItem action handler for the run/continuation identity. Use the existing Worker dispatcher for claiming, heartbeat and recovery. The handler processes until completion, a bounded yield or a durable wait.
  3. Persist WorkflowStepRun and MAF checkpoint state at safe boundaries. Use MAF request/response ports for approvals; request ports transport the wait, while AONIK owns approval authority.
  4. Save waiting state, pending approval/request references and checkpoint before returning. A wait releases the worker and HTTP request. It is successful completion of that continuation work item, not workflow completion; a later wake-up schedules the next continuation.
  5. Approval decisions commit a correlated outbox wake-up with the durable decision. Re-delivery checks run state and already completed steps. Add a small handler for approved workflow continuations; keep callbacks and retries out of the UI.
  6. Connection fulfilment updates readiness and notifies the requester. The pilot requires an explicit Resume after the user sees the exact account; it does not automatically execute held work. The same run/version can resume only if its pinned binding is unchanged.
  7. Persist MAF and checkpoint format versions. An incompatible runtime stops with NeedsAttention; do not interpret old serialized state with a new schema or restart from node one. Runtime upgrades must test old pending checkpoints or drain affected pilot runs first.

Reuse existing outbox/inbox transaction and replay patterns, but verify the complete sequence. Different module DbContexts do not share a transaction merely because they share a physical database. Use the existing owning-context outbox mechanism and idempotent consumer boundary; avoid a fragile synchronous cross-context dual write.

9.4 Idempotency is an action responsibility
