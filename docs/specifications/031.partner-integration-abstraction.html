Spec 031 Status: Draft Size: Large Priority: P1 Domain: Finance / Partners

Partner integration abstraction layer

Defines a partner-agnostic contract for executing money movement through external partners across four services — payout, collection, bill payment, and airtime / data top-up. Today the only provider port is IPaymentProviderGateway (card checkout only) with an inline ResolveProvider switch — nothing for partner transfers, partner-initiated pulls, biller payments, or mobile top-up. This spec adds the connector ports, normalized DTOs / status vocabulary, a capability-aware resolver, and webhook translation contracts — proven by one simulated reference connector wired into DI. Flutterwave is the payout / collection baseline; eTranzact SwitchIt and Interswitch Quickteller are the bill-payment baselines, and Interswitch also anchors airtime / data top-up. All three bill-payment vendors run top-up through the same rails as bill payment, so it is served by the bill-payment port as a distinct service category — not a duplicate port (§5.5). No real vendor implementation is built here. The concrete entity changes and a single tool-generated migration that persist all four services are in scope (§7), with every new and modified table inventoried.

1. Summary

AONIK's Finance module owns "partners (B2B / cross-border money plumbing)" but has no normalized contract for executing money movement through an external partner. The single provider port today — IPaymentProviderGateway — only models card checkout (CreateIntentAsync), is satisfied by one StripeSimulatedPaymentProviderGateway, and is dispatched by an inline ResolveProvider switch inside PublicPaymentService. There is no port for payouts / transfers, partner-initiated collections, bill payments, or airtime / data top-up.

This spec introduces a partner-agnostic abstraction so connectors (Flutterwave, eTranzact, Interswitch, …) can be swapped per deployment via the established "operator-choice provider + factory dispatch" pattern already used for payment gateways and auth providers. Three structurally different vendors collapse onto one small set of ports — that is the proof the abstraction sits at the right level (§4). Airtime / data top-up rides the bill-payment port (every vendor implements top-up on its bill rails), elevated to its own service category for routing and reporting. The deliverables:

  • The abstraction — provider-port interfaces, normalized DTOs / enums, a capability model + resolver, and webhook-translation contracts, all under Aonik.Finance.Contracts.Services.Partners.Connectors.
  • One simulated reference connector implementing all three ports (payout, collection, bill payment — the last also serving airtime top-up), registered in DI through the resolver — mirroring StripeSimulatedPaymentProviderGateway. This proves the contracts compile and route end to end without any network, secret, or vendor dependency.
  • The entity changes + a single migration (§7) that close the gaps in §6 so all four services can be persisted and reconciled — in scope this phase. New and modified entities are tabulated and mapped to gap IDs, and every affected database table is inventoried in §7.4. The migration is tool-generated against AonikDbContext per CLAUDE.md.
Success signals dotnet build Aonik.sln compiles the six contract files, the simulated connector, and the resolver. The simulated connector advertises capability lanes (including an airtime-top-up lane) and returns deterministic fake references; a payout instruction yields a PartnerReference with a non-empty provider reference and a Succeeded status; a bill validate → pay round-trips the ValidationToken; the resolver returns the connector for "Simulated" and throws for an unknown code. The §7 migration is tool-generated against AonikDbContext, applies cleanly with dotnet ef database update, and contains only the new / changed tables. A second vendor would add one connector class — no contract change.

2. Problem

Three concrete shortfalls block partner-executed money movement today:

Concern Today Consequence
Provider port coverage Only IPaymentProviderGateway.CreateIntentAsync (card checkout). No way to express a payout, a partner-initiated collection, a biller payment, or an airtime / data top-up behind a swappable contract.
Provider selection Inline ResolveProvider switch in PublicPaymentService matching a ProviderCode string. No capability-aware routing (“mobile-money payout, KES, Kenya”); selection logic is duplicated per call site.
Async settlement Plaid webhook handler is anonymous + unsigned (AccountLinkEndpoints); no normalized inbound contract. All four partner services settle via callback. There is no translator contract and no idempotent inbox to dedupe / replay them.

A clean abstraction has to do two things at once: present one normalized port per service category that any vendor maps onto, and carry enough vendor-native detail (raw codes, provider references, next-actions) that reconciliation and requery still work. §4 verifies Flutterwave, eTranzact, and Interswitch all satisfy that shape.

3. Scope (in / out)

3.1 In scope

  • New Six contract files under src/Aonik.Finance/Contracts/Services/Partners/Connectors/: common types + base port, payout port, collection port, bill-payment port, webhook translator, resolver (§5).
  • New Normalized vocabulary: PartnerServiceCategory (Payout / Collection / BillPayment / AirtimeTopup), PartnerTransactionStatus, PartnerReference, RawProviderResponse, PartnerConnectorCapability — the single status / reference language every vendor maps onto.
  • Reuse Airtime / data top-up is served by IPartnerBillPaymentConnector (no new port) and surfaced as the AirtimeTopup service category for capability routing and reporting (§5.5).
  • New One SimulatedPartnerConnector implementing all three port interfaces, a SimulatedPartnerWebhookTranslator, and a PartnerConnectorResolver over IEnumerable<IPort> (§5.8).
  • Edit FinanceModule.ConfigureServices — a "Partner Connectors" DI block registering the simulated connector against all three ports plus the translator and resolver.
  • New SimulatedPartnerConnectorTests mirroring StripeSimulatedPaymentProviderGatewayTests — payout / collection / bill + airtime round-trips, capability-based resolution, and resolver lookup.
  • New The entity changes in §7 — new and modified entities + their IEntityTypeConfiguration<T>, DbSets on AonikDbContext (and the FinanceDbContext read/write path), backing all four services.
  • New One migration, tool-generated against AonikDbContext (single stream, per CLAUDE.md), reviewed to contain only the §7 tables, and verified to apply with dotnet ef database update.

3.2 Out of scope

  • Real Flutterwave / eTranzact / Interswitch connectors. No credentials, HTTP clients, request signing, or vendor SDKs. The simulated connector is the only implementation.
  • Inbound webhook endpoints + processing. The PartnerWebhookEvent inbox table is created in §7, and the translator contract is defined; wiring an inbound FastEndpoints route to verify, persist, and dispatch callbacks into domain state is follow-up work.
  • Application-service orchestration. Services that call these ports and write the new entities (a PayoutService, a partner CollectionService, a BillPaymentService) are not in this spec — only the ports and the persistence they will use.
  • Routing-rule evaluation. The resolver exposes capability-aware TryResolve* overloads, but the engine that reads RoutingRule.ConditionsJson to pick a connector is deferred.

5. Abstraction design

5.1 Namespace & file layout

Contracts mirror the in-repo convention from Contracts/Services/Payments/IPaymentProviderGateway.cs: each interface and its DTO records live together in one file, DTOs are records with positional params, and the connector self-describes via a string ProviderCode.

src/Aonik.Finance/Contracts/Services/Partners/Connectors/ PartnerConnector.cs common: enums, reference, raw, capability, base port IPartnerPayoutConnector.cs payout port + DTOs IPartnerCollectionConnector.cs collection port + DTOs IPartnerBillPaymentConnector.cs bill-payment port + DTOs IPartnerWebhookTranslator.cs inbound-callback normalization IPartnerConnectorResolver.cs selection by ProviderCode and by capability src/Aonik.Finance/Services/Partners/Connectors/ SimulatedPartnerConnector.cs internal: implements all three port interfaces SimulatedPartnerWebhookTranslator.cs internal: IPartnerWebhookTranslator PartnerConnectorResolver.cs internal: IPartnerConnectorResolver

5.2 Common types — PartnerConnector.cs

One status vocabulary, one reference shape, one raw-response envelope, and a capability descriptor. Every category port extends IPartnerConnector so the resolver can discover what a connector supports. 

namespace Aonik.Finance.Contracts.Services.Partners.Connectors;

// Airtime / data top-up is a distinct service category but rides the bill-payment port (§5.5).
public enum PartnerServiceCategory { Payout, Collection, BillPayment, AirtimeTopup }

// Single normalized vocabulary every vendor status maps onto.
public enum PartnerTransactionStatus
{
    Pending, Processing, RequiresAction,
    Succeeded, Failed, Reversed, Expired, Unknown
}

// Our idempotent client ref (tx_ref / clientRef) + the provider's ref (flw_ref / paymentRef).
public sealed record PartnerReference(string ClientReference, string? ProviderReference);

// Vendor-native code / message / raw payload, preserved for audit, mapping, and requery.
public sealed record RawProviderResponse(string? Code, string? Message, string? PayloadJson);

public sealed record PartnerConnectorCapability(
    PartnerServiceCategory Category,
    IReadOnlyCollection<string> Countries,
    IReadOnlyCollection<string> Currencies,
    IReadOnlyCollection<string> Methods);

public interface IPartnerConnector
{
    string ProviderCode { get; }
    IReadOnlyCollection<PartnerConnectorCapability> Capabilities { get; }
}

5.5 Bill-payment port — IPartnerBillPaymentConnector.cs

The eTranzact catalog → validate → pay → requery flow. ValidationToken carries the short-lived billQueryRef / paymentRef from validate into pay; Token on the payment result carries vend artefacts (e.g. prepaid-electricity tokens).

    Money Amount, string? ValidationToken,
    PartnerServiceCategory? ServiceCategory,
    IReadOnlyDictionary<string, string>? Inputs);

// Token carries e.g. prepaid-electricity vend tokens.
public sealed record BillPaymentResult(
    PartnerReference Reference, PartnerTransactionStatus Status,
    string? Token, RawProviderResponse Raw);

public sealed record BillPaymentStatusResult(
    PartnerReference Reference, PartnerTransactionStatus Status,
    string? Token, RawProviderResponse Raw);
Airtime / data top-up reuses this port Airtime and data top-up are not a separate port. All three vendors run top-up through their bill rails — Flutterwave bills type = AIRTIME / DATA_BUNDLE, eTranzact's recharge bill category, and Interswitch's categoryId = 4 telco billers paid via the same POST /Transactions as any bill. The interaction shape is identical: catalog → (optional) validate → pay → requery. So a telco is just a BillerCatalogEntry, a data bundle is a BillItem, the MSISDN is the CustomerId, and a recharge PIN / electricity units come back as BillPaymentResult.Token. The guiding rule: a port is the interaction shape; a category is the service offered. Top-up keeps the bill-payment port but is elevated to its own PartnerServiceCategory.AirtimeTopup so it can be routed, reported, and ledgered as a distinct service (and so a connector can advertise top-up without advertising general bill payment). A connector signals support by adding an AirtimeTopup capability lane; nothing on the interface changes. Each BillerCatalogEntry now carries a ServiceCategory so the catalog is self-describing (a telco entry reports AirtimeTopup), and BillPaymentInstruction carries an optional ServiceCategory so the persisted record is unambiguous — the connector still routes purely by biller / item code.

5.6 Webhook translator — IPartnerWebhookTranslator.cs

All four services settle asynchronously via partner callbacks. The translator is per-provider: it verifies the signature and lifts the raw envelope into one normalized PartnerWebhookEvent carrying the category, reference duality, and normalized status.

5.7 Connector resolver — IPartnerConnectorResolver.cs

A single selection point — an improvement on the inline ResolveProvider switch. Direct lookups match a ProviderCode (case-insensitive, mirroring PublicPaymentService.ResolveProvider); the TryResolve* overloads pick a connector whose Capabilities satisfy a PartnerConnectorQuery — the seam a routing engine will later drive. Because airtime rides the bill-payment port, an airtime lane is resolved through TryResolveBillPaymentConnector with Category = PartnerServiceCategory.AirtimeTopup — the same port, selected by category. 

namespace Aonik.Finance.Contracts.Services.Partners.Connectors;

public interface IPartnerConnectorResolver
{
    IPartnerPayoutConnector ResolvePayoutConnector(string providerCode);
    IPartnerCollectionConnector ResolveCollectionConnector(string providerCode);
    IPartnerBillPaymentConnector ResolveBillPaymentConnector(string providerCode);
    IPartnerWebhookTranslator ResolveWebhookTranslator(string providerCode);

    bool TryResolvePayoutConnector(
        PartnerConnectorQuery query, out IPartnerPayoutConnector? connector);
    bool TryResolveCollectionConnector(
        PartnerConnectorQuery query, out IPartnerCollectionConnector? connector);
    bool TryResolveBillPaymentConnector(
        PartnerConnectorQuery query, out IPartnerBillPaymentConnector? connector);
}

public sealed record PartnerConnectorQuery(
    PartnerServiceCategory Category, string? Country, string? Currency, string? Method);

5.8 Simulated connector + DI

SimulatedPartnerConnector is an internal class implementing all three port interfaces, exactly as StripeSimulatedPaymentProviderGateway implements IPaymentProviderGateway. ProviderCode => "Simulated", it advertises a few capability lanes (Payout NG/NGN bank + mobile-money, Collection NG/NGN card, BillPayment NG, AirtimeTopup NG), and it returns deterministic fake references and Succeeded / RequiresAction outcomes — no network, no secrets. 

// FinanceModule.ConfigureServices — "Partner Connectors" block.
// One concrete instance backs all three ports; forwarding registrations keep
// the simulated connector a single object while satisfying each port list.
services.AddSingleton<SimulatedPartnerConnector>();
services.AddSingleton<IPartnerPayoutConnector>(
    sp => sp.GetRequiredService<SimulatedPartnerConnector>());
services.AddSingleton<IPartnerCollectionConnector>(
    sp => sp.GetRequiredService<SimulatedPartnerConnector>());
services.AddSingleton<IPartnerBillPaymentConnector>(
    sp => sp.GetRequiredService<SimulatedPartnerConnector>());
services.AddSingleton<IPartnerWebhookTranslator, SimulatedPartnerWebhookTranslator>();
services.AddSingleton<IPartnerConnectorResolver, PartnerConnectorResolver>();
Note PartnerConnectorResolver injects IEnumerable<IPartnerPayoutConnector>, IEnumerable<IPartnerCollectionConnector>, IEnumerable<IPartnerBillPaymentConnector>, and IEnumerable<IPartnerWebhookTranslator>, then matches on ProviderCode for direct lookups and on Capabilities for the TryResolve* overloads — the same injected-list pattern as the existing gateway resolution. A real vendor is added by registering one more connector against the relevant port(s); no resolver change.

6. Entity-model gap analysis

How well today's entities can back payout / collection / bill payment / airtime top-up through these ports. Severity = impact on covering the four services. This section reports; §7 designs the fix.

6.1 Payout

#GapWhereSev
P1 Payout is too thin (Amount, Currency, DestinationExternalAccountId, PartnerId, Status). No ConnectorId, no ClientReference / idempotency, no ProviderReference (needed for requery / recon), no DebitCurrency / FX, no Fee, no Narration, no FailureReason / raw response, no order-item fulfilment link. Payout.cs High
P2 No structured destination. DestinationExternalAccountId is a single Guid; it can't express bank (branch code) vs mobile-money (MSISDN + network) vs wallet. The PayoutDestination hierarchy has nowhere to persist. — High
P3 No saved-recipient / external-account entity. Flutterwave beneficiaries + name-enquiry result (AccountName) have no home; DestinationExternalAccountId references a type that does not exist. Entities/Partners/* High
P4 No bank / institution directory. Each partner has its own bank codes (Flutterwave 044, eTranzact codes); nothing maps an AONIK institution to per-connector codes. — Med
P5 No payout reversal / recall modelling. Refund is collection-side (PaymentId). Failed transfers that auto-reverse the wallet can't be represented against the ledger. Refund.cs Med

6.2 Collection

#GapWhereSev
C1 No first-class partner Collection record mirroring Payout. PaymentIntent / Payment cover card checkout but not a partner-initiated pull (mobile-money / bank-transfer / USSD) with async settlement. Entities/Payments/* High
C2 PaymentIntent lacks partner linkage: no ConnectorId, no ClientReference, no ProviderReference (only Payment has provider fields), no method-specific data (network / MSISDN). PaymentIntent.cs High
C3 Nowhere to persist a "next action" (redirect URL / USSD code) returned at initiation and relayed to the payer. — Med
C4 No inbound webhook inbox. The Plaid webhook is anonymous + unsigned. Partner callbacks need an idempotent event store (ProviderCode, EventType, ProviderReference, ClientReference, RawPayload, SignatureValid, ProcessedAt) keyed for replay / dedupe. Endpoints/Admin/Accounts/* High
C5 No partner-collection refund persistence. IPartnerCollectionConnector.RefundCollectionAsync returns a CollectionRefundResult (provider reference, normalized status, raw response), but Refund is thin (PaymentId, Amount, Currency, Status, Reason) — no ConnectorId, no ClientReference / idempotency, no ProviderReference, no FailureReason / raw response, and it links only to a card Payment, not the partner PaymentIntent collection path. The refund outcome is homeless. Symmetric to P5 (payout reversal). Refund.cs High

6.3 Bill payment & airtime top-up

#GapWhereSev
B1 No connector↔biller code mapping. CatalogBiller.CorrespondentPartnerId links a biller to one partner, but partner-specific codes (Flutterwave biller_code / item_code vs eTranzact billId / productId) aren't stored — the same logical biller can't route to multiple partners. Core blocker for a multi-partner abstraction. CatalogBiller.cs, CatalogBillerService.cs High
B2 Validation result isn't persisted. The validate → pay handshake produces a short-lived ValidationToken (eTranzact billQueryRef) + resolved customer name / outstanding amount that must carry into payment; RequiresValidation flags it but there is no entity to store the result / expiry. CatalogBillerService.cs High
B3 CatalogBillerService lacks an explicit AmountType (Fixed vs Variable) and FixedAmount; fixed-price items (a specific data bundle) are only implied by Min / Max. CatalogBillerService.cs Low
B4 No executed bill / airtime transaction entity. The port returns a BillPaymentResult carrying a vend Token (prepaid-electricity units, recharge PIN), a ProviderReference, and a status, but there is nowhere to persist the executed transaction — the bill / airtime analogue of Payout. The vend token, provider ref, and outcome are homeless, so requery, reconciliation, and ledger fulfilment can't bind to a stored record. Entities/Payments/* (none) High
A1 Airtime / data top-up has no first-class service representation. OrderType has no airtime value, no AirtimeTopup service category is persisted, and nothing distinguishes a telco top-up from a generic bill at the order / reporting / ledger layer. (Telcos themselves can already be modelled as billers — see §7.) OrderType.cs Med

6.4 Cross-cutting

#GapWhereSev
X1 Transmission is payout-only (PayoutId) and has no ProviderReference (only LastError). Collections and bill payments have no attempt / transmission record; reconciliation can't store the provider txn id. OrderFulfilmentRef shares the same limitation — it links an order only to a PayoutId, so a collection or bill / airtime payment can't be tied back to the order that requested it. 7. Proposed entity changes

The concrete schema work that closes §6, expressed as new and modified entities. Each row names the gap ID(s) it resolves. This is in scope this phase — the entities, their IEntityTypeConfiguration<T>, the DbSets, and a single migration are all delivered here, not deferred. Every change follows the CLAUDE.md workflow: edit the entity + IEntityTypeConfiguration<T>, add the DbSet to AonikDbContext (and the FinanceDbContext read/write path), then tool-generate one migration against AonikDbContext (the single migration stream) — never hand-author it. All new tables take the Ank prefix and inherit AuditableEntity. Tenant scoping is per-entity, not blanket: tenant-owned tables implement ITenantScoped (non-null TenantId), while canonical / ingestion tables — FinancialInstitution (a shared directory) and PartnerWebhookEvent (an inbound inbox written before a tenant is resolved) — are global (AuditableEntity + nullable TenantId). Global scoping here is a query-filter concern, not IsGlobalEntity(): that hook only governs write-time tenant stamping for ITenantScoped types whose TenantId is Guid.Empty (it is consulted only inside EnforceTenantOnWrites(), which iterates ChangeTracker.Entries<ITenantScoped>()) and is a no-op for nullable-tenant AuditableEntity types that don't implement ITenantScoped. Each instead follows the matching in-repo precedent: FinancialInstitution is a tenant-overridable directory like ReferenceDataItem / Country — registered via ApplyNullableTenantQueryFilter(modelBuilder, typeof(FinancialInstitution)) and excluded from the soft-delete filter, so global (null-tenant) rows are visible to every tenant; PartnerWebhookEvent is a purely global inbox like FinancialWebhookEvent — no tenant query filter at all, since rows land before a tenant is resolved. Each entity's scope is marked in Table A. §7.4 inventories every table the migration creates or alters.

Load-bearing first If the schema work is staged, land these first — they are what actually lets all four services execute through swappable partners: B1 (ConnectorBillerMapping), B4 (PartnerBillPayment — the executed bill / airtime record), P1 / P2 (Payout shape + destination), C1 / C2 (PaymentIntent partner linkage), and C4 + X1 (PartnerWebhookEvent inbox + generalized Transmission / OrderFulfilmentRef).

Sensitive-data storage rule Raw destination identifiers — full account number, MSISDN, wallet id — are never persisted in plaintext. ExternalPayoutAccount stores a masked display identifier (e.g. last-four) plus the connector's reusable ProviderBeneficiaryId token; when execution needs the full value it is supplied transiently on the PayoutInstruction DTO or held behind a vault reference (VaultRef), not as a column — mirroring the verified Account / PartyAccount MaskedIdentifier + ProviderAccountReference convention. Likewise every RawResponseJson / RawPayload column (Payout, Transmission, PartnerBillPayment, PartnerWebhookEvent) is redacted of PANs / MSISDNs / secrets before persistence — it is an audit trail of vendor codes and status, not a store of cardholder data. The same holds for a collection's payer MSISDN on PaymentIntent, persisted as MaskedPhoneNumber with the full number carried only on the transient CollectionInstruction. Closes X6.
Why new entities, not reuses Each new entity was checked against an existing type that looked similar; they are kept separate for concrete reasons, not by oversight:
  • ExternalPayoutAccount vs Platform's PartyAccount (AF1). PartyAccount is a party-owned funding / identity account in the Platform module; Finance cannot reference it directly (no cross-module entity refs). The payout destination is connector-facing, so it lives in Finance alongside the Payout it backs and links to the beneficiary through an optional BeneficiaryPartyId — a soft Guid reference to the Platform Party (read via PartyReadModel), exactly as Order.PayerPartyId / PaymentIntent.PayeePartyId reference parties. It is a Guid rather than an EF navigation precisely because of the module boundary, and nullable because a connector can mint a destination from a name-enquiry result alone, before any Party exists.
  • PartnerWebhookEvent vs FinancialWebhookEvent (AF2). Same shape, different correlation. FinancialWebhookEvent keys on Plaid connection references; the partner inbox keys on partner ServiceCategory + ClientReference + SignatureValid and is deduped by provider event id / payload hash. Both copy the same global, nullable-TenantId tenancy model.
  • FinancialInstitution vs ReferenceDataItem / AccountConnection (AF3). ReferenceDataItem is generic Type/Code/DisplayName lookup data, and AccountConnection.InstitutionName is a free-text Plaid label — neither is a typed institution directory that per-connector codes can FK onto. FinancialInstitution is Finance-owned partner-routing data; it borrows ReferenceDataItem's global, nullable-TenantId scoping precedent.

10. Open decisions

Open Collection: extend PaymentIntent vs new entity. §7 Table B takes the pragmatic path — add partner-linkage fields to PaymentIntent (C1 / C2 / C3) rather than introduce a dedicated partner Collection entity mirroring Payout. Extending keeps one intent record per inflow and avoids a parallel lifecycle; a dedicated entity gives collections the same first-class shape as payouts. The collection refund path (C5) follows the same fork and the same chosen resolution — §7 extends Refund rather than adding a parallel CollectionRefund entity. Decide before the §7 entities are implemented and the migration is generated this phase.
Resolved OrderType: service intent, not rail. OrderType carries the service only — Payout, Collection, BillPayment, AirtimeTopup, Remittance. The rail / method (Bank / MobileMoney / Wallet / Card) is modelled on the execution entity instead: Payout.DestinationType (and ExternalPayoutAccount.DestinationType) for outflows, PaymentIntent.CollectionMethod for inflows. Airtime is the sharpest case for the split — a distinct service that runs on the bill rail — mirroring the port/category split in §5.5. This keeps OrderType a clean intent axis and avoids a combinatorial service×rail enum. (A flat service×rail enum was the rejected alternative.)
Resolved Target linkage: typed FKs, not a polymorphic pair. Transmission and OrderFulfilmentRef link to their target via typed nullable FKs (PayoutId? / PaymentIntentId? / PartnerBillPaymentId?) guarded by a DB CHECK that exactly one is set. A polymorphic TargetType + TargetId pair was rejected: it cannot carry a real foreign key, so it drops referential integrity and cascade behaviour and pushes target resolution into application code. Typed FKs cost three nullable columns and one check constraint but keep the database the source of integrity truth.
Resolved Payout destination → beneficiary link: a nullable soft Guid ref, role optional. ExternalPayoutAccount links to the beneficiary through a nullable BeneficiaryPartyId — a soft Guid reference to the Platform Party (read via PartyReadModel), the same convention Order.PayerPartyId / PaymentIntent.PayeePartyId already use; a Guid, not an EF navigation, because Party lives in another module. Beneficiary is a party role (PartyRoles.Beneficiary, assigned via PartyRoleAssignment), not a PartyType — so one party can be a customer and a beneficiary at once (two role rows, one Guid). The payout path traverses the FK only; assigning the Beneficiary role is optional and can be layered on later for listing / permissioning. (An orphan destination with no party link — the prior draft — and a hard cross-module FK were both rejected.)
Open Status storage: string vs CLR enum column. X3 proposes PartnerTransactionStatus as the vocabulary. Persisting it as a string keeps parity with Order / Payment status conventions and is migration-tolerant; persisting as an int-backed enum is tighter but couples the DB to enum ordering. Recommend string-backed for consistency with existing entities.
Resolved Collection status: a separate column, not PaymentIntent.Status. The partner outcome vocabulary (PartnerTransactionStatus) is written to a new PaymentIntent.CollectionStatus field; the existing Status column is left as the PaymentStatus lifecycle it already is. Reason: PaymentService.CapturePaymentAsync / CancelPaymentAsync parse Status with Enum.TryParse<PaymentStatus> and throw on an unknown value, and the partner statuses (Processing, RequiresAction, Succeeded, Reversed, Expired) are not PaymentStatus members — overloading the column would break capture / cancel. Two columns keep the funding lifecycle and the partner-settlement state independent. (Overloading Status with both vocabularies was the rejected alternative.)
Resolved Abstraction altitude. Three structurally different vendors — Flutterwave's transfer / charge / bill model, eTranzact's catalog → query → pay flow, and Interswitch Quickteller's category → validate → pay → requery — all collapse onto the same three ports and one reference / status vocabulary (§4). That confirms the ports are neither vendor-shaped nor over-abstracted. The four services (payout, collection, bill payment, airtime top-up) need only three ports.
Resolved Airtime / data top-up is not a new port. All three vendors run top-up on their bill rails with the identical catalog → (validate) → pay → requery shape, so it is served by IPartnerBillPaymentConnector — a port is the interaction shape, a category is the service offered (§5.5). It is elevated to PartnerServiceCategory.AirtimeTopup for routing, reporting, and ledgering, and persisted via the PartnerBillPayment entity's ServiceCategory. No duplicate port, no parallel DTO set.
