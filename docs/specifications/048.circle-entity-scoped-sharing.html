Spec 048 Status: Draft (Rev 1) Size: Large Priority: P2 (Simi M5) Domain: PersonalFinance / Simi

The Circle — entity-scoped sharing & the Support Statement

"Shared safely": invite the people who share the load — including those who have never installed the app — to see a defined slice of your records. A partner sees everything; a sibling sees the co-owned flat; the property manager sees that asset's documents only, with no amounts anywhere. Extends Spec 020's households, which today share whole bank accounts with already-registered users and have no scoping or amount-masking. This spec adds a CircleGrant model, a single fail-closed visibility filter, link/email/phone invites that provision on accept, and the Support Statement proof projection. The heaviest and most security-sensitive of the Simi specs. Implements Simi readiness plan §5.6 (and Phase D's proof projection).

This is a security spec, not a UI nicety The "documents-only member sees no amounts anywhere" rule is a security property. It must be enforced by one central server-side filter and proven by a test logged in as that member asserting every amount-bearing field is absent — the same fail-closed rigour Spec 042 applied to connector credentials. A leaked total is a trust breach, not a cosmetic bug.

1. Summary

The Circle is how a cross-border household carries the load together — and the only growth channel Phase 1 needs (every invite lands Simi in the hands of exactly the right next user). It needs three things the current household model cannot do: invite someone who is not yet a registered user (WhatsApp-first, by link); scope a member to specific people/assets rather than everything; and a documents-only role that shows an asset's paperwork while hiding every amount. This spec layers a CircleGrant over the existing household container, enforces it through one visibility filter, and adds the Support Statement — the proof artifact a member, an accountant, or a consulate can trust.

Success signals Fola invites her brother Seyi by a shared link; he installs, accepts, and sees the Surulere flat (co-owner scope) and nothing else of her life. She invites Mr Bello, the property manager, who accepts and sees the flat's documents only — never one amount Fola sends Mum, and never will. Seyi logs a ₦120,000 repair; it appears on Fola's Today with his name. She exports Mum's Support Statement: a dated PDF, 12 payments, £2,400, receipts appended — in the accountant's inbox four minutes after his email.

2. Problem & current state

Confirmed against the tree — the readiness review's "materially optimistic" row:

  • The share unit is a whole bank account. PersonalAccountService.ShareAccountWithHouseholdAsync sets account.HouseholdId; every accepted member then sees that account's transactions and amounts. There is no way to share a person or an asset.
  • No scoping field. HouseholdMember has Role (Owner/Manager/Viewer, HouseholdRoles) and a PermissionsJson string that is parsed and normalised but never enforced in any query path. There is no ScopedEntityId, no visibility level, no amount mask — access is all-or-nothing within a household.
  • Invites require a registered user. InviteHouseholdMemberEndpoint takes a Guid UserId; HouseholdService.EnsureUserExistsWithPersonalProfileAsync throws "User not found" if the invitee has not registered. There is no token / link / email / phone path for a stranger to accept and join.

So the household gives us a container and an invite lifecycle skeleton — and nothing else the Circle needs.

3. Scope (in / out)

3.1 In scope

  • New A CircleGrant entity: member, scope (all | entities | docsOnly), entity ids, a no-amounts flag (§4).
  • New A single, fail-closed visibility filter all shared reads pass through (§5).
  • New Link / email / phone invites that provision an account + grant on accept (§7).
  • Edit Re-point the share unit from accounts to CareEntities (§8).
  • New The Support Statement compose projection (§9).

3.2 Out of scope

  • Money movement. The Circle shares records; no member can move funds.
  • The PDF render. The Support Statement PDF is produced client-side (mobile printing/pdf) from the compose projection; this spec ships the data, not the document.
  • The statement verification page (simi.app/verify/…) — the code is printed now; the page is Phase 2.
  • WhatsApp delivery of invites/summaries — a fast-follow channel; the invite link rides the OS share sheet (WhatsApp-first) today.

4. The CircleGrant model new

Per readiness Decision D4, keep Household as the container and add a grant per member that defines exactly what they see: 

public class CircleGrant : AuditableEntity, ITenantScoped
{
    public Guid   TenantId  { get; set; }
    public Guid   OwnerUserId  { get; set; }   // whose records are shared
    public Guid?  MemberUserId { get; set; }   // null until the invite is accepted (§7)
    public Guid   HouseholdId  { get; set; }   // the container (Spec 020)

    public string Scope        { get; set; } = "entities"; // all | entities | docsOnly
    public string EntityIdsJson{ get; set; } = "[]";       // CareEntity ids for scope=entities|docsOnly
    public bool   NoAmounts    { get; set; }               // true for docsOnly; hides every amount

    public string Status       { get; set; } = "pending";  // pending | active | revoked
}

Scope + NoAmounts together express the three presets (§6). The legacy HouseholdMember.Role/PermissionsJson remain for back-compat but the grant is authoritative for Simi visibility — the never-read permissions string finally gets a real successor.

5. The visibility filter the crux

Every read of another user's shared data — Today, an entity profile, a commitment list, payment logs, documents, a statement — passes through one ICircleVisibility resolver. It is the single place the security property lives; no per-endpoint ad-hoc checks. 

public interface ICircleVisibility
{
    // The active grant for (memberUserId → ownerUserId), or null if none.
    Task<CircleGrantView?> ResolveAsync(Guid ownerUserId, CancellationToken ct = default);
}

// Applied centrally:
//   scope=all       → owner's entities (+ their logs/commitments/documents)
//   scope=entities  → ONLY EntityIds (+ their logs/commitments/documents)
//   scope=docsOnly  → ONLY EntityIds' DOCUMENTS; logs, commitments, totals, amounts all EXCLUDED
//   NoAmounts=true  → every amount-bearing field stripped at projection time (defence in depth)
Fail closed No grant → no access (404, not 403 — existence not revealed). An unknown scope value → deny. A docsOnly response is built from a document-only projection that never joins payment logs or totals — so there is no amount in the object graph to leak, and NoAmounts is belt-and-braces over that. The default for every new shared surface is "invisible unless a grant explicitly includes it."

6. The three scope presets

PresetGrantSeesExample
Everythingscope=allAll of the owner's entities, commitments, logs, documents, totals.Partner (Dan)
Specific people/assetsscope=entities, EntityIds=[…]Only the named entities, in full (incl. amounts).Sibling co-owner (Seyi → the flat)
Documents onlyscope=docsOnly, EntityIds=[…], NoAmounts=trueOnly the named entities' documents — no amounts, anywhere.Property manager (Mr Bello → the flat's docs)

The invite flow picks scope first, then entities if scoped — and the invite preview shows exactly what the member will see, as a rendered miniature of their view (rebuild spec §7.8). Revoke is one tap (Status=revoked), always.

7. Non-user invites new

Per readiness Decision D5, an invite must reach someone with no account (WhatsApp-first reality):

create invite → CircleInvite { token (signed, opaque), ownerUserId, scope, entityIds, noAmounts, channel?(email|phone|link), expiresAt } → owner shares the link via the OS sheet (WhatsApp, etc.) accept(token) → if invitee unregistered: run existing registration + OTP (Spec 001) → new user → bind CircleGrant.MemberUserId, set Status=active, attach to the household → consume the token (single-use, expiry-checked)

The token is signed and single-use; acceptance reuses the existing identity registration + email/phone OTP flow (Spec 001) — no shadow users, no pre-provisioning. Email/phone are optional hints for delivery; the link itself carries the grant. A member on the free tier can accept (rebuild spec §7.8 acceptance).

8. Re-pointing the share unit edit

Today sharing keys on account.HouseholdId (a whole bank account). Simi shares CareEntities. The grant's EntityIds become the unit; the visibility filter resolves an entity's commitments, logs, and documents (Specs 043–046) for the member. Bank-account sharing (Spec 020) is unchanged and orthogonal — a household can still share accounts for the PFM features; the Circle simply shares a different, keeper-shaped unit. A member's logged act (Seyi's ₦120,000 repair) is a PaymentLog on a shared entity, attributed to him, surfacing on the owner's Today.

9. The Support Statement new — the proof

Phase D is "the circle and the proof." The Support Statement is the proof artifact: one tap turns a relationship into evidence (rebuild spec §7.9). The backend contribution is a compose projection; the PDF is client-side. 

GET /personal-finance/care-entities/{id}/statement?from=&to=
public record StatementData(
    CareEntityRef Entity, DateTime From, DateTime To, string? PreparedFor,  // date-only semantics
    IReadOnlyList<StatementRow> Rows,           // date · description · channel · amount(original ccy) · receiptRef
    IReadOnlyList<CurrencyTotal> Totals,        // per-currency, never a converted grand total
    IReadOnlyList<DocumentRef> ReceiptAppendix, // for the PDF appendix
    string VerificationCode);                    // printed now; verify page is Phase 2
  • Per-currency totals, never fabricated. "12 payments totalling £2,400.00" — and a separate line for any other currency. No conversion (Spec 043 §9).
  • Corroboration column reserved. Rows whose PaymentLog has CorroborationStatus=confirmed (Spec 045) carry "verified against linked account" — the column is in the projection from day one so early statements don't look inferior later.
  • Free tier: one export ever (taste it); paid: unlimited — the paywall moment is a client gate over this projection.

10. Enforcement & testing

The no-amounts guarantee gets Spec-042-grade treatment:

  • One filter, centrally applied — not per-endpoint. Every shared-read endpoint resolves ICircleVisibility first; a new shared surface added later inherits the default-deny.
  • A docs-only projection that cannot carry amounts — built from documents alone, never joining logs/totals — so the guarantee holds structurally, with NoAmounts as defence in depth.
  • A logged-in-as-member test asserting that for a docsOnly grant, every amount-bearing field across Today, the entity profile, logs, commitments, and the statement endpoint is absent or 404 — the explicit security assertion (acceptance §14).
  • Revocation is immediate — a revoked grant denies on the next request (no cached visibility).

11. Persistence & migration

  • New tables CircleGrant and CircleInvite → dbo.AnkCircleGrants / dbo.AnkCircleInvites via MapFinanceTable (AonikDbContext) + MapTable (PersonalFinanceDbContext); DbSets on both contexts (every new DbSet lives on the canonical AonikDbContext, CLAUDE.md); configs with indexes on (TenantId, OwnerUserId, MemberUserId, Status) and a unique index on the invite token.
  • No backfill. Existing households/accounts are untouched; the Circle is additive. (Existing household members keep their account-sharing; they gain Circle grants only when an owner creates one.)
  • Tool-generated migration only against AonikDbContext (CLAUDE.md).

12. Security

  • The no-amounts property (§5, §10) is the headline guarantee, structurally enforced and explicitly tested.
  • Tenant + owner scoping. A grant binds OwnerUserId within a tenant; a member only ever sees what an explicit, active grant includes; cross-tenant grants are rejected.
  • Single-use, expiring invites; signed opaque tokens; acceptance through the standard registration + OTP path (no privilege escalation, no shadow accounts).
  • Revoke one-tap, effective immediately. Every profile shows "Shared with"; every member screen shows "Can see" (rebuild spec §7.8) — read from the same grants.
  • Audit. Grant create / accept / revoke and statement export are audited (who shared what scope with whom; who exported which entity's statement).

  8. Tests (§14) — including the logged-in-as-docsOnly no-amounts assertion.

14. Acceptance criteria

  • Non-user invite. An owner invites by link; an unregistered invitee accepts, registers via OTP, and is bound to an active grant — no pre-existing account required.
  • Entity scope. A scope=entities member sees exactly the named entities (full, incl. amounts) and 404s on every other entity.
  • Documents-only, no amounts — the security assertion. Logged in as a docsOnly member, no amount-bearing field is present on any surface (Today, profile, logs, commitments, statement) — the member sees the named entities' documents and nothing else; asserted field-by-field.
  • Shared act. A member's logged payment on a shared entity surfaces on the owner's Today, attributed to the member.
  • Statement. Compose returns per-currency totals (never converted), a receipt appendix, the reserved corroboration column, and a verification code; free tier allows one export, paid unlimited (client gate over the projection).
  • Revoke. Revoking a grant denies the member on the next request immediately.
  • Build & migration. dotnet build green; tool-generated migration adds AnkCircleGrants + AnkCircleInvites only; the visibility filter is the single enforcement point (architecture/integration test).

15. Open decisions

  • O1 — Member-write scope. Can a scope=entities co-owner log on a shared entity (Seyi logs the repair), or only read? Leaning yes, log-only for entity-scoped members (no edit/delete of others' records); docsOnly is read-only. Finalise the write matrix in implementation.
  • O2 — Household vs grant as the container. Whether every Circle owner needs a Household row, or grants can stand alone with Household optional. Leaning grants reference a household for continuity with Spec 020, auto-created if absent.
  • O3 — Statement verification page. The code prints now; the simi.app/verify/… page (proving a statement is genuine) is Phase 2 — confirm the code format is forward-compatible.
  • O4 — Invite expiry & resend. Default token TTL and resend/revoke-pending semantics (Spec 020 uses 7-day member-invite expiry; reuse).
