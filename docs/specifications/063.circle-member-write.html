Spec 063 Status: Draft (Rev 1) Size: Medium Priority: P2 (Simi, post-M5) Domain: PersonalFinance / Simi / Documents

Member-write — contributing to a shared entity

Spec 048's own success story ends with "Seyi logs a ₦120,000 repair; it appears on Fola's Today with his name." That sentence was never built — Spec 048 shipped the Circle as strictly read-only and left member-write as Open decision O1. Today a member can see a shared flat but cannot add the repair receipt, log the service charge they paid, or file the new tenancy agreement; every write path is hard-bound to the caller's own records (EnsureOwnedCareEntityAsync, OwnsDocumentAsync). This spec resolves O1: it lets a full-scope member log a payment and attach a document to an entity an owner shares with them — each write authorised by a single fail-closed gate, stamped with the member's identity, and landing in the owner's records so it surfaces on their Today. It turns the Circle from a window into a shared ledger of care.

Decision & scope-tension (mini-ADR) Member-write is a genuine shift from Simi's single-keeper shape, so two guardrail checks are made explicitly. (1) It is not money movement. A PaymentLog is, by Spec 045's own words, "the capture that it happened (paid by bank / Wise / cash elsewhere)" — a record, never a transfer. Spec 048 §3.2's rule "no member can move funds" is preserved intact: no member moves a penny; they record that they did, outside the app. (2) It was anticipated, not smuggled in. Spec 048's acceptance criteria and success signal already describe the member-logged act surfacing on the owner's Today; O1 explicitly deferred the write matrix to "finalise in implementation." This spec is that finalisation. What it deliberately withholds: a member may only create on a shared entity and undo their own contribution — never edit or delete the owner's or another member's records, never touch a docs-only share, never drive the owner's commitment cycles. The owner remains sole keeper; members may only add to the pile they can already see. (Tool and class names in this spec are generic per ADR-013; "Simi" names the configured persona, not a platform symbol.)

1. Summary

A cross-border household shares the load, so the record should be shared too. This spec adds two member-write capabilities on a shared CareEntity: log a payment (a repair, a service charge, a top of the school fees) and attach a document (a receipt, a new tenancy agreement). Both are gated by one new fail-closed check — ICircleWriteGuard.ResolveWriteScopeAsync — that says whether the current member may contribute to this owner's this entity, reusing Spec 048's per-entity covering-grant logic. A member's write lands in the owner's data space (so it flows into the owner's Today, totals, and Support Statement) but is stamped with the member's id for attribution and non-repudiation. A member can undo their own contribution; the owner can remove anything on their entities. Documents-only members remain strictly read-only.

Success signals Fola shares the Surulere flat with her brother Seyi (co-owner scope). Seyi pays a plumber ₦120,000 and, from his phone, logs it against the flat: it appears on Fola's Today as "Seyi · ₦120,000 · repair" and rolls into the flat's year total and her next Support Statement. He photographs the new tenancy agreement and attaches it; it files itself into Fola's Vault against the flat, tagged "added by Seyi". Mr Bello, documents-only, tries the same from a script and is refused — his grant carries no write. Seyi mistypes an amount and undoes his own log; Fola's earlier records are untouched.

2. Problem & current state

  • Every write is strictly caller-owned. PaymentLogService.CreateAsync calls EnsureOwnedCareEntityAsync(tenantId, currentUserId, careEntityId), which throws unless the entity's UserId equals the caller — a member cannot log against an owner's entity. The document path is the same: DocumentLinkService.AddLinkAsync gates on OwnsDocumentAsync (doc.OwnerPartyId == caller party), so a member cannot link into an owner's Vault.
  • The Circle is read-only. Spec 048's member surface is entirely GET (ListSharedEntities, GetSharedEntity, GetSharedPaymentLogs). There is no member-write endpoint, and O1 is still open.
  • No attribution field exists. PaymentLog has a single UserId (the data owner) and no "who logged this" column; Document has OwnerPartyId but no "who uploaded this" column. Surfacing "Seyi's name" on the owner's Today needs one small field on each.

So the reads are safe and scoped; the writes have simply never been opened, and the entity model has no notion of a contributor.

3. Scope (in / out)

3.1 In scope

  • New ICircleWriteGuard — the single fail-closed contribute check (§5).
  • New Member payment-log write: service method + endpoint, attributed, one-offs only (§7).
  • New Member document attach into the owner's Vault: a cross-module owner-scoped writer + endpoint (§8).
  • Edit PaymentLog.LoggedByUserId + Document.UploadedByUserId attribution columns (§6, §10).
  • New One Medium-gated AI tool, pf_add_shared_payment (§9).
  • Edit Surface the contributor's name on the owner's entity/Today projections (§6).

3.2 Out of scope

  • Money movement. A log records an act paid elsewhere; nothing here transfers funds (Spec 048 §3.2 unchanged).
  • Editing or deleting the owner's / another member's records. Members create + self-undo only; the owner is the sole editor of their book.
  • Docs-only writes. A docsOnly grant stays read-only — no logs, no attachments.
  • Driving the owner's commitments. A member logs one-off acts (no CommitmentId); marking a commitment cycle done stays the owner's ritual (Spec 044). See O2.
  • Raw AI file upload. Document bytes are uploaded on the frontend (as with statement import); the AI deep-links, it does not stream files.

4. The write matrix — resolves Spec 048 O1 the decision

Member grantLog a paymentAttach a documentEdit / delete another's record
all or entities covering the entity, NoAmounts=false✅ attributed to the member✅ into the owner's Vault, tagged with the member❌ (own contribution: self-undo only)
full scope but NoAmounts=true❌ (cannot state an amount into a book they may not read)✅ (a document carries no amount)❌
docsOnly❌❌ (read-only)❌
no covering grant❌ 404❌ 404❌ 404

The rule in one line: you may contribute to what you can fully see, you own only what you contributed, and the owner owns everything. Amount-bearing writes additionally require that the member is allowed amounts (NoAmounts=false), so the no-amounts security property is never breached from the write side either.

5. The single write gate the crux

Mirroring Spec 048's "one visibility filter" discipline, there is one write authority. It is the same per-entity covering-grant resolution the reads use (GetActiveGrantsAsync + covering), asked the write question. Implemented by CircleService (which already holds that logic); no write path may bypass it. 

// Contracts/Services/PersonalFinance — the sole contribute authority (fail-closed).
public interface ICircleWriteGuard
{
    /// <summary>What the CURRENT member may contribute to (owner, careEntity). Fail-closed:
    /// no covering grant, or a docsOnly grant, yields (false, false).</summary>
    Task<CircleWriteScope> ResolveWriteScopeAsync(Guid ownerUserId, Guid careEntityId, CancellationToken ct = default);
}

public record CircleWriteScope(bool CanAttachDocument, bool CanLogPayment)
{
    public static readonly CircleWriteScope None = new(false, false);
}
// CircleService — reuse the existing covering + full-scope resolution (same predicate as the read's hasFullScope).
public async Task<CircleWriteScope> ResolveWriteScopeAsync(Guid ownerUserId, Guid careEntityId, CancellationToken ct)
{
    var grants   = await GetActiveGrantsAsync(ownerUserId, ct);                     // active, known-scope, member→owner
    var covering = grants.Where(g => g.Scope == "all" || g.EntityIds.Contains(careEntityId)).ToList();
    var fullScope = covering.Any(g => g.Scope == "all" || g.Scope == "entities");   // docsOnly-only → false
    if (!fullScope) return CircleWriteScope.None;

    var amountsAllowed = covering.Any(g => !g.NoAmounts);
    return new CircleWriteScope(CanAttachDocument: true, CanLogPayment: amountsAllowed);
}
Fail closed, one place Both write services resolve ICircleWriteGuard before touching the database and deny on false. A revoked grant drops out of GetActiveGrantsAsync immediately, so a revoked member's next write fails. There is no per-endpoint ad-hoc check — a new member-write surface added later must route through this gate, exactly as new shared-read surfaces route through ICircleVisibility.

6. Attribution edit

A member's contribution lives in the owner's data space but must never lose the member's fingerprint. Two nullable columns carry it (null = the owner did it themselves — every existing row): 

// PaymentLog.cs  (Spec 045)
/// <summary>The member who logged this on the owner's shared entity (Spec 063); null = the owner logged it.</summary>
public Guid? LoggedByUserId { get; set; }

// Document.cs  (Spec 035/046)
/// <summary>The member who uploaded this into the owner's Vault via a Circle contribution (Spec 063); null = the owner.</summary>
public Guid? UploadedByUserId { get; set; }

The owner-facing projections that already surface recent logs (CareEntityPaymentLogSummary and the entity profile / Today feed) gain an optional LoggedByName, resolved once via IPartyReader the same way owner names are resolved elsewhere. When null, the UI shows nothing extra; when set, "Seyi" appears. This is a pure additive projection field — no amount semantics change.

7. Member payment-log write new

A dedicated method keeps the owner-write path separate from the strictly-caller-owned CreateAsync, rather than overloading it with a mode flag: 

// IPaymentLogService
/// <summary>A member logs a one-off act on an entity an OWNER shares with them (Spec 063). Authorised by
/// ICircleWriteGuard; the log is written into the owner's space (UserId = ownerUserId) and stamped
/// LoggedByUserId = current member. CommitmentId/CommitmentCycleId are rejected — members log one-offs only.</summary>
Task<PaymentLogResponse> CreateForSharedEntityAsync(
    Guid ownerUserId, CreatePaymentLogRequest request, CancellationToken cancellationToken = default);

Behaviour, reusing the existing normalisation/idempotency machinery:

  1. Resolve the member (GetContext() → current user) and call ICircleWriteGuard.ResolveWriteScopeAsync(ownerUserId, request.CareEntityId); !CanLogPayment → deny (404 — existence not revealed, consistent with the reads).
  2. Reject CommitmentId/CommitmentCycleId (one-offs only, O2).
  3. Confirm the entity belongs to the owner and is live — the same EnsureOwnedCareEntityAsync check, but keyed on ownerUserId not the caller.
  4. Write PaymentLog { UserId = ownerUserId, LoggedByUserId = memberUserId, Origin = "manual", … } through the existing validation, currency normalisation, and idempotency-key replay logic.

Endpoint, alongside the Spec 048 shared routes (customer UserPolicy; the gate does the real work): 

POST /personal-finance/circle/shared/{ownerUserId}/care-entities/{careEntityId}/payment-logs
     → 201 Created (the attributed log)   401   404 (no grant / not allowed amounts / entity not found)

// Self-undo of one's OWN contribution (soft-delete, 30-day restore window as Spec 045):
DELETE /personal-finance/circle/shared/{ownerUserId}/care-entities/{careEntityId}/payment-logs/{id}
     → 204   404 (not the caller's own contribution)   // gated on LoggedByUserId == member

8. Member document attach new

A member-attached document must land in the owner's Vault — under the owner's OwnerPartyId — so it files against the shared entity, appears in the owner's document list, and is indexed under the owner's party for the owner's own search. The caller (member) does not own that party, so the normal caller-derived document write (DocumentLinkService.ResolveCallerScopeAsync) cannot be used. Add a narrow owner-scoped contribution writer as a SharedKernel abstraction (so PersonalFinance can invoke it without a Documents ProjectReference — the same direction as the existing IDocumentLinkReader): 

// SharedKernel.Abstractions.Documents — implemented in the Documents module.
public interface ICircleDocumentContributor
{
    /// <summary>Creates a Document under the OWNER's party from an uploaded file, stamps UploadedByUserId,
    /// and links it to (targetType, targetId) — all in one save. NOT an HTTP endpoint of its own: it is
    /// invoked only after ICircleWriteGuard has authorised the member (Spec 063 §11 trust boundary).</summary>
    Task<DocumentRef> ContributeAsync(
        Guid ownerUserId, Guid uploadedByUserId, string targetType, Guid targetId,
        DocumentUpload file, string title, string documentType, CancellationToken ct = default);
}
member taps "add document" on Fola's flat → POST /personal-finance/circle/shared/{ownerUserId}/care-entities/{careEntityId}/documents (multipart) → ICircleWriteGuard.ResolveWriteScopeAsync → CanAttachDocument? no → 404 → ICircleDocumentContributor.ContributeAsync(ownerUserId, member, "careEntity", careEntityId, file, ...) resolve owner party (IUserPartyResolver) → Document{ OwnerPartyId = ownerParty, UploadedByUserId = member } store bytes (DocumentFileStore, tenant-scoped key, SHA-256) → DocumentLink → careEntity → DocumentUploadedEvent → indexed under owner_party_id (owner's Vault + owner's RAG)

Consequence, stated plainly: the bytes enter the owner's party-scoped index, so the owner can later search them; the contributing member does not thereby gain search over the owner's other documents (the party-scoped index still filters on the caller). The member sees the document back only as a ref through the Spec 048 / Spec 062 shared read — consistent with everything else in the Circle.

9. AI exposure new

Logging is a natural thing to ask Simi to do ("log the ₦120,000 plumber against Fola's flat"), so expose exactly one mutating tool, classified Medium in PersonalFinanceToolApprovalManifest — an everyday domain write, confirmed in-session before it runs (Spec 032). Document upload stays on the frontend (raw bytes), so the AI deep-links rather than streaming a file, matching the existing "uploads happen on the frontend" rule. 

// PersonalFinanceToolApprovalManifest.Classifications — add:
["pf_add_shared_payment"] = Medium("Add a payment on a shared entity"),  // verb "_add_" is in MutatingToolNameHeuristic, so an omitted/renamed manifest entry fails closed (throws), never passes ungated
// CircleTools (Spec 062) gains the one write:
[Description("Logs a one-off payment the current user made on an entity a circle owner shares with them "
    + "(e.g. a repair on a sibling's flat). Attributed to the current user and added to the owner's records. "
    + "Requires a full-scope share that permits amounts; refused for documents-only shares.")]
public Task<PaymentLogResponse> AddSharedPayment(Guid ownerUserId, /* amount, currency, date, channel, note */ ...)
    => _paymentLogs.CreateForSharedEntityAsync(ownerUserId, request, ct);

Being classified, the tool is wrapped by ApprovalGatedAIFunction: Simi describes the change ("Log ₦120,000 to Fola's flat?"), the member confirms, and only then does it run once. The <circle> prompt block (Spec 062) gains a line: "You may log a one-off payment on a shared entity with pf_add_shared_payment; it is attributed to the user and needs their confirmation. You cannot edit or delete the owner's records."

10. Persistence & migration

  • Two nullable columns — PaymentLog.LoggedByUserId (→ AnkPaymentLogs) and Document.UploadedByUserId (→ AnkDocuments) — added to the entity classes and their IEntityTypeConfiguration<T>. No new table; no new DbSet. A third nullable column, PaymentLog.AiRunId, links an AI-created log (written via the tool, §9) back to its AiRun — the same convention PersonalTransaction / CompassPlan / FLG rows already follow; it is null for manual and REST-endpoint writes.
  • Tool-generated migration only, against AonikDbContext, per CLAUDE.md (dotnet ef migrations add AddCircleContributionAttribution …). All three columns are nullable with no default, so existing rows are untouched (they read as owner-authored).
  • Index note. The self-undo query filters (UserId, LoggedByUserId); add LoggedByUserId to the existing entity-scoped index if the contributor feed needs it. The idempotency unique index stays (TenantId, UserId, IdempotencyKey) — see O1.

11. Security

  • One write gate, fail-closed (§5). No covering grant, a docsOnly grant, or a revoked grant → denial. Amount-bearing writes additionally require NoAmounts=false, so the no-amounts property is upheld on the write side. And because the gate accepts any careEntityId for an all-scope grant, both write paths must also verify the target entity is the owner's and live — the payment path via EnsureOwnedCareEntity(ownerUserId, ...), and the document path must do the same before ICircleDocumentContributor.ContributeAsync (else an all-scope member could file a document into the owner's Vault against an arbitrary, archived, or non-owned id).
  • Trust boundary on the owner-scoped writer. ICircleDocumentContributor writes into another party's Vault, so it is invoked only from the PersonalFinance member-write endpoint after the gate authorises — it is not exposed as its own HTTP endpoint and takes ownerUserId/uploadedByUserId from the authenticated context + gate result, never from raw request body. An integration test asserts there is no unauthorised route to it.
  • Attribution & non-repudiation. Every member write carries LoggedByUserId/UploadedByUserId; a member can never write anonymously into an owner's book, and the owner always sees who added what.
  • Ownership asymmetry. The owner may soft-delete any record on their entities (their existing owner-scoped delete already covers member-contributed rows, since UserId = owner); a member may undo only rows where LoggedByUserId == self. Member contributions are immutable apart from the member's own self-undo and the owner's delete: because a member-logged row stores UserId = owner, PaymentLogService.UpdateAsync (which gates on UserId alone) must additionally reject an update when LoggedByUserId is set, or the owner could silently edit a member's contribution. Asserted by an owner-cannot-edit-member-log test.
  • Not money movement. Re-affirmed: a log is a record; the AI write is Medium (a domain write), never High (High is money movement in Finance, proposal-gated). The Spec 032 build-time check would trip if pf_add_shared_payment were left unclassified.
  • Audit. Member writes are audited (member id, owner id, entity id, action); the AI path is additionally an AiRun with the approval decision recorded.

13. Acceptance criteria

  • Full-scope log. An entities/all (amounts-allowed) member logs a one-off on a shared entity; it persists with UserId = owner, LoggedByUserId = member, and surfaces on the owner's entity view with the member's name and in the year total.
  • Docs-only denial — the security assertion. A docsOnly member (and a full-scope-but-NoAmounts member for logs) is refused both writes with a fail-closed 404; nothing is persisted.
  • Document attach lands in the owner's Vault. A member's uploaded document is created under the owner's OwnerPartyId, linked to the entity, tagged UploadedByUserId = member, and is retrievable by the owner (and indexed under the owner's party) — while the member gains no search over the owner's other documents.
  • Revocation. After the owner revokes the grant, the member's next log/attach is denied immediately.
  • Delete asymmetry. A member can undo their own contribution and cannot delete the owner's or another member's; the owner can remove any record on their entity.
  • AI path. pf_add_shared_payment is Medium-gated: it does not run until the member confirms, then runs once and is attributed; unclassified would fail the Spec 032 build check.
  • Build & migration. dotnet build green; a single tool-generated migration adds only the two nullable columns.

14. Open decisions

  • O1 — Idempotency scope for member writes. The unique key is (TenantId, UserId=owner, IdempotencyKey). Two members' offline queues colliding on a client GUID is astronomically unlikely, but if strict per-actor replay isolation is wanted, extend the index to include LoggedByUserId. Leaning: keep GUID keys, no index change.
  • O2 — Member marking a commitment cycle. v1 restricts members to one-off logs (no CommitmentId); should a co-owner be able to mark the owner's commitment cycle "done" (Spec 044) — e.g. Seyi pays this month's service charge? Deferred: it mutates the owner's schedule state, a heavier shared-lifecycle question. Revisit if households ask for it.
  • O3 — Owner notification of contributions. Should a member's log/attach notify the owner (push/summary)? Reminder delivery is itself pre-production (FCM no-op today), so this rides the notification-readiness work; the data surfaces on Today regardless.
  • O4 — Contribution rate/abuse limits. A malicious accepted member could spam logs into an owner's book. Attribution + one-tap grant revoke are the v1 mitigations; a per-member contribution rate limit is a possible fast-follow.
