Commerce box add-on lines — extras alongside the box

Activates the AddOn line kind Spec 068 §4.1 reserved: ordinary retail products bought alongside the box at their own price, consuming no box space. Covers the extras merchandising read, the cart routes, the addOns quote component, and checkout's retail order lines — the storefront's Step 3 (/box/extras) server contract.

1. Summary

Spec 068 shipped the LineKind discriminator with exactly one writable value so that every capacity, merge, quote and checkout rule already states which kind it counts. This spec turns the reserved AddOn value on. An add-on is an ordinary retail product — a jar of pepper sauce, a drink, a snack — bought alongside the box at its own price: it consumes no box space, never blocks or is blocked by the fullness gate, carries its own retail price (the deliberate exception to the storefront's no-standalone-dish-price rule), and lands on the order as an ordinary ProductPurchase retail line using the spine's existing shape. Everything extras need beyond that — options, content, stock, merchandising — is machinery specs 066/067/052/070 already provide for any product; this spec adds routes and rules, not tables.

2. Scope (in / out)

InOut (and where it goes)
  • Public extras read (GET /commerce/catalog/extras) with retail prices, resolved content and option summaries
  • Commerce.Storefront.ExtrasCollectionSlug setting (070 config document)
  • Cart routes: add an AddOn line; quantity/personalisation/remove via the existing line routes (kind-aware)
  • addOns quote component (§4.1's promised additive change)
  • Checkout: one retail order item per AddOn line + invoice lines; reservation as ordinary stock
  • Drift/availability handling identical to dishes (066 stored-selection contract)
  • New tables or columns — none needed; AddOn, the price snapshot and the personalisation columns all shipped in 068's migration
  • Extra-specific taxonomies — categories/serve-style/heating are data (070 facets/attributes, 067 content), not schema
  • Cross-sell/recommendation logic — merchandising is the curated collection, nothing cleverer
  • Delivery interplay — delivery stays Spec 069's concern

3. Domain model — nothing new

An extra is a normal Simple product: retail price via ProductPrice (tenant currency), optional Spec 066 option groups (the frontend's Size/Heat choices with addPence are exactly option adjustments), Spec 067 content (nutrition, ingredients, allergens, heating), Spec 052 stock, Spec 070 attributes/tags for serve style and category rails. Merchandising membership is a Spec 070 Collection whose slug the tenant configures (Commerce.Storefront.ExtrasCollectionSlug, default "extras").

On the cart, an AddOn line reuses 068's columns verbatim: LineKind = AddOn, BoxBundleSlotId = null (add-ons fill no slot), UnitPriceSnapshot = the resolved retail unit price (display cache, re-derived each write like every other snapshot), canonical PersonalisationJson + adjustment/surcharge snapshots when personalised. The merge key is (AddOn, null, variant, canonical selection) — the same discipline as dishes, one kind over.

4. The extras read

RouteBehaviour
GET /commerce/catalog/extras (AllowAnonymous) The members of the configured extras collection, in curated rank order, each row carrying: the 070 summary fields (name, slug, hero image, tags, attributes), the retail unit price in the tenant currency (the AddOn exception — a product without a price in that currency is omitted and reported in a skipped diagnostic count rather than served unpriceable), the resolved 067 standard-preparation content (nutrition, declarations, heating) when authored, and the product's effective option groups so the storefront renders the Size/Heat picker without a second call. Unconfigured slug or missing collection ⇒ empty list, never a guess. Vary: X-Tenant-Id like every anonymous storefront read.

5. Cart write semantics

OperationBehaviour
Add extra
POST /commerce/carts/{cartId:guid}/extras		 Box carts only (the generic paths stay closed — R11 is about kind-blindness, and this route is the kind-aware one 068 promised). Validates the variant active + product Active, the product priceable in the cart currency (the retail snapshot is mandatory for AddOn lines), quantity ≥ 1 (R12), the selection via 066 when supplied, and aggregate non-reserving availability across the cart (R5 — dish and add-on demand for the same variant sum). Merges on the AddOn merge key. No capacity check: add-ons consume no box space (R3 explicitly excludes them), and a full box never blocks a jar of sauce.
Quantity / personalisation / remove
PATCH·DELETE /commerce/carts/{cartId:guid}/lines/{lineId:guid}		 The existing line routes serve both kinds; the service branches on the line's kind: AddOn increases re-check availability but never capacity or slot bounds; splits (applyToUnits) work identically; quantity 0 deletes; personalisation re-validates and re-prices via 066 and can merge, exactly as dishes do.
Drift & availability The §8 pass covers AddOn lines unchanged: retired options remap and report, remapped lines can merge, unavailable extras flag (never vanish) and block continue/checkout until removed. Additionally the retail price snapshot is re-resolved on every load; a product whose price in the cart currency disappeared flags the line unavailable — a priceless retail line must never reach checkout.
Continue (R8) Unchanged: fullness counts BoxDish units only. Add-ons neither satisfy nor obstruct the gate; a cart holding only extras cannot continue (the box is the product being bought).

6. The quote

The addOns component joins the ordered, named, additive list — the §7 contract said clients iterate components rather than reconstruct, so this is the non-event it was designed to be:

{ "key": "boxPrice",        "amount": 95.00 },
{ "key": "personalisation", "amount": 16.00 },   // BoxDish adjustments only
{ "key": "unitSurcharges",  "amount":  8.00 },   // BoxDish surcharges only
{ "key": "addOns",          "amount": 21.50 },   // Σ (unit price + adjustment + surcharge) × qty over AddOn lines
{ "key": "deliveryCharged", "amount":  0.00 }

The box-goods components stay BoxDish-scoped — an add-on's option adjustment is part of what that add-on costs, not part of the box's personalisation story — so each line kind has exactly one component family and the total remains the component sum (A24). The line payload gains lineKind and, on AddOn lines only, unitPrice; unitsSelected, spacesLeft and isFull keep counting BoxDish only.

7. Checkout materialisation

  • Re-validation: the A18 drift stop covers AddOn lines (a repriced or retired extra refreshes and 409s exactly like a dish change); the R8 enforcement is unchanged.
  • Reservation: AddOn lines reserve variant × quantity in the same all-or-nothing hold as everything else.
  • Order: still one ProductPurchase order — the box item (goods total, box envelope) plus one ordinary retail item per AddOn line using the spine's existing retail shape: Quantity, UnitPrice = the charged unit price (retail + adjustment + surcharge), ProductId = the variant, Sku, and the 066 §12 envelope in DetailsJson when personalised — the same convention simple product lines already use. The delivery item, when charged, follows.
  • Charge: the goods subtotal becomes box goods + add-on goods; discount and tax apply to that goods subtotal; delivery joins the payable total last, as today. The nonpositive guards (K5/L4) apply to the combined figures.
  • Invoice: the box-aggregate line, one line per add-on (name, quantity, charged unit price — add-ons are ordinary retail and may show their prices), the delivery line.
  • Kitchen: add-ons write OrderBundleSelection rows? No — selection rows are the box's kitchen landing. An add-on that needs preparation appears in production planning through the ordinary retail path (its own order item, expanded by the 055 sheet exactly as simple lines are today), keyed by its own personalisation columns on the item envelope. Nothing new.

8. Server-enforced rules

#Rule
X1AddOn lines exist only on box carts, created only by the extras route; the generic item/bundle paths remain closed to box carts (R11 unchanged).
X2An AddOn line MUST carry a retail price snapshot in the cart currency at every write and at checkout; unpriceable ⇒ reject on add, flag unavailable on load.
X3Add-ons never count toward capacity, fullness, or slot bounds (R3/R8/slot rules stay BoxDish-scoped — 068 §4.1's promise, now load-bearing).
X4R12 quantity rules apply unchanged (≥1 on add; 0 deletes; negatives reject; applyToUnits bounded).
X5Aggregate availability sums BOTH kinds per variant — a dish and an add-on drawing the same stock cannot jointly oversell it (R5 extended).
X6The quote's total remains exactly the component sum with addOns present (A24 contract).
X7Checkout emits one retail order item per AddOn line and includes them in the goods subtotal for discount/tax; the box item never absorbs an add-on amount.

9. Persistence & migration

No migration. Every column this spec touches shipped in AddCommerceBoxBuilderCarts (068): LineKind, the price snapshot, the personalisation columns. The extras collection and setting are data. This is the additive change 068 §4.1 designed for — if a migration turns out to be needed, that is a spec bug to raise, not a hand-written migration to write.

10. Testing

  • Read: configured collection serves priced rows with content + option groups; unpriced members skip with a diagnostic count; unconfigured ⇒ empty; Vary header.
  • Cart: add/merge/split/remove for AddOn lines; a full box still accepts extras (X3) and extras never satisfy continue; mixed-kind availability creep (X5); unpriceable add rejection and load-flagging (X2); personalised extras price via 066.
  • Quote: addOns component maths incl. personalised extras; A24 sum with all five components; BoxDish components unchanged by extras.
  • Checkout: mixed cart → box item + N retail items + selections rows for dishes only; discount/tax on combined goods; invoice lines; reservation covers extras; drift 409 on a repriced extra.
  • Full-solution dotnet test Aonik.sln before PR.

11. Acceptance criteria

#Given / when / then
B1A full 6/6 box; add 2 pepper sauces → accepted; unitsSelected stays 6, isFull true, continue still passes.
B2A cart holding only 3 extras and an empty box → continue rejects with the R8 shortfall; the extras neither help nor block.
B3Extra priced 3.50, size option +1.00, qty 2 → addOns component 9.00; total = Σ components (A24).
B4Add an extra with no price in the cart currency → rejected naming the product; price removed after adding → line flags unavailable, continue/checkout block until removed.
B5Same extra added twice with the same option → one line qty 2; different option → second line; applyToUnits splits.
B6Checkout of box + 2 add-on lines → one order: box item at box-goods total, two retail items at their charged unit prices with envelopes, selection rows for dishes ONLY; payment total = (boxGoods + addOnGoods) − discount + tax + delivery.
B7Dish uses variant V (3 units) and an add-on uses V (2 units), availability 4 → the second add rejects (X5).
B8Extras read: configured collection with one unpriced member → the priced rows serve with content + options, skipped: 1, Vary present; unconfigured slug → empty list, 200.
B9An extra's chosen option is retired mid-session → next load remaps to the default, re-prices, reports in changes[]; checkout after the drift 409s first, resubmit succeeds.

12. Open decisions

O1 — Add-on eligibility. Phase 1 defines eligibility as membership of the configured extras collection at ADD time; the line then lives its own life (drift rules govern). If merchandising removal should also evict cart lines, that is a later policy — eviction today would contradict the "lines never vanish silently" principle.

O2 — Per-kind quote breakdowns. If the storefront ever needs add-on personalisation itemised separately from the unit price, the component list can gain addOnPersonalisation additively — same A24 contract, nobody chases it now.
