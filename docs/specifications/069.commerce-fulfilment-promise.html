Commerce fulfilment promise — delivery calendar & earliest-delivery date

A per-tenant fulfilment calendar and the computed "earliest delivery" promise — the single most-repeated data point in the Abby's Table storefront (five surfaces) and currently unrepresentable anywhere in Aonik. Build area D of the storefront capability plan. Phase 1 (this spec's build) is the promise; phase 2 (delivery capture at checkout) is scoped here and built with the Steps 3–5 checkout work.

1. Summary

Commerce has no concept of customer delivery: no dates, slots, cutoffs, lead times, addresses or fees — checkout carries payment fields only, and the kitchen's production "windows" (specs 055/056) filter on order-creation time. This spec introduces the smallest honest model that makes a delivery promise possible: a per-tenant FulfilmentCalendar (delivery days, order cutoff, preparation lead, blackout dates, timezone) and a deterministic computation of the earliest delivery date, served on a public endpoint the storefront shows everywhere the promise appears.

2. Motivation

  • "Earliest delivery: 6 August" appears on the client's homepage (twice), menu page, dish detail pages, Step 1 and Step 2 — and per the client's notes it "will be pulled from the backend, based on the earliest delivery calculated". A hard-coded date is explicitly ruled out (Step 2 FR-7.6).
  • A batch-cook meal business genuinely computes this. Two cadences exist in the wild and both are modelled (§4): a daily order book (every day has a cutoff time; lead days roll forward) and a weekly cycle (orders close at one weekday's cutoff — say Tuesday noon — and later orders fall to the next week's cycle). The inputs are operational configuration, changing seasonally — data, not code.
  • Deliberately generic (ADR-013): any make-to-order tenant — florist, baker, meal kitchen — has the same shape: which days we deliver, when the order book closes, how long preparation takes.

4. Domain model

/// Per-tenant fulfilment configuration. At most one per tenant (phase 1).
public class FulfilmentCalendar : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    /// IANA timezone id, e.g. "Europe/London". All cutoff/date maths happens in it.
    public string Timezone { get; set; } = "Europe/London";
    /// JSON array of delivery weekdays, lower-case English day names,
    /// e.g. ["wednesday","thursday"]. Must be non-empty for the calendar to be active.
    public string DeliveryDaysJson { get; set; } = "[]";
    /// Local time of day after which an order joins the next cycle, e.g. 12:00.
    public TimeOnly CutoffLocalTime { get; set; }
    /// Null = daily order book (the cutoff applies every day). Set (lower-case day name,
    /// e.g. "tuesday") = weekly cycle: the order book closes at that weekday's cutoff, and orders
    /// after it join the FOLLOWING week's cycle. Lead days count from the cycle-close date.
    public string? CutoffDayOfWeek { get; set; }
    /// Whole days between the effective order date and the earliest dispatch-eligible
    /// date. 0 = same-day eligible.
    public int LeadDays { get; set; }
    /// JSON array of ISO dates ("2026-12-25") on which no delivery happens, whatever
    /// the weekday says. Bounded list; expired entries are pruned on save.
    public string BlackoutDatesJson { get; set; } = "[]";
    public bool IsActive { get; set; } = true;
}

One calendar per tenant in phase 1 — multi-zone/multi-kitchen calendars would key this by zone and belong to the same change as zone fees (phase 2+, O2).

5. The computation

Deterministic, side-effect-free, clock-injected (IClock — never DateTime.Now):

nowLocal        = clock.UtcNow converted to calendar.Timezone

// daily order book (CutoffDayOfWeek = null)
effectiveDate   = date(nowLocal)                    // the order-book day this order would join
                  + 1 day  when time(nowLocal) > CutoffLocalTime

// weekly cycle (CutoffDayOfWeek set)
effectiveDate   = the next date whose weekday == CutoffDayOfWeek and whose cutoff has not passed
                  // i.e. today if it is cutoff day and time ≤ cutoff; otherwise the next
                  // occurrence — orders after Tuesday noon join NEXT week's Tuesday close

readyDate       = effectiveDate + LeadDays          // earliest dispatch-eligible date
earliestDelivery = first date d ≥ readyDate where
                     weekday(d) ∈ DeliveryDays  and  d ∉ BlackoutDates
search horizon  = max(readyDate, latest blackout date) + 62 days
                  // beyond the last blackout no blackout can apply, so with ≥1 delivery weekday a
                  // valid day exists within 7 days of the horizon start — a calendar the admin API
                  // accepted (≤100 future blackouts) can NEVER produce a false 404. Exhaustion ⇒
                  // genuinely misconfigured (treated as inactive).
  • Timezone conversion uses IANA ids via TimeZoneInfo (cross-platform on .NET 10). The cutoff is a local wall-clock time, and DST transitions get an explicit policy rather than a shrug: the cutoff instant for a date is the UTC instant of the first mapping of that wall-clock time — a nonexistent time (spring-forward gap, e.g. 01:30 on the gap day) maps to the first valid instant after the gap; an ambiguous time (autumn overlap) uses its first occurrence. Comparisons run on UTC instants, which makes the passed-cutoff state monotonic: once the cutoff has passed it stays passed — the clock rolling back from 01:45 to 01:15 must never reopen the order book and move the promise backward.
  • The result is a date, not a timestamp. The storefront formats it ("Thursday 6 August") — the weekday label is always derived from the date, never a second configured string. (The client's design mock reads "Wednesday 6 August", but 6 Aug 2026 is a Thursday — the mock's weekday label is internally inconsistent with its own date. This spec's fixture is one consistent definition: Thursday deliveries producing 2026-08-06; the storefront formats the weekday from the API date, so mock copy can never reintroduce the contradiction.)
  • Worked example (launch config: daily cutoff 12:00, lead 14, delivery Thursdays — 2026-08-06 is a Thursday): computed from Tuesday 2026-07-21 10:00 London → effective 21 Jul → ready Tue 4 Aug → first Thursday ≥ 4 Aug = 6 Aug 2026, matching the client's design fixture exactly. Weekly-cycle example (cutoff Tuesdays 12:00, lead 2, Thursdays): ordered Mon 20 Jul → cycle closes Tue 21 Jul → ready Thu 23 Jul → delivery 23 Jul; ordered Tue 21 Jul 13:00 (past cutoff) → cycle closes Tue 28 Jul → delivery Thu 30 Jul.

Unconfigured is a state, not an error. No calendar row, IsActive = false, empty delivery days, or an exhausted search all resolve to "no promise available": the public endpoint returns 404 and the storefront hides the promise line. A wrong date is worse than no date — the endpoint never guesses.

Endpoints

RouteAuthBehaviour
GET /commerce/config/deliveryAllowAnonymous { "earliestDeliveryDate": "2026-08-06", "timezone": "Europe/London" }; 404 when unconfigured. Response is cacheable for minutes — the value only moves at cutoff or midnight, and a short-TTL stale promise on the storefront is acceptable (ISR revalidation handles it). Caching is tenant-partitioned: the response is tenant-specific but the path is not, so the cache key must include the resolved tenant — header-routed deployments (Auth:TenantRouting=Header, the configured mode) must emit Vary: X-Tenant-Id; subdomain routing partitions naturally by host. A shared cache serving tenant A's promise to tenant B would contradict A7 outright.
GET /commerce/admin/fulfilment-calendarAdminUserPolicyCurrent calendar incl. inactive
PUT /commerce/admin/fulfilment-calendarAdminWritePolicy Upsert. Validates: known IANA timezone; day names valid (incl. CutoffDayOfWeek when set); LeadDays 0–60; blackout entries parse as dates, expired ones pruned, and at most 100 future dates — a bound chosen to keep the serialized array well inside the 2,048-character column (§8) so a request that passes validation can never fail at persistence with a truncation error; active calendar must have ≥ 1 delivery day. Response echoes the computed current promise so the operator sees the effect immediately.

7. Phase 2 — delivery at checkout (scoped, not built)

Authored now so phase 1 doesn't paint the schema into a corner; implemented with the storefront's Steps 3–5 build-out. Requirements at contract level:

  1. Delivery address on the checkout command and persisted with the order (recipient name, lines, postcode, country, contact phone). Storefront journeys are guest-first; the address lives on the order, not a party profile.
  2. Chosen delivery date: the customer picks from dates the calendar admits (same §5 rules, offered as a forward list); the server re-validates on checkout — a date that became invalid between page and submission is rejected with the next valid alternatives.
  3. Order linkage: delivery date + address recorded against the ProductPurchase order (new fulfilment-details record referencing OrderId — additive; the spine's OrderFulfilmentRef stays the financial-fulfilment link it is today).
  4. Kitchen planning by delivery date: specs 055/056 gain the option to window production on delivery date rather than order-creation date — the operationally meaningful axis once dates exist.
  5. Per-day capacity: with bookings-per-date now recordable, the calendar gains CapacityPerDeliveryDay?. Capacity is claimed atomically inside the checkout transaction — a per-date claim row guarded by a database uniqueness/counter constraint, never a read-then-write count (two concurrent checkouts observing the same count would both pass and oversell the day). Claims are released on payment failure or cancellation and expire on a TTL sweep — a checkout abandoned with a payment intent still pending fires neither event, and without expiry such ghosts would slowly mark days full with no paid orders (the pattern mirrors inventory reservations' Held-with-ExpiresAt + release sweep exactly). Full days drop out of offered dates and, transitively, out of the §5 promise — which supersedes phase 1's cache policy: the promise then moves on every claim and release, not just at cutoff and midnight, so promise/offered-date responses require tenant-partitioned invalidation on capacity changes (a capacity version in the cache key, or no-store for the offered-dates read) rather than a bare max-age.
  6. Zone fees (if ever needed): delivery zones keyed by postcode prefix with a fee feeding the quote's deliveryCharged; explicitly not designed further here.

9. Security & tenancy

  • Tenant-scoped entity behind the global filters; anonymous read resolves tenant via the existing header/subdomain middleware (plan decision D3).
  • The public endpoint discloses operational cadence (delivery days derivable by probing) — accepted: the storefront publishes the promise anyway; that is its purpose.
  • No PII in phase 1. Phase 2's address capture will carry the platform's standard PII handling on the order record.

10. Config-pack seeding

  • The food-commerce pack MAY seed a default calendar (inactive, Europe/London, empty days) so the admin screen has a row to edit rather than a create-from-nothing flow. Seeding rides CommerceTenantProvisioningContributor, idempotent, gated on the Commerce module — never on business type (ADR-014). Optional task.
  • The Abby's Table tenant's real values (cutoff, lead, delivery weekdays) are operator data entered in admin, not pack content.

11. Testing

  • Unit — computation (fixed IClock): before/at/after cutoff (boundary: exactly cutoff is before — ">" flips the day); lead-day arithmetic; weekday advance across week boundaries; blackout skip incl. consecutive blackouts; DST transition weeks (March/October, Europe/London); 62-day exhaustion → null; both §5 worked examples verbatim (daily and weekly-cycle), incl. the weekly past-cutoff full-week roll.
  • Service (InMemory, TestTenantProvider): unconfigured/inactive → null; upsert validations (bad timezone, empty days on active, LeadDays bounds, expired blackout pruning); upsert response echoes the recomputed promise.
  • API (CustomWebApplicationFactory): anonymous read 200/404 paths; admin authz; tenant isolation (tenant B's calendar invisible to tenant A's promise).
  • Full-solution dotnet test Aonik.sln before PR.

13. Acceptance criteria

#Given / when / then
A1Daily cutoff 12:00, lead 14, Thursdays, London; clock Tue 2026-07-21 10:00 local → ready Tue 2026-08-04, first Thursday ≥ ready = 2026-08-06 (a Thursday).
A2Same calendar; clock Thursday 2026-07-23: at 11:00 → effective 23 Jul, ready Thu 2026-08-06 → promise 2026-08-06; at 13:00 (past cutoff) → effective 24 Jul, ready Fri 2026-08-07 → promise 2026-08-13. Crossing the cutoff visibly rolls the promise a week — an implementation that ignores CutoffLocalTime fails this pair. (At exactly 12:00 the order is still before cutoff — ">" flips the day — so 12:00:00 yields 2026-08-06.)
A32026-08-06 added to blackouts → promise becomes 2026-08-13 (next Thursday).
A4No calendar / inactive / empty delivery days → public endpoint 404; nothing is guessed.
A5Admin changes cutoff or lead → next read reflects it with no other write; upsert response already shows the new promise.
A6Calendar timezone respected: a UTC clock either side of the London cutoff (incl. a BST date) flips the effective date correctly.
A7Tenant isolation: two tenants with different calendars each see only their own promise on the anonymous endpoint — and the response carries tenant-partitioned cache semantics (Vary: X-Tenant-Id under header routing) so no shared cache can cross-serve it.
A8Weekly cycle (CutoffDayOfWeek=tuesday, cutoff 12:00, lead 2, Thursdays): ordered Monday → delivered that week's Thursday; ordered Tuesday 13:00 → the cycle closes next Tuesday and delivery is the following Thursday — a full week later, not one day.
A9101 future blackout dates → upsert 400 naming the bound; 100 succeed and persist without truncation.

14. Open decisions

O1 — Promise granularity. Phase 1 promises a date. If the business later promises "order in the next 3h 12m for the 6 Aug delivery", the countdown derives entirely from this calendar client-side — no schema change; noted so nobody adds a countdown field.

O2 — Multi-zone calendars. One calendar per tenant assumes one dispatch cadence. Zone-dependent cadence (e.g. national vs local delivery days) keys the calendar by zone and belongs with phase 2's zone work.
