Spec 055 Status: Draft Size: Medium Priority: P3 Domain: Commerce / Production / Planning

Production planning — the production sheet & ingredient prep list

The two artefacts a food-production operations manager opens each morning: the aggregated production sheet ("this week: 40 portions jollof, 30 portions steak") and the ingredient prep list ("10 kg rice, 5 kg tomato…"). This is a pure read / aggregation spec — it adds no new persisted entity in v1. The production sheet aggregates ProductPurchase order demand by variant over a window; the prep list is that sheet exploded through the recipes defined in the keystone Spec 050 via its IRecipeService.ExplodeManyAsync. Everything lives in Aonik.Commerce and reads orders through the SharedKernel Ordering contract — never Aonik.Finance.

1. Summary

The keystone Spec 050 made a finished product describable as a bill of materials, and named this spec — 055 — as the primary consumer of its ExplodeManyAsync primitive (050 §11). Spec 050's day-in-the-life opens with the operations manager reviewing incoming orders, reading an aggregated production sheet (40 portions jollof, 30 portions steak), then consulting an ingredient prep list (10 kg rice, 5 kg tomato…). This spec delivers exactly those two views — and nothing else.

Both are projections computed on read, not stored records:

  • Production sheet — for a date window, per-ProductVariant demand in portion counts, aggregated from ProductPurchase orders read through the SharedKernel.Abstractions.Ordering read contract (Commerce reads the orders it created via the spine — never through a Finance reference).
  • Prep list — the production sheet fed into IRecipeService.ExplodeManyAsync, yielding per-Ingredient required quantity in each ingredient's base unit; optionally netted against available stock (OnHand − Reserved) from Spec 052 to add a shortfall column and a suggested reorder quantity.
Success signals An operator (or the commerce-agent) asks for this week's production and gets back "40 jollof, 30 steak", and the prep list "10 kg rice, 5 kg tomato, …" — the exact numbers from Spec 050's verification, now driven by real in-window orders. A variant with no active recipe shows up as a diagnostic line, not a silent under-count. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering and no new migration; dotnet test Aonik.sln stays green with aggregation + explosion + netting unit tests.

2. Context & motivation

Spec 050 framed every operations-manager artefact as a projection of one primitive — a finished good is made of raw materials in known quantities — and called out the ordering of those projections: the production sheet is order demand aggregated by product; the prep list is that demand exploded through recipes. Those two sentences are this spec. 050 built the recipe and the explosion algorithm deliberately ahead of their consumers so this planning slice could be a thin read layer over data that already exists.

Nothing new is persisted because nothing needs to be: the demand already lives in the ProductPurchase orders the storefront created on the Order spine (Spec 042 / Spec 041), and the translation from portions to ingredients already lives in IRecipeService. Planning is the act of reading those two together over a chosen window. Persisting a snapshot of that read (for reproducibility, or to freeze a plan a buyer acted on) is a real want, but it is a follow-up (Open) — v1 recomputes on demand.

Scope discipline, per the family brief: build the thin planning view this persona needs — a production sheet and a prep list for a date range — not a forecasting engine, an MRP time-phased plan, or a scheduling board. Forecast demand (vs. actual-order demand), named/rolling windows, and excluding demand already made are noted as open extensions, not built.

5. Scope (in / out)

In scope

  • IProductionPlanningService in Services/Production/ (beside the Spec 050 recipe vertical it composes) with two read methods — GetProductionSheetAsync(window) and GetPrepListAsync(window, netAgainstStock) — returning DTOs.
  • Production sheet: per-ProductVariant portion demand aggregated from ProductPurchase orders in the window, read through the Ordering read contract; build-your-own-box lines expanded into their chosen component variants via OrderBundleSelection (§9).
  • Additive Ordering-contract extension (§9 contract note): ListOrdersQuery.CreatedFromUtc/CreatedToUtc and IOrderService.ListWithItemsAsync — the smallest honest additions that make the demand query period-bounded and line-carrying.
  • Prep list: the sheet fed through IRecipeService.ExplodeManyAsync → per-Ingredient required quantity in base unit; the no-recipe diagnostic surfaced.
  • Optional netting (caller flag, default on) against Spec 052 available stock → a shortfall column and a suggested order quantity (§11 seed precedence); degrades to "requirement only" with netAgainstStock = false.
  • An explicit, documented order-inclusion filter (which order statuses, which date field) — see §9.
  • Two admin read endpoints (get production sheet, get prep list — each for a window) + two direct commerce-agent read tools, each recording an AiRun.

Out of scope

  • Any new persisted entity or migration. This is a pure read/aggregation spec; a persisted plan snapshot is Open.
  • Forecast demand. v1 plans from actual in-window orders only; predictive demand is Open.
  • Named / rolling production windows. v1 takes a date range; a ProductionWindow entity is Open.
  • Excluding demand already produced. v1 counts all in-window demand; netting against completed production orders to avoid double-making is Spec 056 / Open.
  • Raising reorder alerts or placing purchase orders — the prep list only surfaces a suggested reorder; alerting is Spec 052, procurement is Spec 053.

6. Constraints & guardrails

  • No reference to Finance. Orders are read through the SharedKernel.Abstractions.Ordering read contract / order projections — Commerce reads the orders it created on the shared spine, not via any Aonik.Finance reference. Aonik.Commerce still references only SharedKernel + Aonik.Ordering (ADR-005).
  • No new schema. No entity, no DbSet, no migration. Both artefacts are computed on read from existing data (order projections + recipes + optional inventory).
  • Explicit inclusion filter. Which order statuses count and which date field defines "in the window" is documented and centralised (§9), never left implicit — this is the spec's chief correctness risk.
  • Explosion is reused, not reimplemented. The prep list calls IRecipeService.ExplodeManyAsync (050 §11); 055 owns aggregation and presentation, not BOM math.
  • Netting is optional and non-blocking. Spec 052 has landed, so the on-hand source is always present; the optionality is the caller's netAgainstStock flag — false returns pure requirements with no shortfall column.
  • Agents propose; systems execute. Both planning tools are reads — direct execution, no mutation, no approval gate — and every invocation records an AiRun.

8. Domain model (contracts, no entity)

There is no new persisted entity in v1 — the only additions are read-model DTOs in Contracts/Models/Production/PlanningModels.cs. A window is a plain pair of UTC instants (a named/rolling ProductionWindow entity is Open). Order.CreatedAt — the §9 date field — is a UTC DateTime, so the window is two UTC instants with half-open semantics ([FromUtc, ToUtc)), not a DateOnly pair whose closed upper bound would hide an end-of-day conversion rule inside the very filter this spec calls its chief correctness risk. 

// No entity, no DbSet, no migration. Read-model DTOs only.

record ProductionWindow  ( DateTime FromUtc, DateTime ToUtc );   // UTC instants, half-open [From, To); not persisted

record ProductionSheetDto( ProductionWindow Window,
                           IReadOnlyList<ProductionSheetLineDto> Lines,
                           int TotalOrders,            // orders admitted by the §9 inclusion filter
                           int BundleLinesExpanded );  // bundle order lines expanded via OrderBundleSelection (§9)
record ProductionSheetLineDto( Guid ProductVariantId, string ProductName, string VariantName,
                           decimal PortionsDemanded, int OrderCount );
                           // names resolved from the live catalog, LEFT-join semantics: an
                           // unresolvable variant still shows, with diagnostic placeholder names

record PrepListDto       ( ProductionWindow Window,
                           IReadOnlyList<PrepListLineDto> Lines,
                           IReadOnlyList<Guid> VariantsWithoutRecipe,   // no-recipe diagnostic (050 §11)
                           bool NettedAgainstStock );
record PrepListLineDto   ( Guid IngredientId, string IngredientName, string BaseUnit,
                           decimal RequiredQuantity,
                           decimal? Available,       // Spec 052 Available = OnHand − Reserved; null when not netting
                           decimal? Shortfall,       // max(Required − Available, 0), null if Available null
                           decimal? SuggestedOrderQuantity );  // §11 seed precedence; null when no shortfall
interface IProductionPlanningService {
  Task<ProductionSheetDto> GetProductionSheetAsync(ProductionWindow window, CancellationToken ct = default);
  Task<PrepListDto>        GetPrepListAsync(ProductionWindow window, bool netAgainstStock = true, CancellationToken ct = default);
}

GetPrepListAsync is defined as GetProductionSheetAsync composed with ExplodeManyAsync composed with optional netting — it never re-queries orders differently or re-implements explosion. Netting is the caller's choice: with netAgainstStock = false, Available/Shortfall/SuggestedOrderQuantity are left null and the prep list is a pure requirements list (see §11 — Spec 052 has landed, so the on-hand source is always present and the old capability check materialises as this flag).

9. Demand aggregation (the production sheet)

The production sheet answers "what must the kitchen make this window, and how many portions of each?". It is built entirely from orders read via the Ordering read contract — Commerce reads the ProductPurchase orders it itself created on the shared spine (Spec 041), with no Aonik.Finance reference.

GetProductionSheetAsync(window) → read ProductPurchase orders WITH LINE ITEMS via IOrderService.ListWithItemsAsync WHERE order-inclusion filter holds for `window` (see the explicit filter below) → for each order line: line HAS OrderBundleSelection rows (OrderId + OrderItemIndex) // a build-your-own-box line → expand: each selection row is (component variant, TOTAL quantity) — real kitchen demand else → portions = OrderItem.Quantity, variant = soft-ref ProductId → group by ProductVariantId, sum portions, count distinct orders → resolve names from the Commerce catalog (LEFT join — unresolved variants keep diagnostic names) → return ProductionSheetDto { window, [ {variant, names, portionsDemanded, orderCount} ], totalOrders, bundleLinesExpanded }

The single most important design decision here is the order-inclusion filter — which orders count, and by which date. It is made explicit and centralised (one status set + one windowed query in ProductionPlanningService) so it can be reasoned about and tested, and so §11 and Spec 056 share one definition:

Filter dimensionv1 ruleRationale
Order typeOrderType == "ProductPurchase" onlyOnly sell-side product demand drives production; purchase orders (Spec 053) and other order types are excluded.
StatusCommitted, non-terminal-failed statuses — exactly { Pending, UnderReview, Approved, Transmitted, Complete } from OrderStatusCodes. Excluded: Draft, Cancelled, Failed, Expired.Plan against real committed demand, not speculative baskets. Checkout creates the ProductPurchase order in Draft and only payment completion advances it to Complete (Spec 042 §11) — a Draft is an initiated, unpaid checkout, so counting it would cook for orders that may never fund. Cancelled/Failed/Expired are the terminal failures (IsTerminal() minus Complete). The in-between codes are non-terminal committed states any ops flow may use and are included.
Date fieldThe order creation instant (Order.CreatedAt, UTC) must fall in the half-open [FromUtc, ToUtc)The Order spine exposes no product fulfilment/needed-by date on Order or OrderFulfilmentRef, and this spec adds no schema; v1 filters on CreatedAt only, the one demand-date field available. Half-open bounds mean adjacent windows tile without double-counting a boundary order. A requested needed-by date is an additive spine field — see Open.
Quantity — simple/variant lineOrderItem.Quantity = portions for the variant in OrderItem.ProductIdA ProductPurchase line already carries retail quantity, and checkout writes the variant id into the soft-ref ProductId for simple lines (Spec 041/042 line shape); one unit sold = one portion demanded.
Quantity — bundle lineExpanded through OrderBundleSelection: each selection row contributes (ProductVariantId, Quantity) demand; the bundle line itself is never countedA build-your-own-box line carries the bundle product id in ProductId, not a variant (Spec 042 §12 Option A) — the kitchen makes the chosen components. Commerce owns the selection rows (soft-linked by OrderId + OrderItemIndex, quantities already the line totals: selection × boxes), so the expansion is a direct Commerce read. A line is a bundle line exactly when selection rows exist for it; without rows it falls through as simple demand and an unresolvable ProductId surfaces via the diagnostic names.

This filter is the answer to the "which orders count" risk (§19): it is documented, lives in one place, and is covered by tests that assert a cancelled order, a draft (unpaid-checkout) order, and an out-of-window order are all excluded, and that both window boundaries behave half-open.

Contract note Two additive Ordering-contract extensions carry this read (grounded against the landed contract; precedent: the Spec 053/054 additive changes). ListOrdersQuery gains optional CreatedFromUtc/CreatedToUtc bounds (half-open, applied by CoreOrderService's one shared list predicate) so the demand query is period-bounded at the spine; and IOrderService gains ListWithItemsAsync(ListOrdersQuery) → PagedResult<OrderDto>, because the sheet aggregates per-line Quantity/ProductId and the existing ListAsync returns OrderSummary, which deliberately carries only an item count. Commerce holds no reference to the Ordering DbContext — the contract is the only path, so the aggregation composes the contract rather than reaching into another module's tables.

10. BOM explosion (the prep list)

The prep list is the production sheet run through the Spec 050 explosion primitive — this spec is the motivating consumer 050 §11 was written for. It does not re-derive anything; it hands the sheet's {variantId, portions} pairs straight to ExplodeManyAsync:

GetPrepListAsync(window, netAgainstStock = true) → sheet = GetProductionSheetAsync(window) // §9 — same window, same filter → bom = IRecipeService.ExplodeManyAsync( // Spec 050 §11 sheet.Lines.Select(l => VariantDemand(l.ProductVariantId, l.PortionsDemanded)) ) // ExplodeManyAsync: explode each variant's active Recipe, scale by portions / YieldQuantity, // then SUM RequiredQuantity per IngredientId → the merged bill of materials → when netAgainstStock: net each ingredient line vs Available (OnHand − Reserved) from Spec 052 // §11 → return PrepListDto { window, Lines = bom lines → { ingredient, baseUnit, requiredQuantity, available?, shortfall?, suggested? }, VariantsWithoutRecipe = bom.diagnostics, // variants 050 flagged as having no active recipe NettedAgainstStock = netAgainstStock }

Because ExplodeManyAsync already sums per IngredientId across variants (050 §11), "40 jollof + 30 steak" collapses to a single merged prep list where rice from jollof and rice from steak add into one 10 kg line. The no-recipe diagnostic from 050 (R5 — a variant with no active recipe explodes to an empty bill with a flag) is surfaced verbatim as VariantsWithoutRecipe, so the operator sees "steak has no recipe defined" rather than a prep list that quietly under-counts.

11. Netting against stock — the shortfall (Spec 052)

A prep list of pure requirements ("you need 10 kg rice") is useful; a prep list that also says "you have 2 kg available, so you're short 3 kg — order a 25 kg sack" is what the operations manager actually acts on. That netting is optional (the caller's netAgainstStock flag, default true) and layered on top of the requirement, drawing available stock (not raw on-hand) from the landed Spec 052 read (IInventoryService.GetStockLevelAsync(StockItemRef.Ingredient(id))): 

foreach ingredient line in the exploded prep list (when netAgainstStock):
    Available = Spec 052 Available = OnHand − Reserved              // NEVER raw OnHand; never-stocked reads as 0
    Shortfall = max(RequiredQuantity − Available, 0)
    SuggestedOrderQuantity =                                        // the Spec 053 SHORTFALL-SEED precedence,
        Shortfall == 0            → null                            // mirrored so the suggestion equals what
        ReorderQuantity set (>0)  → ReorderQuantity, as-is          // CreateFromShortfallAsync would order:
        cheapest active 053 catalog row exists (single currency)    // 052's explicit operator suggestion wins;
                                  → ceil(Shortfall / PackSize) × PackSize   // else whole packs of the cheapest
        else                      → Shortfall                       // per-base-unit row; else cover the gap

The shortfall nets against Spec 052's Available (= OnHand − Reserved), never raw OnHand, so the prep list never promises stock already held for another flow (production holds and the like). Concretely: 10 kg on hand, 8 kg reserved, 5 kg required nets against 2 kg available and reports a 3 kg shortfall — not a false "in stock" that netting raw on-hand would give.

The pack rounding composes the Spec 053 supplier catalog: "cheapest" means the lowest per-base-unit price (PackPrice / PackSize) among active suppliers' rows for the ingredient. Commerce holds no FX, so per-unit prices are only rankable within one currency — an ingredient whose active rows span multiple currencies skips pack rounding and falls back to the raw shortfall (a documented v1 limitation; FX-aware ranking is Open). Spec 052 having landed, the on-hand source is always present; the old "ships before 052" capability check materialises as the netAgainstStock flag — false keeps Available/Shortfall/SuggestedOrderQuantity null and the prep list is a plain requirements list. The suggested order quantity is only a suggestion surfaced on a read — 055 raises no alert and places no purchase order; that is Spec 052 (alerts) and Spec 053 (procurement).

12. Defining a window

For v1 a window is simply a ProductionWindow(FromUtc, ToUtc) — two UTC instants, half-open (FromUtc inclusive, ToUtc exclusive), passed on the request. There is no persisted, named, or rolling window; the caller supplies "this week", "tomorrow", or any explicit range, and the service applies the §9 inclusion filter against it. The same window flows unchanged into both the production sheet and the prep list so the two are always consistent for a given call. The service validates the window up-front: FromUtc < ToUtc, and a maximum span of 92 days bounds the demand query (§14's period-bounded guarantee cannot be defeated by a fat-fingered range).

Open Named / rolling windows. A persisted ProductionWindow entity ("Mon–Fri kitchen week", a rolling next-7-days) with its own identity, so a plan can be referenced and re-opened. v1 takes an ad-hoc date range; the DTO is shaped so a persisted window can supply the same FromUtc/ToUtc later without changing callers.

13. Agent & tools

The existing commerce-agent gains two read tools. Per the landed house convention, read tools are omitted from CommerceToolApprovalManifest — the Spec 032 gate passes unclassified, read-looking tools through (exactly like commerce_list_low_stock and the rest of the read set) — and the manifest tests pin them as unclassified. Both execute directly (no approval), tenant-scoped from context, and each records an AiRun via the gate pipeline:

ToolTierEffect
commerce_get_production_sheetreadReturns the aggregated per-variant portion demand for a window ("40 jollof, 30 steak").
commerce_get_prep_listreadReturns the exploded per-ingredient requirement for a window, with the shortfall column when Spec 052 is present and the no-recipe diagnostic always.

These join the family's read set (commerce_list_ingredients, commerce_get_recipe, commerce_check_ingredient_stock, commerce_list_low_stock, …). No new medium or high tool is introduced — planning is read-only; the mutations it informs (reorder, create purchase order, create production order) live in Specs 052/053/056.

14. CommerceDbContext & migrations

No migration This spec adds no schema. It defines no entity and no DbSet, so there is no EF-CLI migration against AonikDbContext and no change to CommerceDbContext. Both artefacts are computed on read from existing data — order projections (via the Ordering read contract), recipes (Spec 050), and optional inventory (Spec 052). A persisted plan snapshot — which would introduce a table and a migration — is a follow-up under Open.

The only performance-relevant note: the production-sheet query is period-bounded (it filters orders to the window and to ProductPurchase), and relies on the Ordering spine's existing indexes on the order date field and type — see the aggregation-performance risk (§18). No index is added by this spec; if one is needed it belongs to the Ordering/Order-spine schema, not to Commerce.

15. Phased rollout

Phase 1 — Production sheet (demand aggregation)

Per-variant portion demand over a window.
  • The additive Ordering-contract extension (§9 contract note: ListOrdersQuery.CreatedFromUtc/CreatedToUtc, ListWithItemsAsync) with a CoreOrderService test; then IProductionPlanningService.GetProductionSheetAsync(window) reading ProductPurchase orders through that contract, applying the explicit §9 inclusion filter (type/status set/half-open window), expanding bundle lines via OrderBundleSelection, grouping by ProductVariantId, resolving catalog names (LEFT join); ProductionSheetDto/LineDto; a GET admin endpoint; unit tests for the filter (cancelled/draft/out-of-window excluded, boundaries half-open) and the bundle expansion.

Phase 2 — Prep list (BOM explosion)

Explode the sheet through recipes; surface the no-recipe diagnostic.
  • GetPrepListAsync(window, netAgainstStock) = sheet → IRecipeService.ExplodeManyAsync (Spec 050 §11) → merged per-Ingredient requirement; PrepListDto/LineDto including VariantsWithoutRecipe; a GET admin endpoint; unit tests for multi-variant merge and the no-recipe diagnostic.

Phase 3 — Optional netting + agent tools

Shortfall against available stock; the agentic surface.
  • Netting against Spec 052 available stock → Shortfall + SuggestedOrderQuantity (null with netAgainstStock = false); the two direct read tools (commerce_get_production_sheet, commerce_get_prep_list) added to CommerceAgentTools, left unclassified in CommerceToolApprovalManifest per the read convention, routed through IToolApprovalGate.GateAll; each records an AiRun.

19. Risk register

20. Decisions baked in

  • 055 is a read/aggregation spec — no new entity, no DbSet, no migration; both artefacts are computed on read. The only contract change is the additive Ordering extension (§9 contract note).
  • The production sheet aggregates ProductPurchase demand by variant over a half-open UTC window on Order.CreatedAt, read through the Ordering read contract — never via a Finance reference — counting only the committed §9 status set (never Draft or the terminal failures).
  • Bundle order lines are expanded, never counted as demand — a build-your-own-box line's OrderBundleSelection components are the kitchen demand (Spec 042 §12 Option A); the bundle product id itself never reaches the sheet.
  • The prep list is the exploded sheet — it calls Spec 050's ExplodeManyAsync (055 is that primitive's primary consumer) and never re-implements BOM math.
  • Netting against available stock is caller-optional (default on) — a shortfall (vs Spec 052's Available = OnHand − Reserved, never raw on-hand) + a suggested order quantity per the Spec 053 seed precedence; pure requirements with netAgainstStock = false.
  • The no-recipe diagnostic is surfaced, not swallowed — variants without a recipe are reported, never under-counted; unresolvable variants keep diagnostic names, never dropped.
  • A window is a plain UTC range in v1 (validated: From < To, ≤ 92 days); named/rolling windows, forecast demand, and a persisted snapshot are Open.

21. Open design decisions

Open Persisted plan snapshot. Storing a computed production sheet / prep list (with a table and a migration) so a plan is reproducible and can be referenced after the underlying orders change. v1 recomputes on read; the DTOs are the natural shape a snapshot would persist.
Open Named / rolling production windows. A ProductionWindow entity with its own identity (a saved "kitchen week", a rolling next-N-days) rather than an ad-hoc date range on the request.
Open Requested / needed-by fulfilment date. v1 filters the window on order creation date (Order.CreatedAt) because the Order spine carries no product fulfilment/needed-by date on Order or OrderFulfilmentRef. Planning by when a thing is needed — so an order placed today but due tomorrow lands in tomorrow's sheet — requires an additive field on the Order spine (a small OrderFulfilmentRef/Order column). That is a follow-up, and adopting it would change this spec's no schema change claim; the §9 filter is centralised so only its date predicate would move.
Open Forecast demand vs. actual-order demand. Planning from predicted demand (history / seasonality) in addition to confirmed in-window orders. v1 plans strictly from actual ProductPurchase orders.
Open FX-aware cheapest-pack ranking. §11's pack rounding ranks catalog rows by per-base-unit price only when an ingredient's active rows share one currency; Commerce holds no FX, so mixed-currency catalogs fall back to the raw shortfall. Ranking across currencies needs a rate source (a Finance seam), deliberately not taken in v1.
Open Excluding demand already produced. Netting the production sheet against completed Spec 056 production orders so already-made portions are not re-planned. v1 counts all in-window demand; this requires the production-order link that 056 introduces.
