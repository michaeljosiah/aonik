Spec 072 Draft Size: Medium Modules: Aonik.Commerce, Aonik.Platform, SharedKernel Depends on: Spec 068 (R10) 2026-07-22

Storefront customer identity — accounts, cart adoption & my orders

Fills the R10 party half Spec 068 left waiting: the storefront's login/register pages get their first real contract, a guest box survives signing in, and customers can see their own orders. Registration and login are the platform's EXISTING capabilities — this spec adds the Commerce seam, not a parallel auth stack.

1. Summary

The platform already owns everything an account needs: POST /v1/registrations/individual provisions the IdP user, the platform User, an Individual Party with the Customer party role, the UserParty link and the PersonalUser role; POST /auth/token exchanges email+password for tokens through the operator-choice IdP (ADR-007); POST /auth/forgot-password is enumeration-safe; and the JWT pipeline rejects same-tenant tokens for unprovisioned users, so register-before-login is already enforced. Spec 072 adds no auth endpoints. It adds the Commerce-side seam: a SharedKernel party resolver so cart access can honour authenticated principals, guest→account cart adoption, authenticated cart creation, and party-scoped order reads.

2. What the storefront calls today (existing platform surface)

ConcernExisting endpointNotes
RegisterPOST /v1/registrations/individualAnonymous; resolves tenant from body/subdomain/X-Tenant-Id; provisions IdP user + User + Party + PersonalUser role. 409 on duplicate email.
LoginPOST /auth/token (grantType: "password")Code-complete for Auth0 (password-realm) and Keycloak (direct access grants — enable per Spec 029 §8.6). Deployment prerequisite, not code.
RefreshPOST /auth/token (grantType: "refresh_token")Same exchange surface.
Forgot passwordPOST /auth/forgot-passwordSilent on unknown email.
Who am Iexisting user-info read (UserInfoResponseDto carries PartyId)Unchanged.

Hard gate (already enforced): a same-tenant JWT whose iss+sub is not a provisioned Active User is rejected by ResolveOrCreateUserAsync — a login-only flow cannot bootstrap an account. Social federation (the storefront's Google button) is the IdP's job per ADR-007 and out of scope here.

3. What this spec adds

#Addition
Y1ICurrentPartyResolver (SharedKernel): Task<Guid?> GetCurrentPartyIdAsync(ct) — null when anonymous or unlinked. Platform implementation: current user id → latest UserParty → PartyId (the GetPrimaryPartyAsync rule). The same cross-module seam shape as ITenantCurrencyProvider.
Y2Cart access gains its party half: the cart endpoints build CartAccessContext(guestToken, partyId) from the header AND the resolver — every cart route (generic, box, extras, checkout) presents both. Party-bound carts authorize by principal exactly as R10 declared; guest carts are unchanged.
Y3Authenticated create binds the caller's party: when a create request carries a resolvable principal, the cart is born party-bound (BuyerPartyId = resolved party). The body-supplied buyerPartyId STAYS rejected — the principal is the only source. Guest create is unchanged; the token remains guest-cart-only in meaning.
Y4Guest→account adoption: POST /commerce/carts/{cartId:guid}/adopt (authenticated, PersonalUser-admitting policy). Requires BOTH halves: the X-Cart-Token proves possession of the guest cart, the principal supplies the party. Sets BuyerPartyId, clears AnonymousToken. Idempotent when the SAME party adopts again; every other mismatch is the R10 404 (no oracle). Open carts only (R9 applies — an ordered cart's buyer is fixed).
Y5My orders: GET /commerce/storefront/orders (party-scoped summaries: order id, created, status, currency, total from the charge summary, box size when present) and GET /commerce/storefront/orders/{orderId:guid} (detail incl. items and the box's selection rows). Only the caller's party's orders resolve; everything else 404s.

4. Server-enforced rules

#Rule
Z1The principal is the only source of a cart's party: body-supplied buyer ids stay rejected on the public routes.
Z2Adoption needs possession AND identity: absent/wrong token → 404; anonymous caller → 401/403; a cart already bound to ANOTHER party → 404 (indistinguishable).
Z3Adoption clears the guest token — a leaked pre-adoption token must be dead afterwards.
Z4R9 bounds adoption: a cart whose OrderId is stamped (or not Open) cannot change its buyer.
Z5My-orders reads are party-scoped at the query: another party's order id is a 404, never a 403 (no existence oracle).
Z6The storefront-order reads admit PersonalUser (the platform's B2C role) — no admin role required, no new role invented.

5. Persistence & migration

No migration. Cart.BuyerPartyId, AnonymousToken, Order.PayerPartyId and OrderChargeSummary all exist. The resolver is a read over UserParty.

6. Testing

  • Resolver: linked user → party; unlinked/anonymous → null.
  • Adoption: guest→party binds and clears the token (old token 404s after); same-party idempotent; foreign-party/ wrong-token 404; ordered cart rejects (R9).
  • Authenticated create binds the party; body buyerPartyId still rejected; guest create unchanged.
  • My orders: only own orders list; foreign order id 404; detail carries items + selections.
  • API: adopt journey (guest cart → authenticated adopt → party GET works, token GET 404s); my-orders authz (anonymous rejected, PersonalUser admitted).

7. Acceptance criteria

#Given / when / then
C1Guest builds a box → registers & logs in (platform endpoints) → adopt with both credentials → cart is party-bound, the guest token no longer authorizes, and the party principal does.
C2Adopt with the right token but no bearer → 401/403; with a bearer but wrong token → 404; adopting a cart already bound to another party → 404.
C3Authenticated create → cart born party-bound; the same request with a body buyerPartyId → 400 (unchanged rejection).
C4Two customers each check out a box → each sees exactly their own order in /commerce/storefront/orders; requesting the other's order id → 404.
C5After checkout, adopt on that cart → rejected (R9); the order's buyer is immutable.

8. Open decisions

O1 — Social login. The storefront's Google button rides the IdP's own federation (Keycloak brokering per ADR-007) via an authorization-code flow the FRONTEND drives; the resulting JWT validates unchanged. No Aonik surface; noted so nobody builds one.

O2 — Registration UX composition. If the storefront wants register+login in one round-trip, a later thin composition endpoint can wrap the two platform calls; deliberately not built until the frontend proves the need.
