Merchandising — collections, the extras rail and facet groups

/commerce/merchandising · MerchandisingPage. Design of record: artboard cs-merch (PR #268). What the shop window shows and how the catalogue filters — all of it data. Two tabs: Collections (ranked membership with a live rail preview) and Facet groups (match semantics as rows, never code).

2 · Page structure

  1. KPI row — collections, curated members (Σ itemCount — drafts included, matching the admin semantics), facet groups, drafts staged (computed from collection details' member statuses; show — until details load).
  2. Tab strip (UnderlineTabs): Collections · Facet groups.
  3. Collections tab — left rail of collections (title, slug mono, member count; the collection whose slug equals extrasCollectionSlug carries an EXTRAS RAIL badge). Right, for the selected collection:
    • Ranked membership editor: rows drag-handle · rank (mono, 2-digit) · product (name + status) · unit price (extras only) · state pill. State pill logic: draft product → Draft — staged (warning, row ghosted); extras member with null public price → Unpriceable — skipped publicly (warning) — the member stays in the admin table so it can be repriced, reordered or removed (round-2 finding); otherwise Live. Reordering is drag-free v1: up/down row actions renumber ranks locally; Save issues the full replace. Add-member opens a product picker Sheet (search over listProducts).
    • Storefront rail preview: a horizontal card strip rendering the membership in rank order as the public read serves it — drafts hidden, unpriceable extras hidden; extras cards show unitPrice, dish cards show "no standalone price". For the extras collection, source the strip from GET /commerce/catalog/extras (the actual public read) and show the skipped count as a warning strip when > 0, quoting that the public read omits and counts, never silently drops.
  4. Facet groups tab — table: group (label + facet.{key} mono) · match kind (Pill, tint for Range) · source (mono, — for Tag/Category) · options (chips; Range chips append [min,max) mono) · active · edit. Create/edit Sheet with the immutability rule stated: "A live group's key and match kind never change — retire and replace instead." Footer caption: "The storefront submits option values, never labels."

3 · Implementation instructions

  • Files: src/pages/commerce/MerchandisingPage.tsx; components/CollectionMembersEditor.tsx, components/RailPreview.tsx, components/FacetGroupSheet.tsx. Route + breadcrumb in commerceModule.
  • Membership editing model: local draft of items[]; every move renumbers ranks 1..n contiguously; Save maps to { productId, rank } lines and full-replaces, then reloads. Dirty indicator on Save; discard resets to the loaded detail.
  • Preview truth: the non-extras preview derives client-side (filter drafts) from the admin detail; the extras preview uses the real public read so admin-vs-public divergence (skipped members) is shown from the genuine source, not simulated.
  • Facet options editor: chips with add/remove; Range rows expose min/max numeric inputs; serialisation to optionsJson lives in lib/facetOptions.ts with unit tests (band ordering, half-open rendering).
  • Errors: rank-uniqueness or replace conflicts surface as the inline banner (userMessage); create/edit Sheets show formError; successes toast.

4 · Acceptance

  1. Reordering members updates the preview strip live; Save round-trips and a fresh load renders the same order (full-replace idempotence).
  2. A draft member is ghosted in the editor, absent from the preview, and counted in the admin KPI.
  3. An unpriceable extras member stays editable in the table with its warning pill, is absent from the preview, and the skipped strip shows the public read's count.
  4. A Range facet renders its half-open bands; edit cannot alter key or match kind (fields read-only with the retire-and-replace note).
  5. The extras collection is identified purely by extrasCollectionSlug from config — renaming the setting rebadges with no code change.
