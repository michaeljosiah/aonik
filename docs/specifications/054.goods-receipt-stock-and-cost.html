Spec 054 Status: Draft Size: Small Priority: P3 Domain: Commerce / Sourcing

Goods receipt (stock + cost) — receiving a purchase order into raw-material on-hand

Closes the procurement loop opened by Spec 053: it is the moment "once stock is confirmed". Receiving a purchase order turns an ordered PO into raw-material on hand — incrementing ingredient stock (Spec 052), refreshing landed cost (Spec 051), resolving the low-stock alert that triggered the reorder, and transitioning the PO on the shared Order spine. This is a small, dependent spec in the maker-operations family (050–057), which hangs off the recipe keystone in Spec 050. Everything lives in Aonik.Commerce and references only SharedKernel + Aonik.Ordering — never Aonik.Finance.

1. Summary

Spec 053 lets an operator place a purchase order with a supplier when a low-stock alert fires. But an ordered PO is a promise, not stock: the ingredient on-hand is unchanged, the alert is still open, and the PO sits Pending (submitted — the landed Spec 053 mapping onto the existing spine OrderStatusCodes). This spec adds the receiving step that makes the delivery real — the "goods have arrived, put them away" action.

It introduces two anemic entities in Aonik.Commerce and one service:

  • GoodsReceipt + GoodsReceiptLine — a receipt recorded against a PurchaseOrder, with a received quantity (and optional actual unit cost) per ingredient line.
  • IGoodsReceiptService.ReceiveAsync — the one operation that, in a single guarded, claim-first receive (§8), increments ingredient on-hand (052), optionally refreshes landed cost (051), resolves the source low-stock alert(s) on demonstrated recovery, and transitions the PO on the Order spine.
Success signals An operator (or the commerce-agent) receives a submitted (Pending) PO — fully or partially — and reads back higher ingredient on-hand, a resolved low-stock alert, a refreshed IngredientCost when an actual cost was entered, and a PO that moved to Complete (fully received) or stayed Pending (partial). Re-submitting the same receipt does not double-count stock. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering; dotnet test Aonik.sln stays green with new unit tests covering receive, partial receive, idempotency, and cost refresh.

2. Context & motivation

In the operations-manager day-in-the-life, receiving is the pivot between "we're low, order more" and "we're stocked, make food." The low-stock alert (052) drives a reorder; the reorder is a PO (053); the PO is fulfilled when the supplier delivers. Until that delivery is recorded, none of the downstream numbers move: the prep list (055) still shows a shortfall, the standard-cost rollup (051) still uses the old price, and the alert still nags. Goods receipt is the single write that reconciles all of them.

It is deliberately the convergence point of three earlier specs rather than new machinery of its own. The stock increment lands through a signed-increment IInventoryService.AdjustOnHandAsync this spec adds beside the Spec 052 set-on-hand surface (a receipt increments, never overwrites, so a concurrent set/receive never loses the other's movement); the cost refresh reuses the Spec 051 effective-dated IngredientCost write; the PO transition reuses the Spec 041 Order spine (IOrderService.TransitionAsync). This spec's own surface is small: the receipt record, the orchestration, and the idempotency guard that keeps a double-submit from double-counting.

4. Scope (in / out)

In scope

  • GoodsReceipt + GoodsReceiptLine entities + configs + DbSets.
  • IGoodsReceiptService.ReceiveAsync(purchaseOrderId, idempotencyKey, lines, ct): increment on-hand via the new AdjustOnHandAsync (052 levels), optional cost refresh (051), resolve alert(s) only when live available clears the live reorder point (052/054), transition the PO to Complete when fully received (041).
  • Partial receipts: receive less than ordered; the PO stays Pending (partially received is derived, never a status) and can be received again until fully satisfied.
  • Idempotency guard: a required client-supplied IdempotencyKey under a per-tenant DB UNIQUE constraint, resolved before any mutation (and before the status guard); the receipt row, persisted first, is the applied-once claim that keeps a re-submitted / duplicate receive from double-counting stock.
  • Admin endpoint to receive goods against a PO; commerce-agent medium-gated commerce_receive_goods tool.
  • One tool-generated migration (CommerceGoodsReceipts) creating AnkGoodsReceipts + AnkGoodsReceiptLines.

Out of scope

  • Paying the supplier (PO funding via PaymentIntent) — Spec 053 follow-up.
  • Landed-cost allocation (spreading freight/duty across lines) — UnitCostActual is ex-supplier in v1; noted under Open.
  • Quality hold / rejected lines / returns to supplier — v1 records received quantity only; noted under Open.
  • Over-/under-receipt tolerance policy — v1 rejects any over-receipt outright, naming the ingredient (§9); a tolerance band is Open.
  • Lot/batch numbers, expiry dates, bin locations — not in v1.

5. Constraints & guardrails

  • No reference to Finance. Aonik.Commerce references only SharedKernel + Aonik.Ordering; the PO transition rides the Ordering spine, not a Finance call (ADR-005).
  • Anemic entities. GoodsReceipt/GoodsReceiptLine are { get; set; } data containers implementing ITenantScoped + AuditableEntity (ADR-002); all logic lives in GoodsReceiptService returning DTOs.
  • Single migration stream. EF-CLI-generated against AonikDbContext; Ank-prefixed tables; CommerceDbContext is runtime scoping with no migrations; agents never hand-author migrations.
  • Idempotent by construction. ReceiveAsync validates everything up-front, then persists the receipt FIRST under a per-tenant DB UNIQUE IdempotencyKey (resolved before any mutation) — the applied-once claim ahead of every stock/cost commit — so a duplicate submit, including a post-commit retry, returns the existing receipt and stock is incremented exactly once (§8).
  • Cost is superseded, not mutated. An actual cost writes a new effective-dated IngredientCost row; the prior row (including a manually set standard cost) is retained for history (§10).
  • Agents propose; systems execute. Receiving is a medium tool — in-session confirmation, args-hash-bound — and records an AiRun.

7. Domain model

All entities are anemic, ITenantScoped, inherit AuditableEntity.

class GoodsReceipt     { Guid Id, TenantId, PurchaseOrderId;
                        string   IdempotencyKey;   // client-supplied; UNIQUE index (per tenant)
                        DateTime ReceivedAt;
                        string   Status;   // Posted (v1; Draft reserved for a future review workflow)
                        string?  Notes; }

class GoodsReceiptLine { Guid Id, TenantId, GoodsReceiptId, IngredientId;   // flat soft-link, no navigation
                        decimal  QuantityReceived;   // in the ingredient's BaseUnit, normalized to 4 dp
                        decimal? UnitCostActual;     // ex-supplier cost, per BaseUnit; null ⇒ no cost refresh
                        string?  Currency;           // of UnitCostActual — stamped from the PO's CurrencyIn }

GoodsReceipt.PurchaseOrderId is a soft reference to the Spec 053 PurchaseOrder (an Order on the Spec 041 spine); a PO may have many receipts (one per partial delivery). GoodsReceiptLine.IngredientId matches the PO line's soft ingredient reference (OrderItem.ProductId = IngredientId, per the Spec 053 line shape). QuantityReceived is always in the ingredient's BaseUnit (Spec 050); UnitCostActual, when present, is per that base unit and drives the cost refresh (§10), and Currency qualifies it — stamped from the PO's CurrencyIn, because the Spec 051 cost write requires a currency and the PO is what the price was agreed in. A receipt carries one line per ingredient (a second delivery is a second receipt — duplicates would write two same-instant cost rows ambiguously), and quantities/costs are normalized to the 4 dp column scale before validation, per the Spec 053 convention. IdempotencyKey is the idempotency lever: it is client-supplied and carries a DB UNIQUE index, so a retried receive resolves back to the already-posted receipt (§8) rather than opening a fresh one — mirroring the Order spine's CreateOrderCommand.IdempotencyKey. Status is a marker, not a guard: ReceiveAsync is an atomic single call, so v1 persists a receipt straight to Posted — the row's existence under the unique key IS the applied-once claim, and a separate Draft state would only be ambiguous on retry (partially-applied effects are unknowable). Draft stays reserved for a future review-before-post workflow.

8. The receiving flow (stock up → cost refresh → alert resolve → PO transition)

ReceiveAsync is the whole spec. It validates everything up-front, claims the idempotency key by persisting the receipt first, then runs the four downstream effects in this order:

IGoodsReceiptService.ReceiveAsync(purchaseOrderId, idempotencyKey, lines[], ct) 0. RESOLVE the receipt by IdempotencyKey (per-tenant DB UNIQUE) — FIRST, before every guard ── idempotency a receipt for this key already exists (already applied) → return it, NOTHING re-applied (before the status guard too: a retry of a receive that COMPLETED its PO must not be rejected by the Pending check — the Spec 053 lesson) 0. GUARD load the PO (053); reject unless Pending (submitted) — Draft/Cancelled/Complete refused lines: one per ingredient, each ON the PO (ProductId soft-ref), quantities > 0 (at 4 dp); cumulative received (prior receipts + this one) must not exceed ordered per ingredient → violations rejected NAMING the ingredient. ALL validation runs before anything persists. 1. CLAIM persist the receipt + lines, Posted — the applied-once claim (first commit): from here a keyed retry returns THIS receipt, whatever happens below 2. STOCK ▲ for each line → IInventoryService.AdjustOnHandAsync(Ingredient(id), quantity) (052+054) a signed increment — raises the ingredient's InventoryLevel.OnHand, never overwrites it 3. COST ↻ for each line with UnitCostActual set → write a new effective-dated IngredientCost (051) (EffectiveFrom = ReceivedAt, currency = the line's PO-stamped Currency); the prior cost row is superseded, not mutated 4. ALERT ✓ ILowStockAlertService.ResolveIfRecoveredAsync(receivedIngredientIds) (052/054) live available (OnHand − Reserved) STRICTLY above the level's live reorder point → flip the unresolved alert (Open/Acknowledged/Ordered) → Resolved still at/below, level missing, or reorder point cleared → left exactly as it was 5. PO → compute received-vs-ordered across all receipts for this PO: fully satisfied → TransitionAsync(po, Complete, "Fully received", expectedFromStatus: Pending) (041) short → leave the PO Pending (partial receipt is DERIVED, not a status) → return { receipt, per-line ordered/cumulative/on-hand-after, alertsResolved, costRowsWritten, poStatus }

The composed services each own their SaveChanges, and the PO transition rides the separate Ordering context — so this is an ordered sequence of commits, not one transaction (the same two-context reality Spec 053 documented for its alert flip). The ordering is the guard: every validation runs before the claim, so a post-claim failure is infrastructure-only and the system fails toward under-application — a Posted receipt whose keyed retry returns it without re-applying (visible, reconciled by hand at worst) — never toward double-counted stock, this spec's High risk. The client-supplied IdempotencyKey is resolved before any stock/cost mutation and before the Pending guard, so a client or agent that times out after the claim and retries gets the existing receipt back rather than a second application — mirroring the Order spine, whose CreateOrderCommand already carries an IdempotencyKey. The agent's args-hash binding (§11) carries the key inside the approved arguments, reinforcing the guard.

9. Partial receipts

Deliveries arrive short or split across days, so a PO is not "all or nothing." A receipt may cover less than the ordered quantity on any line; the service compares the sum of received quantity across all receipts for the PO against the ordered quantity per line:

  • Fully satisfied (every line's received ≥ ordered) → the PO transitions to Complete ("Fully received", compare-and-set from Pending).
  • Short (any line still owes) → the PO stays Pending — partially received is derived from the sums, never a status — open for the next receipt; each subsequent receipt tops up on-hand and re-evaluates.

Received-vs-ordered is tracked explicitly (summed from receipt lines against PO lines), so a half-delivered PO is never ambiguous. A PO that will never be completed (supplier can't supply the rest) is closed by the existing Spec 053 cancel — IPurchaseOrderService.CancelAsync (Pending → Cancelled) — rather than being left indefinitely half-open. Over-receipt (cumulative received > ordered, across all receipts) is rejected in v1, naming the ingredient with the ordered / already-received / this-receipt figures; a tolerance band is Open.

10. Cost update on receipt

When a line carries UnitCostActual, the receipt is also a landed-cost refresh: the price you actually paid becomes the ingredient's current cost, going forward from the receipt date. This reuses the Spec 051 effective-dated IngredientCost mechanism exactly — a new row with EffectiveFrom = ReceivedAt supersedes the prior active cost; the previous row (a manually set standard cost, or an earlier receipt's cost) is retained with its EffectiveTo closed off. Nothing is overwritten in place, so historical standard-cost rollups (051) and margin reports (057) that valued past production at the old cost remain stable.

A line with UnitCostActual = null refreshes stock only — the ingredient keeps its existing cost. The write is in the line's Currency, stamped from the PO's CurrencyIn: the Spec 051 write requires a currency, and the PO is what the price was agreed in. In v1 UnitCostActual is the ex-supplier unit price (what appears on the PO line); spreading freight/duty across lines (true landed cost) is Open.

11. Agent & tools

The existing commerce-agent gains one write tool, classified by CommerceToolApprovalManifest and wrapped by the Spec 032 gate — no change to the gate:

ToolTierEffect
commerce_receive_goodsmediumReceives a PO (full or partial): stock up, optional cost refresh, alert resolve, PO transition. In-session confirmation, args-hash-bound; records an AiRun. The idempotency key is a tool argument, so the args-hash binding pins it — a re-invocation resolves to the existing receipt instead of double-counting.

Reads (the PO to receive, current on-hand, open alerts) are served by the existing Spec 053 / 052 read tools; this spec adds no new read tool. Receiving is medium, not high: it moves stock and cost, not money — paying the supplier is the separate High follow-up in Spec 053.

12. CommerceDbContext & migrations

Two new Ank-prefixed tables — AnkGoodsReceipts and AnkGoodsReceiptLines — are created by one EF-CLI migration against AonikDbContext. Each entity is added to both CommerceDbContext (runtime scoping) and AonikDbContext (canonical stream); both are tenant-scoped (none global). Configurations live in Persistence/Configurations/Sourcing as IEntityTypeConfiguration<T> classes, and AnkGoodsReceipts carries a UNIQUE index on IdempotencyKey (per tenant) backing the §8 guard. 

dotnet ef migrations add CommerceGoodsReceipts --project src/Aonik.Infrastructure --startup-project src/Aonik.Api

16. Verification

  • dotnet build Aonik.sln green; architecture test proves Aonik.Commerce has no Aonik.Finance reference.
  • Full receipt: a submitted (Pending) PO for 25 kg rice with an unresolved low-stock alert; ReceiveAsync with 25 kg raises on-hand by 25 kg, resolves the alert, and moves the PO to Complete.
  • Cost refresh: the same receipt line with UnitCostActual writes a new effective-dated IngredientCost; the prior standard-cost row is retained (closed EffectiveTo), and a rollup at ReceivedAt uses the new cost.
  • Partial receipt: receiving 10 kg of a 25 kg line raises on-hand by 10 kg and leaves the PO Pending (partially received — derived from the sums, not a status); when the recomputed available is still at/below the reorder point the low-stock alert stays exactly as it was; a second receipt of 15 kg completes it to Complete and (now above threshold) resolves the alert.
  • Idempotency: a second ReceiveAsync with the same IdempotencyKey (simulating a post-commit retry) returns the existing receipt and leaves on-hand, cost rows, and PO status unchanged (no double-count) — even after the PO completed, because the key resolves before the status guard.
  • Agent: commerce_receive_goods surfaces a medium approval and records an AiRun; re-invoking with the same args does not double-count.
  • dotnet test Aonik.sln green (xUnit + FluentAssertions, InMemory + test tenant/user providers).

18. Decisions baked in

  • Goods receipt is the convergence point of stock (052), cost (051), alert (052), and PO lifecycle (041) — one guarded write reconciles all four.
  • A PO can have many receipts; partial deliveries are first-class, received-vs-ordered is tracked explicitly (derived, never a status — the PO stays Pending until Complete), and full completion is computed across receipts.
  • Actual cost supersedes, never mutates — a new effective-dated IngredientCost row; prior rows retained for historical valuation stability.
  • Idempotent by client-supplied key — a UNIQUE IdempotencyKey resolved before any mutation and before the status guard (mirroring the Order spine's CreateOrderCommand); the receipt row persisted first IS the applied-once claim, so one logical receipt applies its effects exactly once and post-commit retries are safe.
  • Receiving is medium, not high — it moves stock and cost, not money; supplier payment stays a separate High follow-up (053).
  • Grow in place in Aonik.Commerce; no Finance reference; migrations stay with AonikDbContext.

19. Open design decisions

Open Over-/under-receipt tolerance. A per-line or per-supplier tolerance band (e.g. accept ±5%, flag beyond) with a policy on how out-of-tolerance receipts are handled. v1 rejects any receipt that would take cumulative received above the ordered quantity, naming the ingredient; a tolerance band would relax that rejection.
Open Landed-cost allocation. Spreading freight, duty, and handling across the received lines to compute true landed cost. v1's UnitCostActual is the ex-supplier unit price only; allocation would decorate the cost-refresh step.
Open Quality hold / rejected lines. Receiving into a quarantine state, rejecting sub-standard deliveries, and returns-to-supplier. v1 records received quantity only; a QuantityRejected field and a hold status would layer on without changing the received-vs-ordered core.
