Spec 054 Status: Draft Size: Small Priority: P3 Domain: Commerce / Sourcing

Goods receipt (stock + cost) — receiving a purchase order into raw-material on-hand

Closes the procurement loop opened by Spec 053: it is the moment "once stock is confirmed". Receiving a purchase order turns an ordered PO into raw-material on hand — incrementing ingredient stock (Spec 052), refreshing landed cost (Spec 051), resolving the low-stock alert that triggered the reorder, and transitioning the PO on the shared Order spine. This is a small, dependent spec in the maker-operations family (050–057), which hangs off the recipe keystone in Spec 050. Everything lives in Aonik.Commerce and references only SharedKernel + Aonik.Ordering — never Aonik.Finance.

1. Summary

Spec 053 lets an operator place a purchase order with a supplier when a low-stock alert fires. But an ordered PO is a promise, not stock: the ingredient on-hand is unchanged, the alert is still open, and the PO sits Submitted. This spec adds the receiving step that makes the delivery real — the "goods have arrived, put them away" action.

It introduces two anemic entities in Aonik.Commerce and one service:

  • GoodsReceipt + GoodsReceiptLine — a receipt recorded against a PurchaseOrder, with a received quantity (and optional actual unit cost) per ingredient line.
  • IGoodsReceiptService.ReceiveAsync — the one operation that, in a single guarded transaction, increments ingredient on-hand (052), optionally refreshes landed cost (051), resolves the source low-stock alert(s), and transitions the PO on the Order spine.
Success signals An operator (or the commerce-agent) receives a submitted PO — fully or partially — and reads back higher ingredient on-hand, a resolved low-stock alert, a refreshed IngredientCost when an actual cost was entered, and a PO that moved to Received (full) or stayed open (partial). Re-submitting the same receipt does not double-count stock. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering; dotnet test Aonik.sln stays green with new unit tests covering receive, partial receive, idempotency, and cost refresh.

2. Context & motivation

In the operations-manager day-in-the-life, receiving is the pivot between "we're low, order more" and "we're stocked, make food." The low-stock alert (052) drives a reorder; the reorder is a PO (053); the PO is fulfilled when the supplier delivers. Until that delivery is recorded, none of the downstream numbers move: the prep list (055) still shows a shortfall, the standard-cost rollup (051) still uses the old price, and the alert still nags. Goods receipt is the single write that reconciles all of them.

It is deliberately the convergence point of three earlier specs rather than new machinery of its own. The stock increment reuses the Spec 052 InventoryService receive path; the cost refresh reuses the Spec 051 effective-dated IngredientCost write; the PO transition reuses the Spec 041 Order spine (IOrderService.TransitionAsync). This spec's own surface is small: the receipt record, the orchestration, and the idempotency guard that keeps a double-submit from double-counting.

4. Scope (in / out)

In scope

  • GoodsReceipt + GoodsReceiptLine entities + configs + DbSets.
  • IGoodsReceiptService.ReceiveAsync(purchaseOrderId, idempotencyKey, lines, ct): increment on-hand (052), optional cost refresh (051), resolve alert(s) only when recomputed available clears the reorder point (052), transition PO (041).
  • Partial receipts: receive less than ordered; the PO stays open (partially received) and can be received again until fully satisfied.
  • Idempotency guard: a client-supplied IdempotencyKey under a DB UNIQUE constraint (resolved before any mutation) plus the receipt status keeps a re-submitted / duplicate receipt from double-counting stock.
  • Admin endpoint to receive goods against a PO; commerce-agent medium-gated commerce_receive_goods tool.
  • One tool-generated migration (CommerceGoodsReceipts) creating AnkGoodsReceipts + AnkGoodsReceiptLines.

Out of scope

  • Paying the supplier (PO funding via PaymentIntent) — Spec 053 follow-up.
  • Landed-cost allocation (spreading freight/duty across lines) — UnitCostActual is ex-supplier in v1; noted under Open.
  • Quality hold / rejected lines / returns to supplier — v1 records received quantity only; noted under Open.
  • Over-/under-receipt tolerance policy — v1 accepts any non-negative quantity; tolerance is Open.
  • Lot/batch numbers, expiry dates, bin locations — not in v1.

5. Constraints & guardrails

  • No reference to Finance. Aonik.Commerce references only SharedKernel + Aonik.Ordering; the PO transition rides the Ordering spine, not a Finance call (ADR-005).
  • Anemic entities. GoodsReceipt/GoodsReceiptLine are { get; set; } data containers implementing ITenantScoped + AuditableEntity (ADR-002); all logic lives in GoodsReceiptService returning DTOs.
  • Single migration stream. EF-CLI-generated against AonikDbContext; Ank-prefixed tables; CommerceDbContext is runtime scoping with no migrations; agents never hand-author migrations.
  • Idempotent by construction. ReceiveAsync runs in one transaction keyed on a client-supplied IdempotencyKey (DB UNIQUE, resolved before any mutation), so a duplicate submit — including a post-commit retry — returns the existing receipt and stock is incremented exactly once (§8).
  • Cost is superseded, not mutated. An actual cost writes a new effective-dated IngredientCost row; the prior row (including a manually set standard cost) is retained for history (§10).
  • Agents propose; systems execute. Receiving is a medium tool — in-session confirmation, args-hash-bound — and records an AiRun.

7. Domain model

All entities are anemic, ITenantScoped, inherit AuditableEntity.

class GoodsReceipt     { Guid Id, TenantId, PurchaseOrderId;
                        string   IdempotencyKey;   // client-supplied; UNIQUE index (per tenant)
                        DateTime ReceivedAt;
                        string   Status;   // e.g. Draft | Posted
                        List<GoodsReceiptLine> Lines; }

class GoodsReceiptLine { Guid Id, TenantId, GoodsReceiptId, IngredientId;
                        decimal  QuantityReceived;   // in the ingredient's BaseUnit
                        decimal? UnitCostActual;     // ex-supplier landed cost, per BaseUnit; null ⇒ no cost refresh }

GoodsReceipt.PurchaseOrderId is a soft reference to the Spec 053 PurchaseOrder (an Order on the Spec 041 spine); a PO may have many receipts (one per partial delivery). GoodsReceiptLine.IngredientId matches the PO line's soft ingredient reference (OrderItem.ProductId = IngredientId, per the Spec 053 line shape). QuantityReceived is always in the ingredient's BaseUnit (Spec 050); UnitCostActual, when present, is per that base unit and drives the cost refresh (§10). IdempotencyKey is the idempotency lever: it is client-supplied and carries a DB UNIQUE index, so a retried receive resolves back to the already-posted receipt (§8) rather than opening a fresh one — mirroring the Order spine's CreateOrderCommand.IdempotencyKey. Status is the secondary guard: a receipt only applies its stock/cost/alert/PO effects when it transitions to Posted, and it stops the same persisted receipt being posted twice.

8. The receiving flow (stock up → cost refresh → alert resolve → PO transition)

ReceiveAsync is the whole spec. It runs the four downstream effects in one guarded transaction, in this order, then posts the receipt exactly once:

IGoodsReceiptService.ReceiveAsync(purchaseOrderId, idempotencyKey, lines[], ct) 0. GUARD load the PO (053); reject if not Submitted/PartiallyReceived resolve-or-create the receipt by IdempotencyKey under a DB UNIQUE constraint ── idempotency if a receipt for this key already exists (already applied) → return it, NO re-post otherwise open a fresh receipt (Draft) and continue 1. STOCK ▲ for each line → InventoryService.Receive(IngredientId, QuantityReceived) (052) raises the ingredient's InventoryLevel.OnHand 2. COST ↻ for each line with UnitCostActual set → write a new effective-dated IngredientCost (051) (EffectiveFrom = ReceivedAt); the prior cost row is superseded, not mutated 3. ALERT ✓ for each received ingredient → recompute available (OnHand − Reserved) vs reorder point (052) back above threshold → flip its Open LowStockAlert(s) → Resolved still at/below (short receipt) → leave the alert active (Ordered/Open) 4. PO → compute received-vs-ordered across all receipts for this PO: fully satisfied → IOrderService.TransitionAsync(po, Received) (041) short → leave PO PartiallyReceived (open for the next receipt) 5. POST mark the GoodsReceipt Posted; record the AiRun (agent path); commit → return { receiptId, perIngredientOnHandAfter, costRowsWritten, alertsResolved, poStatus }

Steps 1–5 commit together: a failure in any step rolls the receipt back to Draft with no partial stock movement. The guard at step 0 makes the whole thing idempotent — the client-supplied IdempotencyKey is resolved-or-created under a unique constraint before any stock/cost mutation, so a client or agent that times out after commit and retries gets the existing receipt back rather than a second application. This mirrors the Order spine, whose CreateOrderCommand already carries an IdempotencyKey. The receipt Status guard still protects reposting the same persisted receipt, and the agent's args-hash binding (§11) reinforces it.

9. Partial receipts

Deliveries arrive short or split across days, so a PO is not "all or nothing." A receipt may cover less than the ordered quantity on any line; the service compares the sum of received quantity across all receipts for the PO against the ordered quantity per line:

  • Fully satisfied (every line's received ≥ ordered) → PO transitions to Received.
  • Short (any line still owes) → PO stays PartiallyReceived, open for the next receipt; each subsequent receipt tops up on-hand and re-evaluates.

Received-vs-ordered is tracked explicitly (summed from receipt lines against PO lines), so a half-delivered PO is never ambiguous. A PO that will never be completed (supplier can't supply the rest) is closed by an explicit operator action — a Close transition on the Order spine — rather than being left indefinitely half-open. Over-receipt (received > ordered) is accepted in v1 (the extra stock is real); tolerance policy is Open.

10. Cost update on receipt

When a line carries UnitCostActual, the receipt is also a landed-cost refresh: the price you actually paid becomes the ingredient's current cost, going forward from the receipt date. This reuses the Spec 051 effective-dated IngredientCost mechanism exactly — a new row with EffectiveFrom = ReceivedAt supersedes the prior active cost; the previous row (a manually set standard cost, or an earlier receipt's cost) is retained with its EffectiveTo closed off. Nothing is overwritten in place, so historical standard-cost rollups (051) and margin reports (057) that valued past production at the old cost remain stable.

A line with UnitCostActual = null refreshes stock only — the ingredient keeps its existing cost. In v1 UnitCostActual is the ex-supplier unit price (what appears on the PO line); spreading freight/duty across lines (true landed cost) is Open.

11. Agent & tools

The existing commerce-agent gains one write tool, classified by CommerceToolApprovalManifest and wrapped by the Spec 032 gate — no change to the gate:

ToolTierEffect
commerce_receive_goodsmediumReceives a PO (full or partial): stock up, optional cost refresh, alert resolve, PO transition. In-session confirmation, args-hash-bound; records an AiRun. The args-hash + receipt Status guard keep a re-invocation from double-counting.

Reads (the PO to receive, current on-hand, open alerts) are served by the existing Spec 053 / 052 read tools; this spec adds no new read tool. Receiving is medium, not high: it moves stock and cost, not money — paying the supplier is the separate High follow-up in Spec 053.

12. CommerceDbContext & migrations

Two new Ank-prefixed tables — AnkGoodsReceipts and AnkGoodsReceiptLines — are created by one EF-CLI migration against AonikDbContext. Each entity is added to both CommerceDbContext (runtime scoping) and AonikDbContext (canonical stream); both are tenant-scoped (none global). Configurations live in Persistence/Configurations/Sourcing as IEntityTypeConfiguration<T> classes, and AnkGoodsReceipts carries a UNIQUE index on IdempotencyKey (per tenant) backing the §8 guard. 

dotnet ef migrations add CommerceGoodsReceipts --project src/Aonik.Infrastructure --startup-project src/Aonik.Api

16. Verification

  • dotnet build Aonik.sln green; architecture test proves Aonik.Commerce has no Aonik.Finance reference.
  • Full receipt: a Submitted PO for 25 kg rice with an open low-stock alert; ReceiveAsync with 25 kg raises on-hand by 25 kg, resolves the alert, and moves the PO to Received.
  • Cost refresh: the same receipt line with UnitCostActual writes a new effective-dated IngredientCost; the prior standard-cost row is retained (closed EffectiveTo), and a rollup at ReceivedAt uses the new cost.
  • Partial receipt: receiving 10 kg of a 25 kg line raises on-hand by 10 kg and leaves the PO PartiallyReceived; when the recomputed available is still at/below the reorder point the low-stock alert stays active; a second receipt of 15 kg completes it to Received and (now above threshold) resolves the alert.
  • Idempotency: a second ReceiveAsync with the same IdempotencyKey (simulating a post-commit retry) returns the existing receipt and leaves on-hand, cost rows, and PO status unchanged (no double-count); re-posting an already-posted receipt is likewise a no-op.
  • Agent: commerce_receive_goods surfaces a medium approval and records an AiRun; re-invoking with the same args does not double-count.
  • dotnet test Aonik.sln green (xUnit + FluentAssertions, InMemory + test tenant/user providers).

18. Decisions baked in

  • Goods receipt is the convergence point of stock (052), cost (051), alert (052), and PO lifecycle (041) — one guarded write reconciles all four.
  • A PO can have many receipts; partial deliveries are first-class, received-vs-ordered is tracked explicitly, and full completion is computed across receipts.
  • Actual cost supersedes, never mutates — a new effective-dated IngredientCost row; prior rows retained for historical valuation stability.
  • Idempotent by client-supplied key — a UNIQUE IdempotencyKey (resolved before any mutation, mirroring the Order spine's CreateOrderCommand), backed by the receipt Status guard, so one logical receipt applies its effects exactly once and post-commit retries are safe.
  • Receiving is medium, not high — it moves stock and cost, not money; supplier payment stays a separate High follow-up (053).
  • Grow in place in Aonik.Commerce; no Finance reference; migrations stay with AonikDbContext.

19. Open design decisions

Open Over-/under-receipt tolerance. A per-line or per-supplier tolerance band (e.g. accept ±5%, flag beyond) with a policy on how out-of-tolerance receipts are handled. v1 accepts any non-negative quantity and treats over-receipt as real extra stock.
Open Landed-cost allocation. Spreading freight, duty, and handling across the received lines to compute true landed cost. v1's UnitCostActual is the ex-supplier unit price only; allocation would decorate the cost-refresh step.
Open Quality hold / rejected lines. Receiving into a quarantine state, rejecting sub-standard deliveries, and returns-to-supplier. v1 records received quantity only; a QuantityRejected field and a hold status would layer on without changing the received-vs-ordered core.
