Commerce orders & carts — the kitchen landing and the honest box states

/commerce/orders and /commerce/carts · CommerceOrdersPage, CommerceCartsPage. Design of record: the updated orders/carts artboards (PR #268). Two operator questions answered honestly: what exactly was ordered (per-selection personalisation — the kitchen landing — plus ADD-ON retail lines), and which sessions are live, stuck or recoverable (box fullness, drift-blocked, abandoned).

1 · API contract + dependency callouts

NeedSource
Order list (ProductPurchase)The spine list (GET /orders?orderType=ProductPurchase) is shipped but its row DTO exposes one generic status, payer identity and totals only — no payment status, no fulfilment status, no buyer-kind discriminator.
Dependency callout 0 — list projection. The payment/fulfilment pills, paid-revenue and awaiting-fulfilment KPIs and guest-vs-party rendering need a commerce list projection (or spine-list enrichment) carrying paymentStatus, fulfilmentStatus, buyerKind. Degraded mode until it ships: one generic status pill, KPI row reduced to order count, buyer rendered without a kind icon.
Order storefront detail — box selections with personalisation summaries, ADD-ON flags, delivery-fee line, charge summaryNot composable from the spine read at all: GET /orders/{id} returns the bill-payment response shape — its item DTO omits quantity, product id, SKU and DetailsJson, and its mapper deserializes every item's details as bill-payment details. A ProductPurchase drawer cannot identify the box aggregate, add-ons, delivery fee or charge envelope from it.
Dependency callout 1 — order storefront detail (drawer-gating). Required: GET /commerce/admin/orders/{orderId}/storefront returning the ENTIRE storefront detail — { buyerKind, buyerPartyId?, items: [{ itemType, name, sku?, quantity?, unitPrice?, amount, isAddOn, isDeliveryFee }], selections: [{ productVariantId, quantity, sku, personalisationSummary? }], charge: { subtotal, discountTotal, discountCode?, taxTotal, total, currency }, paymentStatus, fulfilmentStatus } — a projection over data Specs 068/071 already persist. The drawer ships behind this endpoint; degraded mode renders id/status/total from the list row with a "storefront detail pending" panel, never a partial guess.
Carts list — status, buyer kind, box meta (size, filled, drift), value, age
Dependency callout 2 — carts admin read (page-gating), list AND detail. No admin carts endpoint exists (public cart routes are guest-token/party-scoped by design — R10). Required: GET /commerce/admin/carts?status=&page=… returning summaries { cartId, buyerPartyId?, buyerKind, status, currency, itemCount, total, boxMeta?: { size, filled, drift }, updatedAtUtc }, plus GET /commerce/admin/carts/{cartId} for the drawer — lines with nested selections, per-selection unavailable flags and drift reasons, and orderId when checked out (for the "View order" link). No tokens ever serialized in either. The carts page ships behind both; the route can land with an empty-state "requires the carts admin read" panel until then.

2 · Orders page structure

  1. KPI row — orders, revenue (paid), average order value, awaiting fulfilment (warn).
  2. List — payment-status FilterBar + DataTable: order (mono) · buyer (kind icon: party vs guest) · total (mono right) · payment pill · fulfilment pill · date.
  3. Order drawer (Sheet size:'md', route-addressable at /commerce/orders/:orderId exactly like Spec 082's editor — deep links, including Spec 084's recent-orders rows, open it directly) — lifecycle stepper (Created→Invoiced→Funded→Paid→Fulfilled, halted states for cancelled/refunded); items where the box aggregate line expands its selections — each with quantity, name, sku (mono) and its personalisation summary as an accent line (this is the kitchen landing: what Spec 068 snapshots so two differently-personalised preparations never collapse); ADD-ON retail lines badge ADD-ON with their own price and the caption "retail — no box space"; the DeliveryFee item renders as the delivery line; charge summary (subtotal → discount w/ code chip → tax → total payable, mono); payment + fulfilment cards. Buyer links to /customers/:partyId when party-bound (Spec 081's unified detail).

3 · Carts page structure

  1. KPI row — open carts, abandoned (warn), open value, checked out.
  2. List — status FilterBar + DataTable with the storefront columns: cart (mono) · buyer (kind) · box (filled/size mono + "drift — checkout blocked" warn line when flagged; — for non-box carts) · items · value · status pill · activity.
  3. Cart drawer — line items (box selections nested, unavailable selections flagged in warn tone); a warning banner when drift-blocked or incomplete stating the Spec 068 rule; footer actions by status: abandoned → "Send recovery link"; open → Resume checkout disabled as "Checkout blocked" with the reason whenever the box is drifted or under-filled (the review-hardened state — the UI must never offer the operation the rules block); checked-out → "View order" linking to the order drawer.

4 · Implementation instructions

  • Files: src/pages/commerce/CommerceOrdersPage.tsx, CommerceCartsPage.tsx; shared components/OrderLineItems.tsx (box-selection nesting + ADD-ON badge + personalisation accent — also reused by 081's Commerce tab if useful), components/LifecycleStepper.tsx. Routes (/commerce/orders, /commerce/orders/:orderId dynamic, /commerce/carts) + breadcrumbs in commerceModule; the nav child cm-orders points at /commerce/orders with a tab-style switch to carts (or two nav children — implementer's choice, breadcrumbs either way).
  • Blocked-state derivation is pure and unit-tested (lib/cartState.ts): cartBlocked(boxMeta) → { blocked, reason } for drift / under-filled; drives column, banner and footer identically.
  • DetailsJson handling: the box envelope and add-on personalisation envelopes are opaque JSON — render the human summaries the DTOs carry; never re-derive from envelopes client-side.
  • Recovery/refund actions render but no-op with a toast where their backend flows are not yet wired for commerce (refund remains a Finance high-tier action — the button stays disabled with that title, matching the design).

5 · Acceptance

  1. A box order's drawer shows every selection with its personalisation line, add-ons badged with their own prices, the delivery line when charged, and a charge summary whose total equals the API's.
  2. A drifted cart shows the warn column line, the drawer banner, and a disabled "Checkout blocked" action with the reason — all three from one derivation.
  3. Party-bound buyers link to the unified customer detail; guests render as guests with no dead link.
  4. With dependency endpoints absent, both pages render their honest degraded states (generic status pill + count-only KPIs on the list; pending panels for drawer/carts) and nothing fabricates data.
  5. cartState.ts unit tests cover drift, under-filled, full, and non-box cases.
