Spec 030 Status: Draft Size: Small Priority: P1 Domain: Agents / Platform

Proposal execution dispatcher

Adds a generic dispatch path that runs domain-side execution logic when an agent Proposal is approved, and a symmetric cleanup path when one is dismissed. Today only one proposal type (FinancialLifeGraphAnnotation) has working approval and rejection logic — both via bespoke endpoints that bypass the generic flow. This spec generalises both sides into IProposalHandler / IProposalRejectionHandler registered per ProposalType, so a single pair of endpoints flips status and runs the right domain logic.

1. Summary

The Proposal entity in Aonik.Agents already supports the full agent → human → system loop except for the last step: there is no generic way to execute an approved proposal. ProposalApprovalService.ApproveAsync only flips Status from Proposed to Approved and stamps approver / timestamp. The single proposal type that actually does anything on approval — FinancialLifeGraphAnnotation — works around this by exposing its own approval endpoint (/personal-finance/graph/proposals/{id}/approve) whose handler reads the payload, applies domain changes, then calls IAgentProposalStore.ApproveAsync.

This spec replaces that ad-hoc pattern with a paired registry: each module that defines a ProposalType registers an IProposalHandler for execution on approval, and optionally an IProposalRejectionHandler for cleanup on dismissal. Handlers return a structured ProposalHandlerResult so the approval response can carry the applied-resource identity (the created OrderId, updated BudgetId, etc.) and so handlers can signal "couldn't apply for a business reason" without throwing. The generic approval and dismiss endpoints dispatch through the registry as one logical operation (not cross-module ACID; see §4 guardrails).

Success signals Approving any proposal via POST /ai/proposals/{id}/approve applies the domain action and returns the applied resource. Dismissing via POST /ai/proposals/{id}/dismiss runs the rejection cleanup. Both FLG-specific endpoints are removed. A new proposal type ships as one approval handler class plus one registration line (and optionally a rejection handler) — no new endpoint, no changes to Aonik.Agents.

2. Problem

Today's approval flow has two divergent shapes:

Path What happens on approval Where the logic lives
POST /ai/proposals/{id}/approve Flip Status → Approved. Nothing else. ProposalApprovalService.ApproveAsync
POST /personal-finance/graph/proposals/{id}/approve Parse payload, activate FLG node + edge, then flip status. FinancialLifeGraphInferenceService.ApproveProposalAsync

Concrete consequences:

  • A user (or automation) that approves an FLG proposal via the generic endpoint silently does not apply the change — the proposal row is Approved but the graph nodes remain in Proposed state. Two endpoints with overlapping URLs, different semantics, no enforcement.
  • Every future proposal type needs its own endpoint, its own service method, its own knowledge of how to call IAgentProposalStore.ApproveAsync. The Admin UI's approvals page already speaks the generic endpoint — new types are silently broken there until a parallel UI is added.
  • There is no shared place to enforce cross-cutting concerns (idempotency on retry, audit emission, failure rollback, policy gating, observability spans).
  • Spec 030's predecessor (the scrapped Compass spec) assumed proposal types like Orders.CreateBillPaymentOrder would simply work on approval. They will not until this gap is closed.

3. Scope (in / out)

3.1 In scope

  • New IProposalHandler contract in Aonik.SharedKernel.Abstractions.Agents — one method returning ProposalHandlerResult, plus a ProposalType discriminator.
  • New IProposalRejectionHandler contract in the same namespace — symmetric counterpart that cleans up domain state when a proposal is dismissed. Optional per type; the dispatcher no-ops if no rejection handler is registered.
  • New ProposalHandlerResult record — minimal shape (Applied flag, AppliedResourceType, AppliedResourceId, Message). Handlers signal "couldn't apply for a business reason" via Applied = false instead of throwing for expected failures.
  • New IProposalDispatcher in Aonik.SharedKernel.Abstractions.Agents — resolves the approval handler for a given ProposalType string and invokes it. Companion IProposalRejectionDispatcher resolves the optional rejection handler.
  • New ProposalDispatcher + ProposalRejectionDispatcher implementations in Aonik.Agents.Services — backed by DI-keyed services, throw a typed exception when no approval handler is registered for a type.
  • Edit ProposalApprovalService.ApproveAsync — flip status, save, dispatch; revert on exception OR on Applied = false result; return the handler's applied-resource metadata in the response.
  • Edit ProposalApprovalService.DismissAsync — flip status, save, dispatch via IProposalRejectionDispatcher (no-op if no handler registered); on rejection-handler failure, leave the dismissal in place but surface the failure to the caller.
  • New FinancialLifeGraphAnnotationProposalHandler + FinancialLifeGraphAnnotationProposalRejectionHandler in Aonik.PersonalFinance.Services.PersonalFinance that wrap the existing FinancialLifeGraphInferenceService.ApproveProposalAsync / RejectProposalAsync bodies.
  • Edit FinancialLifeGraphInferenceService.ApproveProposalAsync / RejectProposalAsync — reduce to thin facades that call the handlers, or remove if no other caller remains.
  • Edit Remove ApproveFinancialLifeGraphProposalEndpoint and its reject counterpart. The generic /ai/proposals/{id}/approve and /ai/proposals/{id}/dismiss are the only paths.
  • Edit Extend ProposalDetailResponse to carry the applied-resource fields populated by the dispatcher (nullable; pre-existing rows return null).
  • New NoProposalHandlerRegisteredException — thrown by the approval dispatcher and surfaced as HTTP 409 by the approve endpoint (with a structured error body).
  • New ProposalExecutionFailedException — thrown when a handler returns Applied = false; carries the handler's Message; surfaced as HTTP 422.
  • New Unit tests: dispatcher happy path, missing-handler path, handler-throws path, handler-returns-Applied-false path, rejection-handler dispatch, FLG approval and rejection parity with the old inline service.
  • New Integration tests: approve and dismiss an FLG proposal via the generic endpoints; assert both the proposal row and the FLG node/edge transition as expected.

3.2 Out of scope

  • New proposal types. This spec ships the dispatcher and migrates the one existing handler. Orders.CreateBillPaymentOrder, PersonalFinance.UpdateBudget, etc. are separate work that becomes possible after this lands.
  • Background / async execution. Handlers run synchronously inside the approval request. If a handler needs to enqueue work (e.g. payment that polls a partner), that's the handler's choice — the dispatcher does not own scheduling. Background-driven dispatch (retry queues, dead-letter) is a separate decision.
  • Multi-handler fan-out. One ProposalType → one handler. No middleware chain, no decorators, no policy pipeline.
  • Per-handler authorisation rules. Precondition V1 retains the existing AdminUserPolicy gate, which is acceptable only because the FLG migration is the sole live consumer. Before any Payabo-facing proposal type or money-movement proposal type (Orders.CreateBillPaymentOrder, PersonalFinance.UpdateBudget, transfers, payouts) lands, approval authorisation must be moved to policy-based rules that consider actor, subject ownership / delegated permission, tenant, risk tier, and proposal type. That work is a hard precondition for those follow-up specs, not an indefinite deferral.
  • Payload schema validation. The handler is responsible for parsing and validating its own PayloadJson. The dispatcher passes the raw payload and does not enforce shape.
  • Proposal as guidance-only carrier. Proposal is defined as "something that can be approved and applied." Compass and any future module that wants to surface advisory, review-only, or non-executable content must use Insight, a notification, or a guidance card — not Proposal. Creating a Proposal without a registered handler is a hard failure (see §6.2), not a soft no-op.
  • New ProposalStatus values. V1 keeps the existing three-value enum (Proposed / Approved / Rejected). The conceptual limitation this creates is documented in §6.4; a future spec will need to split approval-state from execution-state before payment, refund, transfer, payout, ledger, or externally-integrated proposal types land.

4. Guardrails

Must not change Must follow Ask before
  • The Proposal entity schema (no new columns required).
  • IAgentProposalStore public surface — the dispatcher composes with it, does not replace it.
  • ProposalStatus enum — only the three existing values.
  • The POST /ai/proposals/{id}/approve route, request shape, or response shape (the body just gains the side-effect).
  • Handler registration via DI keyed-services (services.AddKeyedScoped<IProposalHandler>(proposalType, ...)) so each module owns its own wiring.
  • Approval and execution are part of one logical operation, not a guaranteed cross-module ACID transaction. The system must never silently mark a proposal Approved if no handler ran successfully: any known failure (exception OR Applied = false) reverts the proposal to Proposed. Crash recovery mid-handler is explicitly out of scope for v1.
  • Handlers must be idempotent (see §6.1) — the retry path is "user clicks Approve again."
  • Handlers live in the owning domain module, not in Aonik.Agents.
  • The approval dispatcher emits an OpenTelemetry span aonik.proposals.dispatch with tags proposal.type, proposal.id, proposal.applied, proposal.applied_resource_type, and proposal.applied_resource_id. The rejection dispatcher emits aonik.proposals.rejection_dispatch with tags proposal.type, proposal.id, and proposal.cleanup_handler_registered.
  • Introducing async / background dispatch (would change the contract).
  • Letting handlers run outside the approval request thread (e.g. publish-and-forget).
  • Allowing more than one handler per ProposalType.
  • Adding a new database column to Proposal to track handler execution state (versus inferring it from Status).

5. Component design

5.1 Target flow

Approval path ───────────── User clicks "Approve" in Admin UI ↓ POST /ai/proposals/{id}/approve ↓ ApproveProposalEndpoint ↓ ProposalApprovalService.ApproveAsync ├─ Load Proposal (must be Proposed) ├─ Flip Status → Approved, stamp approver + timestamp ├─ SaveChanges (proposal row committed) ├─ result = IProposalDispatcher.DispatchAsync(AgentProposalDetail) │ ↓ │ IProposalHandler resolved from DI by ProposalType key │ ↓ │ ProposalHandlerResult = handler.HandleAsync(detail, ct) │ • throws ⇒ revert Status → Proposed, SaveChanges, rethrow │ • Applied = false ⇒ revert + throw ProposalExecutionFailedException (422) │ • Applied = true ⇒ response carries AppliedResourceType / AppliedResourceId │ └─ No registered handler ⇒ NoProposalHandlerRegisteredException (409) Rejection path ────────────── User clicks "Dismiss" in Admin UI ↓ POST /ai/proposals/{id}/dismiss ↓ ProposalApprovalService.DismissAsync ├─ Load Proposal (must be Proposed) ├─ Flip Status → Rejected, SaveChanges ├─ IProposalRejectionDispatcher.DispatchAsync(detail, ct) │ ↓ │ IProposalRejectionHandler resolved (optional — no-op if not registered) │ ↓ │ handler.HandleRejectionAsync(detail, ct) ← domain-side cleanup │ └─ On handler failure: status stays Rejected, exception bubbles (so the operator knows cleanup did not complete; manual recovery is the fallback for v1).

5.2 Contracts (SharedKernel)

namespace Aonik.SharedKernel.Abstractions.Agents;

/// <summary>
/// Domain-side executor for an approved proposal. Implementations live in the
/// owning module (e.g. PersonalFinance for FLG annotations, Finance for bill
/// payments) and are registered with DI keyed by their ProposalType discriminator.
/// </summary>
public interface IProposalHandler
{
    /// <summary>The ProposalType string this handler is registered for.</summary>
    string ProposalType { get; }

    /// <summary>
    /// Apply the proposal's payload to the owning domain. Called by the dispatcher
    /// after the Proposal row has been flipped to Approved.
    ///
    /// Failure modes:
    ///  • Throw for unexpected errors (DB unavailable, partner API failure).
    ///    Dispatcher reverts the proposal to Proposed and rethrows.
    ///  • Return Applied = false + Message for expected business reasons
    ///    (payload references a deleted entity, idempotency conflict that
    ///    should not retry). Dispatcher reverts and throws
    ///    ProposalExecutionFailedException, which surfaces as HTTP 422.
    ///  • Return Applied = true with optional AppliedResourceType /
    ///    AppliedResourceId on success.
    /// </summary>
    Task<ProposalHandlerResult> HandleAsync(
        AgentProposalDetail proposal,
        CancellationToken cancellationToken);
}

/// <summary>
/// Optional symmetric counterpart: cleans up domain state when a proposal is
/// dismissed (e.g. removes a "Proposed"-status FLG node that was created when
/// the proposal was raised). If no rejection handler is registered for a
/// ProposalType, the dispatcher no-ops — some proposal types have no
/// cleanup to do.
/// </summary>
public interface IProposalRejectionHandler
{
    string ProposalType { get; }

    Task HandleRejectionAsync(
        AgentProposalDetail proposal,
        CancellationToken cancellationToken);
}

/// <summary>
/// Outcome record returned by an IProposalHandler. Carries enough metadata
/// for the approval response, audit log, and UI to describe what happened
/// without forcing the caller to re-query the domain.
///
/// Fields are intentionally minimal: ProposalType / ProposalId are not
/// included because the caller already has them from AgentProposalDetail.
/// No metadata dictionary — add one in a future spec only if a real
/// consumer needs it.
/// </summary>
public sealed record ProposalHandlerResult(
    bool Applied,
    string? AppliedResourceType = null,
    Guid? AppliedResourceId = null,
    string? Message = null);

/// <summary>
/// Resolves the IProposalHandler registered for a given ProposalType and invokes it.
/// Throws <see cref="NoProposalHandlerRegisteredException"/> when no handler is
/// registered — that error is treated as approval failure, not silent no-op.
/// </summary>
public interface IProposalDispatcher
{
    Task<ProposalHandlerResult> DispatchAsync(
        AgentProposalDetail proposal,
        CancellationToken cancellationToken);
}

/// <summary>
/// Symmetric counterpart for the dismissal path. No-ops (returns successfully)
/// when no IProposalRejectionHandler is registered for the ProposalType —
/// missing rejection handlers are not an error, since not every proposal type
/// has cleanup to do.
/// </summary>
public interface IProposalRejectionDispatcher
{
    Task DispatchAsync(
        AgentProposalDetail proposal,
        CancellationToken cancellationToken);
}

public sealed class NoProposalHandlerRegisteredException : Exception
{
    public NoProposalHandlerRegisteredException(string proposalType)
        : base($"No IProposalHandler is registered for proposal type '{proposalType}'.")
    {
        ProposalType = proposalType;
    }

    public string ProposalType { get; }
}

public sealed class ProposalExecutionFailedException : Exception
{
    public ProposalExecutionFailedException(Guid proposalId, string? message)
        : base(message ?? $"Handler returned Applied = false for proposal '{proposalId}'.")
    {
        ProposalId = proposalId;
    }

    public Guid ProposalId { get; }
}

5.3 Dispatcher implementation

namespace Aonik.Agents.Services;

internal sealed class ProposalDispatcher : IProposalDispatcher
{
    private readonly IServiceProvider _services;

    public ProposalDispatcher(IServiceProvider services) => _services = services;

    public Task<ProposalHandlerResult> DispatchAsync(
        AgentProposalDetail proposal,
        CancellationToken ct)
    {
        var handler = _services.GetKeyedService<IProposalHandler>(proposal.ProposalType)
            ?? throw new NoProposalHandlerRegisteredException(proposal.ProposalType);

        // OpenTelemetry span (aonik.proposals.dispatch) wraps the handler call
        // and tags proposal.type, proposal.id, proposal.applied,
        // proposal.applied_resource_type, proposal.applied_resource_id.
        return handler.HandleAsync(proposal, ct);
    }
}

internal sealed class ProposalRejectionDispatcher : IProposalRejectionDispatcher
{
    private readonly IServiceProvider _services;

    public ProposalRejectionDispatcher(IServiceProvider services) => _services = services;

    public Task DispatchAsync(AgentProposalDetail proposal, CancellationToken ct)
    {
        // Missing rejection handler is NOT an error — many proposal types have
        // no cleanup to do. Only approval-side dispatch treats missing as fatal.
        // OpenTelemetry span (aonik.proposals.rejection_dispatch) wraps this and
        // tags proposal.type, proposal.id, proposal.cleanup_handler_registered.
        var handler = _services.GetKeyedService<IProposalRejectionHandler>(proposal.ProposalType);
        return handler is null ? Task.CompletedTask : handler.HandleRejectionAsync(proposal, ct);
    }
}

5.4 Registration pattern

Each module's DependencyInjection.Add{Module} extension registers its handler with the type string as the DI key: 

// In Aonik.PersonalFinance/DependencyInjection.cs
services.AddKeyedScoped<IProposalHandler, FinancialLifeGraphAnnotationProposalHandler>(
    "FinancialLifeGraphAnnotation");

// Rejection handler is optional — register only if the type has cleanup to do.
services.AddKeyedScoped<IProposalRejectionHandler, FinancialLifeGraphAnnotationProposalRejectionHandler>(
    "FinancialLifeGraphAnnotation");

The dispatchers (in Aonik.Agents) register once with the container and resolve handlers by key. A new proposal type ships as: one approval handler + one registration line; optionally one rejection handler + one registration line if the type needs dismiss-time cleanup.

5.5 Approval service change

// Aonik.Agents/Services/ProposalApprovalService.cs (post-change sketch)

public async Task<ProposalDetailResponse> ApproveAsync(Guid proposalId, CancellationToken ct)
{
    var proposal = await _dbContext.Proposals.FirstOrDefaultAsync(p => p.Id == proposalId, ct)
        ?? throw new KeyNotFoundException(...);

    if (proposal.Status != ProposalStatus.Proposed)
        throw new InvalidOperationException(...);

    proposal.Status = ProposalStatus.Approved;
    proposal.ApprovedByUserId = _currentUserProvider.GetCurrentUserId();
    proposal.ApprovedAt = _clock.UtcNow;
    await _dbContext.SaveChangesAsync(ct);

    ProposalHandlerResult result;
    try
    {
        result = await _dispatcher.DispatchAsync(ToDetail(proposal), ct);
    }
    catch
    {
        RevertToProposed(proposal);
        await _dbContext.SaveChangesAsync(CancellationToken.None);
        throw;
    }

    if (!result.Applied)
    {
        // Handler signalled an expected business failure (e.g. payload references
        // a deleted entity). Revert and surface as 422 to distinguish from the
        // 500-class path above.
        RevertToProposed(proposal);
        await _dbContext.SaveChangesAsync(CancellationToken.None);
        throw new ProposalExecutionFailedException(proposal.Id, result.Message);
    }

    var row = await JoinedQuery().FirstAsync(p => p.Proposal.Id == proposalId, ct);
    return Map(row, result);   // response carries AppliedResourceType / AppliedResourceId
}

private void RevertToProposed(Proposal proposal)
{
    proposal.Status = ProposalStatus.Proposed;
    proposal.ApprovedByUserId = null;
    proposal.ApprovedAt = null;
}
Note The revert is best-effort — the proposal row and the domain side live in different DbContexts today, so this is not a true distributed transaction. Handlers must therefore be idempotent (see §6.1) and the v1 consistency promise is "logical operation, not cross-module ACID" (see §4 guardrails).
Response fields are transient AppliedResourceType and AppliedResourceId on ProposalDetailResponse are response-only in v1 — they come from the in-memory ProposalHandlerResult and are not persisted on the Proposal row. A subsequent GET /ai/proposals/{id} will return null for both. If durable linkage is needed, the owning domain handler must persist it in its own domain records (e.g. the created Order carries a foreign key back to ProposalId), or a future spec must add a ProposalExecution table that records what each approved proposal produced. Compass and Orders consumers must not assume the response fields survive a re-read.

5.6 Dismissal service change

// Aonik.Agents/Services/ProposalApprovalService.cs (post-change sketch)

public async Task<ProposalDetailResponse> DismissAsync(Guid proposalId, CancellationToken ct)
{
    var proposal = await _dbContext.Proposals.FirstOrDefaultAsync(p => p.Id == proposalId, ct)
        ?? throw new KeyNotFoundException(...);

    if (proposal.Status != ProposalStatus.Proposed)
        throw new InvalidOperationException(...);

    proposal.Status = ProposalStatus.Rejected;
    proposal.ApprovedByUserId = _currentUserProvider.GetCurrentUserId();   // stamps the dismisser
    proposal.ApprovedAt = _clock.UtcNow;
    await _dbContext.SaveChangesAsync(ct);

    // Rejection dispatch is fire-and-surface: if cleanup fails, the proposal stays
    // Rejected (we don't un-dismiss the user's intent) but the exception bubbles so
    // the caller knows manual cleanup is required.
    await _rejectionDispatcher.DispatchAsync(ToDetail(proposal), ct);

    var row = await JoinedQuery().FirstAsync(p => p.Proposal.Id == proposalId, ct);
    return Map(row);
}
Asymmetry Approval reverts on handler failure; dismissal does not. Reasoning: the user has explicitly said "I don't want this." Un-dismissing because cleanup hit a DB hiccup would countermand the user's intent. The exception still surfaces so the failure is observable.
Reused fields in v1 V1 reuses ApprovedByUserId and ApprovedAt on the Proposal row to record the dismisser and dismissal time, because the schema is intentionally unchanged in this spec. Anyone reading a Rejected proposal row should interpret ApprovedByUserId as "the user who made the Approve-or-Dismiss decision" rather than literally "the user who approved." A future schema change should rename these to DecisionByUserId / DecidedAt, or add explicit rejected-by fields, alongside the approval/execution status split documented in §6.4.
HTTP mapping on cleanup failure When the rejection handler throws, the dismiss endpoint returns HTTP 500 with a structured body identifying the proposal id, that the row was successfully moved to Rejected, and that domain cleanup failed and requires manual intervention. (The status code is semantically loose — the dismissal request did achieve its primary effect — but 500 is the most operationally loud option in the existing error-handling pipeline. An alternative is HTTP 200 with a cleanup_warning field; deferred unless the loudness is undesirable in practice.)

6. Failure & idempotency

6.1 Handler must be idempotent

The dispatcher catches handler exceptions and reverts the proposal status, but a handler that partially succeeded before throwing leaves the domain in a partial state. Handlers must therefore be safe to re-run on the same proposal payload — the retry path is "user clicks Approve again."

Concrete techniques handlers should use:

  • Check current state before mutating (e.g. FLG handler activates a node only if it is still Proposed; no-op otherwise).
  • Use deterministic IDs derived from the proposal payload, never Guid.NewGuid(), when creating downstream records.
  • Treat "downstream record already exists with this deterministic ID" as success, not as a duplicate-key failure.

6.2 Missing-handler is a hard failure

If ProposalType has no registered handler, the dispatcher throws NoProposalHandlerRegisteredException, the approval reverts, and the endpoint returns HTTP 409 with a structured error pointing at the missing type. This intentionally surfaces drift between proposals being created and the handlers that should execute them.

6.3 What this spec does not guarantee

  • Cross-module ACID. The proposal row and the domain-side mutation are still in separate DbContexts.
  • Exactly-once execution under crash mid-handler. If the process dies between the handler partially mutating and the revert happening, the proposal stays Approved with no domain effect. Resolution is operator-driven for now (read the audit log, decide).
  • Ordered execution of multiple approvals. Each approval is its own request.

Both gaps are acceptable for v1 because today's only handler (FLG annotation) already operates in this model with no observed issues; closing them would require an outbox pattern that is out of scope here.

6.4 V1 status-model limitation

V1 keeps the existing three-value ProposalStatus enum (Proposed / Approved / Rejected). With the revert-on-failure rule, Approved in v1 means approved-and-successfully-handled: if the handler throws or returns Applied = false, the row goes back to Proposed.

This is a deliberate simplification. The conceptually correct model splits two distinct facts:

  • "A human (or policy) approved this proposal."
  • "The system successfully applied it to the owning domain."

V1 collapses both into Approved because the FLG migration does not need them split — the handler is synchronous, in-process, and fast. Before any proposal type that does money movement, refund, payout, ledger posting, or external API call lands, a follow-up spec must split approval-state from execution-state — likely as Proposed → Approved → Applied / Failed with Rejected as a terminal branch. That work is a hard precondition for those proposal types, not a "nice to have."

7. Migrating the existing FLG handlers

Both sides of the existing FLG inference service are reference implementations of the handler pattern.

7.1 Approval handler

The existing FinancialLifeGraphInferenceService.ApproveProposalAsync body already:

  • Loads the proposal via IAgentProposalStore.GetByIdAsync.
  • Parses PayloadJson to extract GraphNodeId.
  • Looks up the FLG node and edge.
  • Flips both to Active.
  • Saves the FLG context.
  • Calls IAgentProposalStore.ApproveAsync.
  • Invalidates the FLG cache.

Migration is a near-mechanical lift:

  1. Create FinancialLifeGraphAnnotationProposalHandler : IProposalHandler with ProposalType => "FinancialLifeGraphAnnotation" and the body moved over minus the ApproveAsync call (the dispatcher's caller has already flipped the proposal). Return new ProposalHandlerResult(Applied: true, AppliedResourceType: "FinancialLifeGraphNode", AppliedResourceId: graphNodeId).
  2. "Node already Active" should return Applied: true (idempotent re-apply), not throw.
  3. "Node not found" should return Applied: false with a message — expected business failure, not an exception.
  4. Register it in Aonik.PersonalFinance DI under the key "FinancialLifeGraphAnnotation".

7.2 Rejection handler

The existing FinancialLifeGraphInferenceService.RejectProposalAsync body does real domain cleanup: it sets the FLG node and edge to a rejected status so the graph does not retain orphaned Proposed-state inferences. Removing the bespoke reject endpoint without dispatching rejection would silently break this cleanup, so the rejection handler is required in v1.

  1. Create FinancialLifeGraphAnnotationProposalRejectionHandler : IProposalRejectionHandler with the existing reject body lifted over (minus the IAgentProposalStore.RejectAsync call — DismissAsync on the agents side already flipped the row).
  2. Register it in Aonik.PersonalFinance DI under the same key.
  3. Add an integration test asserting that dismissing an FLG proposal via the generic /ai/proposals/{id}/dismiss endpoint moves both the proposal row and the FLG node/edge into their rejected states.

7.3 Cleanup and frontend updates

  1. Delete ApproveFinancialLifeGraphProposalEndpoint and the corresponding reject endpoint.
  2. Reduce FinancialLifeGraphInferenceService.ApproveProposalAsync / RejectProposalAsync to thin forwarders that call the handlers, or remove if no other caller remains.
  3. Update any frontend references from /personal-finance/graph/proposals/{id}/approve (and the matching reject route) to the generic /ai/proposals/{id}/approve / /ai/proposals/{id}/dismiss.

9. Acceptance criteria

  • dotnet build Aonik.sln and dotnet test Aonik.sln succeed.
  • Approving any FinancialLifeGraphAnnotation proposal via POST /ai/proposals/{id}/approve activates the underlying FLG node and edge, and the response carries AppliedResourceType = "FinancialLifeGraphNode" plus the resource id.
  • Dismissing any FinancialLifeGraphAnnotation proposal via POST /ai/proposals/{id}/dismiss moves both the proposal row and the FLG node/edge into their rejected states.
  • Approving a proposal whose ProposalType has no registered approval handler returns HTTP 409 and leaves the proposal in Proposed.
  • Dismissing a proposal whose ProposalType has no registered rejection handler succeeds (no error) — missing rejection handlers are not fatal.
  • If an approval handler throws, the proposal is left in Proposed (status reverted, approver / timestamp cleared) and the exception bubbles to the endpoint.
  • If an approval handler returns Applied = false, the proposal is left in Proposed and the endpoint returns HTTP 422 with the handler's Message in the body.
  • If a rejection handler throws, the proposal stays Rejected (the user's dismissal intent is preserved) and the dismiss endpoint returns HTTP 500 with a structured body that identifies the proposal id and states that cleanup failed and requires manual intervention.
  • No code in Aonik.Agents references FinancialLifeGraphAnnotation or any other module-specific proposal type by name.
  • ApproveFinancialLifeGraphProposalEndpoint and its reject counterpart are removed; the admin UI / Payabo reference the generic routes.
  • Adding a hypothetical new proposal type requires one approval handler class + one AddKeyedScoped<IProposalHandler> line (and optionally one rejection handler + line if the type needs cleanup), with no edits to Aonik.Agents or Aonik.SharedKernel.

10. Open decisions

Resolved Handler failure-signal shape. Earlier draft asked whether handlers should throw or return a structured failure. Resolved in favour of both: throw for unexpected errors (DB unavailable, partner API outage), return Applied = false for expected business reasons (payload references a deleted entity, idempotency conflict). The two get distinct HTTP status codes (500-class vs 422) so the UI and audit log can tell them apart. No new ProposalStatus value needed in v1; see §6.4 for the future split.
Open Should the dispatcher run inside ProposalApprovalService.ApproveAsync (current proposal) or in a separate post-commit pipeline so the approval HTTP request can return quickly and execution happens out of band? Synchronous is simpler and matches user expectations ("clicked approve, it's done"), but slow handlers (e.g. external API calls) will tie up the approval request. Asynchronous needs an outbox or a hosted-service consumer.
Open How should the dispatcher's failure-revert interact with the audit log? Today there is no explicit audit emission on approve. A clean taxonomy would emit proposal.approval_requested, proposal.approved, proposal.execution_succeeded, proposal.execution_failed, proposal.dismissed, proposal.rejection_cleanup_failed — but that is a real design decision in its own right. Confirm shape against the existing IAuditLogWriter contract before implementing, and consider whether the taxonomy is better landed in a dedicated audit-spec.
