Proposal execution dispatcher

Adds a generic dispatch path that runs domain-side execution logic when an agent Proposal is approved. Today only one proposal type (FinancialLifeGraphAnnotation) executes anything — via a bespoke endpoint that bypasses the generic approval flow. This spec generalises that pattern so any module can register an IProposalHandler, and a single approval endpoint flips status and applies the change atomically.

1. Summary

The Proposal entity in Aonik.Agents already supports the full agent → human → system loop except for the last step: there is no generic way to execute an approved proposal. ProposalApprovalService.ApproveAsync only flips Status from Proposed to Approved and stamps approver / timestamp. The single proposal type that actually does anything on approval — FinancialLifeGraphAnnotation — works around this by exposing its own approval endpoint (/personal-finance/graph/proposals/{id}/approve) whose handler reads the payload, applies domain changes, then calls IAgentProposalStore.ApproveAsync.

This spec replaces that ad-hoc pattern with a registry: each module that defines a ProposalType also registers an IProposalHandler keyed by that type string. The generic approval endpoint dispatches through the registry inside one unit of work, so the proposal row and the domain action either both happen or both do not.

Success signals Approving any proposal via POST /ai/proposals/{id}/approve applies the domain action. The FLG-specific approval endpoint is removed. A new proposal type can be added by writing one handler class and registering it — no new endpoint, no changes to Aonik.Agents.

2. Problem

Today's approval flow has two divergent shapes:

Path What happens on approval Where the logic lives
POST /ai/proposals/{id}/approve Flip Status → Approved. Nothing else. ProposalApprovalService.ApproveAsync
POST /personal-finance/graph/proposals/{id}/approve Parse payload, activate FLG node + edge, then flip status. FinancialLifeGraphInferenceService.ApproveProposalAsync

Concrete consequences:

  • A user (or automation) that approves an FLG proposal via the generic endpoint silently does not apply the change — the proposal row is Approved but the graph nodes remain in Proposed state. Two endpoints with overlapping URLs, different semantics, no enforcement.
  • Every future proposal type needs its own endpoint, its own service method, its own knowledge of how to call IAgentProposalStore.ApproveAsync. The Admin UI's approvals page already speaks the generic endpoint — new types are silently broken there until a parallel UI is added.
  • There is no shared place to enforce cross-cutting concerns (idempotency on retry, audit emission, failure rollback, policy gating, observability spans).
  • Spec 030's predecessor (the scrapped Compass spec) assumed proposal types like Orders.CreateBillPaymentOrder would simply work on approval. They will not until this gap is closed.

3. Scope (in / out)

3.1 In scope

  • New IProposalHandler contract in Aonik.SharedKernel.Abstractions.Agents — one method, HandleAsync(AgentProposalDetail, CancellationToken), plus a static ProposalType discriminator.
  • New IProposalDispatcher in Aonik.SharedKernel.Abstractions.Agents — resolves the handler for a given ProposalType string and invokes it.
  • New ProposalDispatcher implementation in Aonik.Agents.Services — backed by a dictionary built from DI-registered handlers, throws a typed exception if no handler is registered for a type.
  • Edit ProposalApprovalService.ApproveAsync — after the status transition (same transaction / SaveChanges) invoke the dispatcher. On dispatcher failure, roll the proposal back to Proposed and bubble the failure to the caller.
  • New FinancialLifeGraphAnnotationProposalHandler in Aonik.PersonalFinance.Services.PersonalFinance that wraps the existing FinancialLifeGraphInferenceService.ApproveProposalAsync body.
  • Edit FinancialLifeGraphInferenceService.ApproveProposalAsync — reduce to a thin facade that calls the handler (kept temporarily for the legacy endpoint, removed in the same change as the endpoint).
  • Edit Remove ApproveFinancialLifeGraphProposalEndpoint and the matching reject endpoint. The generic /ai/proposals/{id}/approve is the only path.
  • New NoProposalHandlerRegisteredException — thrown by the dispatcher and surfaced as HTTP 409 by the approve endpoint (with a clear error body).
  • New Unit tests: dispatcher happy path, missing-handler path, handler-throws path, FLG handler parity with the old inline service.
  • New Integration test: approve an FLG proposal via /ai/proposals/{id}/approve and assert both the proposal row and the FLG node/edge transition to active.

3.2 Out of scope

  • New proposal types. This spec ships the dispatcher and migrates the one existing handler. Orders.CreateBillPaymentOrder, PersonalFinance.UpdateBudget, etc. are separate work that becomes possible after this lands.
  • Background / async execution. Handlers run synchronously inside the approval request. If a handler needs to enqueue work (e.g. payment that polls a partner), that's the handler's choice — the dispatcher does not own scheduling. Background-driven dispatch (retry queues, dead-letter) is a separate decision.
  • Multi-handler fan-out. One ProposalType → one handler. No middleware chain, no decorators, no policy pipeline.
  • Per-handler authorisation. The approve endpoint's existing AdminUserPolicy is the gate. Per-handler additional checks (e.g. "only the proposal subject can approve a self-transfer") are deferred to a later spec.
  • Payload schema validation. The handler is responsible for parsing and validating its own PayloadJson. The dispatcher passes the raw payload and does not enforce shape.
  • Rejection-side dispatch. DismissAsync stays a pure status flip. Rejection-time cleanup (e.g. removing the proposed-but-not-yet-applied FLG nodes) currently happens inline in the legacy reject endpoint. Moving rejection logic into the dispatcher is a follow-up if a second type ever needs it.

4. Guardrails

Must not change Must follow Ask before
  • The Proposal entity schema (no new columns required).
  • IAgentProposalStore public surface — the dispatcher composes with it, does not replace it.
  • ProposalStatus enum — only the three existing values.
  • The POST /ai/proposals/{id}/approve route, request shape, or response shape (the body just gains the side-effect).
  • Handler registration via DI keyed-services (services.AddKeyedScoped<IProposalHandler>(proposalType, ...)) so each module owns its own wiring.
  • Status transition and handler execution happen in the same logical unit — if the handler throws, the proposal stays Proposed.
  • Handlers live in the owning domain module, not in Aonik.Agents.
  • The dispatcher emits an OpenTelemetry span (aonik.proposals.dispatch) with proposal.type and proposal.id tags.
  • Introducing async / background dispatch (would change the contract).
  • Letting handlers run outside the approval request thread (e.g. publish-and-forget).
  • Allowing more than one handler per ProposalType.
  • Adding a new database column to Proposal to track handler execution state (versus inferring it from Status).

5. Component design

5.1 Target flow

User clicks "Approve" in Admin UI ↓ POST /ai/proposals/{id}/approve ↓ ApproveProposalEndpoint ↓ ProposalApprovalService.ApproveAsync ├─ Load Proposal (must be Proposed) ├─ Flip Status → Approved, stamp approver + timestamp ├─ SaveChanges (proposal row committed) ├─ IProposalDispatcher.DispatchAsync(proposalType, AgentProposalDetail) │ ↓ │ IProposalHandler resolved from DI by ProposalType key │ ↓ │ handler.HandleAsync(detail, ct) ← domain side applies the change │ └─ On handler failure: revert Status → Proposed, SaveChanges, rethrow

5.2 Contracts (SharedKernel)

namespace Aonik.SharedKernel.Abstractions.Agents;

/// <summary>
/// Domain-side executor for an approved proposal. Implementations live in the
/// owning module (e.g. PersonalFinance for FLG annotations, Finance for bill
/// payments) and are registered with DI keyed by their ProposalType discriminator.
/// </summary>
public interface IProposalHandler
{
    /// <summary>The ProposalType string this handler is registered for.</summary>
    string ProposalType { get; }

    /// <summary>
    /// Apply the proposal's payload to the owning domain. Called by the dispatcher
    /// after the Proposal row has been flipped to Approved. If this method throws,
    /// the dispatcher reverts the proposal to Proposed and rethrows to the caller.
    /// </summary>
    Task HandleAsync(AgentProposalDetail proposal, CancellationToken cancellationToken);
}

/// <summary>
/// Resolves the IProposalHandler registered for a given ProposalType and invokes it.
/// Throws <see cref="NoProposalHandlerRegisteredException"/> when no handler is
/// registered — that error is treated as approval failure, not silent no-op.
/// </summary>
public interface IProposalDispatcher
{
    Task DispatchAsync(AgentProposalDetail proposal, CancellationToken cancellationToken);
}

public sealed class NoProposalHandlerRegisteredException : Exception
{
    public NoProposalHandlerRegisteredException(string proposalType)
        : base($"No IProposalHandler is registered for proposal type '{proposalType}'.")
    {
        ProposalType = proposalType;
    }

    public string ProposalType { get; }
}

5.3 Dispatcher implementation

namespace Aonik.Agents.Services;

internal sealed class ProposalDispatcher : IProposalDispatcher
{
    private readonly IServiceProvider _services;

    public ProposalDispatcher(IServiceProvider services) => _services = services;

    public Task DispatchAsync(AgentProposalDetail proposal, CancellationToken ct)
    {
        var handler = _services.GetKeyedService<IProposalHandler>(proposal.ProposalType)
            ?? throw new NoProposalHandlerRegisteredException(proposal.ProposalType);

        // OpenTelemetry span around the handler call (aonik.proposals.dispatch).
        return handler.HandleAsync(proposal, ct);
    }
}

5.4 Registration pattern

Each module's DependencyInjection.Add{Module} extension registers its handler with the type string as the DI key: 

// In Aonik.PersonalFinance/DependencyInjection.cs
services.AddKeyedScoped<IProposalHandler, FinancialLifeGraphAnnotationProposalHandler>(
    "FinancialLifeGraphAnnotation");

The dispatcher (in Aonik.Agents) registers once with the container and resolves handlers by key. New proposal types ship as one handler class plus one registration line.

5.5 Approval service change

// Aonik.Agents/Services/ProposalApprovalService.cs (post-change sketch)

public async Task<ProposalDetailResponse> ApproveAsync(Guid proposalId, CancellationToken ct)
{
    var proposal = await _dbContext.Proposals.FirstOrDefaultAsync(p => p.Id == proposalId, ct)
        ?? throw new KeyNotFoundException(...);

    if (proposal.Status != ProposalStatus.Proposed)
        throw new InvalidOperationException(...);

    proposal.Status = ProposalStatus.Approved;
    proposal.ApprovedByUserId = _currentUserProvider.GetCurrentUserId();
    proposal.ApprovedAt = _clock.UtcNow;
    await _dbContext.SaveChangesAsync(ct);

    try
    {
        var detail = ToDetail(proposal);
        await _dispatcher.DispatchAsync(detail, ct);
    }
    catch
    {
        // Handler failed. Revert so the user can retry or reject explicitly.
        proposal.Status = ProposalStatus.Proposed;
        proposal.ApprovedByUserId = null;
        proposal.ApprovedAt = null;
        await _dbContext.SaveChangesAsync(CancellationToken.None);
        throw;
    }

    var row = await JoinedQuery().FirstAsync(p => p.Proposal.Id == proposalId, ct);
    return Map(row);
}
Note The revert is best-effort — the proposal row and the domain side live in different DbContexts today, so this is not a true distributed transaction. Handlers must therefore be idempotent (see §6).

6. Failure & idempotency

6.1 Handler must be idempotent

The dispatcher catches handler exceptions and reverts the proposal status, but a handler that partially succeeded before throwing leaves the domain in a partial state. Handlers must therefore be safe to re-run on the same proposal payload — the retry path is "user clicks Approve again."

Concrete techniques handlers should use:

  • Check current state before mutating (e.g. FLG handler activates a node only if it is still Proposed; no-op otherwise).
  • Use deterministic IDs derived from the proposal payload, never Guid.NewGuid(), when creating downstream records.
  • Treat "downstream record already exists with this deterministic ID" as success, not as a duplicate-key failure.

6.2 Missing-handler is a hard failure

If ProposalType has no registered handler, the dispatcher throws NoProposalHandlerRegisteredException, the approval reverts, and the endpoint returns HTTP 409 with a structured error pointing at the missing type. This intentionally surfaces drift between proposals being created and the handlers that should execute them.

6.3 What this spec does not guarantee

  • Cross-module ACID. The proposal row and the domain-side mutation are still in separate DbContexts.
  • Exactly-once execution under crash mid-handler. If the process dies between the handler partially mutating and the revert happening, the proposal stays Approved with no domain effect. Resolution is operator-driven for now (read the audit log, decide).
  • Ordered execution of multiple approvals. Each approval is its own request.

Both gaps are acceptable for v1 because today's only handler (FLG annotation) already operates in this model with no observed issues; closing them would require an outbox pattern that is out of scope here.

7. Migrating the existing FLG handler

The existing FinancialLifeGraphInferenceService.ApproveProposalAsync body is the reference implementation of a handler. It already:

  • Loads the proposal via IAgentProposalStore.GetByIdAsync.
  • Parses PayloadJson to extract GraphNodeId.
  • Looks up the FLG node and edge.
  • Flips both to Active.
  • Saves the FLG context.
  • Calls IAgentProposalStore.ApproveAsync.
  • Invalidates the FLG cache.

The migration is a near-mechanical lift:

  1. Create FinancialLifeGraphAnnotationProposalHandler : IProposalHandler with ProposalType => "FinancialLifeGraphAnnotation" and the body moved over minus the ApproveAsync call (the dispatcher's caller has already flipped the proposal).
  2. Register it in Aonik.PersonalFinance DI under the same key.
  3. Delete ApproveFinancialLifeGraphProposalEndpoint and the corresponding reject endpoint.
  4. Reduce FinancialLifeGraphInferenceService.ApproveProposalAsync to a forwarder or remove if no other caller remains.
  5. Update any frontend references from /personal-finance/graph/proposals/{id}/approve to /ai/proposals/{id}/approve.

9. Acceptance criteria

  • dotnet build Aonik.sln and dotnet test Aonik.sln succeed.
  • Approving any FinancialLifeGraphAnnotation proposal via POST /ai/proposals/{id}/approve activates the underlying FLG node and edge.
  • Approving a proposal whose ProposalType has no registered handler returns HTTP 409 and leaves the proposal in Proposed.
  • If a handler throws, the proposal is left in Proposed (status reverted), the approver / timestamp fields are cleared, and the exception bubbles to the endpoint.
  • No code in Aonik.Agents references FinancialLifeGraphAnnotation or any other module-specific proposal type by name.
  • ApproveFinancialLifeGraphProposalEndpoint and its reject counterpart are removed; the admin UI / Payabo references the generic route.
  • Adding a hypothetical new proposal type requires one handler class + one AddKeyedScoped line, with no edits to Aonik.Agents or Aonik.SharedKernel.

10. Open decisions

Open Should handlers be allowed to reject a proposal at execution time (e.g. payload references a deleted entity)? Current proposal: they throw, the proposal reverts to Proposed, and the user has to explicitly dismiss. Alternative: a handler can return a HandlerResult { Status = Failed, Reason = "..." } that moves the proposal to a new Failed state. The alternative requires a fourth value on ProposalStatus.
Open Should the dispatcher run inside ProposalApprovalService.ApproveAsync (current proposal) or in a separate post-commit pipeline so the approval HTTP request can return quickly and execution happens out of band? Synchronous is simpler and matches user expectations ("clicked approve, it's done"), but slow handlers (e.g. external API calls) will tie up the approval request. Asynchronous needs an outbox or a hosted-service consumer.
Open How should the dispatcher's failure-revert interact with the audit log? Today there is no explicit audit emission on approve. The clean answer is: emit two audit events (proposal.approved on flip, proposal.execution_reverted on handler failure) so an operator reading the log sees the full story. Confirm whether that fits the existing IAuditLogWriter contract before implementing.
