Spec 041 Status: Draft Size: Medium Priority: P1 Domain: Agents / PersonalFinance / Platform

Agent memory: decision-aware learning

Extend AONIK's built memory subsystem so agents can remember why a decision was made, under which conditions that rationale applies, and what approach has worked across similar tenant cases. This is not a new memory platform: it adds Rationale entries to UserMemoryEntry, introduces tenant-scoped DecisionPattern records, and reuses the existing conversation-memory extraction machinery from the Worker for outcome-triggered extraction.

1. Summary

AONIK already remembers user facts and preferences. The platform has UserMemoryEntry, typed entries, confidence scores, supersede-not-delete history, SQL and Qdrant-backed IUserMemoryService implementations, user_memory_save / user_memory_recall tools, a User Brief projection path, and a Worker-side conversation summary and memory extraction job. This spec extends that system so memory can become decision-aware without creating a parallel subsystem.

The new behaviour is deliberately narrow. Agents may recall a past rationale as an explicit, overridable assumption only when the current decision's conditions are relevant. Agents may also consider a tenant- or segment-scoped pattern showing what worked across comparable cases. Neither rationale nor pattern memory can change a mutation's risk tier, bypass Spec 032, or pre-authorise money movement.

Success signals After a remittance route, invoice dunning sequence, proposal, or work item resolves, a Worker extraction pass writes a Rationale memory capturing why the choice was made and what conditions it depended on. The next comparable decision surfaces that rationale as a caveated prior and withholds it when the conditions no longer match. Separately, a tenant-scoped DecisionPattern lets the agent propose the cadence or approach that has worked across similar cases, while every mutation remains gated exactly as before.

3. Remaining gap

The built memory system can remember facts and preferences about a user. It does not yet model decisions as first-class memory. Four gaps remain:

  • Memory is about the user, not the choice. Entries can say finance.preferred_currency, but cannot say “chose the cheaper corridor because speed was not important and the payee was verified.”
  • Staleness is time-based, not context-based. A decision rationale does not merely get older; it becomes inapplicable when the payee, corridor, amount band, invoice segment, or verified history changes.
  • Learning is user-scoped only. There is no tenant-scoped aggregate of what worked across cases, such as the dunning cadence that cleared most invoices in a segment.
  • Extraction is idle-conversation triggered. The existing Worker job learns when a chat thread goes stale, not when a proposal, invoice, work item, or order sequence reaches an outcome.

5. Addition A: Rationale entries

Extend UserMemoryEntry rather than creating a new user-memory table. Existing profile memory remains Identity / Preference / Correction / Fact. A rationale is a current or superseded entry about a past choice for a specific user. 

// src/Aonik.Ai/Entities/UserMemoryEntryType.cs
public enum UserMemoryEntryType
{
    Identity = 1,
    Preference = 2,
    Correction = 3,
    Fact = 4,
    Rationale = 5
}

// src/Aonik.Ai/Entities/UserMemoryEntry.cs
public class UserMemoryEntry : Entity, ITenantScoped
{
    // Existing properties omitted for brevity.

    public string? DecisionType { get; set; }    // e.g. "remittance-routing", "dunning", "budget"
    public string? ConditionsJson { get; set; }  // salient features when the choice was made
    public string? StaleWhen { get; set; }        // human-readable invalidation note
}

5.1 Storage rules

  • DecisionType, ConditionsJson, and StaleWhen are nullable for the existing entry types and required by validation for Rationale writes.
  • Key remains the dot-key namespace. Rationale keys should include the decision type and stable subject grain, for example decision.remittance-routing.payee.{payeeId} or decision.dunning.segment.{segment}.
  • ValueJson stores the distilled rationale, not a raw transcript. It should include the chosen option, rejected alternatives if useful, the human steer, and outcome signal, but no secrets, full account numbers, or unnecessary PII.
  • AiRunId should point to the extraction run for inferred rationales. If the rationale is user-stated in a future UI, the value may be null or point to the user interaction run if one exists.

5.2 Recall behaviour

The new behaviour is at recall, not at storage. When an active decision has a DecisionType, the recall path should retrieve candidate current rationale entries for the same tenant/user/decision type and then apply a condition-relevance check against the current decision's salient features.

Condition resultBrief / recall behaviour
MatchSurface as an explicit prior: “Last time, you chose cost over speed for this verified payee and amount band.”
Partial matchSurface with caveat: “This held for EU to NG and a verified payee; the current corridor differs.”
MismatchWithhold from the Brief and from tool recall unless the caller explicitly asks for historical rationale.

V1 may implement condition relevance as a model-judged comparison using a prompt profile and the structured ConditionsJson. A later version may replace that with deterministic feature matching for common decision types. Either way, relevance only controls whether the rationale is presented to the agent; it never changes tool permissions.

6. Addition B: Pattern memory

Pattern memory has a different grain from UserMemoryEntry. It is tenant-scoped, optionally segment-scoped, aggregate, and reinforced across many cases. It answers: “for this kind of decision, what has worked for this tenant or segment?” It must not be filtered to a single user, and it must never leak across tenants. 

// Proposed placement: src/Aonik.Ai/Entities/DecisionPattern.cs
public class DecisionPattern : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public string DecisionType { get; set; } = string.Empty;
    public string? Segment { get; set; }
    public string Statement { get; set; } = string.Empty;
    public string? PayloadJson { get; set; }
    public int ObservationCount { get; set; }
    public decimal Confidence { get; set; }
    public DateTime? LastReinforcedAtUtc { get; set; }
    public DateTime? SupersededAtUtc { get; set; }
}

6.1 SQL-first store

V1 should store DecisionPattern in SQL and query by TenantId, DecisionType, optional Segment, SupersededAtUtc IS NULL, and confidence. This is enough for deterministic dunning and routing patterns without making semantic recall a dependency. A Qdrant-backed semantic collection can be added later if similar-but-not-identical decision matching becomes valuable.

6.2 Retrieval path

Pattern retrieval is a sibling path to memory recall. The User Brief projector should request top patterns for the active DecisionType and tenant/segment, then inject them alongside per-user memory in a clearly labelled section such as Tenant patterns for this decision. The pattern service must not accept a user id as a filter except for audit/context metadata; it is not user memory.

6.3 Reinforcement and supersession

  • When a resolved outcome confirms an existing pattern, increment ObservationCount, update confidence, and stamp LastReinforcedAtUtc.
  • When outcomes contradict a pattern strongly enough, supersede rather than delete. A reversal is itself useful signal.
  • Confidence should be bounded and monotonic only within the current pattern. Superseding starts a new current pattern rather than rewriting history.

7. Addition C: Outcome-triggered extraction

Reuse Worker-side AI extraction. The current stale-session path reacts to idle conversations. This spec adds a second trigger that reacts when a decision reaches an outcome. It should run out of band in the Worker through the transactional outbox, restore the originating tenant before processing, produce an audited AiRun, and write the resulting memory through the existing provider/service abstractions.

decision resolves | Proposal Applied/Failed - invoice Paid - WorkItemRun Succeeded/Failed/Proposed - order route completed v enqueue integration event in same transaction v DecisionOutcomeExtractionHandler (Worker outbox handler, tenant restored per event) +-- load context: AiRun, Proposal/WorkItemRun/invoice/order payload, outcome, available conversation summary +-- run use_case = decision-outcome-extraction through IAiTaskProfileResolver +-- write UserMemoryEntry { EntryType = Rationale, DecisionType, ConditionsJson, StaleWhen } +-- upsert/reinforce DecisionPattern { TenantId, DecisionType, Segment, Statement, PayloadJson } - same spend guards as conversation extraction: 3 attempts, 20 memories/pattern observations per resolution - all LLM calls produce AiRun through AuditMiddleware / IAiRunWriter - handler failure backs off through the existing outbox retry/dead-letter policy

7.1 Event surface

Introduce small integration events, emitted only after the state change is durable: 

public sealed record DecisionResolvedEvent(
    Guid TenantId,
    string DecisionType,
    string SourceType,      // "Proposal", "WorkItemRun", "Invoice", "Order"
    Guid SourceId,
    Guid? UserId,
    Guid? AiRunId,
    string Outcome,
    string? Segment,
    string? ContextJson) : IIntegrationEvent;

The event should be enqueued via AonikDbContextBase.EnqueueIntegrationEvent before the same SaveChangesAsync that persists the terminal state where feasible. If a resolution path already uses a module-scoped DbContext, use that context's inherited outbox support rather than publishing in-process after commit.

7.3 Extraction prompt profile

Add a new AI task profile pair:

  • use_case = decision-outcome-extraction
  • prompt_name = decision_outcome_extraction

The prompt must return structured output for candidate rationales and patterns. It must prefer IDs and references over raw PII. It must state when no memory should be written. It must not recommend a lower risk tier or any form of pre-approval.

8. Worked finance examples

8.1 Remittance routing

A customer chooses a cheaper but slower remittance corridor because the payee is verified and speed does not matter. On proposal application or order completion, extraction writes a user-scoped rationale with DecisionType = "remittance-routing", conditions for corridor/payee/amount band, and StaleWhen = "payee, corridor, urgency, or amount band changes". The next remittance to the same payee surfaces: “Last time you chose cost over speed here; same again?” A new payee or corridor fails relevance and the agent re-reasons from scratch. The payment capture remains High tier and still flows through proposal approval.

8.2 Dunning cadence

Across many invoices, outcome extraction reinforces a tenant-scoped DecisionPattern for DecisionType = "dunning" and a segment such as small-business/low-risk: “a soft reminder at day 3 cleared most invoices before escalation.” When planning the next sequence, the agent proposes that cadence for the tenant/segment. Reminders schedule as Spec 034 WorkItems, and any payment or ledger-affecting operation still becomes a proposal.

10. Guardrails

Hard boundary Memory informs reasoning only. It must never alter a tool's risk tier, satisfy an approval requirement, pre-authorise a mutation, or bypass Spec 030 / Spec 032.
  • Existing UserMemoryEntry semantics for current types must not change: current rows are superseded, not deleted; inferred/system entries decay; user-stated entries do not decay.
  • user_memory_save remains Low tier and user-id-from-auth. user_memory_recall remains read-only and fail-open on hot-path degradation.
  • Rationale and Pattern writes happen in the Worker, off the agent turn, and inherit the existing extraction spend controls.
  • Pattern memory is tenant-scoped and optionally segment-scoped. It is never user-scoped, never global, and never visible across tenants.
  • Qdrant tenant isolation remains fail-closed for any vector-backed extension.
  • Stored content is minimised: distilled judgement, IDs/references, no secrets, no full account numbers, no unnecessary PII.
  • Every LLM extraction call produces an AiRun and uses AiRoutePolicy / task profiles; no hard-coded model usage.
  • Any schema change follows the single migration stream: modify entities/configurations first, then generate with dotnet ef migrations add ... --project src/Aonik.Infrastructure --startup-project src/Aonik.Api.

15. Open decisions

Open O1: Pattern sibling entity vs tenant-scoped namespace. A dedicated DecisionPattern entity is recommended because the grain is tenant/segment aggregate, not per-user memory. Confirm before implementation.
Open O2: SQL only vs Qdrant-backed pattern recall. SQL keyed lookup is enough for v1 and avoids requiring semantic recall. Add Qdrant later if similar-decision matching needs it.
Open O3: Exact trigger set. Start curated: proposals, work item outcomes, and invoice settlement. Add order-specific events only when the remittance order implementation exposes a stable terminal signal.
Open O4: Condition relevance implementation. V1 can be descriptive/model-judged from ConditionsJson. Deterministic feature matching should be introduced per decision type once enough examples exist.
Open O5: Deliberation context. The design note references a companion conversational-deliberation note, but no DeliberationProposal code exists today. Outcome extraction should consume available AiRun, proposal, work item, invoice/order, and conversation-summary context until that companion design lands.
