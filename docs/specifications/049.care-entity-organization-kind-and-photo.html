Spec 049 Status: Draft (Rev 1) Size: Small Priority: P2 Domain: PersonalFinance

CareEntity — organization kind & photo upload

Two additive extensions to the CareEntity introduced in Spec 043. (A) A third kind — organization — for the things a user has a financial relationship with but does not own and that are not a person: a church, a mosque, a school, a cooperative, a hometown union, a charity. (B) First-class photo upload for any CareEntity, so a user can attach a picture (their church, their late father, the Surulere flat) — composed entirely over the existing Documents module (Spec 035) contracts, with no new blob path. The data model stays deliberately generic; the consuming frontend chooses the audience-facing language for each kind.

Why this is small Neither half needs a new table. The kind discriminator is a plain nvarchar(16) with no check constraint, so widening it adds zero migrations. Photo upload reuses CareEntity.PhotoDocumentId (already present, §5 of Spec 043) and the SharedKernel IDocumentWriter/IDocumentReader contracts — no new persistence. The dependent aggregates (commitments, payment logs) FK to CareEntityId regardless of kind, so an organization is fully functional the moment the discriminator accepts it.

1. Summary

Spec 043 modelled a CareEntity as exactly two kinds: a person ("Mum") or an asset you own and look after (a property, land, a vehicle, a business stake, a foreign account). Real users also have standing financial relationships with institutions they do not own — they tithe to a church, pay fees to a school, contribute to a cooperative or a hometown union, donate to a charity. None of these is a person, and none is an owned asset. Forcing them into asset would be a lie (no assetType fits, and §3.2 of Spec 043 forbids growing asset toward valuation), and forcing them into person distorts presentation and meaning.

This spec adds a third kind, organization, and generalises the kind ↔ assetType invariant accordingly. Separately, it makes the long-present PhotoDocumentId field usable: a single consumer endpoint uploads an image, stores it through the Documents module, points PhotoDocumentId at it, and the entity's responses return a time-limited signed URL the client can render.

Success signals A consumer creates "St. Stephen's" (organization, Nigeria) with a PersonalUser JWT — no assetType required, no admin surface — attaches a Support commitment (Spec 044) for a monthly tithe, logs payments against it (Spec 045), and the one-call profile rolls those up per currency. The same user uploads a photo of the church building; GET …/care-entities/{id} and the profile both return a signed photoUrl that renders directly from blob storage. The stored discriminator is the neutral word organization; whatever a given product calls it ("place of worship", "community", "biller") is a frontend choice, not a backend one.

2. Problem & current state

Confirmed against the tree:

  • The discriminator is a hard binary, enforced only in C#. Both the public validator (PersonalFinanceValidators.cs:384 — .Must(k => k is "person" or "asset")) and the service (CareEntityService.cs:80 — kind is not ("person" or "asset")) reject anything else. There is no database check constraint: CareEntityConfiguration.cs:16 maps Kind as nvarchar(16) only. So a third value is a code change, not a schema change.
  • The assetType rule is phrased around "person". The invariant today is "a person has no assetType; an asset must have one" (CareEntityService.NormalizeAssetType, PersonalFinanceValidators.cs:388–393). A third non-asset kind needs the rule generalised to "only an asset carries an assetType."
  • PhotoDocumentId exists but nothing populates or resolves it. CareEntity.PhotoDocumentId (Guid?) and the matching create/update DTO fields are present (Spec 043 §5/§7), but PersonalFinance has no IDocumentWriter usage at all (grep: zero hits) — it only reads links via IDocumentLinkReader in CareEntityProfileService. There is no upload path that sets PhotoDocumentId, and no response field that turns it into a viewable URL. A client can store a Guid but cannot show a picture.
  • The Documents module already does everything the blob side needs. IDocumentWriter.CreateDocumentAsync + UploadFileAsync persist a tenant-scoped, Sha256'd blob and an encrypted-at-rest DocumentFile; IDocumentReader.GetFilesAsync + GetReadUrlAsync(fileId, ttl) issue a time-limited signed read URL. Both are SharedKernel contracts PersonalFinance is allowed to call. No new storage primitive is required.

3. Scope (in / out)

3.1 In scope

  • New A third kind value organization (§4), with the kind ↔ assetType invariant generalised (§5).
  • Mutate The create/update validators and CareEntityService to accept and round-trip organization (§6).
  • New A consumer photo-upload endpoint that composes the Documents module to set PhotoDocumentId (§7–§8), and a remove-photo endpoint.
  • Extend CareEntityResponse (and the profile's embedded entity) with a resolved, signed photoUrl (§9).
  • New Image content-type and size validation at the PersonalFinance boundary (§10).

3.2 Out of scope the guardrail, inherited from Spec 043 §3.2

  • No new capability per kind. organization unlocks no valuation, no scheduling, no analytics, no org-directory — exactly the restraint applied to assetType. It is a presentation and grouping discriminator that carries the same five primitives every CareEntity has: commitments, payment history, documents, totals, circle-scope.
  • No relationship/ownership graph. The free-text relationship label ("my parish", "the co-op") is the only relational field; a typed membership/ownership graph is not in scope.
  • No avatar in the vault list. The photo is the entity's picture, not a piece of proof. It is referenced solely via PhotoDocumentId and is not a DocumentLink (Spec 046), so it never appears in the profile's Documents[] vault array (§8).
  • No image editing. No cropping, filters, or face detection. Optional server-side resize/thumbnail is a noted enhancement (§10), not a requirement.
  • Money movement. Unchanged from Spec 043: a CareEntity is record-keeping; it never funds or routes a payment.

4. Part A — the organization kind new

Three top-level kinds. A person, a thing you own, and a body you have a relationship with:

KindMeaningCarriesExamples
personSomeone you look after / support / administer for.A free-text relationship.Mum, Tope, Appa
assetA thing you are responsible for, pay for, and document — and own.An assetType + an ownership label.Surulere flat, the Hilux, family land
organizationA body you have a standing financial relationship with but do not own, and that is not a person.A free-text relationship (e.g. "my parish"); no assetType.A church, a school, a cooperative, a hometown union, a charity
Generic by design organization is the stored, neutral value — the data schema is product-agnostic. The consuming frontend determines the audience-facing language (a faith app may render it "place of worship", a B2B surface "biller", a generic PFM "organisation"). No Simi-specific or product-specific vocabulary enters the entity, the DTOs, or the validators. Adding the kind must not add a capability (Spec 043 §3.2, §6 restraint rule).

5. The kind ↔ assetType invariant

Spec 043 enforced: a person has no assetType; an asset must have one. With a third non-asset kind, the rule generalises cleanly to a single sentence:

Invariant Only kind = asset may carry an assetType; person and organization must not. An asset still requires one.

kind remains immutable after create (Spec 043 — CareEntityService.UpdateAsync keeps the existing kind). All other fields — name, countryCode, relationship, emoji, photoDocumentId, attributesJson — apply to all three kinds unchanged.

// PersonalFinanceValidators.cs — generalised rules
RuleFor(x => x.Kind)
    .NotEmpty()
    .Must(k => k is "person" or "asset" or "organization")
    .WithMessage("Kind must be 'person', 'asset', or 'organization'.");

RuleFor(x => x.AssetType)
    .NotEmpty().When(x => x.Kind == "asset")
    .WithMessage("An asset must have an assetType.");
RuleFor(x => x.AssetType)
    .Empty().When(x => x.Kind != "asset")     // person AND organization
    .WithMessage("Only an asset can have an assetType.");

// CareEntityService.NormalizeAssetType — generalised guard
private static string? NormalizeAssetType(string kind, string? assetType)
{
    if (kind != "asset")                       // person | organization
    {
        if (!string.IsNullOrWhiteSpace(assetType))
            throw new ArgumentException("Only an asset can have an assetType.", nameof(assetType));
        return null;
    }
    if (string.IsNullOrWhiteSpace(assetType))
        throw new ArgumentException("An asset must have an assetType.", nameof(assetType));
    return assetType.Trim().ToLowerInvariant();
}

7. Part B — photo upload new

Goal: a consumer attaches an image to any CareEntity (person, asset, or organization) and the entity's responses render it. The blob lifecycle lives entirely in the Documents module; PersonalFinance orchestrates and owns only the PhotoDocumentId pointer.

7.1 Design decision — one convenience endpoint, not client orchestration

The raw Documents primitives would make a mobile client issue three or four calls (create document → upload file → set pointer) and handle partial failure. Instead PersonalFinance exposes a single multipart endpoint that composes the contracts server-side — the same "one round-trip" ethos as the §8 profile in Spec 043. The client sends one image; the server does the rest in a transaction-like sequence and returns the updated entity with a ready-to-render URL.

POST /personal-finance/care-entities/{id}/photo (multipart: file) 1. load & own-check the CareEntity (tenant + user) ── PersonalFinance 2. validate image (content-type allow-list, size cap) ── PersonalFinance (§10) 3. resolve OwnerPartyId for the current user ── PersonalProfile (UserId → PartyId) 4. CreateDocumentAsync(type="avatar", classification=Personal) ─ IDocumentWriter (SharedKernel) 5. UploadFileAsync(documentId, image stream) ── IDocumentWriter 6. CareEntity.PhotoDocumentId = documentId; SaveChanges ── PersonalFinance 7. resolve signed photoUrl (GetFilesAsync → GetReadUrlAsync) ── IDocumentReader ──▶ 200 CareEntityResponse { …, photoUrl }

Steps 4–5 and 7 are the existing SharedKernel contracts (IDocumentWriter / IDocumentReader); step 3 is the inverse of PersonalFinancePartyResolver — a lookup of the user's PersonalProfile.PartyId. No DocumentLink is created (§3.2): the avatar is referenced only by PhotoDocumentId and stays out of the vault list.

Replace & remove Re-uploading repoints PhotoDocumentId to the new document and erases the previous avatar document via IDocumentWriter.DeleteDocumentAsync (right-to-erasure, Spec 035 §15) so orphaned blobs don't accumulate. DELETE …/{id}/photo clears the pointer and erases the document the same way. Both are owner-scoped and idempotent.

8. Photo composition flow (service)

A CareEntityPhotoService (PersonalFinance) injects IDocumentWriter, IDocumentReader, the PersonalFinanceDbContext, ITenantProvider / ICurrentUserProvider, and the party lookup. Sketch: 

public async Task<CareEntityResponse?> SetPhotoAsync(
    Guid careEntityId, Stream image, string fileName, string contentType, CancellationToken ct)
{
    var entity = await GetOwnedAsync(careEntityId, ct);   // tenant + user; null → 404
    if (entity is null) return null;

    ImageGuards.Validate(contentType, image.Length);       // §10 — throws ArgumentException → 422

    var ownerPartyId = await ResolveOwnerPartyIdAsync(ct); // PersonalProfile.PartyId for current user

    var doc = await _documents.CreateDocumentAsync(new CreateDocumentCommand(
        OwnerPartyId: ownerPartyId,
        DocumentType: "avatar",
        Classification: DocumentClassification.Personal,
        Source: "personal-finance/care-entity-photo"), ct);

    await _documents.UploadFileAsync(
        new UploadFileCommand(doc.DocumentId, fileName, contentType), image, ct);

    var previous = entity.PhotoDocumentId;
    entity.PhotoDocumentId = doc.DocumentId;
    await _db.SaveChangesAsync(ct);

    if (previous is { } old) await _documents.DeleteDocumentAsync(old, ct); // erase replaced avatar

    return await _mapper.ToResponseWithPhotoAsync(entity, ct);             // resolves signed photoUrl (§9)
}

Classification = Personal matches the owner-party-scoped, non-shared nature of a profile picture (the tax-return / payslip pattern in Spec 035 §10) and keeps it out of any tenant-wide index. DocumentType = "avatar" is a neutral marker; it is not a Spec 046 vault type and the avatar is never linked, so it never surfaces in profile.Documents[].

9. Photo API & DTO changes

9.1 Endpoints new

RouteVerbPurpose
/personal-finance/care-entities/{id}/photoPOSTUpload/replace the entity's photo (multipart file). Returns the updated CareEntityResponse with photoUrl.
/personal-finance/care-entities/{id}/photoDELETERemove the photo: clear PhotoDocumentId, erase the document. Returns 204.

Both are Policies("UserPolicy"), owner-scoped, under the existing /personal-finance/care-entities group, following the AllowFileUploads() + EndpointWithoutRequest multipart idiom of UploadDocumentFileEndpoint (Files[0], empty-file guard → 422).

9.2 Response — resolved signed URL extend

CareEntityResponse gains one nullable field, photoUrl, populated from PhotoDocumentId when present. The raw PhotoDocumentId stays for clients that manage the document directly. The profile (§8 of Spec 043) returns the same enriched entity, so the People/Places screen renders the avatar from its single call. 

public record CareEntityResponse(
    Guid Id, string Kind, string? AssetType, string Name, string CountryCode,
    string? Relationship, string? Emoji, Guid? PhotoDocumentId,
    Uri? PhotoUrl,                       // ← NEW: signed, short-TTL read URL (null when no photo)
    IReadOnlyDictionary<string,string> Attributes, bool Archived,
    DateTime CreatedAt, DateTime? UpdatedAt);

Resolution: GetFilesAsync(photoDocumentId) → first file → GetReadUrlAsync(fileId, ttl) with a short TTL (O3: 15 min default, vs. issuing on demand via a dedicated read-url endpoint). Resolving a URL per row in ListAsync would be N+1; list responses therefore return PhotoDocumentId only and PhotoUrl = null, while GetAsync and the profile resolve it. (Future: populate DocumentRef.ThumbnailUrl — already a field on the contract — for cheap grid thumbnails.)

10. Image validation & limits

Enforced at the PersonalFinance boundary before any blob is written:

  • Content-type allow-list: image/jpeg, image/png, image/webp. Anything else → 422. (The generic Documents upload accepts any type; the image constraint is specific to this avatar path.)
  • Size cap: reject empty files and files over a configured maximum (O2: default 8 MB).
  • Optional magic-byte / dimension check: the platform already ships IImageProcessingService (ValidateImageAsync, GetImageDimensionsAsync, ResizeImageAsync, CreateThumbnailAsync). Using it to confirm the bytes are a real image and to down-size very large originals is a recommended enhancement; it is not required for the first cut and adds no new dependency.
Fail closed Validation runs before CreateDocumentAsync, so a rejected upload writes nothing — no orphan document, no orphan blob. The own-check (404 for a non-owned entity) runs first of all, so existence is never revealed.

11. Persistence & migration

  • Part A: no migration. Kind is nvarchar(16) with no check constraint; "organization" (12 chars) fits. Verified against CareEntityConfiguration.cs. If a future hardening adds a CHECK on Kind, it must be a single tool-generated migration that includes all three values (CLAUDE.md — never hand-author migrations).
  • Part B: no new PersonalFinance table. The avatar lives as a Documents-module Document + DocumentFile (its own tables, created by their own spec); the only mutated column is the already-existing CareEntity.PhotoDocumentId. PhotoUrl is a computed response field, not stored.

12. Security

  • Owner isolation, unchanged. Every photo operation loads the CareEntity through the same TenantId == tenantId && UserId == userId filter; a non-owned id returns 404 (not 403).
  • Document ownership. The created avatar document's OwnerPartyId is the current user's party, resolved server-side from PersonalProfile — never from request input. Classification Personal keeps it owner-scoped and out of any shared index.
  • Signed-URL reads. The client never receives blob credentials — only a short-TTL signed URL from GetReadUrlAsync. Bytes are fetched directly from storage, not streamed through the API.
  • Erasure on replace/delete. Replaced and removed avatars are erased via DeleteDocumentAsync (vectors purged, blob removed, rows soft-deleted), so no orphaned personal image persists.
  • Untrusted bytes. The content-type allow-list and optional ValidateImageAsync guard against non-image payloads; no server-side rendering of the upload occurs in this module.

14. Acceptance criteria

  • Organization round-trips. A PersonalUser JWT creates, lists (filtered by kind=organization), updates, and archives an organization CareEntity with no assetType; an organization with an assetType is rejected (422), and an asset without one is still rejected. person and asset behaviour is unchanged.
  • Commitments & totals work for an organization. A Support commitment and payment logs against an organization roll up into per-currency YearTotals on the profile — proving the dependent aggregates are kind-agnostic.
  • Photo upload sets the pointer and returns a URL. POST …/{id}/photo with a JPEG returns 200 with photoDocumentId set and a non-null, fetchable photoUrl; GET …/{id} and the profile return the same signed URL.
  • Replace erases the old avatar. A second upload repoints photoDocumentId and the previously referenced document is erased (GetDocumentAsync → not found).
  • Remove clears it. DELETE …/{id}/photo returns 204; the entity then returns photoDocumentId = null, photoUrl = null.
  • Validation fails closed. A non-image content type and an over-cap file are both rejected (422) and create no document/blob (asserted via the writer mock).
  • Isolation. User A cannot set, read, or remove the photo of User B's CareEntity (404).
  • Avatar is not a vault item. After upload, the profile's Documents[] array does not contain the avatar document.
  • Build & no migration. dotnet build Aonik.sln green; dotnet ef migrations list shows no new migration introduced by Part A.

15. Open decisions

  • O1 — Backfill of the asset vs organization boundary. Some things created today as asset (e.g. "a business stake") are genuinely owned; a church previously had nowhere to go and may have been mis-entered. No automatic reclassification is proposed (kind is immutable); a user re-creates if needed. Flagged, leaning no-op.
  • O2 — Image size cap & allowed types. Spec proposes 8 MB and jpeg/png/webp. Confirm against mobile capture sizes; heic may warrant transcoding via IImageProcessingService if iOS clients send it.
  • O3 — URL delivery: embedded vs dedicated endpoint. Spec embeds a short-TTL photoUrl on GetAsync/profile (one round-trip). Alternative: a dedicated GET …/{id}/photo/url that mints a URL on demand (longer-lived entity responses, extra call to view). Embed chosen for the one-call ethos; revisit if responses are heavily cached.
  • O4 — Thumbnails. DocumentRef.ThumbnailUrl already exists but is unpopulated. Generating a 128px thumbnail on upload (CreateThumbnailAsync) would make grids cheap. Deferred; not required for Phase 1.
