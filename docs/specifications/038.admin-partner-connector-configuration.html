Spec 038 Status: Draft Size: Large Priority: P1 Domain: Platform / Finance / AdminUi

Admin UI partner connector configuration

Make the Admin UI fully configure partner connectors — provider credentials (client id, client secret, encryption key, webhook signing secret), mode (sandbox/live), enable/disable, and routing — persisted securely and picked up by the connector at runtime, with no redeploy. Today the "Payment gateways" page is a static mockup and the Spec 037 Flutterwave connector reads its config only from appsettings/environment at startup. This spec closes that gap by composing patterns that already exist in the codebase — the DB-backed settings store (ISettingProvider / ISettingManager, encryption-at-rest, audit), the auth-provider settings page (write-only secrets + hasXxx booleans), the GlobalSettingsPage form mechanics, the AdminPolicy FastEndpoints convention, and the Auth0ManagementClient runtime-resolve pattern. No new persistence primitive is invented.

1. Summary

Spec 037 built a real Flutterwave connector, but its credentials (ClientId, ClientSecret, EncryptionKey) and the webhook SigningSecret can only be set through appsettings / environment variables, evaluated once at startup (services.Configure<FlutterwaveOptions>(...) + an if (options.IsConfigured()) DI gate). An operator cannot configure or rotate a partner from the Admin UI; the "Payment gateways" page that looks like it would is a non-functional mockup.

The codebase already has every primitive needed to do this properly, used elsewhere for exactly this shape of problem (auth provider secrets, AI keys, comms connection strings):

  • A DB-backed settings store with a write path (ISettingManager.SetAsync), encryption at rest for secret keys (ISettingValueProtector over IDataProtection), caching, and audit (Setting : AuditableEntity).
  • A proven write-only-secret settings page — the Authentication settings page + AuthProviderSettingsService (never returns a secret; exposes hasXxx booleans; secret fields are write-only "leave blank to keep").
  • A runtime-resolve precedent — Auth0ManagementClient reads its secret from ISettingProvider at call time, so a stored change takes effect without a restart.

This spec wires those together: define partner-gateway setting keys, expose a secure GET/PUT /admin/settings/payment-gateways snapshot endpoint, make the connector resolve its config from the store at call time (layered over appsettings as a bootstrap fallback), and replace the mockup page with a real form built on the established settings-page mechanics. A structured connector-row management tier (per-partner enable/route/credentials-pointer) is included as a second scope band (§5.5).

Success signals In a clean deployment with empty appsettings, an operator opens Settings → Payment gateways → Flutterwave, enters the sandbox client id / secret / encryption key / webhook signing secret, toggles Enabled, and saves. The secrets are written encrypted to the AnkSettings table (never echoed back to the browser); the badges read Configured. A subsequent remittance routed to "Flutterwave" authenticates and transfers against the sandbox with no redeploy or restart, and a webhook verifies against the stored signing secret. Rotating the secret in the UI is picked up on the next call. The change is audited.

3. Scope (in / out)

3.1 In scope

  • New Tier 1 — provider gateway settings (the load-bearing path that makes Flutterwave configurable): setting keys + SettingDefinitions entries; a secure GET/PUT /admin/settings/payment-gateways snapshot endpoint + service (write-only secrets, hasXxx booleans); runtime resolution of those keys in the connector; and a real SettingsPaymentGatewaysPage built on the established settings-page mechanics.
  • Edit The Spec 037 connector to resolve its config from the settings store at call time (layered over appsettings), and drop the startup-only IsConfigured() DI gate in favour of always-register + gate-at-use (§5.3).
  • Edit The webhook signing-secret read to resolve from the settings store (so the UI-set value is honored), keeping the appsettings key as a fallback.
  • New Tier 2 — connector rows & routing (makes the partner-network UI functional): Create/UpdateConnectorAsync on IPartnerAdminService, connector endpoints, request DTOs exposing Status/ConfigJson/CredentialsRef, audit names, and the partner-network connector UI (§5.5).
  • Reuse Encryption at rest, caching, audit, AdminPolicy, FluentValidation, the API client, and the form/secret UX — all unchanged.

3.2 Out of scope

  • Per-tenant provider credentials. Provider credentials are global (one Flutterwave account per deployment), stored at SettingScope.Global — mirroring auth/AI/comms. Per-tenant overrides are a later extension (the store already supports SettingScope + TenantId).
  • A second real connector. The settings model is provider-generic, but only the Flutterwave keys + field model are delivered; eTranzact/Interswitch follow the same template.
  • Azure Key Vault. The settings store's IDataProtection encryption is the established at-rest mechanism; a Key-Vault move is platform-wide, not a connector concern.
  • Card-collection encryption-key usage. The EncryptionKey field is captured/stored here; AES-GCM card flows are Spec 037 phase 2.

5. Design

5.1 Setting keys (Tier 1)

New constants in Aonik.SharedKernel.Abstractions.Settings (neutral home so both Platform's SettingDefinitions and Finance's resolver reference the same strings without a cross-module dependency). Prefix Finance.Partners.* — deliberately not Auth.*, which SettingService treats as configuration-managed and write-locks (IsConfigurationManagedKey). Scope = Global.

KeySettingDefinition flagsMaps to
Finance.Partners.Flutterwave.Enableddefault "false", visibleUseRealFlutterwaveApi + the runtime active gate
Finance.Partners.Flutterwave.BaseUrldefault sandbox URL, visibleBaseUrl
Finance.Partners.Flutterwave.IdpTokenUrldefault IdP URL, visibleIdpTokenUrl
Finance.Partners.Flutterwave.ClientIdvisibleClientId
Finance.Partners.Flutterwave.ClientSecretIsEncrypted: true, not visibleClientSecret
Finance.Partners.Flutterwave.EncryptionKeyIsEncrypted: true, not visibleEncryptionKey
Finance.Partners.Flutterwave.DefaultTransferPurposedefault "family_maintenance", visibleDefaultTransferPurpose
Finance.Partners.Webhooks.Flutterwave.SigningSecretIsEncrypted: true, not visiblewebhook HMAC secret

These map 1:1 to the Spec 037 FlutterwaveOptions shape, so the appsettings binding stays valid as the bootstrap fallback. The secret keys fit comfortably under the Setting.Value 4000-char cap.

5.2 Backend — gateway settings snapshot endpoint (Tier 1)

A dedicated service + two endpoints, mirroring AuthProviderSettingsService / Get|UpdateAuthProviderSettingsEndpoint — but with a real working write (the keys are not Auth.*, so ISettingManager.SetAsync persists them). 

// GET /admin/settings/payment-gateways  → snapshot (NEVER returns a secret value)
public sealed record GatewaySettingsResponse(IReadOnlyList<GatewayProviderSnapshot> Providers);
public sealed record GatewayProviderSnapshot(
    string ProviderCode,            // "Flutterwave"
    bool   Enabled,
    string BaseUrl, string IdpTokenUrl, string ClientId, string DefaultTransferPurpose,
    bool   HasClientSecret,         // projected: !string.IsNullOrWhiteSpace(stored secret)
    bool   HasEncryptionKey,
    bool   HasSigningSecret,
    string SecretSource);           // "Database" | "Configuration" | "None" (provenance, not the value)

// PUT /admin/settings/payment-gateways  → write (secret fields are write-only: null = keep existing)
public sealed record GatewaySettingsUpdateRequest(IReadOnlyList<GatewayProviderUpdate> Providers);
public sealed record GatewayProviderUpdate(
    string ProviderCode, bool Enabled,
    string BaseUrl, string IdpTokenUrl, string ClientId, string DefaultTransferPurpose,
    string? ClientSecret, string? EncryptionKey, string? SigningSecret);  // null ⇒ unchanged
  • Endpoints (Platform, Endpoints/Admin/Settings/): Get|UpdatePaymentGatewaySettingsEndpoint : Endpoint<…>, Get/Put "/admin/settings/payment-gateways", Policies("AdminPolicy"), Options(x => x.WithTags("Settings")).
  • Service IGatewaySettingsService / GatewaySettingsService: GetAsync projects each provider from ISettingProvider.GetForScopeAsync(key, Global) into the snapshot, computing HasXxx = !IsNullOrWhiteSpace(secret) and never copying the secret into the DTO. UpdateAsync writes each non-secret via ISettingManager.SetAsync(key, value, Global), and each secret only when the request value is non-null/non-empty (write-only) — exactly the secret.length > 0 ? secret : null rule the auth page already uses.
  • Where it lives: Platform (alongside AuthProviderSettingsService), because the settings store + ISettingManager are Platform/Infrastructure and the keys are plain strings. Finance only needs the key constants (in SharedKernel) to read them.
  • Validation (PlatformValidators.cs): ProviderCode in an allow-list; BaseUrl/IdpTokenUrl absolute URLs; secret lengths bounded.
  • Audit: one GatewaySettingsUpdated event per save with a redacted detailsJson (which keys changed, never secret values).
  • Key gate: like the generic settings endpoints, reject any key whose SettingDefinitions.Get(key) == null — so the snapshot only ever touches the registered Finance.Partners.* keys.

5.3 Runtime resolution — the connector reads the store at call time

This is the one structural change to Spec 037. Today the connector takes IOptions<FlutterwaveOptions> (a startup snapshot) and is registered only if (IsConfigured()) at boot. To honor a UI change without a restart, the config must be resolved per call — the Auth0ManagementClient pattern. 

// New: resolves the effective options from the settings store, layered over appsettings.
internal interface IFlutterwaveConfigProvider { Task<FlutterwaveOptions> GetAsync(CancellationToken ct); }

internal sealed class FlutterwaveConfigProvider(ISettingProvider settings, IOptions<FlutterwaveOptions> fallback)
    : IFlutterwaveConfigProvider
{
    public async Task<FlutterwaveOptions> GetAsync(CancellationToken ct) => new()
    {
        UseRealFlutterwaveApi = await Bool(PartnerGatewaySettingNames.FlutterwaveEnabled, _fallback.UseRealFlutterwaveApi, ct),
        BaseUrl       = await Str(PartnerGatewaySettingNames.FlutterwaveBaseUrl, _fallback.BaseUrl, ct),
        ClientId      = await Str(PartnerGatewaySettingNames.FlutterwaveClientId, _fallback.ClientId, ct),
        ClientSecret  = await Str(PartnerGatewaySettingNames.FlutterwaveClientSecret, _fallback.ClientSecret, ct),
        EncryptionKey = await Str(PartnerGatewaySettingNames.FlutterwaveEncryptionKey, _fallback.EncryptionKey, ct),
        // … each value: settings-store value ?? appsettings fallback ?? default …
    };
}
  • Layering: stored value wins; appsettings/env remains a valid bootstrap and CI default; built-in defaults last. So Spec 037's existing config path keeps working unchanged when the store is empty.
  • Connector / token provider take IFlutterwaveConfigProvider instead of IOptions<FlutterwaveOptions> and call GetAsync at the top of each operation. (The token provider's cache already shields the IdP from per-call overhead; settings reads are cached by SettingService with CachePolicy.Short.)
  • DI change: drop the startup if (flutterwaveOptions?.IsConfigured()) gate; always register the Flutterwave connector + translator alongside Simulated (Spec 037 §7.6 already argued for alongside-registration). "Is it usable?" becomes a runtime check: if a caller routes to "Flutterwave" while Enabled=false or credentials are missing, the connector throws the clear not-configured FlutterwaveException it already has. The capability the connector advertises can also be gated on the resolved Enabled so the no-code capability route skips a disabled provider.
  • Webhook secret: change RemittanceOrderService.ResolveWebhookSigningSecret to read ISettingProvider.GetAsync(PartnerGatewaySettingNames.FlutterwaveSigningSecret) first, falling back to the existing IConfiguration key — so a UI-set signing secret is honored at webhook time.

5.5 Tier 2 — connector rows & routing (makes partner-network functional)

Tier 1 configures the provider (global credentials). Tier 2 makes the per-partner Connector rows manageable so an operator can say "this partner uses Flutterwave for NGN payouts," enable/disable it, and point its CredentialsRef at the gateway settings. This fills the "awaiting backend" gap in the partner-network UI.

  • New IPartnerAdminService.CreateConnectorAsync / UpdateConnectorAsync / DeleteConnectorAsync (gated on "Settings.Write", audited with new ConnectorCreated/Updated/Deleted event names) — mirroring the existing partner CRUD methods in the same service.
  • New Endpoints under Endpoints/Partners/ (Post/Patch/Delete "/admin/partners/{partnerId}/connectors[/{connectorId}]", Policies("AdminPolicy")) + Create/UpdateConnectorRequest DTOs exposing ConnectorType, Status (enable/disable), ConfigJson, and CredentialsRef (a pointer to the gateway settings, not the secret).
  • Edit PartnerConnectorItem to surface ConfigJson; extend partnerService.ts + types/partners.ts with connector mutations; make the partner-network connector tab a real create/edit form (same useState+service pattern).
  • Note Connector has no IEntityTypeConfiguration today (convention-mapped). If column constraints are wanted, add a ConnectorConfiguration and a tool-generated migration against AonikDbContext (per CLAUDE.md) — otherwise no schema change is required.
  • Capability/routing selection (which connector serves a corridor) still rides the in-memory capability model + the deferred RoutingRule engine (Spec 037 G16/O10); Tier 2 makes the rows editable, not the routing engine. Editing a connector's advertised capabilities persists to ConnectorCapability rows (already present from Spec 031).
Tier boundary Tier 1 alone fully answers the original question — it lets an operator configure Flutterwave's client id / secret / encryption key / webhook secret from the Admin UI and have the connector use them at runtime. Tier 2 is what makes "fully configure partners" true end-to-end (connector rows + routing surfaces). Tier 1 is the priority; Tier 2 can land in a follow-up PR without blocking Flutterwave go-live.

6. Secret-handling rules (normative)

  • Never return a secret to the browser. The snapshot endpoint exposes only hasXxx booleans + provenance, mirroring AuthProviderSettingsService (and deliberately not the generic batch endpoint, which decrypts).
  • Write-only secret fields. A null/empty secret in the update request means "keep existing" — the server skips the SetAsync for that key. Rotation = type a new value; clearing requires an explicit "clear" affordance (out of scope v1).
  • Encrypted at rest. Secret keys are IsEncrypted: true in SettingDefinitions; SettingService encrypts via ISettingValueProtector (IDataProtection, "Aonik.Settings" purpose). No plaintext secret column.
  • Audit without leakage. The audit detailsJson records which keys changed and by whom — never the values. (Setting is already an AuditableEntity.)
  • Authz. All gateway endpoints are Policies("AdminPolicy") (PlatformAdmin/TenantAdmin); the connector-row writes additionally gate on "Settings.Write" at the service layer, like the existing partner CRUD.
  • Redacted logs. Connector/raw-response redaction from Spec 037 (§7.4) already prevents secrets/PANs reaching logs; nothing here changes that.

8. Acceptance criteria

  • Configure from the UI. With empty appsettings, an admin sets Flutterwave client id / secret / encryption key / webhook signing secret + Enabled in Settings → Payment gateways and saves; the secrets persist encrypted to AnkSettings and the badges read Configured.
  • Secrets never leave the server. The GET snapshot response contains no secret values (only hasXxx); asserted by a service + endpoint test.
  • Runtime pickup, no restart. After saving, a remittance routed to "Flutterwave" authenticates + transfers against the sandbox without a redeploy; rotating the secret is honored on the next call. The webhook verifies against the stored signing secret.
  • Bootstrap fallback intact. With the store empty and appsettings/env populated, behavior is identical to Spec 037 (no regression).
  • Authz + audit. Non-admins get 401/403; every save emits an audit event recording changed keys but no secret values.
  • Tier 2 (if included). An admin can create/enable/disable a partner connector and set its CredentialsRef/ConfigJson from the partner-network UI; changes are audited.
  • Build & reuse. dotnet build Aonik.sln + npm run build green; no new persistence table for Tier 1; no React Query introduced.
