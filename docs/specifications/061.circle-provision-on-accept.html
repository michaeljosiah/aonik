Spec 061 Status: Draft (Rev 1) Size: Medium Priority: P1 (Simi launch-gating) Domain: PersonalFinance + Identity / Simi

Circle invites — anonymous preview & provision-on-accept

Spec 048 shipped circle invites described as links "that provision on accept" — but the code stopped short: AcceptInviteAsync requires an already-authenticated user, and there is no way to see what an invite offers before committing. This is the invite loop's last mile on the server: a stranger holding a token must be able to (1) see, without an account, exactly what is being shared, and (2) go from token to registered member in one uninterrupted flow. Pairs with Simi Spec 049 (the mobile deep link + parked-token resume) and the web landing (launch register §8, Simi #22). Closes aonik #197. The client contract already exists — this spec is the server half.

Anonymous surface — token is the capability The preview endpoint is unauthenticated. The invite token is a bearer secret, so preview must be fail-closed (one 404 for invalid / expired / consumed alike — no oracle), rate-limited, and disclose the minimum to render "someone shared X with you." It inherits Spec 048's non-negotiable: no amounts, anywhere, ever.

1. Summary

Two server capabilities complete the growth loop's last mile:

  • Anonymous invite preview new — an unauthenticated, fail-closed, rate-limited endpoint that turns a raw token into a minimal, amount-free summary (owner display name, scope label, the shared entities' names, expiry). It backs the signed-out mobile accept screen (Simi Spec 049) and the web /circle/accept landing so a recipient sees what they're joining before signing up.
  • Provision-on-accept extend — a continuous path from unregistered invitee to active member: the parked token survives registration (Auth0 sign-up + phone/email OTP, reusing the Identity module), and the first authenticated accept materialises the grant — idempotently, with a self-accept guard and single-use enforcement.

No new sharing scopes, no change to the fail-closed visibility filter (Spec 048 §5 owns that). The CircleGrant model already supports what we need: MemberUserId is nullable and a grant may sit in pending status until a member binds.

2. Problem & current state

What exists today (Spec 048, merged):

  • POST /personal-finance/circle/invites mints a signed, single-use, 7-day token (CircleInvite: Token, Scope, EntityIdsJson, NoAmounts, Channel, ExpiresAt, Status = pending|accepted|expired|revoked, ConsumedAt, GrantId).
  • POST /personal-finance/circle/invites/accept — UserPolicy (authenticated). AcceptInviteAsync(token) binds the current user as member and returns the grant, or 404 if the token is invalid / expired / consumed.

The two gaps, stated in the code itself:

ICircleService.AcceptInviteAsync — the deferral "Unregistered-invitee registration + OTP provisioning is a Spec 001 follow-up; accept requires an authenticated user." That follow-up is this spec.
  • No preview. Every circle read is behind UserPolicy. A signed-out recipient — the common case for a growth invite — can see nothing about the invite, so "sign up to find out what a stranger shared" is the ask. That is exactly the friction that kills a share loop.
  • No provisioning path. Accept presumes an authenticated user materialises out of nowhere. For an unregistered invitee there is no defined, tested route from token → registered member, and no guarantee the token survives the registration round-trip or that a double-accept is safe.

3. Scope (in / out)

In

  • Anonymous GET .../invites/{token}/preview — fail-closed, rate-limited, amount-free.
  • Invite-aware registration: the parked token survives Auth0 sign-up + OTP; first accept provisions the member.
  • Accept hardening: idempotency, self-accept guard, single-use, member binding.
  • Optional pre-provisioned pending grant + claim-on-register when the invite carries a verified contact (see §6, gated by an open decision).

Out

  • New scopes or any change to the visibility filter / no-amounts property (Spec 048, unchanged).
  • Deferred deep linking across a store install (token preservation through the App/Play Store is a client concern; a vendor like Branch is explicitly out of scope — see Simi #22).
  • The Support Statement, the member view, and revocation (Spec 048, unchanged).
  • Standing up the OTP transports themselves — ACS SMS (aonik #193) and email (aonik #192) are separate launch-gating items this spec consumes, not delivers.

4. The end-to-end flow

tap https://simi.app/circle/accept?token=T │ ├─ app installed ─────────────► Simi Spec 049 deep link ─► accept screen │ │ └─ not installed ─► web /circle/accept landing (Simi #22) │ │ │ GET .../invites/{T}/preview (anonymous, this spec) ◄───┤ "Ama shared 2 people │ │ & places with you" signed in? ──yes──────────────────────────────────────► POST .../invites/accept │ (idempotent, this spec) └─no─► register (Auth0 + phone/email OTP) ─┘ token parked through sign-up (Simi 049) ─► auto-accept

The client (Simi Spec 049) already parks the token while signed out and resumes accept after auth + setup. This spec makes the two server touchpoints that flow assumes actually exist: the anonymous preview, and an accept that is safe for a brand-new user to call (possibly twice).

5. Anonymous invite preview

new GET /personal-finance/circle/invites/{token}/preview — AllowAnonymous.

Resolves the invite by (TenantId, Token). Returns 200 only when the invite is pending and unexpired; otherwise a single 404 (invalid, expired, and consumed are indistinguishable — no oracle). Response is the minimum needed to render the accept CTA:

InvitePreviewResponse {
  ownerDisplayName : string      // e.g. "Ama O." — from the owner's profile display name
  scope            : "all" | "entities" | "docsOnly"
  scopeLabel       : string      // "Everything they look after" | "Selected people & places" | "Documents only"
  entityNames      : string[]    // names only; [] for scope=all; never for docsOnly if names leak amounts context
  entityCount      : int
  noAmounts        : bool        // always true for docsOnly; echoes the grant term
  expiresAt        : datetime
}

Fail-closed rules:

  • No amounts, balances, corroboration, member lists, or document contents — ever. The preview is a headline, not a view. The scoped view stays behind UserPolicy + the Spec 048 filter, unchanged.
  • Entity names are the one deliberate disclosure (they mirror the mobile accept screen's "they shared: X"). Whether even names are too much for a bearer token is an open decision — the fallback is counts only ("2 people & places").
  • Rate-limited per IP and per token (see §10). Reads are logged.

6. Provision-on-accept

"Provision on accept" means an unregistered recipient becomes a member without a dead end. Two mechanisms, layered:

6.1 Parked-token registration (baseline)

extend The mobile client parks the token and, after the recipient registers (Auth0 sign-up + phone OTP via ACS SMS #193, or email #192), calls accept as the now-authenticated user (Simi Spec 049 already implements the park/resume). The server obligations:

  • A freshly-registered user can accept immediately — no eventual-consistency window between identity creation and ICurrentUserProvider resolving the new user within the tenant.
  • The invite's Channel hint (email|phone) informs which OTP transport the registration flow prefers, so the provisioned member verifies the same contact the owner addressed.

6.2 Pre-provisioned pending grant + claim-on-register (optional, open decision)

new Because CircleGrant.MemberUserId is nullable and Status may be pending, an invite that carries a verified contact can pre-materialise a pending grant. When a user later registers and verifies that same contact (OTP), the grant binds automatically — the share is durable and claimable even if the token is mislaid. This is gated on an open decision (§13): auto-binding on contact match has real privacy weight and must require a verified match, never a bare email string.

7. Hardening accept (idempotency & guards)

extend AcceptInviteAsync / POST .../invites/accept:

  • Idempotent. A repeat accept of a token this same user already consumed returns the existing grant (200), not 404. This is essential: the parked-token resume can fire more than once (cold start + warm link), and a store round-trip can replay the request.
  • Self-accept guard. If the current user is the invite's OwnerUserId, reject with 409 (or 422) — you cannot be a member of your own circle.
  • Single-use across users. A different user accepting an already-consumed invite gets 404 (fail-closed; the invite is spent).
  • Atomic binding. Materialising the grant, setting the invite Status = accepted, ConsumedAt, and GrantId happen in one transaction.

10. Security

  • Fail-closed preview. One 404 for invalid/expired/consumed. Never confirm a token "exists but is used" — that is an enumeration oracle.
  • Rate limiting. Per-IP and per-token ceilings on the anonymous preview to blunt token farming and enumeration. Tokens are already high-entropy and 7-day-scoped; the limiter is defence in depth.
  • Minimal disclosure. Owner display name + entity names + scope + expiry. No amounts, no member graph, no contact of other members, no document bytes.
  • No-amounts property preserved. Preview and provisioning add no amount-bearing path; the Spec 048 filter test suite still governs every authenticated read.
  • Claim-on-register (§6.2) requires a verified contact match — never bind a pending grant on an unverified email string. Tenant isolation holds throughout.
  • Audit. Log preview reads, accepts, and any pending-grant binding with token id (not the raw token), actor, and outcome.

11. Enforcement & testing

  • Anonymous preview of a valid pending invite returns owner name + scope + entity names, and — asserted field-by-field — no amount-bearing field and no member list.
  • Preview of an expired, consumed, revoked, or unknown token → 404, indistinguishable across all four.
  • Unregistered → register (mock OTP) → accept materialises exactly one active grant with MemberUserId = the new user.
  • Double-accept by the same user is idempotent (same grant, 200, no duplicate row).
  • Owner accepting their own invite → rejected.
  • A second, different user accepting a consumed invite → 404.
  • Preview rate limit trips after the configured ceiling.
  • (If §6.2) claim binds only on a verified contact match; an unverified match does not bind.

13. Acceptance criteria

  • [ ] A signed-out client can GET a valid invite's preview and render "<owner> shared <scope/entities> with you" with zero authentication and zero amounts.
  • [ ] Invalid / expired / consumed / revoked tokens all return an indistinguishable 404 from preview.
  • [ ] An unregistered recipient completes register → accept and ends as the member of exactly one active grant; the token does not survive as re-consumable.
  • [ ] Accept is idempotent for the same user and rejects self-accept.
  • [ ] Preview is rate-limited and its reads are audited.
  • [ ] Spec 048's no-amounts test suite still passes unchanged; a new test proves the preview leaks no amounts.
  • [ ] The ICircleService.AcceptInviteAsync "Spec 001 follow-up" deferral note is removed.

14. Open decisions

Preview disclosure Entity names vs counts only? Names match the app's accept screen and read as warmer ("Mum, the Accra flat"); counts leak less to a token-holder. Recommendation: names, since the token is already a secret capability — but make the projection a single switch so it can be dialled back.
Claim-on-register (§6.2) Ship pre-provisioned pending grants + auto-claim now, or defer until a real "invite lands before the app" case appears? Recommendation: defer; ship the parked-token baseline (§6.1) for launch, keep §6.2 behind the open decision. Baseline closes #197's launch-gating need.
Required OTP transport for a provisioned member Phone (ACS SMS, #193) is the registration default; is email (#192) an acceptable alternative for a circle-provisioned member, or must a member verify phone? Recommendation: follow the invite's Channel hint, require at least one verified contact.
Reject code for self-accept 409 Conflict vs 422. Recommendation: 409 — it is a state conflict, not a validation error.
