Spec 033 Status: Draft Size: Large Priority: P1 Domain: Architecture / Platform / AI

Extract Documents into its own module (Aonik.Documents) with RAG-by-default ingestion

Promotes the document capability — today a compliance-shaped folder hierarchy inside Aonik.Platform, plus a second, disconnected RAG upload path in Aonik.Api — into a first-class sibling module Aonik.Documents. Documents become a tenant-and-party-scoped substrate that any module (Finance, PersonalFinance, Platform/Compliance, Ai, Agents) can consume through SharedKernel contracts. Verification stays in Compliance as a consumer. Every indexable document is auto-ingested into the vector store via integration events so the platform’s agents can search a customer’s evidence by default — under a mandatory owner-party retrieval filter that does not exist today. (Tenant isolation already exists fail-closed in the vector store; party-level isolation — the real B2C gap — does not.)

1. Summary

Aonik has two unrelated things both called “documents” today, and neither lives where it should:

  • A compliance evidence model — Document, DocumentFile, DocumentUsage, DocumentVerification, DocumentVersion — buried inside the Compliance slice of Aonik.Platform. It conflates generic file storage with KYC verification, so a customer’s tax document has nowhere natural to live: it is a document, but it has no DocumentUsage and no DocumentVerification.
  • A RAG upload endpoint (POST /ai/documents/upload) in Aonik.Api that chunks, embeds, and upserts text into a single Qdrant documents collection — completely disconnected from the compliance model, text-only, synchronous, and (critically) applying no owner-party isolation: the vector store stamps and filters tenant_id fail-closed, but within a tenant one customer’s agent could retrieve another customer’s documents.

This spec unifies and relocates both. It extracts a first-class Aonik.Documents module — a sibling to Aonik.Finance and Aonik.PersonalFinance, following the precedent set by ADR-006 / Spec 027 — that owns the generic document concern: a file exists, it is owned by a party, it carries metadata and a classification, it is retrievable, and (when indexable) it is searchable by AI. Compliance is refactored into a consumer: DocumentUsage and DocumentVerification stay in Platform/Compliance and reference a document by id through a SharedKernel contract, never by project reference.

Every indexable document is auto-ingested into the vector store by an asynchronous, event-driven pipeline (Worker / Quartz), so agents can search a customer’s documents by default — gated by a DocumentClassification and protected by a mandatory owner-party retrieval filter layered on the vector store’s existing fail-closed tenant filter. The scoping fix is non-negotiable and ships in the same change: routing tax returns, bank statements, and KYC evidence through an unscoped shared collection is a privacy incident waiting to happen.

Success signals dotnet build Aonik.sln succeeds with Aonik.Platform containing no generic-document entities and no Aonik.Infrastructure.VectorStore coupling for document RAG; any module can create and search documents through SharedKernel.Abstractions.Documents with zero project reference to Aonik.Documents; a document uploaded by tenant A / party X is provably un-retrievable by an agent acting for tenant B or party Y; the legacy POST /ai/documents/upload path is removed in favour of the unified ingestion pipeline; dotnet test Aonik.sln stays green.

2. Context & motivation

AONIK is an AI-native platform powering three products (Payabo B2C, MyBillAfrica B2B, RemitExchange remittance). Documents are not a finance concept — they are a customer concept. An individual may upload a tax return, a payslip, a contract, a letter, or an ID scan. Some of those feed compliance (KYC); most do not. Today the only home for a document is the Compliance slice, which forces a compliance shape onto purely personal evidence.

SymptomEvidence
Documents are mis-homed under Compliance Entities live in src/Aonik.Platform/Entities/Compliance/; endpoints are routed under /compliance/documents behind AdminUserPolicy — unreachable for an end customer uploading a personal tax document.
Storage and verification are conflated A Document cannot exist usefully without the DocumentUsage / DocumentVerification compliance machinery, even when no verification is wanted.
Two parallel, disconnected document systems DocumentService (blob) and DocumentUploadEndpoint (vector) share a name and nothing else. A file in blob storage is never searchable; a vector has no durable document of record.
RAG vectors are not party-scoped QdrantVectorStore already injects and filters tenant_id fail-closed (QdrantVectorStore.cs EnhancePayloadWithTenant / BuildMergedFilter), but the DocumentUploadEndpoint.cs payload (lines 121–129) carries no owner_party_id, classification, or purpose. In a shared-tenant B2C product (Payabo) one customer’s agent could retrieve another’s documents. Separately, DeleteAsync ignores its filter argument, so document-level purge needs a scroll-then-delete pass.
No path for “AI knows my documents” For an AI-native platform, an agent should be able to answer “what did my last tax return say” — impossible while uploads and embeddings are two manual, unlinked actions.

ADR-005 anticipated selective extraction once a subdomain earns its own boundary, and Spec 027 established the mechanics (csproj, module class, scoped DbContext, SharedKernel read contracts, migrations staying with AonikDbContext). Documents now meet that bar: a clear bounded vocabulary, cross-cutting consumers, and an expanding AI surface (ingestion, extraction, classification, search) that does not belong to any one product.

3. Scope (in / out)

In scope

  • Create the Aonik.Documents module project and register it in the composition root.
  • Move the generic document entities (Document, DocumentFile, DocumentVersion) and their EF configurations into the new module; add ingestion/extraction state.
  • Add a DocumentClassification and an index-policy gate.
  • Define SharedKernel.Abstractions.Documents read / write / search contracts and integration events.
  • Refactor Compliance so DocumentUsage / DocumentVerification consume documents by id through the contract.
  • Build the asynchronous, event-driven RAG ingestion pipeline (extract → chunk → embed → upsert) in the Worker.
  • Fix vector-store scoping: stamp tenant_id, owner_party_id, document_id, classification, purpose on every vector and enforce a mandatory retrieval filter. P0
  • Provide a scoped IDocumentSearch for agents, plus a document deletion path that purges vectors.
  • Replace POST /ai/documents/upload with unified document upload + automatic indexing.
  • Expose customer-facing upload endpoints (not just AdminUserPolicy) so end users can upload personal documents.

Out of scope

  • Changing the physical SQL database, table names (Ank prefix), or migration ownership — migrations continue through AonikDbContext per ADR-005.
  • Swapping the vector store (Qdrant stays) or the embedding provider.
  • OCR vendor selection for image-only documents (interface defined; a real adapter is a follow-up).
  • The compliance verification workflow itself (KYC decisioning logic is unchanged; only its document linkage moves to a contract).
  • Document e-signing, redaction tooling UI, or a document-bundle concept (noted as extensions).

4. Constraints & guardrails

  • No direct cross-module references. Finance, PersonalFinance, Compliance, Ai and Agents consume documents only through SharedKernel.Abstractions.Documents and integration events — never a ProjectReference to Aonik.Documents.
  • Single migration stream. All schema changes are generated by the EF CLI against AonikDbContext in Aonik.Infrastructure. DocumentsDbContext is a read/write scoping context with no migrations. Agents never hand-author migrations.
  • Anemic entities. All logic lives in services returning DTOs; entities stay { get; set; } data containers implementing ITenantScoped and inheriting AuditableEntity.
  • Tenant + party isolation is an invariant, not a feature. Every blob path, every vector payload, and every retrieval query is scoped by TenantId and (for personal classifications) OwnerPartyId. There is no code path that reads documents or vectors without a scope.
  • Agents propose; systems execute. Search and read are direct, low-risk agent tools. Document deletion and any mutation of compliance state remain governed by the approval tiers in Spec 032.
  • Every AI contribution is auditable. Extraction and AI-assisted classification record an AiRun and carry the AiRunId forward, consistent with the existing DocumentVerification.AiRunId field.
  • HTTP contract care. The legacy /ai/documents/upload route is removed only after the unified path is live; existing /compliance/documents/* routes keep working for admin/compliance callers.

6. The two-concern split

The core design move is recognizing that today’s model fuses two responsibilities that have different owners, lifecycles, and access policies:

Generic document capabilityCompliance verification
Question it answers“A file exists, who owns it, where is it, can the AI read it?”“Does this evidence satisfy a KYC purpose?”
OwnerAonik.Documents (new)Aonik.Platform / Compliance (existing)
EntitiesDocument, DocumentFile, DocumentVersion, DocumentIngestion, DocumentExtractionDocumentUsage, DocumentVerification
Applies to a tax return?Yes — stored, classified, indexedNo — no usage/verification needed
ConsumersEveryone, via SharedKernelCompliance workflow, KYC cases

This mirrors the platform’s existing Order vs Payment vs Ledger discipline: distinct concepts are never collapsed just because they often co-occur. A document is the durable record of a file; a verification is a compliance decision that happens to reference a document. Compliance keeps its DocumentUsage / DocumentVerification tables but stores the document id as a plain Guid (the same pattern DocumentUsage already uses for RelatedEntityId), resolving document detail through IDocumentReader.

9. Domain model

Entities stay anemic, ITenantScoped, and inherit AuditableEntity. Fields carried over from the existing model are unchanged; new fields are marked new.

Document

  • Id, TenantId, OwnerPartyId
  • DocumentType (string) — e.g. TaxReturn, BankStatement, NationalId, UtilityBill, Contract, Other
  • Classification (enum) new — drives indexing & access; see §10
  • Status (string) — Draft, Submitted, Verified, Rejected, Expired, Revoked
  • Source (string) new — CustomerUpload, AdminUpload, StatementImport, PartnerCallback
  • IndexStatus (enum) new — NotIndexable, Pending, Indexed, Failed
  • IndexedAt (DateTime?) new
  • IssuedOn, ExpiresOn, IssuerName, CountryCode, ReferenceNumber (masked/hashed per policy)
  • TagsJson, AttributesJson

DocumentFile

  • Id, DocumentId, StorageProvider, StorageContainer, StorageKey
  • ContentType, FileName, FileSizeBytes, Sha256
  • PageIndex, Side (Front/Back), CapturedAt, CapturedBy, MetadataJson
  • ExtractedTextStatus (enum) new — tracks whether text is available for embedding (Native, OcrRequired, OcrDone, Unsupported)

DocumentIngestion new

  • Id, DocumentId, DocumentFileId
  • VectorCollection, ChunkCount, EmbeddingModel, EmbeddingCost
  • Status (Pending/Running/Succeeded/Failed), Attempts, LastError, CompletedAt
  • AiRunId (Guid?) — embedding run is auditable

DocumentExtraction new

  • Id, DocumentId, ExtractionType (OcrText, StructuredFields)
  • OutputJson, Confidence, AiRunId

DocumentUsage / DocumentVerification (stay in Compliance)

Unchanged fields, except DocumentUsage.DocumentId is now a cross-module reference resolved through IDocumentReader rather than an EF navigation property. The cascade delete from Document is replaced by a DocumentDeletedEvent handler in Compliance that decides how to treat orphaned usages (default: mark Expired, never silently delete a compliance record).

10. Classification & index policy

“Auto-ingest all documents” is the intent, but all is gated by a classification so the pipeline never blindly embeds something it shouldn’t. The default for every common type is indexable; the gate exists to handle the sharp edges (raw ID images, anything explicitly restricted).

ClassificationExamplesDefault index behaviourRetrieval scope
PublicProduct terms, public noticesIndexedTenant
InternalOperational docsIndexedTenant
PersonalTax return, payslip, statement, letterIndexedTenant + OwnerPartyId
SensitiveID scans, proof-of-address imagesMetadata-only by default; text indexed only after OCR + redaction policy passesTenant + OwnerPartyId + purpose
RestrictedExplicitly excluded evidenceNever indexedDirect read only, no vector

Classification is assigned at upload (caller-supplied, defaulted by DocumentType) and may be refined by an AI classifier that records an AiRun. The pipeline reads the classification to decide IndexStatus: Personal/Internal/Public → Pending (will index); Restricted → NotIndexable; Sensitive → Pending only once text extraction + redaction are available.

11. SharedKernel contracts & events

All consumption flows through Aonik.SharedKernel.Abstractions.Documents. Shapes are illustrative; final signatures accept CancellationToken cancellationToken = default and return DTOs (records), never entities. 

namespace Aonik.SharedKernel.Abstractions.Documents;

public enum DocumentClassification { Public, Internal, Personal, Sensitive, Restricted }

public sealed record DocumentSearchScope(
    Guid TenantId,
    Guid? OwnerPartyId,                          // required for Personal/Sensitive
    IReadOnlyList<string>? Purposes = null,
    IReadOnlyList<DocumentClassification>? Classifications = null);

public sealed record DocumentChunkHit(
    Guid DocumentId, int ChunkIndex, string Content, double Score,
    string DocumentType, Guid OwnerPartyId);

public interface IDocumentReader
{
    Task<DocumentDto?> GetDocumentAsync(Guid documentId, CancellationToken ct = default);
    Task<PagedResult<DocumentListItem>> ListDocumentsAsync(ListDocumentsQuery query, CancellationToken ct = default);
    Task<IReadOnlyList<DocumentFileDto>> GetFilesAsync(Guid documentId, CancellationToken ct = default);
    Task<Uri> GetReadUrlAsync(Guid documentFileId, TimeSpan ttl, CancellationToken ct = default);
}

public interface IDocumentWriter
{
    Task<DocumentDto> CreateDocumentAsync(CreateDocumentCommand cmd, CancellationToken ct = default);
    Task<DocumentFileDto> UploadFileAsync(UploadFileCommand cmd, Stream content, CancellationToken ct = default);
}

public interface IDocumentSearch
{
    // Scope is mandatory; there is no overload that omits it.
    Task<IReadOnlyList<DocumentChunkHit>> SearchAsync(
        string query, DocumentSearchScope scope, int topK = 8, CancellationToken ct = default);
}

Integration events (in SharedKernel, raised by Documents):

  • DocumentUploadedEvent(TenantId, DocumentId, DocumentFileId, Classification, ContentType) — triggers ingestion.
  • DocumentIndexedEvent(TenantId, DocumentId, ChunkCount) — lets consumers react when a doc becomes searchable.
  • DocumentDeletedEvent(TenantId, DocumentId, OwnerPartyId) — triggers vector purge and Compliance orphan handling.

12. Compliance refactor

Compliance loses ownership of generic documents but keeps verification. The mechanical changes:

  • DocumentUsage and DocumentVerification entities + configs stay in Aonik.Platform; the EF navigation from Document is removed and DocumentId becomes an indexed Guid column (no cross-module FK).
  • A trimmed DocumentVerificationService (renamed from the verification half of today’s DocumentService) injects IDocumentReader to resolve document detail when presenting a usage.
  • Compliance endpoints stay under /compliance/document-usages/* and /compliance/documents/{id}/usages; the upload + list + get generic endpoints are removed from Compliance and re-homed under /documents/*.
  • A DocumentDeletedEvent handler in Compliance marks dependent usages Expired rather than deleting them, preserving the audit trail.

13. RAG ingestion pipeline

Ingestion is asynchronous and event-driven — upload never blocks on embedding. This decouples cost and latency from the request path, makes embedding failures retryable, and fits the platform’s integration-event model.

POST /documents (multipart) └─▶ DocumentService.UploadFileAsync 1. DocumentFileStore.UploadDocumentFileAsync → blob (tenant-scoped key, Sha256) 2. persist Document + DocumentFile (IndexStatus per classification) 3. publish DocumentUploadedEvent 4. return 201 immediately Worker: DocumentIngestionJob (Quartz, consumes DocumentUploadedEvent) 1. load file; resolve text: native (txt/pdf/docx) → extract image/scan → OCR (DocumentExtraction, AiRunId) or defer if unavailable 2. chunk (512 words / 100 overlap) [reuse existing chunker] 3. IEmbeddingService.GetEmbeddingsBatchAsync 4. ScopedDocumentVectorAdapter.UpsertAsync → Qdrant with full scoped payload 5. record DocumentIngestion (ChunkCount, cost, AiRunId); set Document.IndexStatus=Indexed 6. publish DocumentIndexedEvent on failure: IndexStatus=Failed, Attempts++, LastError; retry with backoff; dead-letter after N

The chunking logic and the embedding service already exist (today inline in DocumentUploadEndpoint); they are lifted into the indexer service unchanged in behaviour. PDF/DOCX extraction — currently a NotImplementedException stub — is implemented here (or routed through OCR), since “index all documents” requires more than text/plain.

14. Vector-store scoping fix P0

Blocker The vector store already isolates by tenant fail-closed (QdrantVectorStore.EnhancePayloadWithTenant stamps tenant_id on every upsert and BuildMergedFilter adds a tenant_id clause to every search). What it lacks is owner-party isolation: in a shared-tenant B2C product (Payabo), routing personal documents through it as-is would let one customer’s agent retrieve another customer’s evidence within the same tenant. That sub-tenant filter is the real fix, and it ships in the same change as RAG-by-default — not as a follow-up.

Implemented additively as ScopedDocumentVectorIndex (in Aonik.Infrastructure.VectorStore, implementing IDocumentSearch + IDocumentVectorIndex) on top of the existing IVectorStore, so the tenant guarantee is reused, not re-implemented. Every chunk it upserts carries: 

payload = {
  // tenant_id is injected fail-closed by the vector store (existing behaviour)
  "owner_party_id": <Guid>,        // NEW — the missing sub-tenant key
  "document_id":    <Guid>,
  "classification": "Personal",    // NEW
  "purpose":        "tax|kyc|...", // NEW (nullable)
  "document_type":  "TaxReturn",   // NEW
  "chunk_index":    i,
  "content":        "...",
  "created_at":     <utc>
}
  • Mandatory filter. IDocumentSearch.SearchAsync takes a non-optional DocumentSearchScope and adds an owner_party_id must clause (plus optional classification/purpose match.any clauses) on top of the store’s tenant clause. There is no unscoped search method.
  • Scope derivation. Agent search tools derive the scope from the authenticated ITenantProvider + ICurrentUserProvider / owner party — never from model-supplied arguments — so a prompt cannot widen its own scope.
  • Erasure. Because IVectorStore.DeleteAsync ignores its filter argument, PurgeDocumentAsync scrolls by document_id (tenant clause auto-merged) and deletes each returned point id — a document-level purge that can never reach across tenants.
  • Collection strategy. Keep a single Qdrant collection but enforce the filter (operationally simpler), or partition per tenant. Decision deferred to §26; the payload + filter contract is identical either way, so the choice is reversible.
  • Defence in depth. A test asserts that a search scoped to party Y returns zero hits for a document indexed under party X within the same tenant (and the existing store tests already cover cross-tenant isolation).

15. Deletion & right-to-erasure

“All documents in a vector store” is a compliance liability without a delete story (NDPR / GDPR right-to-erasure). Deleting a document:

  • Soft-deletes the Document + DocumentFile rows (existing soft-delete infra).
  • Removes the blob object(s) via IDocumentFileStore.
  • Purges all vectors for that document_id via IDocumentVectorIndex.PurgeDocumentAsync (scroll-then-delete under the auto-merged tenant filter).
  • Publishes DocumentDeletedEvent so Compliance and other consumers react.
  • Is governed by the approval tiers in Spec 032 when initiated by an agent — deletion is not an in-band AI action.

Document deletion ties into the user-lifecycle closure flow (Spec 026): account closure must enumerate and erase a party’s documents and their vectors.

17. Module class

internal sealed class DocumentsModule : IModule
{
    public IServiceCollection RegisterModule(IServiceCollection services, IConfiguration config)
    {
        services.AddScoped<IDocumentService, DocumentService>();
        services.AddScoped<IDocumentReader>(sp => sp.GetRequiredService<DocumentService>());
        services.AddScoped<IDocumentWriter>(sp => sp.GetRequiredService<DocumentService>());
        services.AddScoped<IDocumentIndexer, DocumentIndexer>();
        services.AddScoped<IDocumentSearch, DocumentSearch>();
        services.AddDbContext<DocumentsDbContext>(/* shared connection string, no migrations */);
        return services;
    }
}

18. DocumentsDbContext

A module-scoped context over the same physical database, exposing only the generic-document sets. It inherits AonikDbContextBase (tenancy, audit, soft-delete) and declares no migrations — AonikDbContext remains the single migration stream and continues to own every DbSet. 

public sealed class DocumentsDbContext : AonikDbContextBase
{
    public DbSet<Document> Documents => Set<Document>();
    public DbSet<DocumentFile> DocumentFiles => Set<DocumentFile>();
    public DbSet<DocumentVersion> DocumentVersions => Set<DocumentVersion>();
    public DbSet<DocumentIngestion> DocumentIngestions => Set<DocumentIngestion>();
    public DbSet<DocumentExtraction> DocumentExtractions => Set<DocumentExtraction>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        base.OnModelCreating(b);
        b.ApplyConfigurationsFromAssembly(typeof(DocumentsDbContext).Assembly);
    }
}

19. Migration & data strategy

Tables keep their Ank-prefixed names (AnkDocuments, AnkDocumentFiles, …) so the move is project-structure-only for existing data. The schema deltas are limited to new columns and new tables:

  • AnkDocuments: add Classification, Source, IndexStatus, IndexedAt.
  • AnkDocumentFiles: add ExtractedTextStatus.
  • New tables: AnkDocumentIngestions, AnkDocumentExtractions.
  • AnkDocumentUsages: DocumentId becomes a plain indexed column (drop the cross-entity FK constraint; data unchanged).
Migration rule These deltas are generated only by the EF CLI against AonikDbContext: dotnet ef migrations add DocumentsModuleExtraction --project src/Aonik.Infrastructure --startup-project src/Aonik.Api, then reviewed and applied with dotnet ef database update. No hand-authored migrations; no edits to the .Designer.cs snapshot. The entity configs move first (so the model compiles), the DbSets remain on AonikDbContext, and the migration is regenerated from the changed model.

A one-time backfill (optional, Worker job) can publish DocumentUploadedEvent for existing indexable documents so historical evidence becomes searchable; classification for legacy rows defaults from DocumentType.

  • Generate the tool-made migration against AonikDbContext.

Phase 2 — Refactor Compliance to consume documents

Verification keeps working through the contract.
  • Drop the EF navigation; DocumentUsage.DocumentId becomes a scalar resolved via IDocumentReader.
  • Split DocumentVerificationService out; wire DocumentDeletedEvent orphan handling.

Phase 3 — Event-driven ingestion pipeline

RAG-by-default goes live.
  • DocumentIngestionJob consumes DocumentUploadedEvent; implement PDF/DOCX extraction + OCR hook.
  • Lift chunker + embedding into DocumentIndexer; record DocumentIngestion with AiRunId.
  • Expose IDocumentSearch as a scoped agent tool.

Phase 4 — Decommission legacy & backfill

One document system.
  • Remove POST /ai/documents/upload and DocumentUploadEndpoint.
  • Optional backfill of existing indexable documents; update Document-Model.md.

R4End customers (not only admins) can upload personal documents; tax/personal documents require no compliance usage.
R5Indexable documents are auto-ingested into the vector store asynchronously via DocumentUploadedEvent; upload returns before embedding completes.
R6Every vector carries tenant_id, owner_party_id, document_id, classification; every search enforces a tenant (+party) filter with no unscoped overload.
R7Search scope is derived from authenticated context, never from model/agent input.
R8Document deletion removes blob + vectors and emits DocumentDeletedEvent; agent-initiated deletion is approval-gated per Spec 032.
R9Ingestion and AI classification/extraction record an AiRun and propagate AiRunId.
R10All schema changes are EF-CLI-generated against AonikDbContext; tables keep Ank prefixes; no hand-authored migrations.
R11The legacy /ai/documents/upload endpoint is removed once the unified path is live.

25. Decisions baked in

  • New first-class module (Aonik.Documents), not a Platform sub-feature — per the ADR-006 precedent.
  • Verification split out — generic documents vs compliance verification are separate concerns; Compliance consumes documents.
  • RAG-by-default via events — all indexable documents auto-ingested asynchronously, gated only by classification.
  • One unified change — module extraction, verification split, ingestion pipeline, and the vector-scoping fix land together (scoping fix is non-negotiable).
  • Migrations stay with AonikDbContext; tables keep Ank names; no physical DB change.

26. Open design decisions

Open Single Qdrant collection + filter vs per-tenant collections. Filter-on-shared is simpler operationally and is assumed by default; per-tenant collections give harder isolation and easier per-tenant purge at the cost of collection sprawl. The payload + filter contract is identical either way, so this is reversible — decide based on tenant scale.
Open Where the ingestion job lives. Aonik.Worker (Quartz, consistent with existing background jobs) vs an in-process integration-event handler inside Aonik.Documents. Worker is preferred for retry/back-off and cost isolation.
Open OCR provider for Sensitive/image documents — interface defined now, adapter (Azure AI Document Intelligence / Textract / open-source) chosen later.
Open Embedding re-index on model change. Whether to version the embedding model on DocumentIngestion and support bulk re-embedding when the model upgrades.
