Spec 042 Status: Draft Size: Large Priority: P2 Domain: Commerce / Ordering / AI

Aonik.Commerce — a retail commerce module on the unified Order spine

Adds a first-class B2C commerce capability (the initial driver: a wellness-food storefront) as a sibling module Aonik.Commerce that owns the genuinely new retail domain — product catalog, product pricing, inventory, and cart/checkout — while reusing the platform foundations a product purchase already has: the unified Order spine (ADR-011 / Spec 041), Invoice billing, PaymentIntent funding (incl. the public guest-checkout path), the Party customer model, and the agentic / tiered-approval rails (Spec 032 / Spec 030). Commerce never references Finance: it reaches orders, billing, and payments through SharedKernel contracts.

1. Summary

AONIK can already order, bill, fund, and audit a product purchase — that is what Spec 041 delivered by generalising the Order spine, adding the ProductPurchase order type with retail line columns, and relocating the spine into the shared Aonik.Ordering layer. What it cannot yet do is the genuinely retail part: hold a catalog of products, price them, track stock, and let a customer fill a cart and check out. This spec adds that as a new sibling module, Aonik.Commerce.

The design principle is reuse the spine, own the retail:

  • Own (new): Product, ProductVariant, ProductPrice, InventoryLevel, InventoryReservation, Cart, CartItem, plus catalog/cart services and a commerce-agent.
  • Reuse (existing): create the purchase as a ProductPurchase order through SharedKernel.Abstractions.Ordering.IOrderService; bill it through Invoice; fund it through PaymentIntent (incl. guest checkout); identify the buyer through the Party model; govern every AI mutation through the Spec 032 approval gate and Spec 030 proposals.

Critically, Aonik.Commerce holds no ProjectReference to Aonik.Finance. It depends downward on SharedKernel and Aonik.Ordering, and reaches Finance-owned billing/payment through new SharedKernel write contracts (the write-side mirror of the ADR-006 read contracts), implemented by Finance and injected at the composition root.

Success signals A customer (or the commerce-agent) can browse a catalog, add items to a cart, and check out; checkout reserves stock, creates a ProductPurchase order via IOrderService, raises an Invoice, and funds it via a PaymentIntent on the existing public payment path; capturing payment confirms the order and decrements inventory. dotnet build Aonik.sln is green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering and no reference to Aonik.Finance; dotnet test Aonik.sln stays green.

2. Context & motivation

The concrete driver is a real B2C project — selling wellness-food products — that wants AONIK's agentic infrastructure (a domain agent with audited, approval-gated tools), multi-tenancy, and payment rails rather than re-building them. A prior study of the codebase confirmed that the order / payment / billing / party / agent foundations are reusable, but the retail concerns (catalog, inventory, cart, storefront) do not exist and the existing "Catalog" in Finance is a bill-payment biller directory, not a product catalog. Spec 041 closed the order-spine gap; this spec closes the remaining retail gap.

4. Scope (in / out)

In scope

  • Create the Aonik.Commerce module (csproj, module class, CommerceDbContext) referencing only SharedKernel + Aonik.Ordering; register in the composition root.
  • Catalog: Product, ProductVariant, ProductCategory, ProductMedia, ProductPrice + services + customer/admin endpoints.
  • Inventory: InventoryLevel, InventoryReservation + reserve/commit/release.
  • Cart: Cart, CartItem + a checkout orchestrator that creates a ProductPurchase order, invoice, and payment intent.
  • New SharedKernel write contracts for invoicing + payment initiation, implemented by Finance.
  • commerce-agent (IDomainAgentDescriptor) + CommerceToolApprovalManifest + product/cart tools + proposal handlers for any high-tier actions.
  • Public catalog browse + guest-checkout endpoints reusing the existing public payment path.

Out of scope

  • A production storefront UI (a separate app like apps/Payabo); this spec exposes the APIs it would consume and may ship a minimal Admin UI catalog manager.
  • Discounts / coupons / promotions engine, tax calculation, and carrier/shipping integration — noted as follow-ups behind interfaces.
  • Marketplace / multi-merchant payouts, subscriptions/recurring product boxes (a later extension that could reuse PersonalFinance subscriptions).
  • Any change to the Order spine itself (delivered by Spec 041) or to migration ownership (stays with AonikDbContext).

5. Constraints & guardrails

  • No reference to Finance. Aonik.Commerce references only SharedKernel + Aonik.Ordering. Orders go through IOrderService; billing/payment through new SharedKernel write contracts; party data through IPartyReader. Finance and Commerce remain siblings that never reference each other (ADR-005).
  • Order / Payment / Ledger never collapse. A purchase is a ProductPurchase order; funding is a PaymentIntent; truth is the ledger. Commerce orchestrates; it does not post ledger entries or move money directly.
  • Single migration stream. All schema changes are EF-CLI-generated against AonikDbContext; CommerceDbContext is runtime scoping with no migrations. Tables use the Ank prefix. Agents never hand-author migrations.
  • Anemic entities. Commerce entities are { get; set; } data containers implementing ITenantScoped + AuditableEntity (ADR-002); logic lives in services returning DTOs.
  • Product is a soft reference from the order. OrderItem.ProductId is a no-FK Guid (Spec 041). Commerce validates product/variant existence at checkout before calling the spine; the Order layer never depends on the product table.
  • Agents propose; systems execute. Catalog/cart reads are direct agent tools; product/price/inventory writes are medium (in-session confirmation); anything that captures payment stays high and runs only via a Finance proposal (Spec 030/032). Every AI action records an AiRun.
  • Inventory is never oversold. Reservation is atomic and tenant-scoped; checkout reserves before order creation and commits on payment capture, releasing on expiry/cancellation.

8. Domain model

All entities are anemic, ITenantScoped, inherit AuditableEntity.

Product / ProductVariant

class Product       { Guid Id, TenantId; string Slug, Name, Description, Status; Guid? CategoryId;
                      string TagsJson, AttributesJson; }
class ProductVariant{ Guid Id, TenantId, ProductId; string Sku, Name; string OptionsJson; // size/flavour
                      decimal? WeightGrams; bool IsActive; }
class ProductCategory { Guid Id, TenantId; string Slug, Name; Guid? ParentCategoryId; }
class ProductMedia  { Guid Id, TenantId, ProductId; string Url, Kind /*image|doc*/; int SortOrder; }

ProductVariant.Sku is the value copied onto OrderItem.Sku at checkout; ProductVariant.Id is copied onto OrderItem.ProductId (the soft reference). The catalog is the source of truth for product detail; the order keeps an immutable snapshot of what was bought.

ProductPrice

class ProductPrice  { Guid Id, TenantId, ProductVariantId; string Currency; decimal Amount;
                      DateTime? EffectiveFrom, EffectiveTo; bool IsActive; }

Per-variant, per-currency, optionally time-boxed. See §9.

Inventory

class InventoryLevel       { Guid Id, TenantId, ProductVariantId; string? Location;
                             decimal OnHand, Reserved; }   // Available = OnHand - Reserved
class InventoryReservation { Guid Id, TenantId, ProductVariantId, CartId; decimal Quantity;
                             string Status /*Held|Committed|Released*/; DateTime ExpiresAt; }

Cart / CartItem

class Cart     { Guid Id, TenantId; Guid? BuyerPartyId; string? AnonymousToken;  // guest carts
                 string Status /*Open|CheckedOut|Abandoned*/; string Currency; }
class CartItem { Guid Id, TenantId, CartId, ProductVariantId; decimal Quantity, UnitPriceSnapshot;
                 string Sku, NameSnapshot; }

9. Product pricing

Commerce owns product pricing; the Finance "Pricing" subsystem is FX/fee pricing and is not reused. IProductPricingService.ResolvePrice(variantId, currency, atUtc) returns the active ProductPrice for a variant. At cart add and again at checkout the resolved unit price is snapshotted onto the cart line / order item so a later catalog price change never silently alters an in-flight order. Multi-currency is supported by storing one ProductPrice per currency; the cart's Currency selects which.

10. Inventory & reservation

Stock is decoupled from the order so checkout never oversells:

add-to-cart → no stock change (availability is advisory at this point) checkout (begin) → IInventoryService.ReserveAsync(variant, qty, cartId) atomic: Available = OnHand - Reserved ≥ qty ⇒ Reserved += qty, Held row (fails fast if insufficient — checkout returns OutOfStock) payment captured → CommitAsync: OnHand -= qty, Reserved -= qty, reservation Committed cancel / expiry → ReleaseAsync: Reserved -= qty, reservation Released (Quartz sweeps expiries)

Reservation hold has a TTL (default 30 min) so abandoned checkouts free stock. Commit is triggered by the payment-captured signal (see §11/§12). All operations are tenant-scoped and use the row concurrency token to serialise concurrent reservations on the same variant.

11. Cart & checkout flow

POST /commerce/carts/{id}/checkout 1. validate cart: variants active, prices resolvable, currency consistent 2. resolve buyer Party (authenticated party, or create/guest via Party + AnonymousToken) 3. IInventoryService.ReserveAsync for each line (fail ⇒ 409 OutOfStock) 4. IOrderService.CreateAsync(CreateOrderCommand{ OrderType = ProductPurchase, PayerPartyId = buyer, Items = cart lines → OrderItemCommand{ Quantity, UnitPrice, ProductId, Sku, AmountIn } }) 5. IInvoiceWriter.CreateForOrderAsync(orderId) (Finance, via SharedKernel) 6. IPaymentInitiator.CreateIntentForOrderAsync(orderId, method) → PaymentIntent (Draft) 7. return { orderId, invoiceId, paymentIntentId, clientSecret? } → client confirms payment payment captured (Finance, high-tier / public path) → OrderFulfilmentRef links the PaymentIntent; IOrderService.TransitionAsync(order, Complete) → Commerce reacts (event): InventoryService.CommitAsync; cart → CheckedOut

The capture itself is a Finance concern (a Spec 032 high action on the existing public/admin payment path) — Commerce never captures money. Commerce learns of capture via an integration event (e.g. PaymentCompletedEvent already defined in SharedKernel) and commits inventory + closes the cart.

12. Billing & payment write contracts

Commerce must bill and initiate payment without referencing Finance. Two new SharedKernel write contracts — the write-side mirror of the ADR-006 read contracts — are implemented by Finance and injected at the composition root: 

namespace Aonik.SharedKernel.Abstractions.Billing;
public interface IInvoiceWriter
{
    Task<InvoiceRef> CreateForOrderAsync(CreateInvoiceForOrderCommand cmd, CancellationToken ct = default);
}

namespace Aonik.SharedKernel.Abstractions.Payments;
public interface IPaymentInitiator
{
    Task<PaymentIntentRef> CreateIntentForOrderAsync(CreatePaymentIntentForOrderCommand cmd, CancellationToken ct = default);
}

These keep money mechanics in Finance (where the ledger, providers, and approval tiers live) while letting Commerce orchestrate a checkout. Capture/settlement are not on these contracts — they remain Finance-governed high-tier actions.

Open Contract-call vs event-driven billing. The flow above bills synchronously via IInvoiceWriter/IPaymentInitiator for a tight checkout UX. The alternative is to emit OrderCreatedEvent and have Finance create the invoice/intent asynchronously. Synchronous is recommended for checkout responsiveness; revisit if billing grows heavy.

13. Commerce agent & tools

A commerce-agent (IDomainAgentDescriptor) is registered and composed by the Master Orchestrator like the Finance agent. Its tools are classified by a CommerceToolApprovalManifest (IToolApprovalManifest) and wrapped by the existing gate — no change to the gate itself:

ToolTierEffect
commerce_search_products, commerce_get_product, commerce_view_cart, commerce_check_inventoryreadDirect execution.
commerce_add_to_cart, commerce_update_cart_itemlowReversible cart-state writes; in-band with audit.
commerce_create_product, commerce_update_product, commerce_set_price, commerce_adjust_inventorymediumEveryday domain writes; in-session confirmation, args-hash-bound.
commerce_checkoutmediumCreates order + invoice + draft intent; no money moves yet (capture is separate).
commerce_refund (later)highMoney movement → durable Finance Proposal; never in-band.

Read tools resolve tenant/party scope from authenticated context, never from model input. Each invocation records an AiRun; medium/high decisions persist a ToolApprovalRequest / Proposal.

14. Storefront & public API

  • Public catalog — GET /commerce/catalog/products, /products/{slug} (anonymous, tenant-resolved by host/tenant key).
  • Cart — anonymous carts keyed by AnonymousToken; merge into the party cart on sign-in.
  • Guest checkout — reuses the existing public PaymentIntent path (Spec 006); a guest Party is created for the buyer + shipping address.
  • Admin UI — a minimal catalog/inventory manager may land in Aonik.AdminUi; a full branded storefront is a separate app (out of scope), consuming these APIs.

15. CommerceDbContext & migrations

CommerceDbContext : AonikDbContextBase exposes the Commerce DbSets, maps Ank-prefixed tables, applies its own configs, and declares no migrations. Every Commerce entity is also added to AonikDbContext (the canonical migration stream) and registered in IsGlobalEntity only if system-scoped (none expected — all are tenant-scoped). New tables (AnkProducts, AnkProductVariants, AnkProductPrices, AnkInventoryLevels, AnkInventoryReservations, AnkCarts, AnkCartItems, AnkProductCategories, AnkProductMedia) are created by one EF-CLI migration against AonikDbContext: 

dotnet ef migrations add CommerceCatalogAndCart --project src/Aonik.Infrastructure --startup-project src/Aonik.Api

16. Phased rollout

Phase 1 — Module skeleton + catalog + pricing

A browsable, priced catalog. Ships alone.
  • Aonik.Commerce.csproj (refs SharedKernel + Aonik.Ordering), CommerceModule, CommerceDbContext; register in composition root + FastEndpoints assemblies.
  • Product/ProductVariant/ProductCategory/ProductMedia/ProductPrice + services + admin/public catalog endpoints; one migration against AonikDbContext.

Phase 2 — Inventory

Stock that can be reserved.
  • InventoryLevel/InventoryReservation + reserve/commit/release with concurrency; Quartz expiry sweep.

Phase 3 — Cart & checkout (reuse the spine)

A product purchase, end to end.
  • Cart/CartItem + ICheckoutService: reserve → IOrderService.CreateAsync(ProductPurchase) → IInvoiceWriter → IPaymentInitiator.
  • New SharedKernel.Abstractions.Billing.IInvoiceWriter + Abstractions.Payments.IPaymentInitiator, implemented in Finance.
  • React to PaymentCompletedEvent: commit inventory, close cart, transition order to Complete.

Phase 4 — Commerce agent

The agentic payoff.
  • CommerceAgentRegistration + CommerceToolApprovalManifest + product/cart/inventory tools + any high-tier proposal handlers.

Phase 5 — Discounts, shipping, tax, storefront (later)

Retail polish.
  • Discount/coupon engine; tax calculation interface; shipping carrier port + ShipmentId fulfilment; branded storefront app.

21. Decisions baked in

  • New sibling module Aonik.Commerce, depending downward on SharedKernel + Aonik.Ordering, never on Finance.
  • Reuse the order spine — a purchase is a ProductPurchase order via IOrderService (Spec 041), not a new order concept.
  • Commerce owns product pricing; Finance FX pricing is not reused.
  • Bill/pay through SharedKernel write contracts implemented by Finance; capture stays Finance-governed and high-tier.
  • Inventory decoupled from the order; reserve-before-order, commit-on-capture.
  • Migrations stay with AonikDbContext; Ank tables; no physical-DB-ownership change.

22. Open design decisions

Open Synchronous contract billing vs event-driven billing at checkout (see §12).
Open Reservation model — counter columns (OnHand/Reserved) with a concurrency token (simple, default) vs an append-only ledger of stock movements (fuller audit, heavier). Reversible.
Open Catalog price model — flat per-variant ProductPrice (default) vs price lists / customer-tier pricing (reuse Party.CustomerTierCode) as a later add.
Open Storefront surface — extend apps/Payabo, a new dedicated storefront app, or an Admin-UI-only manager first. Driven by the wellness-food project's launch needs.
