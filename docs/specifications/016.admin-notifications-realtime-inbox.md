## Objective

Implement a durable, realtime, user-scoped notification inbox for the Admin UI that:

1. persists notifications in the platform database as the source of truth
2. exposes a REST API for listing and managing notifications
3. streams new and updated notifications to the browser in realtime using SSE
4. allows server-side producers such as agents, background jobs, and future Azure alert workflows to notify users without requiring an active chat session
5. remains architecturally neutral so the same core notification model can later be reused by Payabo without redesign

## Problem Statement

The codebase contains the beginnings of a notifications area, but it does not yet provide a real in-app message center.

Current issues:
- `src/Aonik.AdminUi/src/components/layout/NotificationsPanel.tsx` is entirely mock-driven and does not call the API.
- `src/Aonik.AdminUi/src/components/layout/Header.tsx` opens a notifications panel, but it does not show unread state or live updates.
- `src/Aonik.Platform/Entities/Notifications/Notification.cs` exists, but its current field set looks like an outbound delivery record rather than an in-app inbox item.
- There are active template-management features for notification templates and bindings, but there is no notification inbox API for end users or admins.
- There is no realtime browser delivery path for notifications outside the AG-UI chat stream.
- Future workflows such as agent completions, scheduled-job alerts, or Azure infrastructure alerts have no canonical way to notify a signed-in admin user in realtime.
- Native browser `EventSource` is a poor fit for this Admin UI because the current frontend depends on bearer auth and tenant headers.

## Goals

- Make `Notification` the canonical persisted in-app notification record.
- Support tenant-scoped, user-scoped notifications for Admin UI users.
- Deliver notifications live in the browser without requiring a chat session.
- Reuse the existing `fetch` plus SSE parsing pattern already proven in the AG-UI path.
- Keep REST endpoints as the authoritative query and mutation boundary.
- Support future producers such as agents, scheduled jobs, and Azure alert ingestion.
- Preserve extensibility for Payabo without coupling the domain model to Admin UI-specific concerns.
- Keep the MVP small and practical for the current modular monolith.

## Non-Goals

- Replace the existing notification template subsystem.
- Build a full chat or conversation center in this phase.
- Introduce SignalR or WebSockets as the primary transport in the MVP.
- Let server-side agents push directly to the browser transport layer.
- Create a new microservice or database for notifications.
- Build a multi-product notification UX in phase 1.
- Support arbitrary external recipients or outbound email or SMS delivery in this phase.

## Architectural Principles

- Persisted notification rows are the source of truth.
- REST owns list and state transitions; SSE only projects realtime updates.
- Producers create notifications through a server-side service, never directly to UI clients.
- Notifications are user-targeted and tenant-scoped by default.
- The `Notification` entity should stay product-neutral even if the first consumer is Admin UI only.
- `NotificationTemplate`, `NotificationTemplateBinding`, and `WebhookSubscription` remain separate concerns.
- AI-originated notifications should carry audit references such as `AiRunId` when available.
- The MVP should optimize for the simplest correct design in a single application instance, while preserving a clean path to multi-instance fanout later.

## MVP Simplifications

- Reuse the existing `Notification` entity instead of creating a separate `NotificationInboxItem`.
- Use one channel value, `InApp`, for phase 1.
- Store rendered `Title` and `Body` directly on the notification record.
- Store structured supplemental data in `MetadataJson`.
- Use a simple in-memory realtime publisher for phase 1 fanout.
- Keep producer integration straightforward by calling `INotificationService` directly rather than introducing a new event-driven notification workflow layer immediately.
- Start with a system or test producer before integrating Azure alerts.

## Target Architecture

The target design is a four-part notification architecture.

### 1. Canonical storage model
`Notification`

This is the persisted, queryable, tenant-scoped, user-targeted inbox record.

### 2. Application service model
`INotificationService`

This owns creation, query, and state transitions such as read and dismiss.

### 3. Realtime projection model
`GET /admin/notifications/stream`

This is an SSE endpoint that projects newly created or updated notifications to the currently signed-in user.

### 4. Producer integration model
Server-side producers such as:
- agents
- system workflows
- scheduled jobs
- future Azure alert ingestion

These create notifications through `INotificationService`, which persists the record and publishes a realtime update.

## Canonical Notification Specification

### Recommended entity

```csharp
public class Notification : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid UserId { get; set; }
    public string Channel { get; set; } = "InApp";
    public string Type { get; set; } = string.Empty;
    public string Source { get; set; } = string.Empty;
    public string Title { get; set; } = string.Empty;
    public string Body { get; set; } = string.Empty;
    public string Severity { get; set; } = "Info";
    public string Status { get; set; } = "Unread";
    public string? ActionUrl { get; set; }
    public string? CorrelationId { get; set; }
    public Guid? AiRunId { get; set; }
    public string MetadataJson { get; set; } = "{}";
    public DateTime? ReadAt { get; set; }
    public DateTime? DismissedAt { get; set; }
}
```

### Field semantics

- `TenantId`: current tenant owner of the notification.
- `UserId`: direct notification target for the current MVP.
- `Channel`: phase 1 value should be `InApp`. Later phases may add `Email`, `Sms`, or `Webhook`.
- `Type`: stable semantic type such as `AgentTaskCompleted`, `AgentAttentionRequired`, `ScheduledJobFailed`, or `InfrastructureAlert`.
- `Source`: producer source such as `System`, `Agent`, `Scheduler`, or `AzureMonitor`.
- `Title`: short plain-text summary for list display.
- `Body`: plain-text detail for the message center panel.
- `Severity`: `Info`, `Success`, `Warning`, or `Error`.
- `Status`: `Unread`, `Read`, or `Dismissed`.
- `ActionUrl`: optional internal route to open when the user wants more context. MVP should prefer internal application routes rather than arbitrary external URLs.
- `CorrelationId`: optional workflow or incident correlation value for tracing.
- `AiRunId`: optional audit link to AI execution. This should remain a plain nullable `Guid` in Platform rather than a direct EF relationship to AI persistence.
- `MetadataJson`: structured supplemental details in JSON form.
- `ReadAt`: timestamp set when the user marks the notification as read.
- `DismissedAt`: timestamp set when the user dismisses the notification.
- `CreatedAt`: inherited from `AuditableEntity` and used for ordering and date grouping.

### Taxonomy

Recommended MVP constants:

- Channel:
  - `InApp`

- Status:
  - `Unread`
  - `Read`
  - `Dismissed`

- Severity:
  - `Info`
  - `Success`

- Source examples:
  - `System`

## Transport Decision

### Primary realtime transport
Use Server-Sent Events for the Admin UI notification stream.

### Why SSE is the right MVP choice
- The notification flow is server-to-browser push.
- The system does not need full duplex browser messaging for this feature.
- The codebase already has a working SSE pattern in the AG-UI endpoint and frontend stream parser.
- SSE keeps the design smaller and easier to reason about than introducing SignalR for a simple notification center.

### Why not native `EventSource`
Do not use browser `EventSource` for this Admin UI.

Reason:
- the current frontend relies on bearer auth and `X-Tenant-Id`
- native `EventSource` cannot attach custom headers
- the codebase already uses `fetch` with `ReadableStream` parsing successfully for AG-UI

### Frontend stream approach
Use:
- `fetch`
- `Accept: text/event-stream`
- `Authorization: Bearer <token>`
- `X-Tenant-Id: <tenant-id>`
- `response.body.getReader()`
- line-buffer parsing similar to `src/Aonik.AdminUi/src/lib/agui-client.ts`

### Why not SignalR in phase 1
SignalR remains a valid future option, but it is not necessary yet.

SignalR should only be reconsidered if the platform later needs:
- broader bidirectional realtime features
- connection groups and richer presence state
- more complex client interaction patterns than notification fanout

## Realtime Stream Specification

### Endpoint
`GET /admin/notifications/stream`

### Hosting model
Map this as a minimal API endpoint, following the same general hosting pattern used for `MapAguiStreaming`, not as a FastEndpoints handler.

### Auth and CORS
- Require `AdminUserPolicy`
- Require the existing global CORS policy
- Resolve current user and tenant from the existing auth pipeline

### Event model

Recommended SSE event payloads:

```json
{ "type": "HELLO", "unreadCount": 3, "serverTimeUtc": "2026-04-01T12:00:00Z" }
{ "type": "NOTIFICATION_CREATED", "notification": { /* NotificationResponse */ } }
{ "type": "NOTIFICATION_UPDATED", "notification": { /* NotificationResponse */ } }
{ "type": "HEARTBEAT", "serverTimeUtc": "2026-04-01T12:00:15Z" }
```

### Stream behavior
- Emit `HELLO` immediately after the connection is established.
- Emit `NOTIFICATION_CREATED` when a new notification is created for the current user and tenant.
- Emit `NOTIFICATION_UPDATED` when a visible state changes, such as `Read` or `Dismissed`.
- Emit periodic `HEARTBEAT` events to keep the connection healthy.
- Treat the stream as additive and best-effort. The client should always be able to recover by calling the REST endpoints again.

### Fanout implementation for phase 1
Use an in-memory realtime publisher keyed by `(TenantId, UserId)`.

Recommended pattern:
- `Channel<T>` or equivalent async queue per connected subscriber
- publish notifications to active subscribers
- remove disconnected subscribers cleanly on cancellation

### Multi-instance follow-on
The phase 1 in-memory publisher is not sufficient for multi-instance API deployment.

Future backplane options:
- Redis pub/sub
- Azure Service Bus
- another internal pub/sub abstraction behind the same publisher interface

The SQL notification row remains the source of truth regardless of the realtime backplane choice.

### Service responsibilities
- Resolve current user and tenant for read and mutation operations.
- Enforce ownership on all current-user inbox actions.
- Persist notifications.
- Publish realtime events after successful persistence.
- Return DTOs rather than EF entities.
- Avoid coupling inbox creation to the template rendering service in the MVP.

### Producer rules
All server-side producers should call `INotificationService` rather than touching the DbSet directly.

## API Specification

### Admin notification routes

#### `GET /admin/notifications`
Purpose:
- list recent notifications for the current admin user

Query parameters:
- `status`
- `take`
- `before`

Behavior:
- default to recent first
- default to excluding dismissed items unless requested explicitly

#### `GET /admin/notifications/summary`
Purpose:
- return unread count for header badge and shell state

Response:
- `NotificationSummaryResponse`

#### `POST /admin/notifications/{id}/read`
Purpose:
- mark a single notification as read

Behavior:
- idempotent if already read
- return updated notification or `404` if not owned by the current user

#### `POST /admin/notifications/{id}/dismiss`
Purpose:
- dismiss a single notification from the active list

Behavior:
- idempotent if already dismissed
- return updated notification or `404` if not owned by the current user

#### `POST /admin/notifications/read-all`
Purpose:
- mark all unread notifications as read for the current user and tenant

Response:
- count of updated rows

### Endpoint placement
These routes belong under Platform admin endpoints because:
- the current consumer is `Aonik.AdminUi`
- they are tenant-scoped platform features
- they align with other admin management surfaces already in the Platform module

### FastEndpoints guidance
The non-stream routes should use FastEndpoints and the repo's existing response patterns:
- `Send.OkAsync()`
- `Send.NotFoundAsync()`

## Frontend Specification

### Admin UI shell behavior
The notification stream should live at the shell or header level rather than only inside the panel component.

Reason:
- unread badge and live state should update even when the panel is closed
- the panel should consume existing notification state instead of owning the only source of truth

### Notifications panel behavior
`src/Aonik.AdminUi/src/components/layout/NotificationsPanel.tsx` should:
- fetch recent notifications on mount or when the shared notification state initializes
- render real `Title`, `Body`, `Source`, and relative time values
- compute `Today` and `Yesterday` groups from persisted `CreatedAt`
- support `Dismiss`
- support `Mark Read`
- support `Mark All Read`
- optionally navigate using `ActionUrl`

### Header behavior
`src/Aonik.AdminUi/src/components/layout/Header.tsx` should:
- show unread badge on the bell
- update unread badge from both initial summary fetch and stream events
- open the panel without causing a second isolated notification state tree

### Frontend transport
Create a dedicated notification stream helper or hook rather than reusing AG-UI event types directly.

Recommended approach:
- reuse the stream parsing pattern
- do not couple notification logic to AG-UI protocol event names or AG-UI client abstractions

### UI rendering guidance
- Treat `Title` and `Body` as plain text in the MVP.
- Do not render HTML from `Body`.
- Keep severity styling minimal and consistent with the existing design language.

## Producer Specification

### Core producer rule
A producer should create a notification by calling the notification service, not by opening a stream to the browser.

This applies to:
- agents
- scheduled jobs
- internal admin tooling
- future infrastructure alert workflows

### First producer recommendation
The first integrated producer should be a simple internal system or test notification path.

Reason:
- validate the entity, service, API, stream, and UI end-to-end with minimal risk
- avoid tying the first iteration to Azure integration complexity

### Agent integration
Future agent workflows should create notifications after meaningful completion or when explicit user attention is required.

Recommended examples:
- `AgentTaskCompleted`
- `AgentAttentionRequired`

Agent integration rules:
- attach `AiRunId` when available
- include internal route in `ActionUrl` when there is a concrete drill-down destination
- do not allow agents to write directly to browser transport infrastructure

### Azure alert follow-on
Future infrastructure alert ingestion should flow as:

`Azure Alert -> Authenticated Webhook Endpoint -> Internal Mapping/Workflow -> NotificationService -> Notification row + realtime publish`

Recommended follow-on route:
- `POST /integrations/azure/alerts`

Follow-on rules:
- validate the incoming secret or signature
- map external alert data to stable internal `Type` and `Source`
- keep the notification creation flow inside the application boundary

## Security And Authorization

- All admin inbox read and mutation routes require `AdminUserPolicy`.
- The current user and tenant must come from the existing auth pipeline and providers.
- Clients must never supply their own `UserId` for current-user inbox actions.
- `ActionUrl` should prefer internal application routes in the MVP.
- `MetadataJson` should not be used as an unchecked free-form rendering surface.
- Notification creation APIs intended for internal producers should remain server-side service calls initially rather than broad public endpoints.

## Audit And Observability

- Persist `AiRunId` where the producer is AI-driven.
- Persist `CorrelationId` when the notification comes from a longer-running workflow, incident, or external alert.
- Log stream connect and disconnect events at an appropriate level.
- Log publish failures and dropped subscribers defensively.
- Keep the stream implementation lightweight and exception-safe, similar to the AG-UI streaming path.

## Payabo Extension Path

This design should remain easy to extend to Payabo later.

Reuse strategy:
- keep the same `Notification` entity
- keep the same `INotificationService`
- add Payabo-specific endpoints and policies later
- allow Payabo-specific `Type` and `Source` values without changing the storage model
- do not hardcode Admin UI concepts into the domain entity

## Risks And Follow-On Considerations

- Phase 1 in-memory fanout will not deliver cross-instance realtime updates if the API scales horizontally.
- The stream is not a substitute for durable storage. Clients must be able to recover from disconnects by refetching.
- Overloading the inbox with large payloads in `MetadataJson` should be avoided.
- Outbound template-driven notifications remain a separate concern and should not be collapsed into the inbox model in this phase.
- If the platform later needs richer bidirectional realtime semantics, SignalR can be added behind the same higher-level notification domain model without changing the persisted `Notification` concept.
