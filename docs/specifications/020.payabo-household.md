# Summary

Enable Payabo users to create a household, invite members through a pending invitation workflow, accept or decline invitations, manage household membership, and share personal accounts with the household.

This spec is intentionally phased.

- Phase 1: household membership workflow, role-based authorization, account sharing, notifications, and Financial Life Graph updates
- Phase 2: household budgets, per-member permission overrides, and broader mobile UX expansion

This keeps v1 small, grounded in the current codebase, and scalable without introducing unnecessary tables or policy layers.

# Context

The current codebase already includes a first pass of household support:

- `Household` entity with `TenantId`, `Name`, and `Members`
- `HouseholdMember` entity with `TenantId`, `HouseholdId`, `UserId`, `Role`, and `PermissionsJson`
- `HouseholdService.CreateHouseholdAsync()` creates a household and adds the creator as `Owner`
- `HouseholdService.InviteMemberAsync()` currently adds the member immediately with no pending state
- `PersonalProfile.HouseholdId` and `PersonalAccount.HouseholdId` already exist
- `Budget` is currently user-scoped only and does not include `HouseholdId`
- Financial Life Graph already projects `Household` and `HouseholdMember` nodes
- Flutter has no household feature yet

Important current constraints from the actual code:

- `HouseholdMemberConfiguration` enforces a unique index on `(TenantId, HouseholdId, UserId)`
- `HouseholdMemberConfiguration` has a non-unique index on `(TenantId, UserId)`
- One-household-per-user is currently enforced in service logic, not by a unique DB constraint on accepted membership
- Household feature flags exist as constants in `FeatureFlags.cs`, but are not currently wired into backend endpoint gating, settings definitions, or mobile route gating

# Goals

- Add a proper invitation lifecycle: invite, accept, decline, expire
- Support leaving a household, removing a member, and transferring ownership
- Replace free-form role usage with validated role constants
- Keep authorization simple in v1: role-based, not per-entity ACLs
- Reuse existing `PersonalAccount.HouseholdId` for account sharing
- Publish household integration events and create notifications using existing infrastructure
- Extend the Financial Life Graph to reflect accepted household membership and shared household accounts
- Add a minimal mobile experience for household creation, invitations, membership viewing, and shared accounts

# Non-Goals

- Per-entity permission tables
- Inter-household sharing
- Joint ownership of accounts
- Household analytics and forecasting
- Simi AI integration
- API versioning changes
- Invite-by-email lookup flow in v1
- Server-side 404 feature-flag gating in v1 unless supporting platform settings plumbing is added first
- Household budgets in v1
- Per-member permission override UI in v1

# Constraints And Guardrails

- Must not change existing personal finance ownership semantics: `PersonalAccount` remains owned by a single `UserId`
- Must not backfill or rewrite existing personal finance data except the household membership migration explicitly described below
- Must follow FastEndpoints patterns already used in Personal Finance endpoints
- Must follow `Ank` table naming via canonical EF migration generation
- Must use EF Core CLI-generated migrations only
- Must use `IEventBus` and `IEventHandler<T>` from `src/Aonik.SharedKernel/Events/`
- Must use `INotificationService.CreateForUserAsync` or `CreateForUsersAsync` for in-app plus push notification delivery
- Must keep queries tenant-scoped
- Must preserve existing `HouseholdMember` rows as accepted membership in migration
- Must preserve `PersonalProfile.HouseholdId` consistency on accept, leave, and removal
- Ask for approval before adding or changing a database uniqueness rule for accepted membership, because that is a behavioral constraint change
- Ask for approval before introducing backend feature-flag enforcement if it requires new setting names or client-visible manifest/API work

# Part 1: Phase 1 Backend Design

## 1.1 HouseholdMember Changes

Add the following columns to `HouseholdMember`:

| Column | Type | Default | Notes |
|--------|------|---------|-------|
| `InvitationStatus` | `string` | `"Accepted"` | `Pending`, `Accepted`, `Declined`, `Removed` |
| `InvitedByUserId` | `Guid?` | `null` | User who sent the invitation |
| `InvitedAt` | `DateTime?` | `null` | When the invitation was sent |
| `RespondedAt` | `DateTime?` | `null` | When accepted or declined |
| `ExpiresAt` | `DateTime?` | `null` | Default `InvitedAt + 7 days` for pending invites |

Migration behavior:

- Existing rows become `InvitationStatus = Accepted`
- Existing rows set `InvitedAt = CreatedAt`
- Existing owner rows may leave `InvitedByUserId = null`

## 1.2 Role Constants

Add validated role constants and standardize on:

- `Owner`
- `Manager`
- `Viewer`

Use a string column in the database, but validate in service code.

Migration behavior:

- Existing `Role = "Member"` rows are migrated to `Manager`

Phase 1 authorization remains role-based.

Do not implement editable per-member permission overrides in Phase 1.

## 1.3 Invitation Status Constants

Add `HouseholdInvitationStatus` constants in Finance contracts.

## 1.4 No New Invitation Table

Invitation lifecycle remains on `HouseholdMember` for v1.

This is the smallest change that matches the current design and avoids premature normalization.

## 2.2 DTOs

Add DTOs for:

- `HouseholdDetailResponse`
- `HouseholdMemberDetailResponse`
- `TransferOwnershipRequest`
- `ShareAccountWithHouseholdRequest`

For Phase 1, keep DTOs close to existing `PersonalFinanceModels.cs` patterns.

## 2.3 InviteMemberAsync

New behavior:

1. Validate household exists in tenant
2. Validate inviter is an accepted member with role `Owner` or `Manager`
3. Validate invitee exists and has a `PersonalProfile`
4. Check for an existing `HouseholdMember` row for the same `(TenantId, HouseholdId, UserId)`:
   - If a row exists with `InvitationStatus = Declined` or `Removed`: reset it to `Pending`, update `Role`, `InvitedByUserId`, `InvitedAt`, `ExpiresAt`, clear `RespondedAt`
   - If a row exists with `InvitationStatus = Pending`: reject with "invitation already pending"
   - If a row exists with `InvitationStatus = Accepted`: reject with "user is already a member"
   - If no row exists: create a new `HouseholdMember` with `InvitationStatus = Pending`
5. Do not set `PersonalProfile.HouseholdId`
6. Publish `HouseholdMemberInvitedEvent`
7. Create notification for invitee via `INotificationService`

Important behavior:

- Pending invites may exist for multiple households
- Accepted membership remains exclusive by service logic in Phase 1
- This spec does not assume a DB uniqueness constraint for accepted membership because one does not exist today
- Re-invitation after decline or removal reuses the existing row to satisfy the unique index on `(TenantId, HouseholdId, UserId)`

## 2.4 AcceptInvitationAsync

1. Find pending invitation for current user and household
2. Reject expired invitations
3. Start a database transaction for the accept flow when the provider supports transactions
4. Re-check that the user has no other accepted membership
5. Set `InvitationStatus = Accepted`
6. Set `RespondedAt = DateTime.UtcNow`
7. Set `PersonalProfile.HouseholdId = householdId`
8. Decline other pending invitations for the same user
9. Save changes and commit the transaction
10. Publish `HouseholdInvitationAcceptedEvent`
11. Invalidate Financial Life Graph cache

Concurrency note:

- Phase 1 must implement the accept flow as one transactional unit where supported by the database provider
- The service must perform a final accepted-membership recheck inside that transaction before commit
- If another acceptance succeeds first, this operation must fail with a conflict-style error
- Do not claim the database already enforces this

## 2.5 DeclineInvitationAsync

1. Find pending invitation for current user and household
2. Set `InvitationStatus = Declined`
3. Set `RespondedAt = DateTime.UtcNow`
4. Publish `HouseholdInvitationDeclinedEvent`

## 2.6 RemoveMemberAsync

1. Validate actor is accepted `Owner` or `Manager`
2. Cannot remove self
3. Cannot remove the sole accepted owner
4. Set target membership to `Removed`
5. Clear `PersonalProfile.HouseholdId`
6. Unshare all `PersonalAccount` rows owned by the removed user by setting `HouseholdId = null`
7. Publish `HouseholdMemberRemovedEvent`
8. Invalidate graph cache

## 2.7 LeaveHouseholdAsync

1. Validate current user is an accepted member
2. If sole accepted owner, reject with transfer-ownership requirement
3. Set membership to `Removed`
4. Clear `PersonalProfile.HouseholdId`
5. Unshare all `PersonalAccount` rows owned by the leaving user by setting `HouseholdId = null`
6. Publish `HouseholdMemberLeftEvent`
7. Invalidate graph cache

Phase 1 uses status transitions instead of introducing new delete semantics.

## 2.8 Household Lifecycle When Membership Drops To One Accepted Owner

Phase 1 keeps a strict rule: a sole accepted owner cannot leave.

That means Phase 1 does not allow intentional orphaned households with zero accepted members.

Implications:

- `LeaveHouseholdAsync` must continue to reject when the current user is the sole accepted owner
- household rows are not automatically deleted in Phase 1
- Phase 1 does not include household-wide bulk unsharing of every shared account as a terminal cleanup step
- Phase 1 does unshare accounts owned by the member who leaves or is removed, as part of those lifecycle operations

## 2.9 TransferOwnershipAsync

Phase 1 decision: single effective owner.

Behavior:

1. Current user must be accepted `Owner`
2. Target user must be an accepted member of the same household
3. Promote target to `Owner`
4. Downgrade current owner to `Manager`
5. Publish `HouseholdOwnershipTransferredEvent`

## 2.10 GetMyHouseholdAsync

1. Find current user's accepted membership
2. Load household and accepted members only
3. Resolve display names using the same profile and party lookup approach already used in `FinancialLifeGraphLoader`
4. Return household details

## 2.11 GetPendingInvitationsAsync

1. Load pending invitations for current user where `ExpiresAt > DateTime.UtcNow`
2. Resolve household and inviter display names
3. Return pending invitations sorted by `InvitedAt`

# Part 3: Phase 1 Account Sharing

Extend `IPersonalAccountService` with:

```csharp
Task<PersonalAccountResponse> ShareAccountWithHouseholdAsync(Guid accountId, ShareAccountWithHouseholdRequest request, CancellationToken ct = default);
Task<PersonalAccountResponse> UnshareAccountAsync(Guid accountId, CancellationToken ct = default);
Task<IReadOnlyList<PersonalAccountResponse>> ListHouseholdAccountsAsync(CancellationToken ct = default);
```

Rules:

- Accounts remain owned by the original `UserId`
- Sharing only sets `PersonalAccount.HouseholdId`
- Sharing does not create joint ownership

`ShareAccountWithHouseholdAsync`:

1. Current user must own the account
2. Current user must be an accepted member of the household
3. Current user role must be `Owner` or `Manager`
4. Set `PersonalAccount.HouseholdId`
5. Publish `HouseholdAccountSharedEvent`
6. Invalidate graph cache

`UnshareAccountAsync`:

1. Current user must own the account
2. Set `PersonalAccount.HouseholdId = null`
3. Publish `HouseholdAccountUnsharedEvent`
4. Invalidate graph cache

`ListHouseholdAccountsAsync`:

1. Current user must be an accepted member of a household
2. Return all accounts in tenant where `HouseholdId == currentHouseholdId`

Household account sharing is always explicit.

Phase 1 includes member-scoped automatic unsharing during leave and remove operations, but does not include household-wide terminal cleanup behavior.

# Part 6: Phase 1 Financial Life Graph

Add one new predicate:

- `HOUSEHOLD_HAS_ACCOUNT`

Loader and graph behavior changes:

- include accepted members only in household graph projection
- exclude `Pending`, `Declined`, and `Removed` members from graph nodes and edges
- extend the graph loader snapshot to include personal accounts shared to the household, including accounts owned by other accepted household members
- emit account nodes for those shared accounts
- add household-to-account edges for `PersonalAccounts` where `HouseholdId == household.Id`

Implementation note:

- this is not only a new edge type; it also requires the loader and snapshot model to include household-shared accounts beyond the current user's owned accounts

Phase 1 does not add household budgets to the graph.

# Part 9: Security And Data Isolation

## 9.1 Authorization Rules

| Operation | Allowed Roles |
|-----------|--------------|
| Create household | Authenticated user with no accepted household membership |
| Invite member | Accepted `Owner` or `Manager` |
| Accept or decline invite | Invited user only |
| Remove member | Accepted `Owner` or `Manager` |
| Leave household | Any accepted member except sole owner |
| Transfer ownership | Accepted `Owner` only |
| Share or unshare account | Account owner who is accepted `Owner` or `Manager` |
| View household accounts | Any accepted member |

## 9.2 Data Isolation

- All queries include tenant scoping
- Only accepted members can access household views
- Unshared personal accounts remain private to the owner
- Shared accounts become visible to accepted household members, but ownership remains unchanged
