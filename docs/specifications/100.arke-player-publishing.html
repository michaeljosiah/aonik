Arke Player publishing through AONIK

Studio creates a frozen public edition. AONIK receives it privately, validates it, obtains a human editorial decision and publishes only the approved revision. Player discovers and verifies that edition using its existing catalogue and offline installation model.

This document specifies the complete target. Section 19 records what is implemented and what remains planned. A checked-in design, interface or issue is not evidence of a deployed service.

1. Outcome and scope

PUB-001. An uploaded edition must never become available through the public Player catalogue until a different authorised human has approved its exact package, public metadata, artwork, audience and distribution permission. The system, rather than the approving browser, performs publication.

PUB-002. Authoring, generation, rendering, narration assembly and export remain in Studio. No editable world, private canon, development history, credentials or unrelated assets are included in a submission. Cloud access is optional for authoring and local export.

PUB-003. Initial operations cover adult creators submitting curated public Player editions to the Arke Worlds publisher. Private family libraries, child submission/public-sharing flows, paid distribution, subscriptions, marketplace sales, social features and hosted generation are outside this slice. Existing child safety/guardian consent rules still apply wherever relevant; an edition is not made public merely because family generation or private sharing was permitted.

The full service replaces the manual release/catalogue authority. The December pilot in AONIK #395 remains a separate readiness decision with its existing manual fallback. This specification does not alter its deadline or claim deployment readiness.

2. Verified baseline

Investigated local Studio checkout 3a56d8e9 and cached main c6cc6aea; Player checkout 08d665a3 and cached main 27df1225; AONIK's merged baseline represented by feature commit cd9ee837. These are code baselines, not a fresh network inventory of deployed builds.

  • Studio's actual Player export is a ZIP with world.json, format arke-world-package, currently schema 7. The separate publication.json video publication path is a different contract.
  • Export creates and checks local immutable output plus a release receipt. The documented public process uploads a ZIP to GitHub and edits/publishes the Player catalogue manually.
  • Player supports world schemas 1–7 and a version 2 catalogue; readers verify package length/hash, archive structure and individual extracted assets. Discovery merges bundled and hosted catalogues by increasing serial and supports offline fallback.
  • The checkout catalogue serial is 45 and cached main is 47, both containing five worlds, including one interactive story and one comic production. Neither establishes the live deployed serial.
  • Studio and Player account services have NoArkeCloud defaults. A real Studio creator account adapter is new integration work.
  • AONIK already has scoped identity/party services, Workspaces upload patterns, outbox processing, audit and Arke Worlds navigation/designs. Creator submissions and Player catalogue pages are connection states, not implemented backend workflows.

4. Identity and permissions

PUB-006. A channel belongs to a publisher tenant. A creator is a signed-in user with a server-resolved party and submission authority in that scope. Creator tenant, user and party IDs are never accepted as ownership assertions in a request body. Tenant query filters are defence in depth; all creator queries also constrain creator party. Cross-tenant delegation requires explicit membership/authority rather than bypassing filters.

ActorAllowed actionsServer rule

Creator reads use existing consumer identity boundaries. Creator writes allow a PersonalUser acting on their own party, or an explicit Publishing.Submit permission; the generic staff ReadOnly role alone never grants submission writes. Check authority in services as well as endpoint policy. Missing/inaccessible submission IDs return the same 404. Unauthenticated requests return 401; a signed-in user without a party or submit authority receives 403.

PUB-007. The generic agent proposal approval policy is not the editorial policy: it currently allows authenticated same-tenant decisions and does not implement the needed separation of duties. Publishing decisions must not use it as a shortcut. Optional agent-originated publishing requests use server-classified tools and durable approval; agents cannot mutate catalogue or public storage directly.

Channels are initially operator configuration, with exact publisher tenant ID, enabled flag, maximum package size and accepted permission statement version. An absent, disabled or foreign channel fails closed. Channel enablement does not itself certify the whole publication pipeline as ready. Dynamic channel management is a later persisted configuration surface.

PUB-008. Keep three fingerprints distinct: (1) SHA-256 of the complete ZIP bytes, (2) Player's edition fingerprint derived from edition label and sorted asset path/hash pairs, and (3) Studio's source-change fingerprint. The review digest additionally covers the entire approved public presentation and permission snapshot. None substitutes for another.

PUB-009. Canonical request digest v1 uses a fixed-order JSON object with UTF-8 serialization, an explicit version and normalized field values. Trim outer whitespace, normalize declared SHA-256 to lowercase and preserve meaningful case/content in metadata. Bind every accepted request field, including all permission fields. Replaying an identical client request returns its original receipt; changing any accepted field under the same key yields 409. Recheck current access before replay.

Persist the submission and first revision in one SaveChanges unit, protected by the relational unique index. A concurrent insert loser reloads the winner and compares the digest; a failure without an authoritative winner remains an error, not a successful replay. Later state changes use SQL rowversion/expected-version controls. Relational tests are mandatory for uniqueness and atomicity.

7. Private upload, limits and retention

PUB-010. Intake accepts creator-uploaded frozen package bytes and explicitly selected artwork/evidence. It does not fetch arbitrary creator URLs, execute archive contents or import a whole editable world. Keep quarantine separate from publicly readable asset namespaces and credentials.

Implement owner-scoped single-shot and resumable upload sessions. Reuse Workspaces' streaming hash/length and multipart patterns through a common adapter where appropriate; do not grant access to an unrelated workspace or publicise a workspace blob URL. Initial proposed defaults are a 32 MiB single-shot threshold, 8 MiB parts and 48-hour open session lifetime, matching existing patterns. The channel-specific maximum package size and tenant reservations are mandatory operator settings; no theoretical 64 GiB format ceiling becomes the public service limit by accident.

Validate declared and received Content-Length, total count and per-part sizes; stop on excess; compute full hash and length during finalisation; bind session to tenant/party/submission/revision. Same part replay is accepted only for identical bytes. Changed part or final digest gives 409/422; old upload sessions cannot overwrite a frozen revision. On completion, persist private storage ownership and the validation command before acknowledging submission.

PUB-011. All retained bytes need explicit durable ownership. Workspaces' zero-reference sweeper is not publication retention. Incomplete staging and session data have bounded cleanup; review/rejected/withdrawn content follows a configured retention policy; published editions remain retained while any supported catalogue can refer to them. Deletion requires proving no active review, publication operation or supported catalogue reference needs the bytes.

Operators must configure quotas, upload/session limits, review retention and legal/incident holds before enabling production intake. Record policy versions and expiry dates rather than embedding an invented legal retention period. Do not log uploaded content, tokens or raw private evidence.

8. Validation and private preview

PUB-012. A passing server validation independently verifies the complete submitted archive, not the creator's claimed SHA. Use a pinned, isolated pure-Dart arke_world worker with structured JSON results and no outbound network/content execution. An alternative implementation must pass the same cross-reader fixtures before use.

Important: readWorldPackage() checks structure/documents; media checks happen through extractAsset()/checkAsset(). Walk every inventory asset, verify its existence, length and digest, and calculate outer ZIP SHA/length. pin_world by itself is not a full admission check. Streaming scratch verification may discard extracted bytes once each check completes; bound scratch storage and clean it after crashes.

  • Reject absolute/traversal/backslash paths, symbolic links, case-colliding duplicates, unknown files and disallowed compression. Enforce file counts, archive size, document size, time and memory limits before resource-intensive processing.
  • Parse the exact world schema, required capabilities and each listening/guide/music/story/comic document with the matching reader contracts. Reject unresolved references, invalid assets or unsupported required capabilities.
  • Check the package world and production identities against the reserved channel namespace. Whole editions, guide-only packages, sequential parts and standalone productions have distinct validation and catalogue rules.
  • Apply separate editorial/safety/rights checks. A valid ZIP does not establish appropriate age rating, voice/image rights or distribution permission. Unavailable mandatory checks hold the revision.
  • Verify any derived review preview corresponds to the immutable input digest. Do not re-render or alter the distributable as an invisible side effect of review.

Private preview URLs require reviewer scope or narrowly scoped short-lived preview access. Public catalogue URLs must not use these expiring tokens. Constrain documents/media in the preview viewer, avoid script execution and external links, and record preview/validation availability clearly. A public feed entry is never used as the review mechanism.

Optional AI review is advisory, resolves models through AiRoutePolicy and records AiRun. It can propose findings and recommendations; it cannot supply the mandatory human decision.

9. Human editorial approval

PUB-013. Approve requires current publisher scope, Publishing.Review, no match to originating creator user or party, a passing validation report for the current immutable revision, complete rights evidence, current policy compatibility, the expected rowversion and exact review digest. Deny on uncertainty. Apply these checks in the service even if invoked outside HTTP.

The review digest includes verified archive SHA/length; world/production/edition/fingerprint; all catalogue text and artwork hashes; language/audience/rating; intended channel and release kind; base edition fingerprint and part number where applicable; attribution and distribution permission/evidence versions; validator/policy versions. No privileged actor can change these fields and retain the previous decision.

Decision requests carry revision ID, review digest, expected version, operation UUID, decision kind and reason. Repeated identical decisions return the stored outcome; reused operation identity with different arguments conflicts. Persist the append-only decision, status change and publication outbox command in one transaction where approval also requests publication. A second-person publication release can be configured without weakening the original reviewer separation.

Approved status is distinct from published. The publication service rechecks the active exact decision and any current legal/safety hold before a catalogue commit. Policy changes requiring fresh review invalidate publication authority; they do not rewrite historical decisions.

10. Publication transaction, concurrency and recovery

PUB-014. Publication is an outbox/Worker operation with stable identity, lease and durable phases. Never copy large assets or run a complete publication from the approval request thread.

  1. Load and verify the requested approved revision/decision/digest and namespace ownership under the restored publisher tenant. Refuse superseded, withdrawn or held authority.
  2. Copy/promote exact reviewed bytes and artwork to immutable public paths containing version or content hash. Never overwrite an existing edition, regenerate its package or change its manifest ID during delivery. Check returned public bytes/hash/length before listing.
  3. Read current channel head and validate replacement/part relationships. Under a rowversion/serial compare-and-swap, allocate a strictly increasing serial and commit the complete snapshot, entry changes, published provenance and durable follow-up work. A competing publisher reloads/revalidates rather than overwriting the winner.
  4. Serve only committed complete snapshots. Deliver creator notifications and the optional legacy GitHub catalogue mirror via retryable work. Record canonical publication and mirror delivery states separately.

PUB-015. Recovery is reconciliation, not blind rerun: an existing operation result is replayed; copied but unlisted objects are retained/reused; response loss after commit returns the committed publication. A stale lease cannot commit over a newer operation/head. Outbox redelivery must converge to one visible result. Dead-lettered or uncertain operations need operator evidence before further action.

The SQL transaction cannot atomically include external object storage and GitHub. Sequence effects so failure can leave unlisted immutable objects but never a committed catalogue pointing to partial/missing assets. A catalogue read endpoint can serve the SQL committed head/snapshot; a static snapshot/pointer adapter needs equivalent conditional-write guarantees. IFileStore alone does not promise these semantics.

The legacy mirror is serialized per channel and reconciles to the latest canonical head before each upload. An old retry must not replace a higher serial. If the mirror lags, current AONIK clients may be published while legacy delivery remains visibly pending. Neither route may serve unapproved revisions.

Foundation responses explicitly mark packageVerified: false. A declaration digest is named requestDigest, not reviewDigest. The rights flag records a creator assertion bound to a server-configured version; it is not a legal review result. Later evidence requirements remain mandatory.

Receipt creation accepts at most 128 KiB of metadata JSON. Unknown members, including attempted owner/status/verification assignments, are rejected. Required text is trimmed and must be non-empty without control characters: channel/world IDs at most 64 lowercase hyphenated characters; title and creator display name 200; language 35; edition and rights statement version 120; filename 255 and a ZIP basename without slash, backslash or colon. Summary may be empty and is limited to 2000 characters without control characters. ClientRequestId is a non-empty UUID; declared length is positive and within the configured channel cap; SHA-256 is 64 hexadecimal characters normalized to lowercase. DistributionPermissionGranted must be true and its version must match current channel configuration.

400 malformed JSON or unmapped members; 401 unauthenticated; 403 missing party/submit/review authority; 404 inaccessible submission/channel; 409 idempotency or concurrency conflict; 413 excessive upload/body; 422 invalid declarations/package/evidence; 429 throttled; 503 temporarily unavailable validation/delivery. Rejected operations must not advance state or release retained bytes needed for reconciliation.

13. Studio integration

PUB-017. Implement the existing AccountService seam with browser-based creator authentication appropriate to the configured AONIK identity provider. Use a native public-client flow with PKCE and registered callback, protected host token storage and token refresh. Do not put secrets in the renderer or treat admin-policy /v1/me as an already suitable creator profile.

The coordinator owns PublishingSubmissionService, authenticated transport, retry receipts and file handles. Contracts/client components expose submit, upload progress, cancellation, receipt/status and change requests. Recheck current sign-in/party before resuming; offline/expired sign-in pauses submission without blocking local work.

  1. Export through the existing owner exporter, including its latest credits and external-edit safeguards.
  2. Show the selected frozen package, title/credits/art, audience and scoped distribution permission.
  3. Create/replay the durable AONIK receipt with a stable client UUID, then upload only selected output.
  4. Keep local receipt with package SHA/size, AONIK IDs and last known status; resume identical interrupted uploads.
  5. Poll or refresh safe status and show reasons/links. Any changed output requires another revision.

Local export sidecars represent exports, not AONIK's approved public head. Before submitting a later part, compare base edition and part number against the channel's authorised lineage. Declined or unpublished local parts cannot silently advance the public sequence.

14. Player integration

PUB-018. Move the catalogue URL into one shared build/channel configuration used by both foreground discovery and background part notices. Preserve shipped/cache merging, forced refresh, checksum validation, update detection, local library and offline play. An ordinary reader does not need a creator login.

Configure AONIK's compatible endpoint in new builds and seed an audited bundled catalogue. Current hosted fetching accepts HTTP 200 only; ETag/304 optimisation is a separate change with explicit cache tests. Do not serve 304 to an unmodified request path and assume the reader supports it.

PUB-019. Fix pin_world.dart to emit standalone comics under comic with the required version, like its existing story branch. Add regression tests for whole editions, guide, parts, ordinary standalone/music, story and comic. This helper currently falls through to generic package for comics in both examined Player refs.

Qualification must include current and supported older readers. Unsupported required capability produces the existing update/refusal experience rather than corrupt installation or hiding unrelated catalogue entries. Broader discovery pagination, signed catalogues, private libraries and device revocation require new protocol design and are not hidden inside this migration.

16. Audit, notifications and operations

PUB-021. Record create/replay/conflict, upload session disposition, verification findings/version, preview access, every editorial decision, publication phase/result, catalogue head changes, mirror lag and withdrawal. Correlate tenant/channel, submission, revision, actor, digest and operation; exclude raw content, credentials and unnecessary PII. Rights evidence is access-controlled and retained by policy.

Notifications for receipt, changes, approval, publication and withdrawal reference stable IDs and safe titles. Sending a notification is not the source of submission state. Deliver through existing notification/outbox mechanisms with replay protection. Email/creator communication production configuration and consent are separate operating prerequisites.

Monitor queue age, validation duration/failure category, review age, retry/dead-letter count, publication time, current canonical/mirror serial, asset fetch integrity and storage/retention pressure. Alert on actual failures/stalled work. Configure a reviewer/backup, capacity and support route; the three-working-day pilot target depends on staffed capacity, not software existence.

Before deployment, document storage ACLs/public host, identity client and callback registration, limits, Worker/validator version and sandbox, database/migration readiness, audit/retention settings, creator support, incident hold, catalogue rollback-by-new-serial and manual fallback. This specification authorises no infrastructure purchase or production publication.

17. Migration and rollout

  1. Inspect live hosted catalogue, supported bundled catalogues and release assets. Identify the authoritative highest serial; do not assume cached 47 is current. Import complete entries and provenance with an audited operator baseline, preserving IDs, hashes, URLs, stories/comics and artwork.
  2. Reserve legacy namespaces and record ownership/distribution evidence. Import is not retroactive creator consent; unresolved permission or integrity holds stay explicit.
  3. Build and qualify private intake/review first. Keep publication disabled until validation, reviewer authority, Worker and storage/CDN checks pass.
  4. Build canonical snapshot publication and retry/reconciliation. Rehearse on a separate test channel without changing public production catalogues.
  5. Connect Studio and qualify two independent consenting test creator identities and a separate reviewer. Exercise a nontechnical reviewer journey, not only API tests.
  6. Ship Player with configured AONIK feed and compatible bundled baseline. If older apps must receive publications, deliberately enable a legacy GitHub catalogue mirror using authorised credentials and immutable assets. Never mark a story/catalogue release as the Studio application updater's Latest release.
  7. Observe successful refresh/install across supported devices and offline/update paths. Preserve the private manual intake/review and verified catalogue handoff until the service has deployed acceptance evidence.

PUB-022. A rollback is a newly approved, higher-serial projection referencing retained immutable assets. Disabling intake must not remove public discovery or private audit. A module/channel kill switch must distinguish new submissions, decisions and delivery; stopping a worker must leave operations recoverable.

First AONIK slice: module registration, canonical schema, creator-scoped immutable declaration/receipt, request-digest idempotency and own receipt/list APIs.
