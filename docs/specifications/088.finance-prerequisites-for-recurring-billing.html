Spec 088 Status: Draft (Rev 1) Size: Medium Priority: P1 Domain: Finance / SharedKernel

Finance prerequisites for recurring billing

Six changes inside Aonik.Finance that any module must have before it can bill recurring revenue correctly: a cross-module journal-writing contract, a payment mandate so a background job can charge a saved instrument, an invoice that remembers its order, idempotency on the invoice and payment-intent writers, and settlement that routes revenue by order type and splits per line. Carved out of Spec 087, which needs all six but is the wrong place to specify them — none is subscription-specific, and Commerce wants most of them already.

1. Summary

Spec 087 set out to add subscriptions on top of the existing order, invoice, payment and ledger rails. Review found that six things it assumed those rails already did, they do not. Each is a change inside Finance, none is subscription-specific, and together they were turning 087 into two specs wearing one name.

They are separated here so each is specified properly, reviewed as Finance work, and reusable by anything else.

The through-line Every one of these is the same shape of gap: a capability that exists for the interactive, single-payment, storefront path and was never needed for a background, recurring, multi-line one. None is a defect in what exists; each is the cost of a second use case.

2. Why this is its own spec

ReasonDetail
None of it is about subscriptions A payment mandate, an invoice that knows its order, and revenue routing by order type are all things a one-off ProductPurchase or a Commerce checkout can want. Specifying them inside a subscriptions spec buries generic capability under one consumer's requirements.
Different reviewers These change money-touching paths — settlement postings, invoice writes, payment intents. That is Finance review, and it should not arrive as an appendix to a spec about plans and meters.
Different risk Settlement routing edits a method every existing invoice already flows through. Getting it wrong misposts revenue for products that have nothing to do with subscriptions, so it needs its own acceptance criteria and its own regression bar.
087 stops being a mixed spec What remains there is coherent: catalogue, subscription lifecycle, entitlements, grants, metering. It consumes this spec through contracts and owns none of it.

3. The six gaps, verified

Each verified against the tree rather than inferred:

#GapEvidence
1 No module outside Finance can post to the ledger ILedgerService lives in Aonik.Finance.Contracts. IInvoiceWriter and IPaymentInitiator have SharedKernel mirrors; journal posting has none.
2 Account codes cannot be resolved from a code alone A tenant may hold several Ledger rows (ILedgerService.CreateLedgerAsync), and LedgerAccount.Code is unique per ledger, not tenant-wide.
3 No reusable funding instrument IPaymentInitiator exposes only CreateGuestIntentForOrderAsync — a guest intent on "the permission-free public payment path", requiring Provider and PaymentMethodType per call. No PaymentMandate entity exists anywhere in the tree.
4 Invoice.OrderId is never persisted InvoiceWriter.CreateForOrderAsync uses command.OrderId only for GenerateInvoiceNumber(...); BillingService.CreateInvoiceAsync's request has no order field, so the column stays null.
5 Neither writer is idempotent InvoiceConfiguration.cs:55 indexes (TenantId, OrderId) non-uniquely, and neither IInvoiceWriter nor IPaymentInitiator accepts an idempotency key.
6 Settlement credits one hard-coded account, as one line LedgerPostingService declares private const string RevenueAccountCode = "4000"; PostInvoiceSettlementAsync credits it unconditionally and posts invoice.Total as a single line.

4. Scope (in / out)

4.1 In scope

  • SharedKernel.Abstractions.Ledgers.IJournalWriter, implemented by Finance. Plural deliberately: Ledger is already both a type and a namespace in Finance — the codebase aliases LedgerEntity in three places because of it — and a third colliding name in SharedKernel would push that onto every cross-module consumer.
  • A canonical-ledger concept so a caller can name the ledger it means.
  • A Finance-owned PaymentMandate entity and lifecycle, plus IRecurringPaymentInitiator.
  • Persisting Invoice.OrderId end to end.
  • Idempotency keys on the invoice and payment-intent write paths, with the right uniqueness constraints.
  • Order-type-aware, per-line settlement routing behind a resolver seam.

4.2 Out of scope

  • Anything about plans, entitlements, meters or usage — that is Spec 087.
  • The subscription-specific ledger accounts (2210, 4100, 4110, 5100) and their order-type mapping. This spec provides the seam; 087 registers its accounts into it.
  • General-purpose dunning, or any use of the DunningPlan entity.
  • Refunds and reversals against consumer-specific accounts.
  • Changing how the existing interactive checkout behaves in any observable way.
The regression bar Every existing money path must behave identically after this spec. A non-subscription invoice still credits 4000, as one line. A guest checkout still creates its intent, and can still create a replacement one. This is additive capability, not a change of behaviour, and the acceptance criteria are written to prove that rather than assume it.

5. Journal writing across modules

public interface IJournalWriter
{
    Task<JournalEntryRef> PostAsync(PostJournalCommand command, CancellationToken cancellationToken = default);
}

public sealed record JournalLineSpec(
    string AccountCode,
    string Direction,
    decimal Amount,
    string Currency,
    string? Narration = null,
    string? DimensionsJson = null);

public sealed record PostJournalCommand(
    Guid LedgerId,
    string SourceType,
    Guid SourceId,
    IReadOnlyList<JournalLineSpec> Lines,
    DateTime? TimestampUtc = null);

This mirrors IInvoiceWriter, whose own documentation calls it "the write mirror of the ADR-006 read contracts". Finance validates that debits equal credits, that every code resolves within the named ledger, and that the ledger belongs to the current tenant.

5.1 LedgerId is required, not defaulted

There is no safe default Account codes are unique per ledger, not per tenant. A code-only command would force Finance into a FirstOrDefault, which can post a financially material entry into the wrong ledger — and, because a ledger carries its own BaseCurrency, in the wrong currency. Guessing silently is worse than making the caller say what it means.

Callers that do not track ledgers resolve one through ILedgerResolver.GetCanonicalAsync(tenantId). A tenant with exactly one ledger resolves to it; a tenant with several must have one marked canonical, and resolution throws if none is. Marking a canonical ledger is a small additive flag on Ledger.

5.2 Idempotency comes free

Already enforced JournalEntryConfiguration already carries a filtered unique index on (TenantId, SourceType, SourceId) with filter [SourceType] <> 'Manual', added for LedgerService's own idempotency check. IJournalWriter inherits it: a retried business event returns the existing entry (AlreadyExisted: true) rather than double-posting. The writer rejects the reserved "Manual" source type, because manual entries all share SourceId = Guid.Empty and are excluded from that index — accepting it would silently drop the guarantee.

5.3 Dimensions

JournalEntryLine already carries DimensionsJson, so this only surfaces it on the contract. It is what lets a consumer post several lines into one account and still separate them afterwards — per meter, per product line, per whatever the consumer's analytic unit is. Finance stores it and never interprets it.

6. Payment mandates

A background job cannot use the guest path CreateGuestIntentForOrderAsync requires a Provider and a PaymentMethodType supplied per call, and creates a guest intent designed for anonymous storefront checkout. A job running unattended has neither value to supply, and "guest" is the wrong semantic for charging a saved instrument under a standing authorisation. 
PaymentMandate                       // Aonik.Finance, alongside PaymentMethod
    TenantId, PartyId                // the authorisation belongs to a PARTY
    Provider                         // who holds the vaulted instrument
    PaymentMethodId                  // the vaulted method
    ProviderMandateRef               // the provider's recurring-authorisation token
    Status        active | revoked | expired
    AuthorisedAt, ExpiresAt?, RevokedAt?
    RowVersion
ConcernRule
OwnershipTenant + party. A party may hold several; a consumer references one. Never shared across parties.
CreationAt a successful interactive payment, or an explicit "save for future payments" consent. Never minted by a background job — a mandate records a human's authorisation, so it must originate in one.
RevocationExplicit and immediate. Consumers referencing a revoked mandate cannot charge and must surface re-authorisation.
ExpiryCard or provider-mandate expiry sets expired, treated exactly as revoked.
AuditCreation, revocation and expiry are audit-logged. A standing authorisation to take money is exactly the thing that must be answerable after the fact.
 
public interface IRecurringPaymentInitiator
{
    /// <summary>
    /// Charge a stored mandate for an order. Throws if the mandate is revoked, expired,
    /// or belongs to another tenant. Idempotent on idempotencyKey.
    /// </summary>
    Task<PaymentIntentRef> CreateIntentForMandateAsync(
        Guid mandateId,
        Guid orderId,
        decimal amount,
        string currency,
        string idempotencyKey,
        CancellationToken cancellationToken = default);
}

A missing, revoked or expired mandate is a distinct, non-retryable failure. Retrying cannot fix a withdrawn authorisation, so a consumer must be able to tell that case apart from a soft decline and route the customer to re-authorise rather than looping.

7. The invoice must remember its order

Invoice.OrderId exists on the entity and is never written. InvoiceWriter.CreateForOrderAsync takes an OrderId, uses it to build the invoice number, and then calls a billing request that has no field to carry it.

Two things depend on fixing that, and neither can work until it is:

  • Settlement routing (§9) reads the funding order's type. With a null link there is no order to read.
  • Invoice idempotency (§8) keys on the order. With a null link the key is never distinct.

So CreateInvoiceRequest and BillingService.CreateInvoiceAsync gain the order link and persist it. Invoices raised without an order keep a null OrderId, which stays valid.

8. Idempotency without forbidding retries

Both writers accept an idempotency key, matching IOrderService's existing behaviour. The uniqueness constraints differ, and the difference is load-bearing.

WriterConstraintWhy this one
Invoice filtered unique (TenantId, OrderId) WHERE OrderId IS NOT NULL, plus unique (TenantId, IdempotencyKey) One invoice per order is a real invariant. The filter is mandatory because Invoice.OrderId is nullable and standalone invoices are valid — an unfiltered unique index permits only one NULL per tenant and would fail every tenant's second standalone invoice.
Payment intent unique (TenantId, IdempotencyKey) only — explicitly not unique per order Multiple intents per order are legitimate and required. PublicPaymentService permits an order already in PendingFunding and unconditionally adds another intent (lines 95, 177) — abandoned checkout, a switched method, a retried decline. Constraining by order would break the second attempt for every product on the platform.
Failed intents are terminal, so retries must replace PaymentService enforces its state machine explicitly — capture requires Authorized (if (currentStatus != PaymentStatus.Authorized)), authorisation requires Pending, and Failed is terminal. A consumer retrying a hard decline therefore must create a new intent rather than reuse the failed one. That is the second, independent reason intent uniqueness cannot be keyed on the order.

9. Settlement routing

PostInvoiceSettlementAsync today credits RevenueAccountCode = "4000" unconditionally, and posts invoice.Total as a single line. Two changes, both behind seams, so that adding a consumer never means editing a switch in the posting service.

9.1 Route by order type

public interface ISettlementRevenueResolver
{
    /// <summary>Order types this resolver claims.</summary>
    IReadOnlyCollection<string> OrderTypes { get; }

    /// <summary>The account a settled line credits. May be a liability, not revenue.</summary>
    string ResolveCreditAccountCode(string orderType, SettlementLineContext line);
}

Finance resolves the funding order's type from the now-persisted Invoice.OrderId and asks the registered resolver. An order type with no registered resolver falls back to 4000 — today's behaviour, unchanged, which is what keeps every existing product unaffected.

A credit is not always revenue A consumer may route to a liability account when cash has been received but nothing earned — prepaid units, deposits, gift balances. The resolver returns an account code and the posting service does not assume its type.

9.2 Split per line

A single credit for invoice.Total cannot carry a truthful per-line dimension when an order has several lines of different kinds — two different prepaid meters in one checkout, or mixed goods and services. Settlement therefore emits one credit line per invoice line, each with the dimension its consumer supplies.

A single-line invoice produces exactly one credit line, identical to today. The debit side is unchanged.

12. Acceptance criteria

The first four are regression criteria, and they matter more than the new capability:

  1. A settled non-subscription invoice credits 4000, as a single line, exactly as today.
  2. A guest checkout creates its intent unchanged, and can still create a replacement intent for an order already in PendingFunding.
  3. A tenant can raise two standalone invoices with no order.
  4. No existing Finance test requires modification.
  5. A module outside Finance posts a balanced, dimensioned journal entry to a named ledger.
  6. A PostJournalCommand naming a ledger from another tenant is rejected.
  7. ILedgerResolver throws for a tenant with several ledgers and no canonical one, rather than choosing.
  8. An order-backed invoice persists OrderId; a standalone invoice persists null.
  9. Duplicate invoice and intent writes with the same idempotency key are rejected — on LocalDB.
  10. A stored mandate funds an order with no interactive input.
  11. A revoked or expired mandate fails with a reason distinguishable from a soft decline.
  12. A registered order type routes its credit to the resolved account, one line per invoice line, each dimensioned.
  13. dotnet build Aonik.sln, dotnet test Aonik.sln, and the LocalDB lane green.

13. Open decisions

#QuestionLeaning
O1Should ILedgerResolver infer a canonical ledger when a tenant has exactly one?Yes at backfill, no at runtime. Inferring at runtime means the answer silently changes the day a second ledger appears.
O2Does a mandate belong to a party or to a payment method?Party. A method can be replaced (a reissued card) while the customer's authorisation persists; tying the mandate to the method forces re-authorisation for a bank's administrative act.
O3Should settlement splitting apply to the debit side too?Not in v1. The cash leg is genuinely one movement; only the credit side carries analytic meaning.
O4Should IJournalWriter support reversal entries?Not here. Refunds and reversals against consumer-specific accounts deserve their own spec, with the ledger's immutability rules stated explicitly.
O5 The supplied InvoiceNumber is discarded — should invoices have a real number? Found while implementing §7, and deliberately not fixed here. CreateInvoiceRequest.InvoiceNumber is accepted but Invoice has no such column, so the value is dropped; MapToResponse then returns invoice.Id.ToString("N") under that name. A caller therefore cannot look an invoice up by the number it supplied, and InvoiceWriter's GenerateInvoiceNumber(orderId) computes a string nothing keeps. Invoice numbering is a billing concern with sequence, format and per-tenant-series questions of its own — worth a spec, not a side effect of this one.
O6 Off-session semantics at the provider Delivered in P4: the mandate supplies the provider and instrument a background job cannot, which is what made unattended renewal possible. Not delivered: true off-session provider semantics — merchant-initiated-transaction flags, suppressing the interactive authentication challenge, honouring the provider's own recurring-authorisation token. IPaymentProviderGateway exposes only CreateIntentAsync and CreateSetupIntentAsync, and the one production implementer is simulated, so there is nothing real to express those flags against. ProviderMandateRef is stored ready for it. This is per-adapter work for whichever real gateway is wired, and a live card would likely fail an interactive challenge until it lands.
