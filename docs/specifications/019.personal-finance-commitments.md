# 019.personal-finance-commitments

## Objective

Define the product, domain, data, API, and mobile experience for personal-finance recurring payment commitments in Payabo.

This specification covers the personal-finance spending domain only. It explicitly excludes the provider bill-payment/catalog flow used to execute utility or service payments through external billers.

The goal is to let Payabo customers view, track, classify, and manage recurring payment commitments such as household bills, subscriptions, and debt repayments from the Spending experience, while keeping the underlying domain model precise and auditable.

## Problem Statement

The current codebase already contains several adjacent concepts, but they are not yet shaped into a coherent product feature:

- `Bill` exists as a personal-finance entity and is stored in the database.
- `Subscription` exists as a separate personal-finance entity.
- `PersonalTransaction` supports category classification, including `bills` and `subscriptions`.
- The mobile dashboard shows lightweight upcoming bills.
- The Spending area in the Flutter app does not expose a dedicated bills or commitments section.
- Recurring merchant detection exists, but there is no clear user-facing flow that converts detected recurring activity into first-class tracked commitments.

As a result, the system can partially represent recurring obligations, but the user experience and data model are not yet aligned around a single personal-finance commitments feature.

## Scope

### In Scope

- Personal-finance recurring payment commitments shown in Payabo Spending.
- Distinct domain treatment for:
  - bills
  - subscriptions
  - debt repayments
- Unified read-side experience for users to view all recurring commitments in one place.
- User flows to:
  - create a commitment manually
  - mark a transaction as a commitment
  - confirm or reject detected recurring commitments
  - edit and archive existing commitments
- Mobile-oriented read and write APIs for commitments.
- DB and contract changes needed to support the feature.
- Recommendation and detection rules for identifying recurring commitments from transactions.

### Out of Scope

- Provider-based bill-pay catalog, biller lookup, and bill-payment order execution.
- Replacing the current personal-finance transaction model.
- Autonomous AI mutation of financial state.
- A separate microservice or standalone commitments project.
- Ledger execution semantics. This feature is read/planning-oriented in personal finance, not a money-movement execution engine.

## Architectural Guardrails

- This feature belongs in the Personal Finance area of the existing Finance module.
- Tenant scoping remains mandatory for all entities and queries.
- A commitment is not itself a payment. It is a planned or detected recurring obligation.
- Orders remain business intent for executed payment flows and are not replaced by commitments.
- AI and heuristics may propose commitments, but the system must preserve a distinction between detected and user-confirmed obligations.
- The Spending UX may unify display of commitment types, but the underlying domain must preserve their semantic differences.

## Domain Model

## Core Principle

The system must separate:

1. the nature of a recurring obligation
2. how the system knows about it

These are different concerns and must not be collapsed into one field.

### Nature of obligation

This describes what kind of commitment the user has.

Recommended commitment types:

- `Bill`
- `Subscription`
- `DebtRepayment`

### Knowledge/verification state

This describes how the system knows the commitment exists.

Recommended verification states:

- `Detected`
- `Confirmed`
- `Manual`
- `Imported`
- `Rejected`
- `Archived`

This means:

- a gym membership is a `Subscription`
- a water bill is a `Bill`
- a mortgage is a `DebtRepayment`

Any of those may be:

- detected from transactions
- created manually by the user
- confirmed by the user
- later archived or rejected

## Recommended Target Model

Do not collapse the existing `Bill` and `Subscription` tables into one generic persistence table in the MVP.

Instead, introduce a unified read-side concept named `Commitment`, while preserving distinct domain entities underneath.

### Read-side concept

`Commitment` is a projection for mobile and read APIs.

It is not necessarily a new database table.

Recommended read model fields:

- `CommitmentId`
- `CommitmentType` (`Bill`, `Subscription`, `DebtRepayment`)
- `VerificationStatus` (`Detected`, `Confirmed`, `Manual`, `Imported`, `Rejected`, `Archived`)
- `DisplayName`
- `NormalizedMerchantOrPayee`
- `Amount`
- `Currency`
- `DueDate`
- `Frequency`
- `Status`
- `Autopay`
- `PaidFromAccountId`
- `Category`
- `SubCategory`
- `IsUserConfirmed`
- `ConfidenceScore`
- `SourceTransactionId`
- `DetectionSource`
- `LastObservedAt`
- `LastPaidAt`
- `LastPaidAmount`
- `CreatedAt`
- `UpdatedAt`

## Persistence Strategy

### Keep separate source-of-truth entities

Retain distinct entities for:

- `Bill`
- `Subscription`

Add a new first-class entity for debt-like recurring obligations:

- `DebtRepayment`

Recommended file:

- `src/Aonik.Finance/Entities/PersonalFinance/DebtRepayment.cs`

### Why separate entities are required

Bills, subscriptions, and debt repayments have overlapping UX, but materially different semantics:

- Bills are usually due-date-oriented household or service obligations.
- Subscriptions are merchant/service renewals, usually cancellable and merchant-centric.
- Debt repayments represent contractual liability servicing and may need fields such as lender, account reference, installment structure, or payoff metadata.

The user should see a unified surface. The platform should not lose the distinction.

## Transaction-to-Commitment Flow

The transaction detail screen is the most natural entry point for creating a commitment.

Current file:

- `apps/payabo_mobile/lib/features/spending/presentation/transaction_detail_screen.dart`

Current behavior already allows category override, including `bills` and `subscriptions`, but this only updates transaction classification.

Required new action:

- `Track as commitment`

Recommended flow:

1. user opens a transaction
2. user selects `Track as commitment`
3. system asks for commitment type:
   - bill
   - subscription
   - debt repayment
4. form is prefilled from transaction data
5. user confirms or edits:
   - name
   - amount
   - due date
   - frequency
   - account
6. system persists the appropriate commitment entity

### Prefill rules from transaction

- name from `Merchant` or `Description`
- amount from absolute value of transaction amount
- currency from transaction currency
- source account from `PersonalAccountId`
- category/subcategory from transaction classification if present
- likely due date from similar prior transaction spacing where available

## Detection and Suggestion Rules

## Guiding Principle

Do not automatically create active user commitments solely because a recurring pattern was detected.

The system may detect, suggest, and prefill. The user should confirm before the commitment becomes part of their trusted planning surface.

## Detection Inputs

Use existing data and services where possible:

- `PersonalTransaction`
- recurring merchant candidates from `CustomerInsightSnapshotGenerator`
- graph proposal signals from `FinancialLifeGraphInferenceService`
- merchant history lookups
- user-applied transaction categories

## Candidate heuristics

Create a recurring commitment suggestion when all or most of the following are true:

- the transaction is an expense
- the merchant/payee is repeated over at least 2 or 3 cycles
- the spacing between transactions is plausibly recurring
- the amount falls within a tolerance band
- the category aligns to bills, subscriptions, housing, insurance, utilities, or loan payments

### Suggested classification rules

Default inclination by category and pattern:

- utilities, council tax, insurance, rent-like merchant names -> `Bill`
- streaming, software, gym, membership, magazine -> `Subscription`
- mortgage, lender names, card issuer repayment, loan servicing -> `DebtRepayment`

### Confidence handling

The detection pipeline should produce:

- commitment type proposal
- confidence score
- evidence summary

Examples of evidence summary:

- `Observed 4 monthly charges from Virgin Media over 122 days`
- `Observed 6 recurring repayments to Halifax Mortgage with low amount variance`

## Business Rules

### Bill rules

- A bill is a recurring non-debt obligation with a due date or expected due cadence.
- Bills may be created manually even when no historical transaction exists.
- Bills should contribute to upcoming obligations and safe-to-spend calculations.

### Subscription rules

- A subscription is a recurring access or membership charge.
- It may be merchant-driven and renewable.
- Subscriptions may be auto-detected from transaction history but should still support manual creation.

### Debt repayment rules

- A debt repayment is a recurring payment servicing a liability.
- It should be modeled distinctly from bills and subscriptions.
- Mortgage payments should not be stored as subscriptions.

### Verification rules

- Detected commitments are visible but clearly marked as not yet user-confirmed.
- Confirmed or manually created commitments are first-class planning inputs.
- Rejected detections should not reappear immediately without materially new evidence.

## Reporting and Planning Rules

The commitments read model should support:

- upcoming obligations totals
- due-soon counts
- commitment-type breakdown
- detection review queues

These totals should feed:

- dashboard preview cards
- spending insights
- safe-to-spend style summaries
- future notification/reminder surfaces

## Acceptance Criteria

- Payabo Spending exposes a unified recurring commitments section.
- Users can view bills, subscriptions, and debt repayments in one place.
- Underlying persistence remains distinct for the three commitment types.
- A transaction can be promoted into a commitment through an explicit user flow.
- Detected recurring charges are shown with clear verification status.
- Mortgage and loan-style recurring payments are not modeled as subscriptions.
- Existing bill endpoints remain valid for bill-specific use cases.
- Mobile uses a new commitments-specific repository and DTOs rather than dashboard bill DTO reuse.
- DB changes are added through the canonical `AonikDbContext` migration stream only.

## Open Design Decisions

These decisions should be settled before implementation begins in earnest:

1. Final user-facing label
   - `Commitments`
   - `Bills & subscriptions`
   - `Bills`

2. Detected-item persistence strategy
   - persist native detected records directly
   - or persist proposals and project them into the commitments view

3. Debt repayment rollout scope
   - include `DebtRepayment` in MVP
   - or defer it to phase 2 while keeping the taxonomy ready from day one

4. Dashboard convergence
   - keep dashboard upcoming bills bill-only for MVP

## Recommendation Summary

The recommended direction is:

- unify the user experience around a single commitments surface
- keep `Bill`, `Subscription`, and `DebtRepayment` distinct in the domain
- treat commitment type separately from verification state
- avoid auto-creating trusted commitments without user confirmation
- add a commitments-specific read model and mobile repository rather than stretching the existing dashboard bill shape beyond its purpose
