Spec 036 Status: Draft Size: Large Priority: P1 Domain: Finance / Payabo / Remittance

RemittanceOrderService quote-confirm-settlement flow

Implements the Payabo B2C remittance path as a Finance orchestration service: quote → lock → debit ledger → call connector → record transmission → settle on webhook. Remittance remains an OrderType business intent; execution uses the existing payout connector port from Spec 031, not a new connector port. The public API surface is POST /payabo/remittance/quote, POST /payabo/remittance/confirm, and GET /payabo/remittance/{id}.

1. Summary

Payabo needs a customer-facing remittance flow that is financially safe and traceable. The service must quote the corridor, lock the quote before commitment, debit the tenant ledger before sending the external instruction, dispatch a payout connector call, persist the connector attempt, and later post settlement from the partner webhook. That sequence preserves AONIK's core discipline: orders capture intent, connector payouts execute fulfilment, and the ledger proves money movement.

The implementation is a new RemittanceOrderService in Aonik.Finance. It composes existing shipped primitives rather than creating a separate remittance bounded context:

ConcernUseCurrent artifact
Business intent Create an Order with OrderType = "Remittance" and a remittance-shaped OrderItem. Order, OrderType.Remittance
Quote Reuse the pricing engine, but persist PricingQuote.QuoteType = "Remittance". PricingService, PricingQuote
Beneficiary rail Use a saved, customer-owned ExternalPayoutAccount as the destination reference. ExternalPayoutAccount
Connector execution Call IPartnerPayoutConnector.InitiatePayoutAsync selected through IPartnerConnectorResolver. IPartnerPayoutConnector
Attempt record Persist the outbound call in Transmission, targeted to the Payout. Transmission
Async settlement Ingest partner callbacks into PartnerWebhookEvent, then idempotently settle the order and ledger. PartnerWebhookEvent
Success signals A Payabo user can request a quote, confirm it once, and retrieve the remittance state. Confirming writes exactly one Remittance order, one payout fulfilment record, one debit journal entry, and one transmission per idempotency key; retrying the same confirm returns the same order. The connector call is not made unless the quote is locked and the ledger debit succeeds. A duplicate webhook is stored or deduped without double-posting settlement. dotnet build Aonik.sln and focused service / endpoint tests pass.

This spec is intentionally grounded in what the repository already ships after Spec 031:

3. Scope (in / out)

3.1 In scope

  • New IRemittanceOrderService and RemittanceOrderService under Finance contracts/services.
  • New Payabo-facing API contracts and endpoints for POST /payabo/remittance/quote, POST /payabo/remittance/confirm, and GET /payabo/remittance/{id}.
  • Edit IPricingService / PricingService to support remittance quote persistence with QuoteType = "Remittance" while reusing the current pricing calculation.
  • New Remittance order details JSON shape stored on the order compatibility shadow column and / or ProvenanceJson, plus a remittance OrderItem details shape.
  • Edit LedgerPostingService to support remittance debit, connector settlement, and failure reversal source types.
  • New Payout connector orchestration: resolve route, create Payout, call IPartnerPayoutConnector, and record Transmission.
  • New Partner webhook processing for payout events that updates PartnerWebhookEvent, Payout, Transmission, Order, and remittance ledger settlement idempotently.
  • Edit Cross-border seed data to add remittance / payout capability lanes and routing-rule conditions for seeded corridors.
  • New Unit/integration tests for quote, confirm idempotency, connector failure handling, webhook settlement idempotency, and endpoint routing/policies.

3.2 Out of scope

  • Real Flutterwave / eTranzact / Interswitch remittance adapters. The existing simulated connector remains the first executable connector.
  • Building a full wallet product or customer balance ledger beyond the accounts needed to safely debit and settle this remittance flow.
  • Agent-triggered remittance execution. Remittance confirmation is high-risk money movement and must remain explicit user/system execution; agent support would marshal through Spec 032/030 proposals.
  • Changing the global orders principle. Orders remain business intent and do not become payment or payout rows.
  • Persisting raw account numbers, MSISDNs, wallet IDs, or unredacted partner payloads.

4. Target flow

POST /payabo/remittance/quote 1. Validate customer, corridor, amount, destination, and service code 2. Resolve pricing policy + FX + fees through PricingService 3. Persist PricingQuote with QuoteType = "Remittance" 4. Return quote snapshot + expiresAt + supported destination rails POST /payabo/remittance/confirm 1. Normalize Idempotency-Key and request body 2. Load unexpired remittance PricingQuote and saved ExternalPayoutAccount 3. Resolve remittance payout route / connector 4. Create Order(OrderType = "Remittance") + OrderItem + party roles 5. Lock quote to the order by copying a pricing snapshot into order details 6. Create Payout(status = Pending, ClientReference = idempotency key/ref) 7. Post remittance debit ledger entry (idempotent, before connector call) 8. Call IPartnerPayoutConnector.InitiatePayoutAsync 9. Update Payout + Order status and persist Transmission 10. Return order detail Partner webhook 1. Verify signature + translate with IPartnerWebhookTranslator 2. Insert/dedupe PartnerWebhookEvent 3. Locate Payout by ClientReference or ProviderReference 4. Update Payout / Transmission / Order status 5. If Succeeded, post settlement ledger entry exactly once 6. If Failed/Reversed, post debit reversal exactly once

4.1 State vocabulary

ObjectStatusesNotes
Order.Status Draft, PendingFunding, Transmitted, Complete, Failed, Expired, Cancelled Use existing string convention. Transmitted already exists in OrderStatuses. PendingFunding is already used by public bill-payment payment intent flow.
OrderItem.Status QuoteLocked, DebitPosted, Transmitted, Settled, Failed Item status tracks the single remittance line fulfilment.

Transmission.Status PartnerTransactionStatus string values One outbound connector attempt for the payout. Initial status is connector result.

6.3 Quote method

  1. Validate exactly one of originAmount or destinationAmount.
  2. Normalize country and currency codes to uppercase ISO values.
  3. Require customerPartyId; verify the party belongs to the current tenant/user context before returning a quote.
  4. Use service code REMITTANCE.PAYOUT unless a narrower corridor code is supplied by product configuration.
  5. Call the remittance pricing path and persist PricingQuote.QuoteType = "Remittance".
  6. Optionally resolve available payout lanes from ConnectorCapability for the destination country/currency.
  7. Return the quote values, expiry, fee breakdown, and supported destination methods.

6.4 Confirm method

  1. Require and normalize Idempotency-Key. Missing or blank keys are rejected at the endpoint.
  2. Look up an existing Order with (TenantId, OrderType = "Remittance", IdempotencyKey); if found, return its current remittance response.
  3. Load the PricingQuote and require QuoteType = "Remittance", current tenant, not expired, and matching request customer/corridor fields.
  4. Load ExternalPayoutAccount by id and require CustomerPartyId matches the requester, currency/country/rail are compatible, and the rail is verified or permitted by policy.
  5. Resolve connector route using ConnectorCapability.Category = "Payout", destination country/currency, and rail method; if persistent routing is not ready, fall back to IPartnerConnectorResolver.TryResolvePayoutConnector for the simulated provider.
  6. Create Order, one OrderItem, payer/receiver roles, history events, Payout, and OrderFulfilmentRef in the pre-dispatch database transaction.
  7. Lock the quote by copying all price, FX, fee, route, and destination summary fields into OrderItem.DetailsJson and Order.ProvenanceJson.
  8. Post the remittance debit ledger entry in that same pre-dispatch transaction. If debit posting fails, roll back and do not call the connector.
  9. Build a PayoutInstruction from the locked quote and destination. If a raw account/MSISDN is needed, resolve it from VaultRef or a short-lived request field; do not persist it.
  10. Commit the pre-dispatch transaction before making the external connector call.
  11. Call InitiatePayoutAsync. Update Payout and Order based on the normalized result in a post-dispatch save.
  12. Persist Transmission with the connector result, provider reference, redacted raw response, and idempotency key in the post-dispatch save.
Ordering invariant The connector call happens only after the quote is locked and the debit journal entry has been posted. The ledger debit is the source of proof that customer value was reserved/spent before AONIK asks a partner to pay the beneficiary. If any pre-connector step fails, no partner instruction is sent.
Transaction boundary Do not hold a SQL transaction open while calling the connector. Commit the quote-lock/order/payout/debit state first, then call the connector, then persist the transmission and final initiation status. If the connector fails after the debit committed, record the failed transmission and post an idempotent failure reversal.

7. Ledger postings

Extend LedgerPostingService with remittance source types. The helper writes directly to JournalEntry like payment capture / invoice settlement and relies on the existing unique non-manual source index for idempotency.

7.1 Source types

SourceTypeSourceIdWhenPurpose
RemittanceDebit Order.Id During confirm, before connector call. Reserve/debit customer value and move it into remittance clearing.
RemittanceSettlement Payout.Id On succeeded payout webhook. Move the beneficiary payout amount from remittance clearing to partner prefund / due-from-partner settlement.
RemittanceFailureReversal Payout.Id On failed/reversed payout after debit posted. Undo the customer debit and clear the remittance liability.

7.2 Account model

The exact chart account names can be refined, but the first implementation needs explicit, deterministic accounts. Reuse the seeded partner prefund accounts where possible, lazily create the remittance clearing account like the current payments clearing path, and avoid pretending that Cash is a customer wallet. If the customer has stored Payabo value, the debit reduces a customer-funds liability. If this flow also captures external funding, cash / settlement receivable is debited only for the actual funding receipt.

Open accounting detail The current ledger helper enforces a single currency per journal entry. Cross-currency remittance settlement therefore needs either separate origin/destination entries linked by source metadata, or a settlement-currency policy. The implementation must not create a mixed-currency balanced entry. See Open decisions.

8. Connector and transmission

8.1 Routing

Remittance execution resolves a payout connector. The persistent route should use ConnectorCapability and RoutingRule where available: 

new PartnerConnectorQuery(
    PartnerServiceCategory.Payout,
    country: quote.DestinationCountry,
    currency: quote.DestinationCurrency,
    method: destination.DestinationType)

The route result gives ConnectorId, PartnerId, and ProviderCode. The in-memory connector is resolved by ProviderCode. For the simulated connector, provider code remains "Simulated".

8.2 Payout instruction

PayoutInstruction maps from the locked order state, not from mutable request fields:

PayoutInstruction fieldSource
ClientReferenceNormalized idempotency key or generated REM-{orderId:N}.
AmountDestination payout amount and currency from locked quote.
DebitCurrencyOrigin currency from locked quote.
DestinationConstructed from the saved destination rail. Raw value comes from VaultRef or transient request input only.
NarrationRequest narration or default Payabo remittance.
CallbackUrlConfigured partner webhook callback URL.
MetadatatenantId, orderId, orderItemId, payoutId, quoteId, never raw PII.

8.3 Transmission record

Always write a Transmission after a connector call returns or throws. If the connector throws before returning a provider reference, persist Status = "Failed", LastError, and a null ProviderReference; set the payout/order to failed and post a debit reversal if the debit entry had already posted. 

new Transmission
{
    TenantId = tenantId,
    PayoutId = payout.Id,
    ConnectorId = connectorId,
    IdempotencyKey = clientReference,
    ProviderReference = result.Reference.ProviderReference,
    Status = result.Status.ToString(),
    RetryCount = 0,
    RawResponseJson = Redact(result.Raw.PayloadJson)
};

9. Webhook settlement

Partner callbacks are asynchronous and may repeat. The webhook path must be an idempotent inbox + processor, not direct status mutation from raw HTTP.

9.1 Endpoint shape

Add a partner webhook endpoint if one does not already exist in the implementation slice: POST /partners/webhooks/{providerCode}. It is not part of the Payabo public API, but it is required to satisfy the settlement requirement. The endpoint reads raw body + headers, resolves IPartnerWebhookTranslator, verifies signature, stores PartnerWebhookEvent, and dispatches processing. Signature failure stores the event with SignatureValid = false and does not mutate financial state.

9.2 Processing logic

  1. Translate to normalized PartnerServiceCategory, references, and PartnerTransactionStatus.
  2. Ignore non-Payout events in RemittanceOrderService; other processors handle bill/collection categories.
  3. Find the payout by ProviderReference first, then ClientReference.
  4. Require the payout to belong to an order item whose parent order has OrderType = "Remittance".
  5. For Succeeded: update payout/transmission to Succeeded, set order item Settled, set order Complete, and call PostRemittanceSettlementAsync.
  6. For Failed / Reversed / Expired: update payout/transmission/order as failed and call PostRemittanceFailureReversalAsync if the debit was posted.
  7. Mark the webhook event Processed only after all state and ledger updates commit.
No double settlement Settlement and reversal use JournalEntry.SourceType + SourceId idempotency. The webhook inbox dedupes by provider event id or payload hash, but ledger idempotency is still required because partners can send different event ids for the same final payout state.

11. Security, tenancy, idempotency

  • Authentication. All Payabo remittance endpoints require an authenticated user. Quote is read/compute with quote persistence; confirm is money movement and must not be anonymous.
  • Customer ownership. CustomerPartyId must resolve from the current user/tenant. Do not trust an arbitrary party id in the body without ownership verification.
  • Destination ownership. ExternalPayoutAccount.CustomerPartyId must match the customer; never authorize by BeneficiaryPartyId alone.
  • Idempotency. POST /payabo/remittance/confirm requires Idempotency-Key. Existing order uniqueness (TenantId, OrderType, IdempotencyKey) is the authority for replay.
  • Quote expiry. Confirm rejects expired quotes. Locking means copying quote values into order/item details; it does not extend the quote.
  • PII control. API responses expose masked rails only. Raw connector payloads are redacted before RawResponseJson or RawPayload persistence.
  • Webhook trust. Unsigned or invalidly signed callbacks are stored for audit but never mutate payout/order/ledger state.
  • AI safety. If agents later initiate remittance, confirmation is a high-risk mutation and must marshal through Spec 032/030 durable proposal execution, not direct in-band tool execution.

14. Acceptance criteria

  • POST /payabo/remittance/quote returns a persisted remittance quote with QuoteType = "Remittance", fee breakdown, FX metadata, and expiry.
  • POST /payabo/remittance/confirm rejects expired quotes, mismatched customer/destination ownership, unsupported routes, and missing idempotency keys.
  • Confirm creates one Order with OrderType = "Remittance", one OrderItem, one Payout, one OrderFulfilmentRef, and one Transmission.
  • Confirm posts RemittanceDebit before calling the connector; connector is not called when debit posting fails.
  • Retrying confirm with the same Idempotency-Key returns the existing order and does not create a second payout, transmission, ledger entry, or connector call.
  • Connector success sets order to Transmitted or Complete depending on whether the connector result is final; pending results remain non-terminal until webhook.
  • A succeeded payout webhook posts RemittanceSettlement exactly once and marks the order Complete.
  • A failed/reversed payout webhook posts RemittanceFailureReversal exactly once and marks the order Failed.
  • Duplicate webhooks do not double-post settlement or reversal.
  • Raw destination identifiers and unredacted provider payloads are never persisted or returned.
  • GET /payabo/remittance/{id} returns only orders owned by the current customer/tenant and returns 404 for other tenants/customers.
  • dotnet build Aonik.sln succeeds and the new remittance tests pass.

15. Open decisions

DecisionDefault for first implementationWhy it remains open
Customer funding account Use existing cash / clearing model in LedgerPostingService until a wallet/customer-liability account model lands. A true Payabo wallet or stored-value ledger may require per-customer liability accounts.
Cross-currency settlement entries Do not mix currencies in one journal entry. Post separate idempotent origin and destination entries or settle in one configured currency. The current ledger service enforces single-currency balancing. Final accounting policy needs finance review.
Provider routing source Use persistent ConnectorCapability / RoutingRule where seeded; otherwise fallback to simulated resolver. Spec 031 introduced the capability model, but a full routing engine is not yet broadly used by application services.
Webhook endpoint route POST /partners/webhooks/{providerCode}. A provider-specific route may be required by real vendor callback URL constraints.
Quote lock field Copy quote snapshot into OrderItem.DetailsJson and Order.ProvenanceJson. The OrderDetailsJson compatibility shadow column exists but is not a CLR property today.
