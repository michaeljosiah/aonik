1. Summary

The public catalog can list Active products and fetch one by slug — and nothing else a storefront front page needs. There is no featured construct, no curated grouping, no way to filter by tag or attribute, no way for search to match anything but name and description, and the list DTO (ProductSummaryDto) carries neither image nor tags, so a menu grid would need one detail call per card. This spec adds the merchandising layer as data: Collections with ranked members, FacetGroup definitions with declared match semantics, per-product hidden search keywords, an enriched summary DTO, a public category endpoint, and GET /commerce/config/storefront — the single document of tunables the frontend must never hard-code.

2. Motivation

  • The client homepage shows a curated "featured dishes" rail and grouped featured rails ("Carb-conscious") — chosen in the back office, reordered seasonally, no release.
  • The menu page filters on six facets (protein, spice, wellness goal, meal type, dietary, calorie bands) and the client's Step 2 spec goes further: the groups themselves are configuration — "adding a fifth group, renaming a group, reordering options or retiring a group must need no front-end change" (FR-3.1), and range filters are defined server-side (FR-3.5).
  • Search must catch spellings, regional names and cravings the copy doesn't contain — "goat", "shaki", "party" — via per-product keywords that are matched but never displayed (FR-2.1, AC-28).
  • Step 2 §6.5 enumerates the config the frontend reads instead of hard-coding: page size, back-to-top trigger, delivery display amounts, box bounds. That document needs a home and an endpoint.

3. Scope (in / out)

InOut (and where it goes)

  • FacetGroup definitions + browse-endpoint filtering + public facet endpoint
  • Product.SearchKeywordsJson + search extension (never serialized out)
  • ProductSummaryDto enrichment (hero image, tags, attributes, surcharge)
  • Public category-tree endpoint
  • GET /commerce/config/storefront + the settings keys behind it
  • Admin: product update endpoint (the catalog has create-only today), media list/reorder
  • Migration (tool-generated, canonical stream)
  • Media upload (blob wiring) — storefront-readiness wiring item; this spec orders/removes existing ProductMedia rows only
  • Option groups / content / box pricing — Specs 066/067/068 (the config document references 068's box plan, see §9)
  • Earliest delivery — Spec 069's endpoint; deliberately not duplicated into the config document (one source of truth, different cache cadence)
  • Full-text search infrastructure — filtering stays LIKE-based over name, description and keywords at this catalogue scale (tens of products); a search index is a different spec when a tenant has thousands
  • Personalised/AI-ranked merchandising — Collections are human-curated; agent-proposed curation would arrive as proposals per the platform's agent rules, not silent writes

4. The taxonomy (decision D4)

One product, three axes — ending the two-overlapping-groupings ambiguity the client's design templates carried:

AxisConstructCardinalityAnswers
CategoryProductCategory (existing, nested)exactly one "What is it?" — Mains, Soups & Stews, Sides
TagsProduct.TagsJson (existing) + attributesany number "What is it like?" — wellness goals, dietary suitability, badges ("New"), spice level (attribute)
CollectionsCollection (new)any number "Where do we show it?" — featured rail, "Carb-conscious" group, seasonal edit

"Carb-conscious" the merchandising rail is a collection; "carb-conscious" the filterable property is a tag surfaced through a facet. They can coexist and usually will — the rail is curated and ranked, the tag is exhaustive.

5. Domain model

Anemic, tenant-scoped, in src/Aonik.Commerce/Entities/Catalog/.

/// A curated, ordered, named set of products for storefront display.
public class Collection : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public string Slug { get; set; } = string.Empty;
    public string Title { get; set; } = string.Empty;      // display: "Carb-conscious"
    public string? Subtitle { get; set; }                  // optional supporting line
    /// Featured | Curated | Custom — see CollectionKinds. Presentation hint only;
    /// behaviour is identical.
    public string Kind { get; set; } = CollectionKinds.Curated;
    public int SortOrder { get; set; }                     // order among collections
    public bool IsActive { get; set; } = true;
    public List<CollectionItem> Items { get; set; } = new();
}

public class CollectionItem : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid CollectionId { get; set; }
    public Guid ProductId { get; set; }
    public int Rank { get; set; }                          // order within the collection
}

/// A storefront filter group with declared match semantics. The front end renders
/// whatever this returns; adding/renaming/retiring groups is data, not code.
public class FacetGroup : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public string Key { get; set; } = string.Empty;        // "wellness", "calories"
    public string Label { get; set; } = string.Empty;      // "Wellness goal"
    /// Category | Tag | Attribute | Range — see FacetMatchKinds (§6).
    public string MatchKind { get; set; } = FacetMatchKinds.Tag;
    /// For Attribute/Range: the AttributesJson property read, e.g. "spice" or
    /// "nutrition.kcal". Null for Category and Tag.
    public string? SourcePath { get; set; }
    /// For Category/Tag/Attribute: ordered [{ "value": "...", "label": "..." }].
    /// For Range: ordered [{ "label": "Under 500 kcal", "min": null, "max": 500 }] -
    /// half-open bands, min inclusive, max exclusive.
    public string OptionsJson { get; set; } = "[]";
    public int SortOrder { get; set; }
    public bool IsActive { get; set; } = true;
}

6. Facet semantics & browse filtering

Each group declares how it matches — the four kinds cover every filter in the client designs and the obvious future ones (Step 2 FR-3.1/FR-3.5):

MatchKindMatches a product when…Example
Categoryits category (or an ancestor) is one of the selected option values (category slugs)Mains, Soups & Stews
TagTagsJson contains any selected valueVegan, Gluten-free, New
Attributethe AttributesJson value at SourcePath equals any selected value (string compare)spice = "medium"
Rangethe numeric AttributesJson value at SourcePath falls in any selected band [min, max); a product missing the value matches no bandkcal under 500

Combination semantics (Step 2 FR-3.2, enforced server-side): within one group, selected options combine with OR; across groups, AND; free-text search ANDs with all of it. An unselected group restricts nothing. Unknown facet keys or option values in a request are rejected (400), not silently ignored — a storefront bug should be loud.

The browse endpoint (GET /commerce/catalog/products) gains repeatable facet parameters (facet.<key>=value1,value2) and a collection=slug parameter (membership filter; ordering by rank when no explicit sort). Existing parameters (kind, categoryId, search, paging) are unchanged; a new sort accepts name | newest (default: name).

7. Search & hidden keywords

  • Search matches case-insensitively, anywhere in the text, across: product name, description, and every entry of SearchKeywordsJson (Step 2 FR-2.1).
  • Keywords appear in no response. Not on ProductDto, not on ProductSummaryDto, not indirectly via AttributesJson (they are a dedicated column precisely so they cannot leak through the attributes pass-through). Admin DTOs expose them for editing; a dedicated test asserts the public serialization contract (AC-28: the customer who searches "party" finds the dish and never sees the word).
  • Implementation stays translated-LIKE over the JSON text at this scale (§3 out-scope note); the keyword column is 1024 chars — an authoring bound, not a search-engine substitute.

8. List DTO enrichment

ProductSummaryDto (public browse row) gains what a grid card renders — and nothing that violates the pricing posture:

public record ProductSummaryDto(
    Guid Id, string Slug, string Name, string Status, string Kind, Guid? CategoryId,
    int VariantCount,
    string? HeroImageUrl,          // first ProductMedia image by SortOrder; null when none
    IReadOnlyList<string> Tags,    // from TagsJson
    string AttributesJson,         // pass-through for card badges (spice, etc.)
    decimal? UnitSurcharge);       // Spec 066 column; cards may show "+£4"

No retail price on the summary row — deliberately. The client's brand rule ("dishes never show a standalone price") is only possible if the API doesn't force prices into every list payload. Variant prices stay internal (costing, margin — spec 057); UnitSurcharge is the one price-like field a card may carry because it is an on-top-of-the-box delta, not a dish price. Tenants that do show prices read them from the product detail. Revisit only with a real second storefront's needs on the table.

9. The storefront config document

GET /commerce/config/storefront — one anonymous, cacheable read serving every tunable the frontend must not hard-code:

{
  "currency": "GBP",
  "recommendedChoiceLabel": "Abby's choice",        // Commerce.Storefront.RecommendedChoiceLabel (Spec 066 §15)
  "resultsPageSize": 8,                             // Commerce.Storefront.ResultsPageSize
  "backToTopTrigger": { "type": "cardIndex", "value": 10 },   // Commerce.Storefront.BackToTopTriggerJson
  "delivery": { "listAmount": 10.00, "chargedAmount": 0.00 }, // settings consumed by Spec 068 quotes
  "defaultBoxSlug": "abbys-box",                    // Commerce.Storefront.DefaultBoxProductSlug
  "box": {                                          // embedded 068 size plan of that bundle;
    "minSize": 6, "maxSize": 30,                    //   null when unset or 068 not yet live
    "perSpacePrice": 15.00,
    "presets": [ { "size": 6, "price": 95.00, "badge": "Minimum order", "blurb": "…", "saving": null } ]
  }
}
  • Backed by tenant settings (keys above, under Commerce.Storefront.*) — the same mechanism config packs already write — plus a live read of the default bundle's size plan. Settings are authored through the existing tenant-settings surface; this spec adds the keys and the document, not a new settings system.
  • Unset values return sensible defaults (page size 8, label "Recommended", delivery 0/0, box: null). The endpoint never 404s — an unconfigured storefront gets a valid minimal document.
  • Earliest delivery is not here — Spec 069's endpoint owns it (different cache cadence, single source of truth).

11. Persistence & migration

  1. Configurations in Persistence/Configurations/Catalog/; indexes per §5; Slug/Key 64, Title/Label 128, OptionsJson 4096, SearchKeywordsJson 1024.
  2. Authoring validations: facet SourcePath required for Attribute/Range and forbidden otherwise; Range bands numeric, non-overlapping, ordered; option values non-empty and unique within a group; collection items must reference existing products of the tenant (Active enforced at read time, not membership time — a draft product may be staged into a collection).
  3. DbSets + MapTable entries in both contexts (Collections, CollectionItems, FacetGroups).
  4. One tool-generated migration: 
    dotnet ef migrations add AddCommerceStorefrontMerchandising --project src/Aonik.Infrastructure --startup-project src/Aonik.Api
    Expect three new tables + one column on AnkProducts, nothing else. Review, apply locally, commit both files. Hand-written migrations are prohibited (CLAUDE.md).

12. Security & tenancy

  • Tenant-scoped entities behind the global filters; public endpoints serve Active data only and resolve tenant via the existing anonymous middleware (decision D3).
  • Search keywords are the one sensitive-ish surface (they may encode merchandising strategy): admin-read only, asserted absent from public serialization by test.
  • Admin policy split identical to the rest of Commerce.

13. Testing

  • Unit — facet matching: each MatchKind; OR-within/AND-across; range bands half-open incl. boundary values; product missing the ranged value matches nothing; unknown key/value → 400.
  • Unit — search: keyword hit with no name/description occurrence; case-insensitivity; substring position independence.
  • Serialization contract: SearchKeywordsJson absent from every public DTO (walk the actual serialized JSON, not the type).
  • Service (InMemory, TestTenantProvider): collection full-replace reorder idempotency; draft product staged in a collection is excluded from the public read; facet authoring validations; product PATCH partial-update semantics.
  • API (CustomWebApplicationFactory): collections/facets/categories /config round-trips; enriched browse row carries hero image + tags and no price field; config document defaults when unconfigured; admin authz; tenant isolation.
  • Full-solution dotnet test Aonik.sln before PR.

15. Acceptance criteria

#Given / when / then
A1A "featured" collection with ranked members → homepage endpoint returns them in rank order; reordering in admin changes the next read with no release.
A2Facets Vegan + Mains selected → only vegan mains return (AND across groups); Vegan + Vegetarian → either (OR within a group). [Step 2 AC-13/14]
A3A range facet "Under 500" [null, 500) → a 499-kcal product matches, a 500-kcal product does not; a product with no kcal attribute matches no band.
A4Adding a fifth facet group in admin → public facet endpoint includes it and browse filters on it — zero frontend change. [Step 2 FR-3.1, AC-29 analogue]
A5Product keyword "party", word absent from name/description → search "party" returns it; the string "party" appears nowhere in any public response. [Step 2 AC-28]
A6Browse row for a product with media and tags → hero image URL + tags + attributes present; no variant price field exists on the row.
A7Unconfigured tenant → config document returns defaults (page size 8, label "Recommended", box null); never 404.
A8Configured tenant with a default box bundle carrying a size plan → config document embeds min/max/presets/per-space matching the 068 plan read.
A9Draft product staged into a collection → visible in admin collection read, absent from the public one; activating the product surfaces it without touching the collection.
A10PATCH product updating tags and keywords → browse reflects tags immediately; keyword change affects search only.

16. Open decisions

O1 — Facet option counts. The client UI shows "Show N dishes" live counts; N is computable client-side from the filtered result. Server-side per-option counts (SQL aggregation per facet) are a nice-to-have deferred until a catalogue is big enough that the client can't hold the filtered set.

O2 — Scheduled merchandising. Collections have no start/end dates; a seasonal edit is activated by hand. Add ActiveFromUtc/ActiveToUtc when a real scheduling need appears.

O3 — Money representation. The config document and summary DTO serve decimals, consistent with the rest of Commerce; the storefront converts to minor units in its client class. Follows the plan's "money at the API edge" wiring decision if that lands differently.
