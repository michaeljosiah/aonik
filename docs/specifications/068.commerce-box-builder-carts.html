Commerce box-builder carts — size pricing, line editing, authoritative quotes

The cart is the box (plan decision D1): a mutable, anonymous, server-side box-building session with size-parameterised bundle pricing, personalised line editing with identical-line merging, a hard capacity ceiling, an authoritative quote on every write, and checkout materialisation onto the existing bundle/order shape. Build area C of the Abby's Table storefront capability plan; implements the server contract of the client's Step 2 functional spec.

1. Summary

Spec 042's cart is add-and-checkout: items go in, a bundle line is validated once, checkout converts it to an order. A box-builder storefront needs a session: the customer picks a box size, fills it line by line with personalised dishes over many minutes, changes quantities, changes the size, and expects an authoritative running total after every touch. This spec makes the Commerce cart that session. The bundle product remains the catalog anchor — it now carries a size plan (preset price points + a formula) — while size and lines live on the cart. Checkout still produces the standard one-ProductPurchase-order shape, so production planning (specs 055/056), inventory and payments are unchanged consumers; they simply gain personalisation detail per selection.

2. Motivation & shape of the solution

The client's Step 2 spec (§6–§7) defines the contract this implements: a server-persisted box addressed by id, line CRUD where a line is dish + exact personalisation + quantity, identical lines merged, a capacity ceiling with grow-the-box as the only overflow path, and "every write returns the whole box plus the quote". Decision D1 settled where that lives:

  • Not one bundle product per size — a 6–30 formula-priced range collapses into 25 near-identical products and "grow the box" becomes a product swap.
  • The cart is the box. Cart gains the bundle reference and chosen size; CartItem becomes the line (variant + canonical personalisation + quantity); the existing BundleSlot machinery keeps defining what may go in (source category, allow-duplicates), and the new size plan defines what it costs at any size.

Two pricing regimes, explicitly separated. Container pricing (the box price by size) is this spec. Per-line pricing (personalisation adjustment, per-unit surcharge) is Spec 066, consumed here per line and summed in the quote. Dish variants keep their internal ProductPrice rows for costing and margin (spec 057) — box quotes never read them, and storefront responses never expose them (the "no standalone dish price" brand rule is thereby possible, not enforced, at the API layer).

Line identity is CartItem.Id — the storefront's lineId. The merge key is (LineKind, BoxBundleSlotId, ProductVariantId, PersonalisationJson); canonical-form string equality makes the selection part exact (Spec 066 §7). A variant can be eligible for more than one slot, and each slot carries its own min/max/allow-duplicates rules — so the slot is part of the line's identity: the add command names it explicitly, or the server resolves it automatically when exactly one slot is eligible and rejects as ambiguous otherwise. OrderBundleSelection.BundleSlotId is populated from the line at checkout.

4.1 Line kinds — why the discriminator exists before the feature

A box session will eventually hold two different things: the dishes filling the box, and add-ons — an ordinary retail product bought alongside it (a jar of sauce, a cookbook), priced individually, consuming no box space. Add-ons are not in this spec's scope: no routes, no quote component, no checkout lines are built here.

What is in scope is the discriminator. Without LineKind, every capacity, merge, quote and checkout rule below implicitly means "all lines" — and adding a second kind later would silently give a jar of sauce a box space and require re-auditing R1–R12 to find out where. With it, each rule states the kind it counts, and the later change is additive: new routes, a new quote component, extra order items. The column ships with exactly one legal value (CartLineKinds.BoxDish); writing any other is rejected until the add-on capability lands.

Product constraint (confirmed 2026-07-21): one box per cart. A cart holds at most one box — hence BoxBundleProductId/BoxSize live on Cart and no box-container entity is needed. Add-ons attach to that cart as AddOn lines. If multiple boxes per order ever become real, that is the change that outgrows this shape (the two fields move onto a per-box entity) — it is deliberately not pre-built, and O3 records the trigger.

5. Box pricing

boxPrice(size) = preset(size).Price   when a preset row exists for that size
               = BasePrice + (size − BaseSize) × PerSpacePrice   otherwise
valid sizes:     MinSize ≤ size ≤ MaxSize
  • Presets always win over the formula at their size — 12 is 170.00 even though the formula says 185.00 (Step 2 §3.1). Everything about this table is data; nothing is code.
  • A new pricing-mode constant BundlePricingModes.SizeTiered marks bundles priced this way; authoring a size plan requires that mode, and the existing modes (Fixed / SumOfComponents / SumPlusPremium) are untouched.
  • PerSpacePrice feeds the formula only — it is not the universal marginal price of a space. Around a discounted preset the marginal cost bends: with the launch table, 11→12 costs 0 (formula 170 → preset 170) and 12→13 costs 30 (preset 170 → formula 200). The charge for growing is therefore always boxPrice(target) − boxPrice(current), computed from the authoritative table; grow-flow UI displays that delta, never PerSpacePrice × spaces. The per-space figure still appears in exactly one place — the formula — and never as a per-dish line item (Step 2 FR-13.2).

6. Write semantics

"Units" means BoxDish units throughout this section and §12. Every capacity count, merge lookup and fullness test is scoped to LineKind = BoxDish; an AddOn line consumes no box space and never participates in them (§4.1). At launch every line is a box dish, so the two readings coincide — stating the scope now is what keeps them from diverging silently later.

OperationBehaviour
Create box Cart created with BoxBundleProductId, initial BoxSize (validated against the plan), currency from the plan, optional first line in the same call (the dish-detail → Step 1 handoff: the viewed dish arrives already in the box, personalisation carried over).
Change size Validate MinSize ≤ new ≤ MaxSize; reject when new < total units with the exact count to remove first (never silently drop lines). Reprices the container only.
Add line Validate the target slot (named in the command, or auto-resolved when exactly one slot is eligible — ambiguous otherwise), the variant slot-eligible and active, the product Active, quantity ≥ 1, and the selection via Spec 066 (normalise → validate → price, passing the cart currency — 066 V10 rejects any mis-denominated option group). Availability is checked against aggregate demand: the resulting cart-wide quantity for the variant must not exceed current availability (non-reserving — six units cannot be added when one is in stock, and repeated merges cannot creep past it; checkout still reserves atomically for races). Reject if total units would exceed BoxSize — growing first is the only path (Step 2 FR-13.1: no overflow route exists server-side, whatever the UI does). Merge into an existing line when (kind, slot, variant, canonical selection) matches; else create.
Update line — quantity Increase re-checks the ceiling and aggregate availability; quantity 0 deletes the line; negative quantities reject (R12) — a negative line must never reach pricing or, worse, flow a negative reservation into the inventory engine at checkout.
Update line — personalisation Re-validate/re-price via 066. If the new selection matches another existing line, merge into it (delete the source). Optional applyToUnits (1 ≤ n ≤ line quantity): split semantics per Step 2 FR-10.5 — remove n units from the target line (delete if emptied), merge-or-create a line with the new selection carrying n units. One atomic operation; the two-line state is never client-assembled.
Remove lineDelete regardless of quantity.
Continue Validates total units == BoxSize; rejects otherwise naming the shortfall (Step 2 AC-20). Stateless gate — checkout independently re-validates.

Every write recomputes from scratch. Adjustments and surcharges are re-derived from the live catalogue on each write and re-snapshotted; the snapshots are display cache, never pricing inputs. No client-supplied amount is read anywhere (Step 2 AC-22), and every write response carries the full box + quote so concurrent tabs self-correct on their next action.

Capacity is enforced under a concurrency token, not hope. "Last write wins" describes the UX between tabs, not the integrity model: two adds racing into the last space touch different line rows, so neither overwrites the other and a naive implementation commits seven units into a six-box. Every capacity-affecting write therefore runs in a transaction that also touches the Cart row under its rowversion concurrency token (AonikDbContextBase.ConfigureRowVersions already stamps it): concurrent writers conflict, the loser revalidates against fresh state and retries once, then 409s. Two adds racing into one remaining space can never both commit (A17).

7. The quote

Returned by every write, by GET, and by the explicit quote endpoint:

{
  "box":   { "cartId": "…", "bundleProductId": "…", "size": 6, "currency": "GBP",
             "lines": [ { "lineId": "…", "productId": "…", "variantId": "…", "name": "…",
                          "quantity": 2, "personalisation": { …canonical… },
                          "personalisationSummary": "Full table · Salmon",
                          "isDefaultPersonalisation": false,
                          "personalisationAdjustment": 8.00, "unitSurcharge": 4.00 } ] },
  "quote": { "components": [                  // ORDERED, NAMED, ADDITIVE — total is their sum
               { "key": "boxPrice",        "amount": 95.00 },
               { "key": "personalisation", "amount": 16.00 },   // Σ adjustment × qty (signed)
               { "key": "unitSurcharges",  "amount":  8.00 },   // Σ surcharge × qty
               { "key": "deliveryCharged", "amount":  0.00 } ], //   ("addOns" joins here later)
             "deliveryList": 10.00,           // struck-through display value; NOT a component
             "total": 119.00,                 // Σ components — never a hard-coded formula
             "currency": "GBP",
             "unitsSelected": 6, "boxSize": 6, "spacesLeft": 0, "isFull": true },
  "changes": [ …catalogue-drift notices, usually empty — §8… ]
}
  • The total is the sum of a named component list, not a fixed four-term formula. Clients render the breakdown by iterating components and must not reconstruct the total from known keys — that way the eventual addOns component (§4.1) is an additive change no storefront release has to chase. Zero-amount components may be omitted; unknown keys must render generically rather than break.
  • personalisation is signed and can be negative in aggregate — a box of below-default choices legitimately totals under the box price (Step 2 AC-9).
  • unitsSelected, spacesLeft and isFull count BoxDish units only (§4.1); an add-on never changes them.
  • Delivery display values come from tenant settings (Commerce.Storefront.DeliveryListAmount / DeliveryChargedAmount, default 0/0) until Spec 069 owns delivery properly; the quote shape will not change when it does.
  • No per-dish price appears anywhere in the payload — see §2 callout. (An add-on line, when that lands, does carry its own retail price: it is an ordinary product bought at its own price, not a dish priced by the box.)

8. Catalogue-drift handling

A box session outlives catalogue edits. On every load (GET or any write), each line's selection is re-normalised against the product's current effective options via Spec 066's stored-selection mode (RenormalizeStoredAsync — drift is reported, never thrown):

  • Drift follows Spec 066's RenormalizeStoredAsync contract exactly — the cases differ: a retired choice in a still-servable group remaps to that group's current effective default ({ "lineId": …, "group": "side", "from": "plantain", "to": "wildrice", "reason": "option-retired", "priceDelta": -2.00 }); a deactivated or de-narrowed group has no effective default to remap to and is dropped from the selection ("reason": "group-removed"). Both re-price and re-canonicalise (the merge key changes with the selection). The storefront tells the customer what changed and why (Step 2 edge table).
  • Remapping can merge lines (the remapped selection may now equal another line's) — the change entry says so.
  • A line's product or variant becoming unavailable — product no longer Active, variant deactivated (ProductVariant.IsActive), or availability gone — does not silently vanish: the line stays, flagged "unavailable" in changes[]; add/increase on it is rejected; continue and checkout are blocked while an unavailable line remains (the customer chooses: remove it or keep waiting). A retired SKU can never ride an old cart into a new order.

9. Checkout materialisation

Extends the existing CheckoutService path for box carts; non-box carts are byte-for-byte unaffected.

  1. Re-validate everything (full box, availability, active flags, selections) — the continue gate is advisory UX; checkout is the enforcement. If re-validation produces any drift change (option remap, line merge, unavailable line), checkout stops: it returns 409 with the refreshed box + changes[] and creates nothing — a stale client that skipped the continue step must explicitly review a changed meal or price before money movement begins; resubmitting against the refreshed state proceeds (A18).
  2. Reserve component stock exactly as the bundle path does today (HoldRef = cart id).
  3. Create one ProductPurchase order, idempotency key cart:{id} (unchanged). The order carries one OrderItem per priced thing — today that is the box item and (when charged) the delivery item; each future AddOn line will add one ordinary retail item alongside them, using the spine's existing ProductPurchase line shape (Quantity, UnitPrice, ProductId, Sku) unchanged, so nothing here is reserved for it now. The box OrderItem carries Quantity = 1, UnitPrice = the box goods total (box price + personalisation + unit surcharges — never any add-on amount), AmountIn likewise, and DetailsJson gains a box envelope: 
    { "box": { "bundleProductId": "…", "size": 6,
           "quote": { "boxPrice": 95.00, "personalisation": 16.00,
                      "unitSurcharges": 8.00, "currency": "GBP" } } }
  4. Write one OrderBundleSelection row per BoxDish line — now carrying PersonalisationJson / Summary / Adjustment / UnitSurcharge (§4). This is the kitchen-facing landing: the production sheet and kitchen work orders (specs 055/056) read selections per component and can render "Jollof — Full table · Salmon ×2". Spec 066 §12's DetailsJson envelope remains the contract for simple-product lines with selections; for box orders the per-line facts live on the selection rows and the item-level envelope carries the box aggregate. (Follow-up task in §16: surface the personalisation column on the 055/056 sheet DTOs.)
  5. Delivery charge is materialised, not absorbed. When deliveryCharged > 0, checkout adds a dedicated delivery order item (ItemType = "DeliveryFee", AmountIn = the charged amount) and includes it in the payment total (subtotal − discount + tax + delivery) and charge summary. The existing checkout maths has no delivery step, so without this the customer would be charged less than the authoritative quote. Zero at launch (£10 list, free charged) — the path is defined and tested, dormant in production until Spec 069 phase 2 turns fees on.
  6. Invoices for box carts are box-aggregate. The existing per-CartItem invoice path would emit one line per dish from price snapshots that are explicitly not pricing inputs here — exposing standalone dish prices and disagreeing with the single aggregate order item. A box cart's optional invoice instead carries one line named for the box ("6-dish box") at the goods total, plus the delivery line when charged. Non-box carts keep the existing per-item path untouched.
  7. Kitchen projections ship in this spec, not as a follow-up. ProductionPlanningService today aggregates OrderBundleSelection rows by variant alone — two Jollof preparations would collapse into one demand line, and no added column can un-collapse them afterwards. The Spec 055/056 projections are updated here: production demand groups by (variant, canonical personalisation), and the production sheet / kitchen work-order DTOs render each group's PersonalisationSummary and label-snapshotted display (A14).
  8. Discounts, tax, guest payment intent, funding link — all unchanged.

12. Server-enforced rules

Write-path rules (Step 2 "rules the back end must enforce", mapped):

#Rule
R1Size below plan minimum or above plan maximum → reject.
R2Size below units already selected → reject with the count to remove.
R3Any write taking total BoxDish units above BoxSize → reject. No overflow path exists. (Add-on lines are outside this count by construction — buying a jar of sauce must never consume a dish space, nor be blocked by a full box.)
R4Selection invalid per Spec 066 (V1–V5, incl. option-not-offered-by-product) → reject with 066's rule id.
R5Variant not eligible for the resolved slot, variant inactive (ProductVariant.IsActive), product not Active, ambiguous slot without an explicit BundleSlotId, or resulting cart-wide demand for the variant above current availability → reject.
R6Identical (variant, canonical selection) → merge, never duplicate lines.
R7Price recomputed from scratch on every write; client-supplied amounts ignored.
R8Continue and checkout refused unless units == size and no line is flagged unavailable.
R9Writes to a cart whose status is not Open or whose OrderId is already stamped → reject. The existing checkout deliberately leaves a cart Open (with OrderId set) until payment completes — status alone would let a customer edit a box whose order, reservation and payment amount are already fixed (this mirrors ValidateOpenCartAsync).
R10Guest-token enforcement on every cart operation. Anonymous carts: every read, write, quote, continue and checkout must present the cart's token via the X-Cart-Token header; compared constant-time; any mismatch or absence → 404 (indistinguishable from an unknown cart — no oracle). The token is server-minted: ≥ 256 bits of entropy, opaque, disclosed exactly once in the create response; any client-supplied token value on create is ignored (today's contract stores it verbatim, so an attacker could register an empty or guessable token), and legacy carts whose stored token is null/weak fail closed. Party-bound carts: an authenticated principal matching BuyerPartyId instead. Applies to the generic cart endpoints too, not just box carts. Enforcement lives at the service boundary, not endpoint middleware: IBoxCartService and ICartService operations take a required CartAccessContext (guest token or authenticated party principal) and authorize through one shared authorizer; the endpoints merely translate X-Cart-Token into it. Every direct consumer — CheckoutService, the Commerce agent tools, anything future — must present the context, so non-HTTP call paths cannot read or mutate arbitrary carts by knowing an id.
R11Box carts are writable only through kind-aware routes. The generic cart mutation paths (POST /commerce/carts/{id}/items, /bundles, generic remove) reject any cart with BoxBundleProductId set (400 pointing at the box routes) — a kind-blind insert would land an untyped line that capacity, slot, personalisation, merge and quote rules cannot classify. This is a rule about kind-blindness, not about add-ons: when the add-on capability lands it adds its own IBoxCartService route that stamps LineKind = AddOn, and the generic paths stay closed.
R12Add commands require quantity ≥ 1; update quantity 0 deletes the line, negative rejects; applyToUnits stays bounded 1..line quantity. Non-positive quantities never reach pricing or stock reservation (a negative reservation would release stock).
R13LineKind must be BoxDish — the only value this spec implements. Any other value is rejected until the add-on capability lands, so the column can never hold a kind whose rules do not yet exist. Persisted lines with a null/absent kind are read as BoxDish.

Authoring rules: A1 preset sizes within [Min, Max]; A2 BaseSize == MinSize not required but MinSize ≤ BaseSize ≤ MaxSize; A3 plan requires Kind=Bundle + BundlePricingMode=SizeTiered; A4 currency immutable while any non-stale open box session references the plan (see A6); A5 structural and monetary bounds — MinSize ≥ 1, MaxSize ≥ MinSize, BasePrice > 0, PerSpacePrice ≥ 0, every preset price > 0, and the formula must price every size in [MinSize, MaxSize] strictly above zero — an empty, inverted or zero/negative-quoting plan must never reach order and payment creation; A6 box carts idle beyond a configured window (Commerce.Carts.AbandonAfterDays, default 14, existing background-job infrastructure) transition to Abandoned, so a single stale anonymous session cannot pin plan authoring forever.

13. Persistence & migration

  1. Two new tables (AnkBundleSizePlans, AnkBundleSizePresets) + additive nullable columns on AnkCarts, AnkCartItems, AnkOrderBundleSelections (§4). Configurations in Persistence/Configurations/; amounts decimal(19,4) (matching ProductPrice and the Spec 066 option amounts they are combined with); PersonalisationJson nvarchar(max) (Spec 066 bounds neither group count nor multi-select width — a fixed cap could reject a valid canonical selection at persistence), PersonalisationSummary 512, LineKind 16 with a non-null default of BoxDish so existing rows and generic-cart writes classify correctly without a backfill.
  2. DbSets + MapTable entries in both contexts.
  3. One tool-generated migration: 
    dotnet ef migrations add AddCommerceBoxBuilderCarts --project src/Aonik.Infrastructure --startup-project src/Aonik.Api
    Review (two tables + additive columns, nothing else), apply locally, and commit all three generated artifacts — the migration .cs, its .Designer.cs, and the updated AonikDbContextModelSnapshot.cs (an uncommitted snapshot makes the next migration rediscover these tables). Hand-written migrations are prohibited (CLAUDE.md).

14. Security & tenancy

  • Box endpoints are anonymous like the existing cart endpoints, but access is not cart-id-possession alone: R10 requires the guest token (X-Cart-Token) on every operation — cart ids travel in URLs and URLs leak (logs, history, shared links); the token travels in a header and is disclosed exactly once, in the create response. Carts are tenant-scoped; the global filters plus R10 make any unauthorised access return 404.
  • Rate limiting on cart writes follows the platform's anonymous-endpoint posture (the Spec 061 pattern is the precedent for tightening if abuse appears; not built pre-emptively).
  • No PII added. The personalisation payload is product configuration, not personal data.
  • Money paths: box carts never move money — checkout hands off to the existing guest payment-intent flow, which already carries the money-action logging obligations (issue #142); the new code emits no money actions of its own.

18. Open decisions

O1 — Pending-action memory for the grow flow. Step 2's "remember the dish while the customer decides to grow" is modelled client-side (the FE holds the pending line and replays it after the resize succeeds). Server-side pending intents would add state for no integrity gain — the replayed add revalidates everything anyway. Flagged in case product wants the pending dish to survive a page refresh mid-grow-flow.

O2 — Box session TTL: resolved in this revision. Because A4's currency lock counts open carts, an abandonment sweep became a correctness requirement rather than a nicety: authoring rule A6 transitions box carts idle beyond Commerce.Carts.AbandonAfterDays (default 14) to Abandoned via the existing background-job infrastructure. Spec 069 phase 2 may later tighten the window for stale delivery promises.

O3 — Multiple boxes per session: closed. Confirmed with the client (2026-07-21): an order carries at most one box. So BoxBundleProductId/BoxSize stay on Cart and no box-container entity is built. Trigger to revisit: if two boxes in one checkout ever becomes a real requirement, those two fields move onto a per-box entity and the quote grows from one box price to N — that is the migration this shape does not absorb. Add-ons (§4.1) are not that trigger: they are extra lines beside the one box, which is exactly what LineKind handles.
