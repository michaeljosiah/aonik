Commerce box-builder carts — size pricing, line editing, authoritative quotes

The cart is the box (plan decision D1): a mutable, anonymous, server-side box-building session with size-parameterised bundle pricing, personalised line editing with identical-line merging, a hard capacity ceiling, an authoritative quote on every write, and checkout materialisation onto the existing bundle/order shape. Build area C of the Abby's Table storefront capability plan; implements the server contract of the client's Step 2 functional spec.

1. Summary

Spec 042's cart is add-and-checkout: items go in, a bundle line is validated once, checkout converts it to an order. A box-builder storefront needs a session: the customer picks a box size, fills it line by line with personalised dishes over many minutes, changes quantities, changes the size, and expects an authoritative running total after every touch. This spec makes the Commerce cart that session. The bundle product remains the catalog anchor — it now carries a size plan (preset price points + a formula) — while size and lines live on the cart. Checkout still produces the standard one-ProductPurchase-order shape, so production planning (specs 055/056), inventory and payments are unchanged consumers; they simply gain personalisation detail per selection.

2. Motivation & shape of the solution

The client's Step 2 spec (§6–§7) defines the contract this implements: a server-persisted box addressed by id, line CRUD where a line is dish + exact personalisation + quantity, identical lines merged, a capacity ceiling with grow-the-box as the only overflow path, and "every write returns the whole box plus the quote". Decision D1 settled where that lives:

  • Not one bundle product per size — a 6–30 formula-priced range collapses into 25 near-identical products and "grow the box" becomes a product swap.
  • The cart is the box. Cart gains the bundle reference and chosen size; CartItem becomes the line (variant + canonical personalisation + quantity); the existing BundleSlot machinery keeps defining what may go in (source category, allow-duplicates), and the new size plan defines what it costs at any size.

Two pricing regimes, explicitly separated. Container pricing (the box price by size) is this spec. Per-line pricing (personalisation adjustment, per-unit surcharge) is Spec 066, consumed here per line and summed in the quote. Dish variants keep their internal ProductPrice rows for costing and margin (spec 057) — box quotes never read them, and storefront responses never expose them (the "no standalone dish price" brand rule is thereby possible, not enforced, at the API layer).

4. Domain model

New entities

/// Container pricing for a bundle product priced by size (box of N). One per bundle.
public class BundleSizePlan : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid BundleProductId { get; set; }
    public int MinSize { get; set; }                 // smallest sellable box
    public int MaxSize { get; set; }                 // tunable ceiling - never hard-coded client-side
    public int BaseSize { get; set; }                // formula anchor (launch: 6)
    public decimal BasePrice { get; set; }           // price at BaseSize (launch: 95.00)
    public decimal PerSpacePrice { get; set; }       // per space above BaseSize (launch: 15.00)
    public string Currency { get; set; } = "GBP";
    public List<BundleSizePreset> Presets { get; set; } = new();
}

/// A merchandised price point that overrides the formula at its size.
public class BundleSizePreset : AuditableEntity, ITenantScoped
{
    public Guid TenantId { get; set; }
    public Guid BundleSizePlanId { get; set; }
    public int Size { get; set; }
    public decimal Price { get; set; }
    public string? Badge { get; set; }               // "Most popular", "Minimum order"
    public string? Blurb { get; set; }
    public decimal? SavingAmount { get; set; }       // authored display saving; never computed
    public int SortOrder { get; set; }
}

Line identity is CartItem.Id — the storefront's lineId. The merge key is (ProductVariantId, PersonalisationJson); canonical-form string equality makes that exact (Spec 066 §7). Box lines always reference a variant of a product eligible for the bundle's slot (existing BundleSlot sourcing rules).

5. Box pricing

boxPrice(size) = preset(size).Price   when a preset row exists for that size
               = BasePrice + (size − BaseSize) × PerSpacePrice   otherwise
valid sizes:     MinSize ≤ size ≤ MaxSize
  • Presets always win over the formula at their size — 12 is 170.00 even though the formula says 185.00 (Step 2 §3.1). Everything about this table is data; nothing is code.
  • A new pricing-mode constant BundlePricingModes.SizeTiered marks bundles priced this way; authoring a size plan requires that mode, and the existing modes (Fixed / SumOfComponents / SumPlusPremium) are untouched.
  • PerSpacePrice is also the price of one added space when growing the box — the figure appears in exactly one place, never as a per-dish line item (Step 2 FR-13.2).

6. Write semantics

OperationBehaviour
Create box Cart created with BoxBundleProductId, initial BoxSize (validated against the plan), currency from the plan, optional first line in the same call (the dish-detail → Step 1 handoff: the viewed dish arrives already in the box, personalisation carried over).
Change size Validate MinSize ≤ new ≤ MaxSize; reject when new < total units with the exact count to remove first (never silently drop lines). Reprices the container only.
Add line Validate the variant is slot-eligible, the product Active, availability > 0 (non-reserving check), and the selection via Spec 066 (normalise → validate → price). Reject if total units would exceed BoxSize — growing first is the only path (Step 2 FR-13.1: no overflow route exists server-side, whatever the UI does). Merge into an existing line when (variant, canonical selection) matches; else create.
Update line — quantity Increase re-checks the ceiling; decrease to 0 deletes the line.
Update line — personalisation Re-validate/re-price via 066. If the new selection matches another existing line, merge into it (delete the source). Optional applyToUnits (1 ≤ n ≤ line quantity): split semantics per Step 2 FR-10.5 — remove n units from the target line (delete if emptied), merge-or-create a line with the new selection carrying n units. One atomic operation; the two-line state is never client-assembled.
Remove lineDelete regardless of quantity.
Continue Validates total units == BoxSize; rejects otherwise naming the shortfall (Step 2 AC-20). Stateless gate — checkout independently re-validates.

Every write recomputes from scratch. Adjustments and surcharges are re-derived from the live catalogue on each write and re-snapshotted; the snapshots are display cache, never pricing inputs. No client-supplied amount is read anywhere (Step 2 AC-22), and every write response carries the full box + quote so concurrent tabs self-correct on their next action (last-write-wins is the concurrency model, as the Step 2 edge table specifies).

7. The quote

Returned by every write, by GET, and by the explicit quote endpoint:

{
  "box":   { "cartId": "…", "bundleProductId": "…", "size": 6, "currency": "GBP",
             "lines": [ { "lineId": "…", "productId": "…", "variantId": "…", "name": "…",
                          "quantity": 2, "personalisation": { …canonical… },
                          "personalisationSummary": "Full table · Salmon",
                          "isDefaultPersonalisation": false,
                          "personalisationAdjustment": 8.00, "unitSurcharge": 4.00 } ] },
  "quote": { "boxPrice": 95.00,
             "personalisation": 16.00,        // Σ adjustment × qty (signed)
             "unitSurcharges": 8.00,          // Σ surcharge × qty
             "deliveryList": 10.00,           // display values, tenant settings (§3 out-scope note)
             "deliveryCharged": 0.00,
             "total": 119.00,                 // boxPrice + personalisation + unitSurcharges + deliveryCharged
             "currency": "GBP",
             "unitsSelected": 6, "boxSize": 6, "spacesLeft": 0, "isFull": true },
  "changes": [ …catalogue-drift notices, usually empty — §8… ]
}
  • personalisation is signed and can be negative in aggregate — a box of below-default choices legitimately totals under the box price (Step 2 AC-9).
  • Delivery display values come from tenant settings (Commerce.Storefront.DeliveryListAmount / DeliveryChargedAmount, default 0/0) until Spec 069 owns delivery properly; the quote shape will not change when it does.
  • No per-dish price appears anywhere in the payload — see §2 callout.

8. Catalogue-drift handling

A box session outlives catalogue edits. On every load (GET or any write), each line's selection is re-normalised against the product's current effective options:

  • A chosen key no longer offered (retired choice, tightened narrowing, deactivated group) → that group remaps to the current effective default, the line re-prices, and a changes[] entry describes it plainly: { "lineId": …, "group": "side", "from": "plantain", "to": "wildrice", "reason": "option-retired", "priceDelta": -2.00 }. The storefront tells the customer what changed and why (Step 2 edge table).
  • Remapping can merge lines (the remapped selection may now equal another line's) — the change entry says so.
  • A line's product becoming unavailable does not silently vanish: the line stays, flagged "unavailable" in changes[]; add/increase on it is rejected; continue and checkout are blocked while an unavailable line remains (the customer chooses: remove it or keep waiting).

9. Checkout materialisation

Extends the existing CheckoutService path for box carts; non-box carts are byte-for-byte unaffected.

  1. Re-validate everything (full box, availability, selections) — the continue gate is advisory UX; checkout is the enforcement.
  2. Reserve component stock exactly as the bundle path does today (HoldRef = cart id).
  3. Create one ProductPurchase order, idempotency key cart:{id} (unchanged). The single box OrderItem carries Quantity = 1, UnitPrice = quote.total − deliveryCharged, AmountIn likewise, and DetailsJson gains a box envelope: 
    { "box": { "bundleProductId": "…", "size": 6,
           "quote": { "boxPrice": 95.00, "personalisation": 16.00,
                      "unitSurcharges": 8.00, "currency": "GBP" } } }
  4. Write one OrderBundleSelection row per line — now carrying PersonalisationJson / Summary / Adjustment / UnitSurcharge (§4). This is the kitchen-facing landing: the production sheet and kitchen work orders (specs 055/056) read selections per component and can render "Jollof — Full table · Salmon ×2". Spec 066 §12's DetailsJson envelope remains the contract for simple-product lines with selections; for box orders the per-line facts live on the selection rows and the item-level envelope carries the box aggregate. (Follow-up task in §16: surface the personalisation column on the 055/056 sheet DTOs.)
  5. Discounts, tax, optional invoice, guest payment intent, funding link, charge summary — all unchanged.

12. Server-enforced rules

Write-path rules (Step 2 "rules the back end must enforce", mapped):

#Rule
R1Size below plan minimum or above plan maximum → reject.
R2Size below units already selected → reject with the count to remove.
R3Any write taking total units above BoxSize → reject. No overflow path exists.
R4Selection invalid per Spec 066 (V1–V5, incl. option-not-offered-by-product) → reject with 066's rule id.
R5Variant not eligible for the bundle's slots, product not Active, or availability ≤ 0 → reject.
R6Identical (variant, canonical selection) → merge, never duplicate lines.
R7Price recomputed from scratch on every write; client-supplied amounts ignored.
R8Continue and checkout refused unless units == size and no line is flagged unavailable.
R9Writes to a cart whose status is not Open → reject (checked-out and abandoned boxes are immutable).

Authoring rules: A1 preset sizes within [Min, Max]; A2 BaseSize == MinSize not required but MinSize ≤ BaseSize ≤ MaxSize; A3 plan requires Kind=Bundle + BundlePricingMode=SizeTiered; A4 currency immutable once any open box session references the plan.

14. Security & tenancy

  • Box endpoints are anonymous like the existing cart endpoints; possession of the unguessable cartId (GUID) is the access model, unchanged from Spec 042. Carts are tenant-scoped; the global filters make cross-tenant access return 404.
  • Rate limiting on cart writes follows the platform's anonymous-endpoint posture (the Spec 061 pattern is the precedent for tightening if abuse appears; not built pre-emptively).
  • No PII added. The personalisation payload is product configuration, not personal data.
  • Money paths: box carts never move money — checkout hands off to the existing guest payment-intent flow, which already carries the money-action logging obligations (issue #142); the new code emits no money actions of its own.

17. Acceptance criteria

Numbers in brackets map to the client Step 2 spec's acceptance criteria.

#Given / when / then
A16-box with 5 units; add a line → units 6, isFull, continue succeeds. [AC-1]
A2Full 6-box; any add/increase route → rejected R3; no overflow charge exists anywhere in the quote. [AC-2, AC-11]
A3Grow 6→8 then add → box 8, price 125.00 (formula), pending line added by the client's next call. [AC-3]
A4Same dish added twice with identical selection → one line, qty 2. [AC-5]
A5Same dish added with a different selection → second line. [AC-6]
A6Line qty 3, update 1 unit to a new selection → original line 2, new line 1. [AC-18]
A7Default side (2.00) switched to a 0.00 side → quote total drops by 2.00; breakdown shows the negative. [AC-9]
A8Size 12 quotes 170.00, not the formula's 185.00; changing a preset price in admin re-prices the next quote.
A98 units selected; change size to 6 → rejected naming "remove 2". [AC-17]
A10Continue on a 5/6 box → 4xx naming the shortfall; direct checkout equally refused. [AC-20]
A11Any client-supplied price in any write body → ignored; server figures returned. [AC-22]
A12Option retired while in a box → on next load the line remaps to the current default, re-prices, and changes[] explains it.
A13Product goes unavailable mid-session → line flagged, adds rejected, continue/checkout blocked until removed.
A14Checkout of a personalised box → one ProductPurchase order; every OrderBundleSelection row carries its canonical selection + summary; production sheet input contains them.
A15Signature-surcharge dish ×2 in the box → unitSurcharges 2 × surcharge; independent of personalisation on the same lines. [AC-12]

18. Open decisions

O1 — Pending-action memory for the grow flow. Step 2's "remember the dish while the customer decides to grow" is modelled client-side (the FE holds the pending line and replays it after the resize succeeds). Server-side pending intents would add state for no integrity gain — the replayed add revalidates everything anyway. Flagged in case product wants the pending dish to survive a page refresh mid-grow-flow.

O2 — Box session TTL. Carts already have an Abandoned status; no expiry job is added here. When delivery dates arrive (Spec 069 phase 2), stale boxes quoting stale promises may justify a TTL sweep — decide there.

O3 — Multiple boxes per session. The contract supports it naturally (each cart is one box); the storefront currently builds one at a time. Nothing to build — noted so nobody "adds" it.
