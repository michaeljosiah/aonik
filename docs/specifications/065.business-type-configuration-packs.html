Spec 065 Status: Draft (Rev 1) Size: Large Priority: P1 Domain: Platform / Agents / Commerce / PersonalFinance

Business-type configuration packs

Implements ADR-014. A tenant gains a business type, and provisioning applies the pack for that type — the packaged default configuration that stands up "a Simi tenant" or "a food-commerce tenant" repeatably, instead of hand-assembled rows. A pack is two separable layers: a config pack (identity + behaviour: modules, feature flags, roles, agent overrides, branding, reference data) applied at provision to every tenant of that type, and a sample pack (illustrative content) applied only behind the demo toggle. The platform already has the seed/provision mechanics (three module-contributed seams, phased and reversible) but no notion of a type to seed for; this spec adds it by extending those seams, not forking them. It is the delivery mechanism ADR-013 needed — the Simi config pack (Spec 064) is its first instance.

The split is the point Today the only per-tenant seed pipeline (the demo seed) mixes configuration with sample content and is hard-wired to two payments-vertical types. The load-bearing decision here is to separate them: a config pack is what makes a tenant a Simi (or food-commerce) tenant and is safe for production; a sample pack is example rows for demos and never touches production. Everything else in this spec follows from that separation and from keeping platform code generic (no if (type == "simi")).

1. Summary

AONIK is a product-agnostic platform; a "business type" is the shape of a product built on it (Simi = the personal-finance keeper; food-commerce = maker-ops). This spec makes that shape first-class: a BusinessType on the tenant, a declarative config-pack manifest per type, a generic applier that writes the manifest through the platform's existing tenant-scoped stores (Setting, the Agent override, ReferenceDataItem), type-aware provisioning contributors for the module resources that can't be pure data (giving Commerce its first provisioning contribution), and a sample pack that generalises today's demo seed from a 2-value enum to the open business type — with configuration finally split out of sample content.

Success signal An operator creates a tenant and picks Food commerce. It provisions with the commerce module enabled, units and ingredient categories seeded, the commerce agent configured, and branding set — ready to use, no demo rows. The same operator creates a Simi tenant: the personal-finance keeper persona, its toolset, and the SIMI statement prefix are all in place from the Simi pack. Neither tenant required a code change or a hand-built row; a third product ships by authoring a third manifest.

2. Current state & seams build on these

  • Three module-contributed seed seams, all IEnumerable<T> DI (each module advertises its slice): IGlobalSeedContributor, IDemoSeedContributor (phased via DemoSeedPhase, idempotent, reversible), ITenantProvisioningContributor (all in src/Aonik.SharedKernel/Abstractions/).
  • Orchestrators: TenantProvisioner (real per-tenant resources) and DemoSeedService (phased demo). Provisioning is one-size-fits-all — TenantProvisioningContext (a record of TenantId, DefaultCurrency, UserId, Now) carries no type; every tenant gets the same five roles + chart of accounts + policies.
  • Config stores that are already tenant-overridable: the Agent two-level override (global → tenant, resolved by DomainAgentResolver; written via AgentConfigurationService.UpsertOverrideAsync); Setting (Scope ∈ {Global, Tenant, User}, including feature flags in SettingDefinitions); ReferenceDataItem (TenantId-nullable, tenant rows resolve over global).
  • The gaps: no BusinessType anywhere; DemoSeed is a closed enum of two types that mixes config with content; no per-tenant settings/agent-override seeding (Global-only for settings; Admin-UI-only for agent overrides); Commerce contributes nothing to provisioning; TenantProvisionedEvent is defined but dead.
  • Prior art: PayaboSetupProfile is this exact idea at the user level — a profile that drives what gets set up. This spec lifts it to the tenant.

3. Scope (in / out)

3.1 In scope

  • Edit BusinessType on Tenant, CreateTenantRequest, and TenantProvisioningContext (§4).
  • New The config-pack manifest (JSON per type) + a loader (§6).
  • New IConfigPackApplier / ConfigPackApplier — writes a manifest through the existing tenant-scoped stores (§7).
  • Edit ITenantProvisioningContributor becomes type-aware; Commerce gains its first contributor (§8).
  • Edit Generalise the sample pipeline from the 2-value DemoSeed enum to the open business type; split config out of the demo contributors (§9).
  • New Two first-party packs — Simi (authored by Spec 064) and food-commerce — plus a generic base pack (§6, §8).

3.2 Out of scope

  • Operator/partner-authored packs & a pack marketplace. First-party manifests only in v1 (ADR-014).
  • A config DSL. Manifests are plain declarative JSON over the existing stores.
  • Event-driven provisioning. v1 applies synchronously through TenantProvisioner; TenantProvisionedEvent stays a future async option.
  • Reworking the roles model or the ledger/policy provisioning beyond making them type-aware.
  • Product identity in platform code. The applier/contributors never branch on a specific type; identity lives in the manifest (data) per ADR-013.

4. The business type the keystone

An open string, additive like OrderType, with a known-values helper — so a new product is a new value, never an enum edit: 

// Known values helper (not a closed enum) — src/Aonik.SharedKernel/.../BusinessType.cs
public static class BusinessType
{
    public const string Base         = "base";           // generic tenant, no product specialisation
    // NOTE: concrete product types (simi, food-commerce, ...) are NOT constants here - that would put a
    // product noun in a platform symbol, which Spec 064's architecture test rejects (ADR-013). Concrete
    // types are values discovered from the installed pack manifests (data); only Base lives in code.
    // remittance, billing, … added additively
}

// Tenant gains a persisted type; provisioning threads it through.
public class Tenant : /*…*/ { /*…*/ public string BusinessType { get; set; } = "base"; public int? AppliedPackVersion { get; set; } }
public record CreateTenantRequest(/* name, currency… */ string? BusinessType = null);  // optional - existing callers omit it; missing/blank normalises to "base" server-side
public record TenantProvisioningContext(Guid TenantId, string DefaultCurrency, Guid? UserId, DateTime Now, string BusinessType);  // BusinessType ADDED to the existing record; UserId stays nullable as today

BusinessType is persisted on the tenant (so the platform knows what a tenant is — for re-apply, UI, and support) and carried through TenantProvisioningContext. Unset defaults to base: the current one-size-fits-all behaviour, unchanged.

6. The config-pack manifest new — data, not code

A pack's generic configuration is a declarative JSON manifest per business type — following the existing seed-data convention (finance-demo-catalog.json, platform-demo-ids.json), so identity is data exactly where ADR-013 says it belongs: 

// packs/simi.pack.json  (first-party resource; the Simi pack is authored by Spec 064)
{
  "businessType": "simi",
  "version": 1,
  "displayName": "Simi",
  "modules": ["PersonalFinance", "Documents", "Ai"],
  "settings": {
    "Branding.AgentDisplayName": "Simi",
    "Branding.StatementVerificationPrefix": "SIMI",
    "PersonalFinance.Circle.Enabled": "true"
  },
  "agents": [
    {
      "name": "personal-finance-agent",
      "instructionsRef": "packs/simi/personal-finance-agent.md",   // the de-branded persona (Spec 064)
      "toolset": ["pf_list_care_entities", "pf_get_care_entity_profile", "pf_list_payment_logs",
                  "pf_list_shared_circles", "pf_get_shared_entity", "pf_log_shared_payment", "…"],
      "model": null                                                  // null = platform default routing
    }
  ],
  "referenceData": [],
  "roles": []
}

A food-commerce.pack.json enables ["Commerce", "Ai"], sets the commerce agent, and carries referenceData for units of measure and ingredient categories. A base.pack.json is empty (the current default). The manifest sections map one-to-one onto stores the platform already has (§7); anything that needs code lives in a type-aware contributor (§8), never in the manifest.

7. The generic applier new

One generic component applies a manifest to a tenant through the existing tenant-scoped writers — it contains no product knowledge, only a loop over declarative sections: 

public interface IConfigPackApplier
{
    // Applies the pack for the tenant's business type. Idempotent; preserves admin-edited values (§9).
    Task<ConfigPackResult> ApplyAsync(Guid tenantId, string businessType, CancellationToken ct = default);
}
ConfigPackApplier.ApplyAsync(tenantId, "simi") load manifest for businessType (+ version) ├─ settings[] → SettingsService.UpsertTenant(key, value) // Scope=Tenant; skip if admin-edited (§9) ├─ agents[] → AgentConfigurationService.UpsertOverrideAsync // per agent: instructions (from ref), toolset, model ├─ referenceData[]→ ReferenceDataService.UpsertTenant(type, code, displayName) ├─ roles[] → (beyond the base five) role + permission map └─ record Tenant.AppliedPackVersion = manifest.version
  • Reuses existing writers — AgentConfigurationService.UpsertOverrideAsync is exactly the per-tenant agent override the Admin UI already uses; settings and reference data have tenant-scoped stores. The applier just drives them from a manifest instead of a human.
  • Scope every write to the provisioned tenant explicitly. UpsertOverrideAsync and the settings / reference-data writers resolve their tenant from the ambient ITenantProvider (GetCurrentTenantId()), but TenantProvisioner runs in an admin / bootstrap context whose ambient tenant is not the one being provisioned. The applier must therefore either take an explicit-tenant writer overload or set and restore ITenantContext.TenantId = tenantId around the writes (the pattern CircleService.PreviewInviteAsync already uses). Otherwise pack overrides land on the operator's tenant or throw. This is the applier's single most important correctness rule.
  • Instruction bodies (instructionsRef) are packaged alongside the manifest (a markdown file), keeping a long persona prompt out of the JSON and versioned with the pack.
  • Feature flags are settings — they flow through the same settings[] section (SettingDefinitions already models flags), so "enable the Circle for Simi" is one manifest line.

8. Type-aware provisioning contributors edit

Module resources that cannot be pure data — a chart-of-accounts variant, Commerce's units/categories, a module's bespoke defaults — are emitted by the existing ITenantProvisioningContributors, now given the type: 

public interface ITenantProvisioningContributor
{
    string ModuleName { get; }
    Task<TenantProvisioningContribution> ContributeProvisioningAsync(
        TenantProvisioningContext context, CancellationToken ct = default);   // context.BusinessType now available
    Task ContributeHealthCheckAsync(Guid tenantId, List<string> issues, CancellationToken ct = default);
}
  • Commerce gains its first contributor — CommerceTenantProvisioningContributor — that runs only when the Commerce module is enabled for the tenant (per the manifest's modules[]), seeding units of measure, ingredient/product categories, and starter reference data. It keys off module enablement, not a businessType == "food-commerce" check, so no contributor branches on a type value. This is the forcing function ADR-014 predicted: Commerce stops provisioning bare.
  • Existing contributors stay (Finance ledger/chart/policies, AI route policy) and may branch on type where a variant is genuinely needed — but a contributor never hard-codes a product persona or branding string (that is manifest/config, ADR-013). Most specialisation is data in the manifest, not code here.
  • Where the applier runs: TenantProvisioner.ProvisionAsync calls the type-aware contributors, then IConfigPackApplier.ApplyAsync — one line added to the existing orchestrator.

9. The sample pack edit

The sample layer is the existing demo pipeline, generalised and de-conflated:

  • Key by business type, not a 2-value enum. DemoSeedService.SeedAsync(tenantId, businessType) replaces the DemoSeedTypes constants; the phased DemoSeedPhase orchestration, idempotency, SemaphoreSlim guard, and reversal are kept as-is.
  • Split config out. Today's demo contributors mix config (roles, pricing policies, the agent fleet) with sample content (personas, transactions, activity). The config half moves to the config pack (applied at provision); the demo contributors keep only sample content. A sample seed thus presupposes a provisioned, configured tenant and only adds example rows.
  • Endpoint continuity. The admin surface (POST /admin/tenants/{id}/demo-seed and its reverse) stays; it now dispatches by the tenant's BusinessType. A tenant with no sample contributor for its type simply seeds nothing.

10. Idempotency, versioning, re-apply

  • Idempotent. The applier upserts; a second apply is a no-op. It never overwrites admin-edited values — extending SettingsSeedService's existing Global-scope rule to tenant scope (a setting/agent-override a tenant admin changed is left alone).
  • Versioned. Each manifest has a version; Tenant.AppliedPackVersion records what was last applied. Re-applying a newer pack is additive-only: it inserts genuinely-new settings, tools, and reference data and never updates a value that already exists, so admin edits are inherently safe (no per-key provenance needed — matching SettingsSeedService's insert-missing behaviour), then bumps the recorded version. Updating an existing pack default for live tenants (telling a pack default apart from an admin edit) needs value provenance and is deferred as a later refinement.
  • Reversal stays a property of the sample layer only (the existing reverse machinery); config is not "reversed" — a tenant's type is changed deliberately, out of scope for v1 (O4).

11. Provisioning flow

create tenant (businessType = "food-commerce") → Tenant { BusinessType = "food-commerce" } → TenantProvisioner.ProvisionAsync(ctx{ …, BusinessType }) ├─ base: roles + ledger + policies (existing contributors, now type-aware) ├─ CommerceTenantProvisioningContributor (units, categories — §8, new) └─ ConfigPackApplier.ApplyAsync("food-commerce") settings/flags → Setting (Tenant) agents → Agent override refData → ReferenceDataItem Tenant.AppliedPackVersion = N ⇒ a ready, configured tenant — NO sample rows (production-safe) later (demo / trial only): POST /admin/tenants/{id}/demo-seed → DemoSeedService.SeedAsync(id, "food-commerce") → sample content only (reversible)

12. Persistence & migration

  • Two columns on Tenant: BusinessType (string, default "base") and AppliedPackVersion (int?, nullable). Existing tenants backfill to base / null — no behaviour change.
  • Tool-generated migration only, against AonikDbContext (CLAUDE.md). No new tables for the config path — settings, agent overrides, and reference data already have tables; the manifest is a resource, not a row.
  • Manifests ship as first-party resources (following finance-demo-catalog.json); the exact home (embedded per-module fragments vs a central packs directory vs DB rows) is O1.

13. Security & isolation

  • Tenant-scoped writes only. The applier writes exclusively to the tenant being provisioned; every store it touches (Setting, Agent, ReferenceDataItem) is ITenantScoped.
  • Manifests are first-party — no tenant input becomes a pack; BusinessType is set at tenant creation by an operator, validated against the known-values helper (unknown type → base or a rejected request, O2). This is the boundary until operator-authored packs (a separate, gated spec per Spec 033's model).
  • Agent overrides remain gated. A pack sets instructions/toolset/model on an existing descriptor; it cannot introduce an unclassified mutating tool — the Spec 032 gate and the Spec 033 ToolsetIdsJson allow-list still apply. A pack configures capability; it does not smuggle it.

14. Phasing & tasks

  1. Type keystone. BusinessType + AppliedPackVersion on Tenant; add to CreateTenantRequest and TenantProvisioningContext; known-values helper; tool-generated migration.
  2. Manifest + loader. The JSON schema, the first-party resource location, and an IConfigPackSource that resolves a manifest (+ instruction bodies) by type.
  3. The applier. ConfigPackApplier over settings / agent overrides / reference data / roles; wired into TenantProvisioner after the contributors; idempotent + admin-edit-preserving.
  4. Type-aware contributors. Thread BusinessType into ITenantProvisioningContributor; add CommerceTenantProvisioningContributor.
  5. Sample split. Generalise DemoSeedService to key by business type; move config-shaped demo contributions into packs; keep only sample content in the demo pipeline.
  6. The three packs. base, food-commerce, and simi (the last authored by Spec 064).
  7. Tests (§15) + admin surface to pick a type at tenant creation and show the applied pack version.

15. Acceptance criteria

  • Type-driven provision. Creating a food-commerce tenant yields the commerce module enabled, units/categories seeded, the commerce agent configured, and branding set — with no sample rows; a simi tenant yields the Simi persona, toolset, and SIMI prefix.
  • Config/sample split. A freshly provisioned production tenant has its configuration but zero example entities; the sample seed adds content only, and reverses cleanly.
  • Generic platform code. No brand noun and no if (businessType == "<type>") branch in the applier or a contributor — module-specific provisioning is driven by manifest-declared module enablement, never a type-equality check; a grep for product nouns in src/ (per Spec 064) stays clean — identity is in manifests only.
  • Idempotent + admin-safe. Re-applying a pack is a no-op; an admin-edited setting/agent override survives a re-apply; a version bump is additive-only — it inserts new settings/tools and never updates an existing value, so edits cannot be clobbered.
  • Base unchanged. A tenant with no/unknown type provisions exactly as today.
  • Build & migration. dotnet build green; one tool-generated migration adds the two Tenant columns; the full-solution DI test (Api.Tests) boots.

16. Open decisions

  • O1 — Manifest home. Embedded per-module fragments merged per type (best module-boundary fit, ADR-005), a central packs/ resource directory (simplest), or DB rows (operator-editable later). Leaning: central first-party resources for v1, module fragments when a module's slice grows.
  • O2 — Type taxonomy & validation. The initial value set (base, simi, food-commerce, + remittance/billing?) and whether an unknown type at creation falls back to base or is rejected. Leaning: known-values helper + reject unknown from the API, accept via override for forward compat.
  • O3 — Re-apply trigger. Whether a pack version bump auto-applies to existing tenants of that type (a background job) or is an explicit admin action. Leaning: explicit admin "update pack" action in v1, surfaced by the AppliedPackVersion drift.
  • O4 — Changing a tenant's type. Out of scope for v1 (a tenant is created as a type). Whether re-typing a live tenant is ever supported (and how config is reconciled) is a later question.
  • O5 — Async via TenantProvisionedEvent. v1 applies synchronously in TenantProvisioner. If provisioning grows heavy, the dead TenantProvisionedEvent is the ready hook to move pack application to a handler.
