Spec 057 Status: Draft Size: Small Priority: P3 Domain: Commerce / Reporting

Margin & profit report — revenue vs. COGS vs. target margin

The profit-report moment that closes the operations-manager's day: put actual sales revenue next to what the food cost to make, and flag where next week's plan needs adjusting. This spec is a thin read / reporting layer plus one tiny additive schema change. It sits on the Spec 050 keystone (recipes) and its cost rollup Spec 051, and reads revenue straight from the Order spine / Spec 042 charge data. Everything lives in Aonik.Commerce and references only SharedKernel + Aonik.Ordering — never Aonik.Finance. This is the last spec of the maker-operations family (050–057); nothing depends on it.

1. Summary

The maker-operations family (050–057) has taught AONIK what a product is made of (050), what it costs to make (051), how much raw material is on hand (052), how to reorder and receive (053/054), and how to plan and run production (055/056). The last question the operations manager asks each week is: did we make money, and on what?

This spec answers it with a single read service, IMarginReportService, that for a date window computes — per ProductVariant and in aggregate — revenue (from ProductPurchase order lines), COGS (the Spec 051 standard-cost rollup times the quantity sold), the resulting gross margin and margin percentage, and a variance flag against a target margin. The only persisted change is one additive nullable column, TargetMarginPct, on the existing Spec 042 Product.

Success signals An operator (or the commerce-agent) can ask "how did last week look?" and get a per-dish profit table — revenue, food cost, gross margin, margin %, and a red flag on any variant below its target — plus the aggregate for the window. Setting a target margin on a product records an AiRun. dotnet build Aonik.sln stays green with Aonik.Commerce referencing only SharedKernel + Aonik.Ordering; dotnet test Aonik.sln stays green with unit tests covering revenue aggregation, COGS valuation, margin/variance, and the no-target and no-recipe edge cases.

2. Context & motivation

In the day-in-the-life that drives this family, the operations manager ends the loop by reviewing a profit report: they compare the actual food cost of what was sold to the target margins they set, and decide where next week's plan needs adjusting — drop a low-margin dish, reprice it, or renegotiate an ingredient. That decision closes the loop back to production planning (Spec 055) and, ultimately, to updating ingredient costs (Spec 051).

Every input already exists. Revenue is captured by the Order spine at checkout — Spec 042 records the funded, discounted total as a durable OrderChargeSummary (see §8). Food cost is the standard cost Spec 051 rolls up from the recipe. So the profit report is a projection over data AONIK already holds: this spec adds no ledger, no new money movement, and (bar one nullable column) no new schema — just the read service that joins revenue to cost per variant and measures it against a target.

Scope discipline: this is standard-cost margin, not managerial accounting. Actual (goods-receipt-valued) COGS, labour/overhead, period-close snapshots, and margin sliced by channel or customer tier are noted under Open, not built.

4. Scope (in / out)

In scope

  • IMarginReportService: for a window, per ProductVariant and aggregate — revenue, COGS, gross margin, margin %, and target-variance flag.
  • Revenue from ProductPurchase order lines using the Spec 042 OrderChargeSummary discounted total, read via the Ordering/charge data (no Finance reference).
  • COGS = RollupStandardCostAsync(variant, currency, atUtc) (Spec 051) × quantity sold in the window.
  • One additive nullable column TargetMarginPct on the existing Product entity; a set-target write path.
  • A read endpoint (get margin report for a window) + commerce_get_margin_report read tool and commerce_set_target_margin medium tool.
  • One tool-generated migration (CommerceTargetMargin) adding the single column.

Out of scope

  • Actual (goods-receipt-based) COGS — valuing sold quantity at real received cost (Spec 054 lots) rather than standard cost. v1 is standard-cost; noted Open.
  • Labour & overhead beyond food cost — v1 margin is food-cost margin only.
  • Period close & snapshotting a report as an immutable artefact; v1 recomputes live from current cost + order data.
  • Margin sliced by category / channel / customer tier, and linking a margin variance back to a Spec 055 plan adjustment — noted Open.
  • A separate ProductMarginTarget entity — v1 uses the column on Product; the richer entity is Open.

5. Constraints & guardrails

  • No reference to Finance. Revenue is read from the Ordering spine (ProductPurchase lines + OrderChargeSummary), not from the ledger. Aonik.Commerce still references only SharedKernel + Aonik.Ordering (ADR-005).
  • Revenue is the discounted total. The report uses the funded amount from OrderChargeSummary (subtotal − discount, per Spec 042 §17), never gross list price — so margin reflects what the customer actually paid (§8).
  • COGS is standard cost. v1 values sold quantity at the Spec 051 rollup, not receipt-based actual cost, keeping revenue/COGS timing honest without lot valuation (§9, Risks).
  • Read-only bar one column. The service computes and returns DTOs; the only mutation is setting Product.TargetMarginPct. No new money movement, no ledger, no OrderChargeSummary writes.
  • Single migration stream. The one additive column is EF-CLI-generated against AonikDbContext; Ank table; CommerceDbContext is runtime scoping with no migrations; agents never hand-author migrations.
  • Agents propose; systems execute. The margin report is a direct read tool; setting a target margin is a medium write (in-session confirmation, args-hash-bound); every AI action records an AiRun.

7. Domain model

No new persisted entity. The one schema change is a nullable column on the existing Spec 042 Product; everything else is computed DTOs returned by the service. 

// EXTEND — Spec 042 catalog entity, anemic, ITenantScoped, AuditableEntity
class Product { /* …existing Spec 042 fields… */
                decimal? TargetMarginPct;   // NEW — target gross-margin %, null = no target set
              }

// Computed DTOs (not persisted)
record MarginReportRow  { Guid ProductVariantId; string VariantName;
                          decimal QuantitySold; string Currency;
                          decimal Revenue;        // discounted total, from OrderChargeSummary
                          decimal? Cogs;          // RollupStandardCost × QuantitySold; null ⇒ COGS unknown
                          decimal? GrossMargin;   // Revenue − Cogs (null when Cogs unknown)
                          decimal? MarginPct;     // GrossMargin / Revenue (null when Revenue = 0 or COGS unknown)
                          decimal? TargetMarginPct;
                          bool    BelowTarget;    // MarginPct < TargetMarginPct
                          bool    CogsKnown;      // false ⇒ no recipe / no component cost — excluded from aggregate
                          bool    IsBundle; }     // true ⇒ bundle line; Revenue/Cogs are component-expanded (§8)

record MarginReport     { DateTime FromUtc, ToUtc; string Currency;
                          IReadOnlyList<MarginReportRow> Rows;   // both aggregated and unknown-COGS rows
                          decimal TotalRevenue, TotalCogs, TotalGrossMargin;   // COGS-known rows only
                          decimal? AggregateMarginPct;
                          decimal UnknownCogsRevenue; }   // revenue on rows excluded for unknown COGS

Cogs, GrossMargin, and MarginPct are all nullable because a variant with sales but no computable cost (no active recipe, or a component with no active cost) must be surfaced as a diagnostic rather than a misleading zero (§9): its CogsKnown = false row is excluded from the aggregate, never counted as zero cost. IsBundle marks build-your-own-box lines, whose revenue and cost are attributed by expanding the chosen components (§8). TargetMarginPct lives on Product (not ProductVariant): a target is a product-level commercial intent, and the row carries the resolved value so callers need not re-join.

8. Revenue source (reusing OrderChargeSummary)

Revenue is read from the Order spine, not the ledger — keeping the Commerce/Finance boundary intact. For each ProductPurchase order whose fulfilment falls in the window, the service reads the line-level goods (OrderItem.ProductId / variant, Quantity) and the order's durable OrderChargeSummary — the record Spec 042 §17 persists at checkout capturing subtotal → discount → tax → payable, funded via the PaymentIntent.

Decision Revenue uses the discounted total from OrderChargeSummary (subtotal minus discount), not gross list price. That is the amount actually funded, so margin reflects what the customer paid. Where a whole-order discount spans multiple lines, it is apportioned to each variant pro-rata by line subtotal, so per-variant revenue sums to the order's discounted total.

Tax is excluded from margin revenue (tax is a pass-through liability, not the maker's income). The read goes through the Ordering read surface — no Aonik.Finance reference and no ledger query, per §5.

Decision Bundle lines must be detected, not silently mis-joined. Per Spec 042 §12 (Option A), a build-your-own-box sale stores OrderItem.ProductId = the bundle Product id (Kind = Bundle), not a variant, with the chosen contents in OrderBundleSelection rows — so the report's ProductId → ProductVariant → Recipe join will not resolve for a bundle line. When a line's ProductId resolves to a Product with Kind = Bundle (or fails variant resolution), the service expands its OrderBundleSelection component rows — attributing the line's discounted revenue across components pro-rata by component value and valuing each at its Spec 051 rollup — so bundle revenue/COGS group by real recipe rather than dropping or mis-joining. v1-minimum fallback: if component expansion is not yet wired, a bundle line is excluded and flagged (CogsKnown = false), never silently attributed to the bundle id. Component-level attribution detail is Open.

9. COGS from standard cost (Spec 051)

Cost of goods sold is standard cost: for each variant sold in the window, the service calls the Spec 051 rollup and multiplies by the quantity sold.

for each ProductVariant sold in [FromUtc, ToUtc): qty = Σ OrderItem.Quantity (ProductPurchase lines, fulfilment in window) unitCogs = IProductCostingService.RollupStandardCostAsync(variantId, currency, atUtc) = Σ (RecipeComponent.Quantity × active IngredientCost.UnitCost) // Spec 051 Cogs = unitCogs unknown ? null : unitCogs × qty // no recipe / no component cost ⇒ CogsKnown = false GrossMargin = Cogs is null ? null : Revenue − Cogs MarginPct = (Revenue = 0 || Cogs is null) ? null : GrossMargin / Revenue BelowTarget = TargetMarginPct is set && MarginPct is set && MarginPct < TargetMarginPct // rows with CogsKnown = false are surfaced but EXCLUDED from TotalCogs / AggregateMarginPct

If a variant has no active recipe (or a recipe component with no active cost — reusing the Spec 050/051 "no recipe / no cost" diagnostic), the rollup yields no cost. The row then sets CogsKnown = false with Cogs left null (not zero) and is surfaced as "COGS unknown", so the operator sees "cost unknown — define a recipe" rather than a phantom 100% margin. Such a row is excluded from the aggregate — its revenue is reported under UnknownCogsRevenue so coverage gaps are visible — and never folded into TotalCogs or AggregateMarginPct as zero cost, which would inflate reported profit. To keep revenue and cost on the same footing, COGS values the quantity sold in the window at standard cost (a documented choice; see Risks for the timing nuance vs. actual receipt cost).

10. Target margin & variance

A Product may carry a target gross-margin percentage (TargetMarginPct, nullable). The report resolves it onto each variant row and sets BelowTarget = true when the achieved MarginPct falls below it — the single signal the operator scans to decide what next week's plan must change. A null target means "no target set": the row still reports achieved margin but is never flagged. Setting the target is the only write in this spec (commerce_set_target_margin, medium; §11), recorded as an AiRun. A separate ProductMarginTarget entity — with effective dates or per-channel targets — is deferred (Open); v1 keeps one current target on the product.

11. The profit-report projection

The whole spec is one projection over data AONIK already holds — revenue from the spine, cost from the rollup, target from the product — assembled per variant and summed:

IMarginReportService.GetMarginReportAsync(fromUtc, toUtc, currency) → gather ProductPurchase lines fulfilled in the window (Ordering spine + OrderChargeSummary) → detect bundle lines (ProductId → Product.Kind = Bundle) → expand OrderBundleSelection components → per ProductVariant: QuantitySold, Revenue (discounted, apportioned) → value each at RollupStandardCostAsync → Cogs, GrossMargin, MarginPct (CogsKnown = false ⇒ excluded) → resolve Product.TargetMarginPct → BelowTarget flag → MarginReport { Rows[], TotalRevenue, TotalCogs, TotalGrossMargin, AggregateMarginPct, UnknownCogsRevenue } "Last week: jollof sold 40 @ discounted revenue, food cost from recipe → 68% margin (target 70% ⇒ below); steak 30 → 55% margin (target 50% ⇒ ok); aggregate 62%."

The projection is pure and read-only: it computes from current cost and order data on demand and persists nothing (period-close snapshotting is Open). Every downstream artefact the operator sees — the per-dish table, the aggregate, the below-target flags — is a view of this one call.

13. CommerceDbContext & migrations

No new table — only one additive nullable column, TargetMarginPct, on the existing AnkProducts table, mapped in ProductConfiguration and created by one EF-CLI migration against AonikDbContext. No new DbSet is required (the column rides the existing Product mapping, already present on both CommerceDbContext and AonikDbContext). The migration is reviewed to confirm it contains that single column and nothing else.

19. Decisions baked in

  • Margin report is a live read projection over data AONIK already holds — no ledger, no new money movement, no snapshot.
  • Revenue = discounted total from OrderChargeSummary (Spec 042), read via the Ordering spine — never a Finance ledger query.
  • COGS = standard cost (Spec 051 rollup) × quantity sold; actual receipt-cost valuation is deferred.
  • Target margin is a nullable column on Product, not a new entity; variance is a single BelowTarget flag.
  • Grow in place in Aonik.Commerce; no Finance reference; the one migration stays with AonikDbContext.
  • Read tool direct; set-target medium; every AI action records an AiRun.

20. Open design decisions

Open Actual (goods-receipt-based) COGS. Valuing sold quantity at real received cost from Spec 054 lots (FIFO/average) instead of standard cost, giving a true-cost margin and a purchase-price-variance line. v1 is standard-cost; the DTO leaves room for an ActualCogs column alongside Cogs.
Open Labour & overhead. Extending margin beyond food cost to include prep labour and fixed overhead allocation (a fully-loaded contribution margin). Not in v1; would decorate the COGS term.
Open Period close & snapshotting. Persisting a report as an immutable, dated artefact (so a closed week doesn't move when costs later change) vs. always recomputing live (v1). A MarginReportSnapshot entity would land here.
Open Bundle-component margin attribution. How a build-your-own-box line's discounted revenue is split across its OrderBundleSelection components — pro-rata by component standard cost, by component list price, or by an explicit bundle-tier weighting — and whether the bundle itself is also reported as a rolled-up row alongside its components. v1 expands components (or, at minimum, excludes and flags the line, §8); the exact split key and whether to surface the parent bundle row land here.
Open Slicing & separate target entity. Margin sliced by category / sales channel / customer tier, and a richer ProductMarginTarget entity (effective-dated, per-channel targets) instead of the single TargetMarginPct column.
Open Closing the loop to planning. Linking a below-target margin variance back to a concrete Spec 055 plan adjustment (drop / reprice / re-source a dish), so the profit report drives next week's production sheet rather than just reporting last week's.
