AI route-policy cost governance & model fallback

Defines the enforcement semantics for two governance controls that #116 removed from AiRoutePolicy because they were displayed but never applied — a per-tenant AI spend ceiling and a model fallback chain. This is a design-only spec: it settles the unit / scope / window / action / trigger questions that blocked implementation, and lays out a phased build, but nothing here ships until there is a concrete need. Companion to ADR-012, which records the load-bearing decisions.

Why design-first, not build-now
There is no consumer today, no spend-accounting subsystem, and — until ADR-012 — no agreed semantics. Building now would re-create the “bolted on with guessed semantics” failure the split from #116 set out to avoid. Closing the issue would discard real analysis. This spec is the middle path: the design is complete and reviewable, so a future implementer resumes from a contract rather than a blank page.

1 · Background — what #116 removed and why

AiRoutePolicy carried CostCeiling and FallbackModelIdsJson columns that the admin UI rendered and persisted but that no code path ever read. An operator could set a ceiling, believe spend was capped, and be wrong — a control that is worse than its own absence because it manufactures false confidence. #116 (M3) removed both columns; the removal was behaviour-preserving precisely because nothing consumed them. The enforcement ambition moved here.

Two capabilities are genuinely missing — this is why enforcement is a feature, not a wiring fix:

  • Spend accounting. A budget is meaningless without a running tally. Today AiRun.CostEstimate records cost after a call; there is no pre-flight estimate and no per-scope accumulator to compare against a ceiling.
  • An ordered resolution contract. IAiModelResolver.ResolveModelNameAsync returns a single model name. Fallback needs a chain, runtime-failure detection, and bounded retry — which ripples to every call site that resolves a model.

2 · Cost ceiling semantics

The five questions #215 flagged, answered. These are binding on any implementation.

2.1 Unit — a monetary budget, never tokens or per-request

The ceiling is a USD amount over a window (e.g. $250 / month). A token count would not compose across models with different per-token pricing, and a per-request cap governs the wrong thing (a thousand cheap calls can cost more than one expensive one). Cost is the unit operators reason about, so cost is the unit.

2.2 Scope — per-tenant primary, per-policy optional

The tenant is the enforcement boundary: it is the billing and isolation boundary, and AI spend is a tenant-level cost. A route policy MAY additionally carry its own sub-ceiling (e.g. “the summarisation policy may not exceed $50/mo even if the tenant budget has room”), checked in addition to the tenant budget — the stricter of the two wins. There is no separate per-use-case scope; use-cases are already expressed as route policies.

2.3 Window & reset — rolling calendar month, UTC

The tally is a persisted counter keyed (tenantId, "yyyy-MM") — and (routePolicyId, "yyyy-MM") for policy sub-ceilings — incremented atomically (a DB-level UPDATE … SET spent = spent + @est, not read-modify-write, so concurrent AI calls cannot under-count). A new month key is a fresh $0 bucket; no cron reset job is needed. Calendar month (not rolling-30-day) aligns with how operators and billing think about budgets.

2.4 Estimation — conservative pre-flight, reconciled post-hoc

Charge before, correct after
Pre-flight: estimate = max(estimatedInputTokens × modelInputPrice, floor), drawn from the existing AiCostCatalog pricing table. This is a deliberate upper bound reserved against the tally before the call, so an in-flight burst cannot blow the budget. Reconciliation: when the call completes, the true AiRun.CostEstimate replaces the reserved estimate, so the tally self-corrects (over- and under-estimates wash out). Output-token cost is only known after completion, hence the reserve-then-true-up shape.

2.5 Action at ceiling — configurable, defaults to fail-open

Each policy declares one of three actions for “budget exhausted”:

  • AlertOnly — emit a MoneyActionLog entry + a metric, and proceed. Observability without blocking. This is the default.
  • Downgrade — drop to the next model in the fallback chain (§3) if one exists; otherwise degrade to AlertOnly. Spend control without an outright outage.
  • Reject — fail the call with a typed AiBudgetExceededException (surfaced as a 402/429-class error to the caller). A hard cap.
Why default to AlertOnly
Blocking a tenant’s AI because a spend threshold was crossed is a decision with real user-facing consequences. It must be an opt-in operator choice, not a platform default — the safe default is to stay available and make the overage visible. This mirrors the platform’s general fail-open-but-audited posture for non-money-movement actions.

3 · Model fallback semantics

3.1 Contract — an ordered chain, additively

Add IAiModelResolver.ResolveModelChainAsync(useCase, ct) → IReadOnlyList<string> — primary first, then the policy’s fallbacks. The existing ResolveModelNameAsync becomes a thin wrapper returning chain[0], so every current call site is unchanged and only failover-aware callers opt into the chain. The chain is sourced from the re-introduced FallbackModelIdsJson on the matched route policy.

3.2 Triggers — advance only on transient/config failures

Advance to next modelTerminal (surface the error)
Model inactive / unknown id (config error)Content-policy / safety rejection
Provider rate-limit (HTTP 429)Authentication / authorization failure
Timeout (per-attempt deadline)Malformed-request / 400-class
Transient overload / 5xxA valid response the caller simply did not want

The distinction is “would a different model plausibly succeed?”. A 429 or timeout: yes. A content rejection or an auth failure: no — retrying elsewhere just wastes latency and hides the real cause.

3.3 Retries — bounded, ordered, capped

Each model in the chain is tried once, in order, under a per-attempt timeout. Total attempts are capped (default 3) even if the chain is longer, to bound tail latency — a request should not walk a ten-model chain. A short backoff applies to 429 only (not to config/timeout, which will not self-heal in milliseconds).

3.4 Audit — record the model that actually served

AiRun gains ResolvedModelId (the model that produced the response) alongside the requested id, plus a FallbackReason when they differ. Every downgrade is then visible in the AI trace explorer. The trace name is unaffected — it is still driven by the aonik.use_case stamp, per the existing dedupe convention, so a fallback never leaks a model id as the trace name.

4 · Data model & contract changes

Re-introduced on AiRoutePolicy (via a tool-generated migration, only when Phase 1 lands):

  • CostCeiling — decimal? (USD; null = no ceiling)
  • CostCeilingAction — string enum (AlertOnly | Downgrade | Reject)
  • FallbackModelIdsJson — string (ordered JSON array of model ids)

New:

  • AiSpendCounter — (TenantId, RoutePolicyId?, PeriodKey "yyyy-MM", SpentUsd, UpdatedAt), unique on (TenantId, RoutePolicyId, PeriodKey), atomic increment. Per-tenant by default; a platform-wide budget would make it a global/system entity per the tenancy rules.
  • AiRun.ResolvedModelId + AiRun.FallbackReason (both nullable).
  • IAiBudgetService — TryReserveAsync(scope, estimate) / ReconcileAsync(runId, trueCost).
  • AiBudgetExceededException (SharedKernel abstractions), mapped to a typed HTTP problem.
Admin UI re-exposure gate
The three policy columns are re-shown in the admin UI only after they are enforced (Phase 1+). “Displayed but inert” — the exact defect #116 removed — must never recur.

5 · Phased build (when the need lands)

Phase 1 — Cost ceiling, AlertOnly

The whole accounting spine with zero user-facing risk.
Re-add the columns; add AiSpendCounter + IAiBudgetService; wire pre-flight reserve + post-hoc reconcile into the AI middleware; emit MoneyActionLog on breach. Ship with AlertOnly only — nothing blocks, but spend is now tracked and overages are visible. Re-expose CostCeiling in the UI.

Phase 2 — Fallback chain

Additive contract; independent of cost accounting.
Add ResolveModelChainAsync + the retry/trigger loop; add AiRun.ResolvedModelId/FallbackReason; re-expose FallbackModelIdsJson. Can land before or after Phase 1.

Phase 3 — Enforcing actions

Turn on the teeth, deliberately.
Enable Downgrade (depends on Phase 2’s chain) and Reject (typed exception + caller contract). Per-policy opt-in; the platform default stays AlertOnly.

6 · Explicitly out of scope

  • Any implementation. This spec ships no code, no migration, no columns. It is a contract.
  • Cross-provider price arbitrage / automatic cheapest-model selection — a different, larger problem.
  • Streaming mid-response fallback (once tokens are streaming, we do not switch models mid-flight).
  • Budget alerting UI / email — Phase 1 emits metrics + MoneyActionLog; dashboards are downstream.

7 · Acceptance

This design-only deliverable is complete when:

  • ADR-012 + this spec define unit, scope, window, estimation, ceiling action, fallback triggers, retry bound, and the audit fields — done.
  • #215 is updated to reference them and moved to “design-complete, implementation-pending” (kept open, not closed).

A future implementation PR (not this one) is accepted when it enforces a ceiling with a real spend tally and executes the fallback chain, with tests, honouring the semantics above — re-introducing the columns via a tool-generated migration at that point.
