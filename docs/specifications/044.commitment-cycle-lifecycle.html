Spec 044 Status: Draft (Rev 1) Size: Large Priority: P1 (Simi M2 spine) Domain: PersonalFinance / Simi

Commitment cycle lifecycle & rhythm

Extends Spec 019 so a user can author a recurring support commitment ("Mum — monthly allowance, £200, due the 28th"), attach it to a CareEntity, and run a real per-cycle lifecycle on it: mark a cycle done (which records a payment and rolls the due date forward), skip it, snooze it, pause it — with a visible per-cycle history. Today the commitment surface does manual create and detection verification only; it has no cycle state machine, no anchor-day / termly rhythm, and no CareEntity link. Implements Simi readiness plan §5.2.

Spec family (043–048) Depends on Spec 043 (the CareEntity a commitment belongs to) and on Spec 045 (mark-done writes a PaymentLog). Both, with this spec, form the Simi M2 "spine."

1. Summary

Simi's spine is the daily loop: glance at what needs you, act elsewhere (pay by bank/Wise/cash), then capture that you did it — which rolls the commitment forward and ticks the year total. Spec 019 gave us a unified read model over three entities (Bill, Subscription, DebtRepayment) and a detection verification flow (confirm / reject a recurring pattern the system noticed in bank transactions). What it does not have is the half Simi lives on: a user-authored support commitment, attached to a person or asset, with a rhythm rich enough for "monthly on the 28th" and "each school term," and a cycle lifecycle that advances the due date when a cycle is handled and records honest history when it is skipped.

This spec adds that, additively, on the existing entities — no new commitment table, one new history table.

Success signals Fola creates "Mum — monthly allowance, £200, anchored to the 28th," linked to the "Mum" CareEntity. On the 28th it shows on Today as due. She marks it done with a receipt: a PaymentLog is written, the cycle is recorded Paid, the next due rolls to 28 July, and a reminder re-arms three days out. A school-fees commitment uses a termly rhythm with explicit dates. When she skips a cycle, the timeline shows it as Skipped — and the "never missed" line only appears when it is true.

2. Problem & current state

Confirmed against the tree:

  • Two "bill" entities exist — and the manual-create path feeds the wrong one. The module has a legacy Bill (Payee, free-string Frequency, NextDueDate, LinkedInvoiceId/LinkedOrderId) and the commitment-bearing PersonalRecurringBill (VerificationStatus, Origin — documented values Manual | Detected | PromotedFromTransaction | Imported — ConfidenceScore, nullable SourceTransactionId, ReminderDaysBefore). POST /personal-finance/bills → BillService.CreateBillAsync creates the legacy Bill, which is not part of the commitment projection: CommitmentService.ProjectBills reads Set<PersonalRecurringBill>() (projected as CommitmentType = "Bill"), and a PersonalRecurringBill is created today only by detection or by CreateFromTransactionAsync (promotion). There is no user-authored create for any commitment-projected entity.
  • The service does verification, not cycles. ICommitmentService exposes ListCommitments, GetCommitment, CreateFromTransaction, ConfirmDetected, RejectDetected, ListDetected — and nothing else. There is no mark-done / mark-paid / complete / skip / snooze / advance anywhere. PersonalRecurringBill.NextDueDate is set once and never rolls forward; LastPaidAt/LastPaidAmount are scalars overwritten in place.
  • Rhythm is a free string. Frequency is text (Daily…Annually); the monthly-amount estimator has no Termly case and there is no anchor-day ("the 28th") and no roll-forward date math anywhere.
  • No per-cycle history. Two "last paid" scalars cannot represent "paid in May, skipped in June, paid in July" — required for the detail timeline and the streak/"never missed" mechanic (rebuild spec §7.3).
  • No CareEntity link. A bill has a Payee string + PaidFromAccountId; it cannot yet point at the person or asset it is for (Spec 043).

3. Scope (in / out)

3.1 In scope

  • Edit Widen the commitment: a Support kind, a CareEntityId link, structured rhythm fields, a configurable reminder offset (§4).
  • New A Rhythm value object + roll-forward math (anchor-day clamp, termly explicit dates) in one tested place (§5).
  • New A CommitmentCycle per-cycle history record (§6).
  • New Lifecycle operations: mark-done, skip, snooze, pause/resume on ICommitmentService + endpoints (§7–8).
  • Edit Reminder re-arm on roll-forward / snooze; per-commitment configurable lead (§10).

3.2 Out of scope

  • Money movement. Mark-done records that the user paid elsewhere; it never initiates a payment. The PaymentLog it writes is record-keeping (Spec 045).
  • FX. Amounts keep their original currency; no conversion (Spec 043 §9).
  • The detection engine itself. The existing Detected → Confirm/Reject flow is untouched; this spec coexists with it (§9). Plaid-driven auto-capture of a cycle is a fast-follow (Spec 045 § corroboration).

4. The commitment, widened extend

Per readiness Decision D2, we extend the existing PersonalRecurringBill rather than add a parallel entity, so the Spec 019 unified Commitment read model keeps projecting one shape. New columns (all nullable / defaulted, so detected bills are unaffected): 

// additions to PersonalRecurringBill (Entities/PersonalFinance/PersonalRecurringBill.cs)
public Guid?   CareEntityId    { get; set; }   // FK → CareEntity (Spec 043); null for legacy detected bills
public string  CommitmentKind  { get; set; } = "Bill";   // Bill | Subscription | DebtRepayment | Support  ← new value
public string  RhythmUnit      { get; set; } = "Monthly"; // Weekly|Monthly|Quarterly|Termly|Yearly|OneOff
public int     RhythmInterval  { get; set; } = 1;          // every N units
public int?    AnchorDay       { get; set; }               // day-of-month for monthly rhythms ("the 28th")
public string? TermDatesJson   { get; set; }               // explicit dates for Termly / OneOff (no auto-roll)
// ReminderDaysBefore already exists — now honoured per-commitment (§10); default 3 for Support

Support is the Simi-native kind — allowances, school fees, upkeep, an asset's service charge — that carries a CareEntityId and a structured rhythm. The legacy Frequency string is kept and populated (mapped from RhythmUnit×RhythmInterval) so the existing read model and estimator keep working; new code reads the structured fields. The legacy Bill entity behind /personal-finance/bills — a separate table outside the commitment projection (§2) — is left untouched. The unified CommitmentDetail projection gains CareEntityId, CommitmentKind, and a derived RhythmLabel ("Monthly · 28th", "Each term").

5. Rhythm & roll-forward new

All next-due arithmetic lives in one tested value object, never scattered across services (it is the most error-prone surface in the spine — readiness risk #2): 

// DateTime with date-only semantics — the codebase convention (src has zero DateOnly usage;
// NextDueDate on the entity is DateTime).
public sealed record Rhythm(string Unit, int Interval, int? AnchorDay, IReadOnlyList<DateTime>? TermDates)
{
    // Returns the next due date strictly after `from`, or null for OneOff with no further date.
    public DateTime? NextAfter(DateTime from);
    //   Weekly/Monthly/Quarterly/Yearly → from + Interval units, clamping AnchorDay to month end
    //                                       (29–31 → last day of a short month)
    //   Termly / OneOff                 → the next explicit date in TermDates (no computed roll)
}
UnitRoll ruleExample
Monthly (+ AnchorDay)Same day-of-month each interval; clamp 29–31 to month end (28th stays 28th; 31st → 30 Jun / 28 Feb).£200 on the 28th
Weekly / Quarterly / Yearlyfrom + Interval × unit.Quarterly service charge
TermlyNo computation — the next explicit date in TermDates (school terms are irregular).School fees, 3 terms/yr
OneOffNo roll — completes and closes after one cycle (the plumber).A one-time repair

6. CommitmentCycle entity new

Per readiness Decision D3, an explicit per-cycle record — the only honest way to represent "paid / skipped / snoozed" history and compute "never missed." A new tenant + user scoped entity: 

public class CommitmentCycle : AuditableEntity, ITenantScoped
{
    public Guid    TenantId     { get; set; }
    public Guid    UserId       { get; set; }
    public Guid    CommitmentId { get; set; }   // → PersonalRecurringBill.Id
    public DateTime DueDate     { get; set; }   // date-only semantics (DateTime, per codebase convention)
    public string  Status       { get; set; } = "Open"; // Open | Paid | Skipped | Snoozed
    public Guid?   PaymentLogId { get; set; }   // set when Paid (Spec 045)
    public string? SkipReason   { get; set; }
    public DateTime? SnoozedUntil { get; set; }
    public DateTime? ResolvedAt { get; set; }
}

At most one Open cycle per commitment at a time (the current one). Resolving a cycle (paid/skipped) opens the next via Rhythm.NextAfter; a OneOff closes with no successor. The detail timeline and the "Since Jan 2026: …, never missed" footer read straight off this table.

7. Lifecycle operations new

New methods on ICommitmentService (the verification methods stay):

OperationEffect
MarkDoneAsync(id, PaymentLogDraft)Write a PaymentLog (Spec 045) for this entity/commitment in original currency; set the current cycle Paid + link PaymentLogId; compute next due via Rhythm; open the next cycle; re-arm the reminder (§10). The signature-animation + year-total tick are client-side off this result.
SkipCycleAsync(id, reason?)Set the current cycle Skipped (with optional reason, visible history); advance to the next cycle; re-arm.
SnoozeAsync(id, until)Reschedule the current cycle's reminder (3 days / to payday / a picked date) without resolving it; record SnoozedUntil; re-arm the WorkItem.
PauseAsync(id) / ResumeAsync(id)Set Status = Paused (no reminders fire) / back to Active and re-arm from today.
Idempotency & honesty Mark-done is idempotent per cycle (a second mark-done on an already-Paid cycle is a no-op, not a double log). Skip records a real skipped row — the timeline never silently hides a missed cycle. Editing a commitment never rewrites past cycles (rebuild spec §7.4): history is append-only; archive hides the commitment but preserves its cycles.

8. API surface

Customer-scoped (UserPolicy), under the existing /personal-finance/commitments prefix:

RouteVerbPurpose
/personal-finance/commitmentsPOSTAuthor a Support commitment (CareEntityId, rhythm, reminder offset) — the first manual-create path for a commitment-projected entity (the legacy /bills create feeds the separate legacy Bill, outside the projection — §2).
/personal-finance/commitments/{id}PUTEdit (never rewrites history).
/personal-finance/commitments/{id}/donePOSTMark the current cycle done (body = payment-log draft).
/personal-finance/commitments/{id}/skipPOSTSkip the current cycle (optional reason).
/personal-finance/commitments/{id}/snoozePOSTSnooze the reminder (to a date / payday).

Each new request DTO ships a Validator<T> (build-time enforced by RequestDtoValidatorCoverageTests). MarkDoneRequest carries the PaymentLogDraft shape (amount + currency, date, channel, optional receipt document id, note — Spec 045).

9. Coexisting with detection (Spec 019)

The two paths share one entity and read model but never collide:

  • Detected commitments (Origin = Detected or PromotedFromTransaction, VerificationStatus = Detected) keep their Confirm/Reject flow untouched. On confirm, a detected bill may be promoted to carry a CareEntity + structured rhythm (optional, user-driven).
  • Support commitments (CommitmentKind = Support, Origin = Manual) are born Confirmed and run the cycle lifecycle from creation.
  • The unified CommitmentDetail projection carries both; the "Detected" section of the mobile list only shows VerificationStatus = Detected rows (rebuild spec §7.2), so support commitments never appear there.

10. Reminders & re-arm extend

The pipeline exists end to end: the SharedKernel ITaskService.ScheduleAsync(ScheduleTaskRequest) persists a Platform WorkItem, WorkItemDispatchJob dispatches due items every minute, and NotifyUserTaskActionHandler turns TaskActionTypes.NotifyUser into a notification + push (Spec 034 / Spec 016). But its only consumer in this module is the legacy-Bill create: BillService.ScheduleDueReminderAsync arms a one-off reminder (ReminderLeadDays = 14, SubjectType: "Bill", Spec 034 scenario 9.1). PersonalRecurringBill.ReminderDaysBefore is stored but nothing schedules from it — the commitment path arms no reminder today (CommitmentService has no ITaskService reference). Three changes:

  • Arm on create. Authoring a Support commitment schedules its reminder via ITaskService.ScheduleAsync (SubjectType: "Commitment"), honouring the existing ReminderDaysBefore column — default 3 for Support, matching the first-run "reminds 3 days before" (the legacy Bill path keeps its 14).
  • Re-arm on transition. MarkDone / Skip (new due date) and Snooze (new reminder time) re-arm via ITaskService.ListForSubjectAsync("Commitment", id) → CancelAsync → ScheduleAsync off the new date. This is the missing half the readiness review flagged — the reminder must follow the cycle as it advances, or it fires for a cycle already handled. (PauseAsync / ResumeAsync on the task mirror commitment pause/resume.)
  • Out of scope here. Quiet-hours / digest bundling are a cross-cutting reminder concern tracked in the readiness plan (Phase E), not duplicated per-spec.

11. Persistence & migration

  • Columns added to PersonalRecurringBill (CareEntityId, CommitmentKind, RhythmUnit, RhythmInterval, AnchorDay, TermDatesJson) — all nullable/defaulted so existing rows are valid unchanged.
  • New table CommitmentCycle → dbo.AnkCommitmentCycles via MapFinanceTable (AonikDbContext) + MapTable (PersonalFinanceDbContext); DbSets on both contexts (every new DbSet lives on the canonical AonikDbContext, CLAUDE.md); IEntityTypeConfiguration with an index on (TenantId, CommitmentId, Status).
  • Backfill (one-time, an idempotent startup/seed task — never hand-edited migration SQL, per CLAUDE.md): for each active commitment with no open cycle, open one at its current NextDueDate so existing detected/promoted commitments enter the lifecycle cleanly.
  • Tool-generated migration only against AonikDbContext (CLAUDE.md). Review that it contains exactly the new columns + the new table.

12. Security

  • Tenant + user scoping on every query and on each lifecycle mutation; a user can only transition their own commitments and cycles.
  • UserPolicy; no admin path. The CareEntityId on write is validated to belong to the caller (no cross-user attachment).
  • Mark-done records a payment but moves no money; it is not a "money action" in the Issue #142 sense (no quote/capture/settle), so the money-action-logging convention does not apply — but the resulting PaymentLog is auditable (Spec 045).

14. Acceptance criteria

  • Author + attach. POST /personal-finance/commitments creates a PersonalRecurringBill (Origin = Manual, VerificationStatus = Confirmed) with a CareEntityId, amount+currency, a monthly rhythm anchored to the 28th, and a 3-day reminder; it appears in the unified projection with a RhythmLabel, is not in the Detected section, and no legacy Bill row is created.
  • Mark-done rolls forward. Mark-done writes a PaymentLog, sets the cycle Paid, advances NextDueDate by the rhythm (28th stays the 28th; Feb clamps), opens the next cycle, and re-arms the reminder — all asserted.
  • Anchor & termly math. A 31st-anchored monthly clamps to 30 Jun / 28 Feb; a termly commitment advances to the next explicit term date, not a computed +1 month.
  • Skip is honest. Skip records a Skipped cycle (with reason) visible in /cycles; "never missed" is false thereafter.
  • Snooze & pause. Snooze reschedules the reminder without resolving the cycle; pause stops reminders; resume re-arms.
  • Detection untouched. A detected bill still confirms/rejects exactly as before; no support commitment leaks into the detected queue.
  • Build & migration. dotnet build green; tool-generated migration adds only the new columns + AnkCommitmentCycles; backfill opens one cycle per active commitment.

15. Open decisions

  • O1 — Overdue handling: auto-advance or hold? When a cycle's due date passes unmarked, does it stay Open and overdue (shown first, danger tint) or auto-roll? Spec leans hold (an unmarked cycle stays open and overdue until resolved — honest, and matches "Needs you" sorting). Revisit if it produces reminder fatigue.
  • O2 — Partial payments. A cycle paid in two instalments (two PaymentLogs). Phase 1: a cycle is Paid when first marked done; multiple logs may reference it. A formal "partially paid" status is deferred.
  • O3 — Promote-on-confirm. Whether confirming a detected bill should offer to attach a CareEntity + structured rhythm inline. Leaning yes (cheap, improves data), but not required for M2.
