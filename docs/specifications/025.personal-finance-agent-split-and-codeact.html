Spec 025 Status: Draft Domain: Finance / Agents

Personal Finance Agent Split & CodeAct Adoption

Restructures today's monolithic personal-finance-agent ("Simi") into a user-facing orchestrator that owns most tools directly and delegates only analytical work to three CodeAct-powered sub-agents. Locks in CodeAct (via Microsoft Agent Framework + Hyperlight) as the runtime for sub-agents whose work is computational or loop-heavy.

1. Summary

Aonik runs two independent orchestrators: a master orchestrator in the Admin UI that routes operator queries across domain agents, and the personal-finance-agent ("Simi") that orchestrates the end-user experience in Payabo. This spec covers only Simi.

Today Simi is a single ChatClientAgent with ~45 PF tools attached directly plus two read-only sub-agents (pf-spending-intelligence-agent and pf-obligation-planning-agent) invoked as tools. After this change:

  • Simi keeps her persona and owns ~50 direct tools — every read, every CRUD mutation, every display widget, plus memory and navigation. Most user turns complete in 2 LLM hops (decide + reply).
  • Three new analytical sub-agents take over computational and loop-heavy work: pf-insights, pf-forecast, pf-classify. All three are read-only, CodeAct-powered, and never speak to the user directly — Simi paraphrases their structured output.
  • The two existing sub-agents retire, their scope absorbed into the new three.
  • CodeAct is adopted Day 1 for the three new sub-agents, via the Microsoft Agent Framework CodeAct pattern backed by the Hyperlight Python WASM sandbox.

Mutations stay on Simi's surface with per-call confirmAction approval — the "agents propose; systems execute" rule is preserved. CodeAct's whole-block approval semantics never trigger because the sub-agents are read-only.

2. Background

2.1 What we have today

  • PersonalFinanceAgentDescriptor (src/Aonik.Finance/Agents/PersonalFinanceAgentRegistration.cs) — Simi. AgentType Orchestrator, RequiresUserBrief = true, ~45 PF tools + account-linking + memory.
  • SpendingIntelligenceAgentDescriptor — sub-agent, single tool, returns JSON conforming to spending-intelligence.v1 schema.
  • ObligationPlanningAgentDescriptor — sub-agent, single tool, returns JSON conforming to obligation-planning.v1 schema.
  • Simi invokes the sub-agents as tools via pf_run_spending_intelligence and pf_run_obligation_planning.
  • All mutations are wrapped in ApprovalRequiredAIFunction and surface via the frontend confirmAction tool.

2.2 Problems with today's shape

  • Tool surface is too wide for one LLM call. 45+ tool schemas in a single prompt hurts tool-call accuracy and inflates input tokens on every turn.
  • Analytical questions are throttled by the tool catalogue. "What if I cut dining by 20% and delay rent?", "Walk all my subscriptions and flag drift" — these need composition + computation that no single tool exposes. The existing sub-agents punt to a single big "do everything" tool, limiting depth.
  • The mega-prompt rule. Per Cleo's multi-agent architecture writeup, "a mega-prompt that covers everything accumulates redundancy and internal conflicts." Simi's instructions today already run 120+ lines. Adding new capability means re-balancing the whole prompt.

2.3 What this spec does NOT change

  • The master orchestrator in Aonik.Agents.Framework.
  • The B2B finance-agent, financial-life-graph-agent, platform-agent.
  • The ApprovalRequiredAIFunction mechanism or the frontend confirmAction contract.
  • The User Brief injection pipeline.
  • The CustomerInsightSnapshot / CustomerInsightAiSummary background pipeline.

5. The three sub-agents

All three sub-agents follow the same shape: invoked by Simi via a tool, run inside a Hyperlight Python sandbox with a narrow whitelist of host tools accessed through call_tool(...), return structured-data-plus-narrative back to Simi, never speak to the user directly, never mutate anything. Simi paraphrases their output for the user.

6. CodeAct implementation

CodeAct lets an agent "solve a task by writing code and executing it through an execute_code tool" instead of issuing one tool call at a time. The plan runs once inside a sandbox; the underlying tools stay the same. For tool-heavy workloads this materially reduces latency and tokens.

All three Aonik sub-agents adopt this pattern via the hyperlight-dev/hyperlight-sandbox .NET SDK (v0.4.0). The SDK ships a MAF-shaped CodeExecutionTool.AsAIFunction() that drops straight into a ChatClientAgent's tool list, and bundles the Python WASM guest inside Hyperlight.HyperlightSandbox.Guest.Python so there is no separate WASM guest binary to source or package.

Spec drafted around Microsoft.Agents.AI.Hyperlight originally; that package is preview-only with no bundled guest. hyperlight-sandbox is a CNCF sandbox project from the same upstream Hyperlight team, ships its own Sandbox / RegisterTool / CodeExecutionTool surface, and resolves the guest-sourcing blocker (§11.5) in one move because the guest binary travels inside the NuGet.

6.1 Why CodeAct here

  • Loop + per-item analysis: pf-classify walks a queue of N items and scores candidates for each. With CodeAct this is one Python loop, one model hop, one audit row. Without it, the model issues N×K tool calls sequentially.
  • Parametric arithmetic: pf-forecast computes scenarios that involve multi-variable math. The LLM is unreliable at this; Python is exact. There is no tool surface design that would let us deliver this feature cleanly without code execution.
  • Dynamic composition: pf-insights needs to fetch + transform + rank in patterns we don't know in advance. CodeAct lets the model write the query rather than us pre-baking every analysis shape.

6.2 Why CodeAct is safe here (the whole-block approval issue)

CodeAct frameworks generally treat the execute_code call as a single unit of approval — if any host tool reachable from the sandbox is gated by per-call approval, that gate degrades to "approve the entire script" once it sits behind call_tool(...).

Design All three Aonik sub-agents expose only read-only host tools via call_tool. No mutating tool ever appears in a sub-agent's sandbox whitelist. The whole-block approval question therefore never arises — there is nothing to approve inside the sandbox. Mutations stay on Simi's direct surface where per-call confirmAction applies as today, preserving the "agents propose; systems execute" invariant.

6.3 Wiring (per sub-agent)

Each sub-agent's IDomainAgentDescriptor.Build() picks one of two paths based on HyperlightHostAvailability.IsAvailable. The check probes once per process: explicit AONIK_DISABLE_HYPERLIGHT=true opt-out, then OS family (Linux only at hyperlight-sandbox v0.4.0), then a real sandbox build to confirm the hypervisor is accessible (KVM in containers, MSHV on bare metal). The result is cached for the process lifetime.

Pattern (sketch — the live code lives in src/Aonik.Finance/Agents/CodeAct/): 

using HyperlightSandbox.Api;
using HyperlightSandbox.Extensions.AI;
using HyperlightSandbox.Guest.Python;
using Microsoft.Extensions.AI;

// CodeAct path — one wrapped sandbox per sub-agent invocation.
var codeTool = new CodeExecutionTool(
    new SandboxBuilder()
        .WithPythonModule()     // bundled Python WASM guest
        .WithTempOutput());

foreach (var aiFn in PersonalFinanceTools
    .CreateForInsightsSubAgent(serviceProvider).OfType<AIFunction>())
{
    // Bridge each host AIFunction to the sandbox's call_tool registry.
    codeTool.RegisterToolAsync(aiFn.Name, async json =>
    {
        var args = ParseArgs(json);
        var result = await aiFn.InvokeAsync(new AIFunctionArguments(args));
        return JsonSerializer.Serialize(result);
    });
}

var executeCode = codeTool.AsAIFunction(
    name: "execute_code",
    description: "Execute Python in a secure isolated sandbox...");

return new ChatClientAgent(
    chatClient, name: Name, instructions: InstructionsText,
    tools: [executeCode]);   // single tool: the sandbox itself

On non-Linux hosts (Windows local dev, macOS, Linux without KVM passthrough), the same Build() falls back to the conventional tool-loop path: tools: PersonalFinanceTools.CreateForInsightsSubAgent(sp).ToList(). The Phase-4 prompts say "via call_tool(...); when CodeAct is unavailable the same tools are exposed directly" precisely so a single prompt serves both paths without rework.

6.4 Lifetime & cost

v1 builds a fresh CodeExecutionTool per sub-agent invocation. Cold start is ~2.5 s; subsequent Execute() calls inside the same invocation use the automatic snapshot/restore the SDK provides (≈ 200× faster). The ~2.5 s cost is acceptable while we gather telemetry. Pooling sandboxes per sub-agent name — with a scope-bridging tool registry so request-scoped services still resolve correctly — is the natural next optimisation when usage shows it earns the complexity.

Native resources are reclaimed via the SafeHandle finalizer chain when the wrapping AIFunction becomes unreachable after the request completes. No explicit Dispose handoff is required for the per-request usage pattern.

9. Operational considerations

9.1 Deployment additions

ItemDetail

9.2 Observability

  • One AiRun record per execute_code invocation, with inner call_tool invocations recorded as child events linked to the parent. This is new schema work — see §11.
  • Per-sub-agent script source + tool-call trace stored on the AiRun record, surfaced in the existing trace explorer (App Insights pipeline). Sandbox stdout (print) optionally captured at the execute_code boundary for debugging.
  • Per-sub-agent model selection via route policy / task profile resolver (existing mechanism) — verify this still works when the agent is a CodeAct-backed ChatClientAgent.

9.3 Cost & latency expectations

  • Trivial reads: Simi handles directly. 1 LLM hop. Should be the fast majority of turns.
  • Mutation flows: Simi calls tool, framework prompts for approval, user approves, tool executes. 1 LLM hop + UI round trip for approval. Same as today.
  • Analytical turns (sub-agent invoked): 2 LLM hops on the critical path (Simi decide + Simi paraphrase), plus 1 hop inside the sub-agent for the execute_code generation. Sub-agent's inner tool calls collapse from N sequential LLM hops to 1 script execution — this is the primary CodeAct win.
  • Worst case (sub-agent + multiple Simi tool calls in the same turn): 3 LLM hops. Comparable to today's sub-agent flow (Simi → sub-agent → Simi summary).

9.4 Local dev validation (WSL2 on a Windows host)

Because the deployed ACA environments cannot host Hyperlight, the only end-to-end validation path today is local Linux. On a Windows dev box that means WSL2.

  1. Install WSL2 with an Ubuntu distro (wsl --install -d Ubuntu). Enable the Windows feature "Virtual Machine Platform" if Windows complains. WSL2 exposes /dev/kvm to its guest Linux automatically; no extra setup needed.
  2. Inside the WSL distro, install the .NET 10 SDK and node 20+ (the AdminUi front-end is part of the Aspire AppHost). Mount the repo at /mnt/c/Users/<you>/source/repos/aonik — that path is the same Windows tree, just visible from Linux, so no clone is required.
  3. Run dotnet run --project src/Aonik.AppHost from inside WSL. The AppHost orchestrates API + Worker + Admin UI + Qdrant; sub-agent invocations will hit the CodeAct path because HyperlightHostAvailability.IsAvailable returns true under WSL2.
  4. Smoke-test: open the Admin UI playground (http://localhost:<port>/ai/playground), pick the personal-finance-agent, and ask a question that should route to a sub-agent — e.g. "Why was last month tight?" for pf-insights or "Will rent be covered on the 30th?" for pf-forecast. The trace view should show one execute_code call with multiple inner call_tool invocations rather than N sequential host-tool calls.
  5. Compare the same question against the tool-loop fallback by setting AONIK_DISABLE_HYPERLIGHT=true in the AppHost environment and restarting. Same prompt should still answer correctly via N host-tool calls. This is the proof that the platform-conditional Build() covers both paths with no prompt-side divergence.

Once we have local-validation data showing CodeAct's value vs. the tool-loop fallback, we can decide whether to invest in the ACA → AKS migration (or a sidecar AKS / VM dispatcher) for the deployed environments.

11. Open decisions

Open · 11.1 Unified insights output schema. Collapsing two existing schemas (spending-intelligence.v1 + obligation-planning.v1) into one needs a unified shape that covers "explain", "audit", and "rank" without becoming a kitchen-sink type. Suggested shape sketched in §5.1; needs a schema-first design pass before implementation.
Open · 11.2 Forecast output schema. New territory. Suggested shape in §5.2; needs review with the front-end team since the options[] array drives display_option_selector labels in Simi's reply.
Open · 11.3 AiRun child events for CodeAct. Need a new audit-record shape for execute_code runs: parent AiRun + N child entries (one per inner call_tool) so the trace explorer can show what the script actually did. Tactical schema add to AonikDbContext via the canonical migration stream.
Open · 11.4 Sub-agent invocation limits per Simi turn. Should Simi ever invoke 2+ sub-agents in one turn? "How am I doing overall" plausibly wants pf-insights + pf-forecast. Simplest v1: one sub-agent per turn; revisit if user data shows we need cross-sub-agent synthesis.
Resolved · 11.5 Hyperlight guest module sourcing. Resolved by adopting hyperlight-dev/hyperlight-sandbox v0.4.0 (see §6 rewrite). The Python WASM guest ships inside Hyperlight.HyperlightSandbox.Guest.Python — no separate build artifact, no IaC plumbing, no HYPERLIGHT_PYTHON_GUEST_PATH env var. Trade-off: the SDK is Linux-only at v0.4.0 (Windows support in flight upstream), so each sub-agent's Build() is platform-conditional and falls back to the conventional tool-loop path on Windows/macOS hosts.
Open · 11.6 Per-sub-agent model. Forecast probably wants the most capable model (math reasoning); classify can run lighter; insights somewhere between. Confirm the existing route-policy / task-profile resolver supports per-sub-agent model overrides, or extend it.
Open · 11.7 UserBrief injection on sub-agents. Today Simi has RequiresUserBrief = true. Should sub-agents also receive the brief, or do they pull what they need from their own tools? Default proposal: sub-agents pull from tools; they get the user/tenant context they need from the host tool bindings, not from a brief injection.
