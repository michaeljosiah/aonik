Spec 039 Status: Draft Size: Medium Priority: P0 (launch blocker) Domain: Finance / Payments

Verify-and-register payout beneficiary flow

The missing last mile for real remittance. Today a customer can save a payout beneficiary, but the saved row is always IsVerified = false with no provider recipient id — so it can never pass the remittance gate, and the real Flutterwave connector has no payable destination. This spec adds the flow that takes the customer's raw rail details (transiently), resolves the account with the partner (best-effort name enquiry), registers a reusable recipient (e.g. Flutterwave POST /transfers/recipients → rcb_…), and persists a verified ExternalPayoutAccount (IsVerified = true, ProviderBeneficiaryId = rcb_…) — never storing the raw account number. It is the named prerequisite from Spec 037 (§7.4.1, gaps G19/G20, open decision O12), composing the connector ports already built (ResolveAccountAsync, RegisterRecipientAsync) with the existing beneficiary + party-graph plumbing.

1. Summary

Spec 037 delivered the Flutterwave connector, including RegisterRecipientAsync (mint a provider recipient id) and ResolveAccountAsync (name enquiry). But it flagged — in §7.4.1, gaps G19/G20, and open decision O12 — that the connector method is necessary but not sufficient: nothing in the app calls it, and the shipped beneficiary path can't feed it. Concretely:

  • PayoutBeneficiaryService.SaveBeneficiaryAsync persists IsVerified = false hardcoded and only copies a pre-supplied ProviderBeneficiaryId — it never resolves an account or calls a connector.
  • SavePayoutBeneficiaryRequest carries only a MaskedAccountIdentifier + optional token — never the raw account number, which the partner needs to create a recipient.
  • RemittanceOrderService rejects an unverified destination (if (!account.IsVerified) throw), so no saved beneficiary is payable.

The result: the connector works (proven against the live sandbox via a manually-seeded recipient), but real Payabo UK→NG remittance cannot launch — no self-service customer can produce a payable Flutterwave beneficiary. This spec closes that gap with one new flow.

Success signals A Payabo customer enters a Nigerian bank account (bank + account number) for a new recipient and taps Add. The server resolves the payout connector for the corridor (the real Flutterwave connector now wins capability routing), attempts a name enquiry, registers a recipient (rcb_…), and saves a verified ExternalPayoutAccount with the recipient id — no raw account number persisted anywhere. A subsequent remittance to that beneficiary passes the IsVerified gate, dispatches via recipient_id, and settles. If the partner's name-enquiry endpoint is not entitled (the sandbox returns 403), the flow still succeeds using the customer-supplied name.

3. Scope (in / out)

3.1 In scope

  • New IPayoutBeneficiaryService.VerifyAndRegisterBeneficiaryAsync + implementation: transient raw input → resolve connector → (best-effort) name enquiry → register recipient → persist a verified destination.
  • New POST /payments/payout-beneficiaries/verify FastEndpoint (AdminUserWritePolicy) + VerifyPayoutBeneficiaryRequest DTO (carries raw rail details, never persisted) + FluentValidation.
  • Edit Add a ProviderCode column to ExternalPayoutAccount (+ VerifiedAt set on verify) so a stored recipient is self-describing about its provider — with a tool-generated migration against AonikDbContext (per CLAUDE.md). Remittance dispatch routes to the destination's ProviderCode (small Spec 036 follow-up, §5.5).
  • New Caller-owns-party authorization (resolve the authenticated user's party and require it to match CustomerPartyId) — the same check RemittanceOrderService applies; closes an IDOR the save path lacks (§5.4).
  • New Best-effort name enquiry: when the partner's account-resolve endpoint is unavailable/unentitled (the sandbox returns 403), proceed with the customer-supplied name rather than failing (§5.6).
  • Edit Frontend (Payabo / Admin UI) add-beneficiary form posts raw details to the verify endpoint and shows the verified result; raw details never persisted client-side beyond the request (§5.7).
  • New Tests — service (register→persist verified; name-enquiry fallback on 403; idempotent re-verify; auth rejection), endpoint (authz/validation), and the migration applies cleanly.

3.2 Out of scope

  • Card collection / inbound. This is payout beneficiaries only.
  • The routing engine. Connector selection still rides the in-memory capability resolver (Spec 031 §3.2); this spec just consumes it.
  • Vaulting the raw value. The recipient-id flow means the raw account number is never needed again, so VaultRef stays null (no raw storage). A vault path is only needed if a connector ever requires the raw value at execution — not Flutterwave.
  • Replacing SaveBeneficiaryAsync. The masked/pre-tokenised save path stays for back-office / already-registered tokens; the verify endpoint is the new self-service path.

5. Design

5.1 The flow

Payabo add-beneficiary form VerifyAndRegisterBeneficiaryAsync (new) ─────────────────────────── ─────────────────────────────────────────── raw: bank+account / MSISDN+network ──POST──▶ 1. authz: caller owns CustomerPartyId + customer + currency + country 2. resolve connector by capability (real wins) 3. ResolveAccountAsync (name enquiry) — best-effort 403/unentitled → keep supplied name 4. RegisterRecipientAsync → ProviderBeneficiaryId (rcb_…) 5. party graph (reuse): party + edge + Beneficiary role 6. persist ExternalPayoutAccount: MaskedAccountIdentifier = mask(raw) ← raw discarded AccountName = enquiry name ?? supplied ProviderBeneficiaryId = rcb_…, ProviderCode, ConnectorId?, IsVerified = true, VerifiedAt = now ◀──────────── verified beneficiary ─────────── (the raw account number is NEVER persisted or logged)

5.2 Request / response DTOs

// Carries RAW rail details — transient, validated, used for the connector calls, then discarded.
public sealed record VerifyPayoutBeneficiaryRequest(
    Guid   CustomerPartyId,
    string DestinationType,        // "Bank" | "MobileMoney" | "Wallet"
    string Currency,               // required (account-resolve + recipient type are currency-keyed)
    string Country,                // destination country (capability routing + recipient registration)
    string AccountName,            // fallback when name enquiry is unavailable
    string? AccountNumber,         // bank rail (raw) — never persisted
    string? BankCode,
    string? MobileNetwork,         // mobile-money rail
    string? Msisdn,                // mobile-money rail (raw) — never persisted
    string? WalletId,              // wallet rail (raw) — never persisted
    string? ProviderCode,          // optional; default = capability-routed connector
    Guid?   BeneficiaryPartyId, string? BeneficiaryDisplayName, string? Notes);

// Reuses the existing PayoutBeneficiaryResponse — now returned with IsVerified = true.

The raw fields map to a PayoutDestination (the §5.3 connector input record, which holds full values in memory) and to the MaskedAccountIdentifier on persist. The API response is the existing PayoutBeneficiaryResponse (no new response shape).

5.3 Service — VerifyAndRegisterBeneficiaryAsync

On IPayoutBeneficiaryService / PayoutBeneficiaryService. New dependencies injected alongside the existing ones (FinanceDbContext, IPartyService, ITenantProvider): IPartnerConnectorResolver, IClock, and the current-user/party seam used by RemittanceOrderService for ownership. 

public async Task<PayoutBeneficiaryResponse> VerifyAndRegisterBeneficiaryAsync(
    VerifyPayoutBeneficiaryRequest request, CancellationToken ct = default)
{
    // 1. Authorization: the authenticated user's party MUST equal request.CustomerPartyId (§5.4).
    await EnsureCallerOwnsPartyAsync(request.CustomerPartyId, ct);

    var rail = request.DestinationType.Trim();
    PayoutDestination destination = BuildRawDestination(request);   // holds raw values in memory only

    // 2. Resolve the connector for the corridor (real connector preferred — PartnerConnectorResolver).
    var query = new PartnerConnectorQuery(PartnerServiceCategory.Payout, request.Country, request.Currency, rail);
    var connector = string.IsNullOrWhiteSpace(request.ProviderCode)
        ? (_resolver.TryResolvePayoutConnector(query, out var c) && c is not null ? c : null)
        : _resolver.ResolvePayoutConnector(request.ProviderCode);
    if (connector is null) throw new InvalidStateException("No payout connector serves this corridor.");

    // 3. Name enquiry — best-effort for bank rails; tolerate "not entitled" (§5.6).
    var resolvedName = await TryResolveAccountNameAsync(connector, request, ct);   // null when unavailable

    // 4. Register the recipient with the provider → reusable rcb_… token.
    var registration = await connector.RegisterRecipientAsync(new RecipientRegistrationRequest(
        destination, request.Currency, resolvedName ?? request.AccountName, request.Country, Metadata: null), ct);
    if (!registration.Registered || string.IsNullOrWhiteSpace(registration.ProviderBeneficiaryId))
        throw new InvalidStateException("Partner did not return a recipient id.");

    // 5. Party graph (reuse existing helpers) — recipient party, customer→recipient edge, Beneficiary role.
    var (beneficiaryPartyId, beneficiaryName) = await ResolveBeneficiaryPartyAsync(request, ct);
    await EnsureRelationshipAsync(request.CustomerPartyId, beneficiaryPartyId, Recipient, request.Notes, ct);
    await _partyService.AssignPartyRoleAsync(beneficiaryPartyId, Beneficiary, "Customer", request.CustomerPartyId, ct);

    // 6. Persist VERIFIED — masked identifier only; raw destination goes out of scope here.
    var account = UpsertVerifiedAccount(request, beneficiaryPartyId, connector.ProviderCode, registration, resolvedName);
    await _dbContext.SaveChangesAsync(ct);
    return ToResponse(account, beneficiaryName, Recipient);
}
  • Masking: MaskedAccountIdentifier = a last-four mask of the raw account number / MSISDN / wallet id (e.g. "••••0040"). The raw value lives only on the in-memory PayoutDestination + request, both out of scope after the call.
  • Idempotent re-verify: RegisterRecipientAsync is already idempotent at the provider (deterministic X-Idempotency-Key from currency+name+destination), so a repeat returns the same rcb_…. The persist upserts the customer's matching destination (same customer + rail + masked id + currency + provider) rather than inserting a duplicate.
  • Not money movement: registering a recipient moves no funds, so no MoneyActionLog entry is required (the money-action convention is for fund-moving paths); standard structured logging applies, redacting the raw value.

5.4 Endpoint & authorization

  • New VerifyPayoutBeneficiaryEndpoint : Endpoint<VerifyPayoutBeneficiaryRequest, PayoutBeneficiaryResponse>, Post("/payments/payout-beneficiaries/verify"), Policies("AdminUserWritePolicy") — mirroring SavePayoutBeneficiaryEndpoint.
  • Caller-owns-party (closes an IDOR): the policy authenticates but does not bind the request to the caller's party. The save path trusts CustomerPartyId as-is; the verify path (which submits raw account details and creates a real provider recipient) must resolve the authenticated user's party (the UserParty bridge RemittanceOrderService uses) and require it to equal CustomerPartyId, throwing before any connector call otherwise. (Worth applying the same check to the save path as a follow-up.)
  • Validation (PayoutBeneficiaryValidators.cs): required CustomerPartyId, DestinationType in the allow-list, Currency/ Country present; rail-specific required fields (bank → AccountNumber + BankCode; mobile money → Msisdn + MobileNetwork; wallet → WalletId).

5.5 Provider correlation — a self-describing destination

A rcb_… recipient id is meaningless without knowing which provider minted it, and dispatch must route to that same provider. ExternalPayoutAccount has ConnectorId (a Guid? FK to a Connector row), but the connectors are ProviderCode-keyed with no Connector rows today (Guid.Empty = unmapped). So:

  • Edit Add string? ProviderCode to ExternalPayoutAccount (+ set VerifiedAt on verify). One tool-generated migration against AonikDbContext (single stream, per CLAUDE.md), reviewed to contain only the added columns.
  • The verify flow stores the resolved connector.ProviderCode.
  • Edit (036 follow-up) RemittanceOrderService resolves the dispatch connector from the destination's ProviderCode (so the recipient's provider == the dispatch provider) instead of relying on the request/quote code alone — falling back to the simulator only for a destination with no registered provider.
This is what re-enables auto-routing to the real connector (037 G18/O11) Spec 037 deliberately does not auto-prefer the real connector in the generic capability resolver — an earlier attempt to do so broke confirm for unregistered beneficiaries (they have no recipient id, so dispatch fails closed with NO_RECIPIENT), so the simulator stays the default fallback there. "Prefer the real connector" is inherently destination-aware: it is correct only once a destination has been verified and carries a real ProviderBeneficiaryId + ProviderCode. This flow is what creates such destinations, and the ProviderCode-driven dispatch above is what then routes them to the real connector automatically — closing Spec 037 G18/O11 the safe way (no unregistered destination is ever routed to a connector that can't pay it).

5.6 Best-effort name enquiry

Grounded in a live finding Against the live sandbox, POST /banks/account-resolve returned 403 for a client entitled to transfers but not to bank-account verification. So name enquiry must be best-effort: the load-bearing step is RegisterRecipientAsync (mint the recipient + make the destination payable). TryResolveAccountNameAsync calls ResolveAccountAsync only for bank rails and swallows a FlutterwaveException with 403 (or any resolve failure), returning null so the flow proceeds with the customer-supplied name. When enquiry is available, its returned name is preferred (authoritative account-holder name) and surfaced to the customer for confirmation. Mobile-money / wallet rails skip enquiry entirely.

5.7 Frontend

  • Edit The Payabo (and Admin UI) add-beneficiary surface posts the raw rail details to POST /payments/payout-beneficiaries/verify (via the existing API client), replacing any client-side masking + the unverified save for the self-service path. On success it shows the verified beneficiary (and, when name enquiry resolved a name, a "confirm this is <name>" step).
  • The raw account number lives only in the form state for the request; it is never persisted in the client and never returned by the API (the response carries only the masked identifier).
  • Reuses the established service-module + form patterns (no new data-layer); the recipients/ beneficiary list (recipients surface, Spec 008) shows the IsVerified badge.

6. Sensitive-data rules (normative)

  • Raw rail details are never persisted. The account number / MSISDN / wallet id exist only on the transient request + the in-memory PayoutDestination passed to the connector. The row stores the MaskedAccountIdentifier + the provider's ProviderBeneficiaryId token only — the Spec 031 convention.
  • Raw values are never logged. Structured logs and any RawProviderResponse are redacted of account numbers (Spec 037 §7.4).
  • Secrets unaffected. The provider credentials remain in the settings store / config (Spec 038); this flow uses the configured connector, it does not handle credentials.
  • Authz before any partner call. Ownership is checked first, so an attacker can't use the endpoint to probe arbitrary accounts via name enquiry under another customer's id.

8. Acceptance criteria

  • End-to-end payable beneficiary. A verify call for a bank rail registers a recipient and persists an ExternalPayoutAccount with IsVerified = true, ProviderBeneficiaryId = rcb_…, and ProviderCode set — and a subsequent remittance to it passes the gate and dispatches via recipient_id (closing Spec 037 G19/G20/O12).
  • No raw at rest. The persisted row + API response contain only the masked identifier; no column or log holds the raw account number (asserted by a test).
  • Name-enquiry tolerance. When account-resolve returns 403 (not entitled), the flow still succeeds with the supplied name.
  • Authorization. A caller whose party ≠ CustomerPartyId is rejected before any connector call (no account probing).
  • Idempotent. Re-verifying the same destination does not duplicate the row and returns the same recipient id.
  • Build & migration. dotnet build Aonik.sln + suite green; the single tool-generated migration applies cleanly and contains only the new columns.
