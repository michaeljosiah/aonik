Spec 062 Status: Draft (Rev 1) Size: Medium Priority: P2 (Simi, post-M5) Domain: PersonalFinance / Simi / Ai

The Circle, spoken — Simi answers over what your circle shares with you

Spec 048 made an owner's people, assets, and documents shareable to a member, and Spec 061 let a not-yet-registered person accept. But that shared slice is reachable only through the /personal-finance/circle/shared/… REST screens: the Keeper AI cannot speak a word of it. Every Simi tool is hard-scoped to the caller's own records, so "what does Mum share with me?" or "which documents are on the Lagos flat she shared?" returns nothing. This spec adds a thin CircleTools read set that lets Simi answer over the already-authorised shared slice — by reusing Spec 048's single fail-closed ICircleVisibility filter, introducing no new projection and no new access. It closes the gap between "the data is shareable" and "Simi can talk about it."

Decision & scope-tension (mini-ADR) Simi's guiding invariant to date is "answer from their own records only" (PersonalFinanceAgentRegistration, the <keeper> block). This spec deliberately widens it to "their own records and what others explicitly share with them." That is a real change, so it is stated plainly here rather than buried. Why it is safe: it grants the AI zero data it could not already fetch — the member can open the exact same slice today via the Spec 048 REST endpoints; the tool is a second caller over the same ICircleService methods and the same fail-closed ICircleVisibility resolver. No new projection is written, so the docs-only "no amounts anywhere" property (Spec 048 §5/§10) holds transitively — the model physically never receives a suppressed amount. The describe-never-prescribe fence is unchanged. What changes is only that a capability the product already ships stops being mute. (The tool and class names below are generic per ADR-013 — pf_list_shared_circles, CircleTools — with "Simi" naming only the configured persona, never a platform symbol.)

1. Summary

The Circle already carries a household's load together — a sibling sees the co-owned flat, a partner sees everything, a property manager sees documents only. Spec 048 built the grants, the invites, and the fail-closed visibility filter; Spec 061 provisioned the not-yet-registered invitee. What is missing is voice: Simi, the Keeper, can answer "what is my Lagos flat costing me?" but is silent on "what does my mother share with me, and what's on the properties she shared?" — because the shared reads live only on REST screens and every AI tool is caller-scoped. This spec adds five read tools (pf_list_shared_circles, pf_list_shared_entities, pf_get_shared_entity, pf_list_shared_payment_logs, plus the entry-point who-shares-with-me resolver) that call the existing ICircleService shared reads, and one small service method to give the member a named list of the circles they belong to. No schema change, no new authorisation surface.

Success signals Seyi asks Simi, "what has my sister shared with me?" — Simi answers, "Fola shares the Surulere flat with you." He asks, "what documents are on it?" — Simi lists the tenancy agreement and the title deed by name. He asks, "what has she spent on it this year?" — because his grant is a full co-owner scope, Simi answers "₦1,240,000 across 6 payments." Mr Bello, the property manager, asks the same question — Simi says "I can show you the flat's documents, but not any amounts," because his grant is documents-only and the amount never enters the model's context at all.

2. Problem & current state

Confirmed against the tree:

  • The shared slice exists and is fail-closed — but REST-only. CircleService (implementing ICircleService + ICircleVisibility) exposes ListSharedEntitiesAsync(ownerUserId), GetSharedEntityAsync(ownerUserId, careEntityId), and GetSharedPaymentLogsAsync(…), each gated by the per-entity covering-grant resolver GetActiveGrantsAsync. Their only callers are the *Endpoint classes in Endpoints/PersonalFinance/CircleEndpoints.cs. No agent tool references them.
  • Every Simi tool is caller-scoped. CareReadTools (Spec 047) delegates to ICareEntityService/IPaymentLogService, which filter on e.UserId == currentUser — so the Keeper only ever reads the asker's own entities. The orchestrator-level DocumentSearchTools is documented as scoping "only the current user's documents … so a prompt cannot widen its own scope across parties." That invariant is correct and must be preserved; this spec routes cross-member reads through the grant, not around it.
  • The member has no named handle on their circles. ListGrantsForMemberAsync returns CircleGrantResponse rows carrying a bare OwnerUserId Guid and no display name — unusable for a conversational "your sister Fola shares…". Owner-name resolution (ResolveOwnerDisplayNameAsync via IPartyReader) exists inside CircleService but is private and only used by the anonymous invite preview.

So the plumbing is done and safe; it simply has no mouth.

3. Scope (in / out)

3.1 In scope

  • New CircleTools: five describe-only read tools over the existing shared reads (§4).
  • New One ICircleService.ListSharedCirclesAsync() method returning the member's circles with owner display names (§5).
  • Edit A <circle> block in the Simi system prompt + registration of the tools through the existing gate (§7).
  • Reuse The Spec 048 fail-closed ICircleVisibility filter and per-entity covering logic — unchanged (§6).

3.2 Out of scope

  • Any new access. The tools read exactly what a grant already authorises; no grant, no answer.
  • Cross-member document content retrieval (RAG). The tools surface document refs (title, type) for a shared entity; semantic search over another member's document bytes stays out — the vector index is deliberately party-scoped (ScopedDocumentVectorIndex, owner_party_id filter). Lifting that is a separate, security-sensitive decision (§8, O1).
  • Member-write. Logging or attaching on a shared entity is Spec 063.
  • Money movement, prescription, valuation. Unchanged Simi guardrails — describe only.

4. The CircleTools read set new

A sibling of CareReadTools: an internal sealed class, private constructor, DI-resolved ICircleService, [Description]-annotated methods, and a static CreateAll(IServiceProvider) that yields the named AITools. Every method delegates to an existing shared read; the tool layer adds no query of its own. 

internal sealed class CircleTools
{
    private readonly ICircleService _circle;   // Spec 048 shared reads + the §5 addition

    [Description("Lists the people (circle owners) who share records with the current user — e.g. a sibling "
        + "or parent who shared a property. Returns each owner's display name, the scope they granted "
        + "(everything | selected | documents only), and how many entities are shared. Call this FIRST to "
        + "find whose data you may read, then pass the ownerUserId to the other circle tools.")]
    public Task<IReadOnlyList<SharedCircleRef>> ListSharedCircles(CancellationToken ct = default)
        => _circle.ListSharedCirclesAsync(ct);

    [Description("Lists the people and assets one owner shares with the current user (names, kind, country). "
        + "Returns empty if that owner shares nothing with the caller. Use ListSharedCircles first to get ownerUserId.")]
    public Task<IReadOnlyList<CareEntityRef>?> ListSharedEntities(
        [Description("The circle owner's id, from ListSharedCircles.")] Guid ownerUserId,
        CancellationToken ct = default)
        => _circle.ListSharedEntitiesAsync(ownerUserId, ct);

    [Description("Gets the caller's scoped view of one entity an owner shares: the entity, its linked document "
        + "references (title + type only), and — ONLY if the grant permits amounts — per-currency totals and recent "
        + "payments. For a documents-only share, amounts are absent entirely. Returns null if nothing is shared.")]
    public Task<CircleSharedEntityResult?> GetSharedEntity(
        [Description("The circle owner's id.")] Guid ownerUserId,
        [Description("The shared entity's id, from ListSharedEntities.")] Guid careEntityId,
        CancellationToken ct = default)
        => _circle.GetSharedEntityAsync(ownerUserId, careEntityId, ct);

    [Description("Lists an owner's recorded payments for one shared entity, newest first, paginated. Returns null "
        + "for a documents-only or no-amounts share (amounts are never revealed). Amounts keep their original "
        + "currency and are never converted.")]
    public Task<CircleSharedPaymentLogsResult?> ListSharedPaymentLogs(
        [Description("The circle owner's id.")] Guid ownerUserId,
        [Description("The shared entity's id.")] Guid careEntityId,
        [Description("Page number (default 1).")] int page = 1,
        [Description("Page size (default 20, max 100).")] int pageSize = 20,
        CancellationToken ct = default)
        => _circle.GetSharedPaymentLogsAsync(ownerUserId, careEntityId, page, pageSize, ct);

    public static IEnumerable<AITool> CreateAll(IServiceProvider sp)
    {
        var t = new CircleTools(sp.GetRequiredService<ICircleService>());
        yield return AIFunctionFactory.Create(t.ListSharedCircles,     name: "pf_list_shared_circles");
        yield return AIFunctionFactory.Create(t.ListSharedEntities,    name: "pf_list_shared_entities");
        yield return AIFunctionFactory.Create(t.GetSharedEntity,       name: "pf_get_shared_entity");
        yield return AIFunctionFactory.Create(t.ListSharedPaymentLogs, name: "pf_list_shared_payment_logs");
    }
}

Note the deliberate shape: the model never invents an ownerUserId. It calls pf_list_shared_circles to discover the owners who share with the caller, and every subsequent id it passes was minted by a prior tool return — and even a fabricated id fails closed at the service (§6). Ids are opaque; the Simi prompt already forbids surfacing them to the user, so answers read as "Fola's flat", never a Guid.

5. The one service addition new

ListGrantsForMemberAsync returns owner ids; a conversational answer needs owner names. Add a member-facing projection to ICircleService that folds each active grant into a named, amount-free headline — reusing the private owner-name resolver CircleService already has: 

// ICircleService
/// <summary>The circles the current user is a MEMBER of, each with the owner's display name and a
/// scope summary — the conversational entry point for the Keeper (Spec 062). Never carries an amount.</summary>
Task<IReadOnlyList<SharedCircleRef>> ListSharedCirclesAsync(CancellationToken cancellationToken = default);

// CircleModels.cs — a headline, not a view: no amount, ever.
public record SharedCircleRef(
    Guid OwnerUserId,
    string OwnerDisplayName,   // resolved via the existing IPartyReader path
    string Scope,              // all | entities | docsOnly
    string ScopeLabel,         // the existing ScopeLabel() text, e.g. "Selected people & places"
    int? EntityCount,       // named-entity count; null = "everything" for all scope (the grant's id-union is empty and would misreport 0)
    bool NoAmounts);

Implementation folds ListGrantsForMemberAsync's active grants by OwnerUserId, resolves each owner's display name (batch the IPartyReader.GetByIdsAsync call once), and reports the most-permissive scope and the shared-entity count (for all scope, the owner's live entity count, since the grant's id-union is empty and would misreport 0) — the same merge rule ResolveAsync already uses. It reads only grants where the caller is the member; it exposes no amount and no owner data beyond a display name (the same disclosure Spec 061's preview already makes).

6. How it fails closed the crux is reused, not rebuilt

The security argument is entirely inherited, which is the point. The tools call ICircleService methods that already resolve the caller as member and fail closed:

pf_get_shared_entity(ownerUserId, careEntityId) → ICircleService.GetSharedEntityAsync (current member = GetContext() → currentUser) → GetActiveGrantsAsync(ownerUserId) active grants for (member → owner); unknown scopes dropped → covering = grants covering THIS entity none → return null → tool returns null → "nothing shared" → docsOnly only? → CircleSharedDocsView structurally amount-free (no log/total join at all) → full + amounts? → CircleSharedEntityView amounts only if a covering grant has NoAmounts = false
  • No grant → null → the model is told "nothing is shared", not an amount. A fabricated or guessed ownerUserId/careEntityId resolves no covering grant and returns null. Existence is not revealed (the tool cannot distinguish "no such entity" from "not shared with you").
  • docsOnly is amount-free by construction. GetSharedEntityAsync returns CircleSharedDocsView, which has no amount/total/log field — so there is no amount in the object the tool hands the model. ListSharedPaymentLogs returns null for docsOnly / no-amounts. The Spec 048 "no amounts anywhere" property therefore holds for the AI path with zero new enforcement code.
  • Revocation is immediate. Revoked grants are excluded by GetActiveGrantsAsync (Status == "active"); the next tool call after a revoke returns null. No cached visibility.
  • Reads, so ungated and unwrapped. Like pf_* Keeper reads, these carry no mutating capability and are omitted from PersonalFinanceToolApprovalManifest, so IToolApprovalGate.GateAll passes them through (Spec 032).

7. Prompt & registration wiring edit

Register the tools exactly as the Keeper set is registered — appended inside PersonalFinanceAgentDescriptor.GetTools's gate.GateAll(…) chain: 

        .Concat(CareReadTools.CreateAll(serviceProvider))
        .Concat(CircleTools.CreateAll(serviceProvider)),   // Spec 062 — shared-circle reads (ungated)

Add a <circle> block to the Simi instructions, next to <keeper>:

<circle>
Some people share a slice of their records with the user — a sibling's flat, a parent's affairs.
When the user asks about someone else's people, assets, documents, or support, first call
pf_list_shared_circles to see who shares with them and how much. Then read with
pf_list_shared_entities / pf_get_shared_entity / pf_list_shared_payment_logs.
Refer to the owner by name ("Fola's flat"), never an id. If nothing is shared, say so plainly — do
not guess or imply access. If a share is documents-only, you can name and describe the documents but
you have no amounts for it; never estimate or imply a figure. Describe, never prescribe — the same
rule as the user's own records. Amounts in different currencies are never converted or summed.
</circle>

The tools flow into GetToolNames automatically, so tenant tool-allow-lists and the AI Playground pick them up with no extra wiring. Because RequiresUserBrief is already true, no brief change is needed.

8. Documents: refs now, content later

The user's question "…and any documents associated with those assets?" splits cleanly:

  • In Which documents exist — pf_get_shared_entity returns each linked document's Title + DocumentType (from IDocumentLinkReader.GetForOwnerTargetAsync, read by the owner's identity, refs only). Simi can answer "there's a tenancy agreement and a title deed on the flat."
  • Deferred What a document says — semantic search over another member's document content. Today documents_search / ScopedDocumentVectorIndex filter on owner_party_id == caller precisely so one party's agent cannot retrieve another party's document text (this closed a real cross-customer leak). A circle-aware variant is possible — filter the index to an owner's owner_party_id where the caller holds a covering, non-docsOnly grant — but it reopens the most sensitive index guarantee and deserves its own spec. Tracked as O1.

9. Persistence & migration

No migration This spec is read-only. It adds one DTO (SharedCircleRef), one service method, one tool class, and one prompt block. No entity, no DbSet, no schema change — nothing to migrate.

10. Security

  • Zero new access surface. The tools are a second caller over the Spec 048 shared reads; the authorisation decision remains ICircleVisibility + the per-entity covering check, in one place.
  • No-amounts property preserved transitively (§6) — the docs-only projection carries no amount, so none can reach the model; asserted by the tests below.
  • No scope-widening via prompt. Owner/entity ids are resolved through grants; a model-supplied id with no covering grant returns null. This mirrors the DocumentSearchTools guarantee that scope comes from context, not model input.
  • Tenant + membership scoping is inherited: GetActiveGrantsAsync pins TenantId and MemberUserId == currentUser.
  • Audit. Tool invocations are already recorded as part of the AiRun; no separate audit is added, but the shared-read tool name + owner id make cross-member reads legible in the run log.

12. Acceptance criteria

  • Discovery. A member with an active grant sees the owner (by display name) and scope via pf_list_shared_circles; a user with no inbound grants gets an empty list.
  • Full scope reads. An entities/all member gets the shared entity, its document refs, per-currency totals, and recent payments through the tools — the same data as the REST endpoint.
  • Documents-only, no amounts — the security assertion. Called as a docsOnly member, pf_get_shared_entity returns the docs view with document refs and no amount-bearing field, and pf_list_shared_payment_logs returns null — asserted field-by-field on the tool output, not just the endpoint.
  • Fail closed. A fabricated ownerUserId/careEntityId, or an id whose grant was revoked, returns null/empty on the next call.
  • Ungated. The tools are not classified in the manifest and pass the approval gate unwrapped; a mutating-looking rename would (correctly) trip the Spec 032 build-time check — these are reads.
  • Build. dotnet build green; no migration produced.

13. Open decisions

  • O1 — Cross-member document content RAG. Whether to add a circle-aware IDocumentSearch that lets a full-scope member ask "what does the tenancy agreement say?" over an owner's document bytes. Recommended: a separate spec that filters the vector index by the owner's owner_party_id only where a covering non-docsOnly grant exists, with the same logged-in-as-member leak test. Deferred here to keep this spec zero-migration and zero-new-index-surface.
  • O2 — Member-side alias for the owner. The grant stores no "how the member thinks of the owner" label, so Simi says the owner's display name ("Fola"), not "your sister". A lightweight per-grant MemberAlias (or reuse of user memory: relationship.fola = sister) could let Simi say "your sister's flat". Low priority.
  • O3 — Owner-name disclosure surface. ListSharedCirclesAsync discloses the owner's display name to the member. This equals what Spec 061's preview already reveals and what the REST "Can see" screen shows, so it is assumed acceptable; confirm no stricter tenant wants owner-name masked.
