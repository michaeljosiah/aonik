01Overview

Architecture overview#

AONIK is a module-first modular monolith implementation of a modular AI intelligence platform. AONIK Core provides shared identity, memory, workflows, governance, AI routing, agents, approvals, notifications, and shared human primitives. Finance and PersonalFinance are the first shipped domain modules.

Core principles

Ledger is the source of financial truth. Orders represent business intent, not payments. Payments execute intent; ledger proves it. Agents propose; systems execute. Every AI action is auditable and policy-governed. Risk tier determines AI autonomy. Human approval is explicit for high-risk actions.

LayerRole
AONIK CoreDomain-agnostic intelligence and orchestration substrate: identity, memory, workflows, governance, AI routing, agents, approvals, tasks, notifications, and shared human primitives.
Domain ModulesSpecialised systems that own domain truth, operations, workflows, policies, agents, and intelligence. Finance and PersonalFinance are the first shipped modules.
Product ExperiencesCurated applications such as Payabo, MyBillAfrica, and RemitExchange that package Core and one or more domain modules.

03Implementation

Module organization#

Each module is a self-contained .NET project that owns its entities, services, endpoints, and persistence. Public APIs live in Contracts/; everything else is internal by default.

Module anatomytext
Aonik.{Module}/
├── Contracts/                   # PUBLIC surface
│   ├── Events/                  # Integration events
│   ├── Services/                # Service interfaces
│   └── Models/                  # Shared DTOs / read models
├── Entities/                    # internal — anemic EF entities
├── Services/                    # internal — business logic
├── Endpoints/                   # internal — FastEndpoints
├── Persistence/
│   ├── {Module}DbContext.cs     # internal — module-scoped DbContext
│   └── Configurations/          # internal — EF configurations
├── Agents/                      # internal — MAF agents & tools
└── {Module}Module.cs            # PUBLIC — Add{Module}() extension

Boundary rules

  1. Types in Contracts/ are public.
  2. Everything else is internal by default.
  3. Modules reference each other only through contracts.
  4. Cross-module data access uses integration events, service interfaces, or SharedKernel read contracts.

04Implementation

Module-scoped DbContexts#

Each module owns a DbContext that maps only its tables. The contexts share the same physical SQL Server database, but they do not own separate migration histories.

DbContext patterncsharp
internal class FinanceDbContext : DbContext
{
    public DbSet<Invoice> Invoices => Set<Invoice>();
    public DbSet<LedgerAccount> LedgerAccounts => Set<LedgerAccount>();
    // ... finance entities only
}
Migration rule

AonikDbContext in Aonik.Infrastructure is the canonical migration stream. Module-scoped DbContexts exist for runtime DI scoping only.

Multi-tenancy is enforced via ITenantScoped and global query filters, with tenant context resolved in Aonik.Api.

05Implementation

Data flow#

Request path

  1. HTTP request arrives at Aonik.Api.
  2. Middleware runs: authentication and tenant resolution.
  3. The owning module endpoint validates and maps the request.
  4. The module service performs business logic using the module DbContext.
  5. The DbContext persists changes.

Response path

  1. Service returns a DTO.
  2. Endpoint maps or returns the DTO using Send.*Async() helpers.

AI agent execution

Agent execution flowtext
[Client] → POST /api/agents/orchestrator/chat
[Aonik.Agents/Endpoints/ChatEndpoint]
→ [MasterOrchestratorService]
→ builds ChatClientAgent orchestrator with domain agents as tools
→ creates/resumes AgentSession for conversation history
→ routes to domain agent descriptor (e.g. FinanceAgentDescriptor)
→ Read tools execute directly
→ Mutating tools gated by ApprovalRequiredAIFunction
→ [BillingService / LedgerService / PaymentService]
→ [AuditMiddleware] records AiRun with token usage
Key details

Domain agents are registered as IDomainAgentDescriptor implementations and composed into the orchestrator via agent.AsAIFunction(). MCP tools are available through McpToolProvider. AgentSession manages conversation history natively.

07Reference

Document & file model#

Status

The generic document capability now lives in Aonik.Documents. The original platform-centric placement is superseded; this file remains as the conceptual model.

The model represents evidence composed of one or more files, with the purpose kept separate from the document itself. It is designed for multi-tenant, multi-purpose use with blob storage and strong auditability.

Core concepts

ConceptRole
DocumentLogical evidence container with tenant, owner party, type, status, dates, issuer, country, tags, attributes, and RAG classification fields.
DocumentFilePhysical file reference with storage metadata, hash, page/side info, capture metadata, and extracted-text status.
DocumentVersionImmutable snapshot for re-submission or updates.
DocumentUsagePurpose/workflow link for reuse of the same evidence across multiple workflows.
DocumentVerificationDecisioning record, including AI-run linkage when AI contributed.

Relationships

  1. One Document has many DocumentFiles.
  2. One Document can serve many DocumentUsages.
  3. One DocumentUsage can have many DocumentVerifications.
  4. One Document can have many DocumentVersions.

Module placement

  • Aonik.Documents owns the generic document capability.
  • Aonik.Platform / Compliance keeps DocumentUsage and DocumentVerification.
  • SharedKernel.Abstractions.Documents defines the cross-module boundary.
  • Aonik.Infrastructure hosts blob, vector index, and extraction adapters.
  • Aonik.Worker runs ingestion/backfill jobs.
