Feature guide Module: Aonik.Workspaces

Workspaces & content-addressed storage

How a versioned tree of files is stored, committed, shared and billed — and why every hard part is a single guarded SQL statement rather than a lock. Implements Spec 089. Back to the index.

What a workspace is

A workspace is a folder tree with history. Arke calls it a world; the platform calls it a workspace of kind world, the same way a personal-finance household is a group of kind household. Four entities carry the whole model:

Workspace the container: name, owner party, current head, quota subscriber WorkspaceRevision one immutable snapshot: server-assigned sequence, parent pointer, state WorkspaceFile one path in one revision: path + content hash + size ("the manifest IS the revision") WorkspaceBlob the bytes, once per tenant: hash, storage key, size, reference count

Two deliberate choices in that model. The owner is a party, not a user — a child in Arke Kids owns a workspace but cannot log in, and ADR-015 already established that members need not have accounts. And a revision's manifest is complete, never a delta: a delta requires the server to trust the client's account of what changed, and a client that forgets to mention a deletion silently resurrects the file. With a complete manifest, the revision describes itself and any diff is computed server-side from two full lists.

Content addressing: store the bytes once

A blob is identified by the SHA-256 of its bytes. The storage key is derived from the hash: 

hash       = SHA-256(bytes)                            (lowercase hex, 64 chars)
storageKey = workspaces/{tenantId}/blobs/{hash[0..2]}/{hash}

Same bytes → same hash → same key → one physical object, no matter how many revisions or workspaces name it. An unchanged reference image shared by ten drafts costs one copy. The honest limit: this only dedupes byte-identical content. Two AI takes of the same shot are visually similar and byte-wise unrelated, so media barely dedupes at all — pricing assumes that.

The upload flow: stage, then promote

The old IFileStore.UploadAsync could not do this: it returned a hash after writing to a random path it chose itself — the hash was an output, never an input. Two additive methods fixed it:

CLIENT SERVER (IFileStore) ────── ─────────────────── stream bytes ───────────► StageAsync: write to a TEMP key, hashing each chunk as it streams past (HashingReadStream — single pass, nothing buffered in memory) returns (hash, size, tempKey) PromoteAsync(staged, contentKey): key already exists? → DISCARD the staged copy, report AlreadyPresent. Whoever got there first wrote byte-identical content, so there is nothing to reconcile. otherwise → move temp → content key
Why "last writer discards" is the whole concurrency answer Two clients uploading the same bytes at once both stage privately (temp keys never collide) and both try to promote to the same content key. The second finds the key occupied and throws its copy away. Because the key is the hash, the occupant is guaranteed to hold identical bytes — so a race costs one discarded temp object and can never produce a duplicate or a conflict.

Reference counting, and the race in sweeping

WorkspaceBlob.RefCount counts how many revision files name the blob. Deleting a revision decrements; when a blob reaches zero it becomes sweepable — never deleted inline, because another revision in the same tenant may have deduped against it, and deleting bytes someone still names destroys data that is only discovered when a user opens an old revision to an empty tree.

The race: a zero count is not a stable fact The sweeper reads RefCount = 0 and selects the blob. Before it deletes the object, a new commit legitimately references that hash — the row still exists, so validation passes and the count increments. The sweeper then deletes on the strength of a stale observation, and the fresh revision points at bytes that are gone. The commit succeeded, the manifest is valid, the database is consistent, and the file is simply missing.

The fix is a claim, written as data, before storage is touched:

SWEEP COMMIT (referencing a hash) ───── ─────────────────────────── UPDATE WorkspaceBlobs UPDATE WorkspaceBlobs SET IsDeleting = 1 SET RefCount = RefCount + n WHERE Id = @id WHERE ContentHash = @h AND RefCount = 0 AND IsDeleting = 0 ◄── one statement: AND IsDeleting = 0 read + guard + write 0 rows → someone referenced it, 0 rows → the sweeper claimed it. or another sweeper claimed it. Treat the hash as MISSING; the ABANDON — this pass has no client re-uploads. One redundant right to the bytes. transfer, never a dangling reference. 1 row → re-check RefCount UNDER the claim (it was read stale), then delete object, then delete row.

Both halves are single ExecuteUpdateAsync statements, which is why their tests live in the SQL Server LocalDB lane — the InMemory provider cannot issue them at all. Two more details: a blob is only sweepable after a grace period (an upload sits legitimately at zero refs until its commit lands), and a failed storage delete leaves the claim in place — releasing it would offer the bytes back to a client while storage still holds an object we just failed to remove.

Commits: the head, the sequence, and the CAS

A commit presents a complete manifest plus the parent revision the client believes it is building on. If the parent matches the current head, the commit fast-forwards and becomes the head. If not, it is stored as diverged — a real, sequenced revision that did not move the head — and a human resolves it later. Divergence is an outcome, not an error.

Why the sequence and the head are one decision

The spec paid two review rounds for this. Under SQL Server's default isolation, two concurrent commits both read the same head and both classify themselves as fast-forwards. If sequence numbers are assigned before the head check, the loser collides on the unique sequence index and dies with a database error — never reaching the code that was supposed to reclassify it as diverged. So Workspace.NextSequence lives beside HeadRevisionId, and one guarded write consumes the sequence and advances the head, before any row is inserted:

read workspace (Head = H, NextSequence = S) classify parent == H ? FastForward : Diverged UPDATE Workspaces SET NextSequence = S + 1, HeadRevisionId = (fastForward ? newRevisionId : HeadRevisionId) WHERE Id = @id AND NextSequence = S ◄── the guard IS the invariant: "nobody took this sequence 0 rows → another commit won. NOTHING was since I read it" inserted, so nothing is orphaned. Re-read, re-classify: the parent no longer matches, so this commit is now Diverged — by the same rule, not an exception handler. Bounded retry (5). 1 row → the sequence is ours. NOW insert the revision + files, same transaction.

Idempotency: a retry must land on the original, a different tree must not

Every commit carries a client-chosen CommitId, reused unchanged on retries. The server stores it with a request hash: SHA-256 over the workspace id, the declared parent, and the manifest as a sorted path→hash list.

SituationServer response
Same CommitId, same request hashReplay the stored outcome verbatim — a true retry, no second revision.
Same CommitId, different hash409, loudly. After a timeout the author may have kept working; the client correctly reuses its id but rebuilds the manifest from a tree that changed. Replaying would report the new tree as committed when it is not, and the next pull would silently discard those edits. A loud client bug beats silent data loss.

The hash sorts the manifest (two clients enumerate one tree in different orders) and excludes content type (a hint clients may sniff differently between attempts). Paths are normalised first — forward slashes, Unicode NFC, no .. segments, duplicates refused after normalisation — because café composed two different ways is one filename to a user and two strings to a database.

Divergence ends three ways, and the platform decides none of them

Arke's core mechanic is the accept gate: nothing enters the record without a human accepting it. A remote revision that does not descend from the local head is a proposal — reviewed exactly like a locally-drafted change. The platform's part is deliberately tiny: detect (parent ≠ head), store, expose the two manifests. It never merges, because merging requires understanding file contents.

OutcomeWhat happensWhy this way
AcceptA new revision carrying the divergent manifest is committed, parented on the current head, through the same CAS as any commit. The divergent revision is marked and kept.History is never rewritten. Repointing the head at a revision whose parent is not its predecessor makes the chain a lie and breaks every history read.
RejectMarked rejected. Blobs are not released inline — a retention window keeps rejection undoable; the sweeper releases afterwards.Releasing immediately would make "undo" mean "re-upload".
SupersedeThe human committed a third tree (their edited result); this records the proposal stopped being live.This is what the accept gate usually produces — neither side wins wholesale.

An acceptance derives its CommitId from the accepted revision's id, so a retried acceptance replays instead of committing the same tree twice.

Sharing: read/write is the platform's question

Workspaces register as a Spec 086 share resource (ResourceKind = "workspace"), inheriting invite tokens, expiry, revocation and ownership validation with no new code. But one thing could not be left to the product: whether the recipient may write.

The vulnerability an earlier draft shipped on paper The draft said writability lives in TermsJson — the product's opaque terms — because a platform enforcing an "editor" role would be interpreting terms. But the commit endpoint is a platform HTTP endpoint. A read-only recipient just calls it directly with curl; the product-side check is decoration with nothing behind it, and the platform's own grant reader answers "is there a grant?" with yes.

So grants carry an AccessLevel — read | write, a closed set the platform reads and enforces — while TermsJson stays opaque. Effective access resolves as: owner → Owner; otherwise the highest level on an active grant; otherwise nothing. Unknown levels resolve to nothing (a future value must not widen access by accident), and two grants on one resource take the highest (a stale read-only grant must not silently revoke write access the owner gave).

Quota: storage is a level, not a flow

Two meters, wired to Spec 087: workspaces (a ceiling — one slot per workspace) and workspace-bytes (a weighted ceiling — n bytes held per stored blob). The byte meter is emphatically a ceiling and not a counter: counters move reservations into Consumed, which never decreases — correct for flows like "stories generated", catastrophic for storage, where a customer who uploads 40GB and deletes it would have permanently burned 40GB of allowance while using none.

The weighted claim forced a real widening: CeilingHolding.Held was an int, and a 200GB allowance is 214,748,364,800 — a hundred times int.MaxValue. Held and CeilingClaim.Weight are now long, and the overflow test uploads past 2³¹ bytes in the LocalDB lane, where a column truncation is actually observable.

Per-subscriber possession: who stops paying, and when

The ceiling claim is keyed on the content hash, which gives dedupe-in-billing for free: ten revisions naming one blob are charged once. But that same idempotency means a subscriber has one claim covering all their workspaces that reference the hash — so transferring one of two such workspaces and releasing "their claim" would leave the retained workspace's bytes completely uncharged while the physical blob cannot be swept. BlobPossession is the per-subscriber reference count that closes this:

WorkspaceBlob.RefCount answers: may these BYTES be deleted? (physical) BlobPossession.WorkspaceCount answers: may this SUBSCRIBER stop paying? (billing) same shape, one level apart, genuinely different questions

Ownership transfer is a claim migration: claim against the recipient first, release the sender second — never the reverse, because releasing first opens a window where a concurrent claim eats the freed allowance and the transfer fails with the sender's claim already gone. Insufficient capacity refuses the transfer with the shortfall named. Deletion is the degenerate transfer: release both meters once. The billing subscriber is stored on the workspace, separate from the owner, because an Arke Kids workspace owned by a child can be billed to the family subscription.
