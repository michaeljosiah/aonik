The workspace sync protocol

How a desktop client and the platform exchange only the bytes the other side is missing — without letting a file hash become a password, and without a 2GB upload restarting from zero. Implements the server side of Spec 091. Back to the index.

The shape of a sync

Arke Studio is a desktop product; the workspace lives on the author's machine and the platform holds the synced copy. Sync is built entirely from the primitives in workspaces & blobs — content hashes, complete manifests, the guarded commit. A push is three round-trips, and the middle one is usually nearly empty:

CLIENT SERVER ────── ────── 1. NEGOTIATE "here is the manifest I want to ───► For each hash: can THIS CALLER commit: [path → hash, size]" already reach it? ◄─── "missing: [these hashes]" 2. TRANSFER (only what was missing) small blob → single-shot upload ───► stage → hash → promote (dedupe) large blob → multipart session ───► parts → assemble → verify → promote 3. COMMIT full manifest + parent + CommitId ───► guarded CAS on the head ◄─── FastForward (head moved) or Diverged (stored, needs a human)

A pull is the mirror image: fetch the head revision's manifest, diff against the local tree, download the hashes the client lacks. Because a manifest is complete and every entry is a hash, the diff needs no server-side "what changed" endpoint — two lists and set arithmetic.

Where the rest of the protocol lives Spec 091's client-side slices — the local snapshot store and journal, the filesystem watcher, and the pull/merge loop — belong to the Arke desktop client repository, not this platform. This page documents the server's half: negotiation, transfer, and the invariants that make both safe to expose over HTTP.

Negotiation is scoped to the caller, not the tenant

The first version of "which hashes are missing?" checked whether the blob row existed in the tenant. That is the natural implementation and it is wrong, in a way worth spelling out because it is the mistake most likely to be re-introduced by an optimisation:

A hash is a name, not an authorisation If "the tenant has these bytes" means "you don't need to upload them", then knowing a hash is enough to attach the bytes to your own workspace: commit a manifest naming the hash, skip the upload the negotiation excused you from, then pull — and read content you never possessed. The hash has become a bearer token. The same check is also an existence oracle: probe any hash and the answer "not missing" confirms someone in the tenant stores that exact file.

So negotiation answers a different question: can this caller already reach these bytes? A hash is reported as already-present only if it is in the caller's reachable set — 

reachable(caller) =  possession rows of the caller's billing subscriber
                   ∪ hashes named by revisions of workspaces the caller can access
                   − blobs the sweeper has claimed (IsDeleting)

— and everything else is reported as missing, including hashes the tenant physically holds. The refusal deliberately reads as missing, never forbidden: a "forbidden" answer is itself the existence oracle, confirming the bytes exist while declining to share them. "Missing" is indistinguishable from the bytes never having been uploaded at all.

What happens when two people upload the same file

The caller then uploads bytes the server already has. That is the designed outcome, not waste:

Alice uploads photo.jpg → staged, hashed, promoted, possession recorded Bob negotiates same hash → "missing" (Bob has never possessed it) Bob uploads the same bytes → staged, hashed, promote says AlreadyPresent, staged copy DISCARDED — and Bob's possession is recorded ANYWAY Bob negotiates again → "" (empty — Bob now legitimately reaches it) storage objects for this content: exactly one
The one-line rule that keeps this safe Possession is granted by demonstrating the bytes, never by naming the hash. Bob proved he holds the file by streaming it; the server merely declined to store a second copy. The AlreadyPresent branch still writes the possession row — this is the exact spot a future "skip the bookkeeping, the blob exists" optimisation would re-open the bearer-token hole, which is why an end-to-end test pins the whole sequence above, including the final empty negotiation.

Large files: the multipart session

Arke worlds carry media. A blob above the threshold (default 32 MB) is transferred as a session of numbered parts (default 8 MB each) instead of one HTTP body, because a consumer connection that drops at 99% of a 2 GB upload must cost one part, not the whole file.

Begin(declaredHash, declaredLength) │ an OPEN session already exists for this caller + declared hash? │ → return IT, with which parts it already holds ◄── resume is just │ else create session (expires in 48h) Begin again ▼ UploadPart(n, bytes) 1-based, contiguous, any order, idempotent: │ re-sending a received part overwrites the same │ storage key — a no-op, not an error ▼ GetMissingParts() the client's restart question: "what do you │ still need?" — parts, not bytes, so a crashed │ client re-reads its own file and sends the gaps ▼ Complete() │ all parts present? → assemble as ONE STREAM (parts opened lazily, │ nothing buffered whole) → stage → the staged hash MUST equal the │ declared hash → promote → possession recorded via the same path │ as a single-shot upload ▼ (or Abort() — parts deleted, session closed)

Sessions and parts are database rows (BlobUploadSession, BlobUploadPart), which is what makes two things work: resume survives a client crash because the server's record of received parts is the resume state, and abandoned uploads are sweepable because staging finally has something the sweeper can see — the daily sweep removes sessions that are expired or no longer open, along with their part objects. (The earlier blob-store phase had to ship that sweep as a documented no-op; the session row is what made it real.)

The two bounds an upload must respect

Begin takes a declared hash and a declared length. Both are claims, and each is enforced at the point where it can actually be checked:

BoundEnforcedWhat it prevents
Declared length While bytes stream in. Every part body is read through a bounding stream capped at the space the declaration has left; one byte past it aborts the part and the session. A client (or attacker) declaring 10 MB and streaming 10 GB into staging. Quota is charged on real size at registration, but disk is consumed during the upload — the declaration is the only bound that exists early enough.
Declared hash At Complete, after assembly — the first moment the whole content exists to hash. The staged result must hash to exactly the declared value; a mismatch discards the staged bytes and fails loudly. Hash substitution: declare the hash of popular content, upload junk. If the junk were registered under the declared hash, every future dedupe against that hash — including other subscribers' — would silently resolve to junk. The declared hash selects the session; only the verified hash may name the blob.
Why resume keys on the declared hash A crashed client has no session id — it has the file. On restart it re-hashes locally and calls Begin with the same declaration; the server finds the open session for (caller, declared hash) and hands back the part map. The declared hash is safe as a lookup key precisely because it authorises nothing: it never becomes a blob identity until the bytes prove it.

Commit and pull, briefly

Step 3 of a push is the commit documented in full in workspaces & blobs: complete manifest, client CommitId bound to a request hash (retry replays; same id with a different tree is a loud 409), one guarded SQL statement consuming the sequence and advancing the head, and the losing side of a race reclassified as Diverged rather than failed. Divergence then waits for a human — Arke's accept gate — and resolves as Accept, Reject, or Supersede.

Pull needs almost nothing beyond reads: the head revision, its manifest, and blob downloads by hash — where "by hash" is again bounded by the caller's reachable set. A download request for a hash outside it is, of course, missing.
