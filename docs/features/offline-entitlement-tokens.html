Offline-verifiable entitlement tokens

How a desktop app on a plane, or a child's tablet in a school with no Wi-Fi, proves the family's subscription is real — with zero network, no JWT library, and a revocation list that names nobody. Implements Spec 090. Back to the index.

The problem

Arke Studio and Arke Kids run on devices that go offline for days. "Check the subscription" cannot mean "call the server", but it also cannot mean "trust a flag in a local file", because a flag is edited in seconds. And subscriptions change: they lapse, upgrade, and occasionally must be cut off immediately. So the device needs three things it can hold locally and trust cryptographically:

  1. A token — a signed statement of what this subscriber is entitled to, with a validity window.
  2. The published key set — the public keys that make signatures checkable.
  3. The revocation list — the short list of tokens that died early.

All three refresh opportunistically whenever the device is online. Verification itself touches nothing but those three local artefacts and the clock.

The token on the wire

Deliberately not a JWT. Two base64url segments, one dot:

token         = SIGNING_INPUT "." BASE64URL(signature)
SIGNING_INPUT = BASE64URL(payload-json)

signature     = Ed25519( ASCII bytes of SIGNING_INPUT, exactly as transmitted )
The one rule everything else follows from: no canonicalisation, ever The signature covers the bytes that arrived, not a re-serialisation of what they parse to. The verifier never re-encodes, never normalises JSON key order, never tolerates padding or whitespace and then strips it. Every historical class of token-library vulnerability — alg confusion, "sign the canonical form, verify the parsed form", parser differentials — lives in the gap between what was signed and what was interpreted. This format removes the gap by construction: if the bytes differ, the signature fails; there is no second representation to disagree with the first.

Consequences of that rule, each of which is a test:

  • Strict base64url: unpadded, exact alphabet, nothing else. A token with padding, whitespace, or a stray character is Malformed — not cleaned up and retried.
  • Exactly two segments. The splitter returns the original substring for the signing input — never a reassembled one.
  • Integer Unix seconds only for every timestamp. No ISO strings, no fractions — nothing that two parsers could read differently.
  • No alg field. The algorithm is Ed25519 because the format says so, not because the token asked.
  • Swapping the payload of one valid token onto the signature of another is BadSignature, proven by test with two real tokens.

The payload

{
  "v": 1,                              format version
  "jti": "…",                          unique token id (revocation by id)
  "rvh": "…",                          random revocation handle — see privacy, below
  "sub": "family:1f3a…",               subscriber as kind:id
  "tid": "…",                          tenant
  "plan": "studio-pro",
  "feat": ["export", "sync", …],       feature flags, SORTED
  "lim": { "workspace-bytes": 214…, }  ceilings, SORTED, integers (long)
  "use": { "workspace-bytes": 12…, }   held usage at issue, same shape
  "iat": 1765713600,                   issued
  "exp": 1766318400,                   expires        (default: iat + 7 days)
  "gra": 1768910400,                   grace ends     (default: exp + 30 days)
  "dev": "…",                          optional device binding
  "kid": "…"                           which key signed this
}

feat, lim and use are sorted so the payload for a given entitlement state is deterministic — useful for tests and diffing, and harmless since sorting happens at issue, on the side that is about to sign, never at verification.

Expiry versus grace: two windows, two meanings

iat ──────────── exp ─────────────────────────── gra │ Valid │ ValidInGrace │ Expired │ full product │ product works, degraded: │ stop │ │ "please reconnect soon" │

A seven-day expiry with a thirty-day grace is the compromise between two bad extremes: a long-lived token means a cancelled subscription keeps working for months offline; a short one means a family holiday kills the product on day three. Inside grace the device works but nags; past grace it stops. The verifier reports the two states as distinct verdicts (Valid / ValidInGrace) and the product decides what "degraded" means.

Verification: three passes, because the first one lies

EntitlementTokenVerifier lives in SharedKernel so the desktop client can compile the exact same code. It is a pure function of (token, key resolver, signature primitive, clock) and it reads the payload twice, deliberately:

PASS 1 — UNTRUSTED PEEK split; strict-decode payload; read ONE field: "kid". Nothing else from this pass is kept. The kid is needed to pick a key, so it must be read pre-verification — that is unavoidable — but it is attacker-controlled until the signature says otherwise. kid unknown / absent → UnknownKey / Malformed PASS 2 — VERIFY Ed25519.Verify(publicKey(kid), ASCII(signing input as received), sig) false → BadSignature PASS 3 — TRUSTED READ re-read the payload from the now-verified bytes; build the result from THIS pass only. Includes re-checking that the payload's kid equals the key actually used in pass 2. then: now ≤ exp → Valid; ≤ gra → ValidInGrace; else Expired
Why the discipline is worth two extra reads Everything read before signature verification is untrusted input steering the verifier itself. Keeping the passes physically separate makes the dangerous state — data extracted from an unverified token — impossible to leak into the result by accident: pass 1's parse is discarded, and pass 3 cannot run unless pass 2 succeeded. The kid re-check in pass 3 closes the last inch: a payload whose kid differs from the key that verified it is a splice, not a token.

Keys: rotation, retirement, and the invariant that makes both safe

Signing keys are Ed25519 pairs stored in AnkEntitlementSigningKeys: public key as raw 32 bytes (base64url), private key encrypted at rest with ASP.NET DataProtection, and three lifecycle dates — NotBefore, SigningNotAfter (stop signing; default lifetime 90 days), and VerifyNotAfter (stop being published for verification). Status is Active → Retiring → Withdrawn.

Rotation is routine

Rotate creates a new Active key and moves the predecessor to Retiring: it signs nothing new but stays published, because tokens it signed are still in the field and must keep verifying. Withdrawal is the emergency path — a compromised key vanishes from the published set immediately, and every token it signed dies with it. That is the correct cost of a compromise.

The retirement invariant, enforced where the race is

A key may not stop being publishable while a live token depends on it Formally: VerifyNotAfter ≥ max(gra) over every token the key signed. The naive implementation — issue the token, then update the key's date — has a race: between the two writes an operator retires the key, and a token issued a moment ago is unverifiable tomorrow. Checked-then-written is two facts with a gap between them.

The issuer closes it the same way every other race in this platform is closed — one guarded statement:

UPDATE AnkEntitlementSigningKeys
   SET VerifyNotAfter = MAX(VerifyNotAfter, @graceUntil)
 WHERE Kid = @kid AND Status <> 'withdrawn'

1 row  → the key is committed to outlive this token; NOW sign and issue
0 rows → the key was withdrawn mid-issue; REFUSE to issue
         (never sign with a key that cannot promise verification)

The issued token's GraceUntil is also persisted on its audit row (AnkEntitlementTokenIssues) rather than derived on demand — grace policy can change, and a revocation sweep that re-derived "when does this token leave the field?" under the new policy would sweep entries early or late. The row records the promise as it was made.

The published key set: complete, versioned, absence is authoritative

  • Complete, never a delta. A client replaces its cached set wholesale. Deltas require the client to merge, and a missed delta means a key that should be gone is still trusted.
  • Monotonic version (derived from key count + withdrawals) so a stale set can never overwrite a fresher one.
  • Signed as a unit, so a network position cannot feed the device a key it likes.
  • Absence is authoritative — even for keys bundled in the installer. Shipping first-run keys in the app binary is fine for bootstrap, but a bundled key missing from the current published set is not trusted. Otherwise a withdrawn-because-compromised launch key would remain valid on every install forever.

Revocation without a naming problem

The revocation list is downloaded by every device of every customer. If revoking a subscriber meant publishing their subscriber id, the list would be a public feed of "these families cancelled / were cut off". So nothing on the list identifies anyone:

  • At issue, every token gets an rvh — 16 random bytes, base64url. Random, not derived: a hash of the subscriber id would be brute-forceable offline against a list of known ids.
  • Revoke one token → its jti is listed.
  • Revoke a subscriber → the handles of their outstanding tokens are listed. A device checks its own token's rvh against the list; an outsider sees opaque strings with no join key to any person.
  • Every entry carries SweepAfter = the persisted grace end of the token it kills. Past that moment the token is dead by expiry anyway, so the entry leaves the list — the list stays small because it only ever covers tokens that could otherwise still be alive.
Honest limit Revocation reaches a device when the device next fetches the list. A machine that stays offline through its token's whole grace window never learns — that is the floor set by "works offline", and it is bounded: grace ends, and the token dies of old age at most 37 days after issue.

Why BouncyCastle

OptionVerdict
.NET 10 base class libraryNo Ed25519. (NIST curves and RSA only.)
NSec / libsodiumExcellent, but a native binary per runtime identifier — a packaging tax on every platform the desktop client and server ship to.
BouncyCastle.Cryptography 2.7Chosen. Pure managed, one NuGet package everywhere, mature Ed25519.

The dependency is quarantined behind IEd25519Signer — a two-method interface (sign, verify) over raw 32-byte keys — implemented in Aonik.Infrastructure. SharedKernel's verifier and the Subscriptions issuer see only the interface, so if the BCL grows Ed25519, the swap is one file. The implementation pre-checks lengths and maps any provider exception to false: a verifier must have exactly two outcomes, and "threw" is not one of them.

What is deliberately not here yet

  • HTTP endpoints for token fetch, key set, and revocation list — the services and formats are done and fully tested; exposing them is a thin FastEndpoints slice for when the desktop client is ready to consume them.
  • Device binding enforcement — dev is carried in the payload; deciding how hard to bind (and what a family's device limit is) is product policy.
