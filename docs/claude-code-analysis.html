AONIK · Backend Code Review · Consolidated Edition

A disciplined codebase, with a short list of gaps that outrank the cleanup.

The backend reads like the work of a careful team: a clean modular monolith, a single migration stream, an immutable double-entry ledger, and AI audit records designed in from the start. It is not broadly over-engineered — the speculative parts are localized and mostly deletable in an afternoon. But consolidating a second independent review against my own surfaced a cluster that matters more than any simplification: a few places where money can change state without touching the ledger, AI mutations that execute without the approval gate the docs promise, and access control looser than a financial platform should run. Fix those first. The over-engineering is real, but small, and it can wait its turn.

02Reading the signal

The scary numbers are mostly noise. The real work is specific.

A quick scan turns up things that look like over-engineering: 200-plus interfaces, files past 1,500 lines, five DbContexts over one database, reader/writer interface splits. Read the code and almost all of it is justified — the interfaces are the module-isolation seams the architecture requires, the long files are cohesive vertical slices, and the multi-context design is a deliberate, documented choice with a single migration stream behind it.

So this review separates signal from noise. The genuine over-engineering is small and nameable: a prompt subsystem with no consumers, a workflow engine that throws on half its node kinds, route-policy columns that enforce nothing, an event seam with no handlers. Each is a clean deletion. But consolidating a second review sharpened where the real risk sits — and it isn't the speculative code. It's a cluster of financial-correctness, audit, and access-control gaps that a simplification-only lens would walk straight past. This edition leads with those, then returns to the cleanup.

C1

The immutable ledger has no uniqueness guard against double-posting a source event

CriticalCorrectnessverified ✓
Evidence src/Aonik.Finance/Persistence/Configurations/JournalEntryConfiguration.cs:36 — builder.HasIndex(x => x.SourceId) is non-unique. There is no composite unique index on (TenantId, SourceType, SourceId), yet every journal entry is keyed to exactly that source event.

Why it matters

The ledger is your declared source of financial truth: double-entry and immutable. Each entry traces back to a SourceType + SourceId pair, but nothing at the database level stops the same source event from being journalled twice. A retried command, a redelivered integration event, or a double-submitted action posts duplicate entries that both look perfectly valid. Because the ledger is immutable you can't simply delete the duplicate — you're into reversing entries and a reconciliation that no longer ties out. This is the one finding that can silently corrupt financial truth.

Suggested fix

Add a composite unique index on (TenantId, SourceType, SourceId) via a tool-generated migration — never hand-authored, per the migration rules. First query for and resolve any existing duplicates, then let the unique index become the structural guarantee that each source event posts exactly once. Pair it with idempotent posting in LedgerService so a duplicate command is a no-op rather than a unique-constraint exception on the hot path.

Impact HighEffort LowTheme Financial correctness
C2

Payments reach Captured and invoices reach Paid without ever touching the ledger

CriticalCorrectnessverified ✓
Evidence src/Aonik.Finance/Services/Payments/PaymentService.cs:96 — CapturePaymentAsync sets Status = Captured and saves; the service takes no ILedgerService dependency at all. src/Aonik.Finance/Services/Billing/BillingService.cs:175 — MarkInvoiceAsPaidAsync sets Status = "Paid" and saves. Neither writes a journal entry.

Why it matters

This is the architecture's own non-negotiable rule — "the ledger is the source of financial truth" — quietly unmet on the two paths where money is supposed to have moved. A captured payment and a paid invoice are exactly the economic events a double-entry ledger exists to record, yet both mutate a status column and stop there. The result is a system that believes it has been paid while the ledger that's meant to prove it stays silent, so balances and reconciliation drift apart by construction. Worse, because the status flips without a ledger post, C1's missing uniqueness guard isn't even the backstop here — there's nothing to double-post against.

Suggested fix

Route both transitions through LedgerService inside the same transaction that flips the status, so capture and mark-paid each emit the balanced journal entry they represent (and become idempotent via C1's unique key). If a transition legitimately shouldn't post yet, make that explicit in the status model rather than implicit in a missing call. This is the highest-value correctness fix on the list — it reconnects the money paths to the truth they're supposed to write.

Impact HighEffort MediumViolates ledger-is-truth rule
C3

Mutating AI & MCP tools are not approval-gated in code — only by convention

CriticalGovernanceverified ✓ · corrects a draft claim
Evidence ApprovalRequiredAIFunction appears only in markdown/docs — never in any .cs file. The mutating tools register through plain AIFunctionFactory.Create: InvoiceTools.cs:130–141, PaymentTools.cs:67–72, LedgerTools.cs:76–82, and the orchestrator simply AddRanges them (MasterOrchestratorService.cs:547–554). The only "approval" is a frontend confirmAction prompt.

Why it matters

"Agents propose; systems execute — never bypass human-in-the-loop for mutations" is a stated invariant, and the architecture is documented as enforcing it with an ApprovalRequiredAIFunction wrapper. That wrapper does not exist in the source. So CreateInvoice, CreatePaymentIntent, ledger tools and the rest are exposed to the model as directly-callable functions, and the human gate is a UI convention a different client (or a future server-side agent loop) can skip entirely. An invariant enforced only in prose is an invariant you don't have — and this is the one I most expected to find true. (It corrects a claim in my first-pass draft, which mistook the documented design for the implemented one.)

Suggested fix

Make the gate structural: wrap every mutating tool in a real approval-required decorator at registration time so a tool that mutates state cannot be invoked without a recorded, granted approval — independent of which UI is in front of it. Read tools keep executing directly. Then add a test that fails if a mutating tool is registered un-wrapped, so the invariant can't silently regress again.

Impact HighEffort Medium–HighInvariant in docs, not in code
C4

The MCP host grants every permission and auto-clears compliance, ungated

CriticalSecurityGovernanceverified ✓
Evidence src/Aonik.Ai/Mcp/McpHostingStubs.cs:68–75 returns a permission set that grants everything; :131–141 auto-approves the compliance check. src/Aonik.Finance.Mcp/Program.cs:26–37 hosts the finance tools over this stub with no gate in between.

Why it matters

The MCP surface is how external/agent callers reach finance tools, and the host that's supposed to authorize them is a permissive stub: it answers "yes" to every permission query and clears every compliance check automatically. Combined with C3 (no approval wrapper on the tools themselves), there is no layer between an MCP client and a state-mutating finance operation that ever says no. On a platform whose autonomy is supposed to be bounded by risk tier and compliance, this is an open door wearing the label of a locked one — the stub looks like governance while implementing none.

Suggested fix

Replace the stub permission/compliance provider with the real one before the MCP host is reachable outside local dev, and treat "all permissions granted" as a configuration that only a test profile can select. The compliance check should call the actual compliance service, not return cleared. If the stub is genuinely dev-only, fail fast at startup when it's loaded in any non-development environment so it can never ship enabled.

Impact HighEffort MediumPairs with C3
C5

The global tenant filter fails open — a missing tenant returns every tenant's rows

CriticalSecurityCorrectnessverified ✓
Evidence src/Aonik.SharedKernel/Persistence/AonikDbContextBase.cs:166–172 — the global query filter admits all rows when CurrentTenantId is null. The predicate is composed via Expression.Property(Expression.Constant(this), nameof(CurrentTenantId)) (152–218), which can also bake a per-instance value into the expression tree and undercut plan caching.

Why it matters

On a multi-tenant financial platform the safe default for "I don't know whose data this is" must be show nothing. Here it's the opposite: any code path that reaches the database without an established tenant context — a misconfigured background job, an early-pipeline query, a future endpoint that forgets to set tenancy — sees across all tenants. That's a cross-tenant data-exposure waiting for the wrong call site. The expression also captures this as a constant, a shape that can defeat EF/SQL plan reuse (worth confirming against the captured SQL, but the form is a smell). One filter, carrying both a security default and a performance footgun.

Suggested fix

Make the filter fail closed: a null tenant yields no rows, and genuinely global entities opt out explicitly through the IsGlobalEntity() hook that already exists. Rewrite the predicate to reference a context property the EF way so the tenant id parameterizes and plans are reused. Both changes live in one place and protect every query that flows through it.

Impact HighEffort Low–MediumFail-closed + plan caching
H1

Spending insights aggregate in C# instead of in SQL

HighPerformanceverified ✓
Evidence src/Aonik.PersonalFinance/Services/PersonalFinance/PersonalFinanceInsightsService.cs:249 — query.ToListAsync() materializes the full period's transactions; the GroupBy/Sum then run in memory (category 73–88, merchant 113–122, dominant-currency 271–277).

Why it matters

Every spending-summary, category, and merchant call pulls a user's entire transaction range into process memory and rolls it up there. For an active account that's thousands of rows transferred and garbage-collected to produce a handful of totals. The cost scales with history size, not result size — the opposite of what you want on a per-tenant hot path a dashboard hits repeatedly. It's the single biggest in-memory-aggregation offender I found.

Suggested fix

Push the aggregation into the database with GROUP BY projections (SUM/COUNT). The correct shape already exists in this codebase — copy BudgetService.GetSpentByCategoryAsync:163–173. Where two groupings are needed (e.g. currency normalization), run two grouped queries rather than one full materialization. This is the template fix wherever the pattern recurs.

Impact HighEffort MediumPattern exists in-repo BudgetService
H2

A read-heavy platform tracks every query and pools no contexts

HighPerformanceverified ✓
Evidence Zero QueryTrackingBehavior overrides anywhere in src; the change tracker is opted out by hand 430 times across 108 files (AsNoTracking). All seven contexts register with AddDbContext<T> — none with AddDbContextPool<T>.

Why it matters

Two systemic defaults work against a read-mostly workload. (1) Tracking: EF's default is track-everything, compensated for with 430 hand-placed AsNoTracking calls — pure overhead on the paths that remember it, and a latent bug on the paths that forget, which silently pay change-tracker cost and can even persist accidental mutations on a read path. (2) Pooling: every request constructs a context from scratch; pooling recycles the internal plumbing and measurably cuts per-request allocation under load. Neither is a smell in any one place — they're the wrong global defaults for this system's shape.

Suggested fix

Set QueryTrackingBehavior.NoTrackingWithIdentityResolution as the default in each context's options, then delete the 430 AsNoTracking calls and opt into tracking explicitly on the far fewer write paths. Switch registrations to AddDbContextPool<T>. Both are mechanical and high-leverage — the kind of one-time edit that quietly speeds up the whole platform.

Impact HighEffort Low–Medium430 AsNoTracking calls to retire
H3

The ledger balance check sums across currencies

HighCorrectnessverified ✓
Evidence src/Aonik.Finance/Services/Ledger/LedgerService.cs:246–256 — the debit/credit balance validation sums line amounts without grouping by currency, so a multi-currency entry can "balance" while no single currency does.

Why it matters

Double-entry only means something per currency: debits must equal credits in each currency, not in a blind total across them. Summing all lines together lets an entry that is 100 USD debit against 100 EUR credit pass the balance check, posting an entry that is not actually balanced in any real sense. On a cross-border platform (RemitExchange is a stated product) multi-currency entries aren't an edge case, so this validation can wave through genuinely unbalanced postings into the immutable ledger.

Suggested fix

Group the lines by currency and assert debits equal credits within each group, rejecting the entry if any currency fails. If cross-currency entries are intended, they need explicit FX legs that balance per currency — not a single summed check that hides the imbalance.

Impact HighEffort LowPer-currency invariant
H4

Order mapping loads parties one line item at a time (N+1)

HighPerformanceverified ✓
Evidence src/Aonik.Finance/Services/Orders/OrderService.cs:774–811 — MapOrderAsync loops the order's items (778–781); MapOrderItemAsync calls LoadPartyAsync per item (811).

Why it matters

An order with N line items issues N party lookups on top of the order's own. Render a list of orders and the N+1 compounds into N×M queries. This is the textbook mapping-time N+1: invisible in a three-row demo, a real tail-latency and database-load problem once orders carry many items and lists page through many orders. Orders are the canonical record of a financial service, so this sits on a path that matters.

Suggested fix

Collect the distinct party ids across all items first, load them in one Where(p => ids.Contains(p.Id)) round-trip, and resolve each from an in-memory dictionary while mapping. The codebase already does exactly this in PersonalFinanceInsightsService.GetAccountBreakdownAsync (the accountMap pattern) — mirror it.

Impact HighEffort MediumPattern exists in-repo accountMap
H5

Order idempotency can be defeated by tenant, whitespace, or a race

HighCorrectnessverified ✓
Evidence src/Aonik.Finance/Services/Orders/OrderService.cs:191–215 — the idempotency lookup omits TenantId and compares an untrimmed incoming key against a trimmed stored one. src/Aonik.Finance/Persistence/Configurations/OrderConfiguration.cs:82 — the IdempotencyKey index is non-unique, so two concurrent requests can both pass the check.

Why it matters

Order idempotency is the guard that stops one customer intent from becoming two financial services. Three holes undercut it: the lookup isn't tenant-scoped (so keys can collide or miss across tenants), a trailing space makes "the same" key miss its match, and without a unique index two simultaneous submissions race past the read-then-write check and both create an order. The failure mode is duplicate orders — duplicate transfers, duplicate collections — which is precisely what the key exists to prevent.

Suggested fix

Normalize (trim) the key on the way in, scope the lookup by (TenantId, IdempotencyKey), and make that pair a unique index via a tool-generated migration so the database — not a read-then-write window — enforces single-creation. Treat the unique-constraint violation as "return the existing order," turning a race into a no-op.

Impact HighEffort Low–MediumTenant + trim + unique index
H6

Payment intents are created with placeholder payer/method, and capture is unreachable

HighCorrectnessverified ✓
Evidence src/Aonik.Finance/Services/Payments/PaymentService.cs:45,49 — PayerPartyId = Guid.Empty and PaymentMethodType = "Card" are hardcoded TODOs. Intents start at Pending (42), but CapturePaymentAsync only proceeds when status is Authorized (91–93) — a state nothing in the service ever sets.

Why it matters

Two problems on the core payment path. First, every intent records an empty payer and a hardcoded "Card" method, so the data that should identify who paid, how is fiction — a problem for audit, reconciliation, and any compliance view. Second, the capture guard is a closed loop: intents are born Pending, capture demands Authorized, and no code performs the authorize transition, so by its own state machine capture can never succeed. The path looks implemented but is effectively inert, which is worse than an obvious gap because it passes a glance.

Suggested fix

Carry real PayerPartyId and payment-method details on the create request (or resolve them from context) instead of placeholders. Then make the state machine coherent: either add the authorize step that produces Authorized, or allow capture directly from Pending if that's the intended flow. Whichever you choose, the statuses the code checks must be states the code can actually reach. This also unblocks C2 — capture can't post to the ledger until it can run.

Impact Medium–HighEffort MediumUnreachable Authorized state
H7

Orchestrator sessions live in a static, in-process dictionary

HighScalabilityverified ✓
Evidence src/Aonik.Agents/Framework/MasterOrchestratorService.cs:45–51 — static ConcurrentDictionary<string, AgentSession>: unbounded and process-local.

Why it matters

One field, two problems. (1) It blocks scale-out: agent session state is pinned to a single process, so the moment you run two API instances behind a load balancer — or recycle one — sessions vanish or route to the wrong node. Horizontal scalability is a stated goal, and this quietly prevents it. (2) It leaks: nothing evicts entries, so under sustained traffic the dictionary grows without bound. It works perfectly on one box in dev and fails the day you add the second.

Suggested fix

Move session state to a shared, evictable store: FusionCache (already in the stack) over the distributed cache, or a DB table keyed by session id with a TTL. If profiling later shows a hot read, keep an in-process dictionary only as an L1 cache in front of the shared store — never as the source of truth.

Impact HighEffort Medium–HighBlocks horizontal scale-out
H8

The transactional outbox has no row-claim, so it double-dispatches under scale-out

HighCorrectnessScalabilityverified ✓
Evidence src/Aonik.Infrastructure/Outbox/OutboxProcessor.cs:69–76 reads unprocessed messages and dispatches without claiming them; src/Aonik.SharedKernel/Outbox/OutboxMessage.cs:33–45 has no lock/claim column, and its own XML doc (18–20) admits double-dispatch is possible.

Why it matters

The outbox is the right pattern for reliable integration events, but with no row-claim two worker instances (or two ticks that overlap) select the same unprocessed rows and dispatch them twice. The code comment already concedes this. For at-least-once consumers that's tolerable; for anything that isn't strictly idempotent downstream, a redelivered OrderCreated or payment event can drive duplicate side effects — and it only manifests once you scale the worker past one instance, which is exactly when you need it to hold.

Suggested fix

Claim rows before dispatch: an atomic UPDATE … SET ClaimedBy/ClaimedAt WHERE Processed = 0 AND ClaimedAt IS NULL with OUTPUT (or UPDLOCK, READPAST) so each message is taken by exactly one worker, then mark processed after success and reclaim on timeout. This makes the outbox safe to run on every instance instead of secretly single-writer.

Impact Medium–HighEffort MediumSafe past one worker
H9

A recurring sync job runs under Guid.Empty and so sees no real tenant data

HighCorrectnessverified ✓
Evidence src/Aonik.Worker/Jobs/FinancialConnectionRecurringSyncJob.cs:50–78 — the job sets the tenant context to Guid.Empty and never enables an across-tenants mode, so the global tenant filter scopes every query to a tenant that owns nothing.

Why it matters

This is a live bug, not a latent one: the recurring financial-connection sync executes against tenant Guid.Empty, which matches no real tenant's rows, so it does its work over an empty set and silently accomplishes nothing. Connections that should be refreshed aren't — and because it fails quietly (no error, just no data) it's the kind of gap that surfaces as "why is this account stale?" weeks later. It also shows the flip side of C5: when the filter is the only thing scoping tenancy, a job that sets the wrong tenant id disappears its own data.

Suggested fix

Give the job a real cross-tenant execution mode — enumerate tenants and run per-tenant with each tenant's context set, or use the sanctioned across-tenants escape hatch if one exists — rather than a placeholder id. Pair it with H11's enumerator fix so the worker iterates tenants the same disciplined way everywhere.

Impact HighEffort LowLive bug · sync does nothing
H10

Hot list endpoints return unbounded result sets

HighPerformanceScalabilityverified ✓
Evidence src/Aonik.Finance/Services/Billing/BillingService.cs:252–266 — ListInvoicesAsync does Include(Lines) with no Take and no AsNoTracking. src/Aonik.Finance/Services/Ledger/LedgerService.cs:317–333 — ListJournalEntriesAsync is likewise unbounded.

Why it matters

List endpoints with no upper bound are fine until the first tenant with real history hits them: the invoice list eager-loads every line of every invoice, and the journal-entry list returns the entire ledger range. Both grow without limit, so a single call can pull tens of thousands of rows, spike memory and latency, and — because these are the screens people leave open — do it repeatedly. The cost is unbounded by design, which is the scalability problem you don't see in testing.

Suggested fix

Introduce mandatory pagination (page size + continuation/skip-take) on every list path and add AsNoTracking on the read. A sane default page cap protects the server even when a caller forgets to pass one. This pairs with H2 — once tracking is off by default, these reads only need the paging.

Impact Medium–HighEffort Low–MediumAdd pagination caps
H11

Worker tenant/user enumerators materialize everything in memory

HighPerformanceScalabilityverified ✓
Evidence src/Aonik.Worker/Jobs/CustomerInsightSnapshotJobUserEnumerator.cs:29–58 and CustomerInsightAiSummaryJobSnapshotEnumerator.cs:35–57 load the full cross-tenant set of users/snapshots into memory before iterating.

Why it matters

These background jobs walk every tenant's users (and snapshots) by pulling the entire population into a list first, then looping. At small scale it's invisible; as the platform grows it becomes a job that allocates proportionally to total users across all tenants on every run — the worst scaling shape for a periodic task, and a memory spike that can starve the worker process. It's the batch-side mirror of H1/H10: aggregate-in-memory instead of stream-from-database.

Suggested fix

Stream in tenant-scoped batches: page the query (keyset/skip-take) and process each page, or iterate tenants then users-within-tenant, so working-set stays bounded regardless of total population. Combined with H9, give the worker one disciplined "for each tenant, scoped" iteration helper and route all these jobs through it.

Impact MediumEffort MediumStream, don't materialize
H12

Read-only and personal roles are admitted to a finance-mutating policy

HighSecurityverified ✓
Evidence src/Aonik.Api/DependencyInjection.cs:382–385 — AdminUserPolicy is satisfied by roles including ReadOnly and PersonalUser; endpoints guarded only by that policy (e.g. the finance admin endpoints at :20) therefore accept those roles.

Why it matters

A role literally named ReadOnly should never satisfy a policy that authorizes state changes, yet it's enumerated among the principals that pass AdminUserPolicy. Any endpoint relying on that policy as its mutation gate is open to read-only and ordinary personal users — a straightforward privilege-escalation/authorization gap on financial operations. It's the kind of mistake that's easy to make when one broad policy guards endpoints of mixed sensitivity, and easy to miss because everything still "works" for legitimate admins.

Suggested fix

Split the policy by intent: a read policy that may include ReadOnly, and a distinct mutation/admin policy that does not. Remove ReadOnly (and PersonalUser, unless deliberate) from anything that authorizes writes, and audit each endpoint to ensure it references the policy matching its actual effect. Add a test asserting ReadOnly is denied on a representative mutating endpoint.

Impact HighEffort LowAuthorization gap
H13

Plaid account webhooks are anonymous and unverified

HighSecurityverified ✓
Evidence src/Aonik.Finance/.../AccountLinkEndpoints.cs:313–330 and the PersonalFinance equivalent :310–327 are AllowAnonymous; src/Aonik.Infrastructure/.../PlaidAccountWebhookProcessor.cs:35–75 processes the body without verifying a webhook signature.

Why it matters

An anonymous, unsigned webhook endpoint that drives financial-connection state is an endpoint anyone on the internet can call with a forged body. Without signature verification there's nothing to distinguish a real Plaid callback from a spoofed one, so an attacker can push fabricated account events into the sync pipeline. Webhooks have to be anonymous (the provider isn't carrying your auth), which is exactly why the signature check is the security boundary — and it's missing.

Suggested fix

Verify the Plaid webhook signature (JWT/HMAC per their scheme) before doing any work, reject anything that doesn't validate, and treat the verified payload as the only trusted input. Keep the endpoint anonymous but make signature validation a hard precondition in the processor, not an afterthought.

Impact HighEffort MediumVerify webhook signature
H14

Streaming AI responses complete without an AiRun audit record

HighGovernanceverified ✓
Evidence src/Aonik.Ai/Middleware/AuditMiddleware.cs:30–104 — the streaming branch (92–95) returns the stream without writing an AiRun; the non-streaming branch records one. Streaming is the primary path for chat and voice.

Why it matters

"Every AI action is auditable, recorded as an AiRun" is a non-negotiable rule, and the most-used surface — streamed chat and voice — slips through it. The audit middleware records buffered responses but hands back the streamed ones unrecorded, so the interactions users actually have most often leave no governance trail. That's both a compliance gap (no record of what the AI did or was asked) and a blind spot for cost/usage accounting on the busiest path.

Suggested fix

Wrap the streamed response so the run is opened before the first token and finalized when the stream completes or faults — capturing the same fields the non-streaming path records, plus terminal status. The structured metrics writer that already exists (see H17) is the natural place to land the completion, so streaming and non-streaming converge on one audit shape.

Impact HighEffort Low–MediumBusiest path is unaudited
H15

Chat-thread endpoints are anonymous, with only weak per-user scoping

HighSecurityverified ✓
Evidence ListChatThreadsEndpoint.cs:24, GetChatThreadEndpoint.cs:24, ArchiveChatThreadEndpoint.cs:24 are AllowAnonymous. ChatThreadService.cs:155–209 scopes by the EF tenant filter but the per-user ownership check is weak.

Why it matters

Worth stating precisely, because my verification refined the second review's claim here: threads are tenant-scoped through the global EF filter, so this is not a cross-tenant leak. The real gap is two-fold — the endpoints are anonymous (no authenticated principal required at all), and within a tenant the per-user ownership check is thin, so one user reading or archiving another's threads isn't firmly prevented. Chat content is sensitive (it can contain financial detail), so "anyone unauthenticated, loosely scoped per user" is the wrong posture even with tenant isolation intact.

Suggested fix

Require authentication on these endpoints (drop AllowAnonymous) and enforce ownership explicitly — filter and authorize by the authenticated user id, not only the tenant filter — so a thread is reachable only by its owner (or an admin policy). The tenant scoping stays as defense-in-depth underneath.

Impact Medium–HighEffort LowTenant-safe · user-weak
H16

Per-request tenant resolution blocks on async

HighPerformanceverified ✓
Evidence src/Aonik.Infrastructure/Authentication/TenantResolver.cs:48,67 — .GetAwaiter().GetResult() on async tenant lookups during subdomain resolution, on the request hot path.

Why it matters

Sync-over-async blocks a thread-pool thread while waiting on I/O, and under load that's the classic path to thread-pool starvation — the failure mode that looks fine in testing and tips over at peak. Tenant resolution runs for every authenticated request, so it's the worst possible place to block: the cost is paid on 100% of traffic.

Suggested fix

Make the resolution path async end-to-end (ResolveAsync) and await it from the middleware. If a synchronous interface is forcing the .GetResult(), widen that interface rather than papering over it — the call sites are few.

Impact Medium–HighEffort LowOn every request
H17

The AI run writer re-reads the row it just inserted — and the middleware skips its metrics

HighPerformanceGovernanceverified ✓
Evidence src/Aonik.Ai/Services/AiRunWriter.cs:138–227 — the common path is insert → save → FirstOrDefaultAsync the same row → update → save. M7

Entity lookups are by id alone, not id-plus-tenant

MediumSecurityverified ✓
Evidence src/Aonik.Finance/Services/Payments/PaymentService.cs:68–69,77–78,107–108 — get/capture/cancel resolve the intent by Id only; several order/payment lookups follow the same shape, relying entirely on the global query filter for isolation.

Why it matters

Today these are safe because the global tenant filter scopes them — but that makes the filter the single point of failure for isolation, which is exactly the dependency C5 shows is fragile (it fails open when tenant context is missing). Suggested fix

M8

Indexes aren't tenant-leading, and the outbox dispatch index is unfiltered

MediumPerformanceverified ✓
Evidence InvoiceConfiguration.cs:51–54, OrderConfiguration.cs:79–85, PaymentIntentConfiguration.cs:39–42 define single-column indexes that don't lead with TenantId; OutboxMessageConfiguration.cs:22–23 indexes dispatch state without a filtered/leading predicate on unprocessed rows.

Why it matters

On a platform where virtually every query is implicitly WHERE TenantId = @t (the global filter), indexes that don't lead with TenantId force the database to do more work than it should to isolate a tenant's slice — the composite the workload actually wants isn't there. The outbox dispatch index is the mirror image: without a filter on "unprocessed," the poller scans more than the small hot set it cares about. Neither is catastrophic, but both are leaving free performance on the table on the hottest paths.

Suggested fix

Make the common indexes tenant-leading composites ((TenantId, …)) matching the real query predicates, and add a filtered index for the outbox poller (WHERE Processed = 0) so dispatch touches only pending rows. All via tool-generated migrations. Confirm against actual query plans before committing the set.

Impact Low–MediumEffort MediumTenant-leading composites
M9

Manual transactions run under an EF retrying execution strategy

MediumCorrectnessverified ✓
Evidence src/Aonik.PersonalFinance/Services/.../HouseholdService.cs:239 and FinancialLifeGraphWriteService.cs:67–68 open manual BeginTransaction blocks while the context is configured with EnableRetryOnFailure.

Why it matters

EF's retrying execution strategy can't safely retry a user-initiated transaction, because on a transient failure it would replay only part of the work — so the documented contract is that manual BeginTransaction must be wrapped in strategy.ExecuteAsync(...). Used directly under EnableRetryOnFailure it throws InvalidOperationException at runtime, or worse, leaves a half-applied multi-step write if the retry semantics aren't honored. These are multi-entity writes (household, life-graph), exactly where partial application matters.

Suggested fix

Wrap each manual transaction in the context's execution strategy (Database.CreateExecutionStrategy().ExecuteAsync(async () => { using var tx = …; … })) so the whole unit retries atomically, or use the ambient transaction EF manages. Grep for every BeginTransaction and apply the same wrapping uniformly.

Impact MediumEffort LowWrap in execution strategy
M10

Startup swallows migration and seed failures

MediumCode qualityverified ✓
Evidence src/Aonik.Infrastructure/.../DatabaseStartupConfiguration.cs:98–114 catches and logs migration/seed exceptions but lets startup continue; src/Aonik.Api/Program.cs:67 invokes it without treating failure as fatal.

Why it matters

If a migration or seed fails, the safest outcome is usually don't start — a process that boots on a half-migrated schema serves traffic against a database that doesn't match the model, producing duplicate-column errors, missing-table exceptions, and the schema-drift cascade the project's own migration rules are written to prevent. Swallowing the failure converts a loud, fail-fast startup error into a quiet, intermittent runtime one that's far harder to diagnose.

Suggested fix

Let migration failures be fatal in normal operation: log and rethrow so the host exits non-zero and orchestration can halt the rollout. If there's a legitimate "degraded start" scenario, gate it behind explicit configuration rather than making swallow-and-continue the default. Pair with the project rule to verify applied migrations post-deploy.

Impact MediumEffort LowFail fast on schema drift
M11

Generic exceptions and ad-hoc entity-to-DTO mapping recur across services

MediumCode qualityverified ✓
Evidence Services throw InvalidOperationException for distinct domain conditions (not-found, invalid-state, permission) — e.g. across PaymentService/BillingService/OrderService — and each service hand-maps entities to DTOs in private MapToResponse helpers rather than a shared convention.

Why it matters

Two low-grade but pervasive consistency issues. Using one generic exception type for "not found" vs "invalid state" vs "forbidden" means endpoints can't translate failures into the right HTTP status without string-matching messages, and callers can't distinguish them programmatically. And per-service hand mapping means the same entity gets projected slightly differently in different places, with no single point to change a shape. Neither is urgent; together they're friction the disciplined parts of the codebase don't have.

Suggested fix

Introduce a small set of domain exceptions (NotFoundException, InvalidStateException, ForbiddenException) mapped centrally to status codes in one exception handler, and converge mapping on one approach (consistent projection helpers or a mapper) so a DTO shape has a single home. Apply incrementally — this is a tidy-as-you-touch item, not a campaign.

Impact Low–MediumEffort MediumTidy as you touch
M12

CORS and forwarded-headers configuration is broader than it should be

MediumSecurityverified ✓
Evidence src/Aonik.Api/.../CorsConfiguration.cs:61–64,90–93 allows a null origin alongside credentials; src/Aonik.Api/Program.cs:81–84 enables forwarded headers without restricting KnownProxies/KnownNetworks.

Why it matters

Two hardening gaps. Permitting a null origin while also allowing credentials weakens the same-origin protection CORS exists to provide — null origin is reachable from sandboxed iframes and some redirects, so credentialed cross-origin requests become possible from contexts you didn't intend to trust. And enabling forwarded headers without a known-proxy allowlist lets a client spoof X-Forwarded-For/Proto, which downstream code may trust for client IP, rate limiting, or scheme decisions. Both are "works fine until probed" settings.

Suggested fix

Drop null origin from any credentialed CORS policy and enumerate real allowed origins. Restrict forwarded-headers processing to known proxy addresses/networks so only your ingress can set those headers. Neither change affects legitimate traffic; both close a spoofing avenue.

Impact Low–MediumEffort LowTighten origins + proxies

05Calibration

Looks like over-engineering. Isn't.

A fair review has to say what's not a problem, or every big number becomes a false alarm. These are the metrics that look damning at a glance and turn out to be sound engineering once you read the code. Both review passes agreed: leaving them alone is the correct call.

NOISE200-plus interfaces

Almost all are the module-isolation seams ADR-006 mandates — cross-module contracts that live in SharedKernel so modules never reference each other directly. That's the price of a modular monolith, not over-abstraction. Only flag the handful with zero implementations (see M4).

NOISEFiles past 1,500 lines

Long, yes — but cohesive vertical slices: one service owning one area. Length here tracks scope, not tangled complexity, and splitting purely for a line count would scatter cohesion across files. The genuine exception is M5, which is long and doing several jobs in the wrong module.

NOISEFive DbContexts over one database

A deliberate, documented design: module contexts give DI scoping and runtime isolation while a single canonical context owns the only migration stream. This is how the codebase avoids snapshot drift — a strength, not duplication. (The repeated table mapping inside it is the only real tidy-up — M14.)

NOISEReader/writer splits & anemic entities

The read/write seams are a sensible CQRS-lite split; the anemic entities are intentional per the platform's own rule that logic lives in services. Both are conventions applied consistently, which is exactly what you want — flag them only where one half has no implementation.

08Don't touch these

Patterns worth protecting.

The spine of this system is good. These are the decisions that make the rest of the review small — keep them, and resist refactors that erode them. One carries a caveat, because the design is right but the enforcement isn't there yet.

Single migration stream

All schema changes flow through one canonical context, tool-generated. It's why the codebase doesn't suffer snapshot drift — the discipline behind it is doing real work, and the C1/H5 fixes ride on it.

Module isolation via contracts

The PersonalFinance ↔ Finance read boundary — Order/Invoice/Payment through SharedKernel contracts with no direct project reference — is genuinely well executed. It's the proven pattern M15 should extend to the last few coupled edges.

Immutable double-entry ledger + Orders as canonical

A strong domain spine: financial truth in the ledger, intent in Orders, never collapsed. C1, C2 and H3 protect this invariant where the plumbing currently sidesteps it — they don't replace it.

AI auditability — designed in, not yet enforced

The AiRun audit model and risk-tier governance are the right architecture. But the human-in-the-loop approval wrapper exists only in docs (C3) and streaming runs aren't recorded (H14). Keep the design; close the enforcement gap before relying on it.

Transactional outbox

The right backbone for reliable integration events. It needs a row-claim to be multi-instance safe (H8) and has an unused in-process handler seam to drop (M4) — but the pattern itself is sound, keep it.

House rules

Banned-API analyzers, decimal money discipline, optimistic concurrency via RowVersion, anemic entities. Consistent, enforced conventions — add warnings-as-errors (M6) and the set is complete.

09How this review was done

Method & scope.

Approach

Module-scoped exploration passes — SharedKernel/Platform, Finance, PersonalFinance, Ai, Agents, Infrastructure/Api/Worker — plus cross-cutting searches for systemic patterns (query tracking, context pooling, interfaces without implementations, sync-over-async, in-memory aggregation, anonymous endpoints). This edition then consolidated a second independent agent review into the findings, rather than presenting them side by side.

Verification

Every consolidated claim was re-checked against current source through four parallel verification passes before earning a place here; each finding cites file:line and carries a verified ✓ marker. Where re-verification changed a conclusion, the change is documented in §06 — including a correction to my own first-pass draft (C3).

Scope

Backend services under src/Aonik.* only. Explicitly out of scope: everything in apps/* (including the Payabo app), the AdminUi React frontend, and AdminDesktop. The PersonalFinance backend module is in scope — it's the Payabo substrate, not the Payabo application.

Lens & limits

The brief was architecture, performance, scalability, and — above all — simplification and over-engineering; consolidation widened it to the financial-correctness, audit, and access-control gaps a second pass surfaced. This is a senior-review opinion, not a formal security audit or proof of correctness. Validate each fix against your own benchmarks and production data before shipping.

One-line takeaway. This is a well-built platform with a spine worth protecting — but ship Phase 1 and 2 before the cleanup: reconnect the money paths to the ledger (C1, C2, H3), make the AI approval and tenant defaults real in code (C3–C5), then flip the performance defaults and delete the five speculative pockets. Do that and you have a codebase that's not just clean and enterprise-ready but visibly simpler and safer than it was — without rewriting anything that mattered.
