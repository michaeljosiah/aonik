1.Executive summary

Simi needs five object types and three verbs from the backend: a CareEntity (a person or asset you look after — Mum, the Lagos flat, the car), a Commitment (a rhythm of support), a PaymentLog (an act that honoured it), a Document (the proof), and a CircleMember (someone who sees a slice) — captured, reminded, and proved. I mapped each against the AONIK codebase with file-level evidence.

The result is encouraging and specific. Of the twelve backend capabilities Simi requires, five are production-ready today, three are partial (real infrastructure, missing only the Simi-specific slice), and four need genuinely new work — but every "new" item lives inside an existing module (PersonalFinance, Documents, Ai) and rides infrastructure that is already built and shipping. None requires a new platform primitive. The launch plan's "the hard parts already exist" claim is true for the machinery (auth, blob storage, Quartz reminders, FCM push, the read-tool agent, the AiRun audit) — and the rebuild spec's §8.6 mapping is too optimistic for four of its rows, which this plan corrects.

The shape of the work
Two backend lifts are real and deserve respect: the commitment cycle-lifecycle (mark-done → roll forward, skip, snooze, per-cycle history — none of which exists) and the Circle's entity-scoped sharing (today's households share whole bank accounts with already-registered users; Simi needs link-invited members scoped to one person or place, with a documents-only role that hides every amount). The other four — a neutral CareEntity model, a PaymentLog module, the capture-parse endpoint, and Document↔entity linking — are each a thin slice over an existing module. The Keeper Q&A is almost pure configuration.

Sequenced correctly, this is not a platform project. It is a series of thin endpoints that land alongside mobile milestones M2–M5, each one demonstrable, each one honouring the launch plan's merge rule. The total is meaningfully more than the spec's "thin endpoints" sentence implies — but it is still additive, module-local, and free of the 27k-LOC drift the launch plan warns against, provided the guardrails in §10 hold.

2.Method — how this was assessed

I read the three Simi documents end to end, extracted the backend obligations (the four promises, the five-object model in §3.2, the data contracts in §8, and the capture API in §8.5), then audited the codebase for each — reading entity definitions, endpoint Configure() auth scoping, and service interfaces rather than trusting names. Where a capability looked present, I checked whether it is customer-facing (callable by a consumer PersonalUser JWT) versus admin-only, and whether senders/jobs are actually wired versus interface-only. Verdicts below cite file evidence so they can be challenged.

One correction worth stating up front, because it recurs: several endpoints carry an AdminUserPolicy / AdminUserWritePolicy name but those policies include the PersonalUser role — so they are consumer-reachable despite the "admin" label. Documents are the clearest case: a consumer can already upload and list. The gaps there are linking and sharing, not access.

4.The leverage — what already exists

Before the gaps, the honest good news. These are built, tested, and shipping, and Simi rides them with little or no backend work:

  • Identity & auth, end to end — OAuth2 token/refresh, individual registration, email + phone OTP verification, profile + photo, multi-tenant context. The mobile app already authenticates against it.
  • Blob document storage — a real FluentStorage abstraction (DocumentFileStore), tenant-scoped keys, SHA-256 content hashing; consumer upload/list reachable via the PersonalUser role. The Vault stands on this.
  • Scheduled-reminder machinery — a Quartz WorkItemDispatchJob runs every minute, scans due WorkItems, and a NotifyUserTaskActionHandler turns them into notifications + push. Bill creation already schedules a due-date reminder through it.
  • Push + in-app notifications — a real FCM sender (FirebasePushNotificationSender) integrated into NotificationService, plus DB-backed in-app notifications with an SSE stream and a full template/binding system.
  • The conversational-AI stack — a customer chat endpoint (POST /ai/chat) and AG-UI streaming (POST /ai/agui), a master orchestrator, and a PersonalFinanceAgent carrying 20+ read tools over accounts/transactions/commitments/spending. Read tools execute without approval; every call is tenant + user scoped.
  • The audit + safety spine — the AiRun record with a one-shot writer, and the tool-approval gate (low/medium/high) that already enforces "agents propose; systems execute" — the exact rule the capture review screen depends on.
  • Manual commitment creation — POST /personal-finance/bills persists a user-authored bill (payee, frequency, next-due, amount, currency) with no transaction required; SourceTransactionId is nullable and Origin = "Manual" is a first-class value.
Why this matters for the estimate
Every gap below is a slice over this list, not a foundation under it. That is precisely what makes a part-time, agent-assisted backend cadence realistic: there is no platform to build, only endpoints to add.

5.The gaps — six things to build

Six gap areas, each with what Simi needs, what exists, the precise delta, and the evidence. They are ordered by the mobile milestone that consumes them.

5.1 CareEntity — People & Assets

New (thin)

What Simi needs

A neutral, customer-owned entity for a person ("Mum") or an asset you look after — a property ("Surulere flat"), but equally land, a car, a business stake, or a foreign account — each with a country, owning commitments, payment history, documents and totals, plus a one-call getProfile(id) returning the lot (rebuild spec §7.6, §8.1, §8.3; and the positioning's continuity north star — "anything a loved one would leave").

What exists

A Party model, but PartyType is validated to "Person" | "Organization" only — no asset/place of any kind. The only neutral, customer-facing entity CRUD is the generic financial-life-graph node API. The remittance Recipients surface is customer-facing but payout-coupled (Spec 008) — exactly what M0 deletes.

The delta

  • A generic asset concept, not just "place": kind = person | asset, an open assetType (property · land · vehicle · business · account · other-with-label), and an attributesJson bag for type-specific detail (a vehicle's registration, a property's address) so no migration is needed to add "boat".
  • A neutral care-entity CRUD not tied to payouts/beneficiaries.
  • A one-call profile projection (entity + per-currency totals + commitments + recent logs + document refs) — today this would be several queries against the graph.
Party.cs — PartyType free string; FinanceValidators.cs — .Must(t => t is "Person" or "Organization") · /parties create = AdminUserPolicy (admin) · /personal-finance/graph/nodes = UserPolicy (customer, but generic) · Recipients = customer-facing but "payout-beneficiary party graph (Spec 008)".
The guardrail that keeps "any asset" from drifting
An asset of any type still gets only the five primitives — commitments, documents, payment history, totals, circle-scope. No valuations, no net-worth rollup, no per-type management tooling. A car gets insurance/road-tax commitments and a logbook document, not a depreciation curve; the flat gets a service charge and a deed, not a rent ledger. The moment "asset" means "a thing to value" rather than "a thing to pay for and document," it becomes a net-worth tracker and trips Guardrail 1. Your freeze list already says this for places — generalise the restraint, not just the entity.

Mobile knock-on: the pre-build CareEntityKind enum broadens to match, and an "Asset" category alongside "Person" strengthens the case for the spec's fallback "Yours" tab label (§12.4) over "People & Places".

5.2 Commitment cycle-lifecycle & rhythm

Partial

What Simi needs

A user-authored support commitment attached to a CareEntity, with a rhythm rich enough for "monthly on the 28th" and "termly", and a per-cycle lifecycle: mark-done (writes a PaymentLog and rolls nextDue forward), skip (with reason, recorded), snooze (to a date / to payday), pause, and a visible per-cycle history (rebuild spec §7.3, §8.2).

What exists

ICommitmentService exposes only detection verification — ConfirmDetectedAsync / RejectDetectedAsync. Frequency is a free string (Daily…Annually). LastPaidAt/LastPaidAmount are scalars.

The delta

  • No mark-done / roll-forward anywhere — NextDueDate is set once and never advances.
  • No skip / snooze; Status has a "Paused" value but no service method sets it per cycle.
  • No anchor-day or termly rhythm, and no roll-forward date math (clamp 29–31 → month end, explicit termly dates).
  • No per-cycle history entity — only the two "last paid" scalars.
  • A commitment can't yet point at a CareEntity (today it has a Payee string + PaidFromAccountId).
ICommitmentService.cs — interface is List/Get/CreateFromTransaction/Confirm/Reject only · PersonalRecurringBill.cs — Frequency string, NextDueDate, no anchor day, no CareEntityId · FinancialLifeGraphRetrievalService.cs — frequency switch has no "Termly".

5.3 PaymentLog

New (budgeted)

What Simi needs

An act of support: attached to a commitment (rolling it forward) or standalone (the one-off plumber), in its original currency (+ optional ≈£), with a channel (bank/Wise/cash), an origin (manual / capture-image / capture-voice / mark-done / plaid-detected), receipt attachments, and a note. Plus a per-currency year summary for the Today hero and entity totals, and — when a linked account exists — a link back to the bank transaction that corroborates it (rebuild spec §3.2, §8.1, §8.3, and the §11 corroboration / auto-capture fast-follows).

What exists

Manual transactions exist, but they are spending records — no CareEntity attribution, no commitment-roll-forward, no receipt linkage, no per-currency support totals. Helpfully, commitment-detection already hangs a nullable SourceTransactionId off a detected commitment, so the link-a-record-to-a-transaction pattern is established. The spec flags PaymentLog as the one new module.

The delta

  • The whole PaymentLog aggregate + CRUD, idempotent create (for the offline capture queue), soft-delete with restore.
  • A nullable sourceTransactionId + corroborationStatus (none | matched | confirmed) — the bank-evidence link.
  • A per-currency aggregation projection (yearSummary) — totals are listed per currency, never converted.
  • Wiring so mark-done writes a PaymentLog and a capture-confirm writes one too.
Three layers, and why the link matters
The transaction does not link to the commitment directly — it links through the act: Transaction (bank evidence) → PaymentLog (the act, this cycle) → Commitment (the rhythm). Linking a transaction straight to a commitment would lose per-cycle granularity ("which month did this £200 satisfy?"). The sourceTransactionId unlocks three things: the auto-capture nudge ("£200 to Wise — Mum's allowance?"), the "verified against linked account" statement column, and — the one the spec doesn't name — deduplication: if the user manually captures a payment and Plaid imports the same debit, the link collapses them into one log instead of double-counting and corrupting the year total. The link is the dedup key.
No PaymentLog entity in src/Aonik.PersonalFinance/Entities · transactions = spending model, not support acts · PersonalRecurringBill.cs — existing nullable SourceTransactionId precedent · launch plan §7 budgets "payment-log CRUD" as the one new module.

5.4 Document linking, filter & selective share

Partial

What Simi needs

A consumer tags each document with a person/place + type; filters by person/place/year; links a document to a PaymentLog (the receipt) and a CareEntity; and shares specific documents to a circle member with a documents-only role (rebuild spec §7.7, §7.8).

What exists

Customer upload/list (via PersonalUser in AdminUserWritePolicy), real blob storage, an OwnerPartyId, and a TagsJson field. A signed-URL reader exists at the service layer.

The delta

  • No link from a document to a CareEntity or a PaymentLog/receipt — only OwnerPartyId + untyped TagsJson.
  • No filter-by-entity/year query exposed to the consumer.
  • Selective document sharing to a scoped circle member is absent (depends on §5.6).
  • A consumer file-download / signed-URL endpoint to confirm (list-files exists; content fetch to verify).
Document.cs — OwnerPartyId, TagsJson (untyped), no CareEntityId/PaymentLogId · create/upload = AdminUserWritePolicy which includes PersonalUser · DocumentFileStore.cs — real blob, tenant-scoped keys.

5.5 Capture parse endpoint

New · severable (M4)

What Simi needs

POST /ai/capture/parse: accept an image (base64 receipt/screenshot), text, or audio-transcript plus hints (the user's entities + open commitments) and return a structured draft proposal (matched entity, matched commitment, amount+currency, date, channel, per-field confidence) — never auto-saved, recorded as an AiRun (rebuild spec §8.5).

What exists

The one-shot AiRun audit writer; schema-constrained structured output for sub-agents; deterministic CSV statement-import (not a vision template). ChatRequest takes a string only.

The delta

  • Vision/multimodal input — no image path into the LLM today.
  • The endpoint itself, returning a proposal draft (not a saved record), audited as an AiRun, with entity/commitment hints constraining the match to near-classification.
AiRunWriter.SaveRunAsync — one-shot audit exists · InsightsStructuredModels.cs etc. — schema-constrained output exists for sub-agents · ChatRequest.cs — Message string only, no image · no /ai/capture/parse route.

5.6 The Circle — entity-scoped sharing

New · the big one

What Simi needs

Invite someone (who may not be a registered user) by shareable link / email / phone; they accept and get scoped read access. Three presets — everything · specific people/places · documents-only — where a documents-only member (the property manager) sees no amounts anywhere, and a scoped member sees exactly one CareEntity (rebuild spec §7.8).

What exists

Households with an invite lifecycle and three roles (Owner/Manager/Viewer). The sharing unit is the whole bank account (account.HouseholdId); invites are by existing UserId only; PermissionsJson exists but is never enforced.

The delta

  • Invite a not-yet-registered person — today EnsureUserExistsWithPersonalProfileAsync throws if the UserId isn't already registered; no token/link/email/phone path.
  • Entity-scoped visibility — HouseholdMember has no scoping field; access is all-or-nothing within a household.
  • A documents-only, no-amounts role — roles only vary read/write; nothing masks money.
  • Re-point the share unit from bank accounts to CareEntities/people-places — the whole "share the flat with Seyi, hide it from Mr Bello's view of amounts" model.
HouseholdMember.cs — no ScopedEntityId/visibility field · InviteHouseholdMemberEndpoint — request is Guid UserId; HouseholdService.cs — EnsureUserExistsWithPersonalProfileAsync throws "User not found" · PersonalAccountService.ShareAccountWithHouseholdAsync — share unit is the account; all members see all amounts · HouseholdRoles.cs — Owner/Manager/Viewer only.

10.Guardrails — against backend drift

The launch plan's central fear is that the backend eats the mobile push again (it has, twice). This plan is only safe if it stays disciplined. Five rules, borrowed from the launch plan and CLAUDE.md and made backend-specific:

  • The merge rule is law. No backend PR merges in a week whose mobile milestone has no commits. The backend serves the app's current milestone — never races ahead to Phase D while the app is on M2.
  • Thin endpoints over existing modules. If a work item starts to feel like a new module, a new platform primitive, or tenant-agent extensibility, stop — that is the documented drift. Everything here lives in PersonalFinance, Documents, or Ai.
  • Single migration stream, tool-generated only. All schema changes through AonikDbContext via the EF CLI; never hand-written, never against a module context (the rule that kept Spec 042 clean).
  • No money movement, no FX. Simi's backend stores amount + currency and displays it; it never converts, never posts to the ledger, never calls a partner. That is Payabo, gated on the slow track.
  • Severable AI. Phase C is isolated. If the founder cuts the Keeper, the backend drops one endpoint + a toolset and everything else ships unchanged.
The one-question test for any backend task
Does this unblock the mobile milestone in flight, as a thin endpoint over an existing module, without moving money? If not, it is drift — log it for later, don't build it now.
