Technical Documentation

The AONIK Data Model

AONIK persists every product — billing, the ledger, payments, orders, personal finance, compliance and AI governance — into one physically shared SQL Server database, mapped by EF Core. The schema is organised module-first: each domain module owns its own slice of tables and entity configurations, while a single canonical DbContext owns the one migration stream. This document explains how the database is structured, how multi-tenancy is enforced in the data layer, where entity relationships are configured, and — table by table — what every part of the schema is for.

01Foundations

What the schema is, and why it is shaped this way#

AONIK uses EF Core to map anemic domain entities to a SQL Server schema, organised across domain modules that all share a single physical database. Modules exist for ownership and runtime isolation, not for separate databases: every module reads and writes the same SQL Server instance, and every table lives in the dbo schema for backward compatibility with the existing migration history.

The schema encodes a small number of platform rules that the rest of the data model is built around. Knowing these four makes every table below make sense:

⚖️

Orders say why, payments say how

An Order is the canonical record of a requested financial service. Payments and payouts are how it is funded and executed. They are kept in separate tables and never collapsed into one another.

📒

The ledger is financial truth

Double-entry JournalEntries and their lines prove what happened. BalanceSnapshots are a reporting cache derived from those lines — never a replacement for them.

🔒

Tenant-scoped by default

Most tables carry a TenantId and are filtered at query time. A deliberate few config/reference tables are global (TenantId = NULL) and shared across all tenants.

🧾

Auditable & soft-deleted

Many tables carry CreatedAt/By, UpdatedAt/By and soft-delete fields, applied uniformly by the shared DbContext base rather than per entity.

The organising idea

Orders describe why money should move; payments and payouts describe how; the ledger proves what happened. The schema keeps these three concerns in separate tables on purpose — collapsing them is the one modelling mistake the platform is built to prevent.

The module map

The schema is organised by domain module. Each owns a set of subdomains:

02Foundations

DbContexts & the single migration stream#

Every DbContext inherits from AonikDbContextBase (in SharedKernel), the abstract base that provides tenant query filters, audit stamping and soft-delete handling. Above it sit one canonical context and four module contexts — all mapped over the same physical database.

DbContext hierarchyshared base
AonikDbContextBase  // SharedKernel — abstract: tenancy, audit, soft-delete
 ├── AonikDbContext     // Infrastructure — canonical; owns ALL DbSets; the ONLY migration stream
 ├── PlatformDbContext   // Platform module — runtime read/write; no migrations
 ├── FinanceDbContext    // Finance module  — runtime read/write; no migrations
 ├── AiDbContext         // AI module       — runtime read/write; no migrations
 └── AgentsDbContext     // Agents module   — runtime read/write; no migrations

Single migration stream — non-negotiable

All EF Core migrations are generated against AonikDbContext only; it is the only context whose migrations are applied at startup. Module-scoped contexts exist for DI scoping and runtime isolation, not for independent migration streams — never generate migrations against PlatformDbContext, FinanceDbContext, AiDbContext or AgentsDbContext.

03Foundations

Tenant isolation in the data layer#

AONIK is multi-tenant, and isolation is enforced at the persistence layer rather than left to callers. The same four mechanisms apply to every DbContext, because they all inherit from AonikDbContextBase.

ITenantScoped
The marker interface (defined in SharedKernel) that tenant-scoped entities implement. It is what the base class keys its filters and write-time checks on.
Query filters
AonikDbContextBase applies EF Core global query filters for tenant-scoped entities whenever a tenant context is available, so reads are transparently narrowed to the current tenant.
Write-time safeguards
SaveChangesAsync stamps the current TenantId onto new entities and enforces that modifications and deletions cannot cross tenant boundaries.
Nullable globals
Some AI/agent configuration entities allow a nullable TenantId for global visibility — e.g. Agent, OrchestratorPolicy, AiRoutePolicy — as does shared reference data (currencies, countries).
The tenant-scoped write path
1
Resolve current tenant
The tenant context is established for the request/job before any entity is tracked.
2
Reads are filtered
Global query filters narrow every ITenantScoped query to the current tenant automatically — no explicit WHERE TenantId needed.
3
Inserts are stamped
On SaveChangesAsync, new entities receive the current TenantId.
✓
Cross-tenant writes are blocked
Modifications and deletions that would touch another tenant's row are rejected before they hit the database.
Fail-closed by construction

Because isolation lives in the shared base class, a module cannot accidentally opt out of it. When no tenant context is present the filter exposes only global (TenantId = NULL) rows — never another tenant's data. See Tenant Management for tenant identification, testing patterns and the full security considerations.

04Foundations

Entity relationships & configuration conventions#

Relationships are defined with the EF Core Fluent API in IEntityTypeConfiguration<T> classes, and each domain module owns its own configurations. The canonical AonikDbContext aggregates all of them for migrations; each module context applies the configurations from its own assembly at runtime.

Platform
src/Aonik.Platform/Persistence/Configurations/
Finance
src/Aonik.Finance/Persistence/Configurations/
AI
src/Aonik.Ai/Persistence/Configurations/
Agents
src/Aonik.Agents/Persistence/Configurations/
Infrastructure
src/Aonik.Infrastructure/BackgroundJobs/Entities/ (background jobs only)

Conventions when adding relationships

  • Prefer explicit Fluent API configuration over data annotations.
  • Keep domain entities anemic — simple data containers, no behaviour methods.
  • Place the configuration file in the owning module's Persistence/Configurations/ directory.
  • Cross-module references use read models (e.g. PartyReadModel in Finance) rather than direct entity dependencies, so modules stay decoupled.
A note on entity namespaces

The CLR type names in this document (e.g. Aonik.Domain.Billing.Entities.Invoice) reflect the names stored in migration history. The actual source files now live in their module projects — e.g. src/Aonik.Finance/Entities/Billing/Invoice.cs. The per-table entries below show the short entity name under each table.

06Schema · Finance

Orders#

The Orders subdomain is the business-intent hub: it captures why money should move and orchestrates funding and fulfilment without ever being the payment itself. An order fans out to funding refs, fulfilment refs, items, party roles, and an append-only history.

Order vs Payment vs Ledger

An Order links out to its funding (OrderFundingRefs → PaymentIntents) and its fulfilment (OrderFulfilmentRefs → Payouts), but it is neither a payment nor a journal entry. That separation is the spine of the whole money model.

08Schema · Finance

Ledger#

The ledger is the source of financial truth: a tenant's accounting boundary (Ledgers), its chart of accounts (LedgerAccounts), and the immutable double-entry record (JournalEntries + JournalEntryLines).

Double-entry, and it must balance

A JournalEntry is one accounting event that groups balanced debit/credit lines; the full set of JournalEntryLines must net to zero. BalanceSnapshots precompute balances for reporting and performance — they do not replace the journal entries.

The party graph#

A Party is the canonical representation of a person or business — customers, merchants, senders, receivers. Profiles, addresses, contacts, consents, external accounts, relationships and business-role assignments all hang off the party.

Person vs Business

A Party is typed by PartyType. People carry a PersonProfile (KYC data); organizations carry a BusinessProfile (KYB data). PartyRelationships connect them — e.g. a business to its owner person.

ConventionWhat it means
