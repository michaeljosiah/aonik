Executive Summary

AONIK has a strong modular-monolith foundation, good domain separation intent, clear migration ownership, and a useful AI governance vocabulary. The most important risks are not basic style issues. They are enforcement gaps around AI mutation approval, tenant isolation fail-open behavior, incomplete auditability of LLM calls, unbounded high-volume queries, and cross-module coupling that undermines the intended clean architecture.

The biggest simplification opportunity is to reduce duplicate runtime surfaces. Today there are separate in-process agent tools, MCP tools, broad DbContext facades, duplicate PersonalFinance ownership in Finance and PersonalFinance, and several hand-rolled validation/error paths. Senior engineers will likely view the platform as promising but still carrying too many parallel abstraction paths for its current maturity.

Recommended priority: fix safety and isolation first, then performance hot paths, then simplify module boundaries and duplicated abstractions. Do not add more abstractions before retiring the duplicate ones already present.

CriticalMutating AI agent tools are not enforceably approval-gated

src/Aonik.Finance/Agents/Tools/InvoiceTools.cs:120-141
src/Aonik.Finance/Agents/Tools/PaymentTools.cs:57-72
src/Aonik.Finance/Agents/Tools/LedgerTools.cs:80-82
src/Aonik.Agents/Framework/MasterOrchestratorService.cs:113-122

Mutating tools are plain AIFunctionFactory.Create(...) functions. The code comments say approval is enforced by a frontend confirmAction tool, but prompt instructions and UI conventions are not a security boundary. A model, MCP client, playground, test harness, or future client can invoke the mutating tools directly.

Why it matters: this violates the project rule that agents propose and systems execute, and that mutating tools require ApprovalRequiredAIFunction. It is the highest-risk AI governance gap because it can mutate financial state.

Suggested fix: create one server-side tool registration path that marks each tool as read-only or mutating. Wrap every mutating function in MAF ApprovalRequiredAIFunction, and add tests that enumerate tools and fail if known mutating tool names are exposed without approval metadata.

CriticalFinancial state transitions bypass ledger proof

src/Aonik.Finance/Services/Payments/PaymentService.cs:74-99
src/Aonik.Finance/Services/Billing/BillingService.cs:163-176

CapturePaymentAsync changes a payment intent status to captured without creating or linking ledger entries. MarkInvoiceAsPaidAsync changes invoice status to paid without ledger linkage.

Patterns To Preserve

PreserveCanonical migration ownership is clear. Keeping migrations in AonikDbContext is the right direction for a modular monolith sharing one physical database.

PreserveModule registration methods keep composition understandable. Aonik.Api/Program.cs wiring through module extension methods is cleaner than scattering service registrations across the API host.

PreserveAnemic entities and service-owned business logic are consistent with the repo rules. The backend generally follows the intended pattern of simple entities plus application/domain services.

PreserveThe AI governance concepts are the right ones. AiRoutePolicy, AiRun, prompt specs, agent descriptors, and proposal services are useful building blocks. The issue is enforcement consistency, not the direction.

Recommended Next Steps

  1. Safety sprint: enforce approval-gated mutating AI/MCP tools, secure MCP stubs, fix chat-thread auth, and make tenant filters fail closed.
  2. Financial integrity sprint: tenant-scope all financial lookups, enforce order/payment idempotency, connect capture/mark-paid flows to ledger posting, and fix multi-currency ledger validation.
  3. Scale sprint: add pagination to ledger/invoice lists, make outbox claiming multi-worker safe, move worker enumeration batching into SQL, and add tenant-leading/filtered indexes.
  4. Simplification sprint: centralize tool metadata, finish PersonalFinance namespace/context extraction, remove Platform-to-Finance coupling, and replace broad DbContext runtime usage with narrow module contracts.
