## Objective

Implement a production-grade personal finance customer insight pipeline that:

1. deterministically computes a complete, factual, customer-level financial insight snapshot from AONIK data
2. stores that snapshot as a versioned, queryable artifact
3. generates an AI interpretation from the deterministic snapshot as a separate derived artifact
4. projects both artifacts into the existing personal finance agent prompt context via the `UserBrief`

This specification is intentionally aligned with the current AONIK codebase and fixes the gaps in the existing behavioural insight implementation.

## Problem Statement

The current implementation contains useful primitives but does not yet satisfy the intended product behavior.

Current issues:
- `src/Aonik.Worker/Jobs/BehaviouralInsightJob.cs` schedules a behavioural insight routine, but it only computes a small subset of heuristic insights.
- `src/Aonik.Finance/Services/PersonalFinance/BehaviouralInsightGenerator.cs` creates a few independent text insights rather than a complete customer-wide financial insight artifact.
- `src/Aonik.Ai/Services/InsightWriter.cs` stores only generic prose fields and drops structured data needed for deterministic reuse.
- `src/Aonik.Ai/Services/UserBriefAiDataProvider.cs` expects user-linked behavioural insight rows, but the current writer path does not populate `UserId`, so prompt grounding is incomplete.
- `src/Aonik.Finance/Services/PersonalFinance/PersonalFinanceNarrativeInsightsService.cs` uses the LLM directly against spending data, but this is a second-stage interpretation workflow, not the first-stage deterministic customer insight layer.
- There is no canonical, versioned per-customer snapshot that represents the complete factual financial state and derived metrics for later AI interpretation.

## Goals

- Generate a deterministic, reproducible customer insight snapshot for each personal finance customer.
- Cover the customer's financial position across balances, transactions, spend, bills, subscriptions, goals, budgets, and derived behavioural signals.
- Store the snapshot in a structured, versioned format suitable for audit, rehydration, and downstream reuse.
- Generate an AI summary from the snapshot as a distinct derived artifact with `AiRunId` linkage.
- Preserve clear separation between factual data, deterministic derivations, and AI interpretation.
- Feed the personal finance agent with a compact prompt projection that includes both factual grounding and AI interpretation.
- Keep the design tenant-scoped, auditable, and aligned to existing AONIK agent and AI patterns.

## Non-Goals

- Replace the ledger as the source of truth for material money movement.
- Collapse personal finance insight generation into free-form LLM analysis.
- Store the prompt-ready `UserBrief` as the canonical system-of-record artifact.
- Let AI directly mutate customer financial state.
- Build a separate microservice or database just for insight generation.

## Architectural Principles

- Deterministic facts first; AI interpretation second.
- Storage models are not prompt models.
- Every AI interpretation must reference the deterministic snapshot it was derived from.
- The deterministic snapshot must be reproducible from the same inputs and rules.
- The system must preserve current-vs-historical versions rather than overwriting without trace.
- Prompt assembly should remain a projection step so the runtime agent gets a bounded, shaped context.

## MVP Simplifications

The initial implementation should stay intentionally lean.

- Use one canonical `CustomerInsightSnapshot` entity in the Finance module.
- Use one canonical `CustomerInsightAiSummary` entity in the AI module.
- Use one JSON document per canonical artifact.
- Use the existing Worker scheduling model rather than introducing a new orchestration platform.
- Do not require separate persisted signal-level generic `Insight` records in the MVP.
- Do not require advanced resilience patterns beyond timeout handling, failure isolation, and retry on later scheduled runs.
- Do not require additional prompt-persistence models beyond the existing `UserBrief` projection path.
- Split internal helper classes only if the implementation becomes materially easier to understand or test.

## Target Architecture

The target design is a three-model architecture.

### 1. Deterministic storage model
`CustomerInsightSnapshot`

This is the canonical factual artifact for a customer at a specific point in time.

### 2. Derived AI interpretation model
`CustomerInsightAiSummary`

This is an LLM-produced interpretation of the deterministic snapshot and must always reference both `CustomerInsightSnapshotId` and `AiRunId`.

### 3. Prompt projection model
`UserBrief`

This remains the runtime prompt-facing model. It composes data from:
- deterministic customer snapshot
- AI summary
- user memory
- recent conversation memory
- policy context
- selected live finance data if needed

The `UserBrief` is not the source of truth. It is the prompt adapter.

## Domain Separation

### Deterministic customer insight snapshot
Contains:
- exact values
- counts
- percentages
- time windows
- deterministic classifications and signals
- evidence references

Does not contain:
- narrative prose generated by an LLM
- speculative advice
- ambiguous confidence without a deterministic basis

### AI summary
Contains:
- customer-facing or agent-facing synthesis
- prioritization and interpretation
- notable patterns explained in natural language
- recommended conversational focus areas
- metric references back to snapshot sections

Does not replace the deterministic snapshot.

### User brief projection
Contains:
- only what the runtime prompt needs
- a compact subset of deterministic snapshot data
- a compact subset of AI interpretation
- current policy and conversation context

## Deterministic Snapshot Specification

### Purpose

Provide a complete, concrete, auditable, customer-wide view of personal finance state and derived metrics without using an LLM.

### Recommended entity

Add a new tenant-scoped entity:

- `src/Aonik.Finance/Entities/PersonalFinance/CustomerInsightSnapshot.cs`

Recommended fields:
- `Id` (Guid)
- `TenantId` (Guid)
- `UserId` (Guid)
- `Status` (string) // `Current`, `Superseded`, `Failed`
- `AsOfUtc` (DateTime)
- `WindowStartUtc` (DateTime)
- `WindowEndUtc` (DateTime)
- `Version` (int)
- `SourceHash` (string)
- `SnapshotJson` (string)
- `GeneratedBy` (string) // generator name/version
- `GenerationDurationMs` (int?)
- `FailureReason` (string?)
- `SupersededById` (Guid?)
- `CreatedAt` / `UpdatedAt` via `AuditableEntity`

### JSON storage decision

Use one canonical `SnapshotJson` column rather than separate `MetricsJson`, `SignalsJson`, and `EvidenceJson` columns.

Rationale:
- the snapshot is the canonical system-of-record artifact and should be treated as one versioned document
- a single JSON payload simplifies serialization, persistence, and schema evolution
- logical separation is still preserved inside the JSON document without forcing physical storage separation
- the system is expected to read and write the snapshot primarily as a whole artifact

The JSON document should still contain explicit top-level sections such as:
- `metrics`
- `signals`
- `evidence`

This keeps the internal model structured while avoiding unnecessary column fragmentation.

#### Identity and coverage
- `userId`
- `tenantId`
- `asOfUtc`
- `analysisWindow`
- `currencies`
- `dataCoverage`

#### Cash position

#### Income summary

#### Expense summary

- month-over-month expense delta
- average weekly and monthly spend

#### Category insights
- top categories by amount
- top categories by share of spend
- category trend deltas
- category concentration ratio

#### Merchant insights
- top merchants by amount
- top merchants by frequency
- recurring merchant candidates
- merchant concentration ratio

#### Obligations and commitments
- upcoming bills
- subscriptions
- support obligations
- total upcoming obligations in lookahead period
- obligation coverage ratio vs available balance

#### Budget and planning
- active budgets
- categories above threshold usage
- overspent categories

#### Savings and goals
- active goals
- goal progress rates

#### Behavioural signals
- late-month spend spike
- payday spending pattern

- volatility indicators

- dormant subscription indicators
- repayment burden trend

#### Risk and attention flags

#### Evidence

- account ids used
- date ranges used
- excluded data counts
- rule versions used

### Transaction normalization prerequisites

The snapshot generator should consume normalized transaction semantics rather than infer core transaction meaning from scratch on every snapshot run.

#### Transfer identification timing

Internal transfer identification should happen primarily at transaction creation and import time, with later reconciliation as needed.

Recommended approach:
- when manual transactions are created, account-to-account movements should be recorded as internal transfers when the intent is explicit
- when transactions are imported, deterministic transfer matching should run during normalization
- when a matching counterpart arrives later from another account or a later import, background reconciliation may upgrade an unmatched or candidate transfer to a confirmed internal transfer

This keeps snapshot generation deterministic and efficient because the generator reads normalized transaction state instead of re-discovering transfer pairs from raw data on each run.

#### Transfer normalization model

The system should preserve raw transaction facts while also storing normalized semantics used by insight generation.

Recommended normalized concepts:
- transaction kind or normalized kind
- transfer status
- transfer group or correlation identifier
- linked counterpart transaction identifier where known
- normalization version

The exact field names may vary, but the semantics should exist before snapshot logic depends on them.

#### Transfer treatment in snapshots

Snapshot generation should treat transfers explicitly.

Rules:
- confirmed internal transfers must be excluded from income totals and expense totals
- confirmed internal transfers may appear in transfer-specific metrics or evidence sections
- candidate or weakly matched transfers should not be auto-excluded from income or expense totals unless the deterministic rules are strong enough to promote them to confirmed transfers
- candidate transfer counts and warnings should be recorded in snapshot coverage or evidence metadata when they may affect interpretation

## Multi-Currency Policy

The snapshot must handle multi-currency customers explicitly.

### Canonical rule

The canonical deterministic snapshot should preserve native-currency facts.

Rules:
- do not silently sum monetary values across different currencies
- store balances, inflows, outflows, and other primary money metrics per currency
- when cross-account insights span multiple currencies, the snapshot should expose the customer view in a currency-aware structure rather than flattening into a single total by default

### Optional reporting-currency view

If product needs require a single summarized total across currencies, that view must be produced through an explicit deterministic FX policy.

If a reporting-currency view is implemented, the policy must define:
- reporting currency selection rule
- FX source
- rate timing rule
- rounding rule
- handling when a required FX rate is unavailable

This reporting-currency view is optional for MVP. The canonical snapshot remains the native-currency view.

### Cross-currency transfers

Cross-currency transfers between a user's own accounts must still be treated as transfers rather than income plus expense.

Where identifiable, the system should preserve:
- source amount and currency
- destination amount and currency
- deterministic FX rate used or implied
- identifiable fees if present

### Source hash boundary

The `SourceHash` boundary must be explicitly defined before implementation.

The purpose of `SourceHash` is to determine whether the current deterministic snapshot has materially changed and therefore whether a new snapshot version should be created.

The hash must be computed from a canonical serialized input envelope containing:
- `UserId`
- `TenantId`
- `WindowStartUtc`
- `WindowEndUtc`
- generator or rule version
- deterministic configuration values and thresholds used for the calculation
- normalized source data used to compute the snapshot

The normalized source data should include the relevant customer financial inputs, such as:
- personal accounts
- personal transactions
- bills
- subscriptions
- budgets
- goals
- related support obligations or other deterministic finance-domain dependencies used by the snapshot generator

Where transaction normalization exists, the hash should be based on normalized transaction semantics used by the snapshot generator rather than volatile import-order artifacts.

The hash boundary must exclude volatile or non-semantic fields such as:
- snapshot `Id`
- `CreatedAt`, `UpdatedAt`
- generation duration
- runtime-only timestamps unrelated to the analysis window
- AI outputs
- prompt text
- database row order

Canonicalization requirements:
- all source collections must be sorted with a stable ordering before serialization
- null and empty values must be normalized consistently
- numeric precision and date formatting must be consistent
- cross-currency handling rules must be explicit and consistent

Implementation rule:
- if the newly computed `SourceHash` matches the current snapshot for the same customer and analysis window policy, the system should not create a new snapshot version
- if the hash differs, the current snapshot should be superseded and a new current snapshot created

This boundary is required before implementation to avoid unstable versioning and inconsistent regeneration behavior.

## Insight Taxonomy And Time Horizons

To support rich background insight generation, the deterministic snapshot and derived AI summary should use a consistent insight taxonomy.

### Required insight categories

At minimum, the system should support these categories:
- `cashflow`
- `spending`
- `debt_repayment`
- `savings`
- `subscriptions`
- `budget_pressure`
- `goals`
- `risk`
- `anomalies`
- `trends`

These categories should be used consistently across:
- deterministic signals in `SnapshotJson`
- AI summary observations
- future admin or product surfaces that display customer insights

### Required time horizons

The snapshot generator should support explicit analysis horizons rather than relying on a single vague window.

Recommended defaults:
- `operationalWindowDays = 30` for current-state and near-term cashflow context
- `trendWindowDays = 90` for medium-term changes in behavior
- `behaviourWindowDays = 180` for broader historical pattern detection

Implementation guidance:
- the snapshot should record which horizon each metric or signal uses where the value is not based on the overall snapshot window alone
- the AI summary should not invent additional time horizons beyond what exists in the deterministic snapshot

## Trend And Emerging Pattern Detection

The deterministic layer should explicitly support trend and emerging-pattern detection so the AI summary is grounded in programmatic signals rather than intuition.

### Required first-wave detectors

The first implementation should include deterministic detectors for:
- repayment burden rising over time
- savings rate falling over time
- category spend acceleration
- recurring commitment growth
- income instability
- cash buffer deterioration
- merchant concentration increase
- sustained late-month spend spikes

### Detector output shape

Each detector should emit structured fields, for example:
- `signalKey`
- `category`
- `title`
- `description`
- `severity`
- `confidence`
- `windowStartUtc`
- `windowEndUtc`
- `metricRefs`
- `evidenceSummary`

These signal outputs should live inside the snapshot's `signals` section and be eligible for projection into the `UserBrief`.

### Multi-pass reasoning clarification

This specification does not require multi-pass LLM reasoning for the deterministic layer.

Instead, the intended AONIK approach is:
1. multiple deterministic calculation passes in code if needed to build metrics and detectors cleanly
2. one AI interpretation stage that reads the completed deterministic snapshot

This preserves determinism for factual insight generation while still allowing richer natural-language interpretation afterward.

## Confidence Model

The insight pipeline should define confidence explicitly.

### Deterministic signal confidence

Deterministic signals may expose confidence, but it must be code-defined and reproducible.

Allowed bases for deterministic confidence include:
- coverage sufficiency
- sample size sufficiency
- stability of the observed pattern across the relevant window
- consistency across multiple months or cycles

Deterministic confidence must not be arbitrary prose. It should be derived from documented rules.

### AI summary confidence

The AI summary may include confidence only when grounded in the deterministic snapshot.

Recommended approach:
- AI summary observations should reference the underlying deterministic signal confidence where applicable
- if the snapshot is partial or coverage is weak, the AI summary should explicitly reduce certainty or include caveats

### Confidence representation

Confidence may be stored as:
- numeric score, or
- normalized enum such as `Low`, `Medium`, `High`

Whichever representation is chosen, it must be used consistently across deterministic signals and AI summary references.

### Deterministic rules

All metrics and signals in the snapshot must be produced from code-defined rules only.

Requirements:
- use explicit analysis windows
- use stable ordering before truncation
- define thresholds in code or configuration, not prompt text
- capture generator version so outputs are attributable to a rule set
- calculate all percentages and ratios using documented formulas

### Completeness requirement

For each eligible personal finance user, generation should produce one cohesive snapshot artifact, not many disconnected insight rows.

It is acceptable to still generate secondary per-signal records later, but the canonical artifact must be the complete customer snapshot.

## Background Job Specification

### Job responsibilities

Replace the current small behavioural routine with a stable customer insight pipeline.

Execution host:
- use `Aonik.Worker` to run the scheduled batch generation for deterministic customer snapshots and AI summaries
- `Aonik.Api` may expose admin trigger and read surfaces, but it must not be the primary execution host for recurring batch generation
- this follows the current AONIK separation where background execution belongs in the Worker and operator control/query surfaces belong in API/Admin

Recommended jobs:

#### 1. Customer insight snapshot generation job
- enumerates eligible personal finance users deterministically
- computes snapshots
- persists current snapshot
- supersedes prior current snapshot if source hash changed

#### 2. Customer insight AI summary generation job
- finds latest current snapshots without current AI summary or with stale AI summary
- generates AI interpretation
- persists AI summary with `AiRunId`

These may be implemented as separate jobs or as a two-phase orchestrated pipeline.

### Deterministic user enumeration

The job must not use unstable `Distinct().Take(maxUsers)` patterns without ordering.

### Eligible customer definition

The batch job should operate on eligible personal finance customers only.

For the MVP, an eligible customer is a user who has at least one relevant personal finance domain record in the tenant, such as:
- `PersonalProfile`
- `PersonalAccount`
- `PersonalTransaction`
- `Bill`
- `Subscription`
- `Goal`
- `Budget`

Implementation guidance:
- the initial implementation may resolve eligible users via a deterministic union of distinct `UserId` values from the relevant tables
- the resulting user set must be stably ordered before paging or checkpointing is applied
- eligibility rules may be narrowed or optimized later, but they must remain explicit and testable

Requirements:
- order by stable key such as `UserId`
- support paging or checkpoints
- track run scope and completion progress
- allow eventual processing of all eligible users

### Idempotency and versioning

Snapshot generation must be idempotent.

Recommended behavior:
- compute a `SourceHash` from the relevant underlying inputs or canonical serialized source payload
- if the new hash matches the current snapshot hash, do not create a new snapshot version
- if the hash differs, insert a new current snapshot and supersede the old one

AI summary generation should behave similarly:
- one current AI summary per current snapshot and narrative version
- if the prompt/model/schema version changes, create a new AI summary version

## Runtime Safeguards

The first implementation should include lightweight operational safeguards, but should avoid overengineering.

### Required baseline safeguards

The following are required for the initial implementation:
- one slow or failing user must not fail the whole batch
- deterministic snapshot generation must run with a per-user timeout
- AI summary generation must run with a separate per-user timeout
- failures and timeouts must be recorded with duration and reason
- the batch must continue processing remaining users after an individual user failure
- timed-out or failed users should be retried on a later scheduled run

### Timeout guidance

The exact values may be tuned later, but the implementation should support explicit time budgets.

Recommended initial policy:
- deterministic snapshot warning threshold: 10 seconds
- deterministic snapshot hard timeout: 60 seconds
- AI summary warning threshold: 20 seconds
- AI summary hard timeout: 90 seconds

These values are intentionally conservative and should be configuration-driven.

### Partial snapshot policy

The specification should distinguish between critical and non-critical dependencies.

#### Critical source domains

The following inputs are critical for deterministic customer snapshot generation:
- personal accounts used to establish cash position and account coverage
- personal transactions used to establish inflows, outflows, spend patterns, categories, merchants, and derived signals
- analysis window configuration and rule version metadata required to make the snapshot reproducible

If these critical inputs cannot be loaded or normalized sufficiently for computation:
- do not persist a current snapshot
- record the attempt as failed
- include a concrete failure reason indicating which critical source domain was unavailable or invalid

#### Important but non-critical source domains

The following inputs are important, but snapshot generation may continue without them if the omission is explicitly recorded:
- bills
- subscriptions
- budgets
- goals
- household or support-obligation enrichments
- optional relationship or profile enrichments

If one or more of these non-critical domains is unavailable:
- allow generation of a partial snapshot
- omit only the affected sections or mark them as unavailable
- include coverage markers in `SnapshotJson`
- record the missing domains and omission reason in the evidence or coverage section

#### Coverage metadata requirement

`SnapshotJson` should include a coverage section that makes partial generation explicit.

Recommended coverage fields:
- `isPartial` (bool)
- `availableDomains` (array)
- `missingDomains` (array)
- `omittedSections` (array)
- `warnings` (array)

This ensures downstream readers, including AI summary generation and prompt projection, can reason about whether the snapshot is complete enough to use as-is.

### Slow-user handling

If a single user's snapshot generation repeatedly takes disproportionately long:
- fail or time out that user's current attempt
- record the last attempted phase where possible
- continue processing other users
- allow the user to be retried on the next scheduled run

The initial implementation does not need a dedicated recovery queue or advanced circuit-breaker framework.

### Observability requirements

At minimum, record per user:
- total generation duration
- phase durations where practical
- timeout/failure reason
- whether the snapshot was full or partial
- source counts used in generation

## Acceptance Criteria

- Every eligible personal finance customer can have exactly one current deterministic snapshot and historical prior versions.
- Snapshot generation is deterministic and reproducible from the same source data and rule version.
- Snapshot content includes concrete financial metrics and signals, not only prose summaries.
- AI summary is generated from the snapshot rather than directly from ad hoc live queries.
- Every stored AI summary references both `CustomerInsightSnapshotId` and `AiRunId`.
- The personal finance agent receives prompt context that includes both factual customer insight grounding and AI interpretation.
- The agent still functions when the AI summary is absent by falling back to deterministic snapshot data.

## Explicit Decisions

- Yes, a separate AI summary structure is required.
- Yes, the AI summary structure must align with the prompt projection but should not replace it.
- Yes, the deterministic customer snapshot is the primary artifact to build first.
- No, the current generic `Insight` table alone is not sufficient as the canonical store for the complete customer insight model.
- No, the prompt projection should not be replaced by direct injection of the stored AI summary.

## Open Implementation Notes

- If there is concern about storing large JSON payloads in the Finance module, keep the canonical snapshot there anyway and optimize with summaries or compression later. Do not move the canonical deterministic model into the prompt layer.
- If multiple currencies are present, snapshot formulas must state whether values are per-currency, primary-currency only, or normalized via a deterministic FX policy. Do not silently merge cross-currency amounts without an explicit rule.
- If some customer domains are incomplete, generate partial snapshots with coverage metadata rather than skipping silently.
