# 014.background-jobs-quartz-persistence-admin

## Objective
Evolve the current Quartz-based background job feature into a durable, production-safe, operator-administered scheduling system that follows Quartz.NET best practices, persists scheduler state correctly, and provides a complete Admin UI for operations.

## Problem Statement
The current implementation works as a proof of concept, but it is not yet a production-grade scheduler administration system.

Current issues:
- `src/Aonik.Worker/Program.cs` configures scheduled jobs directly in the Worker using the default Quartz setup, which means `RAMJobStore` and non-durable schedule state.
- `src/Aonik.Worker/Jobs/ScheduledJobRegistrar.cs` duplicates job definitions and writes a separate `Platform.Job` row that can drift from actual Quartz state.
- `src/Aonik.Platform/Endpoints/Admin/Jobs/PauseScheduledJobEndpoint.cs` and `ResumeScheduledJobEndpoint.cs` only edit a database row and do not pause or resume Quartz.
- `src/Aonik.Platform/Endpoints/Admin/Jobs/TriggerScheduledJobEndpoint.cs` does not trigger Quartz and instead writes a flag into `LastResultJson`.
- `src/Aonik.Platform/Endpoints/Admin/Jobs/ListScheduledJobsEndpoint.cs` reads only the projection row, so it does not expose real trigger state, next fire time, or scheduler health.
- `src/Aonik.AdminUi/src/pages/settings/BackgroundJobsPage.tsx` is a minimal list page and does not yet provide real administration, run history, schedule editing, audit visibility, or scheduler health.
- `src/Aonik.Infrastructure/DependencyInjection.cs` currently registers Quartz for all hosts via `AddAonikBackgroundJobs()`, which becomes unsafe once a persistent Quartz store is introduced unless every host is intentionally clustered and configured correctly.

## Goals
- Persist Quartz schedules, triggers, and pause state across restarts.
- Make Quartz the source of truth for schedules and runtime state.
- Keep AONIK-owned persistence for audit, history, and curated read models.
- Ensure only `Aonik.Worker` executes Quartz jobs.
- Provide safe operator controls in the Admin UI for a whitelisted set of known jobs.
- Expose scheduler health, current state, run history, and command audit to operators.
- Support future clustered worker deployment without redesign.
- Align with Quartz.NET best practices around persistent stores, JobDataMap usage, listener behavior, and safe administration.

## Non-Goals
- Allow arbitrary user-defined Quartz jobs.
- Allow arbitrary JobDataMap editing from the UI.
- Expose raw Quartz tables as an application integration surface.
- Replace Quartz with another scheduler.
- Build a generic workflow engine.
- Add direct financial mutation jobs without their own policy review.

## Guiding Principles
- Quartz owns scheduler state.
- AONIK owns audit, reporting, and operator UX.
- Worker is the execution host; API is the admin and query boundary.
- All scheduler mutations must go through Quartz APIs, never direct SQL against `QRTZ_*` tables.
- Listener code must stay concise and exception-safe.
- Recoverable jobs must be idempotent.
- JobDataMap must stay string-only where persistence is involved.
- UI-exposed operations must be limited to a curated registry of safe jobs.

## Best-Practice Alignment
This specification follows the Quartz guidance at `https://www.quartz-scheduler.net/documentation/best-practices.html` and related Quartz JobStore documentation.

Key decisions from Quartz guidance:
- Use `AdoJobStore` instead of `RAMJobStore` for durable scheduling.
- Never write directly to Quartz tables.
- Set `UseProperties = true` so persisted `JobDataMap` values remain string-based.
- Use stable `JobKey` and trigger identities.
- Keep listeners lightweight and wrapped in `try/catch`.
- Avoid DST-sensitive schedules where possible.
- Be careful exposing scheduler functionality; restrict actions to safe, known jobs.

## Target Architecture

### Host Responsibilities

#### `Aonik.Worker`
- Own the Quartz scheduler lifecycle.
- Register and reconcile all known scheduled jobs.
- Execute scheduled jobs.
- Process admin commands from AONIK-owned tables.
- Update AONIK-owned read models and execution history.
- Publish scheduler health snapshots.

#### `Aonik.Api`
- Authorize operator actions.
- Validate job names and allowed operations against a known registry or registry-backed read model.
- Persist admin commands.
- Serve scheduler read models to the Admin UI.
- Never directly manipulate Quartz runtime state in-process.

#### `Aonik.AdminUi`
- Present a curated operational UX for known jobs.
- Surface health, schedule, run history, and command state.
- Never expose arbitrary Quartz internals or free-form job creation.

### Source of Truth Model
- Quartz `AdoJobStore` is the source of truth for:
  - Job definitions
  - Trigger definitions
  - Pause state
  - Next/previous fire times
  - Recovery behavior
  - Cluster coordination
- AONIK-owned tables are the source of truth for:
  - Execution history
  - Operator command audit
  - Curated projection data for the Admin UI
  - Scheduler health snapshots

### Control Flow
1. Admin UI submits an operator action to `Aonik.Api`.
2. API validates the job and creates a `ScheduledJobAdminCommand` record.
3. Worker polls pending commands and executes them through `IScheduler`.
4. Worker marks the command as succeeded or failed.
5. Worker updates the job projection.
6. Admin UI refreshes command state and visible scheduler state.

### Execution Flow
1. Quartz fires a trigger in `Aonik.Worker`.
2. The job executes.
3. Listener captures start and completion data.
4. Worker writes a `ScheduledJobRun` record.
5. Worker refreshes the projection row for that job.

## Scheduler Persistence Specification

### Quartz Store
- Use Quartz `AdoJobStore` on SQL Server.
- Use a dedicated scheduler identity per environment.
- Enable clustering for any environment where more than one worker instance may run.
- Use `Quartz.Serialization.SystemTextJson`.
- Set `UseProperties = true` to keep persisted job data string-only.
- Use a fixed table prefix such as `QRTZ_`.
- Provision Quartz schema via infrastructure or deployment assets, not ad hoc SQL in code.

### Required Quartz Configuration
- Scheduler name: explicit and environment-scoped.
- Instance id: auto-generated or runtime-generated for clustered workers.
- Store type: `JobStoreTX`.
- Driver delegate: SQL Server specific delegate.
- Serializer: System.Text.Json.
- UseProperties: `true`.
- Thread pool size: tuned per workload.
- DB connection pool: at least thread pool size plus three, with headroom for admin operations.
- Misfire threshold: explicitly configured.
- Cluster check-in interval: explicitly configured.

### Configuration Ownership
- `Aonik.Worker` config owns Quartz runtime settings.
- `Aonik.Api` must not create a live Quartz scheduler instance against the same persistent store.
- Shared infrastructure registration must be split so Worker and API do not accidentally share the same scheduler role.

## Job Definition Specification

### New Registry Model
Introduce a code-based registry for all supported scheduled jobs.

Recommended interface:
- `IScheduledJobDefinition`

Required metadata per job:
- `JobName`
- `JobGroup`
- `DisplayName`
- `Description`
- `DefaultCronExpression`
- `TimeZoneId`
- `AllowManualTrigger`
- `AllowPauseResume`
- `AllowReschedule`
- `RequestRecovery`
- `DisallowConcurrentExecution`
- `MisfirePolicy`
- `RiskTier`

### Static Keys
Each job class must expose a static `JobKey` so that all scheduler operations use the same key consistently.

Example requirement:
- `FinancialConnectionRecurringSyncJob.Key`
- `StaleSessionDetectorJob.Key`
- `BehaviouralInsightJob.Key`

### Trigger Identity Rules
- Every recurring trigger must use a stable, deterministic identity.
- Trigger names must not be generated dynamically at runtime for the same logical schedule.
- Manual trigger operations must use `TriggerJob(jobKey)` instead of data-table side channels.

### Recovery and Idempotence
- Jobs may set recoverability only if the underlying business behavior is idempotent.
- Financially sensitive jobs must document why replay is safe before `RequestRecovery` is enabled.

### Misfire Policy
- Each job must specify an explicit misfire policy.
- Default policy should favor predictability over hidden catch-up storms.
- The chosen misfire policy must be visible in the job detail UI.

## Worker Design Specification

### New Worker Components
Recommended additions under `src/Aonik.Worker`:
- `Scheduling/IScheduledJobDefinition.cs`
- `Scheduling/ScheduledJobRegistry.cs`
- `Scheduling/QuartzScheduleReconciler.cs`
- `Scheduling/ScheduledJobCommandProcessor.cs`
- `Scheduling/ScheduledJobProjectionSyncService.cs`
- `Scheduling/ScheduledJobExecutionListener.cs`
- `Scheduling/SchedulerHealthPublisher.cs`

### Startup Reconciliation Rules
On worker startup:
- Load all known job definitions from the registry.
- For each known job:
  - ensure Quartz job exists
  - ensure recurring trigger exists
  - ensure description and static metadata are present
  - preserve operator overrides unless explicitly reset
- For jobs removed from code registry:
  - do not auto-delete in phase 1
  - mark them as orphaned in projection and expose read-only in UI if still present in Quartz

### Command Processing Rules
- Poll pending commands at a fixed interval.
- Claim work using optimistic concurrency.
- Apply commands through Quartz APIs only.
- Update command status and message.
- Refresh projection after every successful command.
- Capture failures with enough detail for operator diagnosis.

### Listener Rules
- Record start and completion timestamps.
- Capture outcome and duration.
- Capture concise error summary only.
- Never do heavy business work in the listener.
- Wrap all listener logic in `try/catch`.

### Projection Sync Rules
- Run at startup.
- Run after every admin command.
- Run after every job execution.
- Run on a periodic timer as a safety net.

## Risks and Mitigations

### Risk: API and Worker both connect as live schedulers to the same store
Mitigation:
- split registration paths and enforce Worker-only Quartz runtime ownership

### Risk: schedule drift between registry defaults and operator overrides
Mitigation:
- store `ScheduleSource`
- preserve operator overrides by default
- provide explicit `Reset to default`

### Risk: replay after failure causes duplicate business effects
Mitigation:
- require idempotence review before enabling recoverability

### Risk: admin UI becomes too close to raw Quartz internals
Mitigation:
- keep the UI curated around known jobs and business-safe controls

### Risk: excessive listener work impacts scheduler throughput
Mitigation:
- keep listeners minimal and resilient
