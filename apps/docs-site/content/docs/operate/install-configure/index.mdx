This is the operator's onboarding flow. Read the overview here, then work through the pages below in order.

<Callout type="info" title="Fastest path: zero external accounts">
  Set the env var `AONIK_AUTH_PROVIDER=Keycloak` before you start the AppHost and Aspire spins up a pre-seeded Keycloak realm alongside the rest of the stack. The Admin UI and API auto-discover the realm; you can sign in immediately as **`admin@aonik.local` / `Aonik!Dev2026`** with no Auth0 / Microsoft tenant to register. See [Run with Aspire — step 2.5](/docs/operate/install-configure/run-with-aspire#step-25-optional-enable-keycloak-for-zero-account-login) for the one-liner, and [Identity & Access → Keycloak](/docs/operate/identity-access/keycloak) for the full picture.
</Callout>

## The path

<Steps>

<Step>

### [Prerequisites](/docs/operate/install-configure/prerequisites)

Install **Docker Desktop**, the **.NET 10 SDK**, **SQL Server LocalDB**, **Node.js 18+**, **PowerShell 7**, and **Git**. Every item has a check command, an install command, and a verify command. The page ends with a one-shot script that asserts the lot.

</Step>

<Step>

### [Run with Aspire](/docs/operate/install-configure/run-with-aspire)

`Aonik.AppHost` is the .NET Aspire orchestrator. Running `dotnet run --project src/Aonik.AppHost` starts five resources at once:

- the **API** (`Aonik.Api`) at `https://localhost:5001`
- the **Worker** (`Aonik.Worker`, headless)
- the **Admin UI** Vite dev server at `http://localhost:5173`
- the **Qdrant** vector store container (Aspire calls Docker Desktop to pull and start it)
- the **Aspire dashboard** at `https://localhost:21183` for live resource state, logs, and traces

SQL Server is **not** containerised — it uses your local SQL Server LocalDB instance directly. With `AONIK_AUTH_PROVIDER=Keycloak`, a sixth resource — a **Keycloak** container on `http://localhost:8080` — joins the set, pre-seeded with a working realm.

</Step>

<Step>

### [Bootstrap your first tenant](/docs/operate/install-configure/bootstrap-tenant)

The `/bootstrap` endpoint is the only way to create the first tenant on a fresh deployment. It is anonymous, single-use, and gated by a setup secret you put in user-secrets. A single call creates a tenant, an owner user, and the `PlatformAdmin` + `TenantAdmin` role assignments on that user. If you're running in Keycloak mode, bootstrap with the pre-seeded admin's email (`admin@aonik.local`) so the placeholder user record links to the realm identity on first sign-in.

</Step>

<Step>

### [Verify the install](/docs/operate/install-configure/verify)

A single PowerShell script runs nine assertions: API healthy, Scalar reference served, bootstrap completed, one tenant present, owner user has both admin roles, Admin UI reachable, Qdrant ready and healthy, OpenAPI document served. Exit code `0` on full pass, `1` on any failure. With Keycloak mode on, the script gains a tenth assertion that the realm's OIDC discovery document is reachable.

</Step>

</Steps>

## What lives where

| Concern                                     | Where it lives                                                   |
| ------------------------------------------- | ---------------------------------------------------------------- |
| Source of financial truth (ledger, orders)  | SQL Server LocalDB → `AonikDb`                                   |
| Vectors for RAG + user memory               | Qdrant container                                                 |
| Background jobs and cost guards             | `Aonik.Worker` (in-process Quartz)                               |
| Operator UI                                 | `Aonik.AdminUi` (React 19 + Vite, served by Aspire in dev)       |
| HTTP + AI + agent runtime                   | `Aonik.Api`                                                      |
| Local developer secrets                     | `dotnet user-secrets` on each project (`src/Aonik.Api`, etc.)    |
| Schema migrations                           | `Aonik.Infrastructure` migrations, run against `AonikDbContext`  |

## Conventions used in this section

The Install & Configure pages are written for **deterministic execution**. Every step uses the same shape:

> **Run:** the exact command (PowerShell). \
> **Expected:** the exact output that proves success. \
> **Verify:** a follow-up command that asserts the post-condition. \
> If the verify fails, the page lists the most likely cause and the fix.

An AI agent can execute every step verbatim. A human can copy-paste. Either reader gets the same outcome.

## Roadmap for this section

The pages currently published are the local-dev onboarding path. The following pages land in later phases of the docs rewrite:

- **Run with Docker Compose** — for environments without LocalDB and without Aspire
- **Run without Docker** — for hosts where the Qdrant container is unavailable
- **Environment variables reference** — every `Database__*`, `Qdrant__*`, `Auth__*`, `Bootstrap__*`, `Ai:*`, `Finance:*`, etc. with default, type, and effect
- **Connect to SQL Server** — LocalDB, Azure SQL, containerised SQL Server, with per-environment connection strings
- **Connect to Qdrant** — self-hosted, Qdrant Cloud, multi-tenant collection prefixes
