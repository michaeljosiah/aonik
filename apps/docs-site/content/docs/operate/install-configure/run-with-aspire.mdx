Aspire is the .NET Aspire orchestrator (`Aonik.AppHost`). It starts the API, the Worker, the Admin UI Vite dev server, and a Qdrant container in one step — and exposes a dashboard where you can see every resource's state.

This page is written for **deterministic execution**. Run every command verbatim and use the verification output to decide whether to continue.

<Callout type="info">
  Make sure [Prerequisites](/docs/operate/install-configure/prerequisites) all pass before starting. The single most common failure on this page is **Docker Desktop not running**.
</Callout>

## What Aspire actually launches

The AppHost (`src/Aonik.AppHost/AppHost.cs`) wires the following resources:

| Resource           | Type                       | URL (default)               | Notes                                          |
| ------------------ | -------------------------- | --------------------------- | ---------------------------------------------- |
| `api`              | .NET project               | https://localhost:5001      | The Aonik REST API + Scalar reference          |
| `worker`           | .NET project               | (no HTTP endpoint)          | Quartz background jobs                         |
| `adminui`          | Vite dev server (Node)     | http://localhost:5173       | React 19 admin UI                              |
| `qdrant`           | Docker container           | http://localhost:6333       | Vector store (`qdrant/qdrant:v1.13.2`)         |
| `keycloak`         | Docker container *(opt-in)*| http://localhost:8080       | Pre-seeded `aonik` realm — opt in via `AONIK_AUTH_PROVIDER=Keycloak` |
| `aspire-dashboard` | Aspire's own observability | https://localhost:21183     | Resource list, logs, traces, metrics           |

Aspire calls the local **Docker Desktop** API to pull and start the Qdrant image (and the Keycloak image when the opt-in is set). SQL Server is **not** containerised — it uses your local **SQL Server LocalDB** instance directly.

## Step 1 — Clone the repository

**Run** (in the directory where you keep your source repos):

```powershell
git clone https://github.com/michaeljosiah/aonik.git
Set-Location aonik
```

**Verify:**

```powershell
Test-Path .\Aonik.sln
```

**Expected:** `True`.

If `Test-Path` returns `False`, the clone failed or your working directory is wrong.

## Step 2 — Configure the bootstrap secret

The `/bootstrap` endpoint is **disabled by default**. The next page ([Bootstrap your first tenant](/docs/operate/install-configure/bootstrap-tenant)) needs both `Bootstrap:Enabled` and `Bootstrap:SetupSecret` set. Configure them now so the API picks them up at startup.

**Run:**

```powershell
dotnet user-secrets --project src/Aonik.Api set Bootstrap:Enabled true
$secret = [guid]::NewGuid().ToString()
dotnet user-secrets --project src/Aonik.Api set Bootstrap:SetupSecret $secret
Write-Host "Bootstrap secret: $secret"
```

**Expected:** the final line prints a GUID. Save it — you will need it on the next page.

**Verify:**

```powershell
dotnet user-secrets --project src/Aonik.Api list
```

**Expected:** at least these two entries appear in the output:

```
Bootstrap:Enabled = true
Bootstrap:SetupSecret = <your-guid>
```

## Step 2.5 — (Optional) Enable Keycloak for zero-account login

This step is the fastest path to a working sign-in. If you skip it, the Admin UI loads but every login attempt fails until you wire Auth0 or Microsoft Entra ID per [Identity & Access](/docs/operate/identity-access).

**What it does.** Setting `AONIK_AUTH_PROVIDER=Keycloak` for the AppHost process makes Aspire spin up a sixth resource — a Keycloak 26 container — and auto-wire every other process to it:

- `keycloak` container at `http://localhost:8080`, pre-seeded with the `aonik` realm (two clients, three users, two protocol mappers — see `infra/keycloak/realm-export.json`)
- `api` receives `Auth__Provider=Keycloak`, `Auth__Keycloak__Authority=http://localhost:8080/realms/aonik`, `Auth__Keycloak__Audience=aonik-api`
- `adminui` receives `VITE_AUTH_PROVIDER=keycloak`, `VITE_KEYCLOAK_AUTHORITY=http://localhost:8080/realms/aonik`, `VITE_KEYCLOAK_CLIENT_ID=aonik-spa`

There is nothing else for you to configure. No user-secrets, no `.env.local`, no realm import — everything lives in the repo.

**Run (PowerShell):**

```powershell
$env:AONIK_AUTH_PROVIDER = 'Keycloak'
```

The variable lives in the current shell session. To make it persistent for your user account:

```powershell
[Environment]::SetEnvironmentVariable('AONIK_AUTH_PROVIDER', 'Keycloak', 'User')
```

To turn Keycloak back off later, set the variable to an empty string or remove it.

**Verify (after step 4 below — once the AppHost is running):**

```powershell
curl.exe --silent http://localhost:8080/realms/aonik/.well-known/openid-configuration |
  ConvertFrom-Json |
  Select-Object issuer, authorization_endpoint, token_endpoint
```

**Expected:** `issuer` is `http://localhost:8080/realms/aonik` and the two endpoints are non-null URLs hanging off the same host.

**Pre-seeded credentials.** The realm includes:

| Username              | Password         | Roles                             | Notes                                |
| --------------------- | ---------------- | --------------------------------- | ------------------------------------ |
| `admin@aonik.local`   | `Aonik!Dev2026`  | `Aonik.PlatformAdmin`, `TenantAdmin` | Use this for the bootstrap email     |
| `user@aonik.local`    | `Aonik!Dev2026`  | `PersonalUser`                    | Regular tenant user for testing Payabo |

<Callout type="warn">
  These credentials are checked into the repo for **local dev only**. Never use them in any deployment a colleague can reach. Production Keycloak realms are operator-owned — see [Identity & Access → Keycloak](/docs/operate/identity-access/keycloak) for the production setup runbook.
</Callout>

## Step 3 — Confirm Docker Desktop is running

Aspire will refuse to start the Qdrant container if the Docker daemon is unreachable.

**Verify:**

```powershell
docker info --format '{{.ServerVersion}}'
```

**Expected:** a version number (for example `27.3.1`). If you instead see `error during connect`, start Docker Desktop:

```powershell
Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"
```

Wait for the tray icon to report **Docker Desktop is running**, then retry the verify command above.

## Step 4 — Start the Aspire orchestrator

**Run:**

```powershell
dotnet run --project src/Aonik.AppHost
```

This is a **long-running** process — do not close the terminal. The shell will print log lines for every resource as Aspire brings them up. After ~15–30 seconds you will see lines like:

```
[api] Now listening on: https://localhost:5001
[adminui] VITE v6.x  ready in N ms
[qdrant] Service started
```

The Aspire dashboard opens in your default browser at `https://localhost:21183`. If it does not open automatically, navigate there manually. Every row should turn green within a minute.

<Callout type="warn">
**Do not stop the AppHost between steps.** Open a *second* PowerShell tab to run the verification commands in steps 5–7. Closing the AppHost stops every resource it manages.
</Callout>

## Step 5 — Verify the API is up

**In a second terminal**, run:

```powershell
curl.exe --insecure https://localhost:5001/health
```

**Expected:** an HTTP 200 with a JSON body like:

```json
{"Status":"Healthy","Timestamp":"2026-05-19T06:30:00.000Z"}
```

If you instead get `Connection refused` or a TLS error:

- Check the Aspire dashboard. The `api` row may still be **Starting** — wait 5 seconds and retry.
- If the `api` row is **Failed**, click its name in the dashboard and read the **Console logs** tab. The most common cause is a LocalDB connection failure — see [LocalDB issues](#localdb-connection-fails-at-startup) below.

## Step 6 — Verify the Admin UI is up

```powershell
curl.exe --silent --output $null --write-out '%{http_code}' http://localhost:5173/
```

**Expected:** `200`.

Open `http://localhost:5173/` in a browser — the login screen renders.

- If you completed [Step 2.5 (Keycloak)](#step-25-optional-enable-keycloak-for-zero-account-login), click **Sign in**. Keycloak's hosted login page loads. Sign in as `admin@aonik.local` / `Aonik!Dev2026`. You'll be returned to the Admin UI; the next step (Bootstrap) creates the matching Aonik-side tenant + user.
- If you skipped Step 2.5, the login button works but no identity provider is wired — that's expected and is fixed in [Identity & Access](/docs/operate/identity-access).

## Step 7 — Verify Qdrant is up

```powershell
curl.exe --silent http://localhost:6333/readyz
```

**Expected:** body is `all shards are ready`.

You can also list the container directly:

```powershell
docker ps --filter "ancestor=qdrant/qdrant" --format "table {{.Names}}\t{{.Status}}"
```

**Expected:** a single row with status `Up <N> seconds (healthy)`.

## Step 8 — (Only if Step 2.5 was run) Verify Keycloak is up

```powershell
curl.exe --silent --output $null --write-out '%{http_code}' http://localhost:8080/realms/aonik/.well-known/openid-configuration
```

**Expected:** `200`. The OIDC discovery document being served proves the realm imported cleanly and Keycloak is ready to issue tokens.

The Keycloak admin console is available at `http://localhost:8080/admin/` (login `admin` / `admin`). You shouldn't need it for normal work — every dev artifact (users, clients, mappers, roles) is in the checked-in realm export.

## All-in-one verification

The block below runs steps 5–8 in sequence and exits non-zero on the first failure. The Keycloak assertion runs only when the env var is set, so it works identically on the Keycloak and non-Keycloak paths.

```powershell
$ErrorActionPreference = 'Stop'

# API health
$api = curl.exe --insecure --silent --max-time 5 https://localhost:5001/health | ConvertFrom-Json
if ($api.Status -ne 'Healthy') { throw "API not healthy: $($api | ConvertTo-Json -Compress)" }
Write-Host '✅ API healthy' -ForegroundColor Green

# Admin UI
$adminStatus = curl.exe --silent --output $null --write-out '%{http_code}' http://localhost:5173/
if ($adminStatus -ne '200') { throw "Admin UI returned $adminStatus" }
Write-Host '✅ Admin UI reachable' -ForegroundColor Green

# Qdrant
$qdrant = curl.exe --silent --max-time 5 http://localhost:6333/readyz
if ($qdrant -notmatch 'all shards are ready') { throw "Qdrant not ready: $qdrant" }
Write-Host '✅ Qdrant ready' -ForegroundColor Green

# Keycloak (only when AONIK_AUTH_PROVIDER=Keycloak)
if ($env:AONIK_AUTH_PROVIDER -eq 'Keycloak') {
  $kcCode = curl.exe --silent --output $null --write-out '%{http_code}' http://localhost:8080/realms/aonik/.well-known/openid-configuration
  if ($kcCode -ne '200') { throw "Keycloak realm discovery returned $kcCode" }
  Write-Host '✅ Keycloak realm reachable' -ForegroundColor Green
}

Write-Host ''
Write-Host 'Aspire stack healthy. Proceed to Bootstrap your first tenant.' -ForegroundColor Green
```

## Troubleshooting

### Docker not running

**Symptom.** The Aspire dashboard shows `qdrant` (or `keycloak`, when enabled) as **Failed**, and the AppHost console logs include `error during connect: this error may indicate that the docker daemon is not running`.

**Fix.** Start Docker Desktop and wait for the tray icon to report **running**. Then click the **Restart** button on the failed row in the Aspire dashboard.

### Keycloak realm fails to import

**Symptom.** The `keycloak` row is **Running** but `http://localhost:8080/realms/aonik/.well-known/openid-configuration` returns `404`. The Keycloak container logs include `Realm 'aonik' not found` or `Failed to import realm`.

**Cause.** The bind mount of `infra/keycloak/realm-export.json` failed — most often because Docker Desktop hasn't been granted access to the repo's drive in **Settings → Resources → File sharing**, or because the AppHost was started from a path that resolved `..\..\infra\keycloak\realm-export.json` to a non-existent location.

**Fix.** Add the repo's drive in Docker Desktop's file sharing settings (if on Windows + WSL2, this is usually unnecessary), then restart the `keycloak` row in the Aspire dashboard. Re-running `dotnet run --project src/Aonik.AppHost` works too — the realm export is re-mounted on container start.

### LocalDB connection fails at startup

**Symptom.** The `api` row stays in **Starting** for more than 30 seconds, or transitions to **Failed**. The API console logs include `A network-related or instance-specific error occurred while establishing a connection to SQL Server`.

**Cause.** The `MSSQLLocalDB` instance is not running.

**Fix.**

```powershell
sqllocaldb start MSSQLLocalDB
sqllocaldb info MSSQLLocalDB
```

The second command must report `State: Running`. Then click **Restart** on the `api` row.

### Port already in use

**Symptom.** A resource's console log includes `Failed to bind to address ... address already in use`.

**Cause.** Another process is using the port (5001 for the API, 5173 for the Admin UI, 6333/6334 for Qdrant, 21183 for the Aspire dashboard).

**Fix.** Identify the offending process:

```powershell
Get-NetTCPConnection -LocalPort 5001 | Select-Object -First 1 OwningProcess |
  ForEach-Object { Get-Process -Id $_.OwningProcess }
```

Stop the process or change Aonik's port (advanced — see [Environment variables reference, coming soon](/docs/operate/install-configure)).

### Aspire dashboard never opens

**Symptom.** The AppHost runs cleanly but the browser does not navigate to `https://localhost:21183`.

**Fix.** Open it manually:

```powershell
Start-Process https://localhost:21183
```

If the URL itself returns nothing, the dashboard is disabled via env vars. The AppHost expects `ASPIRE_DASHBOARD_OTLP_ENDPOINT_URL` to be set in the launch environment. The repo's `launchSettings.json` sets it by default — confirm with `Get-Content src/Aonik.AppHost/Properties/launchSettings.json`.
