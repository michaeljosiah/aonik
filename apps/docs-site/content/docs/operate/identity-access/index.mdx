Aonik authenticates users against one of three identity providers, chosen per deployment via the `Auth.Provider` setting:

| Provider             | Best for                                                            | External account needed?                   |
| -------------------- | ------------------------------------------------------------------- | ------------------------------------------ |
| **Keycloak**         | Local development, self-hosting, data-residency-regulated markets   | No — runs in a container on your laptop    |
| **Auth0**            | Teams already on Auth0; SaaS-style hosted identity                  | Yes — free tier covers most dev scenarios  |
| **Microsoft Entra ID** | Microsoft-365 organisations; native SSO with corporate identity   | Yes — your org's Entra tenant              |

The capability surfaces (JWT validation, user provisioning, password reset, account service, token exchange, IdP management) are identical across all three. Switching providers is a single setting flip plus per-provider credentials — no Aonik code changes.

<Callout type="info" title="Recommended path: Keycloak for local dev">
  If you're getting Aonik up and running for the first time, use Keycloak. It's the only option that needs no external account, no manual realm configuration, and no `appsettings` edits. [Run with Aspire → step 2.5](/docs/operate/install-configure/run-with-aspire#step-25-optional-enable-keycloak-for-zero-account-login) shows the one-env-var setup. Switching to Auth0 or Entra later is a settings change, not a re-deploy.
</Callout>

## How identity flows through Aonik

1. **SPA login flow.** The Admin UI (or Payabo SPA) redirects the user to the configured IdP's hosted login page (Keycloak's `/realms/aonik/protocol/openid-connect/auth`, Auth0's `/authorize`, or Microsoft's `/oauth2/v2.0/authorize`). The user signs in there. The IdP redirects back to the SPA with an authorization code.
2. **Token exchange.** The SPA exchanges the code for an access token + refresh token + ID token via PKCE.
3. **API call.** The SPA attaches the access token as `Authorization: Bearer <token>` on every API request.
4. **Backend validation.** Aonik's `AonikAuthenticationSetup` runs the token through the JwtBearer middleware. The middleware fetches the IdP's JWKS via OIDC discovery (cached) and validates signature, audience, issuer, expiry, and clock skew.
5. **Tenant + user resolution.** A successful token triggers `HandleTokenValidatedAsync`, which resolves the tenant (via `X-Tenant-Id` header or `aonik_tenant_id` claim) and the Aonik-side user record (matched by external issuer + subject, or upgraded from a bootstrap placeholder by email match on first sign-in).
6. **Authorization.** Permission checks read the user's role assignments from `AnkUserRoles` plus any role claims surfaced by the IdP.

This pipeline is provider-agnostic. The differences live entirely in the three `IIdentityProviderManagementClient` implementations (Auth0, AzureAd, Keycloak) and their factory in `Aonik.Infrastructure.Authentication`.

## Roles & permissions

Aonik ships with six built-in roles (`PlatformAdmin`, `TenantAdmin`, `Operations`, `Compliance`, `ReadOnly`, `PersonalUser`) plus per-tenant custom roles. Role claims are normalised by `ClaimsRoleMapper.ExtractRoles`, which reads from a top-level `roles` claim and from `realm_access.roles` (Keycloak default) — your IdP should emit roles in one of those locations.

## Troubleshooting

The most common authentication failures and their causes:

| Symptom                                              | Most likely cause                                                                        | Where to look                                                                                              |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `401 audience invalid`                               | Token audience doesn't match `Auth.<Provider>.Audience`                                  | IdP-side audience mapper / API identifier config                                                           |
| `401 Token issuer not allowed for active provider`   | `Auth.<Provider>.Authority` doesn't match the `iss` claim                                | Provider authority setting; for Keycloak, also check `KC_HOSTNAME`                                         |
| `401 Tenant could not be resolved`                   | First sign-in for a bootstrapped user whose email doesn't match the IdP user's email     | `AnkUsers.Email` vs IdP user email — see [bootstrap email guidance](/docs/operate/install-configure/bootstrap-tenant#before-you-start) |
| `403 forbidden` on every authenticated request       | Roles aren't flowing through the token                                                   | IdP-side roles mapper (Keycloak: `roles-flatten`; Auth0: custom Action; Entra: app roles)                  |
| User logs in but never appears in the Admin UI       | Role-claim mismatch or `Status` not `Active`                                             | `SELECT Status, Email FROM AnkUsers WHERE Email = '<email>'`                                               |

For provider-specific troubleshooting, see the per-provider guides above.
