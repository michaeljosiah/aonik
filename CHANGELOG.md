# Changelog

All notable changes to the AONIK project will be documented in this file.

## [Unreleased]

### Added
- **Admin UI (Spec 084 — commerce overview)**: The Commerce section landing, completing the storefront admin series. Its job is triage: four order tiles, recent orders, and an attention list where every row is a real state read from the surface that owns it, with a link there — never a computed guess. **Four states are kept distinct**, and conflating any two is the failure mode the page exists to avoid: *nothing to report* omits the row (a green "0 need review" row trains operators to skim past the card); *something to report* appears toned by urgency, warn rows sorted above informational and muted ones; *source unavailable* appears **saying so**, because silence would read as "nothing to report" — the one thing a failed read cannot establish; and *clean but partial* appears saying **that**, because a bounded scan which found nothing has established nothing beyond its bound (a 200-product scan of a 300-product store would otherwise render a flagged product 201 identically to a genuinely clean store). Every bounded scan therefore discloses its bound: content review reports "at least N" where there is no server-side `requiresReview` filter, staged drafts name the number of collections inspected and count **distinct** products (one draft staged in three collections is one product to activate), and the open-cart scan names its window. The attention count for carts uses an *anomalous* predicate — drift or over-capacity — rather than the checkout gate, because an under-filled box is the normal state of every live shopping session and warning on it would alarm whenever customers are actually shopping. Sources settle independently: each request owns one state slot and updates it in its own `then`/`catch`, so one failure degrades its own row instead of emptying the page, and a retry generation cannot be overwritten by a slow response from the previous one. The delivery promise treats 404 as the designed "no promise configured" answer (Spec 069: unconfigured is a state) and only other failures as unavailable.
- **Admin UI (Spec 083 — commerce orders and carts)**: `/commerce/orders` and `/commerce/carts`, answering what exactly was ordered and which sessions are live, stuck or recoverable. The order drawer is the kitchen landing: a box is **one** order item at the goods total, while what the kitchen prepares lives in the nested selections array — the nesting Spec 068 exists to preserve, so two differently-personalised preparations never collapse into one line. Personalisation summaries render exactly as the DTO carries them; the stored envelopes are opaque and never re-derived client-side. Add-ons badge with their own price, the delivery fee renders as its own line, and the charge summary walks subtotal → discount (code as a chip) → tax → total. One pure `cartAction` derivation decides the cart footer, and it checks `orderId` **first**: checkout stamps it while deliberately leaving the cart Open until payment confirms, so such a cart is full and undrifted yet the service boundary refuses every further operation — offering "Resume checkout" there would promise what the server denies. The same module's `cartBlocked` gates on **equality** with the box size, matching `BoxCartService`, so an over-filled box is blocked exactly as an under-filled one is. Cart lines deliberately print no computed total: the charge adds personalisation and surcharge to the snapshot, and a BoxDish snapshot is 0 because the box is priced as a container — `AdminCartDetailDto` gained `Total` for the authoritative figure. The lifecycle stepper marks **Fulfilled as untracked** rather than pending, and the spec's "awaiting fulfilment" KPI is not shipped, because `DeriveFulfilment` returns only `Unfulfilled` or `Cancelled` — that count would equal the order count while implying delivery is tracked; awaiting **payment** replaces it, excluding terminal orders whose payment can never arrive.
- **Admin UI (Commerce KPI currency rule)**: Order KPI windows never sum across currencies — there is no rate available, so adding them would invent one. A mixed window reports the **dominant** currency's aggregate (dominant by order *count*, so one large order in a minor currency cannot relabel the window) with the number of excluded orders rendered as wrappable supporting text beneath the tiles, and the mean divides by the orders that made up the total rather than by every capture. Shared by the orders page and the overview.
- **Admin UI (Spec 082 — commerce products)**: The catalogue behind the storefront finally has an operator surface: a paged, filterable product list and a three-tab editor (details, media, storefront placement) reachable at `/commerce/products/:productId`, so a product is linkable rather than only clickable. Full Spec 042 authoring (variants, pricing bands, bundle slots) stays out of scope. Most of the work is in honouring contract asymmetries that lose data *silently*: keywords read as `searchKeywords: string[]` but write as `searchKeywordsJson` (the array member does not exist on the write contract), media replace takes array **position** as the order with no sort field on the wire, and PATCH is partial so a cleared category needs its own flag because an absent member already means "untouched" — all of it in a pure, unit-tested module rather than inline in components. The list refuses what the summary DTO cannot support truthfully: no retail price (summaries carry none by design), no "updated" column (no timestamp on the row), and surcharge as a **marker** rather than an amount, because the summary carries the number but not its currency. Sorting is likewise absent rather than faked — the endpoint takes no sort parameter, so a header click would reorder one page while appearing to order the catalogue. The unit surcharge is constrained to the storefront's canonical currency at authoring: the write path checks only that a code is three characters while quoting rejects any mismatch with V10, so a mistyped currency would save cleanly and then break that product's checkout pricing; where the canonical currency cannot be read, authoring closes (removal stays open, since a clear carries no currency). Amounts are validated on their text rather than through `Number()` — `decimal(19,4)` does not reject a fifth decimal, it rounds it — and media URLs are bounded at the mapped 1024 characters at the point of entry, because the writes are ordered and anything caught late lands as a partial save. When one does occur, each section that committed advances its own baseline and the error names what persisted, so a retry cannot reissue a media replacement that already succeeded.
- **Admin UI (Spec 081 — unified customer detail)**: One customer record instead of per-domain screens: an order spine tab covering every `OrderType` the party participates in, plus module-gated domain tabs (Commerce first) that appear only where the tenant runs that module. Order-type labels render unknown codes verbatim rather than swallowing them, since `OrderType` is an open string; money is formatted per currency with no cross-currency summing; and totals are shown per currency rather than merged into a single misleading figure.
- **Admin UI + Platform (Spec 080 — unified Customers registry)**: Customers became one top-level registry rather than a per-module list, backed by a cross-module read model. Platform owns the registry predicate but cannot reference Commerce, Finance or PersonalFinance, so the dependency is inverted through a SharedKernel `ICustomerRegistryContributor` that each module implements — batch-shaped, so a `domain=` filter narrows before counting and paging rather than after. Order aggregates are grouped in the database via a new `IOrderService.GetPartyOrderAggregatesAsync` rather than materialised per party.
- **Admin UI (Spec 073 — commerce module foundation) + Commerce dependency endpoints**: The live Admin UI had no commerce surface at all — its "Catalog" is the bill-payment catalog — so every storefront page in Specs 074–084 was greenfield. This lands the scaffold they all stand on and the backend reads they gate on. Frontend: a `commerce` module with the full route table (each page ships an on-pattern placeholder naming its implementing spec, so paths are stable from day one), a Commerce navigation section, and a new `NavItem.moduleId` gate — a runtime manifest that omits the module removes the whole subtree rather than leaving a menu of dead links, while an absent manifest still fails open. Hand-written DTO mirrors in `src/types/commerce.ts` carry a `CommercePagedResult` normalizer, because the Commerce paging envelope (`page`/`pageSize`) is not the app's (`pageNumber`/`totalPages`) and must never be cast across; three services follow the house `api.*` pattern; four shared components (`SignedAmount`, `MonthGrid`, `PriceCurve`, `UnderlineTabs`) keep their logic in pure, node-testable modules. Backend (all `AdminUserPolicy`, all read-only over what checkout already persists): the stored option narrowing preserving the null-vs-explicit `AllowedChoiceKeys` distinction the effective view loses (074); the raw content block with server-computed staleness plus a tenant-wide content-status list that also reports figure/declaration publication, since block existence is not publication (075); a status-agnostic size-plan read by product id, so a draft bundle's plan is visible to its author (076); extras-collection pricing state distinguishing an unpriced-but-servable member from a structurally ineligible one (078); and the storefront order/cart/party projections the spine's bill-payment-shaped reads cannot supply — aggregate versus add-on versus delivery lines, the kitchen landing, the charge envelope, and cart availability/price/personalisation drift computed at load and **never persisted**, because drift repair stays the customer load path's job (081/083). Commerce also gained batch reads (`GetEffectiveOptionsBatchAsync`, `ResolvePricesAsync`, a pure `RenormalizeStored`) so these list surfaces cost a constant number of queries rather than one round trip per row.
- **Commerce (payment status convergence)**: `OrderChargeSummary.PaymentStatus` was stamped once with the provider's at-creation intent status and never updated, so every completed checkout still read as pending to any consumer of the durable funding record. Payment completion now converges it to `Captured` — but only for the intent the checkout actually recorded, since Finance permits several payment intents per order and an unrelated capture (potentially a different amount or currency) must not mark this charge captured.
- **Commerce (Spec 072 — storefront customer identity)**: Connected the anonymous box-building session to the platform's existing customer identity — deliberately adding **no** new auth endpoints, because registration (`POST /v1/registrations/individual`), login (`POST /auth/token`), and password reset already exist and already produce a `User` + `Party` + `PersonalUser` role. What was missing was the seam: a new SharedKernel `ICurrentPartyResolver` (implemented in Platform off the latest `UserParty` link) lets Commerce honour an authenticated customer without referencing identity internals. Cart creation now binds `BuyerPartyId` from the principal automatically (body-supplied buyer ids stay rejected), and `POST /commerce/carts/{cartId}/adopt` migrates a guest cart to the signed-in customer: possession of the live guest token is required, adoption permanently retires that token (a leaked pre-login token is dead the moment the customer signs in), the operation is idempotent for the owning party, fails closed as 404 for a wrong token or a cart already bound to another party, and rejects carts that have already produced an order. `GET /commerce/storefront/orders` (+ `/{orderId}`) give the customer their own order history — summaries with box size and charge totals, detail with retail items and the kitchen-facing box selections — scoped at the query through the party's checked-out carts, so a foreign order id is a 404, never a 403 oracle. No schema change: every column (`Cart.BuyerPartyId`, `AnonymousToken`, `OrderId`) shipped with Spec 068.
- **Commerce (Spec 071 — box add-on lines)**: Activated the `AddOn` line kind Spec 068 reserved: ordinary retail products bought alongside the box at their own price — the deliberate exception to the storefront's no-standalone-dish-price rule — consuming no box space and adding no schema (every column shipped in 068's migration). `GET /commerce/catalog/extras` merchandises the configured collection (`Commerce.Storefront.ExtrasCollectionSlug`, default "extras") with retail prices in the tenant currency, resolved Spec 067 content and effective option groups in one read, counting unpriceable members as skipped rather than dropping them silently. `POST /commerce/carts/{id}/extras` adds AddOn lines under the box session's guest token: the retail price snapshot is mandatory (unpriceable rejects on add and flags unavailable when a price later vanishes), options price via Spec 066, identical lines merge, and the existing line routes serve quantity/personalisation/split/remove kind-aware — add-ons never touch capacity, fullness or slot bounds, while availability sums dish and add-on demand per variant so shared stock cannot oversell. The quote gains the `addOns` component (retail + adjustment + surcharge, per unit) exactly as the §7 component contract promised — additive, with the total still the component sum — and checkout materialises one ordinary retail order item per AddOn line (066 §12 envelope in DetailsJson when personalised), includes add-on goods in the discountable subtotal, invoices them by name and price, reserves their stock in the same hold, and keeps the kitchen's selection landing dishes-only.
- **Commerce (Spec 069 — fulfilment promise, phase 1)**: Added the per-tenant `FulfilmentCalendar` (delivery weekdays, order cutoff, optional weekly cycle day, preparation lead days, blackout dates, IANA timezone) and the deterministic earliest-delivery computation it drives — the single most-repeated data point on a make-to-order storefront, previously unrepresentable anywhere in Aonik. The computation is clock-injected and side-effect-free: both real-world cadences are modelled (a daily order book where the cutoff applies every day, and a weekly cycle where orders after one weekday's cutoff fall to the following week's close), exactly-at-cutoff still makes the current cycle, lead days roll to the first delivery weekday skipping blackouts, and DST gets an explicit first-mapping policy (spring-gap times map to the first valid instant after the gap, autumn-ambiguous times to their first occurrence) with comparisons on UTC instants so a clock rolling back can never reopen the order book. Unconfigured is a state, not an error: no calendar, inactive, no delivery days or an unresolvable timezone all mean "no promise" — the public `GET /commerce/config/delivery` returns 404 and never guesses, while a resolvable calendar serves the date with `Vary: X-Tenant-Id` and a five-minute public TTL. Admin GET/PUT validate everything at authoring (known IANA timezone, weekday names, lead 0–60, ISO blackout dates pruned of expired entries and bounded at 100 future dates so a validated request can never hit column truncation) and the upsert response echoes the newly computed promise so the operator sees the effect immediately. The food-commerce provisioning pack seeds a parked (inactive) calendar so the admin screen edits a row rather than creating from nothing; the tenant's real cadence is operator data. Includes the `AddCommerceFulfilmentCalendar` migration; phase 2 (address capture, chosen delivery dates, per-day capacity claims, zone fees) is scoped in the spec and deliberately not built here.
- **Commerce (Spec 068 — box-builder carts)**: The cart is now the box: a server-persisted, anonymous box-building session with size-parameterised bundle pricing, personalised line editing and an authoritative quote on every touch. A `BundleSizePlan` (+ merchandised `BundleSizePreset` price points that always win over the formula at their size) prices the container per size under a new `BundlePricingModes.SizeTiered`; growing a box always charges `boxPrice(target) − boxPrice(current)`, never per-space × spaces, because the marginal cost bends around discounted presets. Cart lines gained a `LineKind` discriminator (`BoxDish` live, `AddOn` reserved so capacity/merge/quote rules already state which kind they count), the filling slot, and the exact Spec 066 canonical personalisation with re-snapshotted pricing — identical `(kind, slot, variant, canonical selection)` lines merge, `applyToUnits` splits a line atomically, quantity 0 deletes and negatives reject, capacity is a hard ceiling with grow-as-the-only-path, and availability is checked as aggregate non-reserving cart-wide demand. Every load repairs catalogue drift via 066's stored-selection contract (retired choices remap and can merge lines, removed groups drop, unavailable dishes flag but never vanish — blocking continue and checkout until resolved) and returns the whole box + a component-list quote whose total is the sum of named components (`boxPrice`, `personalisation` — signed, `unitSurcharges`, `deliveryCharged`), so a future `addOns` component is additive. Capacity-affecting writes serialize on the Cart row's concurrency token (loser revalidates fresh, retries once, then 409s) — proven by a SQL Server lane race test. Checkout re-validates everything and stops with a 409 carrying the refreshed box on any drift (nothing reserved or created), then materialises ONE aggregate `ProductPurchase` order item at the goods total with a box envelope in `DetailsJson`, a dedicated `DeliveryFee` item when charged (dormant at the 0 default), a box-aggregate invoice, and per-line `OrderBundleSelection` rows carrying the canonical personalisation, its projections and the immutable §12 envelope — the kitchen-facing landing. Production planning now groups demand by `(variant, canonical personalisation)` with summary + label-snapshotted display on the production and kitchen sheets, so two differently-personalised preparations can never collapse into one line. Cart access is no longer id-possession: `CartAccessContext` at the service boundary (box, generic and checkout services alike) requires the server-minted 256-bit guest token (`X-Cart-Token`, disclosed exactly once at create; constant-time compare; legacy/weak stored tokens fail closed) or a matching party principal, with unknown and unauthorized identically 404; generic mutation routes reject box carts (400 → box routes), the missing generic remove-item route now exists, agent cart tools take a cart token, and idle box sessions transition to Abandoned via a daily sweep (`Commerce.Carts.AbandonAfterDays`, default 14) so a stale session cannot pin size-plan authoring forever. Includes the `AddCommerceBoxBuilderCarts` migration, the box-plan public read, the storefront-config box section, and admin size-plan authoring under rules A1–A6.
- **Commerce (Spec 067 — option-dependent product content)**: Added authored product content that changes with the customer's option selection and is never computed: a default "standard preparation" block per product (`ProductContent`) and variants per complete selection combination (`ProductContentVariant`), keyed by Spec 066's canonical selection via a fixed-length SHA-256 hash. Resolution is exact-match: an authored variant serves its own figures, declarations and heating; with no exact match the default figures serve captioned as the standard preparation while ingredients, allergens AND heating are withheld — declarations are exact-authored or absent, never substituted, and never dynamically inherited from the default block (the salmon variant can never surface the standard preparation's shellfish line). A default-combination change (recommended-default move or narrowing write) flags the block `RequiresReview` atomically with the change — variant matches keep serving, block-based resolutions arrive stale-flagged with declarations withheld — and the block's stored all-defaults binding makes the reaction self-verifying even if a hook is missed. Cross-row authoring invariants (a variant must publish every figure the default publishes; a default cannot add a figure active variants lack) are serialized on the content row's concurrency token with retry-once semantics, and every content write bumps `ContentVersion` — the public cache key: the resolution endpoint stamps `public, max-age=300` only when the caller's `v` equals the current version and `no-store` otherwise (future values included, killing pre-poisoned cache entries), with tenant-partitioned `Vary`. The public product DTO embeds the resolved standard preparation and version; admin endpoints cover the block upsert, an explicit confirm-review, variant authoring/retire (soft, revivable), and a coverage listing of single-choice authoring gaps. Includes the `AddCommerceProductContent` migration and a SQL Server lane test for the serialized write path.
- **Commerce (Spec 070 — storefront merchandising & configuration)**: Added everything the browse experience needs beyond raw catalog rows, all of it data rather than code. Curated `Collection`s carry ranked members (unique active ranks enforced by a filtered index; full-replace revives soft-deleted memberships; draft products stage invisibly and surface on activation). `FacetGroup` definitions declare their match semantics — Category (active-descendant closure), Tag, Attribute (dot-path into `AttributesJson`), and Range (half-open bands) — so adding, renaming or retiring a filter group needs no frontend change; browse combines facets OR-within/AND-across, rejects unknown keys and values loudly, and layers `collection=`/`sort=name|newest|rank` with rank as the curated default inside a collection. Products gain hidden `SearchKeywordsJson` matched by search but serialized into no public DTO (the admin read moves to a distinct `AdminProductDetailDto` so editors can see what they must not leak), and the browse row is enriched with hero image, parsed tags, attributes and unit surcharge — deliberately no retail price. A public category tree pairs with retire-don't-delete category authoring (`ProductCategory.IsActive`, cycle-checked re-parenting), and `GET /commerce/config/storefront` serves the single tunables document (canonical tenant currency, labels, page size, delivery display amounts, default box slug; never 404s) with `Vary: X-Tenant-Id` on every anonymous storefront read. Storefront settings write through a Commerce-owned `PUT /commerce/admin/storefront-config` backed by a new SharedKernel `ITenantSettingStore` — module-owned keys under module-appropriate policy, so an Operations user who can edit every product can also tune the storefront without holding platform Settings permissions. The missing product PATCH (partial update with strict JSON hygiene, also applied to create) and ordered-media full-replace round out the admin surface. Includes the `AddCommerceStorefrontMerchandising` migration.
- **Commerce (Spec 066 — configurable product option groups)**: Added a first-class option model for configurable catalog products, distinct from variants (discrete SKUs) and bundle slots (box composition). A tenant-level option catalogue (`OptionGroup` / `OptionChoice`) is narrowed per product (`ProductOptionGroup`) with an optional per-product default and selection mode, and `Product` gains a per-unit surcharge carried with its own currency. Selections are validated, canonicalised into a byte-stable form (object keys *and* multi-select arrays sorted, so equivalent submissions are string-identical and usable as a cart line-merge key), and priced as the difference from each group's recommended default — negative adjustments included. Two invariants are enforced by the database rather than service code alone: a filtered unique index makes a second active recommended default unrepresentable, and every unique index filters on `IsDeleted` so a soft-deleted row cannot occupy its key. Stored selections re-normalise with drift semantics (retired choices remap, withdrawn groups drop, selection-mode changes re-shape, and a group the product has gained since the cart was saved is reported rather than silently defaulted) so retiring an option can never make a live cart unloadable — and the re-normalised selection always matches the change report it arrives with. Public storefront endpoints expose the option catalogue and a pre-cart selection quote; admin endpoints cover authoring, an atomic recommended-default move that reports the products whose standard preparation just changed, per-product narrowing, and the surcharge. Includes the `AddCommerceProductOptionGroups` migration and the `Commerce.Storefront.RecommendedChoiceLabel` setting (default `"Recommended"` — product identity stays configuration per ADR-013). Also adds `aonik commerce options list|show|quote|verify` for checking a deployment from the command line; the CLI reads each group's selection mode and shapes values to the API's strict contract (arrays for multi-select, even one-element) so the wire shape is never the operator's problem. Admin update endpoints treat every omitted value-typed member as "leave unchanged" — an omitted flag or amount never falls to a destructive CLR default — and a newly added choice defaults to active. Concurrent writers that lose a guarded row-version race receive `409 concurrency_conflict` rather than a 500, and full replacements of a product's option narrowing serialize on the product row so disjoint concurrent replaces cannot merge.

### Security
- **MCP hosts (C4 — dev-only containment hardened)**: The Finance and Platform MCP servers register blanket-trust security stubs (grant-all `IPermissionService`, auto-clear `IComplianceService`, fixed PlatformAdmin identity) and are intentionally development-only. Hardened the existing fail-closed `DevelopmentOnlyHostGuard` containment rather than productionizing the servers: added a regression test pinning that each host's `Program.cs` invokes the guard before `.Build()` (`McpHostGuardWiringTests`), marked both host projects `<IsPublishable>false</IsPublishable>` so they cannot be published or containerized, and made `McpToolProvider` strip the `DOTNET_ENVIRONMENT`/`ASPNETCORE_ENVIRONMENT` selectors from spawned MCP children when the parent host is not Development, so a child can neither be handed nor inherit a forged `Development` environment. Resolves the C4 remaining-work item as accepted (dev-only).
